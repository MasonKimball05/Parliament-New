# v3.19.3 — What guards the file, what guards the header, what the chain costs

**Date:** 08-07-26
**Type:** Security + performance batch. **Migration: `0016_draft_document_privacy` (adds a column, alters a field, touches no file on disk).**
**Committed & pushed:** *not yet*
**Deployed:** *not deployed*

The 08-07-26 auto-run fix batch. That review had the largest diff any auto-run
has read — five releases in one day, ~6,200 lines — and **none of its findings
were bugs in that work.** v3.18.7's nine fixes are correct and two of them are
better than what the report suggested. What came out instead were three gaps of
a kind worth naming together: **a promise whose enforcement stopped one layer
short of the thing it was promising about.**

- v3.19.0 said a draft is private and scoped the *row*. The *file* was served by
  `/media/`, which is `@login_required` and cannot know who owns anything.
- v3.18.8 correctly fixed *which* IP everything records, and in doing so made
  the whole application depend on a header whose trustworthiness was asserted in
  a docstring rather than enforced anywhere.
- v3.18.7 built a budget test for the middleware chain because middleware cost
  hides inside every per-view ceiling. It counts queries. The chain's most
  expensive per-request operation is a cache write.

## 🟠 1. Draft attachments were readable by any authenticated member

`src/models/legislation.py`, `src/view/legislation_drafts.py`, `src/urls.py`,
both draft templates, migration `0016`.

The feature states its promise four times — module docstring (*"private to its
author until they publish it"*), model docstring, the success message the author
sees (*"Only you can see it until it is published"*), and the `notes` help text.
For the **row** that promise was kept properly: `_get_own_draft()` is the single
read path, it filters on `author=request.user`, and it 404s rather than 403s
because a 403 confirms the row exists.

The **file** was not covered by any of it:

```python
document = models.FileField(upload_to='legislation_drafts/', ...)   # → MEDIA_ROOT
```

```python
@login_required
def serve_media(request, path):     # view/serve_media.py — the entire gate
```

Any member — including a pledge — who requested `/media/legislation_drafts/<name>`
got the file. `serve_media` has no owner check and no way to add one: it
resolves a path on disk and knows nothing about which model owns it.

**And the name was guessable, because of a good fix.** `SanitizedFilenameMixin`
(v3.14.2) slugifies uploaded filenames at save time, deliberately, to kill a
class of header-escaping bugs. A side effect is that the stored name became
*deterministically derived from the name the author chose*. Django's random
7-character suffix only appears on a collision. So a draft uploaded as
`Dues Restructuring Amendment.docx` sat at
`/media/legislation_drafts/dues-restructuring-amendment.docx`. The sanitiser is
still right for what it was written for; it simply moved this file from
unguessable to guessable, and nothing else was protecting the path.

**Why this is worth more than "media permissions are coarse".** Everything else
under `/media/` is chapter-visible by intent — uploaded legislation, minutes and
profile pictures are all *meant* to be read by members, so `@login_required` is
the correct gate and the 07-18 fix that added it was sized correctly. **Drafts
are the first thing in this codebase stored there under a NARROWER promise than
"members may read this."** The gate did not get weaker. The content behind it got
more sensitive, and nobody re-derived whether the gate still matched.

**Fixed three ways, in decreasing order of what is load-bearing:**

1. **`serve_legislation_draft_document`** — the file's protection is now the
   same object as the row's. It goes through `_get_own_draft()`, so there is one
   access rule rather than two that have to agree. Templates link here;
   `draft.document.url` must never be rendered again. `Cache-Control: no-store`
   rather than `serve_media`'s `private, max-age=3600`, because a shared cache
   was never the risk — a private draft has no business in a browser cache on a
   shared library machine after the member logs out.
2. **`legislation_draft_upload_path`** — stores `legislation_drafts/<uuid>.<ext>`.
   ⚠️ **This is defence in depth, not the access control**, and the docstring
   says so in those words. A random path is not authorization and the next person
   to read this must not think it is. It removes the guessability the slugifier
   introduced, which matters for the case where a path leaks some other way — a
   copied link, a screenshot, a proxy log.
3. **Publish now COPIES the file out** instead of re-pointing at it. This used
   to be `legislation.document = draft.document`, leaving both rows sharing one
   path inside the private directory. That made `legislation_drafts/` mean two
   things at once and guaranteed that any future rule of the form "deny
   `legislation_drafts/`" would break published bills. The copy goes through
   `Legislation.document`'s own field, so it lands in `legislation_docs/` under
   the name the author actually uploaded — which is why `document_original_name`
   exists, since the stored name is now a uuid.

**`publish_legislation_draft` is now `transaction.atomic`.** Publishing used to
be one save; the copy makes it three writes, and a failure between them would
leave a published bill with no document and no draft linking to it — a bill on
the chapter ballot its author cannot find. The **file** write is not
transactional and cannot be: a rollback after the copy leaves an orphan in
`legislation_docs/`, which costs disk and nothing else. That is strictly the
better of the two failures, and it is why the copy sits inside the block.

**⚠️ The migration deliberately does NOT rename existing files.** `upload_to` is
consulted at save time only, so the twelve drafts that exist keep their
slugified names. That is safe *because the random name was never the access
control* — `serve_legislation_draft_document` applies to every draft from the
moment it deploys, old rows included. Renaming files inside a migration means
moving bytes in a transaction and leaving a half-migrated directory if it fails
partway, which is a materially worse trade. If you want them rotated, do it as a
separate management command after deploying, where a failure is re-runnable.

## 🟠 2. `CF-Connecting-IP` was trusted with no verification — and v3.18.8 made everything depend on it

`src/utils/security_utils.py`, new `src/utils/cloudflare_ranges.py`,
`Parliament/settings.py`, `src/management/commands/preflight.py`.

The old docstring said the header *"is set by Cloudflare and cannot be forged by
the visitor."* **That was not true as written.** `CF-Connecting-IP` is an
ordinary request header. Cloudflare overwrites it on requests that pass *through*
Cloudflare; on a request reaching the origin any other way — a stale A record,
the raw origin IP, an unproxied subdomain — whatever the client sent arrives.
The claim was true of the intended deployment and silently false of any request
that bypassed it.

`nginx.conf` establishes no such premise: it listens on `:80` with
`server_name _`, and has no `allow`/`deny`, no `set_real_ip_from`, no
`real_ip_header`.

**v3.18.8 did not introduce this — it changed what depends on it, which is why
it is being fixed now.** Before that release, five surfaces parsed
X-Forwarded-For inline and took the rightmost entry. That was *wrong* (it
recorded the Cloudflare edge, which is exactly the bug v3.18.8 correctly fixed)
but it was also **unforgeable**, because nginx appends the socket peer.
Consolidating onto `get_client_ip` fixed the fidelity problem and, in the same
move, put all of the following behind one client-supplied header:

| Consumer | What a forged header buys |
|---|---|
| `IPBlacklist` | Evasion — and v3.18.7 *just widened* this to cover `/admin/` |
| Both per-IP login limiters | A fresh bucket per attempt (the **username** bucket still binds) |
| Honeypot auto-ban | Evasion of the mechanism designed to catch scanners |
| `ActivityLog` / `LoginHistory` / `UserSession` | Audit rows attributed to a chosen address |
| `GeoRestrictionMiddleware` | The login-time lookup that gets stashed in the session |
| Lockdown whitelist suggestion | The value offered to an admin as "the IP to whitelist" |

That last row is the sharp one, and v3.18.8's own comment on that line already
says why: *"a whitelist that admits the attacker is worse than no lockdown at
all."* The reasoning is right and does not stop at the Cloudflare-edge case it
was written for.

**Fixed as an opt-in, and the default is OFF so this release changes no
behaviour on deploy:**

```python
CLOUDFLARE_VERIFY_ORIGIN = os.getenv('CLOUDFLARE_VERIFY_ORIGIN', 'False') == 'True'
```

With it on, `CF-Connecting-IP` is honoured only when the **socket peer** is a
published Cloudflare address — the peer being the one value in a request an
outside client cannot choose. A forged header from a direct connection is
ignored (the peer is used instead) and logged as `FORGED_CF_HEADER` at WARNING,
because that log line is the signal that the origin is exposed and nobody will
write a firewall rule without knowing.

⚠️ **The real fix is at the network layer and this setting is not a substitute
for it.** Firewalling `:80`/`:443` to Cloudflare's ranges, or nginx
`set_real_ip_from` + `real_ip_header CF-Connecting-IP`, fixes every consumer at
once — including ones nobody has written yet — and costs nothing per request.
This is the application-level backstop for when that is not in place.

**`src/utils/cloudflare_ranges.py` fails in the annoying direction, not the
dangerous one**, and that is stated in the module because it is what makes the
staleness tolerable: a range that is *missing* means traffic through that edge
stops being verified and falls back to rightmost-XFF — i.e. audit rows record
the edge again for that subset, the v3.18.8 symptom, visible and irritating. A
missing range can never cause a forgery to be trusted. Only a *wrongly present*
one could, and the only way that happens is someone pasting bad data in.

**There is deliberately no network fetch at import time**, and deliberately no
cron that rewrites the file. A security decision that depends on an outbound
HTTP call is a security decision that fails when the network does, and a job
that unattendedly rewrites a trusted allowlist is a supply-chain edge nobody
would be watching. `preflight` reports the age of `GENERATED` instead, so it
cannot rot silently.

**New `preflight` check** (`check_cloudflare_origin`) does what cannot be done
from inside Django: it sends `CF-Connecting-IP: 192.0.2.111` (TEST-NET-1, never
a real visitor) to `/login/` through `--live-url` and looks for a `CF-Ray`
header on the response. No `CF-Ray` → the request did not pass through
Cloudflare → **fail**. It also asserts the parsed range count matches the
declared one, so one malformed entry narrows verification loudly rather than
quietly. Where the probe genuinely cannot answer the question — it reached the
edge, but cannot tell whether the origin *also* answers on its raw IP — it says
so and warns, rather than implying a clean bill of health.

## 🟠 3. `PerformanceMiddleware` re-serialised the whole history on every request

`src/middleware/performance.py`, plus its three readers.

`PerformanceMiddleware` is **second in `MIDDLEWARE`**, ahead of
`SessionMiddleware`, and exempts only `/static/` and `/health/`. Every other
request ended in a read-modify-write of the entire buffer to append one tuple:

```python
entries = cache.get(CACHE_KEY)          # unpickle + zlib-decompress 500 entries
entries.append(entry)
cache.set(CACHE_KEY, entries, CACHE_TTL)  # re-pickle + re-compress all 500
```

**Measured** on the configured serialisation path (pickle protocol 4 +
django-redis' `ZlibCompressor`), 500 entries of the real tuple shape:

| | |
|---|---|
| pickled | 13,693 bytes |
| after zlib | 9,582 bytes |
| CPU, full round trip | **≈ 0.25 ms per request** |
| Redis traffic | **≈ 19 KB per request** |
| Redis round trips | **2 per request**, serialised, on the critical path |

Worth putting beside what v3.18.7 did: that release removed 2–4 DB queries per
request across three findings, correctly treated as worth fixing. This single
`cache.set` plausibly costs more wall-clock than any one of them, on every page,
every `/media/` download, every 404 and every scanner probe.

**And the instrument built that same release to find exactly this could not see
it.** `MiddlewareChainQueryBudgetTests` (v3.18.7, straight from the 08-06 idea)
measures a trivial-view request and attributes the remainder to chain overhead.
Its docstring states the reasoning correctly. But it counts **queries**, and
this is a **cache** cost — so it would have reported a clean, low, ratcheting
number on a chain whose single most expensive operation it was not watching.

> **THE RULE, and it is the transferable part: a per-request budget has to name
> its resource, and "queries" was never the only answer.** CLAUDE.md already
> records this shape twice — v3.18.5's miss was a *column* rather than a call
> site, which forced the generalisation once. A *resource* is the next widening
> of the same observation, and it is now four releases of "the rule was stated
> correctly and something was left outside the helper."

**Fixed by sampling, and the totals got *more* accurate rather than less:**

- Requests over `ALWAYS_STORE_ABOVE_MS` (1000 ms) are stored **unconditionally**.
  `slow_requests` and `get_slow_requests()` are unaffected — that is the data
  every N+1 hunt in this codebase has actually used, and sampling it would have
  broken the only thing this module is good for.
- Everything else is stored 1 in `SAMPLE_ONE_IN` (20). `random.randrange`, not a
  modulo counter: a counter aliases badly against periodic traffic (a beat task
  every 60 s landing in the same slot), and nothing needs the sample reproducible.
- `total_requests` now comes from `cache.incr`, so it is **exact** — and this is
  a correction, not just a preservation. It used to be `len(entries)`, capped at
  `MAX_STORED`, so it silently saturated at 500 and "requests last hour" was
  really "the last few minutes".
- The averages are now declared as estimates. `get_performance_summary()`
  returns `sampled`, `sample_rate` and `stored_samples` so a caller can label
  them instead of rendering an estimate as a measurement.

**Both readers were updated for the new meaning**, which matters because they
would otherwise have been wrong in a new way: `memory_report`'s "storing many
requests" recommendation compared `total_requests` to `MAX_STORED`, and with an
unbounded exact counter that would have fired permanently after the first few
hundred requests. It reads `stored_samples` now — the buffer size is what
`MAX_STORED` governs.

## 🟡 4. `LegislationDraft` is deliberately unregistered in `/admin/`, and now says so

`src/admin_extra.py`.

Registration in this codebase is explicit, so the new model was never registered
— which is the **right** default. `notes` is documented as *"Private notes. Never
copied to the published bill"* and `publish_legislation_draft` goes out of its
way not to copy it; a `LegislationDraftAdmin` would put every member's private
scratch space in front of any admin, and `export_as_csv` would dump it.

The problem was that this was indistinguishable from an oversight — and the
precedent is on the record. `CalendarSubscription` escaped v3.16.0's coverage
pass by accident, was later *decided* to stay out, and **has an explanatory
comment at the site so a future pass does not helpfully close the "gap."** The
seven unregistered Kai models have the same treatment at all three removal
sites. This one had neither, and v3.16.0's framing (*"registers all 82
previously-missing models"*) is exactly the kind of sweep that finds one.

Now commented beside the `CalendarSubscription` note, naming what any future
registration must exclude (`notes`, `document`) and that read-only is the right
default.

## 🟡 5. Single-lockout "Clear" matched username **OR** IP while reporting one IP

`src/utils/security_utils.py`, `src/view/admin_v2.py`.

`clear_lockouts_for` marked rows with `Q(username=…) | Q(ip_address=…)`, and
`manage_lockouts` passed **both** for a single-row clear — so clicking "clear" on
one lockout marked cleared every row sharing either value, then reported
`Lockout cleared for {ip}`.

The new `release_user_lockout` (v3.19.2) gets this exactly right and says why:

> *Deliberately NOT by IP: a member's lockout is on his account, and his
> last-known IP may be shared (campus NAT). Clearing an IP lockout because one
> member is locked out would release everyone behind that address, which is a
> different and much larger decision than the one this button says it makes.*

That reasoning applies verbatim to the call site one file over, which did the
thing it warns against. **Sixth consecutive release of the same shape** — a rule
stated correctly, a helper written to enforce it, one call site outside it — and
worth noting that it has now moved out of Kai redaction and into shared-helper
adoption. The shape has outlived the subsystem it was first observed in.

Fixed with an explicit `match='any'|'all'` argument, defaulting to `'any'`
because that is what the existing callers were already doing and a silent
behaviour change for callers that did not opt in would be worse than the bug.
The two single-row sites pass `match='all'`; **the bulk "clear all" site keeps
`'any'` deliberately**, with a comment saying so, because widening past the row
is the intent there. The cache keys are still cleared for whatever is passed
regardless of `match` — clearing a stale counter is harmless, and clearing too
few is the failure this helper exists to fix.

## 🟡 7. Three budget classes with no measured ceiling, now tracked in the file

`src/test_query_budgets.py`.

08-06 named two (`TwoFactorDashboardQueryBudgetTests`,
`ServiceDashboardQueryBudgetTests`); v3.18.7 added a third
(`MiddlewareChainQueryBudgetTests`) for the same stated and correct reason — a
ceiling is a *measured* number and there was no working Django to measure with,
and an invented ceiling reads exactly like a measured one.

Three is where the exception starts looking like the convention. Added
`BudgetHygieneTests.AWAITING_MEASUREMENT` plus a test that keeps it honest **in
both directions**: a class that has since gained a `BUDGET` must come off the
list, and a budget class with none must be on it. It deliberately does not fail
merely because the list is non-empty — the exemptions are legitimate; what must
not happen is their becoming invisible. A to-do list allowed to drift stops being
read the first time someone finds a stale entry on it.

⚠️ **Measure all three AFTER deploying v3.18.7, and re-measure every existing
`BUDGET` in the same pass.** v3.18.7 removes 2–4 queries from every page in the
suite, which will push every current ceiling more than `STALENESS_SLACK` out of
date and correctly fail the ratchet. One pass, not two, or the suite is red in
between for a reason nobody will remember.

## Tests

**4 new tests** in `src/test_middleware_hot_path.py`
(`PerformanceMetricWriteCostTests`) and **1** in `test_query_budgets.py`.

The performance ones assert the write *pattern* rather than a byte count,
because a byte ceiling would be measuring the compressor. They force
`random.randrange` rather than running many requests and hoping — a flaky
assertion about a random draw is worse than no assertion. Two of them fail
against the pre-v3.19.3 tree by construction (every call used to write).

⚠️ **NOT EXECUTED.** Same environment limitation as every batch since 08-03: the
repo `.venv` is a macOS interpreter that will not run in the review sandbox.
What *was* verified here, mechanically:

- `py_compile` clean on all 16 changed Python files.
- `cloudflare_ranges` parses 22/22 and classifies correctly — `172.68.1.1`,
  `104.16.0.5`, `141.101.90.1`, `2606:4700::1` inside; `8.8.8.8` and
  `192.0.2.111` outside.
- The sampling predicate, simulated over 200,000 draws: **0.0503** keep rate
  against a 0.05 target, and slow requests kept at every draw value.
- The `match='all'` / `match='any'` Q-algebra, including that an empty `Q()`
  stays falsy under `&` as well as `|` — so a call with neither value supplied
  still touches no rows.

**This is now the fifth consecutive batch shipping with unrun tests.** The
previous four were green when finally run, which is reassuring about the code
and says nothing about the habit.

## Deploy

**Deploys on top of the v3.18.7 → v3.19.2 backlog, which is still unshipped.**
Do that batch's steps first — this release does not replace them.

1. `git pull origin main`
2. **`python manage.py migrate`** — `0016` after `0014` and `0015`. Adds a
   column and alters `upload_to`; **touches no file on disk**, so it is fast and
   trivially reversible.
3. Everything else from the pending batch: `seed_feature_flags`,
   `seed_cnb_documents`, `setup_celery_schedules`, restart worker/beat.
4. Restart `parliament-gunicorn.service` (Daphne/ASGI).
5. **No static asset changes** → no `collectstatic`, no Cloudflare purge.
6. **`python manage.py preflight --live-url https://am-parliament.org`** — the
   new `check_cloudflare_origin` is the reason to run it this time.

**Verify, in priority order:**

- **Draft privacy.** Log in as a member who does not own a draft and request its
  document URL — expect **404**, not 403. Then confirm the author can open their
  own from both My Work and the edit page.
- **Publish still works end to end**, and the published bill's document
  downloads under a readable filename rather than a uuid.
- **`preflight`'s Cloudflare check.** If it *fails*, the origin is directly
  reachable — that is the finding, and the fix is a firewall rule, not this
  setting. If it warns, it means the probe reached the edge but cannot rule out
  the origin answering on its raw IP.
- **Only then consider `CLOUDFLARE_VERIFY_ORIGIN=True`.** ⚠️ **Watch the
  security log for `FORGED_CF_HEADER` afterwards.** If it appears in volume with
  addresses that look like real members, the range table is stale rather than
  under attack — refresh it from `cloudflare.com/ips-v4` and `/ips-v6`.
- **Performance dashboard.** `total_requests` should now climb past 500 (it
  could not before). The slow-request list should look unchanged.

**Not a deploy step, but the reason to do the whole batch soon:** five releases
are pending and two were missing from the ledger. Reconcile `DEPLOYED.md` at the
moment it ships, not after.
