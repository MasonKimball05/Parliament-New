**Migration:** `0027_announcement_view_target_snapshot` — adds two fields
(`Announcement.target_audience_snapshot`, `UserAnnouncementView.
counted_in_target`) plus a best-effort data backfill. Safe on a live DB
(additive columns, backfill only writes to the new columns).

Requested by Mason: the announcement view-rate stat was showing impossible
numbers (e.g. "5 of 0 members, 500%") for an announcement originally
targeted at a pledge class that has since fully initiated.

## The bug

`Announcement.get_view_stats()` computed its denominator by re-running
`ParliamentUser.objects.filter(member_status='Active', member_type__in=...)`
against the **current** roster on every call. For an announcement
`visible_to=['Pledge']`, once every pledge it was sent to has initiated (and
no new pledges have joined since), that query now returns close to zero —
even though the announcement was genuinely seen by everyone it targeted at
the time.

Separately, the numerator had no `member_status` check at all: any
logged-in user whose `member_type` happened to match `visible_to` could
generate a counted "site view" regardless of whether they were `Active`.
Alumni who still have working logins (they don't receive chapter email, so
their only way to see an announcement is browsing the site) could inflate
the count for an audience they were never part of.

## Fix

`Announcement.target_audience_snapshot` (JSONField, list of user ids) is
frozen once — the first time anything needs to know the audience after the
announcement is actually published (a real member viewing it, or an
officer opening its stats) — via `ensure_target_audience_snapshot()`
/ the batched `ensure_target_audience_snapshots()`. Once frozen it never
changes, regardless of later roster churn. `get_view_stats()`'s denominator
is now `len(target_audience_snapshot)` instead of a live recount.

The numerator is fixed the same way, from the same snapshot:
`UserAnnouncementView.counted_in_target` is decided once, at creation time,
from `Announcement.is_in_target_audience(user)` (i.e. "was this user in the
frozen snapshot"). All four places a `UserAnnouncementView` gets created
(`view/announcements.py`'s site-view tracking, `notifications.py`'s
dismiss handler, `view/notifications.py`'s bell-dismiss handler,
`view/officer/manage_announcements.py`'s email-open pixel) now set it
explicitly. `annotate_view_stats()` (the batched query the announcements
list page uses) filters its three `Count()`s on `counted_in_target=True` —
a plain boolean column, so this stays the one-query-per-page shape v3.17.4
built rather than needing a per-row correlated subquery against each
announcement's own snapshot.

Numerator and denominator now being drawn from the same frozen set also
structurally bounds `view_rate` to ≤100% — not a clamp, it falls out of the
math (`unique_together` caps one view per user per announcement, and a
counted view can only come from someone already in the snapshot).

**Performance, caught by `test_url_smoke`'s N+1 sweep before it shipped:**
freezing snapshots one-at-a-time in a loop over a page of announcements
(what the first draft did) reintroduces the exact N+1
`active_counts_by_member_type()`/`annotate_view_stats()` were built to
eliminate in v3.17.4, one field over. Fixed with a batched
`Announcement.ensure_target_audience_snapshots(list_of_them)` — one query
for the roster, one `bulk_update` for however many rows actually need
freezing — called once per page load (`manage_announcements`,
`announcements_view`) before the per-row `get_view_stats()`/view-creation
calls, so those become true no-ops once the page-level batch has run.

## Known, accepted limitation

The migration's backfill (for announcements published before this field
existed) can only snapshot against the **current** roster — there's no
historical record of who held which member_type on the date each
announcement actually posted. That fixes the display for most existing
announcements. For the one that motivated this fix specifically — a pledge
class that's fully initiated with no new pledges since — the true original
audience is genuinely unrecoverable, and the backfill will (correctly, if
unhelpfully) compute zero rather than reproduce the impossible percentage.
Going forward every announcement gets an accurate snapshot.
