## The one-paragraph version

v3.23.0 is a good release. It found that initiation was moving a primary key
that 150 foreign-key columns hold a copy of, established that `role_number` had
been the right home for the roll number the whole time, deleted ~190 lines of
raw SQL, and wrote a structural test to keep the property.

**Every finding here is a place that property was not carried to.** The rule is
right; three readers of it were left outside. And the sharpest one was not a
reader at all — it was a **red button in the Django admin, on every row of the
member list, that still moved the primary key**, using the same technique
v3.23.0 deleted and with the same defects. That is the eleventh instance of the
shape CLAUDE.md records, and the first where the thing left outside the rule was
a *user-facing feature that did the forbidden operation on purpose*. It is now
deleted, and the guard that could not see it has been replaced with one that
can.

## 1 — 🟠 The admin had a button that moved the primary key. **FIXED — deleted.**

`src/admin.py:333`, `migrate_user_id_view`, routed at
`/admin/src/parliamentuser/migrate-user-id/<str:user_id>/` and rendered by
`login_as_link`, which is in `ParliamentUserAdmin.list_display` — so it is a red
button captioned **Migrate User ID** beside *Login As User* on every row of the
member list.

It does exactly what initiation used to do: temporarily blank the unique
columns, construct a second `ParliamentUser` with the new key, walk
`_meta.get_fields()` repointing relations, then `old_user.delete()`.

**Reproduced end to end** against this tree, through the real endpoint, as an
admin:

```
PROBE built reverse-o2o rows -> ['two_factor_requirement']
PROBE migrate POST           -> 302
PROBE new row exists         -> True
PROBE old row still exists   -> False
PROBE two_factor_requirement   survived -> False
```

Three separate defects, all of them ones the v3.23.0 changelog names in the code
it deleted:

* **Every reverse OneToOne is silently destroyed.** For a reverse OneToOne,
  `getattr(old_user, accessor)` returns the related *object*, not a manager, so
  `.all().update(...)` raises `AttributeError` — into `except Exception: pass`.
  The row is never repointed, and four lines later `old_user.delete()` CASCADEs
  it away. `preferences` is skipped explicitly and handled; **`two_factor_
  requirement`, `watch_flag` and `calendar_subscription` are not.**
  `TwoFactorRequirement` is the per-member override on the global 2FA policy,
  read by `Enforce2FAMiddleware` — losing a `required` row is a **silent
  security downgrade**, and losing `UserWatchFlag` silently clears a
  security-monitoring flag on the member being watched.
* **21 of 45 concrete fields are not copied**, because the new row is built from
  a hand-written kwarg list: `big_brother`, `pledge_class`,
  `pledge_class_greek`, `graduation_year`, `graduation_semester`, `about_me`,
  `majors`, `minors`, `concentrations`, `house`, `initiation_chapters`,
  `onboarding_complete`, `onboarding_data`, `backup_codes_acknowledged`,
  `other_email` and all six socials. Every one silently resets to its default.
* **No CASCADE verification before the delete.** The code v3.23.0 removed at
  least *checked* six tables before deleting the original. This one does not, and
  the swallowing loop above means a failed repoint is indistinguishable from no
  rows to repoint.

**And `src/test_user_id_is_permanent.py` cannot see it.** Its regex is
`^\s*(?:\w+\.)?(?:user|member|pledge)\.user_id\s*=\s*(?!=)` — attribute
assignment. `admin.py:387` writes `user_id=new_user_id` as a **constructor
kwarg**. Verified:

```
PROBE guard sees admin.py:387 -> False
```

> ⚠️ **A GUARD WRITTEN AGAINST ONE SYNTAX IS A GUARD AGAINST ONE SYNTAX.** The
> module's docstring says it "fails the build if any code outside creation
> assigns to this field", and CLAUDE.md will record the same sentence. The
> honest statement is narrower: it catches `x.user_id = y` where `x` is spelled
> `user`, `member` or `pledge`. A kwarg, an `update(user_id=…)`, a
> `setattr`, or a variable named `brother` all pass.
>
> Note this is *not* the same complaint as v3.21.7's "a walk that cannot fail".
> That check could never go red. This one can, and does its job — it simply
> describes a smaller population than its docstring claims, and **the operation
> the release exists to abolish lives in the gap.**

### Fixed — deleted

**The view, the route, the button and `templates/admin/migrate_user_id.html` are
gone** (129 lines of view, 138 of template). The alternatives were to rewrite it
properly or to keep it for typo repair and refuse once the member has related
rows; both lose to deletion, because **there is no longer anything for it to
do.** `user_id` is an opaque surrogate key that no human reads, and
`role_number` — unique, freely editable, rendered by 32 templates — carries
everything a member is actually called. Changing what somebody is called is a
`role_number` edit, and the admin change form already offers it.

An explanatory comment sits at the removal site. If a future reader finds
`login_as_link` rendering one button where the git history shows two, that
comment is why.

### And the guard that could not see it was replaced

`src/test_user_id_is_permanent.py`'s scan is now an **AST walk with four
detectors**, because there are four ways to write this field:

| | spelling | precision |
|---|---|---|
| (a) | `member.user_id = x` | leans on a named-variable list, stated in the failure message |
| (b) | `ParliamentUser(user_id=x)`, `create_user(...)` | exact — keys off the call |
| (c) | `.update(user_id=x)` on a `ParliamentUser` queryset | exact |
| (d) | `setattr(member, 'user_id', x)` | exact |

⚠️ **The creation allowlist is keyed on `(file, enclosing function)`, not on the
file, and that is load-bearing.** `src/view/officer/manage_members.py`
legitimately creates members in `add_member` and `_import_member_row` — and it
is also where `initiate_pledges` lives, the function whose key-moving raw SQL
v3.23.0 deleted. Exempting the file would have re-opened the exact hole the
module exists to close. `_CREATION_SITES` is a ratchet: six entries, each with a
reason, and adding one shows up in a diff.

Plus `TheAdminCannotMoveAPrimaryKeyTests`, which catches the *route* returning by
any other means — including a control asserting the Actions column still renders
*Login As User*, since "the button is absent" passes trivially if the whole
column stopped rendering.

**Negative control: 4 of the 19 tests in this module fail against the
pre-deletion tree**, and the one that matters reports exactly what the old regex
could not see:

```
FAIL: test_no_module_writes_a_members_user_id
  src/admin.py:386  [construction] ParliamentUser(user_id=…)
FAIL: test_the_migrate_user_id_route_is_gone          NoReverseMatch not raised
FAIL: test_the_member_list_offers_no_key_moving_action
FAIL: test_the_actions_column_still_offers_login_as   'Migrate' unexpectedly found
```

⚠️ **A sweep afterwards confirms the defect class is gone, not just the
instance:** `grep` for `get_accessor_name` / `_meta.get_fields()` relation walks
across `src/` now returns **nothing**, and `information_schema` / `_migrating_`
survive only in comments explaining why they used to be there (plus one
`InputSanitizationMiddleware` pattern that *detects* schema probing, which is
correct). Both copy-then-delete implementations this codebase had are now
deleted — v3.23.0 removed one, this removes the other.

## 2 — 🟡 `_parse_remember_cookie` was left outside v3.23.0's own fix. **FIXED.**

v3.23.0 correctly found that `Enforce2FAMiddleware._check_remember_cookie` did
`int(user_pk)` against a CharField pk, so "remember this device" had never
worked for a pledge. It fixed that **inline copy** of the parse.

The same cookie has a **named helper** — `src/view/two_factor.py::_parse_
remember_cookie`, sitting three lines below `_make_remember_cookie_value`, which
writes the value the helper reads. It still returned `int(user_pk)`. Measured:

```
PROBE remember-cookie helper -> ValueError: invalid literal for int()
                                with base 10: 'P-TKJ3R3'
PROBE middleware copy        -> compares as strings (fixed)
```

Its one caller is `profile_view`, which catches `ValueError` and reports the
device as not remembered. So v3.23.0 did not merely miss half the fix — **it
made the two halves disagree.** Before, both were consistently broken for
non-numeric ids. Now the middleware honours the cookie and the profile page
tells the member no device is remembered, which is worse than either, because a
member reading that page will try to fix something that is not broken.

Fixed: the helper returns `(str(user_pk), int(device_pk))` and `profile_view`
compares as strings. `device_pk` deliberately stays an `int` — `TOTPDevice.pk`
really is an AutoField, and being explicit about which pk is which is the whole
lesson.

## 4 — 🟠 `/my-attendance/` costs a query per event, and v3.22.0 put it on every member's home page. **FIXED.**

v3.22.0's finding was right and its fix was right: a 224-line personal
attendance dashboard was linked from nowhere, and a feature nobody can reach is
indistinguishable from one that was never built. It linked the page from both
home layouts and the My Excuses header.

Nothing asked what the page costs. Measured through real requests with
`CaptureQueriesContext`:

```
                                        before      after
events= 40, range=90 (default)         116          25
events=120, range=0  ("All time")      349          25
```

The dominant cost was the history loop, two queries per event, both of them
avoidable:

```python
for event in events:
    record = my_attendance_records.filter(event=event).first()      # N
    excuse = AttendanceExcuse.objects.filter(event=event, ...).first()  # N
```

— and the attendance half was re-reading rows the view had already fetched
twelve lines above. Around it sat **five separate `COUNT(*)`s** for the personal
stats and two more for the chapter average, each re-sending one bind parameter
per event, and a per-series loop costing three more queries per recurring
parent.

Now: one evaluation of the records the loop needs anyway (counted in Python),
one conditional aggregate for the chapter average, one query for the excuses,
and two for all series. **Flat in the number of events.**

> ⚠️ **A PAGE'S QUERY COUNT STARTS MATTERING ON THE DAY SOMEBODY CAN CLICK IT.**
> This cost was there the whole time and was harmless the whole time, because
> reaching the page meant typing its URL. Promoting an unreachable page to the
> home page of every member **is a performance change**, and the two halves of
> that thought were one release apart. Worth asking on any future
> reachability fix: what does the page I just connected cost?
>
> And `test_query_budgets.py` could not have caught it — that module's own
> docstring concedes it constrains only the pages someone remembered to add,
> which is the same limitation v3.18.6 recorded when prod dev mode, not the
> suite, found two N+1 dashboards.

New `src/test_my_attendance_budget.py`, 8 tests. **Honest control accounting:
2 of the 8 fail against the pre-fix view** (`83 not less than or equal to 44`
and `97 not less than or equal to 78`). The other 6 pin the arithmetic that
moved out of the database into Python and pass on both trees by design — a
query-count test cannot see a wrong answer, which is v3.18.6's lesson about the
missing `.order_by()` on a grouped aggregate. One of the six is specifically
that another member's excuse must not appear on this page: if the `user=` half
of the excuse lookup were ever dropped while batching, **the query count would
look better, not worse.**

⚠️ **The per-series filters are deliberately NOT the ones used for the history
list** — a series instance counts whether or not it is `is_active` or
individually `requires_attendance`; only the parent is tested. That is what the
old code did. Restating it would silently change every member's per-series
percentage, which is a different change from making the page fast.

## 5 — 🟡 v3.23.0's backfill assertion could not fail. **FIXED.**

`test_the_backfill_left_no_brother_without_one` queried for non-pledges with a
null `role_number` and asserted the list was empty, under a comment conceding
*"an empty test database legitimately has none of either"*. Migrations run
before any test does, against an empty database, and that class creates no
members — so it returned `[]` regardless of what migration `0021` contained.
Neutralising the migration's body left it green.

Replaced with two tests that run `backfill_role_numbers` against a dataset built
to hit every branch it has: a blank that should be filled, an existing value
that must not be overwritten, a **pledge** who must not be given a roll number
he has not earned, and the **collision** case, where a member's key is already
somebody else's roll number and the migration must refuse rather than invent —
because a missing roll number renders as nothing and a wrong one renders as
another man's number. Plus an idempotence test, since a migration can be re-run
during a restore. **Both fail against a neutralised migration**
(`None != '173'`, `None != '201'`); the old one did not.

The migration's deploy-time `print()` is now captured in the test rather than
printed into the suite — v3.21.4's rule, since that print is right on a terminal
somebody is watching at deploy time and wrong behind 1,629 dots.

> ⚠️ Same question as v3.21.7 asked of v3.21.6, one release later and one
> directory over: **before trusting a check, ask what would have to be true for
> it to go red.** Here the answer was "nothing at all".
