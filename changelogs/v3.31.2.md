## 💡 Device/browser info was already captured on every bug report — it was just never shown anywhere Mason looks

`BugReport.browser_info` (the raw `navigator.userAgent` string, set
client-side via a hidden form field) has existed for a while and was already
included in the submission-notification email. But it was never rendered on
`bug_report_detail.html` or `bug_admin.html` — the two pages Mason actually
opens to triage a report — and a raw user-agent string like `Mozilla/5.0
(iPhone; CPU iPhone OS 17_0 like Mac OS X) AppleWebKit/605.1.15 …` isn't
something anyone reads at a glance to answer "was this a phone?"

### What changed

- **`src/view/bug_report.py`** — `submit_bug_report` now parses
  `device_type`, `browser`, and `operating_system` server-side from the
  request's real `HTTP_USER_AGENT` header, via
  `UserSession.parse_user_agent()` — the same parser the "Active Sessions"
  feature already uses, reused rather than duplicated a third time alongside
  `security_utils.parse_device_info()` (which wraps the separate
  `user-agents` PyPI package). Parsing server-side means it's captured even
  if the client-side JS never ran (JS disabled, the form auto-submitted
  before `onload`, etc.) — independent of the existing `browser_info` hidden
  field's timing.
- **`src/models/security.py`** — three new fields on `BugReport`:
  `device_type`, `browser`, `operating_system`.
- **Migration `0039`** — adds the three columns, then a `RunPython` step
  backfilling them for every existing report from its already-stored
  `browser_info`, following this codebase's own convention (see
  `0021_backfill_role_numbers`) of filling new columns for historical rows
  when the source data already exists rather than leaving them blank.
  Skips rows with no `browser_info` to backfill from (nothing was ever
  captured) and rows already filled (idempotent — safe to re-run).
- **`templates/bug_report_detail.html`** — a device/browser line in the
  "Meta Info" strip near the top, plus a fuller "Device & Browser" line and
  the raw user agent string in the "Location Details" card.
- **`templates/bug_admin.html`** — the same summary line on each report card
  in Mason's admin queue, plus a new **Device** filter dropdown alongside
  the existing Status/Type/Priority filters — built from the distinct
  `device_type` values actually on file (not a hardcoded list), so it can't
  silently omit a value or offer a phantom one.
- **`templates/emails/bug_report_notification.html`** — the submission
  email now shows parsed Device/Browser/OS rows ahead of the raw user-agent
  string, instead of only the raw string.
- Deliberately **not** touched: `bug_tracker.html` (the public list every
  member can see) and `my_bug_reports.html` (a member's own submissions) —
  device/browser detail is diagnostic information for triage, not something
  the general membership needs on a public status page. Easy to add later
  if wanted.

### A real, pre-existing bug found while verifying this

`UserSession.parse_user_agent()` (`src/models/users.py`) checked
`'mac os x' in ua_lower` **before** `'iphone'`/`'ipad'` — and every iOS and
iPadOS Safari user-agent string contains the literal substring `"like Mac OS
X"` (Apple's own compatibility token for exactly this kind of sniffing). So
the `'iphone'`/`'ipad'` branches were dead code, and **every phone and
tablet has been reported as "macOS"** for as long as this parser has
existed — including everywhere else it's used, i.e. the "Active Sessions"
page. Caught immediately: the very first test report submitted with a real
iPhone user agent came back `operating_system == 'macOS'`, which would have
quietly defeated the entire point of this feature — knowing at a glance
whether a report came from a phone. Fixed by reordering the checks
(`iphone`/`ipad` before the bare `mac os x` test); no other branch was
affected. In scope here because it directly undermines the accuracy of the
feature this release adds, not a tangential finding.
