# v3.15.2 — Celery schedule orphan reconciliation

Diagnosed 07-19 from the daily digest's own `[HIGH] Task 'Prune old auth
tokens' … last ran 2026-07-01 — Beat may be down` finding — a **false alarm**.

## Root cause

`Prune old auth tokens` (→ `tasks.prune_old_auth_tokens`) is a v3.5.0-era
`PeriodicTask` row whose task function was removed from the code long ago, but
the DB row was never deleted. It ran once (07-01), then — with no registered
task behind it — froze, and now trips the digest's beat-health check every day.
Beat itself is healthy: the prod schedule dump shows every live task running on
time (vote auto-close runs=2870, digest ran 09:30, etc.).

`setup_celery_schedules` was **create-only**: it `get_or_create`s the rows it
manages and never looks at anything else, so dead rows accumulate. Prod also
carries a second one — `Send daily honeypot digest` (→
`tasks.send_daily_honeypot_digest`): honeypot output is now folded into the
main daily digest and only a `send_honeypot_digest` *management command*
remains, so that Celery task no longer exists in code. It ran on old prod code
until today; after the v3.15.x deploy it's a dead orphan too.

Not orphans (verified, left alone): `Prune stale push subscriptions` and
`Prune API access logs` show `last run: NEVER` only because they're monthly
(`day_of_month=1`) and were re-seeded ~07-18 — they first fire Aug 1.

## Fix

`setup_celery_schedules` now reconciles after seeding:

- Flags every `PeriodicTask` whose `task` path is **not a registered Celery
  task** in the deployed code — the precise definition of a dead row. This is
  keyed on registration, NOT the managed `SCHEDULES` set, so a valid task
  seeded elsewhere (e.g. the honeypot digest *when it existed*) is never
  wrongly flagged.
- Populates the registry first via `loader.import_default_modules()` (a
  management command isn't a worker), and has a **safety fuse**: if a sentinel
  managed task (`tasks.send_daily_digest`) isn't registered, the registry
  didn't load — the command reports nothing and touches nothing rather than
  risk deleting live schedules on a false negative.
- New `--prune-orphans` flag deletes the flagged rows. Default is report-only.

Retires the recurring manual "delete the stale PeriodicTask row on prod" deploy
step (weekly-digest row in `v3.12.1.md`, now this) — one command handles all.

## Remediation (prod, AFTER deploying v3.15.x)

1. `python manage.py setup_celery_schedules` — review the orphan list. Expect
   **`Prune old auth tokens`** and **`Send daily honeypot digest`**.
2. Both are safe to drop: auth-token/log hygiene is covered by the managed
   cleanup tasks; honeypot content is in the 09:30 digest. (Only caveat: you
   lose the separate 07:00 honeypot email — the data still arrives at 09:30. If
   you want the standalone 07:00 report back, wire the `send_honeypot_digest`
   management command to cron instead.)
3. `python manage.py setup_celery_schedules --prune-orphans` to delete them.
4. The HIGH digest finding clears the next morning.

## Verify

- Tested: report-only lists dead rows and leaves them; `--prune-orphans`
  deletes only rows whose task is unregistered and preserves valid/managed
  rows; sentinel fuse aborts cleanly if the registry isn't loaded. `check`
  clean; no migration.
