## A tied committee plurality vote no longer passes (and an empty chapter one)

Four committee paths decided a plurality result with `passed = max_votes > 0`,
so any tie with at least one vote was saved as **passed** (status `passed`):

- `tasks.auto_open_close_committee_votes` (the scheduled close),
- the committee vote page's **End vote**,
- the committee vote page's **Recalculate**,
- `recalculate_committee_vote`.

Everything else already required one clear winner:
`CommitteeLegislation.set_passed()` (used by `auto_close_votes`), the chapter
task and chapter `end_vote` (v3.14.0, "a tie used to pass here"). The committee
result page itself shows the tie and offers a runoff, while the status said
passed.

- New `src/vote_rules.py::plurality_passed(counts)`: passes only when the top
  count is above 0 and only one option has it. All four committee paths use it.
- **Chapter `end_vote` had the opposite edge:** its tie check also required
  `max > 0`, so a plurality vote ended with **no ballots** was "no tie", and
  the first option won (`passed=True`, status `passed`). The scheduled chapter
  close was already right. `end_vote` now uses the same helper. This matters
  more since v3.51.0: `assign_appointment` now trusts `passed`, so an
  appointment vote ended before anyone voted would have been assignable.
- Not changed: votes already closed on a tie keep `passed=True` until a chair
  presses Recalculate. Find them with:

      from src.models import CommitteeLegislation
      from src.view.committee.vote import get_vote_tally
      from src.vote_rules import plurality_passed
      [l.pk for l in CommitteeLegislation.objects.filter(vote_mode='plurality', voting_closed=True, passed=True)
       if not plurality_passed(get_vote_tally(l))]
