# v3.15.4 — auth/authz hardening (from the 07-22 security sweep)

A deep sweep of the authentication / session / authorization surface (07-22-26)
turned up four items. Three are fixed here; the fourth was dispositioned as
by-design. No migration — all code-only.

## A. 2FA middleware: narrow the `/api/` exemption → `/api/v1/` (partial 2FA bypass)

`src/middleware/two_factor.py`

`Enforce2FAMiddleware` exempted the **broad `/api/` prefix** ("API endpoints
handle auth separately"). That's true for the token-authenticated DRF app at
`/api/v1/`, but **dozens of session-cookie-authenticated AJAX endpoints also
live under `/api/…`** — `/api/roles/`, `/api/notifications/`, `/api/committee/…/chat/…`,
`/api/channel/…`, `/api/slating/…`, `/api/service-hours/adjustment/…`,
`/api/debug/*` (cache-clear, flag-toggle, session-edit), and `/api/token/request`
(which can **mint an API token**). Exempting all of `/api/` meant a session that
passed the password step but **not** the TOTP verify step could still reach
them — partially defeating the verify-step enforcement (the v3.13.2/v3.5.1
hardening that protects any device-holder regardless of policy). Worst case: a
password-only session mints an API token and escalates to full token access.

**Fix:** the exempt list now carries `/api/v1/` (token API, incl. the honeypot
`/api/v1/users/export/`) and `/api/health-check/` (liveness probe) instead of the
bare `/api/`. Every session-auth `/api/…` endpoint is now subject to the same
2FA enforcement as the rest of the app. No user-facing change for anyone who has
completed 2FA; a required-but-unverified session is now correctly redirected to
setup/verify on these paths.

**Tests:** `src/test_two_factor.py` — `test_session_api_endpoints_no_longer_exempt_from_2fa`
(asserts `/api/roles/`, `/api/service-hours/adjustment/add/`, `/api/notifications/`,
`/api/debug/cache/clear/`, `/api/token/request/` → 302 setup under `all_members`)
and `test_token_api_v1_and_health_still_exempt` (asserts `/api/v1/…` and
`/api/health-check/` still pass). Exemption prefix-matching verified in isolation.

## B. `manage_chapter_document`: scope delete/edit to the document's committee

`src/view/manage_chapter_document.py`

The view is `@officer_required` (officers, **all** chairs, admins) and fetched
the document by id with no committee scoping. The committee-*reassignment*
branch was permission-checked, but **`delete` and the metadata/publish update
were not** — so any officer/chair could delete or edit **another committee's**
document by supplying its `doc_id`.

**Fix:** a single authorization guard after the fetch (covers GET render + POST
mutations): admins pass; a committee-owned document requires
`document.committee.is_chair(request.user)`; chapter-level documents (no
committee) remain manageable by any officer (unchanged behavior). Otherwise 403.

## C. `vpp_required`: remove the `DEBUG` bypass (authz must not depend on DEBUG)

`src/decorators.py`

`vpp_required` allowed **any** authenticated user when `settings.DEBUG` was True.
Dormant in prod (DEBUG=False), but a stray `DJANGO_DEBUG=True` in prod would
promote every member to VPP over the Service Hours officer pages. Removed the
bypass (and the now-unused `settings` import). For local testing, grant the dev
user the VPP role.

## D. `bug_admin_required` hardcoded `user_id == '73'` — INTENTIONAL, no change

Raised in the sweep as a handoff/maintainability smell; **Mason confirmed it's
deliberate** — the bug-tracker admin is pinned to a single hardcoded id on
purpose, to prevent accidental privilege escalation or mis-assigning the role.
Left as-is and recorded in the do-not-re-flag list.

## Deploy

No migration, no dependency change. Deploy the code and restart the app server.
After deploy, anyone whose account requires 2FA but hasn't verified this session
will (correctly) be prompted to complete 2FA before using `/api/…` AJAX features
— expected, not a regression.
