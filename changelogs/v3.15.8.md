# v3.15.8 — `manage.py preflight` production self-check

From the 07-23 auto-run report (item #6, graduation-handoff hardening). One new
file: `src/management/commands/preflight.py`. No migration, no new deps.

## What it is

A deploy/cron gate built on top of `check_env`. It subclasses the check_env
command, runs **all** of its checks (DEBUG, SECRET_KEY, hosts, DB, encryption,
email, cache round-trip, 2FA, security headers, storage, supply chain), adds
two runtime invariants check_env doesn't cover, and — the key difference —
**exits 1 on failure** (check_env always exits 0, so it can't gate anything).

New checks, both chosen because their failure class has actually bitten prod:

1. **Celery beat schedules** — every managed `SCHEDULES` row exists and is
   enabled; beat heartbeat staleness (newest `last_run_at` > 2 h → fail; never
   ran → warn); dead-orphan report using the same registration criterion +
   sentinel safety fuse as `setup_celery_schedules` (report-only — pruning
   stays with `--prune-orphans`). This is the v3.15.2 recurring-digest failure
   class.
2. **Media access gate** — anonymous GET of a real uploaded document (or a
   dummy path) must not return 200. Django-side via test Client;
   **`--live-url https://…`** additionally probes through the real
   nginx/Cloudflare stack — the layer where the v3.14.1 leak actually lived
   and which Django-side checks can't see. Without `--live-url` the live probe
   is a standing warning, so the deploy gate stays visible until verified.

## Flags

`--strict` (warnings also fail), `--email-on-fail` (summary to
`SECURITY_ALERT_EMAIL`), `--live-url <base>` (edge-layer media probe).

## Intended use

Last step of the deploy checklist, and/or daily cron:
`python manage.py preflight --strict --email-on-fail --live-url https://am-parliament.org`
