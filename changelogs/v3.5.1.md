# v3.5.1 — Re-Authentication for Sensitive Security Actions

**Release Date:** June 12, 2026

**Deployment Status:** ✅ Deployed — June 22, 2026

**Type:** Security Hardening

---

## Overview

Closes a gap where security credentials (2FA devices, passkeys) could be removed by anyone holding an active session — without proving they know the account password. Also fixes 2FA enforcement so voluntarily-enabled 2FA is actually enforced at login.

---

## What Changed

### 1. Disabling 2FA Now Requires Password Re-Authentication

`two_factor_disable` previously deleted all TOTP and backup-code devices on any authenticated POST. Worse, `/accounts/two-factor/disable/` was in `Enforce2FAMiddleware`'s exempt-path list — meaning a session that had passed the password check but **not** the TOTP step (i.e., exactly the attacker 2FA exists to stop) could reach the endpoint and strip 2FA from the account.

**Now:**
- The disable form requires the current account password (`check_password`).
- Password attempts are rate-limited: 5 tries per 15 minutes per user (cache-keyed), so the endpoint can't be used to brute-force the password.
- `/accounts/two-factor/disable/` removed from the middleware exempt list — only a fully 2FA-verified session can reach the page at all.
- Denials, rate-limit hits, and successful disables are written to the security log with IP.

**Changed:** `src/view/two_factor.py`, `src/middleware/two_factor.py`, `templates/two_factor/disable.html`

### 2. Passkey Removal Now Requires Password Re-Authentication

`passkey_delete` was `@login_required` only — a walk-up attacker on an unattended session could remove the user's passkey. Now requires the current password, with the same 5-per-15-min rate limit and security logging. The profile UI reveals a masked inline password field on the first "Remove" click; the second click submits. Success/failure now surface via messages instead of a silent redirect.

**Changed:** `src/view/webauthn.py`, `templates/profile.html`

### 3. Voluntary 2FA Is Now Actually Enforced at Login

`Enforce2FAMiddleware` only forced the TOTP verify step for users **required** to have 2FA by policy (`user_requires_2fa`). A member who voluntarily enabled 2FA under a policy of `none`/`admins_only` was never asked for their code — their 2FA was decorative. The verification gate now triggers for **any** user with a confirmed device, regardless of policy. (The setup-redirect remains policy-gated, as before.)

**Changed:** `src/middleware/two_factor.py`

> ⚠️ **Behavior change:** members who voluntarily set up 2FA will start seeing the verify page on their next login. Remember-device cookies and passkey logins still bypass the prompt as designed.

### 4. Passkey Registration Now Requires Password Re-Authentication

`passkey_register_begin` was `@login_required` only — an attacker on an unattended session could register **their own** passkey, a persistent backdoor that bypasses password and TOTP and survives a password reset. The begin endpoint now requires the current password (same 5-per-15-min rate limit, `passkey_register_attempts_<pk>`), returning 403/429 JSON errors. Gating begin is sufficient: complete is useless without the session challenge begin creates. The profile UI reveals a masked password field on the first "Add a Passkey" click.

**Changed:** `src/view/webauthn.py`, `templates/profile.html`

### 5. Security Event Notification Emails to the Account Owner

New `notify_user_security_event(user, title, details, ip_address)` helper in `src/security_notifications.py` emails the account owner when security-relevant changes hit their account. Wired into: **2FA disabled**, **passkey added**, **passkey removed**. Each email includes timestamp, IP, and what-to-do-if-this-wasn't-you steps. Mail failures are logged and never break the underlying action. Passkey registration also now writes a security-log entry (it previously only hit the app log).

**Changed:** `src/security_notifications.py`, `src/view/two_factor.py`, `src/view/webauthn.py`

### 6. Regression Test Suite

New `src/test_security_reauth.py` (20 tests) locks in this release's behavior: re-auth required for 2FA disable / passkey delete / passkey register, rate limits block even correct passwords after 5 failures, unverified sessions can't reach the disable endpoint, voluntary 2FA is enforced, cross-user passkey deletion 404s, and notification emails fire. Run: `python manage.py test src.test_security_reauth`

## Security Notes

- Re-auth pattern: `request.user.check_password()` + cache-keyed attempt counter (`2fa_disable_attempts_<pk>` / `cred_remove_attempts_<pk>` / `passkey_register_attempts_<pk>`, 900 s TTL, max 5).
- No new dependencies, no model changes, **no migrations**.

## Testing Checklist

- [ ] Run `python manage.py test src.test_security_reauth` — all 20 pass
- [ ] Disable 2FA with wrong password → error, devices intact; 5 wrong attempts → 15-min lockout
- [ ] Disable 2FA with correct password → devices deleted, remember-cookie cleared, security log + email
- [ ] Navigate to `/accounts/two-factor/disable/` in a session that hasn't completed 2FA verify → redirected to verify page
- [ ] Remove passkey: first click reveals password field; wrong password → error message, passkey intact; correct → removed + email
- [ ] Add passkey: first click reveals password field; wrong password → inline error; correct → registration proceeds + email
- [ ] Log in as a user with voluntary 2FA (policy `none`) → verify page now appears; remember-device cookie still bypasses

## Deployment

Standard deploy — no migrations, no dependency changes. Template changes mean a **Cloudflare cache purge** if any static assets are affected.
