## 1 — the suite printed 43 times, plus a command that looked like a real warning

`scripts/pre-push.sh` runs the suite and tees the output, so every `print()` in
a test lands in the push log: vote tallies, Kai fixture chatter, feature-flag
dumps. **43 of them**, 34 in `src/tests.py` alone.

Worse, `test_ledger_check` instantiated the `preflight` command directly. A bare
`Command()` writes to the real `sys.stdout`, so every push printed:

```
  ✗  Deploy ledger stamped   1 release(s) are LIVE in this tree and still say
                             "not deployed": v9.9.9
      | v9.9.9 | 08-20-26 | `d2d871e` | … |
```

**That is a fixture.** There is no v9.9.9. It reads like a genuine finding about
a genuine release, in the middle of a log you are scanning for genuine findings.

All 43 prints removed (AST-identified, so multi-line calls came out whole), and
the command's stdout captured the way the sibling helper in that same file
already did.

⚠️ **The cost was never the noise itself.** v3.19.9 had to make this hook
re-print its verdict lines at the end *because* a real `FAIL:` was scrolling
past behind this chatter — the first failure the hook ever reported was
misdiagnosed as a vote-summary bug for exactly that reason. That fix treated the
symptom. **A gate whose output nobody reads is a gate nobody reads.**

`src/test_suite_is_quiet.py` walks every test module and fails on a 44th print,
and asserts that every direct `Command()` in `test_ledger_check` has its stdout
replaced.

## 2 — the gate now runs in parallel

The hook ran `manage.py test src -v 0` **serially**: 291 s on Mason's machine.
It now passes `--parallel`.

⚠️ **This is safe now and was not always.** `tblib` has been a dependency since
v3.19.9 *precisely* so a parallel failure still reports which test failed —
without it the run aborts with `TypeError: cannot pickle 'traceback' object` and
**no results at all**, which is worse than slow. That groundwork is what makes
this a one-word change.

`--parallel` with no value uses one worker per core, deliberately unpinned:
this runs on whatever laptop is pushing. The failure hint now also suggests
re-running **serially** when a failure is unclear, because parallel workers
interleave output.

> **A gate people wait several minutes for is a gate people learn to
> `--no-verify` past.** This repo has the receipt: the previous hook sat
> uninstalled for a month.

## 3 — `make stamp-ledger`, after the tenth blocked push

This changelog originally ended by *recommending* this and declining to build
it, on the standing principle that the response to a pattern should not ride
along with an instance of it. Then the push carrying that recommendation was
itself blocked by the same check, for this very file. **Ten now:** v3.18.8,
v3.19.2, v3.19.4, v3.19.5, v3.19.6, v3.19.7, v3.19.8, v3.19.11, the
v3.20.0–v3.21.3 batch, and v3.21.4.

The principle is a good one and it has been served: the pattern has had eight
separate chances to be something else.

**The gate was never the problem.** `src.W003` is right every time, and it
prints the answer in its own error message. What was missing is that acting on
it meant hand-editing two lines per release — the sort of mechanical edit a
person defers, mistypes, or does for six files out of seven. So the check stays
and the fix becomes one command:

```
make stamp-ledger
git add changelogs/ && git commit -m "Stamp release ledger"
```

It decides nothing. It reads `git log --diff-filter=A` — the same source
`src.W003` reads — and writes down what git already says. `CHECK=1` reports
without changing anything. The hook's failure message now prints those two
lines instead of a `git log` incantation to run by hand.

⚠️ **It does not touch the "Deployed" column, deliberately.** Deployment is a
fact about a server; git cannot know it. `DEPLOYED.md` exists *because* a
plausible-looking unverified claim is indistinguishable from a checked one — the
whole 07-23 → 07-31 eight-report error came from a document that looked
maintained. A tool that inferred "Deployed" would rebuild that trap with better
ergonomics.

⚠️ **AND THE DRY RUN CAUGHT A BUG IN IT BEFORE IT RAN FOR REAL.** The first
draft tested only for the phrase "not yet" and reported **four historical
changelogs** as pending — because each carries a correction note explaining that
its line *used to* read "not yet":

> `**Committed & pushed:** 08-06-26 (`f260539`). *Corrected 08-07-26 — this line
> read "not yet" while the release was already on origin/main.*`

A tool that "fixed" those would have overwritten the very notes that exist
because this kept going wrong. `src.W003` learned the same lesson in v3.19.7;
its sha-before-phrase ordering is now copied rather than reinvented. **A scanner
run over a tree that documents the thing being scanned finds the documentation
first** — fourth time in this codebase, and the first time a dry run caught it
rather than a test.

Verified: run once, it stamped this file and its ledger row; run again, *"every
committed release is already stamped. Nothing to do."*
