## 🟡 New pledges join the current pledge class automatically

**Found by:** Mason, 10-01-26. The Fall 2026 pledges had no color on the
house map. None of them had a pledge class, because nothing ever set one:

- **Add Member** never set `pledge_class`.
- **Bulk import** saved the `pledge_class` column exactly as typed, without
  the Greek letter. The house map and directory badge need both.

The existing pledges were fixed by hand on the server the same day.

**Asked:** "if someone is added as a pledge it auto adds them to the current
(or next) pc."

**Fix.**
- `ParliamentUser.assign_default_pledge_class()` puts a pledge with a
  **blank** class into `pledge_classes.current_class()`, setting both the
  label and the Greek letter. A class someone typed is never overwritten.
- `ParliamentUser.save()` calls it **on creation only**. That covers every
  way a pledge gets added: Add Member, bulk import, the Django admin, a shell.
  Clearing the class on purpose later sticks.
- `edit_member` calls it when someone's type is changed **to** Pledge, and
  logs the change.
- Bulk import now runs a given `pledge_class` through `apply_to_fields`, like
  the profile forms do: `sp24` becomes "Spring 2024" / Gamma.

**"Current (or next)".** `current_class()` is the newest class in the
registry. That's Spring from January, and the upcoming Fall from July, the same
boundary the pledge-class dropdowns already use. So a pledge added over the
summer for fall recruitment lands in the fall class.

**Tests:** `src/tests/users/test_default_pledge_class.py` (10). The 5 that
exercise the new behavior fail without the fix.
