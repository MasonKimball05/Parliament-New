## "Copy [ref]" for new articles, sections and renames

Mason, 10-18-26: the resolution editor's **New Articles, Sections & Renames**
list had no way to copy ref codes. Tracked amendments have had one since
v3.45.0. Structural changes now work the same way:

- **Copy [ref]** on each row (edit page) copies
  `[Change S12: New section: Bylaws Art. III (Officers) § 4 — Dues]`.
- **The corner References panel** (was "Amendment references") lists them
  after the amendments, with **Insert** and placed / not placed. Each row in
  the list shows "✓ Placed in Resolved" or "Reference not placed". The count
  on the button covers both.
- **Citation chips:** a pasted structure ref gets a chip and is protected like
  a section citation (remove it with ×, not by editing inside it).
- **Print preview:** the ref becomes the change itself, in the same callout
  box an amendment gets. For example: "Upon passage: New section: Bylaws Art.
  III (Officers) § 4 — Dues. Current §§ 4–5 become 5–6." followed by the new
  section's text. The **Structural Changes** list further down stays as it
  was, the way the amendment appendix stays.

**How a ref is matched:** by `[Change S<id>:` only. Everything after the colon
can change after it's pasted: the section number shifts when another change
lands in front of it, and the title can be edited. Those refs still match.
(Amendments had the same problem, fixed in v3.45.3 by matching on the
section.) The id is the change's database id, so it never changes and never
clashes. Square brackets in a title are dropped from the ref so they can't
end it early.

**Escaping:** the print preview's text for each change is built by Django
(escaped) into a `<template>`, and the script only copies it in. Nothing is
built from the pasted ref's text.
