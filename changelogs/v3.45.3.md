## 🔴 Tracked amendment refs stopped being recognised

Mason, 10-13-26: "the tracked amendment refs are randomly breaking. The text
for the ref is still there, but the system no longer tracks/realizes that the
ref is there."

### Cause
A ref reads `[Bylaws Art. II § 3 (Addition) — scope - 2]`. The edit page's
reference panel ("References: N of M placed", "✓ Placed in Body") and the print
preview (which turns a ref into "Shall amend …") both looked for that exact
text. Three parts of it change after the ref is pasted:

- **The number** is the amendment's place in the list (`forloop.counter`), and
  the list is sorted by article and section. Adding or removing an amendment
  on an earlier section renumbers every amendment after it. This is the one
  that looks random: the ref breaks because of a change somewhere else.
- **"(Addition)" / "(Deletion)"** is worked out again from the text every time
  the amendment is saved, so editing the proposed text can add, drop or change
  it.
- **The scope note** can be edited.

Reproduced in Chromium on `main` (`da0dd30`): one amendment, its ref in the
Body, panel says 1 of 1 placed and the print preview shows the motion. Add an
amendment on an earlier section: panel says 0 of 2 placed, and the print
preview shows the raw bracket text.

### Fix
- A resolution has at most one amendment per section, so the section says which
  amendment a ref means. New `templates/cnb/_amendment_ref_match.html` gives
  both pages one matcher: `[` + the section + at least one amendment part
  (`(Type)`, `— scope`, `- N`) + anything up to `]`.
- A plain citation, `[Bylaws Art. II § 3]` with nothing after the section, is
  still a citation and is not treated as a ref. `§ 1` does not match `§ 12`.
- Copy [ref] and Insert still write the full current text. Old refs keep their
  old number in the text; the print preview replaces the whole ref, so it does
  not show.
- Checked in Chromium after the fix: renumbered, type changed and scope changed
  refs all count as placed, and all become the motion on the print preview.

### Not changed
- If a passed resolution renumbers the section itself (a new Article II moves
  the old one to III), refs to it in a draft still break. That is a different
  section name, not a stale suffix.

## 🟡 Four views changed data on a GET

### What was wrong
Django's CSRF check only runs on POST and the other write methods. A view that
acts on a GET has no CSRF check. The session cookie is `SameSite=Lax`, and a
Lax cookie is sent when a person follows a link from another site. So a link
in an email, a text or any web page could make a signed-in member's browser do
the action, with that member's permissions.

| View | Who it works for | What a followed link did |
|---|---|---|
| `delete_kai_template` | Kai chairs, admins | deleted a Kai report template |
| `toggle_document_publish` | the committee's chairs | published a committee document to the whole chapter, or took it down |
| `cancel_excuse` | the member who filed it | deleted their pending excuse |
| `recalculate_committee_vote` | chairs, officers | re-ran the pass/fail count (same answer each time) |

The first three pages already send a POST form. Only the Recalculate button on
Chapter Documents was a plain link.

Confirmed with tests on `main` (`da0dd30`): a GET to each of the first three
did the action.
The cross-site part (a link on another site carrying the Lax cookie) is how
browsers treat Lax cookies; it was not tried in a browser.

### Fix
- `@require_POST` on all four. A GET now gets a 405.
- Chapter Documents: Recalculate is a small POST form with the CSRF token. It
  looks the same.
