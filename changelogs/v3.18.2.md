# v3.18.2 — Prose is storage

**Date:** 08-02-26
**Type:** 🔴 Confidentiality fix + an authorization narrowing. **Migration `0013` — one `CreateModel`, no data change, no table rewrite.**
**Deployed:** not yet.

The 08-02-26 nightly review. v3.18.1 closed the activity feed on `KaiReportActivity`
across all four of its renderers and recorded the lesson in its own words:

> *An activity log carries identity in two places that do not look like fields
> — the entry's author, and whatever a previous release interpolated into its
> free-text `details`.*

That is exactly right. It was applied to the wrong model.

---

## 1. 🔴 `ActivityLog` was the eleventh Kai surface

**`src/kai_audit.py` (new), `src/view/activity_logs.py`, `src/view/admin_v2.py`,
`src/admin.py`, `src/view/kai_reports.py`, `src/view/kai_user_dashboard.py`,
`templates/activity_logs.html`, `templates/admin_v2/dashboard.html`**

### What was exposed

The site-wide audit log recorded, and `/activity-logs/` rendered:

| Writer | String | Who it identified |
|---|---|---|
| `submit_kai_report` | `"<Name> submitted Kai case #12"`, `user=request.user` | **the submitter** — on a submission `request.user` *is* the reporter, so the description and the row's own User column both named them, beside the case number |
| `file_appeal` | `"<Name> filed an appeal on Kai case KAI-2026-007"` | **the accused** — `file_appeal` fetches with `targeted_to=user`, so only the accused can ever write that row; its *existence* is the assertion |
| `request_drop` | `"<Name> requested to drop Kai case #12"` | **the submitter** — only the person who filed a case can withdraw it |
| `request_closure` | `"<Name> requested closure of Kai case #12"` | a party, either one |
| batch recusal | `"<Name> recused <Names> from Kai case …"` | **the accused** — `_sync_recusals` auto-recuses them whenever they hold a seat |

Readable by **every officer and chair in the chapter**: `@officer_required`
admits officers, all chairs and admins, and consults no `KaiMemberPermission`
anywhere. With a one-click *Kai Committee* category chip
(`ActivityLog.ACTION_CATEGORIES` contains `('kai', 'Kai Committee')`), a CSV
export carrying the same Description column, an `/admin/` search box over
`description`, and a per-member drill-down in admin-v2 that turns the whole
thing into *"which cases did this person report?"*.

This defeats the promise CLAUDE.md names as *the* Kai guarantee — **the accused
never learns who reported them** — and it takes less effort than the v3.18.1
search oracle did, because the accused in a chapter judicial case is very often
an officer themselves. The oracle needed a Kai seat and a lucky guess. This
needed a filter chip.

### Why four consecutive confidentiality audits missed it

v3.16.2, v3.16.3, v3.17.7 and v3.18.1 all enumerated **templates and views**.
`ActivityLog` is neither: not a Kai model, not in `src/models/kai.py`, not
rendered by any `templates/kai/` file, and it has no `submitted_by` or
`targeted_to` field to redact. It just stores both identities in a `TextField`
called `description`.

`docs/CONFIDENTIALITY_MATRIX.md` even had a cell pointing straight at the page
— `KaiReport.case_number` → *Activity* → "✅ in `ActivityLog` descriptions,
officer-only". Someone looked directly at it, correctly decided an officer may
see a case *number*, and did not look at the words on either side of the number.

**The general lesson, and it is the release title: when you enumerate the
surfaces that render a confidential field, enumerate the MODELS that can store
it first.** Prose is storage. An audit description, a notification body, an
email subject and a log line are all places a value comes to rest under a
different name, and none of them appear in a grep for the field.

Second time the miss was a *place* rather than a *rule*: `CalendarSubscription`
escaped v3.16.0's admin coverage pass because it lived outside `src/models/`.

### The fix

**Writers** — six call sites stop interpolating names. They now name the *role*
and the case: `"A member submitted Kai case KAI-2026-012"`, `"An appeal was
filed on …"`, `"The submitter requested to drop …"`, `"N Kai committee
member(s) recused from …"`. Actor pks moved into `metadata`, which no surface
renders. **This fixes nothing on its own** — every row already in the database
still contains the names, and those are the rows an officer would read today.

**Readers** — one new module, `src/kai_audit.py`, split along the v3.18.1 line
deliberately rather than discovering it again:

* **`redact_kai_logs`** where the row should stay visible — the officer log,
  its CSV, and the admin-v2 dashboard panel. Attaches `display_actor` /
  `display_actor_id` / `display_description`; templates render those. Applied to
  *all* rows, Kai and not, so there is one template code path and no habit of
  reading the raw field. Includes the legacy-row name substitution, which is the
  actual fix.
* **`exclude_kai_logs`** where a hit is *itself* the disclosure — admin-v2's
  per-member drill (`filter(user=user)`: the predicate **is** the author, so
  redacting the actor column achieves nothing when the page is that member's
  own) and `/admin/`'s `ActivityLogAdmin` (the standing v3.16.2 boundary — an
  admin is an operational role, not a judicial one; all seven Kai models are
  unregistered for this reason and this model carried the same identities in
  prose and stayed). `activity_total` counts through the same exclusion, so a
  total cannot disagree with the rows.
* **`audit_search_q`** because **a filter predicate is a join key**. Kai rows
  drop out of the `description` and `user__name` search columns for a viewer
  without both identity flags. Redacting the output while still filtering on the
  input is the v3.16.3 bug and the v3.18.1 bug; it is not happening a third time
  in the same quarter. `object_repr` and `ip_address` stay open — a case number
  is already officer-visible by the matrix and carries no name.

The six reviewer-written descriptions in `kai_reports.py`
(`"<Name> marked Kai case #12 as reviewed"` etc.) are **deliberately left
alone**: those name the acting reviewer, not a party, and `_case_access` recuses
parties from every action that writes one.

## 2. 🟡 `is_admin` no longer grants Kai access, and there is a break-glass

**`src/view/kai_reports.py`, `src/models/kai.py`, `src/migrations/0013_*`,
`src/management/commands/kai_break_glass.py`, `src/checks_kai.py`,
`templates/kai/view_reports.html`**

v3.18.1 removed the `is_exec_board` shortcut from `_get_kai_access` and argued,
correctly, that *a boolean on the committee row must not be able to grant Kai
access*. It left `user.is_admin` — a boolean on the **user** row — doing exactly
that, in the same `if` statement, ten lines below the docstring making the
argument. Full access: both identity flags, every allegation body, no
`KaiMemberPermission` anywhere.

Mason's call (08-02-26): **narrow it, keep a break-glass.**

`KaiBreakGlassGrant` is deliberately awkward in four ways, each of which is the
point:

1. **It cannot be clicked.** No view, no form, no admin registration — granted
   only by `manage.py kai_break_glass`, which needs shell access to the box. A
   stolen session cookie does not clear that bar.
2. **It expires** — four hours by default, 24 maximum. `--hours` is capped so a
   break-glass cannot quietly become a role.
3. **It is audited at both ends**, with a required `--reason` in the log line.
4. **It announces itself** — a red banner on the Kai list page naming the expiry
   for as long as it is live.

**⚠️ Not registered in `/admin/`, and must never be.** An editable admin for it
would let an admin grant themselves the access it exists to withhold — the
`KaiMemberPermissionAdmin` edge v3.16.2 removed.

### ⚠️ The operational edge, and it is the biggest risk in this release

**Anyone reaching Kai through `is_admin` loses access the moment this ships,
silently, via a permission redirect.** The `MasonsThreeReports` fixture in
`test_kai_recusal.py` failed on exactly this, which is how the risk surfaced —
it granted nothing but `is_admin` and had been passing on the shortcut.

A permission change that empties a page is indistinguishable from an empty page,
and this codebase has been bitten by that twice (the calendar Subscribe button;
the three `/guide/` 500s). So `manage.py check` — already a deploy gate — now
emits **`src.W001`** when the Kai committee has no chairs and no
`KaiMemberPermission` rows, i.e. when nobody can open the module. Warning, not
error: a chapter between officer terms may legitimately sit there for a day, and
a hard failure would block unrelated deploys.

**Before deploying, confirm the Kai chair(s) are in the committee's `chairs`.**

## 3. 🟡 Perf and correctness in the code v3.18.1 just touched

* **Sixteen queries per Kai list load → one.** The cross-case activity panel
  called `_case_access` per entry, and `_case_access` costs two `KaiRecusal`
  queries for any case the viewer is not a party to. New `_recusal_rows_for()`
  fetches them all at once; `_case_access` takes an optional `recusal_rows` map.
  It is a **performance argument only** — `test_batched_case_access_matches_unbatched`
  compares both paths role by role, including the empty-`granted_permissions`
  stand-in that must fail closed.
* **Five count queries → three.** v3.18.1 correctly moved `stale_count` and the
  two `assigned_counts` off the capped list, and did it with three separate
  `.count()` round trips beside two `GROUP BY`s on the same queryset. One
  `aggregate()` with conditional `Count`s now. (CLAUDE.md's own checklist:
  *repeated identical queries that could share a single `aggregate()` call*.)
* **The truncation notice switched itself off under exactly the condition it
  exists for.** It was gated on `not (any filter active)` — so search a common
  word, match 700 cases, see 500 rows and no warning. The template's own advice
  ("Filter or search to reach older cases") walked the user into the one state
  where it could not appear. Now `len(reports) >= KAI_LIST_LIMIT`, with wording
  that changes under a filter. Over-reports in the exact-multiple case, which is
  the right way round.
* **The case-number retry is bounded and narrowed.** v3.18.1's single retry
  recomputed `next_case_number()` from the same `MAX`, which returns the *same*
  number if the winner has not committed — and the retry was unwrapped, so that
  path was an uncaught `IntegrityError` and a 500 on submit. Now a bounded loop
  that steps past the number that just failed, and `_is_case_number_collision()`
  re-raises anything that is not our constraint instead of burning a number and
  producing a misleading traceback.
* **Duplicate dict key removed** — `'total_reports'` appeared twice in the same
  40-line context literal. The later (correct) one won silently.

## Deploy

1. `git pull origin main`
2. **`python manage.py migrate`** — migration `0013`, one `CreateModel` on an
   empty table. Instant, no lock of consequence.
3. **`python manage.py check`** — and read it. `src.W001` means nobody can open
   Kai; fix that before you walk away.
4. Restart `parliament-gunicorn.service`.
5. No dependency change, no static change → no `pip install`, no
   `collectstatic`, no Cloudflare purge, no Celery restart.
6. **Update `changelogs/DEPLOYED.md`.** v3.18.1 is still marked *not deployed*;
   it ships with this.
