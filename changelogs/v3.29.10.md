## 🟠 Support-ticket titles were readable by every officer and chair, not just the admin

`FeedbackRequest.request_type == 'support_ticket'` exists specifically so a
member can contact the admin privately — the module's own docstring says
so, and the ticket detail page already 404s for anyone who isn't the
submitter or the feedback admin (`user_id` 73). But `submit_feedback()`
logged the ticket's raw `title` into `ActivityLog.description` on every
submission, unconditionally, for both request types — and
`/officers/activity-logs/` (page and CSV export) is readable by any
`@officer_required` user, not just the admin. A ticket titled e.g.
"CONFIDENTIAL: my roommate is stealing my meds" was one officer-only page
away from every chair in the chapter, with the actually-private detail page
sitting right next to it doing its job correctly.

Reproduced end to end before the fix: submitted a ticket as a member,
confirmed the detail page 404s for an unrelated officer (correct), then
confirmed the same officer could read the title verbatim on the activity
log (it could). Fixed by dropping the free text entirely —
`ActivityLog.description` now reads `"{name} submitted a {type} (#{id},
{priority} priority)"`, matching the sibling `BugReport` system's own
convention (`send_bug_report_notification` already logs `issue_type`/
`priority`, never `bug_report.description`) rather than inventing a new
redaction rule.

## 🟡 Announcement emails re-queried the poll on every recipient

`send_announcement_notification()` (real sends) and
`warmup_announcement_email()` (the admin's preview/test-render path in
`admin_v2.py`) both let the email template touch
`announcement.poll.questions...` once per recipient in the send loop — the
exact N+1 shape `manage_announcements.py`'s list page had already
documented and fixed for itself. A chapter-wide announcement can go to
dozens to hundreds of members, so this was that many redundant identical
queries per send. Fixed in both places the same way: `poll` and its
`questions.prefetch_related('options')` are fetched once before the loop
and passed into the template context per user, rather than resolved through
the reverse accessor for every render.

## 💡 Test/preview announcement emails can now include a mock poll

Small feature bundled into the same commit: `admin_v2.py`'s test-email and
preview-email paths (`send_test_announcement_email` /
`preview_test_email`) previously always rendered a poll-less announcement,
so there was no way to see how a real poll would look in the email layout
without actually attaching one to a live announcement first. A shared
`_build_test_announcement_context()` helper (replacing two drifting copies
of the mock-announcement setup) now takes an `include_test_poll` flag and,
when set, builds a lightweight `_MockPoll`/`_MockPollQuestion`/
`_MockPollOption` set of objects — not a real `AnnouncementPoll` row, since
a test send shouldn't write to the database just to check formatting.
`poll_url` deliberately points at the non-resolving `/announcements/0/poll/`,
matching the existing "obviously fake" convention `tracking_url` already
uses for the same mock announcement (`id = 0`).
