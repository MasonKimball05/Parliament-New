## 🔴 Member-typed text was written into pages as HTML

Found by the 10-08 auto-run. Both cases below were reproduced in Chromium on
`main` (`38246a7`) before the fix and re-run after it.

### What could happen
- **Directory card.** A member saved markup as their "other email". The
  directory's profile card wrote it into `innerHTML`. An admin who opened that
  card got a form the member had written, covering the page. One click
  anywhere submitted it as the admin. In the test, that made the member a
  committee chair.
- **Resolution edit page.** An Editor collaborator saved a citation marker
  that contained a button. The edit page drew the marker as a chip with
  `innerHTML`, inside the main form. When the chair clicked the button, the
  pending resolution was marked passed and its amendment was applied to the
  section.

The CSP stopped injected scripts in both cases. It does not stop injected
forms, buttons, images or styles.

### Why a form was enough
`base.html` adds a CSRF token to any POST form that is submitted without one
(the v3.29.x fix for forms losing their token). So a form written by someone
else is sent with the viewer's own valid token. That guard is **not changed**
here. See "Not changed".

### Fix, layer 1: the pages escape
- **Profile card** (`directory.html`, `house_map.html`, `chat/channel.html`):
  every value from `/directory/<id>/card/` goes through the page's escape
  helper: name, both emails, phone, pledge class, graduation, role names, role
  history dates, social links, member type, picture URL.
- **Resolution edit page**: citation chips (both kinds) and the "article
  context" panels are filled with `textContent`.
- **Escape helpers**: eight copies of `div.textContent = x; return
  div.innerHTML` did not escape quotes, so they were unsafe inside an
  attribute (`title="…"`, `href="…"`, `data-raw="…"`). All now replace
  `& < > " '`. This closes attribute injection from chat messages, chat links,
  excuse reasons in the minutes editor, and form-builder field names.
- **Submit spinner** (`base.html`): the button's label was read with
  `textContent` and put back with `innerHTML`, which re-parsed escaped text as
  markup. It is appended as a text node.
- **Notification list** (`base.html`): `data-link` is escaped.
- **Admin dev panel** (`base.html`, maintenance mode): rows are escaped,
  including the online-users list, which shows members' preferred names.
- **Member list** (`user_list.html`): initiate-pledges list (a pledge's own
  username), role checkboxes, sync-admins results, import results, batch queue.
- **Minutes editor**: motion-author options are built with `new Option()`;
  motion type, vote method, result and caucus values are escaped.
- **Manage roles**: holder names. This also fixes names with an apostrophe
  showing as `O\'Brien` in the "Remove … from this role?" prompt.
- **Quote book**: `data-member-id`. **Admin v2 users**: the password-check
  tooltip.

### Fix, layer 2: the profile refuses `<` and `>`
New `src/profile_text.py`. `profile_view` checks the short profile fields once,
before any branch saves: username, preferred name, email, other email, phone,
pledge class, graduation semester, the five social handles, role history,
custom socials, initiation chapters, majors/minors/concentrations. A value
containing `<` or `>` is refused with a message and nothing in that POST is
saved. "Other email" must also be a valid address when it is changed.

`about_me` is not checked (it is free text and only ever shown as text). The
password form is not checked.

## 🟠 Editing a chat message did not work

Found while driving the chat page in a browser for the fix above. Not related
to it, and on `main` since 06-06-26 (`0e5c23a`).

- **Edit opened a box holding the word "Edit".** The Edit and Delete buttons
  carry the same `data-message-id` as the message text and come first in the
  row, so the page's lookup found the Edit button. Saving rewrote the button,
  and the message on screen stayed as it was until a reload. For a chair or
  admin watching, someone else's edit rewrote their Delete button.
  Fixed: the four lookups use `.message-text[data-message-id=…]`.
- **A message already on the page would have shown `don\u0027t`** in the edit
  box (`data-raw` was filled with `escapejs`). It now holds the plain text.
- **Read-only channels and admin preview opened at the top**, not at the newest
  message. A click listener on the @mention list threw when the list was not
  on the page, and the scroll after it never ran. The listener is guarded.

Checked in Chromium: Edit shows the message text (apostrophe, `&`, a line
break), Save stores and shows the new text, the Edit button is intact; a
channel the viewer cannot post in loads with no script error.

### Not changed
- **The CSRF auto-fill in `base.html`.** It is what turned injected markup into

- **Officer and admin edit paths** (`manage_members.py`, admin v2) still accept

- **`static/js/guide-tour.js`** still has the quote-blind helper. It only uses

  purge, so it was left out.
- **Existing data.** Nothing is rewritten. A value saved before this release is

## Addendum, same day — v3.45.0: how the print preview states an amendment

Mason: "If something is just removed in a section edit have it say 'Shall
strike from x Article, x Section of the Constitution/Bylaws (Section Title)
(what is being struck)'. For amendments (additions or edits) 'Shall amend x
Article, x Section … (Section title) (what is being added if added, the before
and then after if edited)', and some logic to handle if/when there are
multiple edits to 1 section."

Folded into this file under the one-changelog-a-day rule. It is a feature, so
the code comments call it v3.45.0.

### What the reference says now
The callout that replaces a citation marker in the body of the print preview:

| The amendment | Reads |
|---|---|
| Only removes text | **Shall strike from Article IV, Section 2 of the Bylaws (Officers):** "c. VP Communication" |
| Adds text | **Shall amend Article IV, Section 3 of the Bylaws (Fines) by adding at the end:** "Fines are due within fourteen days." |
| Rewords text | **Shall amend Article IV, Section 4 of the Bylaws (Quorum) by changing:** "two-thirds" to read "a majority" |
| Several edits | **Shall amend Article IV, Section 1 of the Bylaws (Dues) as follows:** (a) Change "Dues" to read "All dues" (b) Change "thirty" to read "fourteen" (c) Strike "of each semester" |
| Strikes the section | **Shall strike Article IV, Section 5 of the Bylaws (Old Rule) in its entirety:** the text |

- It replaces the old "Bylaws Art. IV § 2 (Deletion)" heading with its
  "Removed:" / "Added:" lines.
- A scope note, if the amendment has one, follows the reference in brackets.
- A passed resolution keeps the article and section numbers it was voted on
  with (the identifier snapshot from v3.43.0).

### Several edits to one section
A resolution holds one amendment per section, and it stores the whole new
text. "Several edits" are the separate places where old and new text differ.

- Each place is one lettered item: Strike, Add, or Change … to read ….
- If every item is a strike, the lead-in is still "Shall strike from".
- Two edits with one or two unchanged words between them are reported as one
  edit that includes those words, so a reworded phrase is not a string of
  one-word edits. Two strikes (or two additions) are never merged that way.
- A section rewritten almost entirely (under 40% of its words kept) is one
  change of the whole text.
- Trailing punctuation is compared on its own, so striking the end of a
  sentence is a strike and not a change of "meeting" into "meeting.".

### Calls I made
- **An addition says where it goes**: "at the end", "at the beginning", or
  after the four words before it. You did not ask for this. Without it
  "Add 'in full'" does not say where.
- **The appendix** entry now opens with the same statement and no longer says
  "The following shall be added to … of the Samford Chapter, the Alpha Mu of
  Beta Theta Pi". The marked-up section below it is unchanged.

### Known limit
Striking a list item and re-lettering the ones after it in the same amendment
("c." removed, "d." becomes "c.") can be reported as striking the tail of one
line and the head of the next. The old preview had the same limit. The
appendix still shows the full section.

### Where the logic lives
New `src/cnb_amendment_text.py` (`edit_items`, `describe`, `sentence`). The
page gets the result as JSON and only lays it out; every value is escaped.

### Tests
- New `src/tests/legislation/test_cnb_amendment_reference.py` (25 tests).
- One assertion in `test_cnb_amendment_preview.py` updated for the new wording.
- Chromium: a resolution with one amendment of each kind renders as in the
  table, with no script errors. Not tested in Safari or as a printed PDF.

### Files

## Addendum, same day — v3.45.0: filter the Tracked Section Amendments list

Mason: "In tracked amendments can you add a way to filter? Like if I only want
the constitution amendments or only bylaws or only certain types of
amendments."

- **Where:** the "Tracked Section Amendments" card on a resolution's page and
  on its edit page.
- **What:** two rows of chips above the list.
  - **Document:** All, and each governing document that has an amendment in
    this resolution (Constitution, Bylaws, …).
  - **Type:** All, Change, Addition, Deletion (only the types present).
  - The two combine. Each chip shows how many amendments it would leave,
    given the other row's choice. "Showing 3 of 5" appears while a filter is on.
- **Shown only when there is something to choose:** two or more amendments,
  and more than one document or more than one type.
- **Edit page:** when someone else changes the amendments and the list is
  redrawn, the chosen filter is kept. If its last matching amendment is gone,
  it falls back to All.
- **Not affected:** the print preview, the appendix, "Copy [ref]" numbers, and
  what is saved. It only hides rows on your screen, and resets on reload.
- **Not done:** filtering by article, by applied / not applied, or by text.

New `templates/cnb/_amendment_filter.html` (the script; chips are built as
text nodes and reuse the resolution-list filter's classes, so no CSS rebuild).
Rows in `resolution_detail.html` and `resolution_form.html` carry
`data-doc` / `data-type`.

Tests: new `src/tests/legislation/test_cnb_amendment_filter.py` (5). Chromium,
both pages: each chip, both rows combined, the empty state, and the redraw.
Not tested in Safari.

No migration, no `collectstatic`.

## Addendum, same day — v3.45.0: rename a section from the amendment popup

Mason: "there's no way to edit the actual name of a section in the tracked
amendments section. Can you fix this oversight?"

Renaming existed (v3.43.0), but only in the separate "New articles / sections
/ renames" maker. It is now also where you would look for it.

- **The amendment popup has a "Section title" box**, on the resolution's page
  and on its edit page. It fills with the section's title when you pick a
  section, or with the title this resolution already proposes.
- **Change it and save**, and the amendment row shows "New title when this
  passes: …". The live document does not change until the resolution passes,
  the same as the text.
- **One record, two ways in.** The new title is stored as the same
  `rename_section` proposal the maker makes, so it appears in the print
  preview's Structural Changes and is applied by the same code on pass. A
  rename made in either place can be changed in the other.
- **Title only.** If you change the title and leave the text alone, only the
  rename is saved; no empty text amendment is listed. It shows in the renames
  card, not in Tracked Section Amendments.
- **Putting the current title back** withdraws the rename. A blank box is
  ignored (it never clears a title). Striking the whole section ignores the box.
- Same permissions as amending: chair and Editor collaborators, draft or
  pending resolutions.

Server: `_propose_section_title` in `src/view/officer/cnb.py`;
`Resolution.pending_section_titles` (one query per page) and
`ResolutionAmendment.proposed_title`. New `templates/cnb/_amendment_title.html`.

Tests: new `src/tests/legislation/test_cnb_amendment_title.py` (19), including
that passing the resolution applies the title and that the row costs no query
per amendment. Chromium: both popups, add, edit, withdraw, title only.
Not tested in Safari.

No migration, no `collectstatic`.
