## Design

`ServiceHoursSubmission` is one row per date-of-service, and every other
feature built on it — approval (`status`/`reviewed_by`/`reviewed_at`),
editing (`edit_service_submission`), the CSV export (one line per date),
and the per-submission `ServiceActivity` audit trail — assumes exactly
that shape. Adding a real "spans several dates" field to the model would
have meant touching all four; instead, "same hours/organization/
description/attachment, several dates" creates one ordinary submission
row **per date**, sharing everything except `service_date`. Nothing about
approval, editing, export, or the activity log had to change at all.

## What changed

**Template** (`templates/service_hours/submit_hours.html`) — a "+ Add
another date" button under the existing single date field. Each click
adds a plain `<input type="date" name="extra_dates">` row with its own
remove button; no hidden field or JSON encoding needed, since
`request.POST.getlist('extra_dates')` collects every input sharing that
name. Capped client-side at 59 extra dates (60 total with the primary
field) purely so hitting the cap is a disabled button rather than a
silent server-side truncation.

**View** (`src/view/service_user_dashboard.py`, `submit_service_hours`):

- `_extra_service_dates_from_post()` parses, validates, and deduplicates
  the extra dates — blanks and malformed values are dropped silently
  (same "no future-date/bounds check" posture the primary `service_date`
  field already has; this doesn't add a new restriction, just extends the
  existing lack of one to each additional date), and anything equal to
  the primary date or repeated is skipped rather than creating a
  duplicate row. Same 59-date cap as the template, server-side.
- The primary submission saves exactly as before. One clone per extra
  date copies every field except `service_date`/`pk`/`submitted_at`.
- **Attachment**: a clone points its `attachment` at the primary's
  already-stored file name rather than re-uploading it — the same
  physical file, shared across every date's row (correct here: every
  extra-date row is the same event, just a different day it happened on;
  confirmed no `post_delete` signal on this model deletes the underlying
  file, so one row's later deletion can't pull the file out from under
  the others).
- **Custom form fields**: extracted the existing per-field parsing into
  `_save_custom_field_responses()` (unchanged logic), run once for the
  primary submission, then `_clone_custom_field_responses()` copies the
  resulting *values* onto each extra date's row. Deliberately NOT
  re-running the parsing function per extra date — `request.FILES`
  entries are single-read, so a custom FILE-type field's upload would
  silently vanish on every date past the first if the parsing loop ran
  against the request a second time.
- **Activity log**: one `ServiceActivity` row per date, same as if each
  had been submitted separately — so each date's approval history stays
  independently auditable.
- **VPP notification**: new `_notify_vpp_new_submissions()` sends exactly
  ONE email for the whole batch (total hours, date list, one description)
  instead of one per date — a member adding five dates in one form
  submission experienced it as one action, and five separate emails would
  just be spam. Single-date submissions (the common case) still go
  through the original, unchanged `_notify_vpp_new_submission()`.

## New tests

`src/tests/legislation/test_service_hours_multi_date.py` (14 tests),
exercising the real view end-to-end via the Django test client:
single-date backward compatibility (exactly one row, unchanged), multiple
extra dates create the right number of rows with every shared field
identical, per-date activity log entries, auto-approval applied to every
date when the period doesn't require approval, blank/malformed/duplicate
extra-date handling, the 59-date cap, attachment sharing (same stored
filename across rows, not a re-upload), custom-field value cloning across
rows, and notification batching (exactly one `send_email.delay()` call
for a multi-date submission, with "N dates" in the subject; unchanged
single-submission shape for one date).
