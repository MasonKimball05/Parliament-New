## What was wrong

**The websockets skipped the 2FA verify step.** `Enforce2FAMiddleware` is HTTP
middleware. A session that has passed the password check but not the TOTP step
is still *authenticated* as far as Django is concerned (django-otp only adds
`is_verified()`), and every HTTP page sends it to `/accounts/two-factor/verify/`.
The websocket stack in `Parliament/asgi.py` (`AuthMiddlewareStack` →
`URLRouter`) never ran that check, and all four consumers only ask
`user.is_authenticated`.

So someone with a member's password, but not their authenticator, could open:

- `/ws/chat/<id>/`: every new message, edit and delete in any channel that
  member can read, as it's sent;
- `/ws/votes/`: the open/close/tally pings (no ballot data);
- `/ws/cnb/resolutions/<id>/` and `/watch/`: presence, field locks and the
  saved text of resolutions the member can edit.

It's the same class of hole as the 07-22 sweep's Finding A (the broad `/api/`
2FA exemption), on a different transport. Message *history* and sending were
never reachable, because those are HTTP. Confirmed with the new tests:
without the fix, 3 of them fail (chat socket, votes socket, and a session
carrying another member's device id).

## Fix

- `src/middleware/two_factor.py`:
  - `session_passes_second_factor(user, session)`: the HTTP verify rule as a
    plain function. It passes when the member has no confirmed device, when
    it's an impersonation session, after a passkey login, or when the session's
    `otp_device_id` names a device that exists and belongs to that member (the
    same check django-otp's `OTPMiddleware` does).
  - `SecondFactorWebsocketMiddleware`: ASGI middleware that hands a session
    failing that rule to the consumer as `AnonymousUser`. Every consumer already
    refuses anonymous users, so no consumer changed, and a future consumer is
    covered automatically. Each refusal is logged at INFO.
- `Parliament/asgi.py`: the websocket router is wrapped as
  `AuthMiddlewareStack(SecondFactorWebsocketMiddleware(URLRouter(...)))`.

Deliberately not mirrored:
- **The remember-device cookie.** On HTTP it calls `otp_login`, which writes
  `otp_device_id` into the session, so the page that opens the socket has
  already verified it.
- **The "2FA required but not set up" redirect.** It can be dismissed on HTTP,
  and with no device there's no second factor to bypass.

**Effect on members:** none for anyone who got past the verify page, signed in
with a passkey, or has no 2FA. The only sockets refused are ones whose session
HTTP would also have sent to the verify page.

## Tests

`src/tests/security/test_websocket_second_factor.py` (10). They go through the
real `Parliament.asgi.application` with a real session cookie:

- refused: password-only chat socket, votes socket, another member's device id;
- allowed: a verified session, a member without 2FA, a passkey login, an
  impersonation session, an unconfirmed (half set-up) device;
- a helper test for the device rule, including a garbage `otp_device_id`.

Without the fix, 3 fail on PostgreSQL 16. With it, all 10 pass. The full suite
is in the 10-25 report.
