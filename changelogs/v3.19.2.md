## ⚠️ The existing "Clear lockout" button did not fully work

Found while looking for something to reuse. Parliament locks logins out through
**two independent systems with two different key schemes**:

| `login_view.py` | `middleware/security.py` |
|---|---|
| `login_attempts_{ip}` | `login_attempts_ip_{ip}` |
| `login_lockout_{ip}` | `login_lockout_ip_{ip}` |
| `account_login_attempts_{user}` | `login_attempts_user_{user}` |
| `account_login_lockout_{user}` | `login_lockout_user_{user}` |
| `account_login_ips_{user}` | |

`/admin-v2/security/lockouts/` hand-listed **six of those nine**, under a
comment reading *"Clear cache keys for all three systems"*. The three it missed
were the entire `account_*` family — **the username lockout `login_view.py`
sets, which is the one an ordinary member actually hits by mistyping his
password five times.** Clearing a lockout there reported success, marked the
`LoginLockout` row cleared, and left the member locked out until it expired on
its own.

Another stated-and-untrue comment, which makes it the third today after
`InputSanitizationMiddleware`'s *"for all requests"* and
`ActivityLog`'s *"nginx appends the real client IP there."*

**Fixed by `clear_lockouts_for(username=None, ip_address=None, cleared_by=None)`**
in `utils/security_utils.py` — one function that knows all nine keys, plus the
password-reset bucket and the whitelist cache, and marks the `LoginLockout`
rows. All three existing clearing sites (`clear`, `whitelist`,
`clear_all_active`) now call it.

⚠️ **The subtle half, recorded because it is the failure that looks like
success:** clearing a lockout key without its **attempt counter** re-locks the
account on the very next failed attempt. Counter still at 5, one more try,
locked again — indistinguishable from the button not working, except that it
said it worked. The helper always clears both.

## The button

`release_user_lockout` — POST-only, `@require_admin_v2_auth`, audited as
`account_unlocked` (an action choice that already exists, so **no migration**).

Three decisions worth stating:

* **It clears by USERNAME, not by IP.** A member's lockout is on his account;
  his last-known IP may be shared — campus NAT, or a Cloudflare edge on any row
  written before v3.18.8. Releasing everyone behind an address because one
  member is locked out is a much larger decision than the one the button
  claims to make. IP lockouts stay on the Lockout Management page, and the
  panel links there.
* **It is not hidden when the user isn't locked out.** The `account_*` lockout
  is cache-only and writes no `LoginLockout` row, so there is no cheap reliable
  way to ask — and `/admin-v2/security/lockouts/` lists only lockouts that
  *did* write a row, which is why the most common member lockout was invisible
  there and there was nothing to click. A button that hides itself when the
  state it clears is invisible is missing exactly when it is needed.
* **The success message is hedged when nothing was found.** `cache.delete` on
  an absent key is indistinguishable from one on a present key, so claiming
  "released" unconditionally would be the same class of claim this release is
  deleting elsewhere. If rows were cleared it says so; otherwise it says what
  it actually did.

## Tests — `src/test_release_lockout.py`, 12 tests

Assert on **observable state** — *is this account still locked according to
`is_account_locked`, the function that does the locking* — rather than on which
keys were deleted. A key-list assertion would pass for a helper that deletes
nine keys nobody reads.

* `test_it_releases_the_account_lockout_login_view_sets` is the regression test
  for the actual bug: it fails against the old six-key list.
* `test_it_clears_the_attempt_counters_too` covers the re-lock trap.
* `test_clearing_by_username_does_not_release_an_ip_lockout` pins the scoping
  decision above.
* `test_a_non_admin_cannot_release_a_lockout` is the negative control that
  matters — this endpoint undoes brute-force protection.
* The fixture patches **both** halves of `require_admin_v2_auth` (the
  `ALLOWED_USER_IDS` allowlist *and* the admin-v2 session). Patching one gives
  a redirect that looks like the view refusing, which is how a
  green-but-meaningless test gets written against this decorator.
