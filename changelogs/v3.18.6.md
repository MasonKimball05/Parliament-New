## `/admin-v2/two-factor/` — 130 queries for 47 members

`src/view/admin_two_factor.py`, `two_factor_dashboard`.

Per member, in the loop:

| Line | Call | Queries on the live roster |
|---|---|---|
| `:47` | `user_has_device(member)` | 47 TOTP + 36 static |
| `:53` | `member.two_factor_requirement` | 47 |

**The device half is worth understanding, because the panel reported one line
of code as two different counts.** `user_has_device` walks every installed
django-otp device class and returns at the first hit. With `otp_totp` and
`otp_static` both in `INSTALLED_APPS`, a member *with* a TOTP device costs one
query and a member *without* costs two — so 47 TOTP lookups and 36 static ones
means 11 members have TOTP. The asymmetry is the short-circuit, not two
different bugs.

**Fixes.** One query per device class, roster-independent:

```python
for device_cls in device_classes():
    users_with_device.update(
        device_cls.objects.filter(user_id__in=member_ids, confirmed=True)
        .values_list('user_id', flat=True))
```

`device_classes()` rather than importing `TOTPDevice` and `StaticDevice`
directly, deliberately: it is the same enumeration `user_has_device` itself
walks, so adding an OTP plugin to `INSTALLED_APPS` cannot silently make the
batched answer differ from the un-batched one it replaced. Naming the two
models would have been shorter and would have quietly gone stale.

And `select_related('two_factor_requirement')` for the other one — it is a
reverse OneToOne, and select_related caches the **miss** as well as the hit, so
the majority of members (who have no row) also cost nothing. The `try/except
DoesNotExist` becomes `getattr(member, 'two_factor_requirement', None)`, which
is safe rather than clever: Django builds the reverse-OneToOne failure as
`RelatedObjectDoesNotExist`, subclassing `(DoesNotExist, AttributeError)`
precisely so that idiom works. (Checked in the pinned Django source rather than
assumed.)

The queryset is now `list()`ed because it is walked twice — once for the device
batch, once for the loop — and without that the fix would have traded 130
queries for 131.

**130 → 3.**

## `/service-hours/dashboard/` — 88 queries for 22 members

`src/view/service_hours.py`, `service_dashboard`, and
`src/models/service.py`.

Four per-member queries in one loop: an approved `Sum`, a pending `Sum`, an
adjustments `Sum`, and `get_member_expected_hours`, which runs its own `.get()`
one member at a time. Every one of them is the aggregate the loop wanted,
filtered to one member instead of grouped by member — so one `GROUP BY` answers
all 22.

**⚠️ `.order_by()` on each aggregate is required, not tidiness.**
`ServiceHoursSubmission` and `ServiceHoursAdjustment` both carry a
`Meta.ordering` (`-submitted_at`, `-created_at`), and Django adds any ordering
column to the `GROUP BY`. Without the clearing call the query groups by member
**and** timestamp and returns one row per submission — a fast page with wrong
numbers on it, which is a worse outcome than the slow one it replaced.

`get_member_expected_hours` keeps working for its single-member caller
(`service_user_dashboard`) and now carries a docstring warning against calling
it in a loop, with the two-line batch form written out.

**88 → 4.**

## Tests

Two new classes in `src/test_query_budgets.py`.

**⚠️ Neither sets a `BUDGET`, deliberately.** That module is explicit that a
ceiling is a *measured* number — taken twice, cold cache — and these were
written with no working Django available, so any constant would be invented. An
invented ceiling is worse than none, because it reads exactly like a measured
one. **Run them, note the counts, and add `BUDGET = <n>` plus the matching
`test_..._stays_within_budget` in the same commit**; `BudgetHygieneTests`
enumerates budgets explicitly, so it needs the two new entries too.

What they do assert needs no constant and is the property that actually catches
an N+1: **adding members must not add queries.** Both regressions scaled with
the roster, so both would have failed this the day they landed.

Both fixtures are **mixed on purpose** — some members with a TOTP device and
some without, some with an expectation override and some falling back to the
period default, some with pending hours and some without. A uniform fixture
exercises one branch and measures a page that does not exist in production;
that is the same lesson v3.18.4 recorded when every Kai fixture granted both
identity flags together.

`ServiceDashboardQueryBudgetTests` also carries
`test_the_grouped_aggregates_match_the_per_member_ones`, which checks the
**numbers on the page** rather than the query count. Collapsing a per-row
filter into a `GROUP BY` is the kind of fix that can be fast and wrong, and a
query-count test would pass just as happily with the `Meta.ordering` trap
above still in place.

⚠️ **Not executed** — same constraint as v3.18.5. All four changed files pass
`py_compile`.
