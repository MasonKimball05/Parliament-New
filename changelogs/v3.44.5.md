## 🟠 The document viewer no longer renders PDF pages inside its own request

Follow-up to v3.44.4, which listed this under "Not done".

### What was still wrong
v3.44.4 capped how big each preview page can be. It did not change when the
pages are rendered: the viewer rendered every page (up to 50) before it
answered, for every visitor, on every load, and put all of them into the HTML
as base64.

- Desktop visitors paid for it too. They are shown the PDF in an iframe and
  the images stay hidden.
- Daphne runs ordinary views on one shared thread, so the site waits while a
  long PDF is converted.
- The page itself was large. A 60-page text PDF produced a 25 MB HTML page.

The reference documents (Code of Beta, the Kai binder, Robert's Rules) are
long PDFs, so they take this path on every open.

### Fix
- The viewer now only lists the pages (`pdf_preview_manifest`). It opens the
  PDF to read the page count and page sizes and renders nothing.
- Each page is an ordinary `<img>` pointing at a new view,
  `pdf_preview_page` (`/document-preview/<token>/<page>/`), which renders that
  one page as a JPEG. The images are `loading="lazy"` with their real
  `width`/`height`, so a phone fetches the first few pages and the rest as
  they are scrolled to. A desktop browser fetches none.
- The v3.44.4 pixel cap is applied in one shared helper
  (`_render_pdf_page_jpeg`), so the new view has it too.
- Page responses are `Cache-Control: private, max-age=3600`.
- A page image that fails to load is retried twice (a small nonce'd script in
  the template). Each page is its own request now, so one can fail alone.

### How access is checked
There are five viewers with five different permission rules. The page view
does not repeat them. Instead the viewer, after its own check has passed,
issues a signed token (`django.core.signing`) that names the file, the file's
modification time and the member. `pdf_preview_page` requires login and
refuses a token that is forged, older than 2 hours
(`PDF_PREVIEW_TOKEN_MAX_AGE`), or issued to a different member. Every refusal
is a 404.

**One thing to know:** a member who opened a document keeps working page
links for up to 2 hours, even if the document is unpublished in that time.
They could already see (and download) the document when the links were issued.

The token is signed, not encrypted. It contains the file's path under
`/media/` and the member's id, both of which that member's page already shows.

### Measured (cloud machine, Django test client, one process)
| | Viewer request | HTML size | Then, per page |
|---|---|---|---|
| 60-page text PDF, before | 6.7 s | 25.4 MB | n/a |
| 60-page text PDF, after | 0.45 s | 0.15 MB | about 130 ms, 350 KB |
| 5-page scan (2550 x 3300 pt), before | 1.9 s | 2.0 MB | n/a |
| 5-page scan, after | 0.40 s | 0.11 MB | about 280 ms, 270 KB |

In Chromium against a local Daphne server with a 12-page PDF: a 1400 px
desktop window fetched 0 pages; a 390 px phone window fetched 4 on load and
the other 8 while scrolling. A page answered 429 once loaded on the retry.

### Not done / not checked
- Not tested in Safari on a real iPhone or iPad. The image path there relies
  on standard `loading="lazy"`; if lazy loading were ignored the phone would
  fetch all (at most 50) pages at once, one request each.
- Rate limit: the repo's `nginx.conf` allows 10 requests/s per IP with a
  burst of 20. A phone now makes about 5 requests to open a PDF where it made
  1. Many members on one network opening the same document at the same moment
  could see a 429 on some pages; the retry above is for that. The server's own
  nginx config was not checked.
- Rendered pages are not cached on the server. A second member opening the
  same document renders the same pages again (their own browser caches them
  for an hour).
- `convert_pdf_to_images` is kept but no viewer calls it.
- The real document 74 was still not available to test with.
