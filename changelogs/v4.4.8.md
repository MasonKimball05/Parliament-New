### Education: previous pledge classes are kept

The education dashboard only ever showed current pledges. Once a class was
initiated, their tasks, results, points and attendance vanished from it.

Now **initiating pledges saves their class** as it stood on the dashboard
that day. This happens on the Initiate Pledges screen, on the website or in
the app. The dashboard has a new **Previous Pledge Classes** card, and each
class has its own page:

- **Members:** points earned out of possible (point adjustments included),
  required tasks done, meeting attendance, roll number and big.
- **Task results:** every task against every member, with status and score.
  A task that wasn't assigned to someone shows "—".
- **Meeting attendance** for each of the class's meetings, and the **point
  adjustments** made while they were pledges.

It's a snapshot. Later changes to tasks or meetings on the dashboard (for the
next class) don't alter it. The class is named from the pledges' own pledge
class, e.g. "Theta class (Fall 2026)".

**The education admin** (a chair, or a site admin) can still correct it:
rename it or add notes, change a member's points or add a note about them,
and correct any single task result. Every correction is listed in the page's
**Edit History**, with who made it and when. Anyone else with education
access can view the page but not change it.

A pledge initiated within a week of the rest of his class (a straggler)
joins that class's page instead of starting a new one, and keeps the
meetings he sat with them.

**The next class starts clean.** Meetings from before the last initiation
belong to the archived class. They no longer appear in the dashboard's recent
meetings, and no longer count toward the new pledges' possible points (they
used to, which made a new class look behind from day one). Tasks stay as
they are, ready to reuse.

If initiation ever hit a problem saving the snapshot, the initiation still
goes ahead and the problem is logged.

### Committee page header no longer squashes the name

On a committee with several header buttons (Education: Education Dashboard,
Member Perms, Chat, Chat Settings), the buttons sat in a row that never
shrank, so the committee's name was squeezed into a column a few letters
wide ("Educatio / n / Committ / ee"). The header now stacks until there's
room for both, the buttons wrap onto more lines, and the name keeps a
sensible width. Fixed in both looks; checked at desktop, tablet and phone
widths.

## Slating: officer transition in the app, and scheduled transitions run

**In the app.** After results are published, a site admin now runs the
officer transition from the app: the results screen has an **Officer
transition** card leading to it, and links to the website's transition page
open it too. It works as the website does:

- Every position is listed with its role and who holds it now, pre-filled
  with the member elected to it. Any position can be handed to someone else
  (search by name) or skipped. A position with no role linked says so.
- **Review changes** lists what will happen ("Riley gets the role; removed
  from Pat") before anything does.
- Then run it now or schedule it, and cancel a scheduled one. Like the
  website, it can only run once.

**Scheduled transitions now run on their own.** Scheduling a transition for
a later date only saved it. The job that actually runs it was a management
command that needed its own cron entry on the server, and nothing else ran
it. It's now a Celery beat job every minute, like the vote open/close jobs,
so a scheduled transition happens on time. The command still works for
running by hand. The page, the app and the job lock the period first, so
the same transition can't run twice.

The website's transition page works as before. It now loads in a fixed
number of database queries; it used to run two per position.

## Scheduled maintenance and the honeypot digest now run

The same problem as scheduled transitions, in two more places. Each ran
only from a management command that needed its own cron entry, and the
server had none (checked 11-10-26: no crontab for www-data, and root's had
neither):

- **Scheduled maintenance** never started on its own. A window scheduled in
  the admin sat at "Pending start" until someone started it by hand.
- **The daily honeypot digest** (routine scanner hits, one email a day) was
  never sent. Serious hits were, and still are, emailed as they happen.

Both are Celery beat jobs now: maintenance is checked every minute, and the
digest goes out daily at 8:00 AM. The commands still work by hand.

A maintenance window that already ended (its start plus estimated duration
is in the past) is skipped rather than started. Otherwise an old window that
never fired would put the site into maintenance mode the moment this
deploys. "Start now" in the admin still starts any window by hand.

## Slating: candidates can't read their own interview notes

The pages where applicants see their own application only ever showed the
interview's time, place and whether it's done; notes and recommendations are
on committee pages. But two routes let a candidate onto those pages:

- **The general committee "Add member" page** didn't check whether the
  person had applied (only the slating setup page did). A candidate added to
  the slating committee there could read every applicant's interview notes,
  their own included.
- **Site admins** step in on a period that has no slating manager or
  committee admin yet. An admin who applied to such a period could do the
  same.

Now anyone with an application in a period gets no committee or manager
access to it, whatever their role: committee member, chair, manager, or a
site admin stepping in. That covers every slating page, the app, and
uploaded files (GPA screenshots and answer files). Drafts and withdrawn
applications count too, so withdrawing doesn't open the notes. A site admin
who hasn't applied steps in exactly as before.

## Slating: the whole committee interviews by default

Candidates normally meet the whole slating committee, but scheduling an
interview started with nobody ticked, so whoever scheduled it had to tick
every member each time.

- **A new interview starts with the whole committee ticked**, on the
  website and in the app. Untick anyone who won't be there. Saving a new
  interview with nobody ticked also seats the whole committee.
  Rescheduling keeps the interview's panel as it is.
- **"Whole committee"** replaces the list of names wherever an interview's
  panel is everyone on the committee: the applicant page, the Interviews
  list and the app.

## Slating: one page per applicant

Clicking an applicant's name used to open their application and a 50-word
snippet of their interview notes. It now opens a page with everything the
committee has on them for this election, at the same address. Only the
people who can read interview notes see it: the slating committee and the
people who manage the period, never a candidate (see above).

- **At a glance** (top of the side column): the interview's status, time,
  place and interviewers; the latest recommendation; the positions
  interviewers recommended them for; where they are on the slate, and
  whether they were elected once results are in; and any open nominations.
- **Positions:** once a completed interview has marked positions, each
  position they asked for shows **Recommended** or **Not recommended**.
  Before then neither label shows, so a missing tick doesn't look like a
  "no". Positions an interviewer recommended that they didn't ask for are
  listed under "Also recommended for", and the list says if they had marked
  that position Do Not Want.
- **Interviews**, now straight under Positions: every interview written out
  in full. That's the time, place and panel, the recommendation, the
  recommended positions, and the strengths, concerns and notes, with
  line breaks kept. Each has an **Edit notes** (or **Record notes**) link.
  Notes destroyed under the bylaws still show only "Notes destroyed per
  bylaws". With no interview, the card says so and links to scheduling.
- **History:** the period's activity log entries for this application
  (submitted, reviewed, interview scheduled or completed, imported), newest
  first, with who did each and when. Status changes read "from Submitted to
  Under Review", not the internal codes ("submitted to under_review"); older
  log entries are shown the same way, and new ones are written that way.

The page loads the same number of database queries however many interviews
there are.

**App:** the application screen gets the same page: an At a glance card,
Recommended / Not recommended on positions, each interview written out in
full (with strengths and concerns, which the app didn't show before) and a
link to edit its notes, and the History list.
