## New: "View Document PDF" — a live-generated PDF of the whole C&B

New `generate_cnb_document_pdf_buffer()` / `cnb_document_pdf` view
(`src/view/officer/cnb.py`), routed at `cnb/document-pdf/`
(`cnb_document_pdf`), linked from a new button on the Document tab's
sidebar right next to the existing "Official PDF" link.

Built directly on `GoverningDocument.enabled()` — the exact same
queryset `cnb_viewer` already renders the Document tab from — rather than
`.objects.all()`. That one choice is what makes "foreword once this gets
passed and the flag is enabled" work correctly with zero new logic:
`enabled()` already resolves each document's own feature flag
(`cnb_foreword`/`cnb_constitution`/`cnb_bylaws`/`cnb_appendix`) and
already fails closed on `cnb_foreword` specifically (`DISABLED_BY_DEFAULT`
— see `test_cnb_foreword.py` / the v3.19.1 CLAUDE.md entry), so the PDF
generator inherits that guarantee instead of re-implementing it and
risking getting it wrong a second time.

Cover page states plainly that this is generated live and is a
**different thing** from the pre-existing "Official PDF" link (a static
upload of the document as originally ratified, not automatically kept in
sync) — both links now sit side by side so it's clear which is which.
Each document (Foreword when eligible, Constitution, Bylaws, Appendix —
"appendix" is a real `GoverningDocument` doc_type already, so no separate
handling was needed for it) starts on its own page with its title, last-
reviewed date, and preamble, followed by every Article and Section in
`display_order`. A suspended article or section is marked `SUSPENDED`
with its reason; a partially-suspended sub-item is listed; an
amendment-protected section notes when protection expires — the same
information the on-screen viewer shows, so the PDF is a faithful export
of what a member sees, not a simplified version of it.

Built in Times New Roman from the start, applying the fix from v3.29.8
rather than re-discovering it: `getSampleStyleSheet()`'s base styles
default to Helvetica, so `styles['Normal']`/`['Title']`/`['Heading2']`
are overridden to the Times family immediately after
`styles = getSampleStyleSheet()`, before anything is built on top of
them.

Served `inline` (opens in-browser, matching the button's own label —
someone can still save or print from there) to any logged-in member,
same audience as the Document tab itself; no separate CNB permission
needed.

**Two entry points**, added in the same pass after Mason asked for the
second: the sidebar link on the Document tab (next to "Official PDF"),
and a matching button in the page banner next to "New Resolution" —
visible at the top of the page regardless of which tab is open. The
banner button is deliberately **not** gated behind `user_can_manage`
(unlike "New Resolution," which is CNB-only) since viewing the document
is member-facing, same as the sidebar link.

**Routing note:** deliberately `cnb/document-pdf/`, not
`cnb/document/pdf/` — the existing `cnb/document/<str:doc_type>/` route
(`manage_document`) would have swallowed `pdf` as `doc_type` if a route
were added after it in the same `<str:doc_type>` shape, since Django
matches URL patterns in list order.

## Follow-up: paragraph indentation, and a cache-control fix

Mason: "there are no tab spaces in the generated pdf at all so it's hard
to read" — correct: none of the styles had any `leftIndent`/
`firstLineIndent` set, so Article headings, Section headings, and Section
body text all sat flush against the same left margin with no visual
hierarchy at all. Added `SECTION_INDENT = 18` / `NOTE_INDENT = 32`
constants and set `leftIndent`/`firstLineIndent` on the Section-heading,
body, and suspension/protection-note styles, so the structure reads
Article → Section (indented once) → body (indented once more, plus a
first-line "tab" via `firstLineIndent`) → notes (indented furthest),
matching printed-document convention. Verified against real PDF geometry
via PyMuPDF (`page.get_text('dict')` line `bbox[0]`): Article x0=67.2,
Section heading x0=85.2, first line of body x0=103.2, wrapped
continuation lines x0=85.2 (correctly back at the Section's own margin,
not re-indented). New permanent regression test
`test_sections_are_indented_under_their_article_with_paragraph_tabs`
(new `_lines_with_x()` helper).

Mason then reported: "Now only the first thing under each article is
indented, not everything." Could not reproduce this in code: tested a
single article with 3 sections, two documents each with several
articles/sections, and multi-paragraph section content — all
consistently indented correctly. Went further and seeded the actual
production content (`manage.py seed_cnb_documents` — 4 documents, 18
articles, 64 sections) into a scratch database, rendered the real
33-page PDF, and inspected every line's x-position across Constitution
Articles I–VI and the start of Bylaws (~200+ lines, pages 1–10) — every
Article, Section, first line, and wrapped line was exactly where it
should be. No code defect found.

The one plausible explanation that *doesn't* require a code bug: the
view had no `Cache-Control` header, and `inline` PDF responses are
routinely cached by browsers on GET. If Mason had the tab open (or
reopened it) from before the indentation fix shipped, the browser could
easily have served the stale pre-fix PDF from cache instead of
re-requesting it — which would look exactly like "only the first thing
is indented" once the fix landed but the visible copy hadn't refreshed.
Added `Cache-Control: no-store, must-revalidate` to `cnb_document_pdf`'s
response so this PDF — which is meant to always reflect the current,
possibly-just-amended document — can never be served stale again,
regardless of whether that was the actual cause here.

**Mason then confirmed with a screenshot after a hard refresh** — ruling
out caching and showing the actual root cause: Article II § 1 rendering
"1. Eligible members..." tabbed, then "2. Members must not..." flush
against the left margin with no tab at all. That's the real shape of
real section content, and it's exactly the shape none of the earlier
synthetic tests happened to use.

**Root cause, found by querying the real content directly**: a section's
body is not free prose — it's stored as one numbered/lettered clause per
line ("1. Eligible members...\n2. Members must not..."), confirmed
against the actual seeded data (44 of 51 real sections with any line
break use single-newline separation between clauses; only 7 use
blank-line paragraph breaks). `as_paragraphs()` — written for prose, and
still correctly used for the cover page and preamble — only splits on
*blank* lines; every single-newline inside a block was turned into
`<br/>` within ONE `Paragraph`. ReportLab's `firstLineIndent` only tabs a
`Paragraph`'s true first line, never a line after a `<br/>` — so on any
section with more than one clause (nearly all of them), only clause 1
ever got the tab, and every clause after it landed flush against the
section's own margin. The on-screen viewer never had this problem
because it renders `section.content` with plain CSS
`white-space: pre-wrap` — every literal line break in the stored text is
just a line break, no first-line-only styling involved.

**Fixed** with a new `body_lines_as_paragraphs()` that gives every
non-blank line of a section's body its own `Paragraph`, so every clause
gets its own first-line tab — not just the first one. It goes one step
further: real section content also encodes outline depth with 3-space
leading indents for lettered/roman sub-items (e.g. Article VI § 2's
officer-duties list — "1. President\n   a. Be the face of the
fraternity...\n   b. ..."), so each line's leading-space count now maps
to proportional extra `leftIndent` (`NESTED_INDENT = 16`pt/level), and a
lettered sub-item nests visibly under its parent numbered clause instead
of all clauses sitting at the same depth. A blank line between two
top-level clauses in the source (a real, if informal, "new item" signal
in several sections) is preserved as extra space above the next clause
rather than silently discarded.

Verified against the real 33-page production PDF (`manage.py
seed_cnb_documents`), both by geometry (PyMuPDF `bbox[0]`) and visually
(rendered page to PNG): Article II § 1's "1./2." clauses now land at the
identical x-position, and Article VI § 2's "a./b./c...." sub-items nest
one level deeper than their parent "1. President" line, matching the
plain-text outline the content actually encodes.

Two new permanent regression tests use a fixture shaped like the real
content (flat numbered list with no blank lines, plus a nested lettered
sub-item) rather than a single prose paragraph — the earlier
`test_sections_are_indented_under_their_article_with_paragraph_tabs`
test used one long wrapping paragraph and could not have caught this,
which is exactly why the bug shipped past it.

**Negative control**: reverted the section-body call site back to
`as_paragraphs(section.content, style_section_body)` —
`test_every_numbered_clause_is_indented_not_just_the_first` correctly
failed (`103.2 != 85.2`, clause 2 landing at the section's plain indent
instead of getting the tab clause 1 got). Restored; `diff` against the
pre-revert backup showed zero changes.
