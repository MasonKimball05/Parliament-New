## 💡 Role Knowledge Base — handoff wiki tied to each officer Role

Requested by Mason: a place for an outgoing officer to leave procedures,
notes, and links for whoever holds the role next.

Scoped deliberately to the 10 formal `Role` positions (President, VPs,
etc. — anything with `RoleHistory`/`transfer_role` support already).
Committee chairs (Kai, Recruitment, Education, ...) have no term-tracking
model to hang this off of today and are out of scope for this pass.

- **`RoleKnowledgeBase`** — one row per `Role` (`OneToOneField`), holding no
  content of its own. **`RoleKnowledgeBaseRevision`** — append-only; editing
  the page creates a new revision rather than overwriting the last one, so a
  past officer's notes are never silently lost. Same reasoning already
  applied to Kai record retention (institutional memory, not disposable
  scratch content).
- **Read access:** any logged-in member — an open wiki, not officer-only, so
  members can learn how a role works even if they don't hold it.
- **Edit access:** `officer_required`, matching every other page that
  touches `Role` — no separate "only this role's holder" gate, so any
  officer can help keep any role's page current.
- **Read path never writes.** Viewing a role with no knowledge base yet
  shows an empty state rather than `get_or_create`-ing a row — this
  codebase has a standing rule against exactly that shape of bug
  (`src/models/singleton.py`), and the model deliberately follows the same
  discipline even though it isn't a true one-row-total singleton.
- New pages: `role_knowledge_base_index` (browse all roles, who holds each,
  written-vs-empty status), `role_knowledge_base` (view + edit form),
  `role_knowledge_base_history` (every past revision, newest first).
  Content renders through Django's `linebreaks` filter (auto-escaped, not
  `|safe`) — no stored-XSS surface despite being free-text content editable
  by any officer and readable by every member.
- New `Committee.prime_chair_memo()` — a small, separately-shipped
  optimization in the same commit: lets `committee_documents()` hand its
  already-computed chair-status fact into `is_chair()`'s own per-request
  memo instead of paying for a second identical query later in the same
  request via `can_edit_committee_minutes()`. Guarded to only fire when
  `committee.is_exec_board` is `False` — the one case where the raw
  chairs-table check is provably identical to what `is_chair()` would
  compute itself; on an exec-board committee the view still calls the real
  method, since `is_chair()` also grants access to exec-board members there.
- **Not yet registered in `/admin/`** — open item, not a decision; see this
  session's auto-run report (09-17-26) for the recommendation to either
  register both models or note the exclusion explicitly, matching how this
  codebase treats admin coverage as a deliberate choice everywhere else.

**Tests:** `src/tests/users/test_role_knowledge_base.py` and
`src/tests/committees/test_committee_documents_chair_shortcut.py` (the
latter written specifically to pin the exec-board boundary against a
"just reuse the flag" regression). Both green.

## 💡 Database connection-pressure monitor + daily digest additions

Added after a live incident: a chapter meeting onboarding a batch of
pledges drove enough concurrent logins to exhaust Postgres's
`max_connections`, 500-ing nearly every page (home, login, even the CSP
report endpoint) because nothing could get a connection.
`DB_CONN_MAX_AGE=300` means a connection sits open for 5 minutes after the
request that opened it finishes, so a burst leaves a large idle backlog
behind it instead of releasing connections as it settles.

- **New `src/tasks/db_health.py`** — `monitor_db_connection_pressure`, a
  Celery task on a 5-minute schedule, polls `pg_stat_activity` against
  `pg_settings.max_connections` and files a `'high'` security alert (via the
  existing `send_security_alert_task` pipeline, 1-hour cooldown so a
  sustained high-pressure period fires once, not every 5 minutes) once usage
  crosses 60% — chosen because connections were already at 70% the night of
  the incident before the burst that exhausted the rest, so warning
  meaningfully below that steady-state gives advance notice. No-ops cleanly
  on sqlite (dev/test) and if Postgres is already refusing connections
  (returns `None` rather than raising — a monitor that crashes the same way
  the outage does tells you nothing new).
- **Daily digest — two new sections**, both read-only, reusing
  `get_connection_pressure()` and the existing `get_performance_summary()`
  (one source of truth for each number rather than a second copy of either
  query): an **Activity Snapshot** (logins, votes cast, legislation
  submitted, announcements, events, service hours — plain counts regardless
  of whether anything needs attention, so a quiet day isn't a silent one),
  and an **Infrastructure/Ops Health** section (DB connection pressure +
  request performance).
- **Fixed a real pre-existing bug in the same commit:** the Celery Beat
  staleness check used a flat "hasn't run in 48h" window applied to every
  enabled task regardless of its own schedule — correct for a daily-or-more
  task, a permanent false positive for a monthly one (flags 28+ days a
  month). Now asks each task's own `schedule.remaining_estimate(last_run_at)`
  via Celery's own API, with a documented fallback to the old flat check if
  a schedule can't answer (fails toward still flagging, never toward
  silence). `OVERDUE_GRACE = 2h` absorbs ordinary beat-tick jitter.
- **`docker-compose.yml`/`docker-compose.dev.yml`** — added `worker`/`beat`
  services to both (previously only `db`/`redis`/`web`/`nginx`, so a
  compose-based deployment had Celery configured but nothing consuming the
  queue or firing schedules).
- **Reference `pgbouncer.ini` + `docs/PGBOUNCER_SETUP.md`** — the actual
  fix for the incident's shape (a small fixed pool of real Postgres
  connections, multiplexed for many more clients, so a burst queues briefly
  instead of Postgres refusing connections outright). Reference-only, not
  auto-deployed — same convention as `nginx.conf`, copied over by hand per
  the setup doc when Mason wants to roll it out.

**Tests:** `src/tests/infra/test_db_connection_pressure_monitor.py`,
`test_beat_health_check.py`, `test_digest_activity_and_infra_sections.py`.
All green.

## 💡 Excuse-reviewed notification

Requested by Mason: let a member know when their attendance excuse has been
approved or denied, instead of them having to check back.

`AttendanceExcuse.approve()`/`.deny()` now call a shared
`_notify_submitter()`, which covers both the officer review UI and the
admin bulk action from one call site. `notify_excuse_reviewed()`
(`src/notifications.py`) sends an in-app notification (always attempted)
plus an email (skipped cleanly if the member has no address on file,
including the reviewing officer's notes if any were left) — fails closed at
two layers (the model method and the notification function each catch and
log independently) so a notification failure can never surface as an error
on the officer's approve/deny click. New `'excuse_reviewed'` choice on
`Notification.notification_type` (migration `0043`). **Follow-up 09-17-26:
now wired into `NOTIFICATION_PREF_MAP`** as `notify_excuses` — see below.

**Tests:** `src/tests/events/test_excuse_review_notifications.py`. Green.

## 🟡 Roll call now includes Advisors

An advisor has been given a roll number in the chapter and needs to be
callable during roll call same as everyone else. `edit_chapter_minutes()`
dropped its `.exclude(member_type='Advisor')`, and the roll-call sort now
orders non-pledges by `role_number` numerically (falls back to the raw
string, sorted after real numbers, for anyone without a plain-integer roll
number — e.g. an advisor never assigned one) instead of by internal
`user_id`, so the list actually reads in roster order out loud.

Also fixed in the same commit: `chapter_minutes_list` had no
`select_related` on either FK it reads per row — `select_related
('created_by', 'event')` collapses 11x + 7x unjoined per-row queries (caught
live via the dev-mode query monitor) to a flat query count regardless of how
many minutes records exist.

**Tests:** `src/tests/events/test_chapter_minutes_roll_call.py` and a new
`ChapterMinutesListQueryBudgetTests` (scaling test + a negative control
confirming the page actually renders the fields being counted). Green.

## 🟡 CSP error on the onboarding page-guide close buttons

`templates/components/page_guide.html`'s two close buttons used
`onclick="closePageGuide(...)"`, which this app's CSP (`script-src-attr`,
no `unsafe-inline`) silently blocks — the button rendered but did nothing.
Fixed with the codebase's established pattern: a `data-page-guide-close`
attribute plus a nonce'd, delegated `addEventListener` in a `<script
nonce="{{ request.csp_nonce }}">` block. `KNOWN_INLINE_HANDLER_OFFENDERS`
ratchet decremented 18→17.

## 🟡 Quote book mobile fix

PageFlip's own responsive breakpoint collapses the two-page spread into a
single "portrait" page on narrow viewports, leaving no second page for the
spine divider to mark a binding between — it rendered as a stray line down
the middle of the one visible page on mobile. Hidden via an `is-portrait`
class toggled on load and on every `changeOrientation` event (resize,
device rotation).

### 💡 Surface a role's notes to whoever just inherited it

`role_knowledge_base_index`'s own limitation from the day before — a page
someone has to know to go find — is partly closed: `transfer_role()`
(`src/view/officer/transitions.py`) now calls
`notify_new_role_holder_of_knowledge_base(incoming, role)`
(`src/notifications.py`) right after its `transaction.atomic()` block
commits (never inside it — a notification failure must never roll back a
real role assignment; wrapped in its own `try/except` at the call site too,
as a second net around the function's own internal handling, same pattern
as `AttendanceExcuse._notify_submitter()`).

Deliberately silent — no notification at all — when the role has no
knowledge base yet, or one with zero revisions: "there's a page, but
nobody's written anything" isn't useful, and today that's most roles. Also
skipped when the incoming holder already held the role (`incoming_id ==
outgoing_id` — re-affirming isn't a handoff, so there's no predecessor to
point at). New `'role_kb_available'` choice on
`Notification.notification_type` (migration `0044`). Not added to
`NOTIFICATION_PREF_MAP` — low-volume, tied to an officer-only event, matches
how other rare/high-value types in this codebase start out.

**Tests:** new `TransferNotifiesIncomingHolderOfKnowledgeBaseTests` in
`src/tests/users/test_transitions.py` (5 tests: no KB, empty KB, real
content, same-person re-affirmation, and a mocked notification failure that
must not block the transfer). Green.

### 💡 Search on the Role Knowledge Base index

`?q=` on `role_knowledge_base_index` — a case-insensitive substring match
against a role's name, its current holders' names, and its **current
revision's content only** (not every past revision — matching against
history the page doesn't render would surface a role for a word a visitor
then can't find). One extra query total regardless of role or revision
count: `RoleKnowledgeBaseRevision.objects.filter(knowledge_base_id__in=...)
.order_by('knowledge_base_id', '-created_at', '-pk')`, keeping only the
first row seen per `knowledge_base_id` in Python — the ordering groups each
KB's revisions together with the newest first, so this reads the current
revision without a second query or a Postgres-only `distinct(...)`. Same
"candidate set is small" tradeoff `_linkable_events()`
(`chapter_minutes.py`) already makes.

**Tests:** 7 new tests in `RoleKnowledgeBaseIndexTests`
(`src/tests/users/test_role_knowledge_base.py`) — matches on role name,
holder name, and current content; confirms a superseded revision's text does
NOT surface a role; case-insensitivity; the empty-results state; a blank
query showing everything; and a query-count guard (5 extra roles × 3
revisions each must not add a single query). Green.

### 💡 `notify_excuses` — the excuse-reviewed notification is now optional

Closes the item the 09-16-26 work left open on purpose. New
`notify_excuses` key in `UserPreferences.prefs['notifications']` (JSONField —
no migration for this half), defaulting to `True`. Wired into
`NOTIFICATION_PREF_MAP` as `'excuse_reviewed': 'notify_excuses'`. New
`UserPreferencesForm` checkbox ("Excuse Reviews") and a matching toggle on
the Preferences page, following the exact pattern the other four in-app
notification toggles already use. The preference gates the **in-app**
notification only — approving/denying still emails the member regardless,
since email has never had a per-type preference gate in this codebase.

**Tests:** new `src/tests/users/test_notification_preferences.py` (model
default/override behavior + a full `UserPreferencesForm` round-trip,
including that saving doesn't disturb other notification preferences — the
form rebuilds `prefs` wholesale on every save, so a field missing from
either the initial dict or the save dict silently reverts to the class
default for every user); new `NotificationPreferenceTests` in
`src/tests/events/test_excuse_review_notifications.py` (default-on, can be
turned off, can be left on, `NOTIFICATION_PREF_MAP` has the entry). All
green — **⚠️ one real bug found and fixed while writing these tests, worth
keeping:** `create_user_preferences` (the post_save signal that
auto-creates a `UserPreferences` row for every new `ParliamentUser`)
constructs it as `UserPreferences(user=instance)`, and Django's OneToOne
reverse descriptor caches that new object on `instance` itself the moment
the forward FK is set — so `member.preferences` was already a cached,
stale Python object by the time a test's own `UserPreferences.objects.
get_or_create(user=member)` fetched, mutated, and saved a *different*
Python object pointing at the same DB row. The DB write was correct; the
cached attribute on the in-memory `member` was not. Fixed by mutating
`self.member.preferences` (the object already cached on the instance)
directly rather than re-querying — not a production bug (a real request
loads its own `ParliamentUser`/`UserPreferences` fresh and doesn't
independently re-fetch preferences mid-request), but a trap worth a comment
for the next test that touches a signal-populated OneToOne.
