## 2. QR self-check-in for event attendance

Two new models (`EventCheckinWindow`, `EventCheckinEmbed`), six new views,
an officer-facing "open a check-in window" control on the attendance page,
and a public embed endpoint for pasting a live QR code into a slide deck
between meetings.

**Security model, read carefully because it's the whole point of the
feature:** `EventCheckinWindow.token` is `secrets.token_urlsafe(32)`
output, not sequential — a guessable token would make the window's
15-minute (`WINDOW_MINUTES`) expiry moot, since an attacker who could
enumerate tokens wouldn't need to be anywhere near the actual event. An
officer opens the window by hand, in person; it expires on its own a short
time later. This is deliberate: a QR code that never expires is just a
photograph waiting to be shared into a group chat, checking in whoever has
the picture rather than whoever is in the room.

**Additive, never a replacement.** `mark_event_attendance` is untouched by
this feature or by whether `qr_attendance_checkin` is enabled — an officer
can always mark, correct, or override any member by hand, window open or
not, and a self-check-in is just another way an `Attendance` row gets
written, never a second source of truth. `event_qr_checkin` (the scan
target, `src/view/event_checkin.py`) is deliberately `login_required` only
— no officer check, since the whole point is any member in the room can
scan for themselves — but never login-*exempt*: an anonymous scan would
mean the QR content alone (rather than the QR content plus a logged-in
member's account) is what attests presence, a materially weaker claim.
Also fails closed on `attendance_finalized` (403) and on a member whose
`member_status` isn't `Active` (403, mirroring `mark_event_attendance`'s
own eligible-member list — a pledge, alumnus, or removed member scanning a
valid code doesn't get an `Attendance` row an officer's own marking
wouldn't have created either).

`src/utils/qr_svg.py` is a single shared QR-to-SVG renderer used by both
the officer-only check-in image and the public embed image, rather than
the same rendering logic copied into a second view — the same technique
`two_factor.py` already uses for TOTP enrollment QR codes.

## 3. Password change now revokes every other active session

`UserSession.revoke_other_sessions` (extracted from
`session_viewer.revoke_all_other_sessions`) is now also called from
`change_password` and `forced_password_change` — the exact same "log every
other device out right now" path a member gets from the Active Sessions
page. Django's `update_session_auth_hash` already made any *other* session
functionally unusable the moment it was next used; what this closes is
that the Active Sessions page kept *displaying* those sessions as live
until they were next touched or swept up by a cleanup task, and the real
`django_session` row sat around unused rather than being closed at the
exact moment a member has the strongest reason to want every other device
logged out immediately (they usually just changed a password because they
suspect someone else has it).

## 4. Songbook category-tab cache

A cache for the songbook's category-tab listing, invalidated by
`post_save`/`post_delete` receivers on the underlying song model so an
edit or a new song shows up without a stale tab list persisting.

## 5. nginx-level rate limiting + Cloudflare origin verification

Closes two items that had been sitting open in the roadmap since 08-21:
`limit_req_zone`/`limit_conn_zone` in front of Daphne (a floor against a
flood *before* it wakes the app server, not a replacement for the
existing application-level `LoginRateLimitMiddleware`/`LoginLockout`,
which are stricter and account-aware in a way nginx can't be), and a
`realip` block that only trusts `CF-Connecting-IP` when the immediate TCP
peer is itself a published Cloudflare edge address — generated from
`src/utils/cloudflare_ranges.py` via the new `manage.py
render_nginx_cloudflare_block` management command, so the nginx block and
the Python-side range list can't silently drift apart.

⚠️ **`nginx_cloudflare_only.conf` exists but is NOT enabled.** It's an
availability decision, not a drop-in security fix: enabling it means
anything that hits the origin without going through Cloudflare — a direct
health check, a webhook receiver, `curl <server-ip>` for debugging, DNS
not yet fully cut over — stops working. Nothing today is known to need
direct-origin access, but this wasn't testable against live traffic from
review, so enabling it is Mason's call, documented at the top of the file
itself.

## Bug found and fixed during review

`src/admin_extra.py`'s `EventCheckinWindowAdmin` had been inserted in the
middle of `EventReminderRecipientAdmin`'s body, and a trailing
`search_fields = ('user_name',)` line got left behind, becoming a
*second* assignment on the new class instead of staying on the old one —
Python silently keeps the last assignment, so `EventCheckinWindowAdmin`
ended up with a search field that doesn't exist on that model, and
`EventReminderRecipientAdmin` lost its search box entirely.
`manage.py check` can't catch this (`search_fields` is validated lazily,
only when a search actually runs against it); found by importing both
classes directly and comparing `.search_fields`. Fixed by moving the line
back to the class it belonged to.

## Known, low-severity, not blocking

A stray `db.sqlite3-journal` (12.8 KB binary, local dev runtime state —
not secrets, but a journal can hold arbitrary pre-image data from whatever
was mid-write) was committed in this release; `.gitignore` had no pattern
for the `-journal`/`-wal`/`-shm` sidecar files SQLite writes next to the
database. **Fixed in the next commit (v3.28.0/`44ac560`)**, which also
removes the tracked journal file — noted here so this changelog doesn't
read as though the release it actually happened in was clean.
