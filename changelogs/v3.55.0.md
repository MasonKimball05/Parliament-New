## 🟢 Mobile Phase 3 (part 3): chapter ballots from the app

Under `/api/mobile/v1/`, for the app's Votes tab:

- **`GET votes/`**: bills on the ballot (available, not closed, not
  tabled/removed/pending), each with whether voting has opened and whether
  the member has voted, plus `me` (`can_vote`, `attendance_ok`,
  `can_cast_now`, `has_passkeys`).
- **`GET votes/<id>/`**: description, options, votes allowed, threshold, and
  the document link. A bill that's off the ballot is a 404.
- **`POST votes/<id>/cast/`**: `{"choices": [...]}` plus exactly one of
  `"password"` or `"reauth_grant"`. Returns the vote receipt (the same token
  the web shows after voting).
- **`POST votes/reauth/passkey/begin/`** and **`complete/`**: a passkey
  confirmation. It returns a `reauth_grant` that is single-use, lasts 120
  seconds, and only works for the device and member it was issued to.

Errors are `{"error": code, "detail": message}`, with the web form's messages:
`not_eligible` / `not_present` (403), `reauth_required` / `reauth_failed`
(401), `reauth_locked` (429), `already_voted` / `voting_closed` /
`not_started` / `not_open` (409), `invalid_choice` (400).

### One ballot implementation for the site and the app
The body of the web `cast_vote` moved into `src/ballots.py`:
- the attendance window (present or late in the last 3 hours) and member type
- choice validation for every vote mode
- the row-locked one-ballot insert
- the activity log, the receipt and the live tally broadcast

The web form and the app both call it. Re-auth stays with each caller, since
the web confirms through the session:
- **Password:** the app uses the web's own check, now
  `check_vote_password()`, with the same per-member limit of 10 failures per
  15 minutes. Wrong guesses in the app and on the site count together.
- **Passkey:** the app uses the web's failure counter (5 per 15 minutes) and
  requires user verification. The credential must be the member's own.

As on the web, eligibility is checked before re-auth, so a member who can't
vote isn't asked for a password.

## 🟠 Fixed: the web vote form accepted ballots on bills that weren't open

`cast_vote` only checked `voting_closed` and `voting_has_started()`. A
hand-built POST could cast a ballot on a tabled, removed or pending bill
whose voting was never marked closed. Ballots now also have to pass
`open_for_voting()`, the rule the Home page uses for "pending votes". The new
error is "This legislation isn't open for voting." Tested on both the web form
and the app.

## 🟡 Corrected: Home hid pending ballots when `legislation_voting` was off

v3.53.0's `home/` returned no ballots when the `legislation_voting` flag was
off. That flag only gates managing bills (upload, edit, opening voting,
runoffs); the web vote page and `cast_vote` ignore it. Home now follows the
web.
