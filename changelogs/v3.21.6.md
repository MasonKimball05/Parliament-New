## 1 — 🔴 `invalid input syntax for type inet: "unknown"`

`signals.log_successful_login` computes

```python
ip_address = get_client_ip(request) or 'unknown'
```

and that is **correct**. `LoginHistory.ip_address` is an `EncryptedCharField`
with `null=False`, so a missing address needs *some* string; v3.15.2 records
that a `None` there used to crash the geo lookup and silently drop login
tracking altogether. `analyze_login_risk` tests for the sentinel by name.

The same variable is then handed to `ActivityLog.log_activity`. That model's
`ip_address` is a **`GenericIPAddressField`** — `inet` on PostgreSQL, which
accepts an address or `NULL` and nothing else:

```
psycopg2.errors.InvalidTextRepresentation:
    invalid input syntax for type inet: "unknown"
```

Every test that logs a pledge in hit it, because `Client.force_login` builds a
request with empty `META`, so `get_client_ip` returns nothing and the sentinel
takes over. That is 50 tests across `test_pledge_permissions`,
`test_visibility`, `test_geo_restriction` and the whole 08-19 education batch.

**Live since 05-28-26 (`776863a`, v2.19.0) — not quite three months.**

### Why nobody saw it

**SQLite has no `inet` type.** It stored `'unknown'` in that column without a
murmur. The local suite was green, the pre-push hook was green, and eight
release notes said so honestly. The type system that would have caught this runs
only on PostgreSQL — in CI, which had never passed, and in production.

> **A backend difference is not a portability detail; it is a type check you
> only run in one place.** Where the local database is more permissive than the
> real one, "the tests pass" means "the tests pass on the permissive one".

⚠️ **In production this fails quietly rather than loudly.** The call sits inside
`except Exception as log_err: logger.error(...)`, so a pledge login does not 500
— the officer-review row is simply never written. The symptom is an absence, in
the log officers read to review pledge activity.

### The fix

New `ip_or_none()` in `security_utils`, applied inside
`ActivityLog.log_activity` — the only method that writes that column. At the
choke point rather than the one call site that happened to hit it, because
CLAUDE.md records nine times that the call site is what gets left out.

It validates with **Django's own `validate_ipv46_address`**, the same validator
the field runs, so the helper cannot drift from what the column will take. The
sentinel is untouched where it belongs: `LoginHistory` still receives it, and a
test asserts that.

⚠️ **The new tests fail on SQLite too**, deliberately. They assert the *stored
value*, not that the insert didn't raise — a test that only checked for an
exception would still be green on SQLite with `'unknown'` in the column. That is
what moves a Postgres-only failure onto a laptop. Verified: with the
normalisation removed, `test_a_pledge_login_with_no_resolvable_ip_stores_null_not_the_sentinel`
fails on sqlite with `Stored 'unknown'`.

`TheSentinelIsInvalidForEveryInetColumnTests` walks `apps.get_models()` and
asserts all **ten** `GenericIPAddressField` columns reject the sentinel —
written as a walk, not a list, because v3.19.6 and v3.19.11 both record that *a
set is only the general form if something enumerates the population it is drawn
from*, and both times the missing enumeration was a four-minute query nobody
ran. This is that query. Nine of the ten were never at risk; the one that broke
was found by CI, not by anyone checking the other nine.

## 2 — 🟡 `src.W003` printed twenty-five false claims in CI

The same log showed the ledger check reporting that **every** changelog records
the wrong sha — *"v3.18.5 says `d804b6d`, git says `566aae6`"*, repeated down
all twenty-five releases.

None of it is true. `actions/checkout@v4` fetches **depth 1**, so
`git log --diff-filter=A` sees one commit and attributes the creation of every
file in the tree to it. The check was reading the absence of history as
disagreement.

It prints inside the `makemigrations --check` step and never failed the build,
which is worse rather than better: it seeded the log with twenty-five plausible
wrong answers for whoever eventually reads it while diagnosing something else —
and today, that was me.

`_repo_is_shallow()` now returns `[]` on a truncated clone, and on any error
asking, because a check that cannot see its subject should be silent rather than
confident. **The rule is already written twice in `scripts/pre-push.sh` about
its own interpreter and its own scanners: a check that cannot run must not
report like a check that failed.** Same sentence, one repository over.

Three tests, including the control that a full clone is still checked — without
it, "return `[]` always" would pass everything else in that module.

## What this release is really about

v3.21.5 fixed the two causes it could see and I called the environment axis
closed on the strength of two green sqlite runs. The changelog said in as many
words that CI is Postgres and the CI run is the thing to believe — and I still
let a local result stand in for it.

> **Reproducing a failure's stated cause is not reproducing the failure.** I had
> a hypothesis that explained 18 failures and never established that 18 was all
> of them. It was 18 plus 50, and the 50 were invisible to every tool I had.

The residual is worth naming rather than hiding: those 50 tests aborted at
`force_login` on Postgres, so **their bodies never ran there**. They pass on
sqlite. If any of them contains a second, body-level Postgres difference, this
release will reveal it rather than fix it. The next CI run is the evidence; this
table is not.
