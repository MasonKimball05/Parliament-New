# v3.17.0 — Developer mode

An information-dense debug overlay, available on any page, to developer accounts
who explicitly switch it on. Answers "why did this page do that?" without a shell:
every SQL query with N+1 detection, every feature flag and permission gate that was
evaluated and what it returned, and hover metadata on any value a template annotates.

Implemented 07-28-26.

---

## The gate is two-factor

Dev mode is active only when **both** hold:

1. `request.user.user_id` is in **`ADMIN_V2_USER_IDS`** — the same env var that gates
   Admin v2, deliberately reused so there is one list of developer accounts, and
2. the user has switched it on in **Preferences → Developer Mode**.

(2) matters. Being on the allowlist shouldn't put debug chrome on every page forever,
and a stolen session on a dev account doesn't surface the panel until the attacker
takes a second, logged action. Both directions of the toggle write an `ActivityLog`
entry.

Removing someone from the env var is sufficient to revoke — no database cleanup
needed. Their stored preference becomes inert (there's a test for exactly this).

### Why the toggle is its own endpoint

`POST /preferences/dev-mode/` (`toggle_dev_mode`), not a field on
`UserPreferencesForm`:

- The form is shared by every user. A hidden field would be present in the DOM and
  settable by a crafted POST; the endpoint re-checks the allowlist and returns 403.
- The preferences card is rendered only for allowlisted accounts, so for everyone
  else the markup doesn't exist at all.
- `UserPreferencesForm.save()` **rebuilds `prefs` wholesale**, so the `dev` section
  is now explicitly carried across via a new `PRESERVED_SECTIONS`. Without that,
  saving any unrelated preference would silently switch dev mode off. Regression
  test included.

No migration: the flag lives in `UserPreferences.prefs`, a JSONField whose docstring
already promises new preferences need no schema change.

## What it will not do

**Dev mode never widens what you can see.** It shows *metadata* freely — SQL, timings,
flag results, permission outcomes, model/PK/field names, prefetch status. Record
*content* still renders through whatever gate already governs it.

This is a firm rule, not a default. Per CLAUDE.md's standing admin-confidentiality
boundary, an operational role is not a grant of judicial, deliberative or ballot-level
access — and the developer allowlist is an operational role that will be handed to a
successor. A dev mode that bypassed the gates would quietly become the master key to
Kai reports, anonymous ballots and slating notes: precisely the bypass class
v3.16.0–v3.16.3 spent four releases closing.

`DevModeDoesNotWidenAccessTests` is the load-bearing test. A developer holding only
`can_view_report_list` turns dev mode on and still cannot see the allegation body,
still cannot see the submitter, and still cannot search either — with a sanity test
asserting the panel really was injected, so those three can't pass vacuously.

## Panels

- **SQL** — every query for the request with timings. Uses `force_debug_cursor` for
  the duration of one dev request (production is DEBUG=False and stays that way),
  restored in a `finally`.
- **N+1** — queries grouped by shape with literals stripped, flagging any shape
  repeated 4+ times, worst first. Three is a page legitimately fetching three
  things; four upward is a loop. This is the panel most likely to earn its keep —
  it is the same defect class as the last two weeks of auto-run findings.
- **Perms** — which gates ran and what they returned. `_get_kai_access` reports which
  of its three branches decided (admin / chair / permission row / no row).
- **Flags** — every `is_feature_enabled` call and *why* it returned what it did:
  `db row`, `no row → DISABLED_BY_DEFAULT`, or `no row → fail-open default`. That
  last one is the one worth catching: Python fails open on a missing flag while
  templates fail closed, so an unseeded flag is enabled in Python and invisible in
  any template gating on it. That asymmetry hid the calendar Subscribe button for
  weeks (07-25-26).
- **Objects** / **Notes** — from the template tags below.

## Template tags

```django
{% load dev_tags %}

{% dev_value report 'title' %}
{% dev_value report 'description' gated_by=kai_access.can_view_report_details gate_name='can_view_report_details' %}
{% dev_note "turnout source" "computed in view, not annotated" %}
{% dev_badge "queryset" "prefetched" %}
```

With dev mode off, `dev_value` renders exactly what `{{ report.title }}` would — no
wrapper, no cost beyond one boolean check. On, it renders the same text wrapped in a
hoverable span carrying model, PK, field, type, and **how the value was loaded**:
`prefetched`, `NOT prefetched — will query`, or `DEFERRED — reading this fires a
query`. That last one catches silent N+1s from `.only()`/`.defer()`.

`gated_by` takes the permission boolean governing the field. Falsy withholds the
value and reports the gate instead — which is the debugging information you actually
wanted; the allegation text is not.

Coverage grows as you annotate. Nothing is annotated yet; the Kai, voting and
legislation templates are the obvious first candidates.

## Implementation notes

- **`ContextVar`, not `threading.local`.** Parliament is served by Daphne (ASGI),
  which interleaves many requests on one thread. A thread-local recorder would leak
  one user's SQL into another user's panel. There's a test asserting the type.
- **The panel is injected, not `{% include %}`d.** The most useful thing it shows is
  the complete query list, and queries keep being issued through template rendering —
  an include would only ever see the queries you already knew about. Injecting into
  the finished response body also means `base.html` needs no edit.
- **Middleware must be registered LAST.** Request phase runs after everything else
  (so `request.user` and `request.csp_nonce` exist); response phase runs first (so the
  panel is in the body before `InputSanitizationMiddleware` computes the CSP header,
  and the panel's nonce-bearing script is allowed in production).
- **Dev responses are `Cache-Control: private, no-store`.** They're user-specific and
  carry SQL. Cloudflare has served cached responses across users before (the 07-18
  seal bug), so this is not theoretical.
- **Instrumentation is exception-proof and cheap.** Every recorder call is a single
  ContextVar lookup when dev mode is off, and wrapped so a broken recorder can never
  take down a page. Panel injection is likewise wrapped.
- **The panel deliberately looks nothing like Parliament** — monospace, dark, square
  corners, no brand colour. You should never mistake a dev-mode page for a normal one.
  Ctrl+` toggles it; open/closed persists in sessionStorage.

## Tests — `src/test_dev_mode.py` (33 tests)

Allowlist parity (dev_mode duplicates admin_v2's env parsing to avoid an import
cycle — this test is what stops the duplication drifting), SQL normalisation and the
N+1 threshold, all four gate states, the toggle endpoint including the 403 and that
a refusal writes nothing, form preservation, the record-safety suite above, the
template tag in all four combinations of on/off × gated/ungated, and recorder
isolation.

**Testing gotcha recorded:** `dev_mode_enabled_for` reads `UserPreferences` through
the same `user_prefs_<pk>` cache key the context processor uses (deliberately — it
costs no extra query). The cache is **not** rolled back with the test transaction
while SQLite reuses PKs, so one test's dev-enabled preferences get served to a
different user with the same pk. `CacheIsolatedTestCase` clears the cache in `setUp`.
Two tests failed exactly this way before it was added.

## Verification

- **33/33 new tests pass.** `manage.py check` clean.
- **Full suite: 621 tests, 25 failures — byte-identical to the pre-change baseline.**
  Zero regressions.
- **Pre-existing issue found while doing this, worth triaging:** 15 tests in
  `test_two_factor.TwoFactorAdminDashboardTestCase` and
  `test_pillar1.AdminV2DashboardContextTests` **only pass when `ADMIN_V2_USER_IDS` is
  unset in the environment.** Set it and they 302 instead of 200, because the admin-v2
  gate rejects a test user who isn't on the list. Any machine with a populated `.env`
  will see 15 red tests that have nothing to do with the code under test. They should
  patch the allowlist rather than depend on it being empty. Unrelated to this release
  — it is why the regression comparison above was run with matched environments.

## Post-release fixes (same day)

Two coverage gaps found in first use. Both were the recorder faithfully reporting
that nothing had been instrumented, rather than the recorder losing data.

**1. Perms panel read "no permission gate ran" on gated pages.** Only
`_get_kai_access` was instrumented. None of the ten authorization decorators in
`src/decorators.py` were — so officer home, gated by `@officer_or_advisor_required`,
looked ungated. All ten now route their decision through a `_gate()` helper that
records the outcome and the reason (`via is_admin`, `member_type=Officer`, `no VPP
role`, …). Trivially-passing gates are recorded too: "not a pledge — passthrough" is
a gate that ran, and the panel should say so rather than stay silent.

Added a **structural guard test** that walks every function in `src/decorators.py`
and fails if one doesn't call `_gate()`. Verified non-vacuous: it inspects 10
decorators. A new gate added without instrumentation now fails the suite instead of
producing an empty panel someone notices months later.

**2. Some flags appeared, some didn't.** There are two entirely separate ways to ask
whether a feature is on, and only one was instrumented:

| Path | Mechanism | Was recorded? |
|---|---|---|
| `FeatureFlag.is_feature_enabled('x')` | classmethod, hits the DB | yes |
| `{% if feature_flags.x %}` | indexes the context-processor dict | **no** |

The template path never calls the classmethod, so template-gated flags were
invisible. Fixed by making the context processor return `_TrackedToggleDict`, a dict
subclass that records lookups in `__getitem__` — capturing them where templates
actually make them, including the **missing-key case**, which is the valuable one:
KeyError → Django substitutes `''` → falsy, while the same name in Python returns
`True`. The panel now shows that explicitly as *"no enabled row → '' (fail-CLOSED;
Python would return True for this name)"*. This is the asymmetry that hid the
calendar Subscribe button for weeks; it is now visible on the page it affects.

Behaviour is unchanged — KeyError is re-raised so Django's normal
`string_if_invalid` path still runs, with a test asserting a missing flag still
renders falsy. The subclass pickles, so tracking survives the processor's 60-second
cache round-trip (also tested).

Also instrumented `@require_page_enabled`, so a page 403ing because of a `PageToggle`
row is no longer indistinguishable from a permission failure.

Flag entries are now **deduped with a count** — a nav template can consult the same
flag a dozen times per render, and twelve identical rows tell you nothing.

**12 new tests** (45 total in `test_dev_mode.py`), including a regression test per
bug. Full suite: 633 tests, 25 failures, still byte-identical to baseline.

## Deploy

Code + templates only. No migration, no new dependencies.

1. `git pull`
2. Confirm `ADMIN_V2_USER_IDS` is set in prod `.env` (it already gates Admin v2)
3. Restart `parliament-gunicorn.service`
4. `collectstatic --noinput` → purge Cloudflare

Then: Preferences → Developer Mode → Enable, and load any page. Panel is bottom-right.

**Nothing changes for any other user.** With dev mode off the middleware is one
boolean check, the template tags are pass-through, and no markup is emitted.
