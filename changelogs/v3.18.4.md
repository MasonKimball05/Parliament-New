## 🔴 The activity log's own member dropdown was the disclosure `exclude_kai_logs` exists to prevent

`src/view/activity_logs.py` — `activity_logs_view` and `export_activity_logs`.

```
/activity-logs/?user=<member>&category=kai
  → "Anonymous submitted Kai case KAI-2026-012"
```

Two dropdown selections, by any officer or chair, and the answer is *which Kai
cases did this member report*. `officer_required` admits every officer, every
chair and every admin and consults no `KaiMemberPermission` anywhere.

**Why the redaction bought nothing.** `redact_kai_logs` substitutes the
*identity* out of the description and leaves the verb and the case number
standing, so the surviving text still names the action. And the viewer supplied
the name — they picked it from a dropdown listing every active member.
`display_actor` reading *Anonymous* beside a filter chip bearing the member's
own name is a confirmation, not a redaction.

This is **cheaper than the v3.18.1 search oracle** it postdates: that one needed
Kai committee membership and a guessed string. This needs two clicks.

**Why it was missed, which is the transferable part.** `src/kai_audit.py`'s
docstring states the rule correctly and in as many words — *exclusion for
surfaces where a hit is itself the disclosure, "the filter is on the author, so
the row's presence under a member's name is the leak"*. v3.18.2 then applied it
to three of the four surfaces that need it: `/admin/`, admin-v2's per-member
drill, and the audit-log search box. The fourth ran the **identical**
`filter(user=…)`, one file over from a call site that gets it right.

> **THE RULE: the PREDICATE decides which half of `kai_audit` applies, not the
> page.** v3.18.2 classified surfaces by which view they lived in. Three were
> right. And the fourth was on the very page the module was written for — the
> 08-02 report's own finding text became the boundary of the fix.

The two halves are **not alternatives**. They answer different questions — *may
this row be seen* versus *may it be seen under this predicate* — and a surface
reached by an author-valued filter needs both.

**Fixed:** `logs.filter(user__user_id=…)` is wrapped in `exclude_kai_logs` on
both the page and the CSV. `total_logs` and `category_counts` are computed from
the same queryset, so they inherit it for free — which matters for the reason
`admin_v2.py:1811` already gives in a comment: a total above the row count says
how many were hidden, and under a Kai filter hidden means Kai.

## 🟠 v3.18.3's second-axis fix only fired when BOTH identity flags were held

`src/kai_audit.py` — `redact_kai_logs`.

v3.18.3 added `viewer_party_case_ids` because committee-level flags do not
apply on a case the viewer is the accused on, where `_case_access` withdraws
every permission. Correct. But it gated the lookup on the **conjunction**:

```python
party_cases = ... if (show_submitter and show_accused) else set()
```

while the value is consumed **per flag**, twenty lines below:

```python
row_show_submitter = show_submitter and report_id not in party_cases
```

So for flags `(submitter=True, accused=False)` the conjunction was False,
`party_cases` stayed empty, `report_id not in set()` was vacuously true on every
row — and that reviewer read **their own reporter's name** on the case they were
the accused on. The v3.18.1 oracle, a third time, in the branch beside the fix
for it.

The comment justifying the guard is worth preserving as an artefact, because it
sounded right: *"only fetched when the flags would otherwise short-circuit
everything, because that is the only case where it changes an answer."*

**Reachable and natural.** `can_view_submitter_identity` and
`can_view_accused_identity` are independent `BooleanField`s granted separately
in the app. *May learn who reported it, may not learn who it is about* is the
obvious grant for someone triaging intake.

**Why no test saw it, which is the point.** Every Kai fixture in the repo —
`_full_reviewer` in `test_kai_audit_log.py`, `PartySafeSurfaceTests.setUp` —
grants both flags **together**. Three of the four combinations were fine; the
fixtures only ever built one of the three.

> **THE RULE: the second axis applies to each flag separately, not to their
> conjunction.** A partially permissioned viewer is still a viewer, and a case
> they are a party to withdraws whatever they hold.

**Fixed:** `if (show_submitter or show_accused)`. Measured across all four flag
pairs; only `(True, False)` was wrong, and it now matches the other three.

## 🟡 One case-resolution rule, two consumers

`src/kai_audit.py` — new `rows_for_cases_q`, replacing the predicate
`audit_search_q` built inline.

`_log_report_id` reads a row's case from `object_id` (when `object_type` is
`KaiReport`) **or** from `metadata['report_id']` — appeals and recusals set
`object_type` to `KaiAppeal` / `KaiRecusal` and carry the report only in
metadata. `audit_search_q` carried a third, narrower answer that matched
`object_id`/`object_repr` only, so **the rows the redactor could resolve and the
rows the search could narrow were different sets**.

Not live: post-v3.18.2 appeal descriptions carry no names, and the legacy ones
name the accused, who is the viewer. But it is *output redacted, input not* in
miniature — the module's own asymmetry, at one remove — and the next writer to
put anything identifying in an appeal description would have made it live
without touching `kai_audit.py` at all.

Also fixed in the same helper: the old predicate's `object_id__in` was
unconstrained by `object_type`, and `object_id` is a shared `CharField` across
every model in the schema — so an `Event` whose pk equalled a case pk was
silently dropped from that viewer's search results.

## 🟡 The activity-log CSV materialised the whole table

`src/view/activity_logs.py` — new `EXPORT_LIMIT = 5000`.

`date_range` is a query parameter and `'all'` falls through every branch, so
`/activity-logs/export/?date_range=all` asked for every row of the largest table
in the schema. Since v3.18.2 that is worse than it was: `redact_kai_logs` opens
with `list(logs)`, so the whole result set was materialised in memory before a
byte was written, where the pre-v3.18.2 export had streamed through a cursor.

A regression introduced by a correctness fix — the same class `test_query_
budgets.py` was written for, and the one thing it cannot see, because it counts
queries and this is rows.

Truncation is announced in a first CSV row rather than applied silently: a
short export the reader cannot distinguish from a complete one is worse than a
refused one.

## 🟡 Kai identity flags were re-resolved on every helper call

`src/kai_audit.py` — memoised on the viewer object, with
`reset_kai_identity_cache` as the documented escape hatch.

`viewer_kai_identity_flags` ran a `Committee` lookup plus a full
`_get_kai_access` (a `KaiMemberPermission` fetch, and for an admin without one a
`KaiBreakGlassGrant` fetch on top) **every time it was called**, and every
consumer in the module calls it. Measured on a searched `/activity-logs/` load:
4 flag resolutions and 2 party lookups, now 1 and 1.

The cache lives on the `ParliamentUser` instance, which is request-scoped in
every real caller — `request.user` is one object for the life of a request. That
is the whole lifetime contract, and it is why this is an attribute rather than a
process-level cache keyed on pk: an expiring break-glass grant or a changed
permission row is picked up on the next request, which is exactly the freshness
the un-memoised version gave (nothing re-read permissions mid-request either).

`ActivityLogQueryBudgetTests.BUDGET` was measured with no `?q=`, so the search
path — the most expensive one — sat outside the budget that would have caught
this. Worth adding a `?q=`-bearing case next time the budgets are touched.

## 🟡 `calendar_view`'s upcoming-events queryset was unbounded

`src/view/calendar.py` — new `UPCOMING_WINDOW = 60`.

`all_upcoming` selected **every future event** in order to display five; the
`[:5]` is applied to the Python list after `is_visible_to_user` filtering and so
could not be pushed into SQL. v3.18.3 then attached the `_my_excuses` prefetch
to it — correctly, it had the same two N+1s as the month queryset — which meant
the excuse prefetch also ran across every future event on every calendar load.

The bound is safe for a non-obvious reason, recorded at the call site: the list
is ordered by `date_time` and the visibility filter is a **predicate, not a
reordering**, so it can only remove rows, never promote a later event above an
earlier one. The five soonest visible events are therefore necessarily within
the N soonest for any N ≥ 5.

## Tests

**`src/test_kai_audit_log.py`** — two new classes, 7 tests.

* `TheSecondAxisAppliesToEachFlagSeparatelyTests` — the four-flag-pair matrix,
  as a `subTest` table. Includes the **control**: a partially permissioned
  viewer must still read the reporter on cases they are *not* party to, because
  over-redaction is a real cost and not a safe default (it is what made the
  first cut of submitter recusal hide a reporter's own cases from them,
  corrected 07-31-26).
* `TheCaseResolutionRuleIsSharedTests` — asserts `_log_report_id` and
  `rows_for_cases_q` resolve the same rows, including the metadata-only appeal
  row; that a colliding non-Kai `object_id` is not swept up; and that the empty
  case composes under `~` rather than matching everything.

**`src/test_kai_party_safe_surfaces.py`** — two new classes, 8 tests. Every one
fails against the v3.18.3 tree.

* `AuthorValuedFilterTests` — the 🔴, with the same control discipline the
  module already uses: the author filter must keep returning non-Kai rows, and
  a reviewer holding both flags must keep seeing Kai rows under it.
* `TheAuthorFilterEnumerationIsMaintainedTests` — the companion to the existing
  search-term enumeration guard, which greps for search terms and would never
  have flagged a `?user=` dropdown. Greps the view layer for `ActivityLog`
  querysets filtered on their author and fails if one is not wrapped in
  `exclude_kai_logs`. No skip list, deliberately — the existing guard's own
  comment explains why one is how a guard stops guarding.

**One thing caught while writing the tests, worth recording** because it is the
same lesson in miniature: the first draft of
`test_the_counts_do_not_betray_the_excluded_rows` asserted `'Kai Committee' not
in body`. That would have failed regardless of the bug — the category *dropdown*
renders every `ACTION_CATEGORIES` label unconditionally. **An assertion that
cannot distinguish the bug from the fixture is not an assertion.** Rewritten
against `response.context`.
