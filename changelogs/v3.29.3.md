## Link chapter minutes to an event after creation

New `update_minutes_event` AJAX endpoint
(`/officers/minutes/<id>/update-event/`) lets an officer link, re-link,
or unlink an existing minutes session's event from the editor page —
previously only `create_chapter_minutes` could set `ChapterMinutes.event`,
so fixing a missed or wrong link meant deleting and recreating the whole
session (losing all sections/motions/attendance in the process).

`templates/officer/chapter_minutes_editor.html` — the "Linked: ..." text
in the header is now a clickable control (or "Link to event" when
unlinked) that opens a small modal with the same event `<select>` pattern
already used by the create-minutes modal. Saving reloads the page, since
the excuse/attendance sync data shown lower on the page is computed
server-side from `minutes.event` at render time. Changing the link on
published minutes is tracked the same way `save_minutes_data`/
`save_minutes_attendance` already track edits (`edited_after_publish`,
`last_edit_at`/`last_edit_by`/`last_edit_reason`, PDF regenerated if a
document is already published). Committee minutes are unaffected — they
never supported event linking in the first place (`'events': []` in
`edit_committee_minutes`), and the new control is hidden for them.

## The event picker was surfacing the farthest-future events, not the near ones

The actual cause of "an event wasn't showing up." All three places that
built this dropdown (`chapter_minutes_list`, the `create_chapter_minutes`
error path, and `edit_chapter_minutes`) ran
`Event.objects.filter(requires_attendance=True).order_by('-date_time')
[:20]` — no date window at all, sorted purely descending. `-date_time`
puts the event with the *latest* date_time first, and
`generate_recurring_events` can pre-generate up to 52 future instances of
a single recurring weekly meeting. A chapter with one recurring meeting
already has more than 20 events scheduled further into the future than
tonight — every one of those instances outranked an actual near-term
event in that ordering, so a meeting starting in an hour could be pushed
off the list entirely by a series of Tuesday-meeting instances scheduled
months out.

This reproduces regardless of timezone — `TIME_ZONE = 'America/Chicago'`
and `USE_TZ = True` are both configured correctly in `Parliament/
settings.py`, and nothing in `EventForm`, `_linkable_events`, or the
calendar rendering path does naive `datetime.now()`/`.date()` arithmetic
of the kind this codebase has had UTC-vs-CST bugs from before (see
CLAUDE.md's history on that class of bug) — a grep across `src/` for
`datetime.now()` and `now().date()` outside migrations/tests turned up
nothing live. It's purely an ordering/windowing bug, not a storage or
comparison one.

Fixed with a new shared `_linkable_events(limit=20, window_days=60)` in
`src/view/officer/chapter_minutes.py`, replacing all three duplicated
queries: window to `now +/- 60 days`, then sort the (small) candidate set
in Python by absolute distance from `now` — so the event that just
happened and the one starting in an hour both surface near the top, and a
meeting a year out no longer buries them. Reproduced the exact reported
scenario in a test (25 far-future recurring instances + one event an hour
out) and confirmed it fails against the old query before the fix.

## Excuse review page: soonest event first

`review_excuses` (`/officers/excuses/`) grouped excuses by event using
`order_by('-date_time')` — same shape as the dropdown bug above, and
exactly what Mason flagged as counterintuitive: the event furthest in the
future led the list, and the one closest to happening (the one most
urgent to actually review) could be buried below it. Flipped to ascending
`date_time`. `my_excuses.html`'s member-facing "Submit New Excuse" cards
were already ascending — that page needed no change.
