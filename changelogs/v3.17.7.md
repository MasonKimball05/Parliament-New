## 🔴 1. A second, completely unredacted Kai CSV export — reachable from a dropdown

**Files:** `src/view/kai_reports.py`, new `src/test_kai_csv_redaction.py`

There were two exports writing the same thirteen columns of Kai report data:

| | |
|---|---|
| `export_kai_reports_csv` | `kai_reports.py`, ~line 590 |
| `bulk_actions_kai_reports` | same file, ~line 1,700, the `action == 'export_csv'` branch |

v3.16.2 added per-permission redaction to the **first** one, and its comment is
still sitting in the file explaining exactly why:

```python
# v3.16.2: the allegation body is governed by can_view_report_details,
# but this export only gates on can_view_report_list — a list-only
# reviewer could dump every description via CSV.
```

**Nobody looked 1,100 lines down.** The bulk branch wrote `report.submitted_by`,
`report.targeted_to` and `report.description` raw:

```python
report.submitted_by.name,                               # no can_view_submitter_identity
report.targeted_to.name if report.targeted_to else '',  # no can_view_accused_identity
report.description,                                     # no can_view_report_details
```

Its only gate is `can_view_report_list` at `:1596`, and the per-action checks
below it cover `mark_reviewed`/`mark_pending`/`archive` — not `export_csv`.

### ⚠️ It was not an obscure endpoint

`templates/kai/view_reports.html:198–204` renders the bulk-action `<select>`
with **no permission guard at all**, so "Export CSV" was a menu item for anyone
who could load the report list. A list-only reviewer — someone the in-app detail
view specifically refuses the allegation body — ticked Select All and downloaded
submitter identity, accused identity and every description.

This is a direct breach of the standing admin-confidentiality boundary recorded
in CLAUDE.md. Kai access is governed **only** by in-app `KaiMemberPermission`
grants (the seven models are deliberately unregistered from `/admin/`), which
means a permission that does not hold is the entire control.

### Fix

Not "add the conditionals to the second one" — that produces two copies that
merely agree today. There is now **one** `KAI_CSV_HEADERS` and **one**
`_kai_csv_row(report, kai_access)`, and both exports call them.

`export_csv` deliberately gains **no** extra action-level gate, and the reasoning
is commented in place: the two checks above it guard *write* actions with write
permissions, while exporting is a read whose scope is now exactly the list
view's scope with the three detail fields redacted — identical to
`export_kai_reports_csv`, which has gated on `can_view_report_list` alone since
it was written. **Gating the two exports differently is how they drifted apart
in the first place**, so they are kept at parity. If exporting should ever
require more than viewing, change both.

*(The 07-31 report recommended an action-level gate here; this deviates from
that recommendation for the reason above.)*

**Also fixed, same function:** `except Exception as e: messages.error(request,
f'Error performing bulk action: {str(e)}')` put raw exception text in a
user-facing message. Logged now, generic message shown — same shape as the 07-28
CSV export leak and the two `str(e)` removals v3.17.5 made in `changelog.py`.

## 🟠 2. `filter()` before `annotate()` reuses the join — the home page reported "1 member"

**Files:** `src/view/home.py`, new `src/test_annotation_join_reuse.py`

v3.17.5 replaced `{{ committee.members.count }}` (four queries per committee)
with an annotation, and its comment was careful about `distinct=True` — which is
genuinely load-bearing and is **not the trap here**. The trap is one Django rule
earlier:

> `filter()` on a multi-valued relation, followed by `annotate()` on the **same**
> relation, reuses the filter's join — so the aggregate is computed over the rows
> the `WHERE` left standing, not over the relation.

The emitted SQL says it plainly:

```sql
COUNT(DISTINCT committee_members.member_id) …
LEFT OUTER JOIN committee_members ON …
WHERE (committee_members.member_id = ME OR chairs.member_id = ME OR …)
```

For a committee where the OR is satisfied by the *chairs* or *advisors*
disjunct, every member row survives the WHERE and the count is right. For a
committee where the only true disjunct is `members = ME`, **exactly one member
row survives.**

Measured on Django 5.2.16 with three committees, one per role:

| Committee | My role | `member_total` | True |
|---|---|---|---|
| Finance | plain **member** | **1** | 7 |
| Rush | chair | 6 | 6 |
| Alumni | advisor | 6 | 6 |

Most members are plain members of most of their committees, so the "My
Committees" card on the classic home page read **"1 member"** nearly everywhere.
A wrong number, not a slow one — the same category as the `slate_builder`
"N of M positions filled" bug v3.17.5 found in its own sweep.

**Fix:** move `.annotate()` above `.filter()`. Django then emits a second join
for the filter instead of reusing one; verified at 7 / 6 / 6.

**Swept for siblings — there is exactly one.** Four `filter().annotate()` chains
exist under `src/view/`: `global_search.py:195` filters on `name`/`code`,
`kai_reports.py:458` on a datetime, `chat/channel_chat.py:684` on an FK. Only
`home.py` filtered on the relation it counted. `manage_committees` uses the same
three-way `distinct=True` annotation with no such filter and is correct —
probe-confirmed, including that dropping `distinct=True` inflates `chair_total`
from 1 to 6, exactly as its comment claims.

### The part worth remembering

`distinct=True` protects against row **multiplication** from several joins. It
does nothing about a join **narrowed** by a WHERE. The question to ask of a
`Count()` annotation is not "is `distinct` set" but **"does this queryset filter
on the relation it is counting?"** — and the answer decides the clause order.

## 🟠 3. The geo-restriction list still could not reach an export that is a *mode* of a page

**Files:** `src/middleware/geo_restriction.py`, `src/view/officer/announcement_polls.py`, `src/view/admin_v2.py`, `src/test_geo_restriction.py`

v3.17.5 moved this control from path prefixes to resolved URL names and closed
"the parameter is in the middle of the path". It left the other shape standing:
**an export triggered by a query parameter on an ordinary page.** Three exist,
all carrying bulk member or security data:

| Export | Trigger | Columns |
|---|---|---|
| `poll_results` | `GET ?export=csv` | respondent names + every answer |
| `admin_v2_audit_log` | `GET ?export=csv` | actor, target user, detail, **IP address**, whole filtered set, unpaginated |
| `bulk_actions_kai_reports` | `POST bulk_action=export_csv` | see §1 |

Only the third can join `RESTRICTED_EXPORT_VIEWS` — its URL name *is* the
export, a POST-only bulk-action endpoint. Listing the other two would geo-block
the poll results screen and the audit log viewer **entirely**, not just their
exports.

**Fix:** new `geo_export_blocked(request)` in `geo_restriction.py`, returning a
403 or `None`, called at the top of each `?export=csv` branch. It shares
`_block_response()` with the middleware, so a view-level block is
indistinguishable from a middleware one — same page, same security-log line, one
place to change either. `request.geo_suspicious` was already set on every
request; only the *enforcement* assumed route granularity.

### Why the existing completeness test did not notice

`test_the_bulk_member_data_exports_are_all_listed` asserts three hardcoded names
are present. That is a regression guard for the gap v3.17.5 closed, not a
completeness check — **it cannot fail for an export nobody thought of.** The
v3.17.5 changelog's claim that a sweep had found the only missing one was true
only of routes *named* like exports; searching for `text/csv` instead of for
`name='…export…'` finds all three.

New `EveryCsvExportIsGeoGuardedTests` does the discovery version: any file under
`src/view/` containing `text/csv` must be in `RESTRICTED_EXPORT_VIEWS`, call
`geo_export_blocked`, or be allowlisted with a stated reason — and a second test
prunes allowlist entries that stop being needed.

Also removed: the now-unused `HttpResponseForbidden` import.

## 🟡 4. `view_all_activity` got its twin's cap but not its twin's honest totals

**Files:** `src/view/officer/view_all_activity.py`, `templates/officer/view_all_activity.html`, `src/test_bounded_querysets.py`

v3.17.5 §4 capped `view_all_reports` and wrote the rule down:

> **The part worth remembering:** a capped page must not count the capped list.

Its twin was capped one commit later in v3.17.6 and got the cap without the
rule — eleven tab badges were `|length` straight over the capped lists. Past 500
rows the page reports exactly 500 forever.

The second consequence is specific to this page and is the more expensive one:
the status sub-tabs are partitions of the **newest** 500, so an older draft
stops appearing in the Draft tab with no indication anything is hidden. **Drafts
are the actionable items on an officer activity page.**

**Fix:** `_status_totals()` — one GROUP BY per family — feeds nine `*_total`
context values, plus `activity_truncated` and the same amber notice
`view_all_reports` shows. The notice says explicitly that older drafts are not
listed, because that is the part someone needs to know.

A static guard in the tests fails if `|length` returns over any of the six
capped context lists.

## 🟡 5. The 2FA exemption followed the rename; its own legacy redirect did not

**Files:** `src/middleware/two_factor.py`

v3.17.6 correctly updated `Enforce2FAMiddleware`'s exemption from
`/exportable_media/` to `/exportable-media/`, with a comment noting that leaving
the old spelling would re-create the v3.14.1 broken-image bug. **In the same
commit** it added a legacy redirect at `exportable_media/<path:filename>` so old
links keep working — and did not exempt it. The middleware runs before URL
resolution, so an `<img>` on the old path was 2FA-redirected instead of reaching
its 302: the same broken image the hyphenated line prevents.

Both spellings are exempt now, with a comment saying the old one dies with the
legacy redirect.
