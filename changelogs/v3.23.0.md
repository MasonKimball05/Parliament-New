## The finding, and it is not the one I was asked about

`ParliamentUser.user_id` is the primary key, so **150 foreign-key columns in
this schema hold a copy of the string.** `src_vote.user_id` literally contains
`'P-C7JKZY'`. Changing it is not a row update — it invalidates 150 tables' worth
of pointers at once.

So initiation had to: rename the unique columns behind a `_migrating_` prefix,
copy the row by introspecting `information_schema`, walk `_meta` repointing every
relation, consult a hand-maintained list of non-ORM tables, consult a **second**
hand-maintained list of CASCADE tables to check nothing was orphaned, then delete
the original.

**None of it was ever necessary.** The roll number has had its own column the
whole time:

```python
role_number = models.CharField(
    max_length=30, unique=True, blank=True, null=True,
    help_text='Member roll number assigned at initiation '
              '(unique identifier visible to members)',
)
```

Thirty-two templates already render it as `#173`. `edit_member` already lets an
officer change it. **Initiation was changing the primary key to a value it was
separately storing correctly, one field over.**

> **A primary key must be something that can never need to change. The moment a
> value is both an identifier and information, you have bet that the information
> is permanent** — and this one was not, because initiation changed it on
> purpose.

`user_id` was a *natural* key doing a *surrogate* key's job. It is now simply a
surrogate: opaque, permanent, and nobody's business but the database's.

### The new initiation, in full

```python
with transaction.atomic():
    for pledge in pledges:
        pledge.member_type = 'Member'
        pledge.role_number = role_numbers.get(pledge.user_id)
        pledge.save(update_fields=['member_type', 'role_number'])
```

Every vote, attendance row, Kai case and service submission still points at
exactly the record it always pointed at. **There is nothing to migrate because
nothing moved.**

⚠️ **One transaction for the batch, not one per pledge.** The old code committed
each pledge separately and returned a 500 on the first failure, so a class of ten
that failed on the seventh left **six initiated and four not, with no record of
which**. Initiating a pledge class is one chapter decision; it either happened or
it did not.

## What was wrong with the old path, itemised

Each is a shape this codebase has hit before, which is why they are worth
recording rather than just deleting:

1. **`information_schema` is PostgreSQL-only, so the entire path was
   unreachable from the test suite.** The most dangerous operation in the
   application was the one operation no test could execute. ⚠️ **Measured, not
   asserted** — running the new tests against `30e3ae2` returns:

   ```
   500: {"success": false,
         "error": "Error initiating Pledge Pine: no such table: information_schema.columns"}
   ```

   Same lesson as v3.21.6: *a backend difference is not a portability detail, it
   is a type check you only run in one place.*
2. **Both table lists were hand-maintained.** A new non-ORM table meant silently
   orphaned rows; a new CASCADE relation meant the safety check quietly stopped
   covering it. Tenth instance of "a rule stated correctly and something left
   outside the helper".
3. **Two `except Exception` blocks swallowed** — co-authored legislation, and
   the per-relation update loop, which logged a warning and then carried on to
   the DELETE.
4. **There was a window with two user rows for one person**, between the INSERT
   and the DELETE.

## 2 — 🟡 "Remember this device" has never worked for a pledge

`src/middleware/two_factor.py`:

```python
user_pk, device_pk = value.split(':', 1)
if int(user_pk) != request.user.pk:      # int('P-C7JKZY') → ValueError
```

The surrounding `except` catches `ValueError` and returns `False`, so the cookie
is silently rejected. **Every pledge has been asked for a 2FA code on every
single login since the feature shipped**, with nothing anywhere saying why.

It fails closed, so it was never a hole. It is the same numeric assumption as
v3.21.1's three `<int:…>` routes, with the same silence — and it is exactly what
the `P-` prefix is for: the value is *visibly* not a number.

Fixed by comparing as strings.

## 3 — The generator that never existed

The Add Member form had a required free-text box labelled *"Unique member ID"*,
with help text reading *"cannot be changed later"* — **false for pledges**
(initiation changed it) and true for everyone else. `P-C7JKZY` was a convention
somebody typed, so it held only as long as whoever was typing remembered it.

New `generate_member_uid()`: `P-` + 6 characters, `secrets`, uniqueness checked
against the database, raising rather than looping if the space collapses. The
field is now optional — leave it blank and one is assigned.

⚠️ **The alphabet drops one of each confusable pair**, not just the famous ones:
`O/0`, `I/1`, `L/1`, `S/5`, `Z/2`, `B/8`. These ids are read aloud across a
room and typed off a phone by somebody who has had the account for four minutes.
28⁶ is still ~481 million combinations. **My first draft removed the letters and
kept `5` while the test asserted the `S/5` pair was handled — the test caught
it**, which is the argument for writing the rule as an assertion rather than a
comment.

⚠️ **Generated in `clean_user_id()`, not in the view.** The view is currently the
only caller of that form, and "the only caller" is precisely the assumption this
codebase keeps being wrong about.

## Migrations

* **`0021_backfill_role_numbers`** — data only, no schema. Fills
  `role_number = user_id` for non-pledges who have none. Needed because
  `role_number` was only ever written by the initiation path, so anyone created
  directly as a Member (officer add, CSV import, seeds) has the roll number in
  `user_id` and `NULL` in `role_number` — and from this release, `role_number`
  is the only place it lives.

  ⚠️ **It only fills blanks**, skips pledges explicitly (a pledge has no roll
  number — that is the point of initiation), and **refuses rather than
  colliding**: a value already taken by another member is left blank and printed
  at the end for an officer to set by hand. **A wrong roll number is worse than a
  missing one** — missing renders as nothing, wrong renders as somebody else's
  number, and only one of those is obviously broken. Reverse is a deliberate
  no-op: un-setting a roll number is not a rollback, it is data loss.
* **`0022_user_id_help_text`** — help text only, byte-for-byte identical column.
  Kept separate from `0021` on purpose so a reviewer can tell at a glance which
  migration touches data.

## Also

`profile.html` shows `#{{ role_number }}` instead of `{{ user_id }}` on the
member badge. They were the same string for everyone initiated before today,
which is why reading the pk there looked right — and would have started printing
`P-C7JKZY` on the badge of everyone initiated from this release onward.

**New `src/test_user_id_is_permanent.py`** (14 tests), including
`NothingAssignsToTheKeyTests` — a scan that fails the build if anything outside
creation assigns to a member's `user_id`.

⚠️ **That guard passes against the old tree too, and that is not a defect in the
guard** — the old code changed the key in raw SQL, which a Python-level scan
cannot see. It protects the future, not the past, and its docstring says so
rather than implying coverage it does not have.

⚠️ **Honest control accounting.** Of the five behavioural initiation tests, only
**two** fail against `30e3ae2`. The other three pass there **for the wrong
reason**: the old path 500s before changing anything, so "exactly one row
exists" and "every relation survives" are trivially true of a no-op. That is the
*"an assertion that cannot distinguish the bug from the fixture"* trap from
v3.18.4, and it is recorded rather than counted as evidence.

## Deploy

`git pull` → `migrate` → restart Daphne. No `collectstatic`, no Celery changes.

⚠️ **Watch the `0021` output.** It prints a line naming any member it could not
fill, with the reason. If that list is non-empty, set those roll numbers by hand
from Manage Members before telling anyone the release is live.

⚠️ **What did NOT change, deliberately:** existing members keep their current
`user_id`. Nobody is logged out, no FK column is rewritten, and the three
contrib/OTP tables that reference the user are untouched. A member's `user_id`
will now hint at whether he joined before or after today — cosmetic, and
invisible to members, who see `role_number`.
