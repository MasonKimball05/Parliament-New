# v3.19.11 — the fix that was applied to one model instead of to a population

**Committed & pushed:** 08-19-26, `421d429`

The 08-19-26 auto-run fix batch. It reviews **v3.19.10**, which is the tenth
consecutive batch whose subject is the previous batch's output.

## 🟡 1 — `LandingPageContent.get_instance()` was the same defect, on the public front door

`src/models/landing.py`, unchanged since it was written:

```python
@classmethod
def get_instance(cls):
    obj, _ = cls.objects.get_or_create(pk=1)
    return obj
```

`landing_page` is the **anonymous** landing view — the only page an
unauthenticated stranger can reach and have rendered. Measured 08-19-26 with
`CaptureQueriesContext`, row absent:

```
GET /  →  200, 15 queries, 1 of them:
          INSERT INTO "src_landingpagecontent" (…)
second GET /  →  7 queries, 1 of them a SELECT of that row
```

So on a fresh install, a restored database, or after anyone deletes the row,
**a visitor's GET wrote to the database**, and concurrent first requests raced
to be the writer. After that it settled into one uncached SELECT per request
forever, on the most-requested URL this application serves.

This is a smaller problem than v3.19.10's — a landing page is not middleware,
and the row exists on the live server — but it is *the same* problem, and that
is the finding.

### ⚠️ Why this is the eighth instance of one pattern, and what is different about it

CLAUDE.md records seven releases of *"a rule stated correctly, a helper written
to enforce it, then something left outside the helper"* — a call site, a branch,
a column, a resource, a route, the larger surface, the worker process.

v3.19.10 did not leave a call site outside a helper. **It fixed the model it was
looking at.** The fix was excellent in place: a sentinel because caching `None`
is indistinguishable from caching nothing, a receiver because `activate()` is
not the only writer, five tests of which two exist to catch the obvious wrong
fix. And then it stopped, because `SystemLockdown` was what the report was
about.

The rule this codebase already had, from v3.19.6, is exactly the one that was
needed:

> **Building the general mechanism is not applying it to the general case.** A
> set is only the general form if something enumerates the population it is
> drawn from; otherwise it is an `if` with better manners.

Finding it cost one `grep` for `get_or_create` in `src/models/`. **The
enumeration is four minutes and nobody has ever spent them at the right time** —
v3.19.6 recorded the same sentence about a `grep` for `FileField`.

### The fix

New `src/models/singleton.py` — `SingletonRow`, a **plain mixin** (not an
abstract model, so no field changes and no migration). It carries v3.19.10's
`get_instance` verbatim in behaviour: read, return an unsaved `cls(pk=1)` when
absent, cache the row and cache the absence behind a sentinel. Both models mix
it in. `LandingPageContent` gains `CACHE_KEY` and a `post_save`/`post_delete`
receiver, for the reason already recorded for lockdown — **the officer editor
is not the only writer** (`LandingPageContentAdmin` writes the same row from
`/admin/`, and so does a shell session during a handoff).

And the part that makes it a population rather than a second instance:
**`src/test_singleton_rows.py` walks `apps.get_models()`**, finds every model
exposing `get_instance()`, and fails the build if any of them writes while
answering. A third singleton added in 2027 is covered by a test written today.

> **⚠️ `test_the_walk_finds_the_two_we_know_about` is not a formality.** A walk
> that matches nothing passes every other assertion in that module vacuously.
> *An assertion that cannot distinguish the fix from an empty fixture is not an
> assertion.*

One test in there is about a hazard the caching creates rather than one it
fixes: `landing_page` **mutates** the object it just fetched (it substitutes
photo tags into three HTML fields before rendering). If the cache ever handed
back a shared object instead of a copy, that substitution would compound on
every subsequent request. LocMem and Redis both serialize on `set`, so it does
not — `test_mutating_the_returned_instance_does_not_poison_the_cache` pins the
property rather than the backend.

## 🟡 2 — v3.19.10 created a 500 on the emergency-lockdown console

Not a pre-existing bug: this one was **introduced two days ago**, by the fix in
finding 1's ancestor.

Once `get_instance()` stops creating the row, it can return an instance that has
never been persisted. Django does not treat those interchangeably:

```
>>> SystemLockdown.get_instance().save(update_fields=['whitelisted_ips'])
DatabaseError: Save with update_fields did not affect any rows.
```

`update_fields` is an instruction to issue an UPDATE. The UPDATE matches zero
rows, and Django — correctly, for the case it was designed for — refuses to
silently insert instead.

**`admin_v2.manage_lockdown` uses exactly that call, twice:**

```python
elif action == 'update_whitelist':
    lockdown.whitelisted_ips = [...]
    lockdown.save(update_fields=['whitelisted_ips'])   # 500 when the row is absent
elif action == 'update_message':
    lockdown.save(update_fields=['message'])           # 500 when the row is absent
```

`activate()` and `deactivate()` are fine — they call a plain `save()`, which
Django resolves as UPDATE-then-INSERT. So the two actions that break are the
two that *prepare* a lockdown, and the situations where the row is absent are a
fresh install and a database restore — i.e. **"set the whitelist, then
activate" during a disaster-recovery drill is precisely the sequence that
500s.**

⚠️ **And note what did not catch it.** v3.19.10 added four tests for the new
`get_instance` and they are good tests; they assert on the accessor. The full
suite was green at 1,353 both then and this morning. **The change was verified
where it was made and not where its result is consumed** — which is the same
shape as v3.19.9's rule about a guard verified somewhere other than where it
runs, one level out: *a return value's new failure modes belong to its callers.*

### The fix

`SingletonRow.save()` drops `update_fields` when the instance has never been
persisted, because "write only these columns" is not a meaningful instruction
about a row that does not exist. It is on the mixin and not at the two call
sites deliberately — **the thing this codebase has been left holding seven
times running is a call site somebody forgot.**

`force_insert` is deliberately **not** set with it: it would save one query and
convert a concurrent creation into an `IntegrityError`, and the entire subject
of this change is a read path two requests can reach at once.

Two tests are end-to-end through the view rather than on `save()`, because the
finding is a 500 and a unit test on the model does not prove the page recovered.
`test_the_control_update_fields_still_narrows_the_write` exists to catch the
obvious wrong fix — a guard that turned *every* save into a full-row write would
silently persist unrelated in-memory edits, which is a much quieter bug than the
500 it replaces.

## 🟠 3 — a new CVE in Django, and the two-day-old push gate was about to block every push

`pip-audit -r requirements.txt`, run 08-19-26:

```
django  5.2.16  PYSEC-2026-3717  → fix 5.2.17, 6.0.8
```

**PYSEC-2026-3717 / CVE-2026-15830** — GeoDjango's `GEOSGeometry` recurses
without bound on deeply nested `GEOMETRYCOLLECTION` values supplied as WKT, WKB
or hex-WKB, segfaulting the underlying GEOS library. Spatial lookups and
`gis.forms.GeometryField` are affected too.

**Not reachable here.** `django.contrib.gis` is not in `INSTALLED_APPS`, no
model uses a geometry field, and `grep -rn 'contrib.gis|GEOSGeometry|
GeometryField' --include=*.py` over the project returns nothing outside
`site-packages`. Triaged individually rather than bumped as a batch, per
v3.19.10's practice.

**Bumped anyway, and the reason is operational rather than security.** CI's
`security` job runs `pip-audit` with no `continue-on-error`, and v3.19.10's
pre-push hook now runs the same scan and **aborts the push on any finding**.
Verified by running the hook's own parser against today's JSON:

```
VERDICT: FINDINGS -> pre-push aborts, CI red
    ('django', '5.2.16', 'PYSEC-2026-3717', '5.2.17,6.0.8')
```

So the next `git push` on this repository — this one — would have been blocked
by a gate installed on Monday, over a vulnerability in a subsystem the
application does not use.

> ⚠️ **THE THING WORTH KEEPING, and it is a cost the gate is worth paying but
> should be paid knowingly: a CVE gate on a pinned dependency does not fire when
> you write bad code, it fires when someone else publishes.** This one arrived
> two days after the gate did, on an advisory published 08-04 whose OSV record
> was modified 08-19. Nothing in this repository changed. **A gate whose trigger
> is external means a bump can land in the middle of unrelated work, and the
> temptation is `--no-verify`** — which is how the previous hook came to be
> uninstalled for a month. The right response is the one taken here: bump,
> re-run the suite, and record why the CVE did not apply.

Suite verified green on 5.2.17 **before** the pin moved: 1,367 tests, 0
failures, two partitionings.

## 🟡 4 — the bandit suppressions, and the tidy pass that would have reddened CI

Listed in the first pass of this batch as *"cosmetic, worth a tidy pass, not
worth a release"*, with the claim that **two suppressions were stale**. Both
halves of that were wrong, and finding out cost one script.

### The claim was wrong

`bandit` prints `nosec encountered (B608), but no failed test on file X:437`,
and I read that as "this suppression is unnecessary". It is not: on a
**multi-line statement** bandit attributes the finding to the statement's first
line and the directive to the line it is written on, so the warning fires while
the suppression still works.

Measured properly — strip each directive one at a time, re-scan the file, see
whether a finding appears — **25 of the 26 were load-bearing.** Removing any of
them turns CI red. The one genuine redundancy was not on the list at all; see
below.

> **THE RULE: a warning that a guard did not fire is not evidence the guard is
> unnecessary.** It is evidence about *where* the tool thinks the guard is.
> This is the same family as the entry already in CLAUDE.md about `.exists()` on
> a prefetched relation — a plausible reading of a diagnostic, never checked,
> written into a report.

### And the tidy would have broken the build

The proposal was to convert `# nosec B308 B703 - reason` into the documented
comma form. Probed against bandit 1.9.4 before touching anything:

```
mark_safe(…)  ids named  → B308 STILL REPORTED     ← the proposed form
mark_safe(…)  bare       → suppressed
f-string SQL  ids named  → suppressed
```

**Naming the ids on a `mark_safe` line suppresses B703 and leaves B308
reported.** v3.19.10 discovered this for `dev_tags.py` and wrote it down in
place — *"a bare `nosec` is used rather than the pair form because bandit 1.9.4
suppresses only B703 on this line"* — and it is true of all five `mark_safe`
sites in the project. The other four were green only because their prose
justifications contain invalid tokens, which bandit discards, which
**accidentally** promotes them to blanket suppressions.

So the codebase was one plausible cleanup away from a red gate, and the cleanup
was written down in a report as a good idea.

### The one that really was redundant

`dev_tags.py`'s comment block — the one v3.19.10 wrote *to explain* the bare
suppression — wrapped so that a line began with the directive spelling. Bandit's
pattern matches inside a comment as readily as after code, so **the explanation
became a second, blanket suppression sitting on a comment line**, covering
whatever code a later edit might move onto it, and emitting ~18 `not a test
name` warnings out of its own prose.

⚠️ **The first draft of the note explaining that reintroduced it**, by quoting
the spelling in backticks. So did the first draft of the new test's docstring —
caught by the test itself. **Three times in one release**, which is why the rule
now is: *describe the directive, never spell it.*

### The fix

All 26 rewritten to one of two forms, justification always behind a **second**
`#` so prose can never reach the part bandit reads as test ids:

- `# nosec  # B308,B703: <why>` — the five `mark_safe` sites, bare for the
  measured reason above, ids named in the prose where they are documentation
  rather than instruction;
- `# nosec B608  # <why>` — everything else, narrow, because a narrow
  suppression cannot hide a second unrelated finding on the same line. The six
  in `manage_members.py` had no justification at all; the CI file asks for one.

New `src/test_nosec_hygiene.py` (5 tests) pins the four properties: no prose in
the id list, every suppression says why, none on a comment-only line, and
`mark_safe` sites stay bare. **It assembles the directive from two string pieces
so it can be scanned by its own rules with no exemption** — the alternative is
an exclusion list, and an exclusion list is how the next file quietly opts out.

Result: `Test in comment` warnings **~200 → 0**, bandit still exit 0, and the
strip-and-rescan audit re-run afterwards confirms all 25 remaining suppressions
are still load-bearing.
