## 1. 🟠 `passed_legislation` — paginate before the per-row work

`src/view/passed_legislation.py`

v3.17.1 removed this page's N+1s and the query count went flat. The *work* did
not. The view built its display dict for **every bill in the chapter's
history** — percentages, attendance formatting, four `reverse()` calls each —
and then handed the finished list to `Paginator`, which threw away all but 20.

Measured before this release, on the real view through the test client:

| bills in history | queries | Python row-comparisons | wall |
|---|---|---|---|
| 10 | 35 | 4,000 | 119 ms |
| 40 | 22 | 64,000 | 50 ms |
| 120 | 22 | 576,000 | 179 ms |

The comparisons come from the batched attendance fetch. Its range is a
**bounding box** — `min(window_start) .. max(window_end)` across every bill on
the page — not a union of the individual 6-hour windows, so it pulled every
`present`/`late` row in the archive (1,180 rows where 600 were needed, at 30
bills with ordinary committee attendance in between), and then each bill
re-scanned that whole list. `bills × rows`, i.e. quadratic in chapter history.

Now `Paginator(queryset, 20)` runs **before** the loop, so the joins, the
prefetch, the attendance window and the loop are all bounded by the page:

| bills in history | queries | wall |
|---|---|---|
| 10 | 26 | 21 ms |
| 40 | 23 | 26 ms |
| 120 | 23 | 27 ms |

Three supporting changes were needed to make that safe:

- **The row filter moved into SQL.** The loop `continue`d past vote-less
  legislation that isn't passed and has no explicit status. Dropping rows
  *after* counting and paginating them was survivable while pagination came
  last; paginating the queryset would have produced ragged pages (19 rows, or 3)
  and a `total_count` that overstates what is shown. The same predicate is now
  one KEEP filter, written positively — a row survives if it has real yes/no
  votes, **or** it passed, **or** its status is one the page always shows —
  with historical overrides applied via `Coalesce` exactly as the loop does.
  The Python check remains as an invariant, and `_ALWAYS_SHOWN_STATUSES` is now
  one constant instead of the literal appearing twice.
- **Attendance is bucketed in one pass** (`attendance_by_leg`) rather than
  re-filtered per bill.
- **The plurality tally is one GROUP BY for the page** rather than one per
  plurality bill — the last per-row query on the page.

**Equivalence is tested, not asserted.** `DisplayedRowsUnchanged` builds 168
bills covering every combination of status × `voting_closed` × `passed` × votes
× historical override, then walks all pages of all six tabs and compares the
displayed IDs against the pre-v3.17.3 algorithm run verbatim alongside:

```
all      old=69   new=69   IDENTICAL      passed  old=54  new=54  IDENTICAL
pending  old=24   new=24   IDENTICAL      failed  old=42  new=42  IDENTICAL
active   old=72   new=72   IDENTICAL      tabled  old=24  new=24  IDENTICAL
```

Page sizes are now `[20, 20, 6]` summing exactly to `total_count`, which they
did not before — the header count included rows the loop then skipped.

## 2. 🟡 `view_legislation_history` — the fixes its sibling got

`src/view/view_legislation_history.py`, `templates/legislation_history.html`

- **Pagination.** This page had none: it rendered every bill the user has ever
  authored or co-authored, each with two `reverse()` calls, a `set_passed()` and
  a full context dict. It was the only legislation page without a page size.
- **Five status `COUNT`s → one aggregate,** the change v3.17.2 made in
  `passed_legislation.py` and did not carry across. `distinct=True` is
  load-bearing here and commented as such: `base_qs` joins `co_authors`, so
  without it a bill you both posted and co-authored counts twice.
- **`my_polls` stopped prefetching rows it only wanted to count.** The template
  read `poll.responses.count` / `poll.questions.count`, so a poll with 300
  answers pulled 300 rows to render "300". Two `Count(..., distinct=True)`
  annotations replace it — `distinct` again load-bearing, since two multi-valued
  joins in one `annotate()` inflate each other.

## 5. 🟡 `create_user()` was throwing away its `username` argument

`src/models/users.py`

```python
def create_user(self, user_id, name, username, member_type, password=None):
    user = self.model(user_id=user_id, name=name, member_type=member_type)
    user.username = name          # ← the argument is never used
```

**This is a live bug, not a tidy-up.** `manage_members` computes a username
(`generate_username` → first initial + last name) and then runs
`ensure_unique_username` against the database — and the value it so carefully
made unique was discarded, with `name` stored instead. So:

- `username` is `unique=True`, and the uniqueness check was being applied to a
  string that never reached the database. **Two members with the same name
  collide on creation.**
- Anyone created this way could not log in with the credential the officer was
  shown.
- For pledges the temp password *is* the generated username, so a pledge was
  handed a password of `jsmith` and a login of `John Smith`.
- `create_superuser` inherited it, so `manage.py createsuperuser` produced a
  superuser whose login was their full name.

Fixed, plus the missing `**extra_fields` that every other Django user manager
takes — which is why all **12** tests in `src/test_page_visits_filter.py` have
been erroring at `setUp` since the module was written. They pass now.

> **⚠️ Behaviour change on deploy.** Existing accounts are untouched. Members
> created *after* this ships get the generated username (`jsmith`) as their
> login instead of their display name (`John Smith`). That is what the
> surrounding code always intended; tell whoever runs Manage Members.

## 6. 🟡 Flag cache invalidation now survives bulk delete

`src/models_feature_flags.py`

Invalidation lived in `save()`/`delete()` overrides. `queryset.delete()` never
calls `Model.delete()` — and that is exactly what the Django admin's **"Delete
selected"** action uses, so a flag deleted from the changelist kept answering
from cache on every worker for up to five minutes, with nothing in the admin to
suggest anything was stale. Moved to `post_save` / `post_delete` receivers,
which fire for both paths. `invalidate_cache()` stays public for the cases no
signal sees (raw SQL, `queryset.update()`, a restored dump).

## 9. The main event: every member join narrowed

`src/models/users.py` (+ ~55 files across `src/view/`, `src/api/`, `src/tasks/`,
`src/models/`)

v3.17.2 established the rule and applied it to two views. An AST scan found
**127 member-join call sites; 122 were still unnarrowed.** All of them now are.

### `member_defer()` and `member_prefetch()`

Two helpers, because at 120 sites the choice of tool stops being stylistic:

- **`.only()` is a whitelist.** Omit one column some template reads and you get
  a query per row — you have re-created the N+1 you were removing, silently, on
  a page you may not have opened.
- **`.defer()` is a blacklist** of columns established as unused outside
  profile / directory / house-map / chat-card. Getting it wrong costs *one*
  extra query on the page that reads it, and nothing else.

So `MEMBER_DISPLAY_FIELDS` + `.only()` remains right where you have read the
template and know exactly what it renders — the legislation pages still use it.
For a sweep, **defer is the one that cannot fail closed**, and that is the whole
reason this release could touch 120 sites at once.

`member_prefetch(lookup)` wraps the `Prefetch(queryset=...)` form, which is
still the only way to narrow a prefetch at all.

### Why a mechanical sweep was safe to run

Every rewrite was AST-driven and conservative: only calls whose arguments are
all string literals, skipping any statement already carrying `.only()`,
`.defer()`, `.values()` or `.aggregate()`, and skipping the four modules that
legitimately render profile columns (`profile_view`, `directory`, `house_map`,
`profile_card`).

The correctness argument rests on one fact, now asserted by a test: **every
relation name that points at ParliamentUser points at ParliamentUser on every
model that has it** — no `reviewer` or `assigned_to` anywhere targets something
else. So deriving the defer paths from the existing `select_related()` arguments
cannot produce a path that does not resolve.

### Measured effect

Per-request ParliamentUser columns selected, same fixture on both trees:

| page | before | after |
|---|---|---|
| `/officers/` (officer home) | 300 | 210 |
| `/officers/activity-logs/` | 121 | 106 |

Those are columns *per request*, multiplied by row count on every joined row.
The legislation pages are unchanged because v3.17.1/v3.17.2 had already narrowed
them.

## 11. 🔴 `ActivityLog.object_id` was a latent login outage

`src/models/activity.py`, migration `0009_activitylog_object_id_charfield`

`object_id` was an `IntegerField`. Most models here have integer primary keys —
but `ParliamentUser`'s pk is `user_id`, a **CharField**, and ~17 call sites log
a user pk into that column. One of them is `signals.log_successful_login`, which
runs on **every login**:

```
ValueError: Field 'object_id' expected a number but got 'hp-Pledge'.
```

raised inside the login signal, which breaks the login itself. The chapter's
member ids happen to be numeric today, and that is the only reason this has not
fired in production — it is **one non-numeric member id away** from locking that
member out. It is also what kept 8 tests in `test_pledge_permissions` red, which
is how it surfaced: the tests were right and the code was wrong.

Now a `CharField(max_length=64)`. Nothing filters or joins on this column — it is
read only by the admin detail fieldset and the activity-log CSV export — so the
widening is display-compatible; integers render exactly as before. The migration
is a plain `AlterField`; Postgres handles the `integer → varchar` conversion with
an automatic `USING` cast.

## 12. `/home/` could not be opened in local dev, and empty `visible_to` was broken everywhere

`src/utils/visibility.py` (new), `src/view/home.py`

The home page filtered event and announcement visibility inline, and both halves
were wrong:

- **`visible_to__contains` is Postgres-only.** SQLite raises
  `NotSupportedError`, so under `DB_BACKEND=sqlite` — the documented local-dev
  setup — the home page could not be loaded **at all**.
- **`visible_to__len=0` never matched anything, on any backend, including
  prod.** JSONField has no `len` lookup, and Django resolves an unrecognised
  name after `__` as a *key transform*. So that clause did not ask "is the list
  empty"; it asked "does this JSON object have a key `len` equal to 0". The
  comment above it said "null/empty visible_to = all", and the null half worked
  — so an event or announcement saved with an explicit empty list was **invisible
  to everyone** on the home page. Silently, in production, in a way no amount of
  reading the SQL backend would explain.

The rule now lives once in `visible_to_q()`, using lookups that behave the same
everywhere: `__isnull`, an exact `[]` comparison, and `__icontains` against the
**JSON-quoted** value. The quoting is what makes `icontains` exact rather than a
substring guess — `MemberType.ALL` is a closed set of five values and none is a
prefix or suffix of another, which `MemberTypesAreUnambiguousTests` asserts, so
adding a type called `Members` fails the suite rather than silently widening a
visibility filter.

*Tradeoff taken deliberately:* on Postgres, `contains` can use a GIN index and
`icontains` cannot. There is no GIN index on either column and these are
chapter-sized tables, so running the same code path in dev, test and prod is
worth more than an index we do not have.

The load-bearing test enumerates every (member type × `visible_to` shape) pair
and asserts the queryset agrees with the models' own `is_visible_to_user()` —
the assertion that would have caught both bugs.

## 13. Calendar feed made version-proof; the last two red tests were mine

`src/view/calendar.py`, `src/test_geo_ip_guard.py`, `src/test_qol.py`

**Correction to the 07-29 report.** Two of the ten "pre-existing red" tests were
an artifact of this sandbox running an unpinned `icalendar` 7.2.2 against a
repo that pins `6.1.0`. On the pinned version they pass. Recorded because the
report asserted them as repo failures.

The underlying fragility is real, though, and is fixed: `cal.add('refresh-interval', 'PT1H')`
works on 6.x but **6.x is the last version that accepts it** — on 7.x,
`Component.add()` routes duration-valued properties through `vDuration`, which
rejects a `str` and raises `TypeError` inside the view, i.e. a 500 on the
calendar subscription feed. With dependabot PRs open, that is a bump away.
Passing an explicit `vDuration(timedelta(hours=1))` emits `PT1H` on **both**
(a bare `timedelta` does *not* — on 6.1.0 it renders `1:00:00`, which is not a
valid ICS duration). Verified by running the feed tests against 6.1.0 and 7.2.2.

The genuinely stale two:

- **`test_geo_ip_guard`** patched `src.utils.security_utils.requests.get`, a
  target that stopped existing in v3.15.3 when the direct uncached call was
  replaced by delegation to `geo_utils.get_ip_geo` and the unused import
  dropped. `patch()` fails loudly on a missing target, so the test had been
  erroring rather than guarding anything since. It now asserts at two levels —
  security_utils must not even delegate, and no HTTP may happen below it.
- **`test_qol`** asserted an empty-state message its own `setUp` made
  unreachable: `force_login` sends `user_logged_in`, so `track_login` records a
  successful login before the request. The view and template were both correct.
  The test now clears the history first, and a second test asserts the row *is*
  created — the same fact, deliberately, rather than by accident.

## 14. The sweep narrowed joins; it never *added* the missing ones

Reported from the dev panel: three identical full-column `ParliamentUser` pk
lookups on one home-page load, all attributed to `home.py:280` — the view's
`render()` call.

**Why §9 could not have caught this.** That sweep narrowed *existing*
`select_related`/`prefetch_related` calls. A queryset with **no**
`select_related` has no join to narrow, so it was invisible to the scan. The
home page's four card querysets had none at all, and
`home_modern.html:317` prints `{{ announcement.posted_by.get_display_name }}` —
one member fetch per announcement.

> **The lesson, recorded because it cost two rounds:** *"every member join is
> narrow"* and *"every member dereference is joined"* are two different
> properties. §9 checked the first and left the second untested.

Fixed on all four (`announcements`, `upcoming_events`, `pending_votes`,
`recently_passed_legislation`), plus `request.user.preferences` in the same view
— a reverse one-to-one dereference for a row the context processor loads and
caches for the same render anyway (extracted as `get_user_prefs`, the Python-side
twin of v3.17.2's base.html fix). Measured on the same fixture: **47 → 43
queries, and full ParliamentUser pk lookups 4 → 1** (the one remaining is
`request.user` itself). Worst duplicate group: 3× → gone.

Then, correcting an over-application in the same edit: `recently_passed_legislation`
got its join **removed again**. That queryset feeds `legislation_previews`, a
list of plain dicts; nothing ever touches the author. Joining a relation nothing
reads is the same mistake as not joining one everything reads, just quieter.

## 16. Dev mode: queries now name the template expression that fired them

`src/dev_mode.py`, `src/middleware/dev_mode.py`, `templates/dev/panel.html`

This is what turned the two rounds above from guesswork into reading an answer
off the screen, and it is the most reusable thing in the release.

A query fired lazily during rendering had a useless stack: Django's frames are
stripped (rightly), which for a template-triggered query leaves exactly one
project frame — the view's `return render(...)`. So the panel showed six
identical member fetches all pointing at `home.py:280`, and the actual cause was
nowhere on screen. You could see *that* there was an N+1 and not *where*, which
is most of the work.

`Node.render_annotated` is the one method every template node passes through and
that no node subclass overrides. Wrapping it keeps a stack of
`(template, line, source)`, and every query is stamped with the innermost few
frames. Each node carries `origin.template_name`, `token.lineno` and
`token.contents`, so the panel names the **expression**, not just a line:

```
template  announcements.html:149   {% if docs %}
template  home_modern.html:317     announcement.posted_by.get_display_name
```

Duplicate groups carry it too, so an N+1 block now leads with the template
expression that caused it rather than the `render()` line every member of the
group shares. Queries with **no** template frames are the view's own — and that
distinction is itself the signal: a query with template frames is by definition
one the view failed to prefetch.

Cost is one ContextVar read per node when dev mode is off (the first thing the
wrapper does), and a push/pop per node when it is on.

## 18. The inverse audit: joins nothing reads

A `select_related` for a relation no template renders is the same mistake as a
missing one, just quieter — it is a join, and on wide tables it was also
dragging columns. An AST audit checked all **360** join call sites against the
enclosing module *and* the full template tree the view renders (following
`{% extends %}` and `{% include %}` transitively).

Two false-positive sources had to be closed before the output was worth acting
on: `home()` selects its template dynamically (`'home_classic.html' if … else …`),
which a `render(request, '…')` regex misses entirely; and the DRF viewsets
reference fields through serializers by name, not attribute access. After both,
**43 candidates**, each verified by hand against its actual template file.

**12 joins removed** across 9 files — `login_history` on the security-alerts
page, `target_committee` and `created_by` on both notification admin pages,
`schedule` on notification logs, `created_by` on three C&B pages, officer home
and the recruitment dashboard, `reviewed_by` on three Kai/committee surfaces,
`report` on the Kai user dashboard, `added_by` on the legacy candidate list.
Most were pre-existing; §9 had dutifully made them *narrow* when it should have
deleted them.

**5 kept**, with the reason recorded: the `src/api/` viewsets, where
`created_by = serializers.StringRelatedField(read_only=True)` means the
serializer does read the relation even though no template does.

Measured on the home page: member joins 3 → 2, ParliamentUser columns 103 → 79,
query count unchanged (43) — which is the proof the removed join was dead.

## 19. Dev mode: the rows a query returned, redacted

`src/dev_mode_rows.py` (new), panel, `src/middleware/dev_mode.py`

Requested directly, and a deliberate exception to this release's own rule that
the panel shows metadata and never record content. The rule was written about
*judicial, ballot and slating* data, and it still holds for exactly those:

> ⚠️ **Redaction fails closed.** A table nobody has classified is withheld, not
> shown. Adding a model and wanting to read its rows here means coming back to
> say so — which is the moment to think about whether its contents are anyone's
> business.

Three layers, in order:

1. **Whole tables, by domain** — every Kai model, every ballot table (`Vote`,
   `CommitteeVote`, `SlatingVote`, `SlatingBallot`), anonymous poll responses
   and answers, slating interviews and application responses, and the
   credential stores (`APIToken`, `WebAuthnCredential`, `PushSubscription`,
   `CalendarSubscription`, `EmailVerificationToken`, `django_session`), plus
   `LoginHistory` and honeypot access. **Withheld whole, not column-redacted** —
   because v3.16.2's lesson is that a timestamp, a sequence or an ordering *is*
   a join key, so a ballot's "harmless" columns still leak who voted when.
   Redaction follows the `JOIN`, not just the `FROM`.

   The Kai set is **derived from `src/models/kai.py`**, so a Kai model added
   tomorrow is covered the day it is written rather than the day someone
   remembers a list. 23 tables total.

2. **Columns, everywhere else** — password hashes, tokens, keys, session
   material, backup codes, and every field built on `EncryptedFieldMixin`, that
   last set also derived from the models rather than enumerated.

3. **Statement type** — SELECT only, single statement, never a write.

Rows come from re-running the captured SQL with its captured parameters inside a
transaction that is **always rolled back**, capped at 25 rows and 120 characters
per cell, with a per-request budget of 40 queries so leaving dev mode on cannot
quietly double a page's work. The panel keeps them collapsed behind a click and
styled muted rather than highlighted: this is the one place it shows content, so
it should take a deliberate action rather than appear while you are reading
query times. Withheld queries say so, with the reason.

Re-running means the values are a *second* read, so a query whose result
depended on state changed later in the request can render differently from what
the view saw. The panel says that on every row set rather than hiding it.

**`src/test_dev_mode_rows.py`** (new, 17 tests) — the redaction is the feature,
and redaction that isn't tested is a comment. Covers: ballot tables withheld
whole; every Kai model covered without being listed; a join that merely touches
a confidential table withheld; credential stores withheld; all four write verbs
refused; an unparseable query failing closed; password and encrypted columns
dropped from an otherwise-shown table; the row cap; the inspector not mutating;
and the panel integration.

## 20. 🟠 `/committees/` was linear in the number of committees

`src/models/committees.py`, `src/view/committee/committee_index.py`

Reported from the panel as `Committee.get_vp` firing **14×, twice over**. Both
halves were real, and the second was the bigger story.

**The double query:** `get_vp()` was

```python
vps = ParliamentUser.objects.filter(roles=self.role)
return vps.first() if vps.exists() else None
```

`.first()` already returns `None` on an empty queryset, so the `.exists()` was
pure cost — two round trips for one answer, which is why one call site produced
two 14× groups. It also dereferenced `self.role` (a query on its own for a
committee with no VP); now `self.role_id`, so no VP costs no query.

**The N+1 behind it:** the same loop also ran four `.exists()` calls for the
viewer's own roles and three `.count()` calls for the badges. About **9 queries
per committee**, on the page whose entire job is listing committees:

| committees | before | after |
|---|---|---|
| 3 | 65 | 39 |
| 14 | **173** | **26** |
| 30 | **349** | **26** |

Now: the viewer's four role sets are fetched once as id sets; the badge counts
are one aggregate (`distinct=True` load-bearing — three multi-valued joins in one
`annotate()` inflate each other); and VPs come from a new
**`Committee.vp_map(committees)`**, two queries however many committees there
are. Extracted as a classmethod rather than fixed in the one view because four
call sites want it and the next one will too.

`vp_map` preserves `get_vp`'s choice exactly — ParliamentUser's Meta ordering is
`['user_id']`, so the VP is the lowest `user_id` holding the role — and a test
asserts the batched map and the per-object method agree, including for a role
with two holders. Batching must not change who is displayed.

## 21. The N+1 test that should have caught §20, and didn't

`src/test_url_smoke.py`

`/committees/` is a zero-argument page, so
`NoNPlusOneOnZeroArgumentPagesTests` walked it every run and saw nothing. Its
fixture created committees with `Committee.objects.create(name=…, code=…)` and no
`role` — and `get_vp()` returns early when `role_id` is None. **The fixture was
testing the early-return path, not the page.**

The fixture now builds committees *with* a role and populates every membership
relation. Verified the way a regression test should be: against the pre-fix code
it now reports `committee_index (/committees/): 6× src_parliamentuser`, and it
passes on the fixed code.

> **Lesson worth keeping:** a fixture that skips optional foreign keys tests the
> null branch. If the thing you are guarding only happens when a nullable
> relation is set, the fixture has to set it.

**Also fixed here, and it was mine:** these two classes GET ~282 pages each,
which fills every cache the site uses. `TestCase` rolls back the database between
tests but **not the cache**, so the entries outlived the rows they described and
the next class inherited them — concretely, `test_login_as` started returning 403
from an admin-only view when this module happened to run first. Both classes now
clear the cache on entry and on cleanup. (Same root cause as the `set_dev_mode`
note in `test_dev_mode_rows`; worth remembering as a general hazard in this
suite.)

## 22. The admin-v2 dashboard seeded its push flags one query at a time

| | FeatureFlag queries | worst repeated shape |

## 23. `/directory/` — a missing prefetch

`src/view/directory.py`

Attribution named it exactly: `directory.html:128 {% if member.roles.exists %}`
and `:130 {% for role in member.roles.all %}`, 12 and 11 repeats.

The three directory querysets now `prefetch_related('roles')`. **That is the
whole fix**, and the templates are unchanged.

Measured with members spread across all four `member_type` values: **40 → 33
queries, worst repeated shape 5× → 2×.**

> ### ⚠️ Correction: CLAUDE.md's checklist is wrong about `.exists()`
>
> Item five on the performance-sweep checklist reads *".exists() called on a
> prefetched relation (bypasses the prefetch cache — use list(.all()))"*.
>
> **On Django 5.2 it does not bypass anything.**
> `RelatedManager.get_queryset()` returns the cached queryset and
> `QuerySet.exists()` short-circuits on `_result_cache`, so once a relation is
> prefetched, `.exists()`, `.all()` and `.count()` are **all zero queries**.
> Measured, not reasoned — `PrefetchCacheBehaviourTests` pins all three.
>
> I believed the checklist, so the first version of this fix also rewrote three
> slating templates and this one from `.exists` to `.all` and claimed a bypass
> that does not happen. Those edits changed nothing and have been reverted; only
> the prefetches remain.
>
> **The real hazard is narrower:** adding a filter first *does* defeat the cache,
> because `member.roles.filter(...)` builds a new queryset that is not the
> cached one. That case is also pinned by a test.
>
> Suggested rewording for the checklist:
> *"`.exists()`/`.count()` on a relation that is **not** prefetched — one query
> per row. Once prefetched, all accessors are free; but `.filter(...)` before
> them starts a new queryset and queries again."*

Three more prefetches added on the same evidence, in the same pattern — the
relation was simply never prefetched:

- `applications_review.py` — `app.interviews` per row (the "Interviewed" marker)
- `apply.py::my_applications` — same marker, no prefetch at all
- `interview_manager.py` already prefetched `interviewers`, so it was fine

## 24. `/chats/` was 138 queries at 30 channels

`src/models/chat.py`, `src/view/chat/chat_index.py`

Reported as `is_member` 15×, the guest-permission `.exists()` 9×, and
`get_unread_count`'s receipt lookup and count 5× and 4×. The cause is that the
index called **`has_access` twice per channel** — once with the admin override
and once without — and each call re-asked the database the same questions about
the same user.

| channels | before | after |
|---|---|---|
| 4 | 48 (worst 8×) | 37 (worst 2×) |
| 15 | **78 (worst 30×)** | **23 (worst 2×)** |
| 30 | **138 (worst 60×)** | **23 (worst 2×)** |

Three new pieces on the model:

- **`access_context(user)`** — everything `has_access` needs about a user, in
  three queries.
- **`access_map(channels, user, admin_override=…)`** — `{id: bool}`, fixed cost.
- **`unread_map(channels, user)`** — `{id: count}` in two queries.

`has_access` gained an optional `ctx=` argument and answers from it when given.
That shape is deliberate: **the access rules still have exactly one
implementation.** Duplicating an authorization predicate is how v3.16.3's Kai
search ended up wrong in two places at once — *"the duplication is why both were
wrong"* — so this changes where the inputs come from, not what the rule is.

And when `view_all` is false the two `has_access` answers are identical by
definition, so the second call is simply not made — that alone was half the cost.

**Verified by exhaustive agreement, not by inspection:** 72 combinations
(6 user kinds × 2 override states × 6 channels covering `open`/`committee`/
`restricted` × active/inactive, with per-user, per-member-type, chairs-only,
officers-only, alumni-only and *expired* grants) — `access_map` matches
`has_access` on every one. `unread_map` matches `get_unread_count` on 12
channels with and without read markers.

`src/view/admin_v2.py`

The N+1 detector was quiet here because **nothing repeated a shape** — this was

|---|---|---|

- `with_members` was `annotate(Count('members')).filter(member_count__gt=0).count()`;

  left as a literal rather than silently changing what the card shows.

## 28. Closing the argument-taking route gap

`src/test_detail_route_smoke.py` (new)

Of 1,216 named routes, **684 take arguments** — 358 of those are Django's own
admin, leaving ~326 app routes that no test had ever requested. Detail pages,
per-committee pages, per-report pages, the entire slating flow.

The new sweep builds one real object of every kind, maps each URL parameter
*name* to a value for it, then GETs every route whose parameters it can satisfy.
Current reach:

| outcome | routes |
|---|---|
| rendered a page (200) — checked for N+1s | **83** |
| POST-only (405) | 85 |
| redirect (302) | 68 |
| 404 — ambiguous parameter got the wrong model's id | 41 |
| skipped, no value for the parameter | 35 |
| API without a token (401) / other | 7 |
| **requested in total — checked for 5xx** | **284** |

**A 404 is deliberately not a failure.** `pk` means a different model depending
on the route, and `field_id` could be a slating, Kai or service field, so a route
may legitimately be handed the wrong kind of id. The assertion is on **5xx and
raised exceptions**, which no argument value can excuse — a missing module, a bad
`defer()` name, or a dead `{% url %}` will 500 whatever you pass it. Both floors
(284 requested, 83 rendered) are asserted so the sweep cannot quietly shrink.

### What it found on the first run

- **§27** — the two `ModuleNotFoundError` 500s above.
- **`slating_applications`** — one `COUNT` per status choice, 8 queries over one
  table.
- **`slating_results_summary`** — three `COUNT`s per voting attempt (so nine
  after three rounds, growing with every re-vote), plus five more for the
  application stats. Both collapsed to one `GROUP BY` each.

All three are the same shapes already fixed elsewhere in this release; they
simply lived behind a URL argument, which is exactly the blind spot the sweep
exists to remove.
