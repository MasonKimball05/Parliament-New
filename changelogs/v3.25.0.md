## The one-paragraph version

v3.24.0 is sound. Everything it claims is true, the AST guard it rebuilt does
what its docstring says, and the `/my-attendance/` fix it shipped is correct in
both its arithmetic and its query count — checked, not assumed. So this release
is not a list of its mistakes.

It is what happens when you take **one sentence v3.24.0 wrote** and ask it of
the rest of the tree:

> *A page's query count starts mattering on the day somebody can click it.*

The obvious follow-up is *what else is expensive and clickable, and why did
nothing tell us?* — and the answer turned out to be a defect in the instrument
rather than in any page. `src/test_url_smoke.py` runs a real N+1 detector over
216 pages on every CI run. Its fixture creates six events, **all of them in the
future**, and every attendance page in this app filters `date_time__lt=now`. So
the sweep has been rendering those pages against an empty list for as long as it
has existed, and reporting them clean.

Fixing the fixture took four minutes and immediately surfaced
**`/officers/attendance/` at 271 queries** — an officer page, used at every
chapter meeting, 240 of whose queries were one method called forty times.

The other finding is the same question asked of v3.23.0's identifier change:
three member-search boxes can no longer find a member by his roll number, and
**they will keep working perfectly on today's roster and fail only for members
initiated from now on.**

## 1 — 🟠 The N+1 sweep's fixture puts every event in the future. **Fixed.**

`src/test_url_smoke.py`, `NoNPlusOneOnZeroArgumentPagesTests`.

The class has a good fixture — six members with varied `member_type`, six
committees each with a `role` and every membership relation filled, C&B
documents with articles and sections, songbook categories with songs, committee
documents of every type, quarantines. Its docstrings record three separate
occasions on which this file learned that a starved fixture makes the detector
blind:

* a fixture that does not **vary** the data (`member_type`),
* a fixture that skips an **optional FK** (`role=role`),
* a fixture that omits a **model entirely** (`_seed_v3_17_5_families`).

This is a fourth, and it is the most deceptive of the four, because it fails
none of the three checks above. `Event` **is** in the fixture. Six rows of it:

```python
Event.objects.create(
    title=f'E{i}', ..., date_time=now + timedelta(days=i + 1), ...)
```

Every attendance page in this app filters `date_time__lt=now`. `Attendance` and
`AttendanceExcuse` had no rows at all.

> ⚠️ **A FIXTURE CAN SATISFY "THE MODEL IS REPRESENTED" AND STILL SIT ON THE
> WRONG SIDE OF THE ONE FILTER THE PAGES APPLY.** A reader auditing this file
> and asking *does the fixture have events?* gets a clear yes. The question that
> had to be asked is what the page's WHERE clause is, not what its table is.

**Measured before the fix, by re-running the module's own sweep against an
enriched fixture and nothing else changed:**

```
--- BASELINE fixture:                216 pages, 0 offenders
--- WITH PAST EVENTS + ATTENDANCE:   216 pages, 3 offenders
    event_attendance_list (/officers/attendance/) total=161: 88x src_attendance
    event_attendance_list (/officers/attendance/) total=161: 22x src_attendance
    event_attendance_list (/officers/attendance/) total=161: 22x src_parliamentuser
```

Same 216 pages, same detector, same code under test. The only variable was
whether the fixture had rows on the correct side of `now`.

`_seed_past_attendance` now adds six past events with attendance marked in all
five statuses, an excuse on each, and a recurring series with instances —
because `/my-attendance/` has a per-series block that is a separate loop from
its history loop, and a fixture with no series would leave that one starved in
exactly the way this finding is about.

## 2 — 🟠 `/officers/attendance/` cost 271 queries. **Fixed — 33, and flat.**

`src/view/officer/event_attendance.py::event_attendance_list`, rendered by
`templates/officer/event_attendance_list.html`.

The view itself is four queries and is not the problem. The template renders
`past_events` **twice** — once as a desktop table (line 190), once as mobile
cards (line 238) — and each row of each layout calls
`Event.get_attendance_stats()`, which is six queries:

```python
total_members  = ParliamentUser.objects.filter(member_status='Active').count()
present_count  = attendance_records.filter(status='present').count()
absent_count   = attendance_records.filter(status='absent').count()
excused_count  = attendance_records.filter(status='excused').count()
pending_count  = attendance_records.filter(status='pending').count()
...            = attendance_records.count()
```

The view caps `past_events` at `[:20]`, so twenty events → **forty calls → 240
queries**, plus ~31 of chrome.

**Measured through the real endpoint, as an officer:**

| past / upcoming | before | after |
|---|---|---|
| 5 / 2   | 91  | **33** |
| 20 / 5  | 271 | **33** |
| 60 / 30 | 271 | **33** |

⚠️ **The `[:20]` cap is why this survived.** The cost was bounded, so nobody
watching a graph would ever see it grow — it was simply 271 every time, from the
day the second layout was added. **A bounded cost is not a small cost, and a
flat line is not evidence of health.**

Two changes, deliberately separate:

* **`get_attendance_stats()` memoises on the instance.** That alone fixes the
  duplicate layout for every caller without any of them knowing, and takes the
  page to 151. The method still works standalone — `EventAdmin`'s detail page
  calls it on one object and pays its six queries, which is correct for one
  object.
* **`Event.prime_attendance_stats(events)`** computes a whole page's worth in
  **two** queries — one active-member count, one grouped conditional aggregate
  — and fills that cache. The view calls it and keeps the returned list.

### Three things in that fix that are load-bearing, not tidiness

**`.order_by()` on the aggregate.** `Attendance.Meta.ordering` is
`['-created_at', 'user__name']`, and Django adds every ordering column to the
`GROUP BY`. Without the clearing call this groups by event *and* `created_at`
and returns one row per attendance record — **a fast page with wrong numbers,
which is worse than a slow page with right ones, and which a query-count test
cannot see.** Same trap as v3.18.6's service-hours aggregates.
`test_the_primed_numbers_match_the_per_event_ones` is what actually pins it.

**`unmarked` counts every row, not the sum of the buckets.** `'late'` is a fifth
status that no bucket counts, so `total_members - marked` and
`total_members - (present + absent + excused + pending)` are different numbers.
The shape of the dict now lives in one `_build_attendance_stats` used by both
paths, so the fast one cannot drift from the slow one, and the fixture includes
`late` marks so the assertion is not vacuous.

**The view must keep the list.** The primed cache lives on the instances; a
queryset re-evaluated after the call would hand the template fresh objects with
an empty cache and silently restore the N+1. The comment says so at the call
site, and `test_it_does_not_scale_with_the_calendar` is the assertion that
catches it.

**New `EventAttendanceListQueryBudgetTests` in `src/test_query_budgets.py`,
`BUDGET = 33`**, plus a scaling property test that needs no ceiling. Its fixture
builds **24** past events, not 20, because a fixture of exactly the view's cap
cannot tell a page that respects the cap from one that does not.

## 3 — 🟡 Three search boxes cannot find a member by his roll number. **Fixed.**

Since v3.23.0, `user_id` is an opaque surrogate (`P-C7JKZY`) assigned at
creation and never changed, and `role_number` carries the roll number.

Three member searches filter on `user_id` and not on `role_number`:

* `src/view/global_search.py` — the chapter-wide search box, officers only.
* `src/view/admin_v2.py::manage_users`.
* `src/view/slating/applications_review.py::applications_list` — the surface
  where an officer is most likely to be working from a written list of numbers
  rather than names.

**Reproduced through the real endpoint** with a member whose `user_id` is
`P-C7JKZY` and whose `role_number` is `173`:

```
PROBE global_search  q=173               -> 200  found= False
PROBE global_search  q=Bartholomew (CTL) -> 200  found= True
PROBE user_list      q=173   (CONTROL)   -> 200  found= True
```

⚠️ **THE NASTIEST POSSIBLE SHAPE, and worth naming.** Every member who exists
*today* still has a legacy `user_id` equal to his roll number, because until
v3.23.0 initiation copied it there. So all three surfaces keep working on the
current roster and fail only for members initiated **from now on**. It would
have surfaced months later as "search is broken for the new guys", long after
anyone would connect it to an identifier change.

⚠️ **And nobody asked the question at all.** `user_list.py` and
`ParliamentUserAdmin.search_fields` both already searched `role_number` — but
`git log -S` puts that in **v2.6.0**. They were covered by an accident of
history, not by a sweep. v3.24.0 asked *who else needed to be told* and found
three home-page badges printing the pk; it did not ask the same question of the
places that take a number as **input**. **A search box is a reader of the
identifier scheme.**

New `src/test_member_search_covers_role_number.py`: an AST walk requiring every
function with a `…user_id__icontains` lookup to offer `…role_number__icontains`
too, keyed on the enclosing function (never the file, per
`test_user_id_is_permanent`'s reason), with an empty-by-design `_EXEMPT` ratchet
— plus the behavioural test above and three controls.

**Negative control:** run against pristine `30e3ae2` copies of the four search
modules it reports exactly the three offenders and correctly leaves
`user_list.py` alone.

## 6 — Second pass: the open items, closed

### 6.1 — `/my-attendance/` has a measured ceiling, in the right file

v3.24.0 measured the page at 25 queries and then shipped its budget class in a
sibling module **with no `BUDGET`**, citing v3.18.6.

> ⚠️ **AN EXEMPTION INHERITED WITHOUT ITS REASONING IS A RITUAL.** v3.18.6's
> reason was *there is no working Django to measure with*, and an invented
> ceiling reads exactly like a measured one. v3.24.0 had a working Django and
> had already measured the page. The rule was right; it did not apply. This is
> the same failure `DEPLOYED.md` records about `--diff-filter=A` — a check
> inherited without its reasoning becomes a ritual, and a ritual will happily
> produce a confident wrong answer.

`MyAttendanceQueryBudgetTests` now lives in `src/test_query_budgets.py` with
**`BUDGET = 34`**, measured twice through `QueryBudgetMixin` (cold cache,
warmed singletons — so it is the pessimistic first-request number and is
comparable with every other ceiling in that module; it is *not* the 25 measured
with a bare `CaptureQueriesContext`). The page's **correctness** tests are not
budget tests and stayed behind, in the renamed `src/test_my_attendance.py`.

**And the ratchet that missed it has been re-keyed.** It enumerated classes
whose name ends `QueryBudgetTests`, **in its own module** — two keys, both
wrong, and v3.24.0's class failed both. It is now keyed on **`QueryBudgetMixin`,
across every `src/test_*.py`**: a class that uses this module's measuring
machinery is a class this module is responsible for, wherever it lives and
whatever it is called.

⚠️ That also resolves a collision the module docstring had been warning about
for months — `src/test_query_narrowing.py` contains a class literally called
`QueryBudgetTests` which is a *scaling* test and would have been swept up by any
name-based widening. It does not use the mixin, so it is correctly out of scope
without anyone having to remember the warning.

⚠️ **The widening needed a control, because every budget class in the tree is
now back in this module** — so green against the real tree would have proved
nothing, which is v3.21.7's *a walk that cannot fail* in a new costume.
`_budget_classes()` therefore takes a directory, and
`test_the_walk_reaches_a_class_in_another_module` builds a module elsewhere,
containing a class named nothing like the convention, and requires the walk to
find it (plus a non-test file whose class it must *not* find).

### 6.2 — `make_event` / `manage_event` deleted

Two views, four routes (`/make-event/`, `/manage-event/` and two legacy
underscore redirects), 238 lines of template, and the two `KNOWN_ORPHANS`
entries. Nothing in `templates/` or `src/` referenced either name; the only
remaining mentions in the tree are comments at the removal sites.

Both views were `render(request, '<name>.html', {})` — no context whatsoever —
superseded by `create_event` / `manage_events` (plural), which is what all six
linking templates use.

⚠️ **`manage_event.html` is why this was worth a diff rather than tolerating.**
It was 229 lines of a *real-looking* announcements page: a heading, a New
Announcement button, an Upcoming Events section. Its view passed `{}`, so every
`{% if %}` in it was false and it could only ever render as an empty shell. A
future officer finds that file, edits it, and nothing changes anywhere on the
site. Same shape as v3.24.0's admin button — a landmine, not a bug.

`test_the_known_orphan_list_only_shrinks` is now pinned at **2**, and the stale
paragraph above `KNOWN_ORPHANS` describing the stubs in the present tense has
been rewritten — leaving it would have been this repo's own false-comment
category, in the file whose subject is unreachable code.

### 6.3 — A fifth detector: raw SQL

`_scan_for_key_writes` had four detectors, all Python-level, and **the operation
the module exists to forbid was originally written in raw SQL.** For the whole
of v3.24.0 the guard was blind to the exact technique it commemorates. That was
survivable only because v3.24.0 swept the tree and found no raw-SQL writer left
— and **a sweep is a fact about one afternoon.** This is the enforcement.

It matches two spellings, both of which this codebase has shipped: a write
naming `parliamentuser`, and a read of `information_schema` (the row-copy
technique). Two new offender fixtures and two new false-positive controls (a raw
`SELECT` on the member table, and an FK rewrite `UPDATE src_vote SET user_id`,
which must stay clean or the guard gets deleted within a week).

⚠️ **Named limitation:** a statement whose table name is interpolated from a
variable is invisible to it — including, ironically, the deleted initiation
code, which built its table names from `_meta.db_table`. That is exactly why the
`information_schema` half exists: the introspection is the part that cannot be
spelled without saying so.

⚠️ **The detector's own control caught a bug in it before it shipped.** The
first regex was `\bparliamentuser\b`; the real table is `src_parliamentuser` and
`_` is a word character, so the leading boundary never matched and the write
fixture went unflagged while the `information_schema` one passed. A control that
only checked "the scan found *something*" would have been green.
