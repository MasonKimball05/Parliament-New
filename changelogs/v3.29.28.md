## What the latest repro showed, and what it proved

Mason reproduced again with v3.29.27 deployed. The log:

```
13:55:12,222  CSRF token refresh called | had_csrf_cookie_before=True | returned_a_token=True | ...
13:55:12,432  CSRF failure | reason=CSRF token missing. | posted_token_present=False | ... | is_js_resubmit=False
```

`is_js_resubmit=False` rules out hypothesis (a) from v3.29.27 —
**and it does more than that.** Walking `base.html`'s submit listener
line by line: every path that reaches `form.submit()` either sets
`tokenField.value` to a real refreshed token, or falls back to an
already-non-empty existing value; the one remaining case (no token AND
no existing value) hits `P.toast(...); return;` and never calls
`form.submit()` at all. There is no code path in that listener that can
reach `form.submit()` with an empty token field. So this isn't just "the
marker suggests it wasn't the resubmit" — it's proven the resubmit
**cannot** have produced this failure, full stop.

That leaves a real gap: `refreshCsrfToken()` has two independent
callers — the `pageshow` handler (proactive, fires on a bfcache restore,
no click involved) and this submit listener (about to resubmit) — and
both hit the exact same endpoint, producing an identical-looking log
line either way. So we don't actually know whether the .222 refresh
was even related to the failure 210ms later, or just a coincidence of
timing (e.g. a `pageshow` refresh from an unrelated bfcache restore,
while some entirely different, un-intercepted submission produced the
actual failing POST).

## The fix

`refreshCsrfToken(attempt, source)` now takes a `source` argument
(`'pageshow'` or `'submit'`), sent to the server as `?source=` on the
existing GET (there's no other way to pass it — this is a GET fetch, no
body). `csrf_token.py` reads it and logs `source=%s` on the existing
`CSRF token refresh called | ...` line. The retry branch
(`refreshCsrfToken(1, source)`) threads the same value through so a
refresh that only succeeds on its second attempt doesn't silently
degrade to unlabeled.

On the next reproduction, the refresh line immediately preceding a
failure will read one of:

- **`source=pageshow`** → confirmed: the refresh was unrelated to the
  failing submission. Combined with this round's proof that the
  submit listener's own resubmit is innocent, this would mean the
  failing POST never touched any of this app's CSRF-handling JS at
  all — a genuinely different class of bug (a native/uncontrolled
  submission bypassing interception entirely) than anything targeted
  in v3.29.24–27.
- **`source=submit`** → the submit listener's refresh really did
  precede the failure. Given the resubmit logic is now proven
  incapable of sending an empty token, this would be the more
  surprising outcome and would need the next diagnostic to look at
  something even more unusual — e.g. whether a *different* submission
  raced the marked one for the same form, arriving first.

### What the `source=submit` result proved

Mason reproduced a second time with v3.29.28 deployed:

```
14:09:13,033  CSRF token refresh called | source=submit | returned_a_token=True | ...
14:09:13,206  CSRF failure | reason=CSRF token missing. | posted_token_present=False | ... | is_js_resubmit=False
```

`source=submit` — a genuine click WAS intercepted this time, and its own
refresh succeeded. But v3.29.27's proof still holds: that exact
listener's own resubmit cannot reach `form.submit()` with an empty
token field. Put together, this can only mean a **second, separate
submission** — one this refresh call knows nothing about — is what
actually failed. The intercepted, refreshed click either succeeded
silently or its own outcome isn't in the pasted log window.

### The fix

`base.html` already has a second, older mechanism — the "Global Form
Submit Protection" script — that silently blocks a genuine second
`submit` DOM event on a form already marked as submitted (10-second
window, existed before any of this saga). That block has always fired
silently. It now also fires a bare `fetch()` GET to the existing
`csrf_token_refresh` endpoint with `?source=duplicate_blocked` (no
token use — purely to produce a log line via infrastructure that
already exists) the moment it detects and blocks a real second submit
event. A hit here around a failure's timestamp is direct proof a second
submission was attempted client-side, rather than something inferred
from silence.

`csrf_token.py`'s module docstring got a third dated entry explaining
this addition and why it follows from the `source=submit` result above.

mystery failing request resembles the real upload or something
thinner/different.

## Addendum 4 — 09-08-26, same day — THE ACTUAL FIX (v3.29.30)

Mason reproduced once more:

```
content_type=multipart/form-data; boundary=----WebKitFormBoundaryf1P8JmCb
content_length=0 | post_field_count=0 | has_file=False
```

Decisive. The Content-Type header — a fresh WebKit multipart boundary,
generated per-submission — proves this genuinely IS the resubmit's own
request, not something unrelated. But the body is completely empty:
zero fields, no file, despite the DOM having a real token and the
resubmit marker set moments before. `form.submit()`, called a second
time on a form whose native submission was already prevented once,
appears to silently serialize an empty body in Safari — most visible on
a form holding a file input. This resolves the "contradiction" every
earlier round hit: `is_js_resubmit=False` was never about the marker
not being set — it was that *nothing at all* made it into the
transmitted bytes.

**⚠️ Open question, not fully closed:** this diagnosis is built entirely
from Safari log data. Mason separately confirmed other members hit the
same symptom on Chromium browsers, and there's no confirmed log sample
proving Chromium produces the identical empty-body signature — it's
possible Chromium's failures share the same proximate cause (a browser
mishandling a second `.submit()` call after one was prevented, which
isn't tightly specified across engines) or a different one entirely
that happens to look the same from the server side. The fix below
doesn't depend on which is true, because it stops relying on native
form re-submission altogether, in any browser — but if a Chromium log
sample ever surfaces, compare it against these same four fields before
assuming this closes that case too.

### The fix

`base.html`'s resubmit no longer calls `form.submit()` at all. It now
builds `new FormData(form)` — reading every current field, including
the file input's current File, at the moment of sending, not asking the
browser to re-serialize a form whose submission was already prevented
once — and POSTs it via `fetch(form.action, { method: 'POST', body:
formData, credentials: 'same-origin' })`. On a successful response,
`window.location.href = response.url` mirrors what a native
redirect-after-POST would have done (a real navigation, so session-based
flash messages render normally). On a failed response or a network
error, a toast tells the member to try again instead of a silent native
failure with zero signal. The `about_to_submit` beacon (v3.29.29) is
removed — superseded, since the real fetch response now tells us
directly what the old beacon could only indirectly infer.

### New tests

`TheFetchBasedResubmitTests` (6 tests, replacing the now-deleted
`ThePreSubmitBeaconTests`): FormData is built after the marker is
stamped; the fetch POSTs to `form.action` with the right method/body/
credentials; Content-Type is never set manually (would break the
boundary the browser generates); a successful response navigates the
browser; a failed response toasts without navigating; a network error
(fetch rejecting) also toasts. Plus a control confirming neither
`form.submit()` nor the old beacon remain in the resubmit body.

Six pre-existing tests across three other classes
(`TheCsrfSubmitSafetyNetExistsTests`, `TheCsrfRefreshRetriesOnFailureTests`,
`TheResubmitMarkerTests`) that asserted on `form.submit()` directly were
updated to check the new `new FormData(form)` call site instead — same
ordering/reachability guarantees, new mechanism.

8 ERROR); restored and confirmed the diff matched exactly (58 lines,

## Addendum 6 — 09-08-26, same day — manage-chapter-documents visibility fix (v3.29.32)

Separate from the CSRF saga above, folded in per the one-changelog-a-day
rule rather than a new file. While confirming the CSRF fix, Mason
uploaded two test documents ("Test" ID 58, "Test 2" ID 59) as
unpublished drafts and then couldn't find them anywhere to delete —
`/chapter-documents/manage-all/` showed only Custom Folders, no
documents at all.

### Root cause

`manage_chapter_documents` (`src/view/manage_chapter_documents.py`)
filtered its document query on `committee=<the Committee row flagged
is_chapter_committee=True>` — a specific Committee object used
elsewhere (meetings/attendance). But `upload_chapter_document`, the
only way to create a document through this feature, sets
`committee=None` for the normal case (nothing selected from its
committee dropdown) — a different concept, "chapter-level," that
`manage_chapter_document.py`'s own edit view already treats as
synonymous with "chapter document" (`document.committee is None` grants
any-officer management there). Nothing the upload form creates by
default ever matched the manage page's filter, so every chapter-level
draft — the normal case — was invisible on the one page meant to show
it, from the moment the feature shipped. Custom Folders rendered
because that query (`ChapterFolder.objects.all()`) was unconditional.

### The fix

The document query now matches: chapter-level (`committee__isnull=True`),
published to the chapter regardless of which committee owns it
(matching what's already visible on the public `chapter_documents`
page), or explicitly tied to the `is_chapter_committee=True` row
(kept for back-compat). Deliberately excluded: an unpublished draft
belonging to some *other* committee — that stays that committee's own
draft to manage until it's actually published, not surfaced to every
officer on a shared page. Also fixed in passing: `total_documents` used
`.count()` after the queryset had already been iterated (and cached) a
few lines above — a redundant `SELECT COUNT(*)` where `len()` on the
already-evaluated queryset does the same thing for free. Added a
"Committee: X" label to the document-row template so a document now
visible here because it was published from another committee is
identifiable as such.

The per-document "quick actions" Mason asked for — delete, publish/
unpublish, edit — already existed end to end via
`manage_chapter_document.py` and were simply unreachable for any
document this bug hid; nothing new needed building there.

### New tests

`src/tests/documents/test_manage_chapter_documents.py`, 11 tests:
