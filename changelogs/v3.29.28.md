## What the latest repro showed, and what it proved

Mason reproduced again with v3.29.27 deployed. The log:

```
13:55:12,222  CSRF token refresh called | had_csrf_cookie_before=True | returned_a_token=True | ...
13:55:12,432  CSRF failure | reason=CSRF token missing. | posted_token_present=False | ... | is_js_resubmit=False
```

`is_js_resubmit=False` rules out hypothesis (a) from v3.29.27 —
**and it does more than that.** Walking `base.html`'s submit listener
line by line: every path that reaches `form.submit()` either sets
`tokenField.value` to a real refreshed token, or falls back to an
already-non-empty existing value; the one remaining case (no token AND
no existing value) hits `P.toast(...); return;` and never calls
`form.submit()` at all. There is no code path in that listener that can
reach `form.submit()` with an empty token field. So this isn't just "the
marker suggests it wasn't the resubmit" — it's proven the resubmit
**cannot** have produced this failure, full stop.

That leaves a real gap: `refreshCsrfToken()` has two independent
callers — the `pageshow` handler (proactive, fires on a bfcache restore,
no click involved) and this submit listener (about to resubmit) — and
both hit the exact same endpoint, producing an identical-looking log
line either way. So we don't actually know whether the .222 refresh
was even related to the failure 210ms later, or just a coincidence of
timing (e.g. a `pageshow` refresh from an unrelated bfcache restore,
while some entirely different, un-intercepted submission produced the
actual failing POST).

## The fix

`refreshCsrfToken(attempt, source)` now takes a `source` argument
(`'pageshow'` or `'submit'`), sent to the server as `?source=` on the
existing GET (there's no other way to pass it — this is a GET fetch, no
body). `csrf_token.py` reads it and logs `source=%s` on the existing
`CSRF token refresh called | ...` line. The retry branch
(`refreshCsrfToken(1, source)`) threads the same value through so a
refresh that only succeeds on its second attempt doesn't silently
degrade to unlabeled.

On the next reproduction, the refresh line immediately preceding a
failure will read one of:

- **`source=pageshow`** → confirmed: the refresh was unrelated to the
  failing submission. Combined with this round's proof that the
  submit listener's own resubmit is innocent, this would mean the
  failing POST never touched any of this app's CSRF-handling JS at
  all — a genuinely different class of bug (a native/uncontrolled
  submission bypassing interception entirely) than anything targeted
  in v3.29.24–27.
- **`source=submit`** → the submit listener's refresh really did
  precede the failure. Given the resubmit logic is now proven
  incapable of sending an empty token, this would be the more
  surprising outcome and would need the next diagnostic to look at
  something even more unusual — e.g. whether a *different* submission
  raced the marked one for the same form, arriving first.

## Addendum — 09-08-26, same day, folded in rather than a new file

**Per Mason: at most one changelog file per day going forward.** This
addendum documents what would otherwise have been `v3.29.29` — same day,
same diagnostic saga, no reason for a separate file.

### What the `source=submit` result proved

Mason reproduced a second time with v3.29.28 deployed:

```
14:09:13,033  CSRF token refresh called | source=submit | returned_a_token=True | ...
14:09:13,206  CSRF failure | reason=CSRF token missing. | posted_token_present=False | ... | is_js_resubmit=False
```

`source=submit` — a genuine click WAS intercepted this time, and its own
refresh succeeded. But v3.29.27's proof still holds: that exact
listener's own resubmit cannot reach `form.submit()` with an empty
token field. Put together, this can only mean a **second, separate
submission** — one this refresh call knows nothing about — is what
actually failed. The intercepted, refreshed click either succeeded
silently or its own outcome isn't in the pasted log window.

### The fix

`base.html` already has a second, older mechanism — the "Global Form
Submit Protection" script — that silently blocks a genuine second
`submit` DOM event on a form already marked as submitted (10-second
window, existed before any of this saga). That block has always fired
silently. It now also fires a bare `fetch()` GET to the existing
`csrf_token_refresh` endpoint with `?source=duplicate_blocked` (no
token use — purely to produce a log line via infrastructure that
already exists) the moment it detects and blocks a real second submit
event. A hit here around a failure's timestamp is direct proof a second
submission was attempted client-side, rather than something inferred
from silence.

`csrf_token.py`'s module docstring got a third dated entry explaining
this addition and why it follows from the `source=submit` result above.

### New tests

`TheDuplicateSubmitDetectionTests` (2 tests) in `test_bfcache_reload.py`
— structural: the diagnostic fetch fires before `e.preventDefault()`
inside the `submittedForms.has(form)` branch (not anywhere else); it
targets the same `csrf_token_refresh` endpoint with the right query
param and `credentials: 'same-origin'`.

## Addendum 2 — 09-08-26, same day

Mason pasted an **11-minute log window** around the `source=submit`
failure above (not just the 3 lines immediately around it) at his own
initiative when asked for wider context. It contains exactly one
refresh and one failure and **nothing else** related to that upload
attempt — no second failure line, no success, no trace whatsoever of
what the marked, properly-tokened resubmit (which the code guarantees
carries a real token if it ever reaches `form.submit()`) actually did.

Also clarified in conversation: this reproduction is genuinely on
**Safari** (mobile), not Arc/Chromium as first said — a momentary
correction, doesn't change anything above. Separately, Mason confirmed
he's aware of **other members hitting the same symptom on Chromium
browsers** — meaning this is not a Safari/WebKit-only bfcache
peculiarity. That matters: it argues against any theory resting on a
WebKit-specific quirk as the *sole* cause, and toward something in
either this app's own shared JS logic or something server/edge-side
that isn't browser-specific. Worth keeping in mind interpreting the next
repro's log, whichever browser it comes from.

### The fix

`base.html`'s submit listener now fires one more diagnostic hit,
`?source=about_to_submit`, immediately before its `form.submit()` call
— using `fetch(..., { keepalive: true })` specifically because a plain
`fetch()` can be aborted mid-flight by the very navigation
`form.submit()` triggers. If this fires with nothing following it
server-side (no success, no `is_js_resubmit=True` failure), that proves
the code reaches the submit call but the resulting request never
actually leaves the browser or never arrives — narrowing the remaining
mystery to "why does the browser silently drop this specific request"
rather than anything left to find in this app's CSRF logic itself.

### New tests

`ThePreSubmitBeaconTests` (2 tests) — the beacon fires between the
marker stamp and `form.submit()`; it uses `keepalive: true`. (First
draft of both tests mistakenly matched this class's own explanatory `//`
comment instead of the real code — `//` comments aren't stripped by the
file's block-comment-only regex — fixed by anchoring on the actual
`fetch()` call's literal URL fragment instead of the bare source value.)
