## 1. `manage_events` N+1 from the recurring-event "Instance" badge (Mason)

`/officers/events/` — the officer event-management list — renders an
"Instance" badge on any event whose `parent_event` is set (a generated
occurrence of a recurring event), reading `event.parent_event.id`/`.title`
per row, in both the desktop table and the mobile card layout. The events
queryset never joined `parent_event`, so displaying that badge cost one
extra query per recurring-instance row on the page — invisible until a
chapter actually has enough recurring-event children on one page for the
count to matter, same shape as `EventAttendanceListQueryBudgetTests`
already documents for a different page.

**Fix:** `.select_related('created_by', 'parent_event')` — self-
referential (`Event` → `Event`), so no `member_defer()` needed for the new
join, just the join itself. Measured before/after on a fixture of 18
standalone events + 1 recurring parent + 9 of its instances (28 rows,
paginated at 25/page so the cap is actually exercised): 34 queries pre-fix,
29 post-fix, same both times. `BUDGET` raised from 25 to 29 with the
measurement documented in the test file.

Caught this review found itself, before discovering Mason was already
fixing it live in the same window: `src.tests.guards`'s query-budget suite
flagged `manage_events` at 29 queries against the (then) budget of 25. By
the time it was traced to the missing join, the fix was already sitting in
the working tree, uncommitted, with a correct budget correction and two
new tests (`test_it_does_not_scale_with_instance_count` — a scaling
control proving the join, not a cap, is what fixed it; and
`test_the_fixture_actually_renders_instance_badges` — a control proving
the fixture actually exercises the `{% if event.parent_event %}` branch at
all, since a budget/scaling pair that passes on a page not exercising the
bug would be measuring nothing). Verified independently in a fresh scratch
checkout rather than trusting the in-progress diff: all 3 tests in
`ManageEventsListQueryBudgetTests` pass, and the full `src.tests.guards`
suite (205 tests) passes with the fix applied.

## 2. `generate_recurring_events` didn't copy reminder configuration

Flagged in v3.28.0's own changelog as found-but-not-fixed: recurring event
instances (`generate_recurring_events`, `src/view/officer/
manage_events.py`) are generated as independent `Event` rows with
`parent_event` pointing back to the original, and
`send_event_reminder_pushes` reads `reminder_N_enabled`/
`reminder_N_hours_before`/`reminder_N_email_enabled` per-row with no
fallback to the parent. None of those six fields (both slots, push and
email) were being passed into the generated `Event(...)`, so every
instance got the model defaults — both reminders off. An officer
configuring reminders on a recurring weekly meeting got them for the first
occurrence (the parent row) and silent reminder-less meetings after that,
with nothing on the create/edit form suggesting the setting wouldn't carry
forward.

**Fix:** copy `reminder_1_enabled`, `reminder_1_hours_before`,
`reminder_1_email_enabled`, `reminder_2_enabled`, `reminder_2_hours_
before`, `reminder_2_email_enabled` from the parent into each generated
instance. `reminder_N_sent_at` is deliberately **not** copied — each
instance has its own independent send state, and copying a sent timestamp
from the parent would make a freshly generated instance that has never
actually dispatched a reminder look like it already had one.

New `src/tests/events/test_recurring_event_reminders.py` (4 tests):
generated instances inherit both reminder slots correctly; `reminder_N_
sent_at` stays null on a fresh instance even when the parent's is set; a
parent with reminders *disabled* generates instances with reminders
disabled (control — the copy isn't just hardcoded to always-True); and a
saved instance with a due reminder is a real row `send_event_reminder_
pushes`'s own candidate query would match, not just a Python attribute set
on the unsaved object. **Verified 2 of 4 fail against the pre-fix code**
(reverted just the copy, reran — the two behavioral assertions failed for
the right reason; the "stays off" control and the "doesn't inherit sent_
at" negative case correctly passed either way, since neither exercises the
missing copy).

## Known, not fixed here, still open

- Prod `RecruitmentEvent` rows possibly stored 5-6 hours off (v3.28.0) —
  needs a human spot-check against prod data, not something fixable from
  a review sandbox.
- Whether `ServiceEvent` should get the same email-reminder toggle
  `Event` has, or keep its separate system (v3.28.0) — undecided, Mason's
  call.
- `generate_recurring_events` also doesn't copy signup-related fields
  (`requires_signup`, `max_signups`, `signups_open`, `allow_waitlist`,
  `rsvp_email_enabled`) to generated instances. **Noticed while fixing
  the reminder gap, deliberately not fixed here** — unlike reminders,
  it's not obvious this is a bug rather than a design choice (each
  occurrence of a recurring event arguably *should* manage its own
  sign-up capacity independently rather than inheriting the parent's).
  Worth Mason's explicit call rather than silently expanding this fix's
  scope to cover it.
