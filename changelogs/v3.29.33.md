## Context

The 09-09-26 auto-run review of v3.29.30 (the mobile-CSRF saga's actual
fix — see `changelogs/v3.29.28.md`'s Addendum 4) found a follow-on bug in
that fix and reported it that same day. v3.29.30 replaced a second
native `form.submit()` — proven to silently serialize an EMPTY body on
WebKit — with `fetch()` + `FormData` in `templates/base.html`'s global
submit listener. That part is correct and stays untouched. But
`fetch()`'s default `redirect: 'follow'` makes the browser transparently
execute the redirect TARGET request *inside* the fetch call, invisibly
to the calling JS. That target request is a real Django request/response
cycle, and `base.html` renders `{% if messages %}{% for message in
messages %}` on every page — so Django's one-shot session flash message
was consumed by that invisible hop before the JS's own, separate
`window.location.href` navigation ever requested the page a second time.
For a validation error that re-renders the form in place instead of
redirecting (confirmed in `upload_chapter_document.py`,
`submit_excuse.py`, `kai_reports.py`, `slating/apply.py`, and likely
more of the ~20 views with a file-input form), it was worse:
`response.ok` was true for that 200, so the old code took the *success*
branch and navigated away, discarding the rendered error and leaving the
member with zero indication anything went wrong.

Verified directly with the Django test client before writing the fix —
not just reasoned about — by POSTing to `bug_report` (same
`messages.error()` + `redirect()` shape) and confirming the message
renders on the FIRST subsequent GET to the redirect target and is GONE
on a second one, regardless of whether anything reads that first
response's body. That is exactly what `fetch()`'s automatic
redirect-following does invisibly, followed by the JS's own separate
navigation.

## The fix

`src/middleware/js_resubmit.py` — new `JsResubmitEnvelopeMiddleware`.
For a POST request carrying the `X-Parliament-Resubmit` header (sent
ONLY by the one `fetch()` call site in `base.html`'s resubmit path —
deliberately NOT the pre-existing `X-Requested-With: XMLHttpRequest`
already used by ~13 other views for their own, unrelated JSON
responses), it intercepts the view's response — after the view runs,
before `MessageMiddleware` decides what to persist — and hands back a
small JSON envelope instead of raw HTML or an HTTP redirect:

```json
{"redirect": "<url>" | null, "messages": [{"text": "...", "level": "success"}]}
```

`redirect` carries the `Location` header's value if the view returned a
3xx, or `null` if the view rendered in place (200). `messages` is read
directly out of `request._messages` — iterating it here marks it used,
the same thing `{% for message in messages %}` does, so
`MessageMiddleware`'s own `process_response` (which runs AFTER this one
— see the ordering note below) will not persist these messages a second
time for wherever the browser eventually, visibly, navigates.

This makes the browser's `fetch()` see exactly ONE HTTP response either
way — never a 3xx it could silently follow — so there is nothing left to
lose: `fetch()` never executes the redirect target at all.

**Scope, deliberately:** only POST + the one header + a 200 or 3xx
response. GET, other methods, 4xx/5xx, and anything already JSON pass
through completely untouched — including the ~13 existing
`X-Requested-With`-keyed endpoints. Not scoped to a hardcoded list of
"the upload views" either; any current or future form routed through
`base.html`'s file-input resubmit path is covered automatically, since
the mechanism is generic rather than enumerated.

**⚠️ Ordering.** Django calls `process_response` in REVERSE of
`settings.MIDDLEWARE`, so "this must run BEFORE `MessageMiddleware` in
the response phase" means it must be listed AFTER
`django.contrib.messages.middleware.MessageMiddleware` in `MIDDLEWARE`
— placed directly after it, before `XFrameOptionsMiddleware`. Get this
backwards and `MessageMiddleware` would persist "still unread" messages
forward before this middleware ever reads them, regressing the fix into
showing every message TWICE instead of the zero times it showed before
today. `TheMiddlewareOrderingTests` in the new test file pins the
relative position directly.

`templates/base.html`'s resubmit fetch now sends the header and parses
the JSON envelope instead of trusting `response.ok`/`.url` directly:
each message in the payload is shown via `P.toast()`, and navigation
only happens when `redirect` is non-null. On a validation error
(`redirect: null`), the member stays on the page with their typed input
and selected file intact — the toast already told them why, and nothing
is silently discarded anymore.

## New tests

`src/tests/security/test_js_resubmit_envelope.py` (10 tests), against
real views, not a synthetic urlconf:

- `TheMiddlewareOrderingTests` — pins `JsResubmitEnvelopeMiddleware`
  after `MessageMiddleware` in `settings.MIDDLEWARE`.
- `RedirectCaseTests` (`bug_report`) — an untagged POST is untouched
  (control); a tagged POST with a validation error returns the envelope
  with the error message and a redirect; **the message does not arrive a
  second time on a later plain GET to the same URL** — the actual bug,
  proven end to end; a tagged successful POST also arrives as an
  envelope with the success message.
- `RenderInPlaceCaseTests` (`upload_chapter_document` — the actual view
  this whole saga is about) — a tagged validation error (missing file/
  title) arrives as an envelope with `redirect: null`; the untagged
  version is confirmed to really be a 200 HTML render, not a redirect
  (control, otherwise this class would be testing the wrong shape); a
  tagged successful upload still produces a redirect in the envelope.
- `PassthroughTests` — a GET with the header is never wrapped; a 403
  (non-officer hitting an officer-only view) is never wrapped either,
  matching the JS's existing generic-failure-toast handling for non-2xx
  responses.

`src/tests/security/test_bfcache_reload.py`'s `TheFetchBasedResubmitTests`
— one v3.29.30 test (`test_a_successful_response_navigates_the_browser_there`,
which asserted the now-removed direct `response.ok` → `window.location.href
= response.url` shape) replaced with four: the header is sent; the
response is parsed as JSON before any branching; messages from the
envelope are toasted; navigation only happens when `redirect` is
present. The other three v3.29.30 tests (failed-response toast, network-
error toast, old-mechanism-removed control) needed no changes — they
still hold under the new code.

## Known, not addressed here

- The 4xx/5xx passthrough case still relies on the JS's pre-existing
  generic "could not be completed" toast rather than relaying a
  view-specific message — acceptable per the report that prompted this
  fix, since these are already-exceptional paths (permission denied,
  server error) rather than the two paths (success, validation error)
  every one of the ~20 affected views actually exercises in normal use.
- Not re-verified against every one of the ~20 file-upload views
  individually — `bug_report` and `upload_chapter_document` were chosen
  because they cover both response shapes these views use (redirect-only
  and render-in-place), and the middleware's behavior is generic (keyed
  on the header + status code, not on which view produced the response),
  so this isn't expected to need per-view changes. Worth a spot-check on
  a couple more of the ~20 (e.g. `submit_excuse`, `kai_reports`) next
  time one of them is touched for an unrelated reason.
