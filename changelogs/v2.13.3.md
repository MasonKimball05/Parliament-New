# v2.13.3 - Decorator Hardening

**Release Date:** May 10, 2026

**Deployment Status:** Deployed

**Type:** Code Quality / Maintainability

## Overview

Four related problems in Parliament's decorator layer were fixed. None of these change what any page does — every permission check, every redirect, and every access rule is identical to before. The changes are about correctness, consolidation, and eliminating dead code that was easy to misread.

---

## Problem 1 — `@wraps` Missing on All Decorators

### What the problem was

Python's `functools.wraps` is required when writing decorator wrappers. Without it, the wrapper function replaces the original function's metadata — its `__name__`, `__doc__`, `__module__`, and other attributes — with its own. All six decorators in `src/decorators.py` were missing it:

```python
# Before — every decorator looked like this
def officer_required(view_func):
    def wrapper(request, *args, **kwargs):
        ...
    return wrapper   # <-- wrapper's __name__ is 'wrapper', not 'officer_home'
```

This has practical consequences:

- **Django URL reverse can fail.** Django identifies views internally by their function name. When a decorated view returns `wrapper` everywhere, tools that inspect view names see `wrapper` instead of the actual function, which can cause cryptic failures.
- **Stack traces are misleading.** An exception inside `officer_required` shows `wrapper` in the traceback, not the view that was actually called.
- **Admin and debug tools show garbage.** Django admin's view list, `django-extensions` graph_models, and similar tooling all show `wrapper` instead of the correct function name.

### What was done

`@wraps(view_func)` was added to all six decorators:

```python
from functools import wraps

def officer_required(view_func):
    @wraps(view_func)
    def wrapper(request, *args, **kwargs):
        ...
    return wrapper   # <-- now __name__ is 'officer_home', __doc__ preserved
```

**Decorators fixed:** `log_function_call`, `committee_chair_required`, `officer_required`, `officer_or_advisor_required`, `admin_required`, `exclude_pledges`

## Problem 2 — Decorators Defined Outside `src/decorators.py`

### What the problem was

Three decorator definitions had drifted out of `src/decorators.py` into view files:

**`kai_chair_required` in `src/view/kai_form_builder.py`:**
This decorator was defined right alongside the views it was protecting. The consequence is that any other view that needed to protect access to Kai-chair-only logic couldn't import the decorator without importing `kai_form_builder.py` — a view file — as a dependency.

**`bug_admin_required` in `src/view/bug_report.py`:**
Same problem. The decorator was local to the file, making it unavailable for reuse without a circular-style import of a view module.

**A weaker copy of `require_admin_v2_auth` in `src/view/notification_admin.py`:**
This was the most consequential one. `notification_admin.py` had its own definition of `require_admin_v2_auth`, but it was missing two security checks present in the real version in `admin_v2.py`:

```python
# notification_admin.py's copy — only checked the session key
def require_admin_v2_auth(view_func):
    def wrapper(request, *args, **kwargs):
        if not request.session.get('admin_v2_authenticated'):
            return redirect('admin_v2_login')
        return view_func(request, *args, **kwargs)
    return wrapper

# admin_v2.py's real version — also checks user ID and 7-day timeout
def require_admin_v2_auth(view_func):
    def wrapper(request, *args, **kwargs):
        if not request.session.get('admin_v2_authenticated'):
            return redirect('admin_v2_login')
        # Additional: validates the authenticated user_id matches the session
        # Additional: enforces 7-day timeout on the session token
        ...
```

The notification admin pages were protected by a lighter-weight check than the rest of the admin v2 panel.

### What was done

- `kai_chair_required` was removed from `kai_form_builder.py` and the file now imports it from `src.decorators`
- `bug_admin_required` was removed from `bug_report.py` and the file now imports it from `src.decorators`
- The weak local copy of `require_admin_v2_auth` was removed from `notification_admin.py`; it now imports directly from `src.view.admin_v2`

All three decorators are now defined in exactly one place. Notification admin pages now use the full auth check.

## Problem 3 — Redundant `@login_required` Stacking

### What the problem was

Several views were decorated with both `@login_required` and a custom auth decorator:

```python
@login_required       # <-- dead code
@officer_required
def attendance(request):
    ...

@login_required       # <-- dead code
@vpp_required
def service_dashboard(request):
    ...
```

Every one of Parliament's custom decorators (`officer_required`, `vpp_required`, `kai_chair_required`, `bug_admin_required`, `exclude_pledges`, etc.) already checks `request.user.is_authenticated` and redirects to `'login'` if not authenticated. The `@login_required` on top does nothing — the inner decorator catches unauthenticated users first regardless.

Dead decorators create a false impression that the auth check is coming from `@login_required`, when in reality the custom decorator is doing all the work. A future maintainer might remove the custom decorator thinking `@login_required` covers it.

### What was done

The redundant `@login_required` decorators were removed from 17 views across 6 files. The unused `from django.contrib.auth.decorators import login_required` imports were also removed from files where `login_required` was no longer used anywhere.

| File | Views fixed |
|---|---|
| `src/view/service_hours.py` | 11 views |
| `src/view/activity_logs.py` | 2 views |
| `src/view/service_form_builder.py` | 2 views |
| `src/view/submit_new_version.py` | 1 view |
| `src/view/upload_legislation.py` | 1 view |
| `src/view/reopen_legislation.py` | 1 view |

Note: `chapter_documents.py` has `@login_required` above `@require_page_enabled`, which is intentional — `require_page_enabled` does not check authentication, so removing `@login_required` there would let unauthenticated users hit the page-enabled check first. That one was left alone.
