## 🟢 Backup restore drill: prove the nightly backup actually restores

**Why.** `parliament-backup.timer` writes a `pg_dump -Fc` archive every night,
and nothing has ever restored one. Every way a backup goes bad is silent: the
timer stops, a full disk leaves a truncated file, the dump is of the wrong
database, or the archive won't restore into the Postgres you have. You find
out on the day you need it.

**What.** `python manage.py verify_backup`
(`src/management/commands/verify_backup.py`). Each step stops the drill on
failure:

1. **Fresh:** the newest `*.dump` in `/var/backups/parliament` (or
   `PARLIAMENT_BACKUP_DIR` / `BACKUP_DIR`) is under 48 hours old. This
   catches a backup timer that died.
2. **Readable:** `pg_restore --list` reads the archive and finds table data.
3. **Restores:** a full `pg_restore --exit-on-error` into a throwaway
   database, `<DB_NAME>_restore_check`. That database is dropped afterwards
   in a `finally`, and before the restore too, in case an earlier run died.
4. **Plausible:** row counts in 8 core tables are at least 50% of live, and
   every migration in the copy is one the live database applied. This
   catches an empty dump or a dump of a different database.

A **failure** sends a critical `BACKUP_VERIFY_FAILED` security alert (emailed
to `SECURITY_ALERT_EMAIL`) and exits non-zero, so systemd logs it as failed.
A **success** logs a low-severity `BACKUP_VERIFIED` row in the security
notification log, with no email. The admin security log then shows when the
last good drill ran.

**Confidentiality.** The drill only counts rows, and none of the counted
tables are Kai, Slating or vote tables. Nothing from the restored copy is
printed or emailed except those counts and migration names. The password is
passed in `PGPASSWORD`, never on the command line.

**Options.** `--file X.dump`, `--list-only` (steps 1–2, for a role without
CREATEDB), `--max-age-hours`, `--min-ratio`, `--no-alert`.

**Verified against real Postgres 16** before writing the tests: a real
dump restored, and a copy truncated to 60% failed at `pg_restore`. A dump
older than 48h, an empty directory, a dump of a different database and a
role without CREATEDB each failed with a clear message. No
`_restore_check` database was left behind in any case.

**Tests:** `src/tests/infra/test_verify_backup.py` (14 tests; the suite runs
on SQLite, so the pg tools are mocked). The test for dropping the throwaway
database was checked by removing the drop, which makes it fail.

### Install (one time, on the server)

```bash
sudo -u postgres psql -c "ALTER ROLE <DB_USER> CREATEDB;"   # step 3 creates the throwaway DB
sudo cp parliament-backup-verify.service parliament-backup-verify.timer /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now parliament-backup-verify.timer
sudo systemctl start parliament-backup-verify.service         # one drill now
journalctl -u parliament-backup-verify -n 30                  # read the result
```

The timer runs **Sundays at 04:30**, an hour after the 03:30 nightly backup.
It runs as root like `parliament-backup`, because the backups are written
0600 as root. Its `PATH` includes `/usr/bin`. The other units set `PATH` to
the venv only, which would hide `pg_restore`.

If you'd rather not give the app role CREATEDB, change `ExecStart` to add
`--list-only`. You lose step 3, which is the step that proves the restore.
