# v3.15.6 — page-visits member filter + 07-23 review fixes

Small feature + two perf cleanups from the 07-23 auto-run report, plus one
latent bug found while implementing. No migration; no new dependencies.

## Page Visits: filter by individual member (feature)

`admin-v2/page-visits/` previously only aggregated by path (total + unique
users), with a per-user breakdown only after drilling into a single path.

- **New member filter on the top-level dashboard** (`?user=<term>`): restricts
  every row's Total Visits / Unique Users to members whose name, preferred
  name, or username contains the term (case-insensitive) — answers "what has
  this member been looking at" in one step. Matched members are shown as chips
  above the table (first 20), with a clear empty-state when nothing matches.
- The filter carries through the sort toggles, the column-header sort links,
  and the drill-down links (and the drill view's "All Pages" back link), so
  you can pivot between views without retyping it.
- Drill-path values in links are now `|urlencode`d.

### Latent bug fixed while in here — in THREE admin-v2 views

The drill view's existing name filter queried
`user__first_name__icontains` / `user__last_name__icontains` — **fields that
don't exist on `ParliamentUser`** (it extends `AbstractBaseUser`, which has
neither). Any actual use of that filter box raised `FieldError` (500). Both
page-visit views now share `_page_visit_user_q()` matching the real fields:
`name` / `preferred_name` / `username`.

A repo-wide grep found the same dead lookups in two more admin-v2 views, both
fixed the same way:

- **legislation management** (`?search=`) — `posted_by__first_name/last_name`
  → `posted_by__name/preferred_name/username` (title match unchanged)
- **login history** (`?user=`) — `user__first_name/last_name`
  → `user__name/preferred_name` (username match already present)

All three search boxes were 500-on-use; they now work. No other live
`first_name`/`last_name` lookups remain in `src/` (grep-verified).

## 07-23 report item #3 — kai_reports double query (perf)

`src/view/kai_reports.py`: removed the three-tier schema-probe fallbacks
(`member_status` → `is_active` → all users) around the `targeted_to` form
queryset (2 sites) and the try/except around `select_related` in
`view_kai_reports` / `export_kai_reports_csv`. The probes' discarded
`list(queryset)` force-evaluations doubled the member-table query per form
render; the fallbacks existed for a legacy test DB without the real schema —
obsolete since the 07-05-26 migration consolidation (test DBs are built from
the tracked migrations). The detail-view try/excepts around prefetched
relations were left as-is (they don't double-query).

## 07-23 report item #4 — view_logs tail read (perf)

`src/view/officer/view_logs.py`: `f.readlines()[-200:]` loaded up to the full
10 MB rotation cap into memory per page view. New `_tail_lines()` seeks to the
last 256 KB, drops the partial first line, and returns the final 200 complete
lines. Verified against a synthetic ~900 KB log (exact last-200 selection,
small-file and empty-file cases).
