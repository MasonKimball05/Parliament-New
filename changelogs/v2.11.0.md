## Overview

Major security update introducing a full suite of attack mitigation tools: auto-quarantine, honeypot/poison pill endpoints, emergency lockdown mode, and security email notifications. Also includes a complete redesign of the admin-v2 dashboard with a modern card-based layout using Alpine.js.

## Security Features

### Session Tracking Middleware

**Problem:** The preferences page showed 0 active sessions for all users.

**Root Cause:** Sessions were not being tracked on each request.

**Solution:** Created `SessionTrackingMiddleware` that updates session records on each authenticated request, throttled to 5-minute intervals using cache to reduce DB load.

**Files Changed:**
- `src/middleware/session_tracking.py` *(new)*
- `Parliament/settings_postgres.py` — added middleware to `MIDDLEWARE` list

---

### Auto-Quarantine System

Accounts that trigger attack detection thresholds (20+ attacks from a single IP) are automatically quarantined. Quarantined accounts cannot log in until manually released by an admin.

**How it works:**
1. Security middleware tracks attack count per IP
2. When threshold is crossed, the associated user account is quarantined
3. Login view checks `is_quarantined` flag before authenticating
4. Admin can release quarantine via admin-v2 or Django admin

**Files Changed:**
- `src/middleware/security.py` — added auto-quarantine trigger
- `src/view/login_view.py` — added quarantine check pre-login
- `src/models.py` — added `is_quarantined` field to `ParliamentUser`, added `QuarantinedAccount` model

### Emergency Lockdown Mode

One-click emergency lockdown blocks all logins except for IPs on the whitelist. A user-friendly lockdown page is shown to blocked visitors.

**Features:**
- Singleton `SystemLockdown` record in DB
- Whitelisted IPs (comma-separated) can still log in
- Custom message shown to blocked users
- Activation/deactivation logged with admin and timestamp

**Files Changed:**

### Page Toggles Fixed

Page enable/disable toggles in the admin-v2 dashboard had three bugs:

1. **Blank labels / always showing OFF** — Template used nonexistent fields `page.name` and `page.is_visible`. Corrected to `page.display_name` and `page.is_enabled`.
2. **Scrolling to top on click** — The toggle button's click event bubbled up to an Alpine.js `@click="expanded = !expanded"` on the parent element, collapsing the section and jumping to the top. Fixed with `event.stopPropagation()` and `type="button"`.
3. **State not updating after toggle** — CSRF token retrieval from `document.cookie` was unreliable. Fixed by adding a hidden `{% csrf_token %}` form in the template and reading the token from the DOM via `FormData`.

**Files Changed:**
- `templates/admin_v2/dashboard.html`

### Active Sessions Fix (Production)

Active sessions and login alerts were not appearing on prod. Two root causes:

1. **Missing middleware in prod settings** — The production `settings_postgres.py` (not in GitHub) did not include `SessionTrackingMiddleware` or the security middleware added in this release. These were added manually to prod.
2. **`cleanup_expired_sessions` deleting all sessions on Redis** — Production uses Redis-backed sessions; the `django_session` DB table is empty, so the old cleanup code deleted every `UserSession` record. Fixed to use `last_activity` age-based cutoff when the session backend is not the DB backend.

**Files Changed:**
- `src/models.py` — `UserSession.cleanup_expired_sessions()` now checks `SESSION_ENGINE` setting

---

### Force Password Change Fix (Production)

After adding `ForcePasswordChangeMiddleware` to prod, users with `force_password_change=True` already set in the DB were unexpectedly prompted to change their password. Resolved by clearing the flag on affected accounts via the Django shell.

### Honeypot Notification Digest

Honeypot hits were previously sending an immediate `critical` email on every access, creating noise for routine scanner/bot activity.

**New behaviour:**
- Routine honeypot hits are logged to the DB only — no immediate email
- A daily digest email summarises all hits from the last 24 hours (total count, top endpoints, top IPs)
- **Serious hits still fire immediately** as a `critical` email:
  - Same IP hits 3+ distinct honeypot endpoints within 1 hour (coordinated recon)
  - POST requests that include form field data (credential probing attempt)

**Setup — add to cron (run once daily):**
```
# 8pm every evening
0 20 * * * cd /path/to/project && /path/to/venv/bin/python manage.py send_honeypot_digest
```

**Files Changed:**
- `src/security_notifications.py` — `alert_honeypot_triggered` downgraded to `severity='low'` by default; added `escalate` parameter and `send_honeypot_digest()` function
- `src/view/honeypot.py` — added escalation logic (multi-endpoint recon, POST credential probes)
- `src/management/commands/send_honeypot_digest.py` *(new)* — management command for cron

## Deployment Notes

1. **Run migrations:**
   ```bash
   python manage.py migrate
   ```

2. **Set environment variable:**
   ```bash
   SECURITY_ALERT_EMAIL=your-admin-email@example.com
   ```

3. **No data migration required** — all new models start empty.

4. **Test honeypots** by visiting `/wp-admin/` while logged in as admin to confirm logging works.

5. **Verify lockdown** by activating/deactivating from `/admin-v2/security/lockdown/` in a staging environment before deploying.
