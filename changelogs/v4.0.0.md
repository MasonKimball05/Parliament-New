### New: `/api/mobile/v1/`

| Route | What |
| --- | --- |
| `auth/login/` | Password sign-in through the same checks as `/login/` (shared `src/login_pipeline.py`). Returns tokens, or `mfa_required` + a 5-minute ticket, or `mfa_setup_required` (no token) |
| `auth/verify/` | Authenticator or backup code against the ticket; same failure counting and alert as the web verify page. A locked IP gets `locked` before the ticket is touched, so it isn't used up |
| `auth/passkey/begin/`, `complete/` | Native passkey sign-in; origins = the site plus `MOBILE_ANDROID_APK_KEY_HASH_ORIGINS` |
| `auth/refresh/`, `auth/logout/` | Token rotation; sign this device out |
| `auth/web-session/` | One-time code for the web-view handoff |
| `me/` | Profile, member type, flags and page toggles the app uses to show tabs; `links.education` (the Education dashboard path when the Home page shows that card, else `null`) |
| `ws-ticket/` | 30-second websocket ticket (sent as a subprotocol, never in the URL) |
| `devices/`, `devices/<id>/revoke/`, `devices/push-token/` | Your signed-in phones; register the Expo push token |

**Tokens:** 15-minute access, 30-day refresh, rotated on every use, never
stored except as SHA-256 hashes. A device can live 90 days
(`MOBILE_DEVICE_MAX_AGE_DAYS`) before a fresh sign-in. A replayed refresh
token gets one 60-second grace use; any other reuse revokes the device and
alerts the member.

**Every request re-checks the device** (`MobileDevice.still_allowed`): not
revoked or past its age, user active, not quarantined, not Removed, password
unchanged (via Django's session-auth hash, so any password change by any path
signs the app out), and, for a device signed in with a password alone, that the
member still has no 2FA and isn't required to.

**One error shape:** every mobile view subclasses `MobileAPIView` (or
`PreAuthAPIView`), so every error is `{"error": code, ...}`: `not_authenticated`,
`invalid_token`, `token_expired`, `signed_out_<reason>`, `not_found`,
`throttled`, ... (`views_session`, `views_devices`, `views_push` used to answer
DRF's code-less `{"detail"}`).

**Throttle:** signed-in mobile views have their own per-member `mobile` scope,
`MOBILE_API_THROTTLE_RATE` (default 1200/hour), not the site-wide DRF `user`
300/hour. Login, verify, passkey and refresh keep their stricter per-IP and
per-device limits.

**Guard test** `src/tests/guards/test_mobile_views_use_mobile_auth.py`: every
mobile route uses the mobile auth class and `MobileAPIView`, except the five
listed pre-auth ones (`PreAuthAPIView`).

### New: web view handoff (`POST /m/handoff/`)

The app's web view gets a normal session by POSTing a one-time code **and** the
same device's access token. The code alone does nothing, never appears in a
URL, and the redirect is sent with `Referrer-Policy: no-referrer`.

The token comes as the form field `access_token` or as `Authorization: Bearer`
(both checked the same way; if both are sent they must match). The form field
is there because Android's web view drops headers on a POST load. Either
credential in the query string is refused, the field is redacted from error
reports and never scanned into the attack log, and a request the browser marks
cross-site (`Sec-Fetch-Site`, or a foreign `Origin`) is refused, so nobody can
post their own code and token into someone else's browser. The session
is flushed first, then marked 2FA-verified exactly as the website does after
the verify step (or the passkey flag), and carries `mobile_device_id` and the
device's sign-in geo result, so the non-US export block still applies.

`MobileSessionGuardMiddleware` logs out any session whose device is no longer
allowed, on HTTP and on websockets. No LoginHistory row or new-device alert is
written per handoff; the app sign-in already recorded one.

### New: native push

- `send_push_notification` (same signature, so every call site is unchanged)
  now queues `send_web_push` and `send_native_push`; each retries only what
  failed. The old task declared retries but never retried.
- Expo's HTTP API is called directly, ≤100 messages per request, with
  `EXPO_ACCESS_TOKEN` (Enhanced Push Security; `src.W020` warns while it's
  empty). `DeviceNotRegistered` clears the token; receipts are checked every
  15 minutes (`tasks.check_expo_push_receipts`).
- Only devices that pass the live check get pushes; a failing device's push

- Pushes carry `{url, screen, id}`; `src/mobile/deeplinks.py` maps site paths
  to app screens and refuses anything that isn't a same-site path. `/chats/` is
  `chat` with no id (the channel list); the query string is ignored for
  matching but kept in `url` (`/calendar/?year=…&month=…`).
- **Now push (in-app before):** excuse reviewed, role knowledge base, chat
  mentions, security alerts, API-token expiry, scheduled reminders. Each has a
  push preference (new JSON keys, on by default; toggles on Preferences).
  Security alerts and excuse reviews push a generic line; details stay in-app.
- Web push: a 404 now removes the subscription, like 410.
- Event reminders linked members to an officer page that isn't a route; they
  now open the calendar on that month.

### New: app links

`/.well-known/apple-app-site-association` (universal links + passkey
`webcredentials`) and `/.well-known/assetlinks.json` (app links +
`get_login_creds`). Both 404 until the settings below are set, and are reachable

### 🟢 Mobile Phase 3 (part 1): Home and Notifications endpoints

The first native-screen endpoints for the app, under `/api/mobile/v1/`. The
app's Home tab and the notification bell can now load from JSON instead of
the web view.

#### Endpoints
- **`GET home/`**: the whole Home screen in one request.
  - `pending_votes`: open chapter ballots the member hasn't cast (up to 5).
    It's `null` (not `[]`) when they can't vote, the `legislation_voting`

    "nothing to vote on" from "no Votes tab". Committee ballots come with the

- **`GET notifications/count/`**, **`POST notifications/<id>/read/`** (someone
  else's id is a 404) and **`POST notifications/read-all/`**.

Every item carries `target` (`{url, screen, id}`), the same routing a native
push uses, so tapping a notification and tapping its push land in the same
place. Links that aren't same-site paths become `/home/`.

#### One rule set with the website
- **Same queries.** Home uses the web page's `open_for_voting()`, the
  `visible_to_q` audience rule and the cached badge counts.
- **Shared code.** The two unread counts moved out of the context processor
  into `unread_notification_count()` and `unread_chat_count()`. Mark-read and
  mark-all-read moved out of the web views into `mark_read()` and
  `mark_all_read()`, announcement-view stats included. The website calls the
  same functions, unchanged.
- **Web-page gates.** `MobileAPIView` has a new `web_page` setting: the url
  name of the web page an endpoint mirrors. That page's toggle and pledge
  restriction then apply to the app too, since both key on the web name
  (`home`), which a `mobile_home` route would otherwise slip past.
  `web_page_toggle = False` skips the toggle for a page that has none on the
  web (Notifications). The guard test now fails any mobile route other than
  the sign-in plumbing that doesn't name a real web page.

#### Tests
`src/tests/mobile/test_home_and_notifications.py` (18 tests): own-only
listing, paging, filters, unsafe links, 404 for others' notifications, the
toggle and pledge gates, ballots hidden for pledges and when voting is off,
and a query budget for Home. The guard test was checked by removing
`web_page` from Home, which made it fail. Full suite on Postgres: all pass
except the two checks that clear on their own (the unstamped ledger, and the
pre-push hook test while `scripts/pre-push.sh` has the uncommitted folder-move
path edit).

#### Every mobile request now checks its token once
The site-wide middlewares (`bearer_device()`, used for lockdown, quarantine
and pledge pages) and DRF's `MobileTokenAuthentication` each ran the full
token check on every request. That's the device, plus
`still_allowed()`'s three second-factor lookups for a password-only device:
8 queries where 4 do. Both now call one `check_access_token()`, remembered on
the request per token. Nothing is skipped, only not repeated, and the memo
dies with the request, so a device revoked between two requests is refused
on the second. Home's query budget drops from 11 to 7.
`src/tests/mobile/test_auth_checked_once.py` pins one device lookup per
request. Switching the memo off fails both it and Home's budget (2 lookups,
11 queries).

## Formerly v3.54.0 (`c88998e`)

### 🟢 Mobile Phase 3 (part 2): Calendar endpoints

Under `/api/mobile/v1/`, for the app's Calendar tab:

- **`GET events/?from=YYYY-MM-DD&to=YYYY-MM-DD`**: visible events in a date
  range, in the chapter's time zone with `to` inclusive. Defaults to today
  plus 31 days. At most 93 days per request, within a year either side of
  today (the web calendar's window).
- **`GET events/<id>/`**: one event. Hidden, inactive or archived is a 404.
- **`POST` / `DELETE events/<id>/signup/`**: sign up (or join the waitlist)
  and cancel. Refusals are `{"error": "signup_refused", "detail": <the web
  page's message>}`.
- **`GET calendar/subscription/`**: the member's `webcal://` feed URL, for
  "Subscribe". Behind the `calendar_subscriptions` flag, like the web.

Each event has its sign-up state (counts, full, waitlist, the member's own
status), excuse state (`Event.can_submit_excuse`, any excuse's status), add-to-
calendar links and `updated_at`, so the app can refresh a cached event.

**Same rules as the website.** The audience rule is `visible_to_q`, the SQL
twin of `Event.is_visible_to_user`. The `calendar` page toggle and pledge
restriction apply through `web_page`. Sign-up also honours restrictions on the
web buttons' own names (`event_signup`, `event_cancel_signup`), because on the
web those are separate restrictable routes.

**Sign-ups are one implementation.** The join/cancel logic (row lock,
waitlist, promotion on cancel, 404 for an event you can't see) moved out of
the two web views into `src/event_signups.py`. The website's buttons and the
app both call it. Unlike `/api/calendar-data/`, the app's list fetches
sign-up counts and the member's own sign-ups and excuses once per page, not
per event (the query count is the same for 3 events and 13).

### 🟠 Fixed: the last sign-up slot could never be taken

`event_signup` saved the member's new sign-up as confirmed (`get_or_create`)
and only then counted confirmed sign-ups to see if a slot was free, so it
counted the member themself. On an event with N slots the Nth person was put
on the waitlist, or refused with "This event is full" if there was no
waitlist. A 1-slot event waitlisted its first sign-up. Their own row is now
left out of the count. Regression tests go through both the web button and
the app, and both fail with the old count.

### 🟢 Subscribed calendars now see edits (`Event.updated_at`)

The feed sent every event with `LAST-MODIFIED` = creation time and
`SEQUENCE:0`, so calendar apps kept the first copy they saw: a moved or
renamed event stayed wrong on members' phones. Events now have `updated_at`
(`auto_now`). The feed sends it as `LAST-MODIFIED`, and `SEQUENCE` is
`Event.ical_sequence` (seconds from creation to the last edit: 0 until edited,
higher after each one, no counter to maintain).

- Bookkeeping saves with `update_fields` (reminders, RSVP emails) don't count
  as edits.
- "This and following" / "all" series edits use `bulk_update`, which skips
  `auto_now`, so `apply_series_edit` stamps the moved occurrences itself.
- The migration backfills existing events to `created_at`, so nothing looks
  edited and subscribed calendars don't all refresh at once.

This was the plan's Phase 0 item "bump `sequence` on edits".

#### Tests
`src/tests/mobile/test_calendar.py` (23 tests): range and time-zone edges,
bad and over-long ranges, the one-year clamp, sign-up and excuse state, a
flat query count, toggle and pledge gates (including the web sign-up button's
own restriction), 404s for hidden events, sign-up/waitlist/promotion through
the app, the last-slot regression via web and app, the subscription URL and
flag, and the feed: `SEQUENCE:0` until edited, rising after an edit,
bookkeeping saves ignored, series edits stamped. All 202 existing event tests
pass unchanged. Full suite on Postgres: 3,931 tests, all pass.

#### Noted, not fixed here 🟡
- `/api/calendar-data/` (the web month view) still runs two sign-up queries
  per event that takes sign-ups. Its `signup_count` also counts waitlisted
  members, while the sign-up buttons' responses count confirmed only. The
  app's list does neither.

### 🟢 Mobile Phase 3 (part 4): Chat endpoints

Under `/api/mobile/v1/chat/channels/`, for the app's Chat tab:

- **`GET chat/channels/`**: the channels the member can read, each with its
  unread count, last message, whether they can write, and their notification
  level. Newest activity first.
- **`GET …/<id>/messages/?before=|since=<message id>&limit=`**: a page of
  messages (default the latest 50, max 100), oldest first, each flagged
  `can_edit` / `can_delete`. Fetching marks the member active in the channel,
  so they aren't pushed while looking (same as the web chat's polling).
- **`POST …/<id>/send/`**, **`…/messages/<mid>/edit/`**, **`…/delete/`**.
- **`POST …/<id>/read/`** `{up_to?}`: moves the read marker.
- **`GET|POST …/<id>/notification-level/`**: `all`, `mentions` or `none`.

**Access is ChatChannel's one rule, with no admin override.** The app has no
"View All Channels" mode, so an admin sees only what the rule admits them to;
Kai committee chat appears only for someone on that committee. A channel the
member can't read is a 404, so ids can't be probed. Behind the `chats` flag
and the `chat_index` toggle and pledge restriction, as on the web. (This means
the open "admin View All can read Kai" question stays a web-only one.)

**One implementation.** Sending, editing, deleting and read markers moved out
of `src/view/chat/channel_chat.py` into `src/chat_service.py`. That covers:
- the write rule
- the 5-per-3-seconds rate limit, now shared with the web
- @mentions only reaching people who can read the channel
- push text hidden for non-open channels
- the websocket broadcast

The website's endpoints call the same code, with the same responses.

**Live updates.** The app opens `/ws/chat/<id>/` with a socket ticket (Phase 1)
and gets the web's events. Until websockets are confirmed in production it
polls `messages/?since=`.

### 🟠 App sockets no longer get the admin "View All" override

The chat websocket admitted any admin to any channel (`admin_override=True`),
for the web's admin preview mode. That applied to app sockets too, so an
admin's phone could subscribe live to a committee channel they aren't on.
Ticket-authenticated sockets now get exactly what the app's endpoints give:
the `chats` flag plus the plain read rule. Browser sockets are unchanged.

### 🟡 `ChatChannel.unread_map` counts in the database

The web chat index's unread counts (and now the app's) fetched one row per
undeleted message in every channel and compared timestamps in Python, so the
cost grew with chat history. It's now one grouped query, with the same rule:
no receipt, or no marker message, means everything is unread. A test checks it
against the per-channel `get_unread_count` for every case.

   the manager ticks "I've checked who is getting an application and what's

4. **Import.** Re-plans from the CSV (the preview is never trusted) and writes

### 🟠 Fixes from a review of the slating code

- **Locked periods leaked to site admins.** The confidentiality model says
  that once a slating manager or committee admin is set, site-admin status

  - `complete_interview`, whose GET returns the confidential interview
    notes, so any site admin could read them;

### 🟢 Slating changes (Mason, 10-26-26)

#### Voting history is kept, and the export includes it
Every voting round keeps its number, its raw votes and a results snapshot
(new `SlatingRound`).
- **Reopening after a failed round starts a new round.** Before, any reopen
  from deliberation counted as resuming a pause, so a failed slate round's
  ballots could block members from voting again. A pause still resumes the
  same round.
- **Individual re-votes no longer delete** the failed positions' earlier
  votes. Counts are per round now, and failed positions go back on the ballot
  as pending.
- **"Clear & Reset Votes" is now "Void This Round".** The round stays in the
  history marked *voided* and isn't counted; reopening starts a new round.
- **A candidate replaced mid-round** has their counts saved to the round
  history first. Deleting the candidate removes their votes.
- **The results export** ("Election Results" in Chapter Documents) is built
  from the round history: the final round's result, then a **Voting history**
  section with every round (when it opened and closed, outcome, and
  online/paper counts), voided rounds and candidate replacements included.
  The results summary and the results page show the same history. *Fixed in
  passing:* the results page and the export counted every round's slate votes
  together, so a re-vote's official numbers included the round that failed.

#### Paper ballots
For members who voted on paper because of tech problems. **Paper Ballots**
(next to Pause/Close Voting, and on the paused-vote panel) takes this round's
paper counts:
- **Full-slate vote:** approve, reject and abstain.
- **Individual vote:** the number of ballots, then each position's counts. No
  position can have more votes than there were ballots.

They can be entered while a round is open or paused, and saving again replaces
them. Closing the vote adds them to the online votes. Results, the summary
and the export show them separately. Each save is logged with counts only
(`SlatingPaperBallots`; no voter identity, like an online vote).

#### Results stay hidden until the committee announces them
Members no longer see a running tally after voting. The individual-vote page
no longer marks earlier positions Passed/Failed; they're "decided in an
earlier round". The results page was already gated on publishing, and
`period_status` shows tallies only to managers (v3.57.0).

#### No IPs in slating
Slating activity records no IP address. The views stopped passing one, the
migration cleared the stored values (nginx's socket address anyway), and the
admin column is hidden. This closes `test_client_ip_single_source`'s
`PENDING_DECISION`, which is now empty.

Only **active members**: inactive members, alumni and advisors can't apply.
The apply page refuses them, the eligibility check says why, and Import
