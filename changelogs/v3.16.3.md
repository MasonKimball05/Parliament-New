# v3.16.3 — Kai confidentiality closeout, dead URL names, and perf fixes

**Deployed:** ✅ 07-28-26 — shipped in `c95bfa6`.
Fix batch for the 07-26-26 auto-run report, implemented 07-28-26; then extended
the same day with the 07-28-26 auto-run's findings, which were mostly *the same
bugs one surface further on*. Three themes:

1. **v3.16.2's confidentiality fixes were half-applied in the Kai module.**
   The redaction landed on the *output* columns but not on the *filter*, not on
   the search result card, and — the one that mattered most — not on the report
   list page itself. A filter predicate is a join key; so is a page nobody
   thought to check.
2. **Templates referencing URL names that don't exist.** One was found by
   review; a new generic test then found four more, three of which were live
   500s on guide pages.
3. **Perf and correctness on the pages this batch already had open.**

**The lesson, recorded because it recurred three times in four days:** when you
redact a field, enumerate *every surface that renders it* and fix them together.
`KaiReport.description` has five (list page, detail page, print view, CSV export,
global-search card). v3.16.2 fixed one, the first half of v3.16.3 fixed two more,
and the list page — the most obvious of the five — survived both passes because
each fix was scoped to the report that prompted it. There is now a note to that
effect at the gate in `templates/kai/view_reports.html`.

No new dependencies. **One migration, `0008`, which emits no SQL** — it carries a
`help_text` change only (`sqlmigrate` confirms `-- (no-op)`); it exists so
`makemigrations --check` stays clean. **One new management command must be run on
deploy** (`normalize_kai_tags`, section 2b) — it is the data half of a security
fix and the code change is incomplete without it; `migrate` does **not** do its
job. Static changes are template-only, so `collectstatic` + a Cloudflare purge
are needed but nothing else.

---

## 0. 🔴 The Kai report list page rendered the allegation body ungated

`templates/kai/view_reports.html`

`{{ report.description|truncatewords:30 }}` had no permission check, while the
two lines immediately below it correctly gated submitter and accused identity on
`kai_access`. `kai_access` was already in the context — this was an omission, not
a scoping problem.

Trace what a reviewer holding `can_view_report_list=True,
can_view_report_details=False` could reach:

| Surface | Allegation body | Gated in |
|---|---|---|
| `manage_kai_report` detail page | denied outright | pre-existing |
| `export_kai_reports_csv` | `[Redacted]` | v3.16.2 |
| Kai search filter (list + CSV) | not searchable | v3.16.3 §1 |
| Global-search result card | hidden | v3.16.3 §2 |
| **`/kai/reports/` — the list page** | **first 30 words of every case** | **nothing** |

So the CSV redaction, the filter gating and the card gating were all bypassed by
opening the page those features exist to accompany. No search term, no unusual
state, and the list is unpaginated — every report in the chapter, in order.

**Fixed:** wrapped in `{% if kai_access.can_view_report_details %}`, with a
comment listing all five surfaces so the next person redacting a field has the
enumeration in front of them. Covered by `KaiListPageDescriptionTests`, including
a positive case (a chair still sees the preview) and a guard that the identity
gating on the same card still works.

## 1. 🟠 Kai search filter was a redaction oracle

`src/view/kai_reports.py`

`view_kai_reports` and `export_kai_reports_csv` each carried their own copy of
the search predicate, filtering unconditionally on:

```python
Q(title__icontains=q) | Q(description__icontains=q) |
Q(submitted_by__name__icontains=q) | Q(targeted_to__name__icontains=q) |
Q(tags__icontains=q)
```

while the CSV wrote `[Redacted]` into *Submitted By*, *Targeted To* and
*Description* for reviewers lacking the matching permission. A list-only
reviewer could therefore type a member's name into the search box and read off
which cases that member submitted or was accused in — the exact fact the
redaction hides — or binary-search the allegation body a word at a time.

**Fixed:** new shared `_kai_search_q(search_query, kai_access)` helper. Title
and tags are always searchable (anyone who can see the list can see those);
`description`, `submitted_by__name` and `targeted_to__name` are each gated on
the flag that governs *reading* them. Both call sites now use the helper, so
the two copies can't drift again — the duplication is why both were wrong.

## 2. 🟠 Kai results in global search: dead link + ungated allegation body

`templates/global_search.html`, `src/view/global_search.py`

- The Kai result card linked to a route named `kai_report_detail`. **No such
  route has ever existed** — the view is `manage_kai_report`. `{% url %}`
  raises `NoReverseMatch`, which Django does not silence, so any Kai-cleared
  user whose search matched a report title got a **hard 500 on the whole
  search page**. Fixed to `manage_kai_report`.
- The same card rendered `item.description` — the allegation body — with no
  permission check, even though v3.16.2 had just stopped list-only reviewers
  from *searching* that field. Search was strictly more permissive than the
  detail view it linked to (`manage_kai_report` denies them the page outright).
  The view now passes `kai_can_view_details`, and the preview is gated on it.
- The card's badge classes were built from `item.category_color`, an attribute
  `KaiReport` has never had, producing dead class names like `bg--100`.
  Replaced with fixed neutral styling.

## 2b. 🟠 Kai tags were free text — an unguarded channel through the identity redaction

`src/models/kai.py`, `src/view/kai_reports.py`, three templates, one new command

`_kai_search_q` searches `tags` with **no** permission gate, the list card
renders them, and the CSV export writes them — all at `can_view_report_list`
level. `KaiReport.tags` was a free-text `JSONField` whose own help text suggested
`['urgent', 'follow-up', 'academic']`. Nothing stopped a chair tagging a case
`smith-incident`. The moment one did, that name was searchable, displayed and
exported to precisely the reviewers whose `can_view_submitter_identity` and
`can_view_accused_identity` are False — straight through the boundary §1 and §2
exist to enforce.

**Fixed by closing the vocabulary**, which is what makes the unconditional
`Q(tags__icontains=...)` in `_kai_search_q` correct rather than lucky:

- `KaiReport.TAG_CHOICES` — 12 status/handling tags, with a comment stating the
  two rules that keep it safe (never add a tag that names a person; if this is
  ever loosened back to free text, `_kai_search_q` must start gating `tags`).
  Adding a tag is deliberately a code change, so rule 1 gets read.
- `KaiReport.normalize_tags(raw)` → `(accepted, rejected)`. Case- and
  separator-insensitive (`Follow Up`, `follow_up`, `FOLLOW-UP` → `follow-up`),
  order-preserving, de-duplicating. The single chokepoint.
- Enforced at **every** write site: the `update_tags` action, template create,
  template edit — each reporting rejections rather than silently dropping them —
  plus `clean()` on both `KaiReport` and `KaiReportTemplate` as a backstop for
  the admin and for surfaces that don't exist yet.
- The tag inputs are now checkbox lists over the vocabulary, in
  `manage_report.html`, `create_template.html` and `edit_template.html`, each
  carrying a line telling the chair that tags are visible to every list-level
  reviewer.
- Display switched to `get_tag_labels()` so the UI shows "Follow-Up Needed"
  rather than the slug.

**Existing rows are handled by `manage.py normalize_kai_tags`, not a data
migration.** Migrations run unattended; this one edits disciplinary records and
makes judgement calls about values nobody has reviewed. It **defaults to a dry
run** and prints exactly what it would drop. Anything removed is first written to
the case's own `KaiReportActivity` timeline, which is `can_view_report_details`-
gated — so nothing is destroyed silently, and the removed text does not land
anywhere a list-only reviewer can read it. If a dropped value is worth keeping,
put it in the chair notes before re-running with `--apply`.

## 3. 🟠 Four more nonexistent URL names — three of them live 500s

Found by the new `TemplateUrlNameTests` (section 7), not by review:

| Template | Bad name | Fix |
|---|---|---|
| `guide/members/service_hours.html` | `service_user_dashboard` | transposed — now `user_service_dashboard` |
| `guide/officers/recruitment.html` | `manage_signups` | button removed |
| `guide/officers/education.html` | `manage_pledge_tasks` | block removed |
| `guide/officers/education.html` | `pledge_progress_overview` | block removed |

All four sat in **unconditional** blocks, so `/guide/members/service-hours/`,
`/guide/officers/recruitment/` and `/guide/officers/education/` have each been
returning 500 since those buttons were added.

The two education buttons and the recruitment one were removed rather than
repointed: `education_home` is scoped to a committee
(`committee/<code>/education/`) and the guide page has no committee in
context; there is no pledge-progress route at all; and sign-ups are per-event
(`event_signup_list` takes an `event_id`), so there is no chapter-wide page to
link. Adding the routes is a feature decision, not a bug fix. Explanatory
`{% comment %}` blocks are left at each site.

## 4. 🟡 Search result counts rendered blank

`templates/global_search.html`

Since the 06-26-26 list-conversion, every value in `results` is a Python list,
so `{{ results.committees.count }}` resolved to `string_if_invalid` (`''`) —
`list.count` is a bound method requiring an argument, so Django's variable
resolution falls through silently. Eight section headers had been rendering
"Committees ()" for a month, with no error and no log line. All eight are now
`|length`.

The two remaining `.count` calls (`committee.members.count`,
`committee.chairs.count`) were *genuine* related-manager querysets and did
work — but fired 2 queries per committee row inside the result loop. The view
now annotates `member_total` / `chair_total` and the template reads those.

## 5. 🟡 Kai gate cost every searcher extra queries

`src/view/global_search.py`, `src/view/kai_reports.py`

v3.16.2's rewrite ran `FeatureFlag.is_feature_enabled('kai_reports')` — an
uncached `objects.get` — before the access check, so every searcher on the
site paid for it, including members who can never match the branch.

- The flag check moved **below** the access check: only Kai-cleared users pay.
- `_get_kai_access` now tests `user.is_admin` (a field read) **before**
  `committee.is_chair(user)` (1–2 queries). Admins reach the same answer
  without touching the DB, at all six call sites.

**Deliberately not done:** short-circuiting on
`request.user.committees.filter(is_kai_committee=True).exists()`. A
`KaiMemberPermission` row is not guaranteed to imply membership of the
committee's `members` M2M — the permission UI also lists chairs and
voting_members, and the grant endpoint takes an arbitrary `user_id` — so that
cheaper pre-check could silently hide results from someone legitimately
granted access. `_get_kai_access` stays the single source of truth.

**Corrected 07-28-26 — the first draft of this section overstated the win.**
Only the *flag lookup* moved behind the access check. The committee lookup and
the whole of `_get_kai_access` still run for every searcher, including when the
`kai_reports` flag is disabled chapter-wide. Counted against the source
(`is_chair` = 1–2 queries, `KaiMemberPermission.get` = 1):

| | before (v3.16.2) | after |
|---|---|---|
| ordinary member | 4–5 | 3–4 |
| admin | 3–4 | **2** — not 1; admins are cleared, so they do pay the flag lookup |

A real improvement, smaller than first claimed. The remaining win is caching
`FeatureFlag.is_feature_enabled`, which also covers the flag-disabled case that
no amount of reordering reaches. Left for its own release.

## 6. 🟡 Poll results N+1, and a stronger anonymity shuffle

`src/view/officer/announcement_polls.py`

- `poll_results` counted option selections with one `COUNT` query per option
  per question (a 6×4 poll = 24 queries), plus one query per free-text
  question — while the view already prefetched `answers__selected_options` and
  ignored it. Both are now single aggregates for the whole poll, indexed in
  Python.
- The anonymous-poll CSV row shuffle moved from the module-level Mersenne
  Twister to `random.SystemRandom()`. The shuffle is an unlinkability control,
  not a cosmetic one; the global `random` state is shared process-wide and
  reconstructable from enough observed output.

## 6b. 🟡 Kai search placeholder promised what the gate refuses

`src/view/kai_reports.py`, `templates/kai/view_reports.html`

The placeholder hardcoded "title, description, submitter, targeted person, or
tags". After §1 that is false for anyone lacking the matching flags — a list-only
reviewer types a member's name, gets zero rows, and concludes either that search
is broken or **that the member has no cases**. The second reading is a wrong
inference the UI was inviting.

Now built server-side by `_kai_search_placeholder(kai_access)`. A test walks the
whole permission matrix asserting the placeholder and `_kai_search_q` never
disagree — they are one decision rendered twice.

## 6c. 🟡 Kai dashboard: 13 count queries, and a trend chart that dropped months

`src/view/kai_reports.py`

Two bugs in the same block.

**The queries:** 4 `.count()` for status + 3 for outcomes + 6 in a month loop, on
every load — while the category counts three lines away already demonstrated the
right pattern. All three are now single `values().annotate(Count())` aggregates.
13 queries → 3.

**The chart:** it stepped months with `timezone.now() - timedelta(days=30 * i)`,
which is not one step per calendar month. Enumerating 2026 day by day: on **32
days** two of the six steps land in the same month, so one dict key overwrites
another and the chart silently renders five bars instead of six. On 2026-03-01
the keys came out `['Oct','Nov','Dec','Dec','Jan','Mar']` — **February missing
entirely, December double-counted**. No error, no log line.

Now steps by calendar month and buckets with a single `TruncMonth` aggregate, so
a key collision is structurally impossible. `KaiDashboardStats` tests assert six
distinct consecutive months ending in the current one, correct per-month
placement, zero-fill, window exclusion, and a query budget that fails if
per-month counting returns.

## 6d. 🟡 Poll editing did a point lookup per question and per option

`src/view/officer/announcement_polls.py`

`create_or_edit_poll` ran `AnnouncementPollQuestion.objects.get(...)` per
submitted question and `AnnouncementPollOption.objects.get(...)` per submitted
option — a 6×4 poll re-save was ~30 lookups. Both sets are now fetched once,
scoped to the poll (preserving the ownership check the per-row `get(id=...,
poll=poll)` was doing) and indexed in Python. Same shape as the `poll_results`
fix in §6.

## 6e. 🟡 CSV export leaked exception text to the user

`src/view/kai_reports.py`

`except Exception as e: messages.error(request, f'... {str(e)}')` surfaced DB and
driver internals — table names, column names, query text — to any list-level
reviewer. Django escapes it, so it was never XSS, but it was free reconnaissance.
Now logged via `logger.exception` with a generic message to the user.

## 7. Tests — three new files, 56 tests

**`src/test_kai_search_gating.py`**

- `KaiSearchPredicateTests` — permission matrix over `_kai_search_q`, asserting
  each searchable field appears only with its governing flag. No DB.
- `KaiSearchOracleTests` — end-to-end: a list-only reviewer searching the
  submitter name, the accused name, or a marker word from the allegation body
  gets no match, on both the list view and the CSV export; searching the title
  still works, and the CSV still redacts.
- `GlobalSearchKaiCardTests` — the search page renders (regression for the
  `NoReverseMatch` 500), links to the real route, hides the description from a
  list-only reviewer, and still shows it to a chair.
- `TemplateUrlNameTests` — **the generic guard.** Scans every template for
  literal `{% url 'name' %}` tags and asserts each name is registered. This is
  what found the four extra dead names. Namespaced names (`admin:`) and the
  unrendered `templates/archive/` tree are skipped.
  *Known limitation:* it checks the name exists, not that the right arguments
  are passed — `{% url 'education_home' %}` with no args would still 500 and
  still pass. Catching that needs a real render.
- `KaiListPageDescriptionTests` — §0. A list-only reviewer sees the case exists
  and not what it alleges; a chair and a detail-permitted reviewer both still see
  the preview; the identity gating on the same card still works (so the fix can't
  be "achieved" by deleting the block).
- `KaiSearchPlaceholderTests` — §6b, including a matrix test asserting the
  placeholder and the predicate never drift apart.

**`src/test_kai_tag_vocabulary.py`** — §2b. `normalize_tags` directly (casing,
separators, duplicates, blanks, `None`); `clean()` on both models; every write
site refusing a name and changing nothing; the end-to-end case — a legacy
free-text tag naming a member is removed by the command, then is neither
searchable nor rendered for a list-only reviewer, while a control search still
finds the case by title. Plus the command's own contract: dry-run by default,
audit entry on `--apply`, idempotent, `--no-audit` honoured.

**`src/test_kai_dashboard_stats.py`** — §6c. Six distinct consecutive months
ending in the current one, per-month placement, zero-fill, out-of-window
exclusion, status/outcome counts after the aggregate rewrite, and a query budget.

## Notes for reviewers

**`{% comment %}`, not `{# … #}`.** Django's `{# #}` comment is **single-line
only** — the lexer regex isn't DOTALL, so a multi-line `{# … #}` is not
recognised as a comment and its contents get rendered and evaluated. Every
comment added in this release uses `{% comment %}`.

**Whole-page assertions are the wrong instrument on `/kai/reports/`.** The
dashboard's recent-activity panel renders report titles independently of the
search filter, so `assertNotContains(resp, '<title>')` can fail for reasons that
have nothing to do with the filter. Assert on `resp.context['reports']` instead.
(Titles are list-level information, so the panel is not itself a leak.) The
pre-existing oracle tests in `KaiSearchOracleTests` pass only because their
fixtures happen to create no activity rows — worth knowing before adding to them.

## Deploy

Code + templates only — **plus one required command**.

1. `git pull`
2. `python manage.py migrate` — `0008` only, and it emits no SQL (a `help_text`
   change on `KaiReportTemplate.suggested_tags`). Instant, nothing to plan for.
   `TAG_CHOICES` itself is a Python-level constant on a `JSONField`, so adding a
   tag later will never need a migration.
3. **`python manage.py normalize_kai_tags`** — read the dry-run output. If any
   dropped value is worth keeping, put it in that case's chair notes first.
4. **`python manage.py normalize_kai_tags --apply`** — this is the data half of
   §2b. Skipping it leaves existing free-text tags, and therefore the leak, in
   place. `migrate` does not do this for you.
5. Restart `parliament-gunicorn.service`
6. `collectstatic --noinput` → **purge Cloudflare**

Spot-check after: `/kai/reports/` as a list-only reviewer (case titles visible,
no allegation text, placeholder offers only title and tags); `/search/?q=…` as a
Kai-permissioned member; the tag editor on a case is a checkbox list; the Kai
dashboard trend chart shows six months; and the three guide pages in section 3.
