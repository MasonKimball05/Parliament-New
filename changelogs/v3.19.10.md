## 🟠 1 — CI's Security Check job has been failing since 07-29-26

`.github/workflows/ci.yml` runs a `security` job on every push to `main` and
every PR. It has two steps and neither carries `continue-on-error`:

```yaml
- name: Dependency vulnerability scan (pip-audit)
  run: pip-audit --ignore-vuln PYSEC-2025-49
- name: Static security scan (bandit) — fail on MEDIUM+
  run: bandit -r src/ -ll --exclude src/migrations
```

**The bandit step exits 1 and has done since 07-29-26.** Bisected by running

That is **nineteen days and roughly a dozen pushes**, including six releases
whose entire subject was code quality. The CI file's own comment says the
baseline "reached 0 MEDIUM in v3.12.1 … so MEDIUM regressions now block CI
(flipped 07-08-26)". The gate did exactly what it was configured to do; the

⚠️ **THIS IS THE FOURTH RECORDED INSTANCE OF ONE PATTERN AND THE THIRD THAT
COST WEEKS.** CLAUDE.md already carries: `test_url_smoke` red 07-30 → 08-02
found by a nightly; the `makemigrations --check` gate red until v3.18.1; the 16
feature flags that gate nothing; *"a guard that swallows exceptions reports the
absence of a signal as the absence of a problem."* The variant here is worse in
one specific way — **nothing swallowed anything.** GitHub recorded a red ❌ on
every push for nineteen days. The failure was entirely in the reading.

**And note what did NOT catch it.** v3.19.9 built a pre-push hook precisely so
that "a check nobody remembers to run" stops being possible. The hook runs the
test suite and the release-integrity checks — **it does not run bandit or
pip-audit**, so the one gate that was actually red is the one the new gate does
not cover. A trigger built for a pattern still has to be pointed at every
instance of it.

### What the 12 findings actually were

All benign, and that is the point — the gate was red on false positives, which
is the fastest way to teach a team to stop looking at it.

| Test | Where | Why it is safe |
|---|---|---|
| B608 ×8 | `test_dev_mode.py`, `test_dev_mode_rows.py` | SQL literals built from a loop counter or from a hard-coded tuple of table names. No user input reaches the string. |

## 🟠 2 — seven CVEs in two pinned dependencies, one of them reachable

`pip-audit -r requirements.txt`, run 08-17-26:

```
sqlparse     0.5.5    CVE-2026-71491, -59894, -59893, -54284   fix 0.6.0
cryptography 48.0.1   PYSEC-2026-3552, -3553, -3554            fix 49.0.0 / 50.0.0
```

**Six of the seven are not reachable from this application, and one is.**
Triaged individually rather than bumped as a batch, because "upgrade everything"
teaches nothing and gets skipped when it is inconvenient:

- **`sqlparse` — all four unreachable.** It is a *transitive* dependency (Django
  requires `>=0.3.1`); `grep -rn sqlparse src/ Parliament/` returns nothing.
  Three of the four are parser DoS paths that need attacker-supplied SQL text,
  and this application never passes user input to a SQL *parser*. Bumped
  anyway: the CI gate does not care whether a CVE is exploitable, and neither
  should the pin.
- **`PYSEC-2026-3554`** (name-constrained sub-CA escaped by a wildcard SAN) —
  not reachable. Parliament verifies no server certificates itself.
- **`PYSEC-2026-3552`** (Bleichenbacher oracle in `pkcs7_decrypt_*`) — not
  reachable. Field encryption is Fernet; PKCS7 is never touched.
- **⚠️ `PYSEC-2026-3553` IS REACHABLE.** Exponential blowup resolving an invalid
  certificate chain containing duplicate self-signed certificates.
  `verify_registration_response` in `src/view/webauthn.py` parses an
  **attestation statement supplied by the client**, and an attestation
  statement carries an `x5c` certificate chain. That is attacker-controlled
  chain material reaching a certificate path routine — CPU burn on the
  passkey-registration endpoint. Not a disclosure and not remote code
  execution; it is the one of the seven with a path from a request to the
  vulnerable code, which is the distinction worth making.

### The bump is not one line

`pyOpenSSL` 26.2.0 pins `cryptography<49`, so `cryptography==50.0.0` drags
pyOpenSSL forward too (26.4.0 resolves cleanly). pyOpenSSL is transitive via
daphne/twisted and stays unpinned; **if it is ever pinned, pin the pair.**

**Verified rather than reasoned about:** the full suite was re-run against
`cryptography==50.0.0` + `sqlparse==0.6.0` + `pyOpenSSL 26.4.0` — 1,340 tests,
0 failures — *before* the pins were changed, so the upgrade was known green
rather than hoped green.

## 🟡 3 — every query budget in the suite was exactly 3 too high

`src/test_query_budgets.py` is a ratchet: absolute per-view ceilings, measured
and pinned, deliberately failing in **both** directions so that accumulated
slack gets noticed. Measured 08-17-26, four consecutive cold-cache requests per
page:

```
view_kai_reports          45, 42, 42, 42     BUDGET was 45
activity_logs             41, 38, 38, 38     BUDGET was 41
home                      44, 41, 41, 41     BUDGET was 44
admin_v2_security_alerts  35, 32, 32, 32     BUDGET was 35
admin_v2_two_factor       32, 29, 29, 29     never measured
service_dashboard         43, 40, 40, 40     never measured
```

**Every declared budget is the first number.** The extra three, identified by
diffing the query shapes of run 1 against run 2, are always the same:

```
SAVEPOINT
INSERT INTO "src_systemlockdown" (…)
RELEASE SAVEPOINT
```

`SystemLockdown.get_instance()` is `get_or_create(pk=1)` and
`EmergencyLockdownMiddleware` calls it on every request. In production the row
has existed since the table was created. Under `TestCase` each method runs in a
transaction that is rolled back, so the row is absent again at the start of
every test and **the first request a test makes pays to create it** — three
queries production will never spend.

So four pages could each have grown by three queries with nothing failing.

⚠️ **AND IT SAT ONE QUERY UNDER THE SUITE'S OWN DETECTOR.**
`assert_within_budget` fails when a page comes in more than `STALENESS_SLACK`
(= 4) *under* its ceiling, for exactly this reason. The artefact was 3. **A
four-query artefact would have been caught the day it landed; a three-query one
was invisible for fifteen days.** The tolerance was not wrong — it is the
distance between "reproducible" and "worth investigating" — but it means the
suite's self-check cannot find an error smaller than itself, and nothing else
was looking.

> **THE RULE: a ceiling measured from inside a fixture measures the fixture
> too.** The remedy is not a wider tolerance. It is to make the measured request
> resemble the thousandth request rather than the first, because the thousandth
> is the one production actually serves. New `warm_singleton_rows()` runs before
> the capture in both `measure()` implementations; all six budgets are now the
> steady-state number.

**Two budgets closed a standing to-do.** `TwoFactorDashboardQueryBudgetTests`
and `ServiceDashboardQueryBudgetTests` shipped in v3.18.6 without a `BUDGET`,
correctly — *"an invented ceiling is worse than none: it reads exactly like a
measured one"* — and had been on `AWAITING_MEASUREMENT` for thirteen days
waiting for an environment that could measure them. Both now carry a measured
constant and a `test_..._stays_within_budget`, and both are off the list.
`MiddlewareChainQueryBudgetTests` stays on it deliberately: it asserts relative
properties (cold vs warm, anonymous vs authenticated, steady state), and a
single ceiling there would be a number with nothing to compare against.

`BudgetHygieneTests.declared` now covers all six rather than three — the same
"the helper exists, three of six call sites use it" shape this codebase keeps
recording, one level down.

## 🟡 4 — the pre-push hook did not run the gate that was red

The direct response to finding 1, and it was **deliberately held back from the
first pass** on v3.18.4's principle that the response to a pattern should not
ride along with an instance of it. It is here now because the pattern is the
finding.

`scripts/pre-push.sh` runs the sqlite suite and the release-integrity checks.
It did not run bandit or pip-audit — **so the one CI gate that was actually red
for nineteen days is the one the new gate did not cover.** Both scans now run
after the ledger check, with flags matching `ci.yml` exactly.

The design constraint is the one already stated at the top of that file, and it
cuts both ways:

> **A check that cannot run must not report like a check that failed** — a
> missing binary or an offline laptop is a loud skip that allows the push, never
> an abort. A gate that blocks for environment reasons is a gate people delete,
> and a deleted gate is how this repo went a month without a hook.

⚠️ **AND ITS MIRROR, WHICH THE FIRST DRAFT GOT WRONG.** That draft ended with
`✓ all gates green — pushing` after skipping both scans. **A check that cannot
run must not report like a check that *passed* either**, and the summary line is
the only line most pushes are read for. `_skipped` now drives a different final
message. Caught by running the missing-tool branch rather than reasoning about
it — which is the same lesson as everything else in this batch.

Two implementation choices worth their comments:

- **Verdicts come from parsing JSON, not from exit codes.** bandit exits 1 for
  findings and something else for its own errors; pip-audit exits 1 both for
  vulnerabilities and for "could not reach the network". The exit code cannot
  distinguish *a finding* from *a failure to look*, and that distinction is the
  entire design. The JSON either parses or it does not.
- **⚠️ The hook audits `requirements.txt` while CI audits the installed
  environment, deliberately.** A developer's venv accumulates tools the server
  never sees, so auditing it locally would block pushes on CVEs CI cannot see —
  and a local gate that disagrees with the remote one is a local gate people
  learn to bypass. The residual gap is a CVE in bandit or pip-audit themselves,
  which CI catches and this does not. **Prefer the false negative in the local
  gate and the false positive in the remote one.**

**Verified by running all four branches**, not by reading them: real tools →
both clean, exit 0; injected bandit findings → abort, exit 1, naming the
finding; bandit crashing with unparseable output → loud skip, exit 0; pip-audit
failing as if offline → loud skip, exit 0. `src/test_repo_hooks.py` gains three
tests, including one that reads `ci.yml` and fails if the hook's bandit flags
and CI's ever diverge — because a hook that scans more laxly than CI reports
green on pushes CI rejects.

## 🟡 5 — `SystemLockdown.get_instance()` was a write on the read path

Listed in the first pass of this batch as *noted, deliberately not fixed*.
Fixed here, because "the window is narrow" is not the same as "there is no
window", and because the same defect was what made finding 3 possible.

`get_instance()` was `get_or_create(pk=1)`, and `EmergencyLockdownMiddleware`
calls it on essentially every request — authenticated or not. So the first
request after a fresh install, a database restore, or an admin deleting the row
**issued an INSERT while serving a GET**, concurrent first requests raced for
it, and the request path could not run against a read-only connection at all.

Now: read with `filter(pk=1).first()`, and return an unsaved `cls(pk=1)` when
there is no row. `is_active` defaults to `False`, so the answer is identical to
the one `get_or_create` produced — the difference is that **answering the
question no longer changes the answer.** `pk=1` on the placeholder means a
caller who goes on to `activate()` writes the singleton rather than a second row.

⚠️ **THE ABSENCE IS CACHED TOO, AND THE NAIVE FIX WOULD HAVE BEEN A
REGRESSION.** Dropping the write without caching the miss trades one
INSERT-once for **one uncached SELECT on every request, forever**, on any
install where nobody has opened the lockdown page — undoing v3.18.7 on exactly
the widest hot path in the application, which is what v3.18.7 was for. A miss
stores a sentinel (`CACHE_MISSING`), because `cache.get` returns `None` for a
miss and caching `None` is indistinguishable from caching nothing. Same
`found`/`value` shape `SiteSetting.get_setting` already uses.

The sentinel is safe for a stated reason rather than a lucky one: the
`post_save` receiver fires when the row is **created**, which is the exact
moment "there is no row" stops being true.

**Four new tests, and their controls are worth reading as a set** — they were
run against three different trees:

| Test | vs. the old `get_or_create` | vs. the naive fix (no sentinel) |
|---|---|---|
| `…never_writes` | **FAILS** ✅ | passes |
| `…missing_row_is_cached…` | passes | **FAILS** ✅ |
| `test_repeated_reads_cost_one_query` (existing) | passes | **FAILS** ✅ |
| `…invalidates_the_cached_absence` | passes | passes |
| `test_the_control_an_existing_row_is_still_returned` | passes | passes |

Only one is a regression test for the original bug; two exist to catch the
*obvious wrong fix*, and two are controls that must pass everywhere. Recorded
this way because "all new tests pass" says nothing on its own — the useful
question is which tree each one fails against.
