## The real, second bug: legacy vector image formats have no web-renderable form

v3.29.16 correctly fixed bleach stripping the `src` off every `<img>`. But
mammoth doesn't only emit modern raster formats — for an image whose OOXML
part declares a legacy type (`image/x-emf`, `image/x-wmf` — Enhanced/
Windows Metafile, a vector format Word still uses for a lot of pasted-in
content: clip art, anything copied out of an older `.doc`, or pasted from
another Office app like Excel/PowerPoint), mammoth still emits a perfectly
well-formed `data:image/x-emf;base64,...` — it just also logs a warning
that this codebase was silently discarding:

```python
if content_type in ["image/png", "image/gif", "image/jpeg", "image/svg+xml", "image/tiff"]:
    messages = []
else:
    messages = [results.warning("Image of type {0} is unlikely to display in web browsers".format(content_type))]
```

(source: `mammoth/docx/body_xml.py`, confirmed by reading it directly, not
assumed from documentation)

v3.29.16's validation regex correctly recognized this as a well-formed
`data:image/<type>;base64,<data>` URI — because it is one — and let it
through, since that regex exists to catch a security case (a relabeled or
malformed content-type), not to judge whether the type is web-renderable.
No browser can actually decode EMF/WMF from an `<img src>`, so the tag
painted nothing: no failed-fetch broken-image icon (the data isn't
malformed, so there's no request that fails), no fallback, just an empty
box the surrounding text flows around exactly as if the tag wasn't there.
That's indistinguishable from v3.29.16's original bug by eye, which is
presumably why it read as "the fix didn't work" rather than "a different
image in the same document has a different problem."

**Confirmed directly, not inferred**: built a real minimal `.docx` (hand-
assembled zip of OOXML parts, same technique as v3.29.16's tests) whose
image part declares `image/x-emf`, ran it through mammoth directly — it
does exactly this: emits the `<img src="data:image/x-emf;base64,...">` and
the "unlikely to display" warning, unconditionally, not a hypothetical.

## Fix

Two changes, `src/view/view_document.py`:

1. **mammoth's `result.messages` are now logged** (`logger.warning`) rather
   than discarded — `convert_docx_to_html` computed `result.value` and threw
   away `result.messages` entirely before this. This is a permanent
   observability fix independent of the specific bug: any future "an image/
   style/whatever silently didn't show up" report now has a log line saying
   exactly why, instead of needing to be reverse-engineered from scratch the
   way this one was.

2. **`_replace_unsupported_image`** — a new pass, run as part of
   `_sanitize_docx_html_images` after the existing security validation.
   For an `<img>` whose `src` is a well-formed image data URI (already past
   v3.29.16's security check) but whose declared type isn't one of
   `{png, jpeg, jpg, gif, webp, bmp, svg+xml}` — the types an evergreen
   browser actually renders from an `<img>` tag — the tag is swapped for a
   visible `<span class="docx-unsupported-image">` notice ("*this image's
   format can't be shown here; download the document to view it*"),
   carrying the image's `alt`/`descr` text if the docx had one. **This list
   is deliberately narrower than mammoth's own** — mammoth also waves TIFF
   through as "fine," but Chrome and Firefox render no TIFF at all from an
   `<img src>`, so trusting mammoth's list here would have left a second,
   quieter version of the same bug for any docx with a TIFF image.

   The security check and this new check are sequential and distinct, not
   merged: a data URI that fails the *security* check (relabeled/malformed
   content-type, not a real `data:image/*` shape at all) is stripped to
   nothing exactly as before — it never reaches the placeholder logic,
   which only ever runs on an image that's already been confirmed to
   genuinely be one.

   New `.docx-unsupported-image` CSS in `templates/view_document.html`
   (dashed border, muted italic text, light/dark variants matching the rest
   of `.docx-content`'s styling) so the notice reads as an intentional
   "here's what happened," not as broken markup.
