# v3.19.4 — What the number means, what the alarm costs, who owns the file

**Date:** 08-08-26
**Type:** Correctness + hardening batch. **No migration.**
**Committed & pushed:** 08-08-26 (`0bcf510`, "v3.19.4")
**Deployed:** *not deployed*

The 08-08-26 auto-run fix batch. That review read v3.19.3 — the previous day's
fix batch — and found all eight of its fixes present and correct, including the
two that deviated from what was suggested. Five findings came out, **all 🟡, and
four of the five in one file**: `src/middleware/performance.py`.

That concentration is worth stating plainly rather than treating as bad luck.
`performance.py` was rewritten last, at the end of a five-release day, and it is
the file with the least consequence for being wrong — nothing a member touches
depends on it. It is therefore exactly where a careful author's attention is
thinnest, and every finding in it is an accounting error rather than a defect.

The one theme across all five: **v3.19.3 wrote down what it intended and did not
re-read it against what it built.**

## 🟡 1. `perf_sampled_count` was written on every stored sample and read by nothing

`SAMPLED_KEY` had one writer (`_append_metric`), one test teardown, and **no
reader**. It cost a Redis round trip per stored sample and its value was thrown
away.

What makes it more than a dead constant is what `stored_samples` did instead:
`len(entries)` — **buffer occupancy, capped at `MAX_STORED = 500`.** So the
release that correctly identified `total_requests` as a saturating `len()` and
replaced it with an exact `cache.incr` counter introduced a second saturating
`len()` sixty lines below the fix, under a new name, *while incrementing the
exact counter that answers it and discarding the result.*

**Fixed.** `get_performance_summary()` now returns both, under names that say
which is which:

| key | kind | bounded? |
|---|---|---|
| `total_requests` | exact counter — every request seen | no |
| `sampled_requests` | exact counter — every request stored | no |
| `stored_samples` | buffer occupancy — what is retained now | yes, `MAX_STORED` |

Their ratio is the *effective* sample rate, which is **not** `SAMPLE_ONE_IN`:
slow requests are stored unconditionally, so the realised rate is always a little
richer than 1-in-N and drifts with how slow the site is. `memory_report` now
prints the measured figure rather than quoting the constant.

⚠️ **Why the existing guard could not see this.**
`MonitoringReaderLivenessTests.test_no_view_reads_the_dead_perf_cache_key`
(v3.18.7) greps for readers of a **named** key. A key with writers and no readers
*at all* is a different shape from a key whose reader was deleted. New
`EveryCounterThisModuleWritesIsAlsoRead` asserts the property instead — **the
fourth time this codebase has had to rewrite a guard from an instance to a
property**, after v3.18.5 (a column, not a call site) and v3.19.3 (a resource,
not a query).

## 🟡 2. `memory_report`'s "buffer near capacity" recommendation could never be false

The check first compared `total_requests` to `MAX_STORED`. v3.19.3 saw that
`total_requests` had become an unbounded counter and swapped in `stored_samples`
— a correct observation about the wrong quantity. `stored_samples` is `len()` of
a ring buffer **trimmed to `MAX_STORED` on every write**, so `> MAX_STORED * 0.8`
is the steady state of a buffer doing its job. The recommendation fired forever
on any live install, advising *"consider reducing MAX_STORED"* about a buffer
behaving exactly as designed. Sampling moved when it latched on, not whether.

**Fixed** by asking a question that can be answered no. This is a *memory*
report, so it now measures **bytes**: `len(pickle.dumps(entries))`, reported in
section 6 and recommended on above 512 KB. That number can be false, it gets
worse if `MAX_STORED` or the entry shape changes, and it is what somebody reading
a memory report came for.

⚠️ **The rule, and it is general: before writing a threshold, ask what the world
looks like when it is NOT crossed.** If the answer is "a brand-new process", the
threshold measures uptime.

Also: `ImportError` is **not** caught around the new block. v3.18.7 narrowed that
`except` deliberately — a missing name here is a code defect and belongs in a
traceback, not in a silently absent recommendation.

## 🟡 3. Three accuracy claims in `performance.py` were wrong, one contradicting a comment four lines away

* `_append_metric`: *"`total_requests` and `requests_last_hour` are **exact**,
  because they now come from `cache.incr` counters."* `total_requests` does.
  `requests_last_hour` was `len()` over the retained buffer, has never come from
  a counter, and **cannot** — a counter has no timestamps to filter on.
* Four lines above the value itself: *"Sample counts, scaled to an estimate of
  real traffic."* **No scaling was ever performed.** The same number was
  documented as exact-and-counter-derived in one place and as a scaled estimate
  in another, and was neither.
* `get_performance_summary`: *"`slow_requests` and `get_slow_requests()` are
  **complete**, not sampled."* Slow requests are stored unconditionally — true,
  and the design — but they land in the same `MAX_STORED` ring buffer and are
  evicted FIFO like anything else. Sampling made this much better (500 slots now
  span ~10,000 requests instead of 500) without making it absolute.

**Fixed.** `requests_last_hour` / `requests_last_5min` → `samples_last_hour` /
`samples_last_5min`, **renamed rather than scaled**: inventing a multiplier would
be a second wrong number wearing the first one's name. If a caller wants
estimated traffic in a window, the honest source is `total_requests` sampled at
two points in time. Both readers (`debug_panel`, `memory_report`) updated; the
endpoint is admin-only debug JSON with no in-repo consumer, so the rename is free.

⚠️ **This is a variant of CLAUDE.md's tracked false-comment category, not another
instance of it.** The four recorded so far were *true of a simpler deployment and
never revisited*. These were **never true** — they describe the design that was
intended, and nobody re-read them against the function that got written. Worth
distinguishing, because the two have different tells: the first kind rots with
the infrastructure, the second is wrong in the commit that introduces it and is
findable by reading the docstring next to the code.

**And the one user-visible consequence, fixed:** `admin_v2/dashboard.html`
renders `avg_response_time_ms`, `max_response_time_ms` and `slow_requests`, all
now sampled and **biased upward** because slow requests are kept preferentially.
`memory_report` and the debug JSON were both given labels in v3.19.3. The
dashboard card — the only one a person actually looks at — was not. It now says
which numbers are exact and which are estimated, and over how many samples.

## 🟡 4. `FORGED_CF_HEADER` was logged unthrottled, into a log it shares with everything

Three facts compounded:

1. `get_client_ip` runs **more than once per request** —
   `InputSanitizationMiddleware` calls it unconditionally,
   `SessionTrackingMiddleware` and `EmergencyLockdownMiddleware` on their own
   conditions — so one forged request wrote several identical lines.
2. The `security` logger's only file handler is a `RotatingFileHandler` at
   **10 MB × 3 backups, shared with `django`, `src`, `admin_actions` and
   `function_calls`**. There is no separate security log to protect.
3. What triggers it is, by construction, someone who has already found a route
   to the origin — someone able to repeat it at will.

So the alarm could roll the log and take every other security event with it.
Slow, noisy, and not the reason to fix it: **an alarm that destroys the record
when it fires is the wrong shape regardless of how hard it is to abuse.**

**Fixed.** New `_log_forged_cf_header`: one line per peer per 300 s via an atomic
`cache.add`, with suppressed hits counted and the count riding on the next line
that gets through, so the volume stays visible. `_socket_peer` split out of
`_peer_is_cloudflare` so the peer is computed once.

⚠️ **The throttle is keyed on the SOCKET PEER, and that is the whole design.**
The forged value is chosen by the attacker; a throttle keyed on
attacker-controlled input is not a throttle, it is a per-choice allowance. The
peer is the one field an outside client cannot pick — the same reason
`_peer_is_cloudflare` checks it. And because verification-on plus no-nginx means
XFF is fully client-supplied, the peer is normalised through `ipaddress` before
it reaches a cache key, with everything unparseable sharing one bucket. Otherwise
a 5,000-character peer is a 5,000-character cache key and a fresh one per request.

The forged value is truncated to 64 chars and the path to 200 in the line itself.

## 🟡 5. Publishing a draft orphaned its private file forever

v3.19.3 made publish **copy** the attachment into `legislation_docs/` instead of
re-pointing at the private path. Right fix. What it did not say was what happens
to the original — so every published draft left a second copy under
`legislation_drafts/<uuid>` that nothing referenced, nothing could name, and no
code path would ever delete. `delete_legislation_draft` was the same story:
Django has not deleted files on model delete since 1.3, so deleting a draft
orphaned its blob too. **The footgun the copy removed (two rows, one path) was
replaced by an orphan set with no owner.**

**Fixed**, in two halves that are one invariant:

* **`post_delete` receiver** on `LegislationDraft` (module scope in
  `models/legislation.py`, matching `models_feature_flags.py`). `post_delete`
  rather than `pre_delete`: a rolled-back delete restores the row, and a
  `pre_delete` unlink would already have destroyed the file it points at.
* **Publish clears `draft.document` inside the atomic block and unlinks after
  commit.** ⚠️ `transaction.on_commit`, **not** "after the `with` block" — if
  `ATOMIC_REQUESTS` is ever turned on, that `atomic()` becomes a savepoint inside
  the request's transaction and deleting there would destroy the only copy on a
  later rollback. Correct either way, costs nothing today.

Nothing is lost: the bytes are in `legislation_docs/` under the author's own
filename, chapter-readable and linked from the draft row's "view the bill" line,
and the draft is immutable from that point (`edit_legislation_draft` redirects on
`is_published`). `document_original_name` is kept — it is the record of what was
published, and `document_display_name` returning it with no file attached is
harmless because every template gates on `draft.document` first.

⚠️ **The unlink goes through one guarded helper, `delete_draft_document_file`,
and the guard is the point.** `DualLocationStorage.path()` falls back to
`BASE_DIR/exportable_media/` when a name is absent from `MEDIA_ROOT` — and
`exportable_media/` is **committed to a public repo by design** and holds the
chapter's governing documents. A plain `document.delete()` on a row whose file
had already gone missing could therefore resolve into the public directory and
delete a governing document out of the working tree. Nothing in the current code
can reach that state; that is exactly the kind of fact that stops being true
later, so the guard is unconditional and is tested against inputs the application
cannot currently produce.

⚠️ **DO NOT generalise the receiver to `Legislation.document`.** That field's
file *is* shared in the way Django's default protects against — publish copies a
draft's bytes into it, and older bills may point at paths under
`exportable_media/`. A published bill's document is chapter history and must
outlive the row.

## Testing

**31 new tests. NONE EXECUTED** — the sandbox has no working Django (the repo
`.venv` is a macOS interpreter). **This is the sixth consecutive batch shipping
unrun tests.** The previous five were green when finally run, which is reassuring
about the code and still says nothing about the habit.

What *was* verified mechanically:

* `py_compile` clean on all 10 changed files.
* **An AST scope check over `security_utils.py`** — which caught a real defect
  before it shipped: `_log_forged_cf_header` used `cache`, and this module has
  **no module-level `cache` import** (`clear_lockouts_for` imports it inside the
  function). That is a `NameError` on the first forged request, in a security
  path, and `py_compile` cannot see it. Now a local import, matching the file.
* **The unlink guard, 9 cases** against a real temporary tree including
  `../exportable_media/…`, a nested traversal, an absolute path, a missing file
  and a directory — all refused, public file intact, the legitimate case deleted.
* **The throttle, 5 scenarios** against a fake cache: 1,000 calls from one peer →
  1 line; 200 rotated *forged values* → 0 extra lines; window elapse → 1 line
  carrying `1199 suppressed`; 5 distinct peers → 5 lines; 5 distinct junk peers →
  1 line, all keys under 100 chars.
* **Every `summary[…]` subscript in both readers resolves** against the keys
  `get_performance_summary()` actually returns — run as a script here, and
  shipped as `test_every_reader_of_the_summary_asks_for_a_key_it_returns` so the
  next rename cannot break a page silently.
