## 💡 The changelog index now groups releases by minor series, automatically

### The problem

`/changelog/` split detailed changelogs into exactly two buckets: a flat row
of one badge per v3+ release, and a single "Version 2.x" catch-all
collapsible for everything before it. v3.29.x alone has shipped **32**
patch releases — more than most projects ship in their whole lifetime — so
the flat row for v3 had become a wall of nearly-identical badges with no
way to tell at a glance which minor series they belonged to.

### The fix

New `group_changelogs_by_minor()` (`src/view/changelog.py`) collapses every
changelog file into a `{major}.{minor}.x` group — e.g. every `v3.29.*` file
becomes one `3.29.x` group — keyed purely on `(major, minor)` parsed from
the filename. **There is no hardcoded list of series anywhere in it**: the
function walks whatever `.md` files are actually in `changelogs/` on each
call, so the first `v3.32.0.md` that ever gets written creates a brand new
`3.32.x` group the next time the (cache-TTL-bounded) index is rebuilt, with
nothing to update in the view or the template. This replaces the old
major-version-3 cutoff entirely — v2.x and v3.x now go through the exact
same grouping mechanism instead of one being special-cased.

`templates/changelog.html`'s "Detailed Version Changelogs" card now renders
one row per group — a toggle button showing the series label, its release
count, and an amber dot if any release in it had an external contributor —
that expands its own dropdown panel of that series' individual version
badges (same badge styling and per-version external-contributor dot as
before). The newest series is expanded by default; every other series
starts collapsed. Any number of groups can be open at once — each toggle
only opens or closes its own panel — and the existing "Community
contributions" filter still works across every group: it hides badges (and
whole groups) with no external contribution, and force-opens any group that
does have one so the matching badge is actually visible rather than sitting
in a collapsed panel.

The old flat v3+ row and the single hardcoded "Version 2.x" toggle/JS
(`toggleV2`, `#v2-changelogs`, `#v2-chevron`) are gone, replaced by the
generic per-group toggle (`toggleChangelogGroup`) — one function instead of
one bespoke one, since the mechanism no longer needs to know which major
version it's looking at.

### Tests

New `src/tests/landing/test_changelog_grouping.py` (11 tests):
`group_changelogs_by_minor()` unit tests — same-series entries collapse into
one group, different series stay separate, a series with no prior releases
in this codebase (`3.32.x`) still produces a correct group (the actual
point of "automatic"), within-group ordering is semantic-version-aware (not
string sort, so `v3.29.10` sorts above `v3.29.2`), the external-contributor
flag propagates correctly in both directions, an empty input produces no
groups, and the group's `key` is dot-free (used as an HTML id). Plus three
integration tests against the real `changelogs/` directory, deriving
expectations from what's actually on disk rather than hardcoding a version
number (same technique `test_changelog_cache.py`'s
`test_known_versions_come_from_the_directory` already uses): every minor
series present on disk gets a rendered group label, the newest group's
panel is not hidden by default, and at least one older panel is.

All new tests green on sqlite. Re-ran the full `src.tests.landing` suite
(26 tests, includes the pre-existing viewer-independent-caching guards from
v3.17.4/v3.17.5 — this change touches the same view, so it mattered that
