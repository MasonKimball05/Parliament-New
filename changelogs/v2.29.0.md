# v2.29.0 — Daily Site Digest, Automated Housekeeping & Email Change Verification

**Release Date:** 2026-06-02
**Deployment Status:** Pending
**Type:** Feature

---

## Overview

Replaces two separate scheduled tasks (weekly system audit and daily honeypot digest) with a single unified daily digest that runs every night at 3:30 AM CST. The digest always sends — an absence of the email is itself a signal the task stopped running. Adds four new automated housekeeping tasks that clean up data the audit was detecting but not acting on. Closes a HIGH severity security gap: email address changes now require confirmation before taking effect.

---

## Daily Site Digest

### What Changed

The weekly system audit (`tasks.weekly_system_audit`) and the daily honeypot digest (`tasks.send_daily_honeypot_digest`) have been retired and replaced by a single task: `tasks.send_daily_digest`.

**New behavior:**
- Runs every night at 3:30 AM CST (instead of the audit on Sundays only)
- Always sends an email — even on a fully clean run — to confirm the system ran
- Shows all check results (OK and flagged), not just issues
- Includes a "Honeypot Activity (last 24h)" section: total hits, attack-blocked count, top targeted endpoints, top attacking IPs with blacklist status
- Subject line includes the date and status: `[Parliament] Daily Digest — Mon Jun 2 — ALL CLEAR`

**Email structure:**
```
Parliament Daily Site Digest
============================
Date / Run time / Duration / Status

HONEYPOT ACTIVITY (last 24h)
-----------------------------
Total hits / Attack-blocked / Top endpoints / Top IPs [BLACKLISTED / not blacklisted]

HIGH SEVERITY        (if any)
MEDIUM SEVERITY      (if any)
LOW SEVERITY         (if any)

ALL CHECK RESULTS
-----------------
[OK] category: message   ← every check, not just flags
...

CHECKS THAT ERRORED  (if any)
```

**Files changed:**
- `src/tasks.py` — new `send_daily_digest` task; removed `weekly_system_audit` and `send_daily_honeypot_digest`
- `src/management/commands/setup_celery_schedules.py` — updated Beat schedule entries

## Automated Housekeeping Tasks

Four new Celery tasks that clean up data the daily digest audit was detecting but not resolving.

### `prune_expired_login_lockouts` (daily, 3:05 AM CST)

Deletes `LoginLockout` rows whose `expires_at` has passed and that were not manually cleared by an admin. The cache lockout expires automatically; the DB row previously stayed forever. Manually-cleared rows are retained for audit history.

### `expire_stale_ip_blacklist_entries` (daily, 3:10 AM CST)

Sets `is_active=False` on `IPBlacklist` entries that have passed their `expires_at`. Entries with no `expires_at` are permanent and are not touched. Previously these entries stayed active past expiry until someone manually toggled them in admin-v2.

### `prune_stale_push_subscriptions` (monthly, 1st at 3:15 AM CST)

Deletes `PushSubscription` records that haven't been used in 90+ days. Subscriptions returning 410 Gone are already deleted on send; this catches the remainder — subscriptions from browsers where the user revoked permission or cleared site data and never explicitly unsubscribed.

### `prune_old_auth_tokens` (monthly, 1st at 3:15 AM CST)

Deletes DRF auth tokens older than 90 days. DRF tokens have no built-in expiry; without this they accumulate indefinitely for every user who has ever called `/api/v1/auth/token/`.

**Files changed:**
- `src/tasks.py` — four new task definitions
- `src/management/commands/setup_celery_schedules.py` — five new Beat schedule entries

## Email Change Verification (HIGH severity fix)

Previously, submitting a new email address via the "Set Email" form saved the change immediately with no confirmation step. A user with brief session access (shared device, session hijack) could silently reroute password reset and 2FA recovery emails to an address they control.

### New behavior

- **First-time email set** (account has no email): saved immediately — no friction for new members completing onboarding.
- **Changing an existing email**: a confirmation link is sent to the *new* address. The change is not applied until the link is clicked.

### Details

- Token stored in the new `EmailVerificationToken` model (UUID, 24-hour expiry, single-use)
- Submitting the form again invalidates any existing pending token before issuing a new one
- Rate-limited to 3 verification emails per hour per user
- The new address is checked against existing accounts before sending — duplicate addresses are rejected immediately
- Confirmation link requires the same logged-in user who initiated the request (`GET /set-email/confirm/<uuid>/`)
- If the new address gets claimed by another account between request and confirmation, the token is invalidated and the user is prompted to try again

**Files changed:**
- `src/models/security.py` — new `EmailVerificationToken` model
- `src/models/__init__.py` — model exported
- `src/view/set_email.py` — rewritten; new `confirm_email_change` view
- `src/urls.py` — added `set-email/confirm/<uuid:token>/` route
- `templates/emails/` — HTML confirmation email template (inline)
- `src/migrations/0184_email_verification_token.py` — new migration
