already works today, not an on switch for something new. Deploying this

## Design decisions made under judgment (per Mason's "make a reasonable call
and note it" standing instruction)

**`event_attendance` / `excuse_system` are additive, not alternatives to
`attendance_tracking`.** All three flags are already-independent AND-gates:
attendance-taking and excuse-handling each need `attendance_tracking` *and*
their own flag on. This mirrors this codebase's existing `ical_export` /
`calendar_subscriptions` pattern (one flag for the button, one for the
endpoint) rather than either duplicating `attendance_tracking` wholesale or
discarding the two new flags as redundant.

**`document_versioning` gates a feature that did not exist yet, not a
toggle on existing behaviour.** `DocumentVersion` had zero writers anywhere in
the codebase before this release — no "replace this file" action existed to
gate, only delete-and-re-upload-as-new. Built `committee_replace_document`
(archives the current file as a `DocumentVersion` row, bumps
`document.version_number`, chair-only) and
`download_committee_document_version`, both behind the flag, plus a version
history panel and Replace-File button in `committee/documents.html`. Off: the
delete-and-re-upload path is untouched — there is no bare-overwrite behaviour
to preserve, because there never was one.

**`email_notifications` routes through one chokepoint, not ~15 call sites.**
Rather than editing every `send_mail`/`EmailMessage` call, added
`src/email_backend.py::FeatureFlagGatedEmailBackend`, set as
`settings.EMAIL_BACKEND` with the real backend moved to
`settings.REAL_EMAIL_BACKEND`. When the flag is off, only mail whose subject
matches a small always-send allowlist actually transmits — 2FA codes,
password resets, email-change confirmation, security alerts, watch-flag
notices, preflight failures. Everything else (announcements, digests, welcome
mail) is silently dropped, same as if `email_notifications` had always meant
something. `check_env.py` and `bug_report.py` both read
`REAL_EMAIL_BACKEND` (falling back to `EMAIL_BACKEND`) so they keep reporting
the actual transport rather than this wrapper's class name.

**`committee_system` has a named gap, left as a gap rather than closed
here:** deep-linked committee sub-pages (chat, documents, attendance,
minutes, recruitment, education) are not individually gated by this flag —
only the index/home/management surface and the nav entry are. Closing that
is a bigger, separate change (each sub-page has its own existing gates to
reconcile with) and wasn't part of "wire the flag that gates nothing" — it
already gates something, just not everything its name might suggest.

## ⚠️ Deploy note: `email_notifications`'s seeded default changed

It was seeded `is_enabled: False` while gating nothing, so the value was
inert. Now that it's load-bearing, the seed default was flipped to `True` to
preserve current behaviour (email has always gone out). **But
`seed_feature_flags`'s `get_or_create` never touches `is_enabled` on a row
that already exists** — only `display_name`/`description`/`category` sync.
If prod already has an `email_notifications` row (it likely does, from an
earlier partial seed run), this deploy's seeder will **not** flip it to
`True`. **Check `/admin/` → Feature Flags → "Email Notifications" is enabled
before/after this deploys**, or non-critical chapter email will silently stop
going out with nothing in the logs to say why.

## Two regressions found running the full suite, both fixed in this release

Running the full suite (rather than just the new tests) surfaced two real
problems this batch introduced — both in how *stacking flags on one page*
interacts with the rest of the codebase, not in any single flag's logic.

**`require_feature_flag` now takes multiple names in one call, not stacked
decorators.** `event_attendance_list`, `my_attendance`, `review_excuses` and
several others needed both `attendance_tracking` and a new sub-flag, and were
written as two stacked `@require_feature_flag(...)` decorators. Each one is
its own cached lookup, so two stacked decorators cost two `src_featureflag`
queries on a cold cache where one flag cost one — tipping several pages from
2x the same query shape (already normal, under threshold) to 3x, and failing
`test_url_smoke` / `test_detail_route_smoke` / `test_query_budgets`' N+1
detectors on nine pages. `require_feature_flag(*feature_names)` now resolves
every name in one call via the existing `FeatureFlag.resolve_many` (built in
v3.19.7 for the identical shape of problem, a loop rather than a stack). All
12 stacked call sites from this release collapsed to one call each.

**The dark-mode inline script broke on any database with no `dark_mode`
row** — reproduced by `test_changelog_cache.py`'s cross-visitor cache tests,
which build bare fixtures. `{% if feature_flags.dark_mode %}` in base.html's
theme-detection script read the `feature_flags` context dict, which is
**deliberately fail-CLOSED** (documented codebase-wide asymmetry — see
`FeatureFlag.is_feature_enabled`'s docstring); a behaviour switch read
through it inherits that and fails closed too, forcing every session to
light mode the moment the flag row is absent. Fixed by having the
`feature_flags` context processor also resolve a `dark_mode_enabled` value
the fail-OPEN Python way, from the *same* query rather than a second one (a
first attempt added a second context processor calling
`is_feature_enabled('dark_mode')` directly — correct in isolation, but a
second `src_featureflag` query on every single page, reintroducing the first
regression). base.html's script also had a multi-line `{# #}` comment,
caught by the same run — Django's hash-comment syntax is single-line only,
so it was rendering as literal text on every page; converted to
`{% comment %}...{% endcomment %}`. And the first attempt at the fix changed
`const theme = '...'` from a literal string into a JS ternary, which is
functionally equivalent but broke `test_changelog_cache.py::theme_of()`'s
regex parser — reverted to a template-level `{% if %}` that still emits a
plain quoted string.
