# v3.17.5 — Auto-run fixes: cache-key bounding, geo-restricted exports, and two ceilings

**Date:** 07-30-26
**Type:** Fix batch (security + hardening). No migration, no new dependencies.
**Deployed:** ✅ 07-30-26 — shipped in `c608f82`.

The five findings from the 07-30-26 auto-run report. Four of the five land on
code that v3.17.3/v3.17.4 had *just* touched — in each case the fix was right
about the problem it named and left a second one standing next to it. That is
the theme of this release and it is worth stating plainly: **a fix that closes
one property of a change does not close the others.**

## 🟠 1. `changelog_detail` minted unbounded, anonymous-chosen cache keys — in the Redis that also stores every session

**Files:** `src/view/changelog.py`

v3.17.4 correctly removed `@cache_page` from the three public content pages: it
caches the whole *response*, those pages extend `base.html`, and so the cached
HTML carried whichever visitor primed it — their navbar, their name, their
theme. All of that is closed and stays closed.

But the replacement keyed on `f'changelog_detail_v1:{safe_version}'`, and the
**not-found branch fell through to the same `cache.set(...)` as a hit**. The
route is `changelog/<str:version>/`, public, no rate limit. So every distinct
junk URL an anonymous visitor requested minted its own 30-minute entry.

The comment sitting directly above it said the opposite:

```python
# Cache key uses the SANITISED version, so it cannot be poisoned by an
# attacker-controlled path […]
```

**Sanitising the key stops key *injection*. It does nothing about key
*cardinality*.** Measured through the test client: 25 requests to
`/changelog/<random-hex>/` produced **25 new cache entries**, each returning
**HTTP 200** with the body `Changelog for version … not found.`

### ⚠️ Why this is not merely cache bloat

`Parliament/settings.py`:

```python
SESSION_ENGINE      = 'django.contrib.sessions.backends.cache'
SESSION_CACHE_ALIAS = 'default'
```

**Sessions and this cache are the same Redis.** So an unauthenticated loop
contends with session storage, and which way it fails depends on
`maxmemory-policy`: under `allkeys-lru`/`allkeys-random` it evicts sessions — a
chapter-wide logout — and under `noeviction` Redis refuses writes, and the write
that fails is the session write, so login breaks. `LoginRateLimitMiddleware` and
`PasswordResetRateLimitMiddleware` are the only rate limiters in the stack and
neither covers this path.

### Fix

1. **New `known_versions()`** — the set of versions that actually have a file,
   read from the `changelogs/` directory and cached under the same TTL (it only
   changes on deploy). A version not in it is a **404 before the cache is
   touched**, so the key space is bounded by files-on-disk (~97) no matter what
   is requested.
2. **Only a successful parse is cached.** Both failure paths return early.
3. **A missing version is a 404**, not a cached 200.
4. **`str(e)` is gone from both views.** It was interpolated into
   `changelog_html`, which both templates render through `|safe` on a *public*
   page — so a filesystem error showed anonymous visitors the server's absolute
   `BASE_DIR`, and then cached it for thirty minutes. Logged now, generic
   message shown. (Same shape as the CSV export leak fixed 07-28-26.)

**Checked and clear:** the `safe_version` interpolation is *not* an XSS — the
filter keeps only `[alnum].-`, so no `<`, `>`, quote or slash survives, and it
lands in text content rather than an attribute.

## 🟡 2. `GeoRestrictionMiddleware` could not express a parameterised export route

**Files:** `src/middleware/geo_restriction.py`

The restriction list was a tuple of path prefixes matched with
`path.startswith(...)`. Every entry in it happened to have a **static** prefix,
which hid a structural gap: **a route with a parameter in the middle of it
cannot be written as a prefix at all.**

`event_signup_export` is exactly that route —
`/calendar/event/<int:event_id>/signups/export/` — and it writes **Name and
Email for every member signed up to an event**, the same class of bulk member
data as the directory and user-list exports already in the list. It could not be
added. It has also been a hard 500 since v3.9.1 (see §3), so it is about to be
reachable in production for the first time.

**Fix:** the list is now `RESTRICTED_EXPORT_VIEWS`, a frozenset of **resolved
URL names**. That is parameter-agnostic, survives a route being moved or
re-pathed, and makes the list read as a list of *capabilities* rather than a
list of strings. `event_signup_export` is now in it.

Notes on the implementation:

- Middleware runs **before** Django's handler sets `request.resolver_match`, so
  `_restricted_view_name()` calls `resolve()` itself. `resolve()` reads the
  cached resolver (a dict lookup, not a re-parse), and it only runs for sessions
  already flagged non-US — the rare path.
- `RESTRICTED_PATH_PREFIXES` is **kept**, OR'd with the name check, as
  belt-and-braces for any route with no `name=`. It now holds one entry:
  `/officers/db-dump/`, which — worth recording — **matches no route anywhere in
  `src/urls.py`** (verified 07-30-26). Kept deliberately: it costs one string
  comparison and fails closed if that endpoint ever comes back.
- The block log line now carries the resolved view name alongside the path.

## 🟡 3. The revived sign-up views gated on `is_officer`, which excludes Chairs

**Files:** `src/view/calendar.py`

v3.17.3 found that `event_signup_list` and `event_signup_export` both imported
`src.utils.officer_check` — **a module that has never existed**, added in v3.9.1
and never written — so both had been a hard `ModuleNotFoundError` 500 for a
year. Correct find, correct fix.

The replacement reached for `request.user.is_officer`. That is a real property,
but it is **not what the rest of the app means by "officer"**:

```python
# src/models/users.py
is_officer  ->  member_type == 'Officer' or is_admin

# src/decorators.py — what every other officer view uses
officer_required  ->  "officers, chairs, and admins"
```

So a **Chair would have got a 403 on the sign-up list for an event they run**.
Nobody ever hit it, because the view 500'd before reaching the check — it would
have shipped as a first-appearance bug the first time the page loaded in prod.

**Fix:** both views now carry `@officer_required` and the inline check is gone.
Two things come free with the decorator: the denial passes through `_gate()`, so
it appears in dev mode's Perms tab and the authz log; and the response is the
app's standard 403 body rather than a bare `PermissionDenied`.

A static guard (`test_the_inline_is_officer_check_has_not_come_back`) fails the
suite if `if not request.user.is_officer` reappears in `calendar.py` — the
inline check is easy to re-add and looks harmless.

## 🟡 4. `view_all_reports` materialized the whole `CommitteeDocument` table

**Files:** `src/view/officer/view_all_reports.py`, `templates/officer/view_all_reports.html`

v3.17.4 fixed a real problem here — the view queried the table six times, once
per `document_type` tab — by fetching once and partitioning in Python. But the
rewrite also turned a lazy queryset into `list(...)` **with no slice**. The
comment justified it as:

> *"the page renders every document anyway, so there is nothing to save by
> filtering in SQL"*

True of the **filtering**. Not true of the **fetch**. `CommitteeDocument` is
append-only and grows for the life of the chapter.

**Fix:** `[:DOCUMENT_FETCH_LIMIT]` (500). Ordinary pagination does not fit —
the six tabs are **client-side**, so every tab's rows must be in the one
response, and a cap is the only shape available.

**The part worth remembering:** a capped page must not count the capped list.
`type_totals` comes from a separate one-line GROUP BY so the tab badges report
**true** totals, and a truncation notice renders when the cap bites. Counting
`len(all_documents)` instead would tell a chapter past the cap that it has
exactly 500 documents, forever.

## 🟡 6. `active_quarantines.count` ran six `SELECT COUNT(*)` on one page load

**Files:** `src/view/admin_v2.py`, `templates/admin_v2/security_dashboard.html`, `templates/admin_v2/quarantine_management.html`

Found by dev mode's N+1 panel, which reported it as a 4× repeated shape with
template attribution pointing at four expressions in `security_dashboard.html`.
The measured number is **six**: `.count` appears six times across the file (card
border, card number, nav badge ×2, section badge ×2), and the same queryset is
then iterated.

**`.count` on a queryset is a fresh `SELECT COUNT(*)` every single time.** The
queryset result cache does not cover it, and neither does having already
iterated the queryset — so the more places a template shows the number, the more
round trips it costs. `quarantine_management.html` had the same shape in
miniature: `.count` for the heading, a truthiness test, then the loop.

**Fix:** the same one the 07-28-26 review applied to the global-search page —
materialize in the view (`list(...)`, with an explicit `order_by`, since a
`list()` of an unordered queryset takes whatever order the backend feels like),
`|length` in the template. Both views and both templates.

Not slice-capped: the filter is unreleased-and-unexpired and a member can only
be quarantined once at a time, so the row count is bounded by chapter size.

**Measured against the pre-fix code: 6 `COUNT(*)` on `src_quarantinedaccount`
for one dashboard load, now 0.**

## 🟡 7. The site-wide `.count`-in-a-template sweep

**Files:** 9 views, 21 templates, new `src/test_template_counts.py`

§6 was one instance. Sweeping every template for the same pattern found ~30
more. Fixed in three shapes, chosen per site:

**Lazy context queryset the template also iterates → `|length`.** This is the
cheap, large win and it needs no view change: `|length` calls `len()`, which
*evaluates and caches* the queryset, so the `{% if %}` and `{% for %}` that
follow reuse that cache. `.count` primes nothing, so
`{{ x.count }} thing{{ x.count|pluralize }}` plus a loop was three queries where
one does. Applied to `ip_blacklist`, `ip_whitelist`, `attendance`,
`kai/user_dashboard`, `public_songbook`, `applications_review`,
`songbook_categories`, `recruitment_event_detail`, `announcement_poll_results`,
`period_setup`, `slate_builder`.

**Un-prefetched related manager in a loop → annotate `Count()` in the view.**
The real N+1s. `Resolution.amendments` (12 references across 7 templates —
`cnb/dashboard.html:135` used it *twice on one line*), `GoverningDocument.articles`,
`Committee.members` on the classic home page (which also needed
`chairs`/`advisors` prefetched — four queries per committee), and
`SongCategory.songs`. Also `songbook_list` had a literal `.count()` inside a
Python `for` loop over categories; that is now one filtered aggregate.

**Counted *and* iterated → add the missing `prefetch_related`.** `edit_resolution`
and `confirm_delete_resolution` had none.

Two things found while sweeping that were bugs rather than slowness:

- **`slate_builder.html` was showing the wrong number.** The line read
  `{{ slate.candidates.filter.is_runoff.False.count|default:slate.candidates.count }}`,
  which is not a valid expression: Django resolves `candidates.filter` to the
  bound method, **calls it with no arguments** (returning the unfiltered
  queryset), fails to find `.is_runoff` on that, and the whole chain collapses
  to `''` — so `|default:` silently fell through to the total candidate count.
  It had been reporting *all* candidates, runoffs included, as "N of M positions
  filled". Now computed from the `assignments` dict the view already builds.
- **`edit_announcement.html`** printed the poll's question and response counts
  twice each — four COUNTs for two numbers. One aggregate.

### ⚠️ A measured correction to CLAUDE.md's sweep list

CLAUDE.md's page-performance rules say:

> `.exists()` called on a prefetched relation (bypasses the prefetch cache — use
> `list(.all())`)

**That is not true on Django 5.2, and I checked rather than assuming because I
had already written it down as fact.** On a relation that *is* prefetched, both
`.count()` and `.exists()` read the prefetch cache and cost **zero** queries —
`RelatedManager.get_queryset()` returns the cached queryset, and
`QuerySet.count()`/`.exists()` short-circuit on `_result_cache`. Measured with
`CaptureQueriesContext`, both directions:

| | prefetched | not prefetched |
|---|---|---|
| `.count()` | **0 queries** | 1 query |
| `.exists()` | **0 queries** | 1 query |
| `len(.all())` | 0 queries | 1 query |

So `prefetch_related` genuinely does fix those, and the four `.exists()` calls
v3.17.3 prefetched (`directory.html`, `applications_review.html`,
`my_applications.html`, `committee/vote_result.html`) were already correct — they
are allowlisted in the new test rather than rewritten. What remains true, and is
what actually cost queries here, is `.count` on a **lazy context queryset** (a
query every time, and it primes no cache for the loop) and on an
**un-prefetched relation** (one per row). **The rule in CLAUDE.md should be
corrected.**

The new `src/test_template_counts.py` scans every template and fails on any
`.count`/`.exists` not in an allowlist keyed by *file and expression*, so each
exemption is a decision about a specific line and naming the same variable
elsewhere does not inherit it. A second test fails if an allowlist entry outlives
the line it excuses.

## 🟠 8. The N+1 sweeps were reporting clean because their fixtures were empty

**Files:** `src/test_url_smoke.py`, `src/test_detail_route_smoke.py`, plus the three views this found

§6 and §7 were found by dev mode and by hand. The obvious question is why
`test_no_page_repeats_a_query_shape` — a real N+1 detector that already existed
— had not found any of them.

**It was not broken. It was starved.** The fixture seeded six rows each of
Announcement, Event, Legislation, Vote, ActivityLog, Role and Committee, and
*nothing at all* for GoverningDocument/Article/Section, Resolution,
SongCategory/Song, CommitteeDocument or QuarantinedAccount. Those pages rendered
with zero rows. **A per-row query that fires zero times repeats zero times.**

Measured on the pre-fix code, same page, same detector, only the fixture varied:

| `/songbook/categories/` | repeated shapes |
|---|---|
| no categories seeded | none |
| five categories seeded | **5× `src_song`** |

This is the third time this exact lesson has been paid for in that one file. Its
own comments already say *"a fixture that doesn't vary the data doesn't reach the
code"* (the `member_type` spread) and *"a fixture that skips the optional FK
tests the early-return path, not the page"* (the committee `role`). The third
form is the one that had not been written down: **a fixture that omits a model
entirely excludes its pages from every sweep in the module, and nobody decides
that.**

### What changed

1. **Fixtures widened** — `_seed_v3_17_5_families()` adds documents/articles/
   sections, resolutions with amendments, categories with songs, committee
   documents in *every* `document_type`, and quarantines. Row counts are
   deliberately above the repeat threshold.
2. **Every repeated shape is checked, not just the worst.** Both sweeps tested
   `shapes.most_common(1)`, so a page with three *different* shapes repeating
   three times each passed clean while a page with one shape at four failed.
3. **Threshold 4 → 3, chosen by measurement rather than taste.** Across the
   whole sweep: **≥2 → 489 hits** (a count plus a fetch of the same table is
   normal; 2 is noise), **≥3 → 6**, **≥4 → 0**.
4. **`ACCEPTED_REPEATS`** allowlists the repeats reviewed and deliberately not
   fixed, each with its reason — and `test_accepted_repeats_are_still_repeating`
   fails if an entry stops being needed, so fixing a repeat deletes its own
   exemption.

### What it found on the first run

- **`public_songbook_list` — a `.count()` per category, on the public,
  unauthenticated songbook.** Same shape as the `songbook_list` fix in §7, on
  the one page in the app that needs no login to hammer. This is the payoff:
  a page nobody had looked at, found by the tool rather than by reading.
- **`view_all_activity` — `view_all_reports`' twin.** One base queryset plus
  three `.filter(status=…)` derivatives per family, all four rendered: four
  SELECTs over the same rows, per family. Fetched once and partitioned in
  Python, capped like its twin. (`3× src_legislation` **and**
  `3× src_committeelegislation` on one page — the kind of double hit the
  `most_common(1)` rule was structurally unable to report.)
- **`legislation_detail` — a COUNT per vote choice.** Four in the percentage
  branch, one-per-option plus a total in plurality. **This is the fourth site of
  the pattern v3.17.1, v3.17.2 and v3.17.3 each fixed once somewhere else** —
  which is the argument for the sweep over another manual pass. Now one
  `values('vote_choice').annotate(Count(...))`.

### Reviewed and *not* a finding

The first probe showed `otp_totp_totpdevice`, `otp_static_staticdevice` and
`src_usersession` repeating on **every** page, which looked like a site-wide
per-request cost worth 🟠. It is not: `two_factor_status` caches for 5 minutes
and `SessionTrackingMiddleware` throttles both its fingerprint check and its
session write through the cache. The probe cleared the cache before each request,
so it measured the cold path only. Recorded here because the next person to run
a sweep with `cache.clear()` in the loop will see the same thing and reach the
same wrong conclusion.

**Verified against the pre-fix code, not just the fixed code.** The old

  the inline-check guard).
- `ChangelogDetailCacheKeysAreBoundedTests` → **2 failures**
  (`test_unknown_versions_create_no_cache_entries`,
  `test_unknown_version_is_a_404_not_a_cached_200`).
- `ActiveQuarantinesIsCountedOnceTests` → **4 failures**, and the query-count
  assertion is what produced the "6, not 4" number above.

Worth noting which test would *not* have caught things:
`test_the_bulk_member_data_exports_are_all_listed` passes against the broken
middleware, because the list held the right *names* — the gap was that names
were not what it matched on. The behavioural block test is the one that catches
it. A membership assertion is not a substitute for exercising the control.

A test that passes against the bug it exists to catch is worse than no test —
this codebase learned that on 07-29 with `auto_now_add` and the frozen clock.
