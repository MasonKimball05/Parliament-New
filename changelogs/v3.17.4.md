# v3.17.4 — A shared page cache, a nightly date bug, and six N+1s

**Deployed:** ✅ 07-29-26 — shipped in `b2ffd17`.
Reported as *"the changelog page on prod is suddenly displaying in light mode."*
It is not a theme bug. The theme was the visible symptom of a shared response
cache, and the same mechanism was showing a logged-in member's navbar to
anonymous visitors.

Implemented 07-29-26. Three unrelated things ended up in this release because
each one uncovered the next: fixing the sweep that finds N+1s revealed six of
them, and running the tests that had been skipped all evening revealed a date
bug that only fails after 19:00.

**One migration (`0010`), no new dependencies.** On PostgreSQL `0010` emits no
SQL whatsoever — see [Deploy](#deploy).

---

## What was happening

`changelog`, `changelog_detail` and `roadmap` have carried
`@cache_page(60 * 30)` since **v3.11.1**. `cache_page` caches the whole rendered
**response**. All three pages are **public** and extend `base.html`, so the
cached HTML included whatever the first visitor's page looked like:

- the inline `const theme = '{{ user_prefs.theme|default:"light" }}'` that
  switches dark mode on,
- their name and avatar in the navbar,
- their notification badges,
- any admin-only nav links they could see.

Whoever primed the cache decided the page for everyone else for the next 30
minutes. Reproduced both directions:

| cache primed by | dark-mode member sees | light-mode member sees | anonymous sees |
|---|---|---|---|
| dark-mode member | dark ✓ | **dark ✗** | **dark ✗** |
| anonymous | **light ✗** | light ✓ | light ✓ |

The reported symptom is the second row: a public visitor (or a crawler — these
pages need no login) hits `/changelog/`, and every dark-mode member gets light
until the entry expires. **"Suddenly" is just the 30-minute TTL turning over**, or
a deploy/Redis restart re-priming it.

And the more serious half, also reproduced: with an admin priming the cache, a
different member's page showed **the admin's name instead of their own**, and an
anonymous visitor got the admin's name too.

## Why `Vary: Cookie` did not save us

This is the counter-intuitive part, and the reason it survived review — the
response really does carry `Vary: Cookie`.

`UpdateCacheMiddleware` runs **inside** the `cache_page` decorator, so it stores
the response *before* `SessionMiddleware` adds the Vary header. The learned Vary
list is therefore empty and the cache key is **the URL alone**. The
`Vary: Cookie` you can inspect on the response is added afterwards, too late to
influence the key.

So the header is real, the protection is not.

## The fix

`@cache_page` removed from all three views. Instead, the **expensive part** is
cached and the template renders per request:

- `changelog` — reads `CHANGELOG.md`, markdown-parses it, then opens **all 97
  files** in `changelogs/` to extract contributors. That is the real cost, and it
  is now cached as context data under `changelog_index_v1`.
- `changelog_detail` — the parsed HTML per version, keyed
  `changelog_detail_v1:<version>` using the **sanitised** version string, so a
  hostile path cannot choose the key it writes to.
- `roadmap` — **no caching at all.** Its context is literal Python lists; there
  was nothing to save, so the decorator bought no speed and only shared the
  navbar.

Measured: `/changelog/` cold **337 ms**, warm **7 ms**. The saving is intact.

## The rule

> **Never cache a response whose body depends on who asked for it.**

Same failure class as the 07-18-26 Cloudflare seal incident, and the reason
dev mode sets `Cache-Control: private, no-store` on its own responses. Worth
noting `base.html` makes almost every page in this app viewer-dependent, so
`cache_page` is essentially never the right tool here — cache the data instead.

Checked while fixing: **no other view uses `cache_page`, and there is no
site-wide cache middleware.** This was the only instance.

## Tests

**`src/test_changelog_cache.py`** (new, 10 tests). Verified the way a regression
test should be — against the pre-fix code it fails on **8** of its assertions,
and passes on the fix.

- `test_no_view_uses_cache_page` — a static guard so the decorator cannot come
  back. If a genuinely viewer-independent endpoint ever needs it, add an
  allowlist entry with a reason rather than deleting the test.
- `test_no_site_wide_cache_middleware` — the same hazard applied to every page at
  once.
- The behavioural half: each visitor gets their own theme; a dark member is not
  given the anonymous page (the exact reported symptom); one member's identity
  does not appear in another's navbar; nothing authenticated reaches an anonymous
  visitor. That last one asserts on link `href`s rather than the word "Admin",
  which appears ~64 times in the changelog prose and is not a leak.
- `ChangelogContentIsStillCachedTests` — removing `cache_page` must not have
  removed the point of it.

## Also: `preflight` crashed instead of reporting

`src/management/commands/preflight.py`

v3.15.8 built `manage.py preflight` as the gate for deploys and cron, and its
note said it needed one local run before being relied on. **This was that run,
and it did not survive it.**

`check_celery_schedules` guards its two imports but not its query, so against a
database where `django_celery_beat` has not been migrated it died with a raw
`OperationalError` traceback — no summary, no exit code, no indication of which
check failed. That is the one environment a preflight tool most needs to survive:
its entire job is reporting on a broken setup, so a broken setup has to come out
as a **finding**, not a crash.

The query is now wrapped and reports
`✗ Celery schedule table — could not query PeriodicTask … run migrate first`.

With that fixed, the first complete run reports **34 passed, 5 warnings,
8 failed, exit 1**. All eight failures are expected in a sandbox (dev `DEBUG`,
five unmigrated tables, and `MEDIA_ROOT`/`LOG_DIR` not writable there). The
useful part is what passed, unprompted:

- all **6** vendor asset hashes verify against `.integrity.json`
- **no CDN references** across 315 templates
- the Django media gate **302s an anonymous request** — the v3.14.1 leak check

**Noted, not fixed:** the `pip-audit` CVE scan resolves to
`shutil.which('pip-audit')` or `BASE_DIR/.venv/bin/pip-audit`. If neither exists
on prod it *warns and skips* rather than failing, which is a quiet gap given
v3.15.10 deliberately made the other supply-chain checks hard-fail. Worth
deciding whether a missing CVE scanner should block a deploy — that is a policy
call, not a bug.

## The sweep was blocking itself, and hiding five N+1s behind a 403

`test_url_smoke.py` visits every zero-argument page and flags any that repeats a
query shape four or more times. It reported clean. It was not clean — it was
**not reaching most of the site**.

The app's own security middleware auto-blacklists an IP after enough suspicious
requests, and a sweep of ~300 URLs from one client looks exactly like an attack.
The test already cleared the cache between pages, which was not enough: **the
block is a row in the database, not a cache entry.** After roughly 132 pages,
every subsequent page returned 403 — and the test's own `status_code >= 400`
guard skipped them silently. A test that appears to check 282 pages while
actually checking 132 is worse than no test, because it is trusted.

Both sweeps now delete any `IPBlacklist` row they create about themselves, and
assert on the number of pages actually exercised (`> 100`), so a future
reachability regression fails loudly instead of quietly shrinking the sweep.

With the site fully reachable, five N+1s appeared immediately:

| page | before | cause |
|---|---|---|
| `manage_announcements` | 50× + 25× + 11× + 8× + 6× | `get_view_stats()` per row in the template |
| `manage_roles` | per-role member counts | no aggregate |
| `view_all_reports` | per-report joins | missing `select_related` |
| `manage_committees` | per-committee lookups | missing `prefetch_related` |
| `manage_events` | per-event counts | missing `select_related` |

`manage_announcements` was the worst: five separate per-row queries, one of them
counting active members **by member type for every announcement on the page**.
It is now two queries for the whole page — `annotate_view_stats()` does the view
counts as conditional aggregates, and the member-type census is computed once and
attached to each object. Verified identical output across 9 announcements × 9
`visible_to` shapes.

And a sixth, of a kind now familiar: `service_form_builder` ran
`get_or_create()` per built-in field on **every page load** — six SELECTs to
discover that nothing needed creating. That is the **third** instance of
seeding-on-read this release (the admin-v2 push flags and `SiteSetting` were the
others), so it is a pattern, not an accident: one SELECT plus one
`bulk_create(ignore_conflicts=True)`, and nothing at all in the steady state.

## `Attendance.date`: the app disagreed with itself about what day it is

This one was found by three tests that had been failing **for hours without
anyone seeing it**, because the modules containing them never finished inside a
single run. They were right, and they were reporting a live bug.

`Attendance.date` was `auto_now_add=True`. Django populates such a field from
`datetime.date.today()` — the **server-local** date, because Django sets
`os.environ['TZ']` from `TIME_ZONE` (Central). But every caller looked the row up
with `timezone.now().date()` — the **UTC** date.

Those are different days from **19:00 Central until midnight**. Which is to say:
during chapter meetings, committee meetings, and every other time attendance is
actually taken.

So `update_or_create(user=..., date=<utc today>)` could not find the row it had
itself written moments earlier. Worse, `auto_now_add` also makes a field
non-editable, so the explicit `date=` those callers passed was **silently
discarded on insert** — the new row got stamped with the Central date too, which
the next request also missed. The consequences, in ascending order of severity:

- The officer attendance page's checkboxes came up **blank** for attendance taken
  earlier the same evening.
- The quick-attendance panel returned `{"ok": true}` while **inserting a new row
  on every single click**, unbounded.
- The committee-minutes path passes a real committee, where a unique constraint
  on `(committee, user, date)` exists — so saving the same minutes a second time
  in the evening was an **`IntegrityError`, i.e. a hard 500**. Reproduced.

The v3.13.3 `MultipleObjectsReturned` healing branch in `mark_attendance_quick`
turns out to have been treating this symptom. Its comment blames "two rapid
clicks racing `update_or_create`". The duplicates were not a race; they were the
clock. (The branch stays — with `committee=NULL` there is no unique constraint,
so a genuine race is still possible.)

**Fixed by converging on `timezone.localdate()`,** in twelve places, and by
changing the field to `default=timezone.localdate` so an explicit date is
honoured and a lookup key can finally agree with the row it creates. Central is
the correct basis, not a coin-flip: every row already in the table was written on
the Central calendar by `date.today()`, so Central is what reads history
correctly — and it is what a human means by the date of a meeting.

Four of the twelve sites had nothing to do with attendance. `ServicePeriod`
stopped being "current" at 19:00 Central on its own final day; the landing-page
recruitment banner hid five hours early; the notification dashboard's "logs
today" counted the wrong day's rows all evening (`__date` on a DateTimeField is
evaluated in the *current* timezone, so it must be compared against a local
date); and a partial-suspension record stamped tomorrow's date. Same root
confusion, same one-word fix.

### The test that would have caught it, and the trap in writing it

`AttendanceDateBasisTests` (6 tests) freezes `timezone.now()` to an instant that
straddles the boundary, so the two calendars disagree **regardless of what time
the suite runs**. Without that, these assertions pass for ~19 hours a day — which
is precisely how the bug survived.

The frozen instant is deliberately **2020-01-02**, six years in the past, and
that detail matters. `auto_now_add` reads the real system clock via
`datetime.date.today()`, which `mock.patch` on `timezone.now` cannot reach. With
a frozen instant near today's date, the old buggy code produces the expected
value **by coincidence** and the test passes against the very code it exists to
catch. I hit exactly that: the first version of the test passed on the broken
field. A date six years back cannot collide.

There is also a `test_the_two_calendars_really_do_disagree_at_this_instant`
guard, so if the frozen instant ever stops spanning a boundary the suite says so
instead of quietly asserting nothing.

Verified by restoring the old field definition: **5 of the 6 new tests fail**,
including the `IntegrityError`. The sixth is the guard, which correctly still
passes.

## Deploy

**One migration: `0010_attendance_date_localdate`.** On PostgreSQL it emits **no
SQL at all** — a Django `default` lives in Python, not in the DDL, and the column
itself is unchanged (`date NOT NULL`, same type, no new constraint). No rewrite,
no lock, safe against the live table at any size. Verified by building the
statement with the Postgres schema editor, which produced nothing. Contrast
`0009`, which does rewrite `src_activitylog`.

It deliberately **does not backfill and does not delete anything.** Existing rows
already hold the Central date, which is the basis the readers now use.

**After deploying, check for the duplicate rows this bug already created:**

```sql
SELECT user_id, date, attendance_type, committee_id, COUNT(*)
FROM src_attendance
WHERE attendance_type = 'committee'
GROUP BY user_id, date, attendance_type, committee_id
HAVING COUNT(*) > 1
ORDER BY COUNT(*) DESC;
```

Expect clusters on evenings when attendance was taken. Deleting attendance
records is a judgement call — hence no migration for it — but the rows are
identifiable and the newest of each cluster is the one the panel last wrote.

**Flush the cached pages after deploying**, or the poisoned entries linger up to
30 minutes:

```python
from django.core.cache import cache
cache.clear()          # or delete the changelog_* keys specifically
```

Then check `/changelog/` while logged in as a dark-mode user, and again in a
private window, and confirm each looks right.
