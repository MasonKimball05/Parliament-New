## 🟠 1. A green suite still blocked the push

`manage.py test src --parallel` printed `OK` and then crashed a moment later
while deleting its own scratch database: Django's sqlite backend does
`os.remove(test_database_name)` with no existence check
(`django/db/backends/sqlite3/creation.py`), and on Mason's machine (Python
3.14, macOS, `--parallel` with no pinned worker count) one worker's file was
sometimes already gone by the time `teardown_databases` got to it —
`FileNotFoundError: default_1.sqlite3`. The hook was trusting the process exit
code alone, so a crash a full test run *after* the real verdict looked
identical to a failing suite.

Fixed by reading the printed verdict line first (`^OK\b` / `^FAILED\b`) and
treating a nonzero exit *after* a printed `OK` as a non-blocking warning —
the log is kept rather than deleted so the distinction is checkable, not just
asserted. This is a workaround for a Django/platform interaction, not a
Parliament bug; nothing in this repo's own test suite is at fault.

## 🟡 2. The ledger stamp was two manual steps on every push

`src.W003` (a stale `**Committed & pushed:**` line or missing `DEPLOYED.md`
row) is mechanically fixable — `scripts/stamp_ledger.py` exists specifically
to fix it — but the hook only ever *reported* it, leaving "run the stamp, then
commit it" as something to remember on every push that touched a changelog.
Annoying enough to be worth automating, and mechanical enough to be safe to:
when `src.W003` is the *only* check blocking the push, the hook now runs the
stamp, commits it (`Stamp release ledger`), and re-checks. Anything else
blocking (`src.W002`, a real system-check `ERROR`) still stops the push with
the original guidance — those need a human, not a script.
