Requested by Mason: fix the off-centre checkbox on My Tasks, make each task say

## 🔴 0 — the Delete button did nothing, and neither did anything else on that page

Reported by Mason. The endpoint was always fine; **the browser never reached
it.**

`committee/education.html` read the CSRF token as

```js
const CSRF = document.cookie.match(/csrftoken=([^;]+)/)?.[1] || '';
```

and `CSRF_COOKIE_HTTPONLY = True` (settings.py:285). **JavaScript can never see
that cookie**, so `CSRF` was permanently `''`, every `fetch()` on the page sent
`X-CSRFToken: ''`, and Django rejected all of them with 403.

That is not one button. It is **Delete Task, the whole completion grid, the
publish toggle, and both page-restriction endpoints** — every interactive
control on the education dashboard, none of which has ever worked from a
browser. Each handler ends in `catch (e) { console.error(...) }`, so the page
did nothing visible and nothing appeared in any log the chapter reads.

### The same read exists in two more templates

- **`admin_v2/csp_violations.html`** — identical shape, empty fallback. The
  Dismiss buttons have never worked either.
- **`preferences.html`** — worked, but by accident: it fell through to a
  rendered `{{ csrf_token }}`. Its comment said the cookie was preferred *"so
  the token stays fresh even if the page is served from bfcache"*. That is a
  **false comment** of the kind CLAUDE.md already records a category for — true
  of a simpler deployment, never revisited when `CSRF_COOKIE_HTTPONLY` went on.

### ⚠️ And `base.html` had already solved it

It renders `<meta name="csrf-token" content="{{ csrf_token }}">` and its
`getCookie()` prefers that tag, carrying the comment *"works even with
CSRF_COOKIE_HTTPONLY=True"*. **The helper existed, was correct, and was
documented — and three templates were written outside it.** Ninth instance of
that shape.

`base.html` itself kept a dead cookie *fallback* on its page-visit beacon; that
is removed too, because **a dead fallback reads as an endorsement** and is
plausibly where the other three were copied from.

The response is the enumeration, not the three fixes:
`src/test_csrf_token_source.py` walks every template and fails on any read of
the token from `document.cookie`. Its own first draft reported the wrong line
number — stripping comments deleted lines and shifted everything after them —
so it now blanks comments in place. Verified against a probe file: it catches a
reintroduction at the right line.

## 🟡 0b — the Add Task modal ran off the screen

Also reported. The form has title, description, type, phase, points, display
order, scored-out-of, required, three activation modes and a pledge picker; the
panel was `items-center` with no max height, so on a laptop viewport the submit
button sat below the fold with **no way to scroll to it** — the form could be
filled in and not submitted.

Now `items-start` + `py-8` on the backdrop with `overflow-y-auto`, and
`max-h-[85vh] overflow-y-auto` on the panel. `items-start` rather than
`items-center` is deliberate: a centred panel taller than the viewport clips
equally at *both* ends, hiding the title as well as the button.

Applied to **all three modals on the page**, not just the one reported — the
restriction modal and the new meeting modal had the same shell.

## 🟡 0c — the homework picker on the meeting form

Also reported as confusing, and it was worse than confusing. It was a
`<select multiple>`:

- picking a second task needs **ctrl/cmd-click**, which nothing on screen says;
- a **plain click deselects everything else**, silently.

So the most likely outcome of using it was assigning one task when you meant
three, with no feedback that it had happened. Nothing about that is a
presentation problem — it is a control whose default gesture destroys the input.

Now a checkbox list. Each row says what the task **is**, not just its title —
type, due date (or *no due date*), required, scored out of N — because ticking a
bare title does not tell a chair whether he is assigning a quiz or something
already overdue.

**The empty state is the other half.** With no tasks created the old control
rendered an empty box and no explanation, and the reason is not guessable:
homework *links to tasks that already exist*. It now says so and points at
**+ Add Task**.

The label and helper text say what the link does and does not do — *"this just
links them to the meeting, it does not create or change anything"* — because
"Homework" next to a list of tasks reads equally well as "create these" or
"these are due now".

⚠️ **Checkboxes post the same repeated `homework` field**, so
`request.POST.getlist('homework')` is untouched. That equivalence is pinned by a
test, because a UI change that quietly breaks the wire format looks completely
fine and assigns nothing.

## 🔴 1 — the quiz grading page has never rendered

`templates/committee/quiz_submissions.html` referenced
`committee.committee_code` in four `{% url %}` tags. **`Committee` has no such
attribute** — it is `code`. A missing template variable resolves to the empty
string, so every one of those became `{% url 'education_home' '' %}` and raised
`NoReverseMatch`.

So `/committee/EDUCATION/education/tasks/<pk>/submissions/` — the page a chair
opens to read and grade quiz answers — has been a **500 since it was written**.

### And it explains finding 2

The same page posts a `set_status` hidden field that the view ignored (below).
Nobody noticed, because **the page whose buttons were broken could not be
opened.** One bug hid the other.

⚠️ **v3.16.3's `TemplateUrlNameTests` was one level too shallow.** It scans
templates for `{% url %}` *names* that do not resolve — and this name was real;
the **argument** was wrong. Rather than deepen that scanner into an argument
checker (which would have to know each view's signature), the fix is four tests
that **render the page**. A scanner approximates; a request does not.

## 🟠 2 — both grading buttons did the same thing, and the wrong one

`education_toggle_completion` cycled `pending → completed → incomplete →
pending` and never read `set_status`. The grading page posts *Mark Passed* and
*Mark Incomplete* as that field, so from `pending` **both buttons marked the
pledge passed.**

The failure mode is the bad direction: a chair grading a failed quiz clicks
*Mark Incomplete* and passes him.

Now: `set_status` is honoured when present and validated against
`STATUS_CHOICES`; absent, the cycle behaviour is unchanged, because the
dashboard grid depends on one-click cycling and that page works.
`test_the_control_no_set_status_still_cycles` pins that half.

## Scored tasks

`PledgeTask.max_score` (optional) and `PledgeTaskCompletion.score`. A chair
records what a pledge earned; the pledge sees `50/60 (83%)` on My Tasks,
colour-graded, with *Not yet graded* while it is pending.

Three design calls, all Mason's:

- **`max_score` is a new field, not a reuse of `points`.** `points` is
  progress/gamification and is the same for everyone who completes the task; a
  score is per pledge. One column meaning both would have made every existing
  task look scored.
- **Scoring is informational.** It does not decide pass/fail — a chair still
  marks completed/incomplete. A threshold that flips standing means a mistyped
  score silently changes whether a pledge is eligible for initiation.
- **Any task type can be scored**, not just quizzes. A graded reading
  reflection is scored the same way; tying it to `task_type` would mean a new
  branch every time a type is added.

Details worth keeping:

- **`0` is a real score.** `has_score` tests `is not None`, because a
  `if self.score` would render a pledge who got none of them right as *not yet
  marked*.
- **An absent `score` field leaves the stored score alone; an empty one clears
  it.** The dashboard grid posts a status and no score — if absent meant
  "clear", one click there would silently wipe a mark typed on the grading page.
- **A score above `max_score` is rejected**, not clamped and not allowed as
  extra credit. With scoring informational a wrong number is cheap to correct
  and a silent typo is not; if extra credit is ever wanted, raise the max.
- `_parse_optional_positive_int` is separate from `_parse_non_negative_int`
  because the latter folds blank to `0`, and a task "scored out of 0" is not the
  same thing as an unscored one.

## Education meetings

`EducationMeeting` is a **sidecar on `Event`**, exactly as `RecruitmentEvent`
is: the `Event` owns the calendar entry, so a meeting appears on the chapter
calendar, in the iCal feed and in reminders for free, and the sidecar owns the
education specifics — type, homework, attendance points, chair notes.

- **Visible to the whole chapter** (`visible_to=None`). Brothers should be able
  to see when the pledge class meets; only *attendance* is pledge-only.
- **Homework links to real `PledgeTask` rows**, so it lands in My Tasks with its
  own due date, required flag and score — rather than as prose a pledge has to
  remember.
- **Points for attending**, earned by `present` and `late`. Excused earns
  nothing and costs nothing.
- My Tasks now shows a points summary split into **tasks** and **attendance**,
  because one combined number leaves a pledge unable to tell which half he is
  behind on.

### ⚠️ Why attendance is its own table

The obvious implementation was a third `attendance_type` on the chapter-wide
`Attendance` model. It was rejected, and the reason is this project's own
history: `Attendance` has **49 call sites** and unique constraints keyed on
`attendance_type='event'`, and several queries select on `event=` alone. Putting
education rows there makes "pledges only" a property held up by every one of
those call sites remembering — and CLAUDE.md records **seven consecutive
releases** of a rule stated correctly with one call site left outside it.

`EducationMeetingAttendance` makes it true by construction. The test asserts the
structural property — take attendance through the real view, then assert
`Attendance.objects.count() == 0` — rather than checking the two views that
exist today.

The roster is also the authorization: a POST naming a brother's pk is ignored,
because only pks in the pledge roster are accepted.

## 🟡 3 — `Committee.is_chair()` N+1 (reported from prod dev mode)

*4× the same query shape*, `SELECT … src_parliamentuser INNER JOIN
src_committee_chairs … LIMIT 1`. `view/committee/recruitment.py` alone calls
`is_chair` four times while building one view's context.

Memoised per request. **The memo lives on the user, not on the committee** —
`request.user` is built fresh per request by the auth middleware, whereas a
`Committee` instance can be cached, and a stale memo inside a cached committee
would be a *permissions* bug. Keyed by committee pk so one user object answers
for many committees, which is what the committee index does.
`test_the_memo_does_not_live_on_the_committee` pins that.

## The My Tasks page

- **The off-centre checkbox.** It was an emoji at `text-2xl` beside 16px text.
  An emoji glyph carries its own baseline and line-height, so no margin nudge
  lines it up reliably across platforms — it is now an inline SVG in a fixed
  20px box, one icon per status.
- **Each row now says what the task entails.** Previously a title, a type chip
  and a status icon left "so what do I actually have to do?" unanswered — a
  pledge could not tell a quiz he must sit from a milestone a chair ticks off on
  his behalf. Each row now states who acts and what happens next, per type and
  per status.

## Audit of the surrounding education code

Asked for after the feature landed. Three more findings, **two of them
introduced by the scoring change itself** — which is the pattern this project
keeps recording: a fix is verified where it was made, not where its results are
consumed.

### 🟡 4 — scoring added an N+1 to both pages it was built for

`has_score`, `score_display` and `score_percent` all read
`self.task.max_score`, and neither page joined the task. Measured on a
12-pledge / 10-task fixture:

```
quiz_submissions   44 queries → 32     (13 × src_pledgetask → 1)
my_pledge_tasks    41 queries → 30     (11 × src_pledgetask → 1)
```

Fixed with `select_related('task')` on both completion querysets. The tests
assert the **property** — adding graded rows must not add queries — rather than
an absolute ceiling, which would be a second place to maintain the numbers in
`test_query_budgets.py`. Verified by removing the joins again: 6 more pledges
cost exactly 6 more queries, 8 more tasks exactly 8.

### 🟡 5 — a chair adding a question silently un-graded everyone

`already_submitted` means *"has answered every question"*, so adding a question
to a quiz makes it false again for pledges who already sat it, and their next
submission runs `update_or_create(defaults={'status': 'pending'})`.

Before scoring that was defensible — new answers, so read them again. **With
scoring it left the old mark attached to the new answers**: a pledge's page
would read *50/60* beside answers no chair had seen, and the grading page would
show a score for a submission that did not exist when it was given.

The mark is now cleared with the status. **A stale grade is worse than no
grade** — and the control test pins that the score survives everything short of
an actual resubmission.

### 🟡 6 — "N pledges marked" counted rows, not marks

The attendance form pre-selects `pending` for every unmarked pledge, so a chair
who opens it and hits Save writes a row for the **whole roster**.
`Count('attendance_records')` then reported *"12 pledges marked"* for a meeting
where nobody had been marked — and that number is precisely what a chair uses to
decide whether attendance still needs taking.

Now counted with `filter=~Q(attendance_records__status='pending')`. Absent and
excused still count: **marked means a chair decided, not that the pledge turned
up.**

### Looked at and left alone

- **No edit for a meeting** — a chair who mistypes the time must delete and
  recreate, which destroys attendance. Worth building; it is a feature, not a
  fix, so it is not riding along with this batch.
- **Creating a meeting is officer-or-chair, deleting is chair-only.** The
  asymmetry is deliberate (destructive vs not) but it is a judgement call, and
  task deletion is officer-or-chair — worth a decision rather than a drift.
- `education_home`'s grid is O(tasks × pledges) in Python with no pagination.
  At chapter scale that is nothing; noted so nobody rediscovers it as a bug.
