## 🟢 Mobile app: cached profile photos, update notice (Mason, 10-29-26)

- **Photos.**
  - `src/mobile/views_directory.photo_path` — every photo path the app gets
    now ends in `?v=<hash of the stored file name>`, and `me/` carries the
    member's own. The app keeps photos on the phone and downloads one again
    only when its path changes.
  - The photo view sends `immutable` caching for a versioned path. It
    ignores the query.
- **Profile uploads get a fresh file name** (`profile_view`: 16 random hex
  characters plus the original extension). The old file is deleted first, so
  a phone uploading "image.jpg" every time would otherwise reuse the name, and
  the app would never notice the new picture. The activity log still records
  the name as uploaded.
- **"Update available" in the app.**
  - `me/` → `app_update` `{latest_build, min_build, url}` for the device's
    platform, from six new Site Settings (Admin v2 → Site Settings,
    `APP_UPDATE_DEFAULTS`; seeded with the dashboard defaults):
    `mobile_{ios,android}_{latest_build,min_build,update_url}`.
  - All default to 0 / blank, so no notice until set. After a build reaches
    testers, set *latest build* to its build number (TestFlight shows it).
  - Raise *minimum build* only to force an update.
- Tests: `test_tokens_and_me.MeTests.test_app_update_comes_from_site_settings`,
