## 🟠 Four education-dashboard symptoms, investigated separately

All four were on `templates/committee/education.html` /
`src/view/committee/education.py` — the same dashboard whose "Add Meeting"
button was fixed for a CSP/onclick bug earlier the same day (v3.31.1). None
of these four were a recurrence of that bug: `education.html` has zero
`onclick=`/`onchange=`/`onsubmit=` attributes left in it. Each had its own
root cause.

### 1. "Cannot set due dates"

`PledgeTask.due_date` has existed on the model the whole time, and is even
*displayed* on the dashboard grid (`Due {{ row.task.due_date|date:"M j" }}`)
— but the Add Task modal never had an input for it, and `education_add_task`
never read it from `POST`. There was nowhere to set it, and no edit page to
set it on later either. Fixed by adding a `due_date` field to the shared task
form (see #2) and parsing it in the shared helper both Add and Edit now use.

### 2. "Cannot edit tasks after I make them"

There was no `education_edit_task` view, URL, or template at all — only Add,
Duplicate, Delete, and Publish/Unpublish existed. The only way to correct a
typo, adjust a due date, or change a task's phase/points/scoring was to
delete the task and recreate it, which `on_delete=CASCADE`s
`PledgeTaskCompletion` and destroys every pledge's recorded progress on it.

Fixed by mirroring this codebase's own established pattern for exactly this
shape of problem — the meeting create/edit split
(`_apply_meeting_fields` + `_education_meeting_fields.html` +
`education_edit_meeting` + `education_meeting_form.html`, v3.20.1):

- New `_apply_task_fields(request, task)` in `src/view/committee/education.py`
  — reads the form into `task` without saving, shared by both
  `education_add_task` and the new `education_edit_task`. Two copies of this
  parsing would drift the first time a field was added to one of them.
- New `templates/committee/_education_task_fields.html` — the field markup,
  shared by the Add Task modal and the new edit page, parameterized by an
  optional `task` (edit) the same way the meeting partial is parameterized by
  an optional `meeting`.
- New `education_edit_task` view (GET renders prefilled, POST saves) and new
  `templates/committee/education_task_form.html` (mirrors
  `education_meeting_form.html`, including its own Delete-with-confirmation
  button).
- New **Edit** link on every task row in the Task Completion Grid, gated
  `is_chair` like Duplicate/Delete.
- Editing never touches `completions` — a pledge's recorded status and score
  survive a change to anything else about the task.

**⚠️ One thing worth being deliberate about, because getting it wrong would
have been a quiet regression:** `_apply_task_fields` only forces
`is_published = True` for immediate-mode tasks. It does **not** force it
False for manual/timed mode, because that rule is only correct for a
brand-new task. If it ran unconditionally on edit, fixing a typo on an
already-published manual-mode task would have silently unpublished it again
— hiding it from pledges the moment a chair touched anything else about it.
`education_add_task` (which has no "already published" state to protect)
explicitly closes the other half itself. Covered by
`test_editing_a_published_manual_task_does_not_silently_unpublish_it`.

`education_delete_task` now dispatches on `X-Requested-With` the same way
`education_toggle_completion` already does: the dashboard grid's Delete
button calls it via `Parliament.post()` (fetch) and gets JSON back to remove
the row without a reload; the new Edit page's Delete button posts a plain
HTML form and gets a real redirect back to the dashboard, because there is no
JS on that page to hand a JSON body to.

### 3. "Cannot add questions to the quizzes"

`education_add_quiz_question` and `education_delete_quiz_question` have been
fully implemented and correct since quiz scoring shipped — validated, and (as
of this release) tested end-to-end. **No template anywhere ever called
either one.** A repo-wide grep for both names, `quiz_question`, and
`add_question` across `templates/` returned nothing. The backend was never
the bug; there was simply no page.

Fixed with a new GET-only `education_manage_quiz_questions` view and
`templates/committee/education_quiz_questions.html` — lists a quiz's
existing questions with a chair-only Delete button per row, and an Add
Question form. Both post to the same two pre-existing endpoints via
`Parliament.post()`, the identical fetch-plus-JSON pattern every other
control on the education dashboard already uses (no new write-path code).
Reachable from a new **Questions** link on every quiz-type task row.

### 4. "Cannot change pending → complete → incomplete"

Investigated and found already fixed — this is the same `toggle-completion`
`data-action` wiring the v3.31.1 CSP fix (earlier the same day) repaired
along with every other control on this page. Re-verified here rather than
taken on faith, since nothing in that release specifically named this
symptom: confirmed the rendered grid cell carries the correct
`data-action`/`data-task-pk`/`data-pledge-pk` attributes, confirmed the
delegated click listener's `switch` dispatches to `toggleCompletion(...)`,
and drove the real endpoint through three clicks
(`pending → completed → incomplete → pending`).
