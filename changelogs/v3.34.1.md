## 🔴 Education permissions: granted members got no buttons

Reported by chapter members: people granted access, grading or task-management permissions on the education dashboard weren't getting the options or buttons for them.

**Root cause.** v3.32.0 made education access granular. `_get_education_access` returns `can_view_submissions` / `can_grade_submissions` / `can_manage_tasks`, and every POST view checks the specific key with `_require_education_permission`. That part was correct.

**All 27 `{% if is_chair %}` gates in the education templates were left unchanged.** `is_chair` is True only for `committee.chairs`, so a member with an `EducationMemberPermission` row reached the dashboard (`_education_committee_or_404` let them in) and saw a read-only page.

- **Site admins were affected too.** `_get_education_access` gives them full access but `is_chair=False` unless they're also a chair.
- **The server would have accepted their actions.** Only the UI hid them.

**Fix:**
- `education.html` (13), `_education_meeting_row.html` (1), `education_task_form.html` (3), `education_quiz_questions.html` (5) and `education_meeting_form.html` (3) now gate on `access.can_manage_tasks`.
- `quiz_submissions.html` grading and answer-marking controls (2) now gate on `access.can_grade_submissions`. These match the permission each endpoint enforces.
- `education_edit_task` / `education_manage_quiz_questions` / `education_edit_meeting` now pass `access` into their context. They only passed `is_chair` before.
- `is_chair` stays in the contexts; nothing in the education templates branches on it any more.
- `committee_home.html`'s "Permissions" link still uses `is_chair or user.is_admin`. That's correct: managing permissions is chair/admin-only.

**Guard:** `src/tests/guards/test_education_template_access.py` fails if any education template has `is_chair` inside an `{% if %}` / `{% elif %}`. Negative control: the same regex finds all 27 in `HEAD` (`3ec50ba`).
**Behaviour tests:** `src/tests/education/test_education_permission_ui.py` renders the real pages as a non-chair member.
- A `can_manage_tasks` grant sees Add Task, Add Meeting, Adjust and the task Delete button.
- A view-only grant sees none of them.

## 🟡 Adjust Points history: stored HTML injection (from the 09-24 auto-run)

`renderAdjustmentHistory()` put `entry.reason` (free text a chair types) and `entry.created_by` into `row.innerHTML`. `_script_safe_json` only stops the `</script>` breakout. Once parsed, the value is a plain string again and `innerHTML` interpreted it as markup.

In prod, CSP blocks inline JS, which left markup/overlay injection and `img-src https:` beacons. In DEBUG there's no CSP, so it was script execution.

**Fix:** the row is now built with `createElement` + `textContent`. The v3.34.0 test only covered the script-block layer; the new guard asserts that `renderAdjustmentHistory` assigns no template literal to `innerHTML`.

## 🟡 Out-of-range point adjustments 500'd on PostgreSQL (from the 09-24 auto-run)

`current_delta` / `max_delta` are `SmallIntegerField` (±32767) and `_parse_signed_int` was unbounded. On Postgres an out-of-range value raised `NumericValueOutOfRange`, which is a 500. SQLite doesn't enforce the width, so the suite couldn't see it.

- **New `POINT_ADJUSTMENT_LIMIT = 1000`** in `src/view/committee/education.py`. The view returns the same 400 JSON shape the all-zero case uses.
- **The modal inputs carry matching `min`/`max`.**
- **Tested at the boundary:** ±1001 is rejected with no row written, and 1000 is accepted.

## 🔴 Kai: the ways in ignored member grants, and two doors let admins in

Mason asked that the Kai dashboard be checked for the same bug, **without giving admins access: "it's sensitive data."**

The Kai pages themselves already gate every control on `kai_access.*` flags, so there was no template-wide `is_chair` problem inside the module. **The entry points and two permission helpers were wrong.**

**Grantees couldn't find the dashboard.** Each of these used `Committee.is_chair()` or `is_chair or user.is_admin`, so a member with a `KaiMemberPermission` grant saw none of them:
- the **"Chair Dashboard" link on /kai/** (`kai_user_dashboard.py`), now called "Review Dashboard";
- the **admin-bar nav link** (`ParliamentUser.can_access_kai`);
- the **Kai sections on `committee_home.html` / `detail.html`**.

`Committee.is_chair()` also has the `is_exec_board` shortcut that `_is_kai_chair` exists to avoid.
- **Now:** all of them use `_get_kai_access(...)['can_view_report_list']`, the same predicate the list page enforces.
- **The "Member Perms" link** inside the committee-page section is shown to chairs only, matching its page.

**🔴 Two admin doors into case data:**
- **`manage_kai_permissions` accepted `is_admin`.** This applies to `_require_kai_chair`, which also gates `update_kai_member_permission` and `reset_kai_permissions`. Any site admin could open the page and **grant themselves `can_view_report_details` and both identity flags**. That's the exact edge v3.16.2 closed by unregistering `KaiMemberPermissionAdmin` from /admin/, still open in the app.
- **`_can_appoint_standins` accepted `is_admin`.** `appoint_kai_standin` never consults `_get_kai_access`, so a site admin with no Kai grant could POST a stand-in appointment on any case. A stand-in receives a snapshot of that seat's permissions.
- **Both now require an actual Kai chair** (`_is_kai_chair`): no admin, no exec-board shortcut.
- **Recovery paths are unchanged:** assign a chair on the committee, or use `manage.py kai_break_glass` (time-boxed and audited) for case access.
- **Also:** `update_kai_member_permission`'s "chairs already have full access" refusal now uses `_is_kai_chair`. Before, it refused grants to exec-board members who *don't* have full access.

**Deliberately not changed, #needs-review:** `manage_kai_templates` / create / edit / delete, `kai_form_builder`, `reorder_kai_fields` and the `kai_chair_required` decorator still allow `committee.is_chair(user) or user.is_admin`. These manage **form and template definitions**, not case data, so they don't expose reports. They still carry the exec-board shortcut and the admin allowance. Mason's call whether to narrow them too.

**Tests:** `src/tests/kai/test_kai_permission_entrypoints.py` (11) covers the following.
- A grantee sees the /kai/ link, the committee-page section and `can_access_kai`, but not Member Perms.
- An admin with no grant sees no link, gets redirected from Member Perms, can't grant themselves permissions and can't appoint stand-ins.
- An exec-board flag doesn't make a member a permissions manager.
- The chair still can do all of it.

## 🟡 C&B resolutions: multiple "be it resolved" clauses ran together

Reported by Mason: a second resolved clause rendered on the same line as the first in the Preview PDF. `resolution_print.html` and `resolution_detail.html` put all of `resolved_text` in one `<p>`, so the newline between clauses collapsed to a space. Whereas clauses have always been split per line.

**New `Resolution.resolved_clauses` property** (`src/models/cnb.py`):
- One paragraph per non-blank line, the same rule both templates now use.
- The first line gets "Therefore, be it resolved,".
- Later lines get "Therefore, be it further resolved,", unless the line already opens with its own "Therefore…"/"Be it…resolved"/"Resolved…" wording. Existing resolutions where the second opener was typed by hand render unchanged, with no doubled prefix.
- The form placeholder now says "One clause per line".
- The model's help_text is deliberately untouched, so no migration is needed.

**Tests:** `src/tests/legislation/test_cnb_resolved_clauses.py` (4), including Mason's exact text through the real print page.

## 💡 Working notes on resolutions (sticky notes)

Requested by Mason: *"a way for people who are working on a resolution to make notes for themself off to the side of the resolution without that being added to the resolution ... it says who put what note (or edited a note) like a sticky note ... where there can be multiple ... like Word's comments but not tied to a part of the page."*

**Model:** new `ResolutionNote` model (`src/models/cnb.py`, migration **`0050_resolutionnote`**: new table, additive, safe on a live DB).
- Fields: `body` (max 2000), `color` (yellow/blue/green/purple), `created_by/at`, `edited_by/at`, `is_done` + `done_by/at`.
- **Kept entirely separate from the resolution:** nothing is written to any `Resolution` field, and the print/PDF view never renders notes.

**Who:**
- **The working group only:** CNB permission holders plus anyone listed as a collaborator (viewer *or* editor), via `ResolutionNote.user_can_use_notes`.
- **Everyone else sees nothing.** Resolutions are readable by every member, but the panel isn't rendered for them and every note endpoint returns **404** (not 403), so a member can't tell notes exist.
- **Within the group, everyone sees every note.** Anyone can add, edit (records "Edited by X · time") or mark done/reopen (records who).
- **Delete** is limited to the note's author or a CNB holder, so one collaborator can't quietly remove another's note. Marking done is the normal way to clear one.

**Where:**
- **`templates/cnb/_resolution_notes.html`**, included at the top of the resolution page's sidebar and below the form on the Edit page.
- **Plain form POSTs with a `next` redirect, no JS.** CSP isn't involved, and it works the same on both pages. Edit and delete live in a `<details>` drawer so a stray click can't delete.
- **`next` is checked with `url_has_allowed_host_and_scheme`**; an off-site value falls back to the resolution page.
- **Every Tailwind class in the partial was checked against the compiled `static/css/tailwind.css`.** Pink/sky/emerald weren't built, hence purple/blue/green, and **no CSS rebuild is needed**.

**Admin:** `ResolutionNoteAdmin` is registered with read-only attribution fields and added to `admin_sections.py` under C&B.

**Tests:** `src/tests/legislation/test_cnb_resolution_notes.py` (13) covers:
- CNB/editor/viewer can add, and an outsider gets a 404 and no panel;
- collaborators see all notes with authors;
- edit and done attribution, and an unchanged save isn't recorded as an edit;
- delete limited to author or CNB;
- a cross-resolution note id returns 404;
- notes are absent from the resolution text and the print view;
- empty, too-long and bad-colour input;
- an off-site `next` is ignored;
- the panel appears on the Edit page.
