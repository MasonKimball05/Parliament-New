# v3.16.2 — Admin confidentiality pass (Kai removed, anonymity enforced)

Mason-directed 07-25-26. The v3.16.0 full-coverage pass registered every model
in the Django admin; this release walks that back for the data that shouldn't
be admin-visible at all. Principle applied: **where the app makes a
confidentiality or anonymity promise, the admin must not be the way around
it** — being a Django admin/superuser is an operational role, not a grant of
judicial, deliberative, or ballot-level access.

No migration, no static changes — code-only + restart.

## 1. Kai (judicial/disciplinary) fully unregistered

All seven Kai models are now absent from `/admin/`:

- **Removed from `src/admin.py`:** `KaiReportAdmin`, `KaiReportTemplateAdmin`
  (and the `KaiReport`/`KaiReportTemplate` imports).
- **Removed from `src/admin_extra.py`:** `KaiFormField`, `KaiReportActivity`,
  `KaiReportFieldResponse`, `KaiClosureRequest`, `KaiMemberPermission`
  registrations (and their imports).
- **Removed from `src/admin_sections.py`:** the `'Kai Committee'` section.

Rationale: Kai case data (allegations, accused/submitter identities,
deliberation outcomes, committee notes) is confidential and access is
governed by per-user `KaiMemberPermission` grants in the app —
`can_view_report_details`, `can_view_submitter_identity`,
`can_view_accused_identity`. The admin bypassed that model entirely: any
admin could read every report, and `KaiMemberPermissionAdmin` was *editable*,
so an admin could grant themselves identity visibility, mutate the grant
flow, and leave only an `AdminActionLog` trace. Kai is now managed
exclusively through the in-app module.

Explanatory comments left at all three removal sites so the registrations
aren't "restored" later as an oversight.

## 2. Vote anonymity enforced at the admin layer

`Legislation.anonymous_vote` / `CommitteeLegislation.anonymous_vote` were an
app-layer promise only — both vote admins showed voter identity alongside
choice regardless of the flag (the previous docstrings said as much).

- **`VoteAdmin`** (admin.py): now excludes `legislation__anonymous_vote=True`
  rows via `get_queryset()`, and is **read-only** (`has_add`/`change`/`delete`
  = False) to match the ballot-integrity rule `CommitteeVoteAdmin` already
  had. `cast_at` added to `list_display`.
- **`CommitteeVoteAdmin`** (admin_extra.py): same `get_queryset()` exclusion.

Non-anonymous votes are unchanged — the app already publishes those per
member. Anonymous-vote tallies/turnout remain available in the app.

## 3. Slating confidentiality + de-anonymization vector

- **`SlatingVoteAdmin`** — `voted_at` removed from `list_display` and
  excluded. `SlatingVote` deliberately carries no voter FK, but
  `SlatingBallot` records per-voter timestamps for the same period; with both
  visible, second-level timestamps allow a correlation join that
  re-identifies ballots in a chapter-sized electorate. *Residual caveat
  documented in the docstring: sequential PKs still leak coarse ordering —
  never add `voted_at` or id-adjacent ballot data back to this view.*
- **`SlatingInterviewAdmin`** — `notes`, `strengths`, `concerns` excluded.
  The model itself labels `notes` "CONFIDENTIAL interview notes"; these are
  slating-committee-only and are subject to the notes-destruction feature, so
  admin exposure both breaks the confidentiality promise and undermines
  destruction. Scheduling/outcome metadata (`scheduled_at`, `completed_at`,
  `recommendation`, `notes_destroyed`) stays visible.
- **`SlatingApplicationResponseAdmin`** — answer values (`text_value`,
  `number_value`, `json_value`, `file_value`) excluded; the view is now
  metadata-only. `SlatingFormField.is_confidential` was enforced only in the
  app, so this view previously showed confidential answers to every admin.

`SlatingBallot` (participation record: who voted, not what for) and
`SlatingActivity` (audit trail) are unchanged — both are legitimate
officer-visible records and neither exposes choices.

## 4. Anonymous poll responses

`AnnouncementPoll.is_anonymous` promises "only aggregate counts are shown",
but `AnnouncementPollAnswerAdmin` joined answer content to a `response` FK
that resolves to the respondent's name.

- **`AnnouncementPollAnswerAdmin`** — now excludes
  `response__poll__is_anonymous=True` rows.
- **`AnnouncementPollResponseAdmin`** — left as-is (participation record
  only, same shape as `SlatingBallot`); docstring updated to explain *why*
  it's safe now that answer content is gated.

## 5. 🔴 `export_as_csv` ignored `exclude` — field redactions were bypassable

Found while verifying the above. The shared `export_as_csv` action built its
column list from `queryset.model._meta.fields`, i.e. **every** field on the
model, ignoring the ModelAdmin's `exclude`. Any redaction that relied on
`exclude` was one "Export selected as CSV" click away from being undone.

This was not only a new-code problem — it silently defeated the **secret
exclusions shipped in v3.16.0**:

| Admin | Excluded from detail view | Was exportable via CSV |
|---|---|---|
| `APITokenAdmin` | `key` | ✅ yes |
| `EmailVerificationTokenAdmin` | `token` | ✅ yes |
| `PushSubscriptionAdmin` | `p256dh`, `auth` | ✅ yes |
| `WebAuthnCredentialAdmin` | `credential_id`, `public_key` | ✅ yes |

`export_as_csv` now filters the field list through
`getattr(modeladmin, 'exclude', None)`, so every `exclude` in the codebase —
existing and new — is honoured in CSV output. Row-level protection was
already sound: admin actions operate on the changelist queryset, which
`get_queryset()` has already filtered, so the `anonymous_vote` /
`is_anonymous` exclusions above apply to exports too.

## Verification (sandbox)

- `py_compile` clean on `admin.py`, `admin_extra.py`, `admin_sections.py`.
- No dangling `Kai*` references outside explanatory comments; no module
  imports the removed admin classes.
- All 18 field paths referenced by the new `exclude`/`get_queryset` code
  AST-validated against the model definitions in `src/models/` (incl.
  `Legislation.anonymous_vote`, `CommitteeLegislation.anonymous_vote`,
  `AnnouncementPoll.is_anonymous`, the three `SlatingInterview` note fields,
  the four `SlatingApplicationResponse` value fields).
- Full Django suite **not** run (sandbox lacks PyPI/Postgres/Redis) —
  **run the local sqlite suite before deploy**; Django's admin system checks
  will exercise the changed registrations at startup.

# Part 2 — beyond the admin (same release)

The first pass assumed `/admin/` was the only bypass path. It wasn't. Audit of
API serializers, CSV/PDF exports, global search and officer views found four
more, one of them a hard bug.

## 6. 🔴 The entire Kai module was 500-ing (since 06-05-26)

`_get_kai_access(user, committee)` in `src/view/kai_reports.py` carried
`@login_required`, `@require_feature_flag('kai_reports')` and
`@log_function_call` — **orphaned from an earlier view** when the helper was
inserted above it (decorators blame to 2025-12-26; the function to 06-05-26,
commit `5990174`). All three expect a *request* first and dereference
`request.user`; this helper receives a `ParliamentUser`, which has no `.user`
attribute (confirmed: no field, no property, and no `related_name='user'`
anywhere in `src/models/`). Every call therefore raised
`AttributeError: 'ParliamentUser' object has no attribute 'user'`.

All **five** call sites pass `request.user`, so every Kai review view — list,
detail, CSV export, closure flows — raised a 500. Verified by reproducing
Django's `user_passes_test` semantics against a stand-in object.

Fix: the three decorators are removed (they're also redundant — all five call
sites are views that already apply `@login_required` +
`@require_feature_flag('kai_reports')`). A codebase-wide AST scan for the same
pattern — request-dependent decorator on a function whose first parameter
isn't `request` — found **zero** other instances.

*Note: this likely went unnoticed because the module is low-traffic and/or the
`kai_reports` flag is off in prod. Worth confirming Kai pages load after deploy.*

## 7. Global search bypassed the Kai permission model

`src/view/global_search.py` gated Kai results on
`request.user.is_admin or user.committees.filter(is_kai_committee=True)` —
i.e. **mere committee membership**. A Kai committee member with
`can_view_report_list`/`can_view_report_details` set False (or no permission
row at all) is denied everything in the module, but could full-text search
report titles *and* `description` — the allegation body — from the search bar.
It also never checked the `kai_reports` feature flag.

Now calls the module's own `_get_kai_access`, requires `can_view_report_list`,
and only searches `description` when `can_view_report_details` is set.

## 8. Kai CSV export leaked descriptions to list-only reviewers

`export_kai_reports_csv` correctly redacts submitter/accused identity per
permission, but gates on `can_view_report_list` while exporting the full
`Description` column unconditionally — same bug class as #7. Description is
now `[Redacted]` unless `can_view_report_details`.

## 9. Anonymous polls were de-anonymizable by joining two surfaces

Neither surface leaked on its own:

- `AnnouncementPollResponseAdmin` showed `respondent` + `submitted_at` per row.
- `_export_poll_csv` correctly omitted the respondent for anonymous polls, but
  emitted `Submitted At` with the rows ordered by `-submitted_at`.

Join on the timestamp and every anonymous poll is fully re-identified. The
admin view also bypassed the app's deliberate *"only reveal respondents once
more than 2 have responded"* threshold — with a single respondent it named them
outright.

Fixes: the admin now excludes `poll__is_anonymous=True` rows entirely
(participation stays available, threshold-protected, on the in-app results
page); the CSV drops the timestamp column **and shuffles row order** for
anonymous polls, since the ordering is itself a join key. Non-anonymous polls
are unchanged.

## 10. 🟢 Clean / no action

- **API (`/api/v1/`)** — no Vote, Kai, Slating or Interview endpoints exist at
  all. `LegislationSerializer` exposes the `anonymous_vote` flag but no
  tallies; `CommitteeSerializer` omits `is_kai_committee`/`is_slating_committee`.
- **Poll results page** — already careful: >2-respondent threshold, partial
  non-respondent disclosure, respondent set ordered by name rather than
  submission time.
- **`CalendarSubscription`** — deliberately left unregistered from the admin
  and now documented as such in `admin_extra.py`. Its `token` is a bearer
  credential (anonymous read of a member's feed). It lives outside
  `src/models/`, so v3.16.0's coverage pass never enumerated it; that
  accidental gap is now an intentional decision.

## 11. Perf (drive-by, same function)

`_export_poll_csv` called `resp.answers.get(question=q)` inside a loop over
questions. The caller prefetches `answers__selected_options`, but `.get()`
bypasses the prefetch cache — one query per response × question. Now indexes
the prefetched rows into a dict (`{a.question_id: a}`). Matches the standing
review rule about `.exists()`/`.get()` on prefetched relations.

## Verification (part 2)

- `py_compile` clean on all four changed files.
- AST scan for orphaned request-decorators across `src/`: 0 remaining.
- 200,000 generated `/calendar/feed/<token>/` paths tested against the live

- Field paths AST-validated against the models.
- Full Django suite still **not** run — `src/test_pledge_permissions.py`

# Part 3 — feature-flag seeding (same release)

## 12. The calendar Subscribe button was hidden by an unseeded flag

Mason reported the calendar subscription feature had "been removed at some
point". It never was — model, view, routes, tests and UI are all intact. The
cause is an asymmetry in how flags are read:

| Access path | Missing row behaves as |
|---|---|
| `FeatureFlag.is_feature_enabled('x')` (Python) | **True** — fails OPEN |
| `{% if feature_flags.x %}` (template) | **falsy** — fails CLOSED |

The template path fails closed because `context_processors.feature_flags`
builds its dict from `FeatureFlag.objects.filter(is_enabled=True)`; a name
with no row is simply absent, and Django resolves the missing key to `''`.

The calendar feature is gated by **two different flag names**:

- the Subscribe **button** → `{% if feature_flags.ical_export %}` (template)
- the feed **endpoints** → `@require_feature_flag('calendar_subscriptions')`

`ical_export` was defined **only in `seed_admin_v2.py`**, never in the
canonical `seed_feature_flags.py`. So on any install seeded by the latter the
endpoints worked (fail open) while the button silently never rendered (fail
closed) — the feature looked deleted. Mason added the row by hand 07-25-26.

Fixes:

- `ical_export` added to `seed_feature_flags.py`; both flags' descriptions now
  document that they are a **pair** and should be toggled together.
- New **`src/test_feature_flag_seeding.py`** — scans `templates/**/*.html` for
  `feature_flags.<name>` and fails if the name has no entry in
  `seed_feature_flags.py`. Includes two self-guard tests so the scan can't
  silently pass if the seeder format or template path changes. Runs standalone
  (no Django): currently 3 flags referenced (`chats`, `global_search`,
  `ical_export`), all seeded, 3/3 green.

## 13. Full flag reconciliation (audit result)

Every flag referenced in code was cross-checked against both seeders:

- **Template-gated:** `chats`, `global_search`, `ical_export` — all now seeded.
  `ical_export` was the only gap. No other invisible features exist.
- **Python-gated:** all 9 real flags are seeded. `voting_system` appears
  unseeded but is a **false positive** — it only occurs in a docstring example
  in `models_feature_flags.py`, not as a live gate.
- **Seeded but referenced nowhere (16):** `abstain_voting`, `activity_logs`,
  `anonymous_voting`, `calendar`, `chapter_documents`, `chat_channels`,
  `committee_documents`, `committee_system`, `committee_voting`, `dark_mode`,
  `document_versioning`, `event_attendance`, `email_notifications`,
  `excuse_system`, `legislation_voting`, `login_as_user`. These render as
  toggles in the admin but gate nothing. **Not changed in this release** —
  flagged for Mason's decision, since several have security-sounding names
  (`anonymous_voting`, `login_as_user`) that a future officer could reasonably
  believe are enforcing something.
