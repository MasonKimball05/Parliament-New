# v3.16.2 — Admin confidentiality pass (Kai removed, anonymity enforced)

Mason-directed 07-25-26. The v3.16.0 full-coverage pass registered every model
in the Django admin; this release walks that back for the data that shouldn't
be admin-visible at all. Principle applied: **where the app makes a
confidentiality or anonymity promise, the admin must not be the way around
it** — being a Django admin/superuser is an operational role, not a grant of
judicial, deliberative, or ballot-level access.

No migration, no static changes — code-only + restart.

## 1. Kai (judicial/disciplinary) fully unregistered

All seven Kai models are now absent from `/admin/`:

- **Removed from `src/admin.py`:** `KaiReportAdmin`, `KaiReportTemplateAdmin`
  (and the `KaiReport`/`KaiReportTemplate` imports).
- **Removed from `src/admin_extra.py`:** `KaiFormField`, `KaiReportActivity`,
  `KaiReportFieldResponse`, `KaiClosureRequest`, `KaiMemberPermission`
  registrations (and their imports).
- **Removed from `src/admin_sections.py`:** the `'Kai Committee'` section.

Rationale: Kai case data (allegations, accused/submitter identities,
deliberation outcomes, committee notes) is confidential and access is
governed by per-user `KaiMemberPermission` grants in the app —
`can_view_report_details`, `can_view_submitter_identity`,
`can_view_accused_identity`. The admin bypassed that model entirely: any
admin could read every report, and `KaiMemberPermissionAdmin` was *editable*,
so an admin could grant themselves identity visibility, mutate the grant
flow, and leave only an `AdminActionLog` trace. Kai is now managed
exclusively through the in-app module.

Explanatory comments left at all three removal sites so the registrations
aren't "restored" later as an oversight.

## 2. Vote anonymity enforced at the admin layer

`Legislation.anonymous_vote` / `CommitteeLegislation.anonymous_vote` were an
app-layer promise only — both vote admins showed voter identity alongside
choice regardless of the flag (the previous docstrings said as much).

- **`VoteAdmin`** (admin.py): now excludes `legislation__anonymous_vote=True`
  rows via `get_queryset()`, and is **read-only** (`has_add`/`change`/`delete`
  = False) to match the ballot-integrity rule `CommitteeVoteAdmin` already
  had. `cast_at` added to `list_display`.
- **`CommitteeVoteAdmin`** (admin_extra.py): same `get_queryset()` exclusion.

Non-anonymous votes are unchanged — the app already publishes those per
member. Anonymous-vote tallies/turnout remain available in the app.

## 3. Slating confidentiality + de-anonymization vector

- **`SlatingVoteAdmin`** — `voted_at` removed from `list_display` and
  excluded. `SlatingVote` deliberately carries no voter FK, but
  `SlatingBallot` records per-voter timestamps for the same period; with both
  visible, second-level timestamps allow a correlation join that
  re-identifies ballots in a chapter-sized electorate. *Residual caveat
  documented in the docstring: sequential PKs still leak coarse ordering —
  never add `voted_at` or id-adjacent ballot data back to this view.*
- **`SlatingInterviewAdmin`** — `notes`, `strengths`, `concerns` excluded.
  The model itself labels `notes` "CONFIDENTIAL interview notes"; these are
  slating-committee-only and are subject to the notes-destruction feature, so
  admin exposure both breaks the confidentiality promise and undermines
  destruction. Scheduling/outcome metadata (`scheduled_at`, `completed_at`,
  `recommendation`, `notes_destroyed`) stays visible.
- **`SlatingApplicationResponseAdmin`** — answer values (`text_value`,
  `number_value`, `json_value`, `file_value`) excluded; the view is now
  metadata-only. `SlatingFormField.is_confidential` was enforced only in the
  app, so this view previously showed confidential answers to every admin.

`SlatingBallot` (participation record: who voted, not what for) and
`SlatingActivity` (audit trail) are unchanged — both are legitimate
officer-visible records and neither exposes choices.

## 4. Anonymous poll responses

`AnnouncementPoll.is_anonymous` promises "only aggregate counts are shown",
but `AnnouncementPollAnswerAdmin` joined answer content to a `response` FK
that resolves to the respondent's name.

- **`AnnouncementPollAnswerAdmin`** — now excludes
  `response__poll__is_anonymous=True` rows.
- **`AnnouncementPollResponseAdmin`** — left as-is (participation record
  only, same shape as `SlatingBallot`); docstring updated to explain *why*
  it's safe now that answer content is gated.

## 5. 🔴 `export_as_csv` ignored `exclude` — field redactions were bypassable

Found while verifying the above. The shared `export_as_csv` action built its
column list from `queryset.model._meta.fields`, i.e. **every** field on the
model, ignoring the ModelAdmin's `exclude`. Any redaction that relied on
`exclude` was one "Export selected as CSV" click away from being undone.

This was not only a new-code problem — it silently defeated the **secret
exclusions shipped in v3.16.0**:

| Admin | Excluded from detail view | Was exportable via CSV |
|---|---|---|
| `APITokenAdmin` | `key` | ✅ yes |
| `EmailVerificationTokenAdmin` | `token` | ✅ yes |
| `PushSubscriptionAdmin` | `p256dh`, `auth` | ✅ yes |
| `WebAuthnCredentialAdmin` | `credential_id`, `public_key` | ✅ yes |

`export_as_csv` now filters the field list through
`getattr(modeladmin, 'exclude', None)`, so every `exclude` in the codebase —
existing and new — is honoured in CSV output. Row-level protection was
already sound: admin actions operate on the changelist queryset, which
`get_queryset()` has already filtered, so the `anonymous_vote` /
`is_anonymous` exclusions above apply to exports too.

## Verification (sandbox)

- `py_compile` clean on `admin.py`, `admin_extra.py`, `admin_sections.py`.
- No dangling `Kai*` references outside explanatory comments; no module
  imports the removed admin classes.
- All 18 field paths referenced by the new `exclude`/`get_queryset` code
  AST-validated against the model definitions in `src/models/` (incl.
  `Legislation.anonymous_vote`, `CommitteeLegislation.anonymous_vote`,
  `AnnouncementPoll.is_anonymous`, the three `SlatingInterview` note fields,
  the four `SlatingApplicationResponse` value fields).

  **run the local sqlite suite before deploy**; Django's admin system checks
  will exercise the changed registrations at startup.
