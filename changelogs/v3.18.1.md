# v3.18.1 — Redaction is not exclusion

**Date:** 08-01-26
**Type:** 🔴 Confidentiality fixes + CI repair. **Migration `0012` — choices-only `AlterField` plus a partial unique index. No table rewrite.**
**Deployed:** not yet.

The 08-01-26 nightly review of v3.18.0. The recusal machinery it shipped is
sound — 66 tests, a real chokepoint, enforcement computed from the case rather
than from a record. The defects are in the two places the release changed its
*approach* halfway through, and in a surface no enumeration in this codebase
has ever contained.

Findings 1 and 2 were both reproduced with runnable probes before anything was
changed, and every fix below has a test that was verified to **fail against the
pre-fix code**.

---

## 🔴 1. The reviewer list's search box was an oracle over the fields the card redacts

**Files:** `src/view/kai_reports.py`, new `src/test_kai_redaction_surfaces.py`

v3.18.0 changed the list three times and shipped the third version: a case the
viewer is the accused on is **shown as a redacted row** instead of being
excluded. The reasoning is right and stays:

> Hiding the row protects nothing — the accused is notified and it is on their
> own dashboard. What they must not have is the allegation body, the
> submitter's identity, and any power to act.

**The search predicate did not move with the decision.** `_kai_search_q` builds
its `Q` from the viewer's *committee-level* flags, which say this user may read
`description` and `submitted_by__name` — true in general, false for this one
row. So the row was matchable on precisely the three fields the card refuses to
print, and it is trivially identifiable by its `KAI-YYYY-NNN` number and its
"Recused" badge:

| Search term | Own row returned |
|---|---|
| `Distinctive Case Title Alpha` (control) | ✅ yes, body + submitter redacted |
| `zzzz-no-such-term` (control) | ❌ no |
| a word appearing **only in the hidden description** | **✅ yes** |
| the **redacted** reporter's surname | **✅ yes** |

Both controls pass, so this is a clean oracle and not a rendering artefact. It
defeats the promise CLAUDE.md names as *the* Kai guarantee: **the accused never
learns who reported them.**

**Fix.** `_kai_search_q` takes `redacted_case_ids`. Rows in that list are
matchable on title and tags — the two fields the redacted card still renders —
and the permission-gated predicate is `AND NOT IN` those pks. The list view
passes `_recused_case_ids(request.user)`; `export_kai_reports_csv` passes it too
even though it already excludes those rows, because **the helper's guarantee
should not depend on each caller remembering to exclude first** — which is
exactly how this went wrong.

### The rule worth keeping

**When a surface stops EXCLUDING a row and starts REDACTING it, every predicate
that touches that row becomes a disclosure.** Exclusion protects the filters for
free; redaction does not. This is the general form of v3.16.3's "a filter
predicate is a join key", and it is now recorded in
`docs/CONFIDENTIALITY_MATRIX.md`.

## 🟠 2. The activity feed printed both parties' names — in four places

**Files:** `src/view/kai_reports.py`, 4 templates, `docs/CONFIDENTIALITY_MATRIX.md`

Two mechanisms, neither of which looks like a field:

1. **The row's author.** `submit_kai_report` writes the `created` entry with
   `user=request.user` — the submitter. Every renderer printed
   `{{ entry.user.name }}`, so the case page opened with *"Report Created ·
   <the reporter>"* whatever `can_view_submitter_identity` said.
2. **The `details` string.** Three call sites interpolated the accused's name:
   `'Accused person set to: X'`, `'Accused person removed (was: X)'`,
   `'Accused (X) notified of the case'`.

Measured: a reviewer holding `can_view_report_details` and **neither** identity
flag saw both names on the detail page. The header was redacting correctly the
whole time; the feed underneath undid it.

**`can_view_report_details` is not a superset of the identity flags.**
`KaiMemberPermission` models four independent booleans and the grant UI offers
them independently, so a details-only reviewer is a real configuration.

### It was four renderers, not one — and the count keeps being wrong

| # | Renderer | Audience | Note |
|---|---|---|---|
| 1 | `manage_report.html` Activity card | `can_view_report_details` | pre-existing |
| 2 | `partials/case_timeline.html` | `can_view_report_details` | **added by v3.18.0**, in the same commit as the matrix that omits the surface |
| 3 | `print_report.html` | `can_view_report_details` | renders the **entire** log, not the last 20, into a document that leaves the app |
| 4 | `view_reports.html` "Recent Activity" | **`can_view_report_list`** | spans **every case in the chapter** — the widest audience of the four and the one nobody would have looked for |

**Fix.** One `_redact_activity_log(entries, report, kai_access)` resolves
`display_actor` and `display_details` per entry; all four templates read those
and never the raw fields. The three write sites no longer emit names — but
redaction happens at *render*, because rows already in the database still
contain them and a fix that only changed the writers would have left every
existing case leaking. #4 applies it per entry against that entry's own case and
skips cases the viewer is recused from, since cross-case recusal matters here
too. The archived, unrouted `kai/archive/dashboard.html` was converted as well —
it now fails **closed** if anyone revives it.

### 🔴 And found while fixing it: the print view's own header was ungated

`print_report.html` checked `can_view_report_details` at the door and then
printed **"Submitted By"** and **"Directed To"** outright — plus both names for
every linked case. The template had never been passed `kai_access` at all, so
there was nothing to gate on. Every other Kai surface has honoured these flags
since v3.16.2. This one produces a PDF.

## 🟠 3. CI had been red since `eb9f72e`

**Files:** `src/migrations/0012_kai_case_number_unique_and_recusal_reason.py`

`KaiRecusal.REASON_CHOICES` gained `unavailable` after `0011` was generated, so
`makemigrations --check --dry-run` exited 1 — and that is the gate at
`.github/workflows/ci.yml:74` and `Makefile:19`.

Nothing was broken at runtime: `choices` is validation metadata, emits no DDL,
and `get_reason_display()` reads the model rather than the migration. **The cost
is that every other guard's signal was buried under a red run** — and this
codebase has already shipped past a guard that way twice in ten days
(`test_hardcoded_urls` was red at `abe7367`; v3.17.7 shipped anyway, as its own
changelog records). A gate that is red for an unrelated reason is a gate nobody
reads.

## 🟡 4. `_get_kai_access` still had the exec-board bypass v3.18.0 fixed the previews to avoid

**Files:** `src/view/kai_reports.py`

`Committee.is_chair()` returns True for any **member** of an `is_exec_board`
committee. v3.18.0 rewrote both committee-page Kai previews specifically to
escape that, and said so:

> "Should Kai ever be flagged exec-board, every exec member would read
> allegation bodies and both parties' identities without holding a single
> KaiMemberPermission."

**But it rewrote them to call `_get_kai_access`, whose first branch is
`if user.is_admin or committee.is_chair(user)`.** The previews were routed
*through* the hole rather than around it — the stated property was not the
property achieved.

New `_is_kai_chair()` checks `committee.chairs` directly and ignores
`is_exec_board`; `_get_kai_access` and `_can_appoint_standins` both use it. Kai
access is governed **only** by `KaiMemberPermission` grants — a boolean on the
committee row must not be able to confer it. Currently latent (the flag is
False), but appointing a stand-in is the most privileged action in the module
and the last place that shortcut belongs.

## 🟡 5–8. The rest of the review

- **Case numbers.** `next_case_number()` is a read-then-write with no
  uniqueness, so two concurrent submissions could share one — and case numbers
  go into minutes, where a duplicate is worse than a gap. Partial
  `UniqueConstraint` (conditional, because blank is legal for `bulk_create`d
  fixtures) plus an `IntegrityError` retry in `save()`. Also fixed: a
  `save(update_fields=[...])` call computed a number, set it on the instance and
  then didn't write it. Migration `0012` de-duplicates first, so the constraint
  cannot abort a production `migrate` halfway.
- **Stale comments.** `_recused_case_ids`'s docstring said the reviewer list
  excluded party cases and the status-counts comment claimed recused cases were
  excluded from the counts. Neither was true of the shipped code. **A comment
  describing enforcement that does not exist reads as enforcement** — it is how
  finding 1 would survive a code review. Both rewritten to describe which
  callers exclude and which redact, and why they differ.
- **The aging banner** could point "Open oldest" at a case the viewer is
  recused from — a button that could only bounce, above a case number the cards
  are otherwise careful about. Excluded from that lookup only; the counts still
  include it.
- **The list was unbounded** and a bare `except Exception` reported any failure
  in eighty lines of query-building as *"table not yet created"*. Capped at
  `KAI_LIST_LIMIT = 500` with true totals from the existing GROUP BYs and a
  truncation notice; `stale_count` and `assigned_counts` moved from
  `sum(... for r in reports)` to aggregates so they do not freeze at the cap.
  Handler narrowed to `DatabaseError`.

### One bug introduced and caught in the same session

Adding `from datetime import timedelta` at module level surfaced a latent trap:
`view_kai_reports` had **function-local** `from datetime import ...` lines
inside its date-filter branches, and a local import binds the name for the
*whole* function scope — so the module-level `timedelta` used eighty lines
earlier raised `UnboundLocalError`. All the inner imports in that function are
gone. Worth knowing because the code had been correct for as long as nothing
above those branches needed the name.

## Tests

New `src/test_kai_redaction_surfaces.py` — **23 tests**, four classes.

**Verified against the pre-fix code, not just the fixed code.** Each fix was
neutralised at its definition and the suite re-run:

| Neutralised | Tests that fail |
|---|---|
| `redacted_case_ids` ignored in `_kai_search_q` | **2** — both oracle directions; all six controls still pass |
| `_redact_activity_log` made a no-op | **5** — including both print-view tests |
| `_is_kai_chair` reverted to `committee.is_chair` | **2** |

`test_no_template_renders_raw_activity_fields` greps `templates/kai/` and fails
if any template renders `activity.user.name`, `activity.details`,
`entry.user.name` or `entry.details` — the enumeration maintained by a grep
rather than by a person, which is the whole lesson of the surface count being
wrong four releases running.

**Regression runs, all green:** `test_kai_recusal` 66, `test_kai_appeals` 23,
`test_kai_csv_redaction` 11, `test_template_compiles` 5, `test_kai_search_gating`
+ `test_hardcoded_urls` + `test_bounded_querysets` 44, `test_annotation_join_reuse`
+ `test_geo_restriction` + `test_template_counts` + `test_feature_flag_seeding`
+ `test_csp_templates` 36. `test_kai_page_health` renders clean (the sandbox
reaps it one test from the end; no failures). `manage.py check` 0 issues.
`makemigrations --check` **exit 0** — green for the first time since `eb9f72e`.

**`test_template_compiles` earned its keep.** The first draft of these fixes
used multi-line `{# … #}` comments in six templates. Django's hash comment is
single-line only, so all six would have **rendered into the page** — including
the one explaining that the print view used to leak both parties' names. The
guard caught every one; they are `{% comment %}` blocks now. CLAUDE.md records
this exact trap from v3.16.3 and it still caught a fresh author.

## Deploy

**Migration `0012`.** The `AlterField` is choices-only — no DDL. The
`AddConstraint` builds a partial unique index on `kaireport.case_number`;
`_dedupe_case_numbers` runs first and is expected to be a no-op (0011's backfill
numbered per year in submission order and could not collide), but it means the
constraint cannot fail to apply against a database that somehow already holds
one. Reversible.

Otherwise code-only. No new dependencies. No new routes.

**Spot-checks:**

1. **As a Kai reviewer who is also the accused on an open case** — type a word
   from the allegation into the list search box, then the reporter's surname.
   Neither should return your own case. Searching its title still should, and
   other members' cases must still search normally.
2. **As a reviewer with `can_view_report_details` and neither identity flag** —
   open a case: the Activity card and Case Timeline should read "Anonymous" and
   "Redacted", never a name. Then print it and check the header and the whole
   log. Then check the "Recent Activity" panel on the list page.
3. **As a fully-permissioned reviewer** — confirm both names are still visible
   everywhere. This is redaction, not removal; the feed has to stay useful.
4. Confirm the aging banner's "Open oldest" never points at your own case.
5. Case numbers still render `KAI-YYYY-NNN`, and a newly submitted report gets
   the next one.
