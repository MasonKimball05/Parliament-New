# v2.13.0 - Security Patch

**Release Date:** May 6, 2026

**Deployment Status:** Deployed

**Type:** Security Update

---

## Overview

This patch fixes several security vulnerabilities identified during a comprehensive security audit. All changes are backwards-compatible with no user-visible behavior changes under normal use.

---

## Security Fixes

### IP Spoofing — Rate Limiting and Blacklist Bypass (Critical)

**Issue:** All `get_client_ip()` functions read the leftmost value from the `X-Forwarded-For` header, which is fully attacker-controlled. An attacker could send arbitrary `X-Forwarded-For` values to appear as a different IP on every request, bypassing:
- Login rate limiting and lockouts
- IP blacklist enforcement
- Geo-restriction
- Honeypot bans

**Fix:** Changed all IP extraction logic to read the **rightmost** `X-Forwarded-For` entry. nginx appends the real client IP at the rightmost position via `$proxy_add_x_forwarded_for`, so the rightmost value cannot be forged.

**Files changed:** `src/utils/security_utils.py`, `src/logging_utils.py`, `src/middleware/security.py` (4 methods), `src/middleware/lockdown.py`, `src/middleware/maintenance.py`, `src/context_processors.py`, `src/view/login_view.py`, `src/view/honeypot.py`, `src/models.py` (2 locations), `src/view/admin_v2.py`

---

### Honeypot Ban Not Propagating to Middleware (High)

**Issue:** When an IP triggered a honeypot, it was banned via a `honeypot_ban_{ip}` cache key. However, `InputSanitizationMiddleware` checks a separate `ip_blacklisted_{ip}` cache key backed by the `IPBlacklist` database table. A honeypot-banned IP could still reach login, voting, and all other endpoints freely. Additionally, bans were lost on cache flush or server restart.

**Root cause of 100-hit incident:** Combined with the IP spoofing bug above, each request with a different spoofed IP appeared as a new attacker, creating a new ban key each time and bypassing the repeat-hit suppression entirely.

**Fix:** On first honeypot trigger, the IP is now:
1. Written to the `IPBlacklist` database table (persistent, survives restarts)
2. The middleware's `ip_blacklisted_{ip}` cache key is invalidated so the block takes effect on the very next request
3. The existing `honeypot_ban_{ip}` cache key is still set for fast short-circuit on repeat honeypot requests

---

### Stored XSS — Landing Page Rich Text Editor (Critical)

**Issue:** The officer landing page editor accepted raw HTML from the Quill rich-text editor and saved it to the database without sanitization. The template rendered the stored HTML with `|safe`, bypassing Django's escaping. An officer could inject `<script>` tags or event handler attributes that would execute for every public visitor to the landing page.

**Fix:** All three landing page HTML fields (`who_we_are_html`, `what_we_believe_html`, `chapter_history_html`) are now passed through `bleach.clean()` before being saved to the database. Only tags and attributes produced by the Quill Snow editor toolbar are permitted; all others are stripped.

---

### Stored XSS — Vote Result Chart Labels (Critical)

**Issue:** Plurality vote option names (officer-created) were injected directly into a `<script>` block via `{{ vote_breakdown.keys|safe }}` and `{{ vote_breakdown.values|safe }}`. A malicious vote option name like `"], alert(1), ["` could execute JavaScript for any member viewing the vote results page.

**Fix:** Replaced `|safe` injection with Django's `json_script` template tag, which serializes data to a `<script type="application/json">` element with proper escaping. JavaScript reads it back with `JSON.parse(...)`.

---

### Stored XSS — Guide Articles (High)

**Issue:** Guide article content stored in the database was rendered with `{{ article.content|safe }}`, bypassing Django's escaping. Articles are admin-authored, but a compromised admin account could leverage this to inject JavaScript for all authenticated users who view the guide.

**Fix:** Article content is now sanitized with `bleach.clean()` in the view before being passed to the template. The sanitized result is marked safe via `mark_safe()` and passed as `article_content` rather than accessing `article.content` directly in the template.

## No Breaking Changes

All fixes are transparent to normal users. Officer-created landing page content with legitimate HTML (paragraphs, headings, images, links, lists) is preserved exactly as before. Only executable content (`<script>`, event handlers, `javascript:` URLs) is stripped.

## Quality of Life

### Session Fingerprint Validation

**Added:** `SessionTrackingMiddleware` now performs session fingerprint checks (throttled to once per 10 minutes per session). If the browser or OS reported by the User-Agent changes between requests on the same session key — a strong signal of session hijacking — a `WARNING` is written to the server log and a high-severity `ActivityLog` entry is created for admin-v2 visibility. IP changes alone are not flagged since mobile users legitimately roam between networks.

### Open Redirect — Login and Five Other Views (High)

**Issue:** Six views accepted a `next` or `next_url` parameter from GET/POST and passed it directly to `redirect()` without validation. An attacker could craft a link like `/login/?next=https://evil.com` to redirect a victim to a phishing site after a successful login.

**Fix:** All six redirect sites now call `url_has_allowed_host_and_scheme()` (Django's built-in validator) before following the `next` URL. Any URL that points off-site or changes scheme is ignored and the user is sent to the default destination instead.

**Files changed:** `src/view/login_view.py`, `src/view/bug_report.py`, `src/view/committee/push_to_chapter.py`, `src/view/committee/recalculate_vote.py`, `src/view/committee/unpush_from_chapter.py` (2 locations)

## Features

### 2FA Backup Codes

**Added:** Users who enable Two-Factor Authentication now receive 10 one-time backup codes immediately after confirming their TOTP device. Backup codes can be used in place of the 6-digit authenticator code when the user doesn't have their phone.

- **Setup flow**: After TOTP confirmation, user is redirected to a "save your codes" page with copy-to-clipboard and print buttons. Codes are only shown once.
- **Verification**: The verify page accepts both 6-digit TOTP codes and 8-character backup codes (auto-detected by length). Each backup code is consumed on use. A warning is shown when ≤ 2 codes remain.
- **Regeneration**: Users can regenerate backup codes from their profile at any time. A confirmation step warns that existing codes will be invalidated.
- **Profile display**: The profile 2FA section now shows remaining backup code count with colour-coded status (green / amber warning at ≤ 2 / red at 0).
- **Disabling 2FA**: Backup code device is deleted alongside the TOTP device.

`otp_static` is now in `INSTALLED_APPS` — run `manage.py migrate` to create the `otp_static_staticdevice` and `otp_static_statictoken` tables.

**Files changed:** `src/view/two_factor.py`, `src/urls.py`, `Parliament/base_settings.py`, `Parliament/settings_postgres.py`, `src/view/profile_view.py`, `templates/two_factor/verify.html`, `templates/two_factor/backup_codes_reveal.html` *(new)*, `templates/two_factor/regenerate_backup_codes.html` *(new)*, `templates/profile.html`

### Email Deliverability Flagging

**Added:** When an email send fails for a specific user (announcement notifications, etc.), their account is automatically flagged with the error reason. On their next login, a warning message tells them their email address appears undeliverable and prompts them to update it in their profile. The flag is cleared when they save a new email address.

- **Flag storage**: Three new fields on `ParliamentUser` — `email_flagged` (bool), `email_flagged_reason` (text), `email_flagged_at` (datetime). Migration 0153.
- **Flagging**: `notifications.py` calls `_flag_user_email()` on per-user send failure (only flags once — won't overwrite the original error with a later one). Each flagging event is also written to `ActivityLog`.
- **Login warning**: A Django `messages.warning` is added on successful login if the user's email is flagged.
- **Profile indicator**: A red inline alert appears below the email field on the profile page when the email is flagged.
- **Clearing**: `set_email.py` clears all three flag fields when the user saves a new email address.

**Files changed:** `src/models.py`, `src/migrations/0153_*.py` *(new)*, `src/notifications.py`, `src/view/login_view.py`, `src/view/set_email.py`, `templates/profile.html`

## Security Fixes (Continued)

### Cloudflare IP Protection — Shared Exit IP Blacklisting (Critical)

**Issue:** When the site is behind Cloudflare, the rightmost `X-Forwarded-For` entry is Cloudflare's shared exit IP, not the visitor's IP. Attack counts from all users sharing a Cloudflare exit IP accumulated against that single IP, triggering the automatic blacklist threshold. This caused legitimate users to receive 403 errors and prevented login — as happened when `104.23.187.155` (a Cloudflare exit IP) was auto-blacklisted, blocking backup code regeneration.

**Fix:** Added a `BEHIND_CLOUDFLARE` setting (env var). When enabled, IP extraction reads the `CF-Connecting-IP` header, which Cloudflare sets to the real visitor IP and which cannot be forged by the visitor. This is now the canonical IP used for rate limiting, blacklisting, honeypot bans, geo lookups, session tracking, and all logging.

**Files changed:** `src/utils/security_utils.py`, `Parliament/settings_postgres.py`, `src/middleware/security.py`, `src/middleware/lockdown.py`, `src/middleware/session_tracking.py`, `src/view/login_view.py`, `src/view/honeypot.py`, `src/logging_utils.py`

**Environment variable to add:** `BEHIND_CLOUDFLARE=True`

### Quarantine Login Bug — Incorrect Failed Attempt Recording (Medium)

**Issue:** When a quarantined user attempted to log in with correct credentials, `record_failed_attempt()` was called before rejecting them. This incremented the failed login counter and could eventually lock out the IP, even though the credentials were valid.

**Fix:** Removed the `record_failed_attempt()` call from the quarantine branch. A quarantined login is logged as a warning but does not count toward rate limiting.

**Files changed:** `src/view/login_view.py`

**Added:** 10 new honeypot trap endpoints covering common scanner and recon targets:

| Endpoint | Mimics |
|----------|--------|

| `/admin.php`, `/login.php` | Generic PHP admin panels |

Each endpoint returns a convincing fake response and triggers the same IP ban + blacklist + alert escalation logic as existing honeypots.

### 2FA Brute-Force Detection (Medium)

**Added:** Failed OTP verification attempts are now tracked per-user via cache. After 5 failed verifications within 15 minutes, a `CRITICAL` security log entry is written and a security notification email is sent. The counter resets on a successful verification.

**Files changed:** `src/view/two_factor.py`

### Honeypot — Stale Cache Log Spam Fix (Low)

**Issue:** After the 24-hour honeypot ban cache entry expired, already-blacklisted IPs could create new `HoneypotAccess` log records on every subsequent visit, flooding the honeypot log table.

**Fix:** On cache miss for the ban key, the view now falls back to a DB check against `IPBlacklist` and restores the cache key if the IP is still blacklisted. No new log record is created for already-blocked IPs.

**Files changed:** `src/view/honeypot.py`

---

### Honeypot "Clear All Logs" Navigation Bug (Low)

**Issue:** Clicking "Clear All Logs" on the honeypot page returned a raw `{"success": true, "deleted": 0}` JSON response instead of redirecting back to the page.

**Fix:** Replaced `JsonResponse` return with Django `messages` framework + `redirect('admin_v2_honeypot_logs')`.

**Files changed:** `src/view/admin_v2.py`

---

### CSP Violation Spam — Cloudflare Beacon (Low)

**Issue:** Cloudflare's `beacon.min.js` was blocked by `script-src 'self'`, causing a CSP violation to be logged on every page load when `BEHIND_CLOUDFLARE=True`, flooding the security dashboard with medium-severity alerts.

**Fix:** When `BEHIND_CLOUDFLARE=True`, `https://static.cloudflareinsights.com` is conditionally added to `script-src` and `connect-src` in the CSP header. The `csp_report` endpoint now also downgrades violations originating from Cloudflare's beacon domain to `severity='low'` and logs them at `INFO` level rather than `WARNING`.

**Files changed:** `src/middleware/security.py`, `src/view/csp_report.py`

---

### Console Logging Handler

**Added:** A `LOG_TO_CONSOLE` environment variable (default `False`) enables a `StreamHandler` on all loggers. When set to `True`, all `WARNING`-and-above log messages are echoed to stdout alongside the rotating file log. Useful for Docker/container deployments where stdout is the primary log sink.

**Files changed:** `Parliament/settings_postgres.py`

**Environment variable to add:** `LOG_TO_CONSOLE=True`
