# v3.6.1 — Onboarding Bug Fixes

**Release Date:** June 13, 2026
**Deployment Status:** ✅ Deployed — June 22, 2026
**Type:** Bug Fix

---

## Overview

Fixes discovered during end-to-end testing of the v3.6.0 onboarding wizard. All five issues were caught before any user hit them.

---

## What Changed

### 1. Email step silently false-succeeded

`/set-email/` was intercepted by `ForcePasswordChangeMiddleware` mid-wizard (the user hadn't changed their password yet), causing a 302 redirect to the password change page. The wizard's `fetch()` followed the redirect to an HTML 200 response, `resp.json()` silently failed, and the `data.success !== false` check evaluated true — the wizard reported "email saved" and advanced, but no email was stored.

**Fix:** Added `/set-email/` to `ForcePasswordChangeMiddleware.exempt_paths`. Also added AJAX JSON support to `set_email` (checks `X-Requested-With: XMLHttpRequest`) so the wizard gets a proper `{"success": true}` response. Tightened the wizard's success check to `data.success === true`.

**Changed:** `src/middleware/security.py`, `src/view/set_email.py`, `templates/onboarding/wizard.html`

### 2. Passkey step burned the rate limit on every click

The wizard called `passkey_register_begin` with an empty password, which v3.5.1's re-auth guard always rejects with 403. Each click incremented `passkey_register_attempts_<pk>` — five clicks and the user was locked out of passkey registration everywhere for 15 minutes during their very first session, with no useful UI feedback.

**Fix:** Removed the doomed WebAuthn attempt entirely. The passkey step now shows an informational card directing users to Profile → Security to set up their passkey after completing onboarding.

**Changed:** `templates/onboarding/wizard.html`

### 3. Grandfather check fired mid-wizard after password change

The `onboarding_view` grandfather check (`not has_default_password AND email set → mark complete`) was designed for established users who predate the feature. But after the wizard's password change step, `has_default_password` is cleared and the email was just set — causing the check to fire and skip the passkey and guide steps.

**Fix:** Skip the grandfather check when `in_onboarding` is present in the session (meaning the user is actively mid-wizard).

**Changed:** `src/view/onboarding.py`

### 4. Home checklist included in wrong template

The checklist `{% include %}` was added to `templates/home.html`, but the home view renders `home_modern.html` or `home_classic.html` depending on the user's layout preference. `home.html` is unused.

**Fix:** Include added to both `home_modern.html` and `home_classic.html`.

**Changed:** `templates/home_modern.html`, `templates/home_classic.html`

### 5. Missing `{% endif %}` in checklist component

`onboarding_checklist.html` had a `{% if user.is_authenticated and not dismissed %}` block whose `{% endif %}` was missing. Django's template engine silently produced no output — the div and all its children never rendered.

**Fix:** Added the missing `{% endif %}`.

**Changed:** `templates/components/onboarding_checklist.html`
