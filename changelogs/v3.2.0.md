# v3.2.0 — API Token Security Overhaul

**Release Date:** June 8, 2026

**Deployment Status:** Not yet deployed

**Type:** Security / New Feature

---

## Overview

Complete replacement of the Django REST Framework default token system with a custom-built API token infrastructure designed for audit-readiness, granular access control, and admin oversight.

The prior system issued a single opaque token per user with no scopes, no status tracking, no approval gate, and no access logging. This release replaces it with a purpose-built system that gives admins full visibility and control over every token and every request made with it.

**What's new at a glance:**

- Token request workflow with optional admin approval gate (controlled by feature flag)
- Granular per-token scope system — each token is limited to only the data it needs
- Per-request access logging with non-repudiation (logs survive token/user deletion)
- Full admin dashboard: approve, reject, revoke, edit scopes, view logs per token
- In-place feature flag toggles for `rest_api` (global kill switch) and `api_token_auto_approve`
- Redesigned Developer API section on the preferences page
- New "Setting Up Your First Integration" section in the developer guide

## What Changed

### Token Model & Status Workflow

**New model: `APIToken` (`src/models/api.py`)**

Each token tracks its entire lifecycle — from request to approval to revocation.

| Field | Description |
|-------|-------------|
| `key` | 64-character hex string (`secrets.token_hex(32)`) |
| `name` | Display label the user assigns when requesting |
| `status` | `pending` → `active`, `revoked`, or `rejected` |
| `scopes` | JSONField — list of scope keys the token is authorized for |
| `request_note` | Free-text rationale provided by the user at request time |
| `expires_at` | Optional expiry; enforced at auth time |
| `approved_by` / `approved_at` | FK + timestamp set when an admin approves |
| `revoked_by` / `revoked_at` / `revoke_reason` | Audit trail set on revocation |
| `rejection_reason` | Reason recorded when an admin rejects |
| `last_used_at` | Stamped on every authenticated request |

`APIToken.generate_key()` uses `secrets.token_hex(32)` — cryptographically random, 256-bit entropy.

`APIToken.has_scope(scope)` returns True if the given key is in the token's `scopes` list.

**Defined scopes:**

| Key | Access granted |
|-----|----------------|
| `members:read` | Read member directory and profiles |
| `events:read` | Read events calendar |
| `legislation:read` | Read legislation and vote records |
| `committees:read` | Read committee list |
| `attendance:read` | Read attendance records |

**Status state machine:**

```
pending ──► active
        └─► rejected

active ──► revoked
```

Users can only have one non-revoked, non-rejected token at a time. The creation endpoint enforces this.

### Access Log Model

**New model: `APIAccessLog` (`src/models/api.py`)**

A record is written after every API request — regardless of whether it succeeded.

| Field | Description |
|-------|-------------|
| `token` | FK to `APIToken`, nullable — remains queryable even if token is deleted |
| `user` | FK to `ParliamentUser`, nullable |
| `token_key_prefix` | First 8 characters of the raw token key — identifies the token if it is later deleted |
| `username` | Denormalized username at request time — survives user deletion |
| `timestamp` | When the request arrived |
| `endpoint` | URL path |
| `method` | HTTP method |
| `ip_address` | Client IP (via `get_client_ip`) |
| `response_status` | HTTP status code of the response |
| `scopes_used` | List of scopes evaluated for this request |

The combination of `token_key_prefix` + `username` + `timestamp` makes each log entry independently readable for forensic purposes even after the associated token and user records are gone. This is the non-repudiation guarantee.

**90-day automatic purge:** `cleanup_api_access_logs` Celery task (`src/tasks.py`) deletes `APIAccessLog` rows older than 90 days. Register with `setup_celery_schedules` or add to Beat manually.

### Authentication Backend

**New: `src/api/authentication.py` — `APITokenAuthentication`**

Custom `BaseAuthentication` subclass for Django REST Framework.

- Parses `Authorization: Token <key>` from the request header
- Looks up the token, validates `status == active` and `expires_at` (if set)
- Stamps `last_used_at` via `.update()` — no full-row save, no unnecessary DB writes
- Attaches the token object to `request._api_token` for downstream scope enforcement
- Returns `(user, token)` to DRF as the auth result

If the token is missing, invalid, expired, or in the wrong status, returns `None` (unauthenticated) rather than raising, so DRF's standard `IsAuthenticated` check produces the correct 403.

### Permission Classes

**New: `src/api/permissions.py`**

Two permission classes sit on every viewset:

**`APIEnabled`** — checks the `rest_api` feature flag before processing any request. If the flag is off, returns 403 with `"API not currently enabled."`. This is the global kill switch — flip it off in the admin and every API request is immediately rejected without touching any other code.

**`ScopePermission`** — reads `view.required_scope` (a class attribute set on each viewset), then calls `request._api_token.has_scope(required_scope)`. Returns 403 if the token does not carry the required scope. If `required_scope` is not set on the view, the check is skipped (permissive default for non-scoped internal endpoints).

---

### API Logging Mixin

**Updated: `src/api/views.py` — `APILoggingMixin`**

Overrides `finalize_response()` on any viewset that inherits it. After DRF assembles the response object (including status code), writes an `APIAccessLog` row. All exceptions in the logging path are caught and swallowed — a logging failure will never break an API response.

All 5 viewsets (`MemberViewSet`, `EventViewSet`, `LegislationViewSet`, `CommitteeViewSet`, `AttendanceViewSet`) now inherit `APILoggingMixin` and have:
- `authentication_classes = [APITokenAuthentication]`
- `permission_classes = [IsAuthenticated, APIEnabled, ScopePermission]`
- `pagination_class = None`
- `required_scope = '<scope_key>'`

### User-Facing Token Management

**New views (`src/view/api.py`):**

**`request_api_token` (POST `/api/token/generate/`):**
- Blocks if the user already has a pending or active token
- Validates `name` (required) and `scopes` (at least one valid scope key)
- Creates token as `active` (with `approved_at = now()`) if `api_token_auto_approve` is enabled, otherwise `pending`
- Returns `{status, pending, message}` — no raw key in the response (token key is shown once on the preferences page via a separate DB lookup)

**`revoke_api_token` (POST `/api/token/revoke/`):**
- Requires `token_id` in POST body
- Validates ownership (`user=request.user`)
- Sets `status = revoked`, `revoked_by = request.user`, `revoked_at = now()`, `revoke_reason = 'Revoked by owner'`

**Updated: `templates/preferences.html` — Developer API section**

Completely rebuilt as a first-class preferences section matching the rest of the page (card layout, indigo icon, `text-xl font-semibold` heading).

The section renders a different UI depending on the user's token state:

| State | UI shown |
|-------|----------|
| No token / rejected | Request form — token name field, scope checkbox cards, note field, submit button |
| Pending | Amber banner — "Your request is pending admin approval" |
| Active | Token key card (monospace, copy button) + details/scopes grid + revoke row |

The request form scope checkboxes are styled as selectable cards. The active token key is shown once and can be copied — it is not re-displayed after leaving the page.

### Admin Token Management

All admin views require `request.user.is_admin`. Non-admins receive 403.

**`admin_api_tokens` (GET `/admin-v2/api-tokens/`):**
- Lists all tokens with `select_related('user', 'approved_by', 'revoked_by')`
- Status filter via `?status=` query param (all / pending / active / revoked / rejected)
- Passes `flag_rest_api` and `flag_auto_approve` objects to the template for the settings panel

**`admin_approve_token` (POST `/admin-v2/api-tokens/<id>/approve/`):**
Sets `status = active`, `approved_by = request.user`, `approved_at = now()`.

**`admin_reject_token` (POST `/admin-v2/api-tokens/<id>/reject/`):**
Sets `status = rejected`, `rejection_reason = reason`. Accepts optional `reason` in POST body.

**`admin_revoke_token` (POST `/admin-v2/api-tokens/<id>/revoke/`):**
Sets `status = revoked`, `revoked_by/at/reason`. Accepts optional `reason` in POST body.

**`admin_update_token_scopes` (POST `/admin-v2/api-tokens/<id>/scopes/`):**
Replaces the token's `scopes` list with the submitted `scopes[]` POST values. Only valid scope keys are accepted; invalid keys are silently dropped.

**`admin_api_token_logs` (GET `/admin-v2/api-tokens/<id>/logs/`):**
Shows the last 200 `APIAccessLog` entries for the token, ordered by most recent first.

**`admin_toggle_api_flag` (POST `/admin-v2/api-tokens/flag/<flag_name>/`):**
Toggles `rest_api` or `api_token_auto_approve` feature flags. Returns `{"is_enabled": true/false}` — no page redirect, designed for in-place JS toggle. Only these two flag names are accepted; others return 400.

### Admin v2 API Tokens Page

**New: `templates/admin_v2/api_tokens.html`**

**API Settings panel** (above the status filter):

Two toggle switches for the feature flags. The switches update their pill color (gray ↔ green) and dot position client-side on success without a page reload.

- **REST API Enabled** (`rest_api`) — global kill switch. Turning this off blocks all API requests immediately.
- **Auto-Approve Tokens** (`api_token_auto_approve`) — when on, new token requests are activated immediately; when off, they go to `pending` and require manual approval.

**Status filter tabs:** All / Pending / Active / Revoked / Rejected — links append `?status=<value>` to the current URL.

**Token table columns:** User, Token Name (+ request note), Status (with audit detail on revoked/rejected), Scopes, Created, Last Used, Actions.

**Actions per token:**
- `pending`: Approve (one-click with `confirm()`), Reject (modal with reason field)
- `active`: Revoke (modal with reason field), Edit Scopes (modal with scope checkboxes)
- All statuses: Logs (link to `admin_api_token_logs`)

All modals are zero-dependency vanilla JS. Approve/reject/revoke update the page via `location.reload()` on success. The Edit Scopes modal pre-checks the current scopes from a `data-scopes` attribute on the button.

## Migration

**Migration `0202_apitoken_apiaccesslog`** creates both tables.

A `RunPython` data migration copies all existing DRF `authtoken_token` rows to `APIToken` with:
- `status = active`
- `scopes = all scope keys`
- `approved_at = created` (from the DRF token)
- `name = 'Migrated token'`

If no DRF tokens exist (expected — there should be none in prod), the migration is a no-op.

---

## Breaking Changes

The old DRF `Token` model and `authtoken` app are no longer the auth mechanism for the REST API. If any external client was using a token issued by the old system, it will continue to work because the migration copied those tokens. The `Authorization: Token <key>` header format is unchanged.

## Deployment Notes

```bash
git pull origin main

# 1. Run migrations
python manage.py migrate   # 0202_apitoken_apiaccesslog

# 2. Seed the new feature flag
python manage.py seed_feature_flags   # adds api_token_auto_approve (disabled by default)

# 3. Collect static and purge cache
python manage.py collectstatic --noinput
# Cloudflare dashboard → Caching → Purge Cache

# 4. Restart services
systemctl restart parliament-gunicorn parliament-worker
```

**After deploying:**

1. Go to Admin v2 → API → toggle "REST API Enabled" on
2. Verify with a test request: `curl -H "Authorization: Token <key>" https://am-parliament.org/api/v1/members/`
3. Check the Logs button on the token to confirm the access log recorded the request

**Feature flags after deploy:**

| Flag | Default | Notes |
|------|---------|-------|
| `rest_api` | `False` | **Turn this on manually after confirming deploy worked** |
| `api_token_auto_approve` | `False` | Manual approval flow; turn on if desired |
