# v3.3.0 — Authentication UX, Passkey Nudge & API Token Fixes

**Release Date:** June 11, 2026

**Deployment Status:** ✅ Deployed

**Type:** New Features / Bug Fixes / Security Enhancement

---

## Overview

Several authentication UX improvements, a passkey nudge system to drive passkey adoption, and fixes for a cluster of API token bugs that had accumulated since v3.2.0 deployed.

**What's new at a glance:**

- Sign in with either username or email address
- Passkey bypass on the 2FA verification screen
- Passkey nudge modal on Profile and Preferences pages — non-dismissible, disappears once a passkey is registered
- Passkeys accordion deep-link via `profile#passkeys` or `profile?open=passkeys`
- Set-Email modal now snoozes for 15 minutes when skipped
- API token admin buttons fixed (persistent 400 error resolved)
- API token UX fixes: toggle knob, revoke/withdraw AJAX, request form encoding
- Admin approval no longer silently wipes user-requested expiry

---

## What Changed

### Email/Username Login

Users can now sign in using either their username or their registered email address. The login view resolves an email input to the matching username before calling `authenticate()`, so the underlying auth backend is unchanged. If the email matches multiple users or no users, the input is passed through as-is (graceful fallthrough).

**Changed:**
- `src/view/login_view.py` — Added email-to-username resolution: if the login field contains `@`, looks up the user by `email__iexact` before authenticating. Gracefully falls through on `DoesNotExist` or `MultipleObjectsReturned`.
- `templates/registration/login.html` — Label updated to "Username or Email"; placeholder updated to "Username or email address".

---

### 2FA Passkey Bypass

Users who have a passkey registered can now use it to complete the 2FA verification step when they log in with a password. A "Use a Passkey instead" button appears on the verify screen (only when the user has passkeys), running the full WebAuthn assertion flow and redirecting on success.

**Changed:**
- `src/view/two_factor.py` — Imports `WebAuthnCredential`; queries it in `two_factor_verify` and passes `has_passkeys` to context.
- `templates/two_factor/verify.html` — Added conditional passkey button and full WebAuthn JS block (begin → credentials.get → complete → redirect), matching the login-page passkey flow.

---

### Passkey Nudge Modal

Users without a passkey registered now see a modal popup on the Preferences and Profile pages encouraging them to set one up. The modal has no permanent dismiss — it reappears each visit until a passkey is registered, then disappears automatically.

- On **Preferences**: a persistent non-dismissible banner also appears at the top of the page. The modal's "Set Up Now" link navigates to `profile#passkeys`.
- On **Profile**: the modal's "Set Up Now" button closes the modal and opens + scrolls to the Passkeys accordion inline (no navigation). Modal is suppressed when viewing another user's profile.

The prior `nudge_dismissed` prefs key and `dismiss_passkey_nudge` server endpoint have been removed — dismissal is now purely client-side (close button hides the modal for the current page visit only).

**Changed:**
- `src/view/preferences.py` — `show_passkey_nudge` simplified to `not has_passkeys`; removed `dismiss_passkey_nudge` view and its imports.
- `src/urls.py` — Removed `dismiss_passkey_nudge` URL and import.
- `src/view/profile_view.py` — Added `show_passkey_nudge = (passkey_count == 0) and (user == request.user)`; added to context.
- `templates/preferences.html` — Added non-dismissible indigo banner at top; added passkey nudge modal with "Set Up Now" (navigates to profile#passkeys) and "Maybe Later" (hides modal).
- `templates/profile.html` — Added passkey nudge modal; "Set Up Now" opens the passkeys accordion in-place and scrolls to it.

### Passkeys Accordion Deep-Link

The Passkeys section on the Profile page can now be opened and scrolled to directly via URL: `profile#passkeys` or `profile?open=passkeys`. Used by the Preferences banner link and 2FA screen "Set up a passkey" links.

**Changed:**
- `templates/profile.html` — Added `id="passkeys-accordion"` to the passkeys `<details>` element. Added JS that opens and smooth-scrolls to the accordion when the URL hash or query param matches.

### Set-Email Modal Snooze

The "Set Email" modal in the base layout now respects a 15-minute snooze when the user clicks "Skip for Now". The modal will not reappear until the snooze expires, preventing it from interrupting every page visit during a session.

**Changed:**
- `templates/base.html` — Added `localStorage`-based snooze key (`parliament_email_modal_snoozed_until`). On load, checks if a snooze is active and hides the modal immediately if so. "Skip for Now" button writes a 15-minute expiry timestamp on click.

### API Token Admin Button Fix

Fixed a persistent HTTP 400 error on all admin API token action buttons (Approve, Reject, Revoke, Toggle). Root causes were two independent issues that both had to be resolved together.

**Root cause 1:** `postJSON` in `api_tokens.html` was sending `multipart/form-data` via `FormData`. Daphne had issues parsing empty multipart bodies on some requests, causing 400s. Fixed by converting to `application/x-www-form-urlencoded` via `URLSearchParams`.

**Root cause 2:** `CSRF_TRUSTED_ORIGINS` was empty, so Django fell back to Referer-header CSRF validation. Cloudflare modifies the Referer header on HTTPS requests, causing CSRF checks to fail with 403. Fixed by always including `SITE_URL` in `CSRF_TRUSTED_ORIGINS`.

**Changed:**
- `templates/admin_v2/api_tokens.html` — `postJSON` now converts `FormData` to `URLSearchParams` before sending.
- `Parliament/settings_postgres.py` — Added `CSRF_TRUSTED_ORIGINS` always including `SITE_URL` (defaults to `https://am-parliament.org`).

---

### API Token UX Fixes

Three UX issues on the API token pages, all confirmed after the 400 fix verified buttons were working end-to-end.

**Toggle knob not moving:** `classList.replace()` silently fails if the source class isn't present (returns `false` with no error). Replaced with explicit `remove()` + `add()` calls. Also fixed `dark:bg-gray-600` not being handled — the colon in the class name was breaking `replace()`.

**Revoke/Withdraw navigating to raw JSON:** Both forms were plain HTML `<form>` submissions with only a JS confirm dialog. The server's `JsonResponse` was being rendered as a raw JSON page. Fixed by intercepting `submit`, posting via `fetch`, and reloading on success.

**Token request showing error then pending:** The request form was still using `FormData` multipart. Switched to `URLSearchParams` + explicit `Content-Type: application/x-www-form-urlencoded` + `credentials: 'same-origin'`. Improved the catch-block error message to note the request may have already been submitted before the error surfaced.

**Changed:**
- `templates/admin_v2/api_tokens.html` — Toggle button JS uses `remove`/`add` instead of `replace`.
- `templates/preferences.html` — Revoke and withdraw forms post via `fetch` + reload on success. Token request form switched to URL-encoded.

---

### API Token Expiry Bug Fix & `_parse_expiry` Helper

Admin approval was unconditionally overwriting `token.expires_at` with whatever the admin entered — including `None` when the field was left blank. This silently wiped the user's originally requested expiry.

Fixed so `expires_at` is only updated in `update_fields` when the admin explicitly provides a date. If blank, the existing expiry (or lack thereof) is preserved.

Also extracted the duplicated 13-line expiry parsing block (present identically in both `request_api_token` and `admin_approve_token`) into a shared `_parse_expiry(raw)` helper.

The approve modal now prefills the expiry date input with the token's existing `expires_at` (via `data-token-expires` on the approve button), so admins can see what the member requested and either keep it or change it.

**Changed:**
- `src/view/api.py` — Added `_parse_expiry()` helper; replaced both duplicated expiry blocks. `admin_approve_token` only writes `expires_at` to `update_fields` when a date was provided.
- `templates/admin_v2/api_tokens.html` — Approve button carries `data-token-expires="{{ token.expires_at|date:'Y-m-d' }}"` attribute; modal JS prefills the date input from it.
