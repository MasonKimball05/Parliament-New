## What the CNB "previewer" was actually rendering

Three places in the codebase touch "Times New Roman" for CNB documents,
and they disagreed:

- `templates/cnb/resolution_print.html` (the actual print/PDF page,
  reached via the resolution detail page's "Print / PDF" button) already
  had `font-family: "Times New Roman", Times, serif;` set correctly. This
  one was never the problem.
- `templates/cnb/resolution_detail.html`'s on-screen "Resolution Text"
  preview card — the thing Mason was almost certainly looking at, since
  it's what the print page previews *from* — used Tailwind's `font-serif`
  utility class instead. Tailwind's default `font-serif` stack is
  `ui-serif, Georgia, Cambria, "Times New Roman", Times, serif` —
  **"Times New Roman" is fourth in that list**, behind three fonts
  (`ui-serif`'s OS-mapped serif, Georgia, Cambria) that are installed on
  most systems and so win the match every time. The preview never
  actually rendered Times New Roman; it rendered whichever of those three
  the browser/OS picked first. Confirmed by reading the compiled
  `static/css/tailwind.css` directly (no project-specific `font-serif`
  override exists — this is Tailwind's unmodified default).
- `templates/cnb/viewer.html` (the live Constitution & Bylaws document
  reader, `/constitution-bylaws/?tab=document`) sets no font at all on
  section content — plain sans-serif inherited from the page body. Left
  as-is: it's a different kind of page (a live governance-document
  reader with suspension badges, protected-section tags, etc.), not
  something meant to look like a formal printed document the way a
  resolution or its PDF does, so it wasn't touched.

Fixed the four `font-serif` usages in `resolution_detail.html` (the
whereas-clause block, the resolved-text line, the resolution body, and
the conclusion/certification block) by replacing the Tailwind class with
an explicit `style="font-family: 'Times New Roman', Times, serif;"` —
the exact stack `resolution_print.html` already uses — so the on-screen
preview now actually matches what printing produces.

## The other PDF maker: chapter/committee minutes

The only other real PDF generator in the codebase (grepped for
`getSampleStyleSheet`/`SimpleDocTemplate`/`reportlab.platypus` across all
of `src/` — one hit) is `generate_minutes_pdf_buffer()` in
`src/view/officer/chapter_minutes.py`, shared by chapter minutes and
committee minutes (`committee_minutes_editor.py` imports and calls the
same function) for download, publish-to-documents, and republish-on-edit.

Every one of its 17 `ParagraphStyle` definitions is built with
`parent=styles[...]` from ReportLab's `getSampleStyleSheet()`, and none
of the four base styles actually used as a parent (`'Normal'`, `'Title'`,
`'Heading2'`, `'Heading3'`) had a font override — `getSampleStyleSheet()`
defaults every one of those to a Helvetica variant. So the title, body
text, section headers ("ATTENDANCE", "MINUTES"), motion headers/detail,
attendance names, footer, and every "Indented" nested style built on top
of one of those (which is most of them) rendered in Helvetica, not Times,
regardless of what the CNB documents elsewhere in the app looked like.
Three markdown heading styles (`style_md_h1`/`h2`/`h3`, used for `#`/`##`/
`###` inside a minutes text section) went further and named
`'Helvetica-Bold'`/`'Helvetica-BoldOblique'` explicitly.

Fixed by overriding the four base styles right after
`styles = getSampleStyleSheet()` — `styles['Normal'].fontName =
'Times-Roman'`, `['Title']` and `['Heading2']` to `'Times-Bold'`,
`['Heading3']` to `'Times-BoldItalic'` — so every style inheriting from
one of them (the entire document, including nested "Indented" variants
several levels down) follows automatically, plus the three explicit
markdown-heading overrides changed from Helvetica to the matching Times
variant. `'Code'` (used for fenced code blocks) was deliberately **not**
touched — code should stay monospace regardless of the surrounding font,
same convention as everywhere else in the app.

ReportLab has no real "Times New Roman" — `Times-Roman`/`Times-Bold`/
`Times-Italic`/`Times-BoldItalic` are 4 of the 14 standard PDF base
fonts and the built-in equivalent, the same substitution most PDF
tooling makes when true Times New Roman isn't embedded.

## Verification

New `src/tests/documents/test_minutes_pdf_font.py` (4 tests) — actually
**generates a PDF** from a real `ChapterMinutes` fixture (attendance
table, a motion, a text section with `#`/`##`/`###` markdown headings, an
edit-after-publish notice) and opens the real output bytes with PyMuPDF
to read back which fonts are painted on visible glyphs, rather than just
re-reading the Python source:

- `test_chapter_minutes_pdf_has_no_helvetica` / `_actually_uses_times` —
  the rendered PDF contains Times fonts and no Helvetica.
- `test_committee_minutes_pdf_also_has_no_helvetica` — confirms the fix
  isn't accidentally scoped to only the chapter-minutes code path, since
  committee minutes call the exact same generator function.
- `test_code_block_stays_monospace_not_times` — a fenced code block still
  renders in a Courier font, confirming the deliberate exception wasn't
  swept up in the change.

**A real bug this caught during development, worth recording:** the
first version of the font check used `page.get_fonts()` (PyMuPDF's font
*resource* listing) and failed even after the fix, reporting a phantom
`'Helvetica'` entry. Reproduced directly with a minimal ReportLab
document built entirely from a `Times-Roman` style with zero Helvetica
anywhere in it — `get_fonts()` still lists `'Helvetica'`, because
ReportLab's `Canvas` always declares a Helvetica font resource as part of
its default graphics state whether or not anything is ever drawn with
it. Switched to reading `page.get_text("dict")`'s per-span `font` field
instead, which reports what glyphs were actually painted — that's the
only way to know what the PDF actually looks like, and it's also a
mechanism worth remembering for the next PDF font/rendering bug.

**Negative control**: reverted the four `styles[...].fontName =` lines,
confirmed `test_chapter_minutes_pdf_has_no_helvetica` and
`test_committee_minutes_pdf_also_has_no_helvetica` both failed —
reproducing the exact pre-fix bug, real `Helvetica`/`Helvetica-Bold`/
`Helvetica-Oblique`/`Helvetica-BoldOblique` glyphs on the page — then
restored the file (`diff` against the pre-revert backup showed zero
changes).
