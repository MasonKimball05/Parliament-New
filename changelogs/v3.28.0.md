## 1. Calendar month-boundary bug (reported)

Mason reported an event placed on October 31 wasn't showing on the
calendar, while the 30th worked fine, and suspected it wasn't isolated to
that one date.

**Root cause:** `calendar_view` and `calendar_data_api`
(`src/view/calendar.py`) both built their month query window
(`month_start`/`month_end`) by localizing the naive month boundary as
**UTC**, while grouping events for display by **local** calendar day
(`timezone.localtime(event.date_time).day`). The app's real timezone is
`America/Chicago`, not UTC, and `USE_TZ=True` stores every `date_time` in
UTC. So a late-evening local event on the last day of a month — an 11 PM
Central meeting on Oct 31, say — is stored as ~4-5 AM UTC on Nov 1: outside
October's UTC query window, pulled into November's instead, then grouped
there under local day 31 — a day-of-month November, a 30-day month,
doesn't have a calendar cell for. The event vanished from both months.
**Not October-specific** — this recurs for the last evening of any month
rolling into a shorter or equal-length next month, and would be worse
going into February.

**Fix:** `tz = pytz.timezone('UTC')` → `tz =
pytz.timezone(settings.TIME_ZONE)` in both functions. The query boundary
and the display grouping now agree on what a "day" is, regardless of DST.

## 2. Recruitment event timezone bug (found while investigating #1)

A grep for the same anti-pattern (`pytz.timezone('UTC')`) across `src/`
turned up exactly two more instances, both in
`src/view/committee/recruitment.py`: `create_recruitment_event` and
`edit_recruitment_event` parse the `<input type="datetime-local">` value —
a bare local wall-clock string with no timezone of its own — and were
localizing it as UTC directly. **This is a more severe version of the same
bug, not an edge case**: every recruitment event's stored `date_time` has
been 5-6 hours off from what was actually typed in, for as long as this
view has existed, not just on month boundaries.

**Fix:** `timezone.make_aware(naive)` instead of `pytz.timezone('UTC').
localize(naive)`, matching how every other `date_time` field in the app
already resolves through `settings.TIME_ZONE` via the ModelForm/ORM layer
(e.g. `EventForm` gets this for free).

⚠️ **Not fixed, and not mine to fix: existing prod `RecruitmentEvent` rows
may already be stored 5-6 hours off** from what was actually scheduled,
dating back to whenever this view was first written. No prod DB access
from review to check or correct existing rows, and guessing which rows are
"wrong" versus already hand-corrected is exactly the kind of silent
mass-data mutation this project's history warns against (see CLAUDE.md's
`users.json` purge and the `PledgeQuizAnswer` corrections). **Still open —
worth Mason spot-checking a few recruitment events against what he
actually scheduled.**

## 3. Event reminder emails (new feature, requested mid-session)

Event push reminders can now optionally also send an email, per reminder
slot — `Event.reminder_1_email_enabled` / `reminder_2_email_enabled`, both
default `False`, independent per slot rather than one event-wide toggle,
since the two push slots already run on independent schedules (e.g. 24h-
out vs. 1h-out) and an officer might reasonably want email on one and not
the other.

**Reused a previously-dead field rather than adding a second one.**
`UserPreferences.email_events` already existed — a per-user "email me
about events" checkbox on the Preferences page, saved correctly, but never
read anywhere in the code (confirmed by grep before building; same shape
as the 16-dead-feature-flags finding, one field instead of a flag). It's
now the preference this feature respects.

`EventReminderLog` gains three counters (`users_with_email`,
`users_email_opted_out`, `emails_dispatched`); `EventReminderRecipient`
gains `email_status` (blank means "this slot's email option was off," not
"unknown" or "failed" — a redaction/status distinction worth being
precise about, per this project's own standing rules on what a blank field
is allowed to mean).

`send_event_reminder_pushes` (`src/tasks/notifications.py`) does push
(unchanged behavior) and, per slot, an independent email pass, synchronous
`send_mail()` per recipient (matching `send_recruitment_rsvp_reminders`'s
existing pattern, not `send_mass_mail`, because per-recipient delivery
status needs to be known). **Fails closed sensibly:** a slot with email
enabled but no `DEFAULT_FROM_EMAIL` configured degrades to push-only for
that run (logged once) rather than mislabeling every recipient
`skipped_no_email`; one recipient's send exception is caught and recorded
as `failed` without aborting the rest of the batch.

**Scope decision, flagged rather than silently made either way:**
`ServiceEvent`'s reminders (`service_hours` app) were deliberately **not**
touched — that model already has its own separate, more elaborate email-
reminder system (custom subject/body, its own enabled flag). Adding this
simpler toggle there too would just create a second, competing email
mechanism on the same underlying `Event` row. Still Mason's call whether
that should ever change.

**Found, not fixed:** `generate_recurring_events`
(`src/view/officer/manage_events.py`) did not copy any reminder
configuration (push or email) from a recurring parent event to its
generated instances, so a recurring event's reminders only ever fired
once, off the parent row. Pre-existing, unrelated to this change. **Fixed
separately in v3.28.2** — see that changelog.
