## 1 — `/my-attendance/` has never been linked from anywhere

`templates/my_attendance.html` is 224 lines. The view behind it builds a
personal attendance dashboard: history, a date-range filter, stats, and a
comparison against the chapter average. Its own docstring says
*"Personal attendance dashboard for members."*

**Nothing links to it.** Not the nav, not the home page, not the profile, not
the excuses page. Zero `{% url 'my_attendance' %}` in the entire template tree,
and no `reverse()` or `redirect()` in Python. The only way a member has ever
reached it is by typing the URL.

> **A feature nobody can reach is indistinguishable from a feature that was
> never built** — and it costs more, because it still has to be maintained,
> tested and reasoned about.

This is the third instance of the shape in this codebase's recorded history, and
the first found deliberately:

* the **calendar Subscribe button**, invisible for months because
  `feature_flags.ical_export` was never seeded — the endpoints worked the entire
  time (v3.16.2);
* the **guide buttons** pointing at routes that did not exist, three of them
  live 500s, found by v3.16.3's template URL-name scanner.

Both of those were found by accident.

### Linked in three places, and no new nav preference

* **Home**, both layouts. `home_modern.html` gains a fourth featured card, so
  that grid goes `sm:grid-cols-3` → `sm:grid-cols-2 lg:grid-cols-4`;
  `home_classic.html` gains a card next to Excuses.
* **The My Excuses page header** — the closest thing that page has to a natural
  next click. An excuse is a request about one absence; this is the record the
  requests add up to.

⚠️ **Deliberately NOT a nav item, and the reason is worth keeping.** Every nav
entry is gated on a `show_*_menu` preference, and `UserPreferencesForm.clean()`
caps the member at **9 selected menu items**. A new preference defaulting
`False` would reproduce the exact bug — invisible unless someone goes looking —
and one defaulting `True` would push members who already have nine selected over
the cap, so the preferences form would reject a configuration they never
changed. The nav is a scarce resource by design; the home page is not.

## 2 — The guard, and why it is a ratchet

New `src/test_reachable_pages.py`. For every named route whose view renders a
template, it asserts something links to it.

`test_hardcoded_urls` already catches a link that goes nowhere, and v3.16.3's
`TemplateUrlNameTests` catches a `{% url %}` naming a route that does not exist.
**Nothing checked the opposite direction — a route with no link.** Now something
does.

⚠️ **`KNOWN_ORPHANS` is a ratchet and may only shrink.** It holds four routes
that were already unreachable and whose fate I did not want to decide inside the
change that found them — the same call made for `is_ip_honeypot_banned()` hours
earlier in v3.21.7. `test_the_known_orphan_list_only_shrinks` pins the count, for
the reason v3.20.1's `test_fetch_error_visibility` ratchet exists: **a debt
register that is allowed to grow becomes a place to put things so the build goes
green.**

What is in it, and what I think should happen:

* **`make_event` and `manage_event` (singular) are dead stubs.** Each is
  `return render(request, '<name>.html', {})` with no context, superseded by
  `create_event` and `manage_events` (plural), which is what all six linking
  templates actually point at. They still own `/make-event/`, `/manage-event/`
  and two legacy redirect routes, and `manage_event.html` is 229 lines. **They
  are a landmine rather than a bug:** a future officer finds
  `manage_event.html`, edits it, and nothing changes anywhere in the app.
  Deleting two views, four routes and 238 lines of template is a deliberate diff.
* **`slating_periods`** and **`view_passed_legislation_document`** need a look —
  the second is plausibly reached by a URL built in JavaScript, which this
  scanner cannot see.

⚠️ **NAMED LIMITATION.** The scan reads `{% url %}` in templates and
`reverse()` / `redirect()` in Python. A page reached by a URL assembled in
JavaScript is invisible to it. That direction is already closed from the other
side by `test_hardcoded_urls`, which fails the build on string-built site paths —
the two tests are complements, not duplicates, and the docstring says so rather
than implying coverage it does not have.

Both scans carry an "it found a plausible number of things" guard, because a
broken regex would otherwise report either zero orphans (silent pass) or every
page as orphaned (a catastrophic-looking finding that is really a typo).

## 3 — Documentation: the roadmap was three months and one major version stale

Not shipped in the repo, but done in the same session and recorded here because
it changes what the next person reads.

`AI/Parliament-Roadmap.md` said **"Current Version: 2.28.1"** and listed the iCal
feed, audit-log retention, `set_email` verification, automated DB backups and the
models.py split as pending. **All five had shipped.** The 3.0 roadmap's Pillar 4
said the same.

Rewritten as a verified status table — every BUILT line carries the command that
proved it — plus a genuinely-open list where every entry was greped for on
08-21-26. Both originals are preserved verbatim in `AI/archive/`.

⚠️ **The rewrite got one wrong, and the scanner caught it.** My first draft
listed *bulk member CSV import* as unbuilt, on a loose grep. It exists —
`bulk_import_members`, `officers/members/import/`, JSON batch **and** CSV upload,
with the UI in `user_list.html`. Corrected before the file was saved. **A
roadmap written from memory is how the last one went stale; a roadmap written
from a grep needs the grep checked.**

The general rule, and it is `DEPLOYED.md`'s: **state that only ever lives in
prose goes stale, and prose is persuasive.** A roadmap is exactly that kind of
document, so this one carries dates and verification commands per line.
