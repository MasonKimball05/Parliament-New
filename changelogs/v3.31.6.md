## 🟠 Add Member: separate credentials popup, self-healing ID collision

Reported by Mason: *"When you click add it just adds on the username and
temp password at the bottom and the add becomes a greyed out adding... If
you click adding... it says that a user with this ID exist already, which
makes me think it's trying to create another user with the same id. So you
need to regenerate the id number if you want to make another user."*

### The problems

`/users/`'s Add Member modal (`templates/user_list.html`) showed the new
member's username/temp password in a div (`#add-member-success`) appended
below the form itself, and `submitAddMember()` never re-enabled or reset the
submit button on success — it went from "Adding..." to "Done" and stayed
disabled. The only way out was Cancel/X, which reloaded the whole page. And
the Member ID box is filled by client-side `generatePledgeId()` (for the
Pledge default) — nothing ever cleared or regenerated it after a successful
submission, so the box still held the ID the server had *just* used if an
officer tried to add a second member without reloading first, and
resubmitting it collided with the record that ID now belonged to.

### The fix

- New `#member-created-modal` — a separate popup showing the username and
  temporary password, with **Add Another** and **Done** buttons. The old
  inline `#add-member-success` block is gone entirely.
- New `resetAddMemberForm()` is now the one place that puts the Add Member
  form back into a genuinely clean state (form reset, error hidden, submit
  button re-enabled and re-labeled, roles re-populated, ID regenerated for
  the Pledge default) — called on open, and on a successful submit *before*
  the credentials popup even appears, so there is no "stuck" state and no
  stale ID left sitting in the box for a follow-up submission to collide
  with.
- `submitAddMember()` now also regenerates the ID automatically the moment
  an "ID already exists" error comes back (checking both `result.errors.
  user_id` and the rendered error text), rather than requiring the officer
  to notice and click Generate themselves — the exact manual step Mason
  described having to do.
- **Add Another** closes the popup and reopens Add Member already reset and
  ID-regenerated, so adding several members in a row no longer requires a
  full page reload between each one. **Done** reloads the page so the new
  member shows up in the list, matching the previous close-and-reload
  behavior.

### Tests

New `src/tests/officer/test_add_member_ui.py` (10 tests): the old inline
success block is gone, the new popup and its two buttons render, the
`resetAddMemberForm`/regeneration wiring is present in the rendered script,
no inline event handlers were introduced, and backend-level confirmation
that resubmitting a used ID is an ordinary 400 validation error (not a
crash) while leaving-blank continues to generate a fresh ID every time.

## 💡 Creating a quiz sends the chair straight to its questions

Mason, mid-session, about the v3.31.5 quiz-question-management fix: *"can we
just give them another popup/redirect to make the quiz instead of them
having to go find it in the tasks?"*

`education_add_task` now redirects a newly created **quiz**-type task
straight to its own `education_manage_quiz_questions` page (with `?created=1`,
which shows a one-line "was created, add at least one question" banner)
instead of back to the dashboard — since a quiz with zero questions is not
useful to a pledge yet anyway. Every other task type is unaffected and still
returns to the dashboard.

New tests in `src/tests/education/test_education_task_editing.py`
(`CreatingAQuizRedirectsStraightToItsQuestionsTests`, 4 tests): the redirect
target and its query string, that non-quiz creation is unaffected, and that
the banner shows only on the redirect path and never on a direct visit.

## 🟠 Quiz questions can now be edited, not just added/deleted

Mason, mid-session: *"for quizzes you cannot edit the questions after making
them can we change that."*

New `education_edit_quiz_question` view (POST, mirrors the shape of
`education_add_quiz_question`/`education_delete_quiz_question`) updates a
question's text, model answer, and display order in place. New route
`committee/<code>/education/tasks/<task_pk>/questions/<question_pk>/edit/`.
**Pledge answers already submitted for the question are left untouched** —
correcting a typo is not the same act as retracting the question, and
fixing a comma should not make a pledge's answer to question 3 vanish, which
is what deleting-and-re-adding (the only previous option) would have done.

`templates/committee/education_quiz_questions.html` gained an inline edit
form per question (Edit/Cancel/Save), toggled without a page reload; Save
posts to the new endpoint and reloads to reflect it, mirroring the existing
Add pattern. Cancel restores the pre-edit values via `data-original-*`
attributes on the form rather than leaving whatever was typed sitting there
for the next click.

New `EditQuizQuestionTests` (8 tests) in `test_education_task_editing.py`:
editing updates the row and is reflected on the page, a pledge's existing
answer is untouched by the edit, a blank question is rejected without
saving anything, non-committee members get 404, and the manage page renders
the edit buttons/forms with no inline event handlers.
