# v3.17.2 — Stop reading columns the page doesn't use

Follow-up to v3.17.1. That release removed the N+1s on both legislation pages
but left the underlying problem: **`select_related` and `prefetch_related` fetch
every column by default.** One query instead of six is an improvement; one query
still dragging ~43 `ParliamentUser` columns per author and per co-author is not
the finish line.

Implemented 07-28-26. Code only — no migration, no new dependencies.

---

## 1. Narrowing the member joins

`src/models/users.py`, both legislation views

`MEMBER_DISPLAY_FIELDS` (v3.17.1) now has a complement, **`MEMBER_PROFILE_FIELDS`**
— the heavy columns, for use with `.defer()`. Two constants because the right
tool differs by relation type:

| Relation | Tool | Why |
|---|---|---|
| `prefetch_related('co_authors')` | `Prefetch(..., queryset=ParliamentUser.objects.only(*MEMBER_DISPLAY_FIELDS))` | An explicit `Prefetch` queryset is the **only** way to narrow a prefetch — the plain form always selects everything. |
| `select_related('posted_by')` | `.defer(*(f'posted_by__{f}' for f in MEMBER_PROFILE_FIELDS))` | `.only()` here would force you to enumerate every *Legislation* field the page touches too — long, and broken the moment a template reads one more. Deferring the known-heavy related columns says the same thing without the fragility. |

Applied to `passed_legislation` and `view_legislation_history`. The co-author
prefetch on the passed-legislation page went from 43 columns to 7.

A test asserts the two constants are disjoint and that every name is a real
field — a typo in either would silently narrow nothing.

## 2. Six status COUNTs → one aggregate

`src/view/passed_legislation.py`

The status tabs ran one `COUNT` round trip per tab over the same table. They are
six different predicates, but conditional aggregation evaluates all of them in a
single pass (`Count('pk', filter=Q(...))`). Six queries → one. The `personal` tab
counts a different table, so it stays separate.

**Gotcha worth recording:** an aggregate alias may not share a name with a model
field. `passed=Count(...)` fails with *"Cannot compute Count('passed'): 'passed'
is an aggregate"* because `passed` is also a `BooleanField`. The aliases are
`n_`-prefixed and mapped back.

## 3. `PageToggle.is_page_enabled` is now cached

`src/models_feature_flags.py`

Same treatment `FeatureFlag.is_feature_enabled` got in v3.17.1, for the same
reason: `@require_page_enabled` decorates a large number of views, so this was an
uncached `objects.get` on essentially every page load. Invalidated on
`save()`/`delete()`, which also busts the `context_feature_flags` dict so Python
and templates can't disagree.

## 4. `base.html` was re-fetching preferences it already had

`templates/base.html`

The nav read `user.preferences.show_*_menu` in 25 places. That is a fresh
one-to-one dereference — a query — even though the `user_preferences` context
processor had *already* loaded the same row and cached it for five minutes as
`user_prefs`. All 25 now read `user_prefs`, removing one query from **every
authenticated page on the site**.

Behaviour for anonymous users is unchanged: the context processor supplies
`user_prefs = None`, and a missing attribute resolves to `''` — falsy, exactly as
before.

## 5. Dwell-hover links the page to the queries behind it

`src/templatetags/dev_tags.py`, `templates/dev/panel.html`

Hold the pointer on an annotated value for ~600 ms and the panel opens, switches
to whichever tab has the matches, and highlights every query that touched that
table. The reverse works too: hovering a panel row lights up the page elements
it produced. `Esc` clears; annotated values are focusable, so Tab-and-hold does
the same thing.

The link is **by database table** — `dev_value` now emits `data-pdev-table`, and
every SQL and Shapes row carries `data-pdev-tables`. Both sides are asserted in
tests, because if either stops emitting the attribute the feature silently does
nothing rather than breaking visibly.

A dwell rather than a plain hover: annotated values sit inside ordinary prose,
and firing on every incidental pass would make the page flicker.

When a hovered element matches no query, the hint says so explicitly — *"no
query on this request (cached or prefetched)"* — which is a useful answer in its
own right rather than silence.

## Tests

`src/test_dev_mode.py` → 101 tests. New here:

## Not done — carried to the next session

**Only the two legislation views are narrowed.** The same un-narrowed member join
exists across the app: roughly **90 `select_related`/`prefetch_related` calls
pulling member rows without a matching `.only()`/`.defer()`**, including the home
page. `MEMBER_DISPLAY_FIELDS` / `MEMBER_PROFILE_FIELDS` and the two patterns in
§1 are the template for fixing them; it is mechanical but wants doing a file at a
time with dev mode open to confirm each one.

Also still open: **splitting the profile columns into a `MemberProfile`
one-to-one**, which would make this structural instead of a convention. That is
the real fix and it is a migration touching every profile read — its own release.
