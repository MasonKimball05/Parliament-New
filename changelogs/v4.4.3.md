## The app: check-in and poll QR codes

An officer running a meeting can show an event's check-in QR from their phone
(`src/mobile/views_qr.py`): open a 15-minute window, a live countdown, close it
early or open a new one, how many have checked in so far, and the stable embed
link for slides (share or revoke). A poll's QR works the same way. Same
permissions and feature flags as the website's pages; a finalized event can't
be reopened. The code is drawn on the server as a PNG
(`render_qr_png_data_uri` in `src/utils/qr_svg.py`), so it needs no new app
build. Opening, closing and the embed links go through helpers now shared with
the web views in `src/view/officer/event_attendance.py` and
`announcement_polls.py` (`open_checkin_window`, `close_checkin_window`,
`revoke_checkin_embed`, `revoke_poll_embed`, …). The attendance roster's
response gains `event.qr_checkin` so the app only offers the QR when it's on.

## The app: committee vote results and runoffs

A committee vote's result page is native (`GET committees/<code>/votes/<id>/result/`):
the tallies, the winner or a tie, voter names unless the vote is anonymous,
the parent vote and any runoffs. Chairs and whoever posted the vote can end
it and start a runoff from the app; the committee's ballot list gains its
voting history (the last 20 closed votes). The rules and figures moved out of
the web views into `src/committee_management.py`, which the website's vote,
result, runoff and recalculate views now call.

- **Recalculating:** officers can now recalculate from the app as well as
  chairs, as the website already allowed. An open vote is refused with 409
  instead of 403. The website's recalculate now also writes an activity-log
  entry.

## The app: activity and system logs

Officers and chairs get Activity Logs (filters by date range, category, action,
member and search, 50 to a page) and System Logs (the last 200 lines, newest
first, filtered by level and text on the phone)
(`src/mobile/views_officer_logs.py`). Both use the pages' own code
(`filtered_activity_logs`, `activity_category_counts`, `read_log_entries`), so
the Kai redaction is the same: no reporter name, id or IP reaches a row, and
filtering by member leaves Kai rows out for anyone without full Kai access.

- **System Logs on the website:** if reading the log file fails partway, the
  page now shows the error with no lines, rather than the lines it had read.

## The app: Site admin

Members on the admin-v2 allowlist get a Site admin row in More
(`src/mobile/site_admin.py`, `views_site_admin.py`): the dashboard's numbers
and Celery health, the feature and page switches, maintenance mode and
lockdown; members (search, devices, sign out everywhere, login security,
release a lockout, force a password reset, reset 2FA or require it); lockouts,
security alerts and the audit log; and the app installs page with a test push.

The gate is the website's, per phone:

- **Allowlist.** Every `admin/` endpoint answers 404 to anyone not on
  `ADMIN_V2_USER_IDS`, before anything else is checked; `me/` only says
  `site_admin: true` to those on it.
- **Step-up.** Unlocking takes the member's password and
  `ADMIN_V2_SECRET_KEY`, checked by `admin_v2_step_up`, which the website's
  login now calls too: one attempt counter shared by the website and every
  phone (5 tries, then 15 minutes), the same log rows, the secret compared in
  constant time. No passkey in the app (it would need a native module).
- **Per device, 12 hours.** The unlock is stored on the phone's
  `MobileDevice` row (`admin_unlocked_until`), not the cache, and ends after
  12 hours (the website's lasts 7 days), on Lock, or when the device is signed
  out or revoked.
- **Nothing secret sent.** Setup checks are yes/no; a forced-reset password is
  emailed or typed by the admin, never returned; member activity leaves out
  Kai rows, as the website's member page does.

Every action runs through helpers taken out of the website's admin views, so
it writes the same activity-log rows.

- **Website fix:** the dashboard's in-page page switch now logs its
  `page_toggle` row; it returned before logging.
- **App only:** you can't force-reset your own password from the app (it would
  sign that phone out); the website still allows it.
- **Passkey unlock:** `admin/unlock/passkey/begin/` and `/complete/`, through
  `admin_v2_passkey_options` / `admin_v2_passkey_verify`, which the website's
  passkey step-up now calls too: the same shared attempt counter and log
  rows. The app's challenge is a single-use `MobileAuthTicket` bound to the
  member and the phone, good for 2 minutes; user verification is required.
- **Website fix:** the website's Admin v2 passkey asked for user
  verification (Face ID, a PIN) but never checked the answer; it now refuses
  a passkey that skipped it.
- **Lockdown blocks the app too** unless the phone's address is on the
  lockdown allowed list; the lockdown screen says so and fills in the phone's
  current address.

## The app: dark mode and large text (app only)

A pass over every screen. The status bar is white on the blue header; delete
buttons and the songbook's play icon are readable on the dark palette. With
large text, names and titles get more lines instead of being cut off, rows put
their icons and counts above the title at the accessibility sizes, segmented
controls and date pickers stack, Home's stat tiles stack, and the signed-out
screens scroll.

## The app: creating passkeys

Members can create, rename and remove passkeys in the app
(`src/mobile/views_passkeys.py`, Settings → Account and Profile → Security);
before, a passkey could only be made on the website. The website's code in
`src/view/webauthn.py` is now helpers both call: the same registration options
(existing keys excluded, user verification required), the same password
re-check to add or remove one (and the same 5-per-15-minutes limit), the same
security log lines and "a passkey was added/removed" notice and email.

After a password sign-in on a phone that supports passkeys, a member without
one is offered to create one ("Sign in faster next time"); "Not now" hides it
for 30 days. `me/` gains `has_passkeys`.

- **Removing a passkey from the app** keeps that phone signed in, as a
  password change does; other phones are signed out as before. A phone that
  signed in with a passkey is signed out too, since it can't be told whether
  that was the one removed. The website still signs out every phone.

## The app: header buttons, prompts and more contrast (app only)

- **Header buttons** on iOS 26 sat as white text in a light glass pill, hard to
  read in light mode. They're now the system's own bar buttons (dark on the
  light pill, light on the dark one, like the back button), through one kit
  helper, `headerButtons`; older iOS and Android keep white on blue.
- **Text prompts** (reasons, notes, names, renames: 14 places) were iOS's
  `Alert.prompt`, which doesn't exist on Android, so there they did nothing
  or skipped the text. One themed prompt now serves both, with multi-line
  notes and large text.
- **Dark mode's segmented control** shows the selected option as a raised,
  lighter segment; **names with a pill** put the pill under the name at the
  largest text sizes; **sign-in's** two fields' placeholders match in size.

## Build 19

The native modules this release adds, each skipped on older builds so an
update can't crash them:

- **QR screens** keep the phone awake and at full brightness while a code is
  shown (put back after), and the embed link can be copied.
- **Add to my calendar** on an event, asking for (write-only) calendar access
  only when tapped.
- **No screenshots or screen recording** on Kai case screens and Site admin,
  and they're blurred in the app switcher.
- **A rating request**, at most once every 120 days, after five days of use,
  and only after a vote is cast or a check-in.

Expo SDK 58's packages are brought up to their current patch versions.

## The app: links open the app's screens (app only)

A notification the server tags as a website page now opens the app's own
screen when it has one. Before, only slating, Kai cases and committee pages
were caught; announcements, events, minutes, attendance, members, polls,
recruitment and the rest opened the website. The app also reads about forty
more website addresses as its own screens. Actions, JSON endpoints and the
rich-text editors still open the website.

## The app: Quote Book pages bend (app only)

The turning page was one flat sheet swung on the spine. It's now drawn as
strips along a curve, so it bends as you turn it: the edge you pull leads, it
casts a shadow on the page underneath, and a page you let go of settles on a
spring at the speed of your swipe.

## Still on the website

The QR images pasted into slides and the check-in link the code opens, the
