## How it was measured

Production settings (Postgres 16, Redis, `DEBUG=False`) on a cloud copy:
Daphne serving the real site over a unix socket, the Celery worker and beat
started exactly as the unit files start them. The same workload each time:
every page a signed-in admin and member can open, then 20 members loading 10
common pages at once, three times, then every periodic task once. Memory is
PSS (each process's own memory plus its share of what it shares).

| | Before | After |
|---|---|---|
| Peak memory, app processes + their Postgres connections | **749 MB** | **479 MB** |
| After the load: Daphne | 280 MB | 231 MB |
| After the load: Celery (worker + beat) | 259 MB | 192 MB |
| Postgres connections left open after the load | 62 (146 MB) | 2 (11 MB) |
| 500 errors during the run | 137 | 1 (the attendance bug below) |

Not measured: the server's own processes (Postgres's shared memory, nginx,
the OS, anything else installed). `parliament-ram-check.sh` (in the Claude
folder) reads those from the server without changing anything.

## 🔴 Every request left a Postgres connection open

`CONN_MAX_AGE` was 300. Under Daphne (ASGI), Django runs each request's sync
code in a thread made for that request, and a persistent connection belongs
to the thread that opened it. So every request left one open connection
behind when its thread ended, and nothing ever reused it. One burst of 20
members left 100 idle Postgres backends (~220 MB), and the next requests got
"too many clients". That is the 09-16-26 incident (`src/tasks/db_health.py`
blamed the 5-minute linger; the real cause is one connection per request).

**Fix:** the default is now 0 (close after each request). Not slower: 300
requests to `/home/` and `/vote/` took a median of 42-44 ms either way (two
runs each). Under ASGI the old setting never saved a connection anyway: each
request has a new thread, so it opened a new connection every time and only
left the old ones behind.
`src.W007` warns at `manage.py check` / `preflight` if `.env` still sets
`DB_CONN_MAX_AGE` above 0. **An old RAM guide told the server to set it, so
check `.env`.**

## 🟡 Beat was a second full copy of Django

`parliament-beat.service` ran its own Django (~115 MB) only to put scheduled
tasks on the queue. Beat now runs inside the worker (`celery worker -B`), as
a small process forked from it that shares its memory. Safe because there is
one worker; `Parliament/celery.py` says what to do if that ever changes.
`Conflicts=parliament-beat.service` in the worker unit stops the old service
if it is still installed, so periodic tasks never run twice.

## 🟡 Celery loaded the whole website at startup

- Celery's Django integration runs the system checks when a worker starts.
  The URL check imports every view and the libraries they use (~30 MB) into
  processes that never serve a page. `Parliament/celery.py` sets
  `CELERY_SKIP_CHECKS=1`. The checks still run at `manage.py check`,
  `migrate` and `preflight`.
- `'daphne'` was in `INSTALLED_APPS`, which loaded Twisted and the Daphne
  server (~16 MB) into the worker, beat and every management command. It is
  only needed so `manage.py runserver` serves websockets in development, so
  it is now added only for `runserver`. Production runs the `daphne` program,
  which does not need it.
- The process that runs tasks is replaced after a task leaves it above
  ~160 MB (`--max-memory-per-child`).

## 🟡 Memory freed after a burst stayed with Daphne

glibc gives each thread that allocates its own memory arena (up to 8 per
CPU), and Daphne runs every request in a new thread. Three bursts of 20
members loading 10 pages each grew Daphne from 181 MB to 296 MB, and it
stayed there. With
`MALLOC_ARENA_MAX=2` (both units): 181 MB to 235 MB, same speed. jemalloc was
tried and was no better.

## 🟡 Daphne's limits were wrong for what it does

- `LimitAS=268435456` capped *virtual* memory at 256 MB. Python reserves far
  more address space than it uses. Tested: with the app and PyMuPDF loaded, a
  process under that cap could not start a second thread, and Daphne needs a
  thread per request. If the server's unit really has this line, PDF
  previews can make the site fail until a restart.
- `MemoryLimit=256M` (the old cgroup-v1 name) killed Daphne at a size it
  reaches in normal use (180-240 MB, more once PDF previews and exports load
  their libraries).
- Now `MemoryHigh=320M` (the kernel reclaims from Daphne first above this)
  and `MemoryMax=420M` (hard ceiling, so one runaway request cannot take
  Postgres down). Worker: 300M / 400M.

## Deploy (server steps)

These change systemd units, so they are more than a pull and restart.

```bash
cd /var/www/Parliament-New && git pull origin main

# 1. DB_CONN_MAX_AGE: remove it from .env if it is there (the default is now 0)
grep -n DB_CONN_MAX_AGE .env        # if this prints a line, delete that line

# 2. Install the new unit files and retire beat
sudo cp parliament-gunicorn.service parliament-worker.service /etc/systemd/system/
sudo systemctl disable --now parliament-beat.service
sudo rm /etc/systemd/system/parliament-beat.service
sudo systemctl daemon-reload

# 3. Restart
sudo systemctl restart parliament-worker.service parliament-gunicorn.service

# 4. Check
python manage.py check                 # no src.W007
systemctl status parliament-worker.service --no-pager | head -5
grep -i "beat: Starting" logs/celery-worker.log | tail -1
```

`python manage.py preflight` checks the beat heartbeat a few minutes later.
