## 🟠 Email-change confirmation links didn't work for members with 2FA or passkeys

**Reported:** "the email confirmation to change your Parliament email isn't
working."

**What was wrong.** The confirmation flow works when the link is opened in a
browser that's already signed in and verified. It had no tests at all, so I
pinned that. The link is usually opened **signed out**, though: the email is
read on a phone. `@login_required` sends that to the login page with `?next=`,
and two of the three ways to sign in dropped it:

- **Members with 2FA** (officers and admins must have it; anyone may turn it
  on): the password login redirected to `next` correctly, but
  `Enforce2FAMiddleware` then redirected to the 2FA verify page **without**
  `next`, and verify always sent people home.
- **Passkey sign-in** always returned `{"redirect": "/"}` and ignored `next`.

Either way the member landed on the home page with the email unchanged and no
message. Only a password login by a member without 2FA made it through. The
same bug broke every other deep link opened signed out, e.g. shared event
links.

**Fix:**
- New `src/next_url.py`: `safe_next()` (same-site URLs only) and `with_next()`.
- `Enforce2FAMiddleware` carries the requested page as `?next=` for GET page
  loads.
- The verify view redirects to `next` after a TOTP or backup code (and when
  already verified).
- Passkey sign-in on both the login and verify pages forwards the page's query
  string, and the server returns `next` when it's safe.
- An off-site `next` is ignored.
- **Smaller:** the non-JS profile form no longer shows "No changes were made."
  right after "A confirmation link has been sent".

**Tests:** new `src/tests/security/test_email_change_confirmation.py` (7):
- signed-in click;
- signed-out click with password login;
- signed-out click with 2FA, which failed before (it landed on `/home/`);
- off-site `next` ignored;
- the passkey pages forward the query string;
- the helper functions.

2 fail against the old code. `test_two_factor`'s middleware test now expects
`?next=`.

## 🟢 go-sentinel can tell when Cloudflare needs a purge

**The problem this solves.** Deploy step 7 is "purge the Cloudflare cache if
static files changed". Parliament's CSS/JS live at fixed URLs
(`/static/css/tailwind.css`), and nginx marks them `public, immutable` for 30
days, so after a deploy that changes one, Cloudflare keeps serving the old
file, or a 404 it cached before the file existed. curl against the origin
looks fine while members see an unstyled site.

**What's new.** `GET /site-monitor/static-assets/?path=css/tailwind.css&path=…`
returns the SHA-256 and size of each file as it sits in `STATIC_ROOT` on the
origin, which is what nginx serves. go-sentinel's new `cdn-assets` check hashes
the same files as served through Cloudflare and fails with "purge the cache:
…" when they differ, or when Cloudflare answers 404 for a file the origin has.

**Locked down the same way as the honeypot bypass (v3.35.3):**
- The endpoint needs `X-Site-Monitor-Token: <SITE_MONITOR_TOKEN>`. Without it,
  including when no token is configured, it's a plain 404, so the endpoint is
  invisible.
- Only `.css`/`.js` files inside `STATIC_ROOT` are answered. `..`, absolute
  paths and symlinks out of `STATIC_ROOT` are refused (answered `null`).
- At most 20 paths per request, and `Cache-Control: no-store`.

Code: `src/view/site_monitor.py`. Tests: `src/tests/security/test_site_monitor_static_assets.py` (5).

## 🧹 Guard: every seeded feature flag must gate something

The 07-25-26 audit found 16 feature flags that appeared as admin toggles but
were read nowhere. Some had security-sounding names (`anonymous_voting`,
`login_as_user`), so an officer could reasonably think flipping one did
something. v3.26.0 and v3.29.35 wired or pruned every one of them.

**Checked again today:** all 28 seeded names are read somewhere. The four
`cnb_*` flags look dead to a plain grep, but they're read through
`models/cnb.py`'s doc-type → flag table.

**New test:** `SeededFlagsAreReadTests` in
`src/tests/activity/test_feature_flag_seeding.py` fails if a seeded name isn't
referenced as a string literal in `src/` or as `feature_flags.<name>` in a
template. It covers the reverse of the existing "template flag isn't seeded"
test.
