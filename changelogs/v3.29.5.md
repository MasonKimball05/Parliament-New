## New model: `FeedbackRequest`

Deliberately built to mirror `BugReport` (same status/priority/resolution
shape — `new` → `acknowledged`/`in_progress` → `resolved`/`wont_fix`/
`duplicate`, `admin_notes`, `resolved_at`/`resolved_by`) so the two systems
stay easy to maintain side by side. One field splits it in two:

`request_type` is `feature_idea` or `support_ticket` (`support_ticket` is
the default — reaching the admin directly is the more common reason someone
opens the page). The submit form (`/feedback/`) presents this as two large
selectable cards rather than a dropdown, and re-labels itself around the
choice (title/description copy, "Priority" vs. "Urgency", the submit button
text) so it reads as two purposes on one page rather than one generic form.

## The public/private split — the one place this genuinely isn't just BugReport

A feature idea is **public**: posted to `/feedback/ideas/`, a lightweight
board any logged-in member can browse (status, priority, who suggested it),
so the chapter can see what's already been asked for instead of duplicate
requests piling up quietly in an inbox. A support ticket is **private**:
visible only to its submitter and the admin, never listed on the board.

That split is enforced at three layers, each independently, because a
list omission is not the same guarantee as a 404 on a guessed URL:

- **`feedback_tracker`** (`src/view/feedback.py`) — the board's queryset is
  `filter(request_type='feature_idea')` at the database level, not a
  template `{% if %}`. A ticket's title/description is asserted to never
  render on that page at all (`test_tracker_never_renders_ticket_title`).
- **`feedback_request_detail`** — a feature idea is readable by any member
  (same as a bug report detail page); a support ticket 404s for anyone but
  its submitter or the admin. This is the layer that actually matters: a
  ticket being absent from the board's list means nothing if the detail
  URL alone will still hand it to a guess.
- **`serve_feedback_attachment`** — same branch, applied to the file. An
  idea's attachment (e.g. a mockup) is public like the idea itself; a
  ticket's attachment follows the ticket. Per this codebase's private-
  upload convention (`src/view/serve_private_upload.py`'s v3.19.6 rule —
  "the file's access rule is the same object as the page's access rule"),
  `feedback_requests/` is classified in `PRIVATE_MEDIA_PREFIXES`
  (`src/view/serve_media.py`) so `/media/` itself can never serve it
  regardless of type — the public/private branch lives only in the
  dedicated view, not in the generic one. `test_media_classification`'s
  enumeration guard (walks every model's `upload_to`) required this; it
  would have failed the build otherwise.

## Only a support ticket emails

`send_feedback_notification` mirrors `send_bug_report_notification`
(same fail-silently-on-broken-transport contract, same recipient —
`BUG_REPORT_EMAIL` setting, reused rather than adding a second one since
it's the same person receiving both) with one deliberate difference: it
returns immediately for a `feature_idea`. Every bug report has always
emailed on submission; doing the same for every feature idea would page
the admin's inbox for something that isn't urgent by nature and is already
collecting on the public board. A support ticket is the "contact me
directly" path Mason asked for, so every one of those emails, the same way
every bug report already does.

## Also fixed this session: the "Edit User" button doing nothing

Mason reported that the Edit button on `/user-list/` stopped responding to
clicks. Root cause: the header "select all pledges" checkbox only renders
when `has_pledges` is true for the currently-filtered page, and
`templates/user_list.html`'s `DOMContentLoaded` handler bound it with an
**unguarded** `document.getElementById('select-all-pledges')
.addEventListener(...)`. Whenever the visible page had zero pledges — the
common case between recruitment cycles, or just filtering to a name that
isn't a pledge — that element is absent from the DOM, `getElementById`
returns `null`, and calling `.addEventListener` on `null` throws. Because
every other button's event listener (edit, add, batch add, CSV import,
delete, etc.) is wired up **later in that same synchronous handler**, the
one uncaught exception silently aborted everything after it — so the edit
button (and everything below it) had no listener at all, with no console
error a typical user would think to check. Fixed with the same null-guard
shape already used for `sync-admins-btn` two lines above it in the same
function. Grepped every other unguarded `getElementById` bound in that
handler against the template for a matching `{% if %}` — none of the
others are conditionally rendered, so this was the only instance of the
pattern in this file.
