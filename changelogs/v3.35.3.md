## 🔴 The pre-push hook's tests wrote into the real repository from a linked worktree

**What happened (09-28-26).** Pushing `main` from the linked worktree
`~/Documents/GitHub/Parliament-main` ran the pre-push hook there. Git exports
`GIT_DIR` to hooks, and in a linked worktree it is an absolute path, which
overrides `git -C <dir>`. So `test_ledger_check`'s throwaway-repo helpers
(`git init`, `git add`, `git commit` in a temp dir) acted on the REAL repository:

- `core.bare` was set to `true`, so the main checkout's `git status` failed
  with "must be run in a work tree";
- nine commits named `c` (author `T <t@example.com>`, a four-file tree) were put
  on the real `main`;
- the worktree's index was replaced.

The push aborted only because those commits made two ledger tests see an
unexpected sha. **Repaired the same day:** `core.bare = false`, `main` reset to
`e62d6cb` with `update-ref` (the junk commits are only in the reflog), and the
worktree index rebuilt from `main`. Nothing reached GitHub.

**Fixed three ways:**
- `scripts/pre-push.sh` unsets `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and
  the other location variables right after `cd`-ing to the top level. Re-run
  `make hooks` so the installed copy matches.
- `test_ledger_check._git` strips those variables itself (defence in depth: a
  test that creates repositories must never inherit which repository to use).
- `test_repo_hooks` finds the hooks directory with `git rev-parse --git-path
  hooks`. In a linked worktree, `<git-dir>/hooks` doesn't exist, because hooks
  live in the common dir. That's why `test_the_hook_is_installed_and_current`
  failed from Parliament-main.

*(Written 09-28-26 on `v3353-ready` as `c5fd34e`, whose changelog also carried
the honeypot-expiry work under a renumbered v3.35.3. `main` had already shipped
that work as v3.35.2 (`62afafb`), so this is the hook fix alone, cherry-picked
onto `main` 09-29-26. `v3353-ready` can be deleted.)*

## 🟢 The site monitor (go-sentinel) is no longer banned by the honeypot

**What was wrong.** go-sentinel checks the live site from outside every 30
minutes, including that `/.env`, `/.git/HEAD` and `/.git/config` are not
public. Those are honeypot paths, so on 09-27 it got the owner's IPv4 and IPv6
blacklisted, and since then its config has had to *skip* them — the checks it
exists for. Two more problems even without the ban: the honeypot's fake `.env`
(`KEY=value` lines) and fake `.git/config` (`[core]`) are exactly what the
monitor's leak test looks for, so it would report a leak every run.

**Fix.** A request carrying `X-Site-Monitor-Token: <SITE_MONITOR_TOKEN>` is
answered by the honeypot with the site's ordinary **404**: no cache ban, no
`IPBlacklist` row, no `HoneypotAccess` row, no alert; one INFO log line. It's
checked first, so a monitor IP with an older cache ban still gets the 404
rather than a fake body. A real leak (nginx serving the file itself) never
reaches Django, so the monitor still catches that.

**Why a token, not an IP or user-agent allowlist.** The monitor runs on GitHub
Actions, whose IPs change every run; a user-agent check would let any scanner
opt out by copying it.

**What the token does NOT do (on purpose):** authenticate, lift an existing
`IPBlacklist` ban, skip rate limits or the input scanner. A leaked token lets
one person probe trap paths without being banned, and nothing else. Compared
with `hmac.compare_digest`; a wrong or missing token is an ordinary scanner.

**Details:**
- `src/site_monitor.py` — `is_site_monitor_request()`. Tokens under 32
  characters are ignored.
- New system check **`src.W005`** (`src/checks_site_monitor.py`) warns when the
  token is set but too short, so it can't silently do nothing.
- The `X-Site-Monitor-Token` header is now **redacted** from
  `HoneypotAccess.additional_data`, like `Cookie`/`Authorization`. Otherwise a
  monitor hitting a server with the token unset or too short would store the
  secret in the admin's honeypot log.

(The `/admin/backup/` honeypot was unreachable when this was written. It's
fixed in the section below.)

## 🟡 An assigned Chorister couldn't manage songs

**What was wrong.** `manage_categories` creates the Chorister role with code
`'CHOIR'` (name `'Chorister'`), but `can_manage_songs` checked
`roles.filter(code='Chorister')`, i.e. the role's *name*. Officers and Chairs
pass the check anyway, so this only bit a plain **Member** made Chorister: the
role did nothing, and they couldn't add, edit or delete songs.

**Fix.** `can_manage_songs` checks `code='CHOIR'`. New
`src/tests/songs/test_chorister_role.py` (3); 2 fail against the old line.
(If someone hand-made a role with code `Chorister` in the admin, it stops
granting song management. Nothing in the app creates one.)

Found by the multi-chapter slice 3e guard (`test_required_role_codes`), which
lists every role code the code looks up.

## 🟡 The `/admin/backup/` honeypot never fired

**What was wrong.** It was registered with the other honeypots, *after*
`path('admin/', admin.site.urls)`. Django admin's catch-all matched first and
302'd every probe to the admin login, so nobody was ever banned for it.

**Fix (Mason's call, 09-29-26).** The route now comes right before `admin/`,
in both `src/urls.py` and `Parliament/urls.py`. The rest of `/admin/` is
unchanged. New `src/tests/security/test_admin_backup_honeypot.py` (3). The site
monitor also gets its 404 there (it's in `test_site_monitor`).

**Heads-up:** from this release, anyone who requests `/admin/backup/` is banned
for 24h, like every other honeypot. The site monitor token skips the ban.

## 🟡 Bug reports and support tickets no longer go to an address hard-coded in the repo

**What was wrong.** `send_bug_report_notification` and
`send_feedback_notification` read `getattr(settings, 'BUG_REPORT_EMAIL',
'<personal address>')`, but `BUG_REPORT_EMAIL` was never defined. So every
deployment used the fallback: a personal email in a public repo, and the inbox
another chapter's reports would reach too.

**Fix.** New setting `BUG_REPORT_EMAIL` (env, empty by default). Empty means
`SECURITY_ALERT_EMAIL`, the same fallback `ERROR_ALERT_EMAIL` uses. Added to
`.env.example`. New `src/tests/security/test_report_recipient.py` (3): the
setting routes a support ticket, the fallback works, and neither view contains
a personal address.

## Deploy reminders

- Code only: pull, restart `parliament-gunicorn.service`. No migrate, no
  collectstatic.
- **⚠️ Set `BUG_REPORT_EMAIL` in the server's `.env`** (to the inbox you want
  bug reports and support tickets in), then restart. Otherwise they go to
  `SECURITY_ALERT_EMAIL` from now on.
- **Run `make hooks`** on your Mac after pulling so the installed hook is the
  fixed one.
- **To turn on the monitor bypass:**
  1. `python -c "import secrets; print(secrets.token_urlsafe(32))"`
  2. Add `SITE_MONITOR_TOKEN=<value>` to the server's `.env`, then restart.
  3. In the go-sentinel repo: **Settings → Secrets → Actions**, add
     `SENTINEL_PARLIAMENT_TOKEN` with the same value.
  - Until both are set, go-sentinel keeps its `skip_paths` behaviour (see its
    README).
