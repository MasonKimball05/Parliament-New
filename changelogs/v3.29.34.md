## Context

Found by the 09-10-26 auto-run review of `v3.29.33` (the flash-message
fix — see `changelogs/v3.29.33.md`), same day. `v3.29.33` made the
fetch-based file-upload resubmit relay Django's flash message text out
of a JSON envelope instead of losing it — real progress — but it
toasted every message with `P.toast(m.text, m.level === 'success' ?
'success' : 'error')`. `P.toast` has always been a binary
`'success' | 'error'` control (its own doc comment said so), so that
line collapsed anything that wasn't literally `'success'` down to the
red "error" treatment.

That's wrong for `messages.warning()` and `messages.info()`, both of
which are used on POST paths that go through this exact resubmit path —
e.g. `kai_reports.py`, `legislation_drafts.py`, `vote_view.py`,
`slating/apply.py`, `upload_legislation.py`, `submit_excuse.py`,
`profile_view.py`, `service_user_dashboard.py`. "You have already
submitted an excuse for this event" and "This legislation is already
open" are not errors, but under `v3.29.33` they'd show as one. The
full-page flash-message partial a few hundred lines down in this same
file has always drawn a clear distinction — green/red/yellow/blue for
success/error/warning/info via `message.tags` — so the toast and the
full-page rendering of the same message disagreed on tone.

## The fix

`P.toast(message, kind)` now looks `kind` up in a `TOAST_STYLES` map
with all four tones (`success`/`error`/`warning`/`info`), matching the
full-page partial's own four colors. An unrecognized `kind` (or none)
falls back to the `info` treatment, not `error` — an unknown level
should read as neutral, not alarming, since collapsing it to red would
just be the same bug one level more defensive.

The resubmit handler now calls `P.toast(m.text, m.level)` directly.
`js_resubmit.py` already puts Django's own `message.tags` value in
`level` (unchanged by this fix — verified no view in this codebase
uses `extra_tags`, so `level` is always exactly one of Django's five
plain tags: `debug`/`info`/`success`/`warning`/`error`), so there was
nothing to translate — the only bug was the JS throwing that
information away.

**Duration unchanged**: `kind === 'success' ? 3000 : 8000`, i.e. only
success toasts dismiss quickly. Warnings and info notices now get the
same 8-second window errors already got, on the same reasoning the
original comment gave — the point of any non-success toast is that
somebody reads it.

**⚠️ Near-miss while writing this.** The first draft of the new
`P.toast` doc comment quoted the full-page partial's loop tag literally
inside a JS comment — exactly the mistake this same file's very first
comment block (above `window.Parliament = window.Parliament || {};`)
already warns about by name: Django's template engine parses `{% %}`
tags inside JS comments same as anywhere else, and a stray one breaks
the page. Caught immediately by the Django template compiler itself
(`TemplateSyntaxError: Unclosed tag ... 'for'`) when the updated test
suite ran — not by manual review. Fixed by describing the partial
rather than quoting its tag, matching the existing convention a few
lines above. Fifth+ time this specific trap has bitten in this file
per its own comments; still easy to do even reading the warning.

## Known, not addressed here

- `js_resubmit.py`'s `level` field would silently stop matching any of
  the four `TOAST_STYLES` keys if a future view ever called
  `messages.*(request, text, extra_tags='something')` on one of these
  forms — `message.tags` becomes `"something error"` in that case, and
  the JS's exact-match lookup falls back to `info`, not the tag that
  was actually intended. Not fixed here because no view in this
  codebase uses `extra_tags` today (confirmed by grep across
  `src/view/`), and handling it would mean parsing `extra_tags` back
  out in `js_resubmit.py`, JS, or both, for a case that doesn't
  currently exist. Worth a look if `extra_tags` is ever introduced.
