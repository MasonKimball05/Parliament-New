v3.29.25 shipped, was deployed, and the identical failure
(`posted_token_present=False`) recurred on a live mobile retest —
reported with no visible toast and "almost no time at all" between
tapping submit and landing on the 403 page. That pattern is consistent
with the client-side safety net (`refreshCsrfToken()` in `base.html`)
never reaching the server at all for this failure, but nothing server-
side could confirm or rule that out. Verified separately that the
deployed JS has valid syntax (parsed with Node after stripping Django
template tags) and that a fresh, uncomplicated render of this exact page
does include a correct CSRF field — so the bug isn't in either of those
places, which narrows it to something happening client-side, live, that
code-reading alone can't diagnose further.

Rather than walk Mason through Safari's remote Web Inspector (connect
phone to Mac, enable Web Inspector, Develop menu, Network tab, Console
tab — real but friction-heavy for a live repro), `csrf_token_refresh`
(the ONE place `refreshCsrfToken()` ever talks to the server) now logs
every hit. A log line appearing around a failure's timestamp is proof the
safety net ran; silence is proof it didn't — and either answer picks the
next fix.

## What's logged

To the `security` logger — the same logger, same file
(`logs/django_actions.log`), same pipe-delimited style
`csrf_failure.py` already uses for the 403 itself — not `ActivityLog`.
This is throwaway debugging signal, not an audit-trail event members
could ever be shown, and doesn't belong mixed into the formal activity
log this app treats carefully elsewhere (Kai redaction, admin
confidentiality boundary, etc.).

```
CSRF token refresh called | referer=<url> | had_csrf_cookie_before=<bool> |
returned_a_token=<bool> | ip=<ip> | user=<id (username)|anonymous> | ua=<truncated>
```

- **`had_csrf_cookie_before`** is the key field for the live question:
  the failing POST's own log line already showed `has_csrf_cookie=True`
  — if a refresh call around the same time shows
  `had_csrf_cookie_before=False`, this endpoint minted a brand-new
  cookie, meaning whatever cookie the failing POST carried wasn't
  produced by a refresh call at all.
- `returned_a_token` (not the token itself — same "don't log secrets"
  reasoning `csrf_failure.py`'s own docstring states) confirms
  `get_token()` actually succeeded server-side.
- `referer` identifies which page's form triggered the call, without
  needing a query param — `fetch()` sends it the same as a normal
  navigation for a same-origin request.

Logged at `INFO`, matching this project's existing convention for
this logger's routine (non-failure) events.

## New tests

`CsrfTokenRefreshDiagnosticLoggingTests` in
`src/tests/security/test_csrf_token_refresh.py` (6 tests, using
`assertLogs`, exercising the real view through the test client):

- a real hit actually logs the line;
- the token value itself is never present in the log output (only
  `returned_a_token=True/False`);
- an authenticated hit identifies the user (id and username both
  present);
- an anonymous hit is labeled `anonymous`, not left blank or erroring;
- `returned_a_token=True` appears on a normal successful call;
- `had_csrf_cookie_before=True` appears on a SECOND call from a client
  that already has the cookie from a first one — proving the field
  actually distinguishes "minting new" from "confirming existing"
  rather than always reading one value.
