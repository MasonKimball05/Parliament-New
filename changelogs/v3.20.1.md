## 1 — `Parliament.post()`: a failed request is now visible

v3.20.0 found that every interactive control on the education dashboard had been
answering **403 since the page was written**. What made that survivable — and
therefore what made it last — was not the 403. It was that each handler caught
the rejection and only wrote it to the console. The page did nothing, said
nothing, logged nothing anyone reads.

> **A silent failure is worse than a crash.** A crash gets reported the first
> day somebody hits it.

`base.html` now defines `Parliament.post(url, body, options)`, which does the
two things that between them cover the whole bug:

1. **One place knows where the CSRF token comes from.** Three templates had each
   written their own read, two against a cookie `CSRF_COOKIE_HTTPONLY = True`
   makes unreadable. A helper cannot be copied wrong.
2. **A non-2xx raises and is shown as a toast**, unless the caller passes
   `{quiet: true}` because it is rendering its own error.

Details worth their comments:

- **403 is called out by name** in the default message. It is what a missing or
  wrong CSRF token produces, it is the failure that hid for months, and
  "Forbidden" on its own sends the reader hunting for a permissions problem
  that is not there.
- **The helper is defined in `<head>`.** Page scripts live inside the content
  block, which base.html renders *before* its own later script blocks — a helper
  defined further down would be undefined exactly when a page tried to use it.
  A test pins the ordering.
- **The converted handlers have empty catch blocks on purpose.** The helper has
  already reported the error; the catch only undoes optimistic UI (re-enable the
  button, un-tick the checkbox, keep the modal open so typed values are not
  lost).

**Converted: the two pages that were provably broken** — the education dashboard
(6 handlers) and CSP violations (1). **Not converted: the other 37 templates**
that hand-write an `X-CSRFToken`. Converting them all blind, with no tests
covering them, would be a worse trade than the bug.

So `src/test_fetch_error_visibility.py` is a **ratchet, not a clean bill of
health**: twelve handlers still swallow a failure into the console, they are
listed by file and line, and the number may only go down. Same shape as
`test_query_budgets.py`, including a test that fails if you convert one and
forget to lower the constant.

## 2 — meetings can be edited

v3.20.0 shipped create and delete and no edit, so the only way to fix a mistyped
time was to delete the meeting and make a new one — **and deleting cascades to
`EducationMeetingAttendance`.** A typo destroyed the record of who turned up.

Editing keeps the meeting's pk and the same `Event`, so attendance survives
untouched. `test_attendance_survives_an_edit` is the point of the change; the
control asserts the calendar entry is not replaced either, since a new `Event`
would strand the old one on the chapter calendar.

**Delete moved onto the edit page**, so the row offers the safe action and the
destructive one sits next to a warning that now has a real alternative to point
at: *"To change the time or place, use Save changes instead — that keeps the
attendance."*

### One form, not two

The fields are a shared include (`_education_meeting_fields.html`) and the
parsing is a shared function (`_apply_meeting_fields`), used by both the Add
modal and the edit page.

⚠️ Two copies of a form drift, and **the symptom is a field that silently does
nothing on one of them** — the same shape this codebase has recorded nine times
as "the rule was stated correctly and one call site was left outside it". Tests
assert both halves: that both pages render the same field names, and that both
views call the same parser.

## ⚠️ Five self-references in one day, and the fifth broke the site

Every guard written today flagged the comment written to explain it, and this
release produced the worst instance:

| # | Where | What happened |
|---|---|---|
| 1 | `test_nosec_hygiene` | the docstring's example was scanned as a real suppression |
| 2 | `dev_tags.py` | prose quoting the directive **became** a directive |
| 3 | `test_csrf_token_source` | the note explaining the cookie fix matched the cookie scan |
| 4 | `test_fetch_error_visibility` | the helper's docstring counted as a swallowing handler |
| 5 | **`base.html`** | the helper's comment named the content block, and **Django parses tags inside JS comments** — `'block' tag with name 'content' appears more than once`, i.e. every page 500s |

The first four were noise. The fifth took the whole site down in the test suite,
and would have done the same in production.

> **The rule, now with teeth: describe the construct, never spell it.** A
> comment is not inert — not to a scanner, and not to Django's template parser,
> which does not care that the tag is inside `/* … */`.

**And an existing guard caught the follow-on.** Two of the new comments were
multi-line `{# … #}`, which Django does not treat as comments at all — v3.16.3's
`test_template_comments` failed immediately and named both files. That check was
written for this exact mistake and did its job with no help from me.
