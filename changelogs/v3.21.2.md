# v3.21.2 — the modal component broke every submit button in it

**Date:** 08-19-26
**Type:** Bug fix — regression from v3.21.0. **No migration.**
**Committed & pushed:** 08-19-26, `d2d871e`
**Deployed:** *not deployed*

Reported by Mason: *"the add task button isn't working now"* — the one inside
the form, not the one on the page.

✅ **1,516 tests, 0 failures, 3 skipped**, two partitionings. `manage.py check`
silent, bandit exit 0. Negative control verified.

---

## 🔴 The bug, and it is mine from two releases ago

v3.21.0 extracted the modal shell into `components/modal_open.html` +
`modal_close.html` (ideas list #10) so the overflow bug could not be
hand-copied a fourth time. The footer — Cancel and the submit button — moved
into `modal_close.html`.

Which renders **after** the caller's `</form>`:

```
{% include "components/modal_open.html" … %}
  <form method="post" …>
    …fields…
  </form>                                    ← form closed here
{% include "components/modal_close.html" … %}  ← submit button rendered here
```

**A `<button type="submit">` outside its form submits nothing.** No error, no
network request, no console message. The modal opened, the fields accepted
input, and the button did nothing.

All three modals on the education dashboard: **Add Task, Add Meeting, and
Restrict a Page.**

### The fix

The HTML `form` attribute — a submit button may live anywhere in the document
and belong to a form by id. `modal_close.html` takes a `form_id`, each form got
an `id`, and the three call sites pass it.

---

## ⚠️ Why nothing caught it, and what now does

The template reads correctly. `<form>` … `</form>` … `{% include %}` is
unremarkable, `manage.py check` was silent, `test_modal_component` was green
(it counts opens against closes, which were balanced), and 1,509 other tests
passed. **The defect does not exist in any file. It exists in the relationship
between two elements of the rendered output.**

So the new guard parses the **rendered page**: every `type="submit"` must either
sit lexically inside a `<form>…</form>` or carry `form="id"` naming a form that
exists. Removing the `form` attribute again fails it immediately.

> **A scanner approximates; a request does not.** Same conclusion as the
> `committee.committee_code` 500 in v3.20.0 — and I wrote that sentence in that
> changelog, then two releases later shipped a bug that only a rendered page
> could show.

Two controls, because this assertion has an obvious way to pass for the wrong
reason:

- `test_the_detector_actually_detects` — feeds it four hand-built fragments
  (orphan, wrong id, in-form, by-attribute) so the check is known to work. A
  page with no submit buttons at all would otherwise pass silently, which is
  exactly what a broken fixture produces.
- `test_the_three_modals_still_render_their_submit_buttons` — a footer that
  rendered *nothing* would also pass the orphan check and be just as broken.

---

## The pattern worth naming

This is the third bug in three releases where **the abstraction introduced to
prevent a class of error introduced a different one**:

| Release | The fix | What it broke |
|---|---|---|
| v3.20.1 | `Parliament.post` helper | nothing — but its own comment named a template tag and took the site down in tests |
| v3.21.0 | shared modal component | every submit button inside a modal |
| v3.21.1 | — | (a fixture assumption, not an abstraction) |

Extracting a shell is still right; the overflow bug really was copied three
times. But **moving markup across a boundary can break relationships the markup
depended on**, and form ownership is exactly that kind of relationship —
invisible in both halves, only real in the assembled page.
