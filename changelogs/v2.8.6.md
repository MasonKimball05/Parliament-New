## Email Warmup System

When officers create announcements and land on the email confirmation page, the system now pre-loads all email data in the background while the user reviews the recipient list.

### How It Works

1. **Page Load**: When the confirmation page loads, JavaScript automatically calls the warmup endpoint
2. **Background Processing**: The server pre-creates the email log, recipient records, and renders email templates
3. **Cache Storage**: All prepared data is stored in Django's cache for 10 minutes
4. **Fast Send**: When the user clicks "Send", the system uses the pre-warmed data instead of recomputing
5. **Cleanup**: If the user skips or navigates away, the warmup data is automatically cleaned up

### New Endpoints

| URL | Method | Purpose |
|-----|--------|---------|
| \`/officers/announcements/<id>/warmup-email/\` | POST | Pre-warm email data |
| \`/officers/announcements/<id>/cancel-warmup/\` | POST | Clean up warmup data |

### Files Changed

- `src/view/officer/manage_announcements.py` - Added `warmup_announcement_email` and `cancel_warmup_announcement_email` views
- `src/urls.py` - Added warmup URL routes
- `templates/officer/confirm_announcement_email.html` - Added JavaScript for warmup lifecycle

### Bug Fixes

- **Foreign Key Error**: Fixed race condition where warmup data in cache referenced deleted email logs
- **Robust Validation**: Send function now validates warmup log exists before using pre-warmed data
- **Cancelled Status**: Cancelled warmup operations now mark logs as 'cancelled' instead of deleting (audit trail)
- **Admin-v2 Display**: Warmup and cancelled logs now display with proper status badges in email logs page

### New Status Values

Added to `AnnouncementEmailLog.STATUS_CHOICES`:
- `warming_up` - Email preparation in progress
- `pending` - Ready to send
- `cancelled` - User cancelled before sending

## Database Optimization

### Removed Redundant Notifications

Previously, the system created one \`Notification\` row per user for every announcement and event. This was redundant because:

- **Announcements** have their own display system (home page popup, announcements page) with \`UserAnnouncementView\` tracking
- **Events** are displayed on the calendar page which all members access

### Changes Made

| File | Change |
|------|--------|
| \`src/view/officer/manage_announcements.py\` | Removed \`notify_all_active_members()\` call from \`create_announcement\` |
| \`src/notifications.py\` | Removed \`notify_all_active_members()\` call from \`process_pending_scheduled_announcements\` |
| \`src/view/officer/manage_events.py\` | Removed \`notify_all_active_members()\` call from \`create_event\` |

### Database Cleanup SQL

To clean up existing redundant notification rows:

\`\`\`sql
-- Delete announcement and event notifications
DELETE FROM src_notification
WHERE notification_type IN ('announcement', 'event');

-- Also run Django's session cleanup
-- python manage.py clearsessions
\`\`\`

### Impact

- **Before**: ~32 notification rows created per announcement/event (one per active member)
- **After**: 0 notification rows created per announcement/event
- **Savings**: ~2,000+ rows in typical deployment
