## 🟡 N+1 on the committee documents page — `uploaded_by`, version history, and committee membership checks

`committee_documents()` (`src/view/committee/documents.py`) built
`all_documents = CommitteeDocument.objects.filter(committee=committee)`
with no `select_related`, and the permission filter one line below
(`doc.can_user_view(user)`) doesn't reliably warm the `uploaded_by` FK
either — `can_user_view` short-circuits on `published_to_chapter` (and
several other visibility branches) before ever touching
`self.uploaded_by`. `documents.html` then prints `doc.uploaded_by.name`
once per row: one query per document. Fixed with
`.select_related('committee', 'uploaded_by')` on the queryset (the
`committee` half fixes a second, related re-fetch inside
`can_user_view`'s `committee_only` branch — see below).

Pinning that down to a genuinely flat query count (rather than just
"fewer queries," which can still hide an N+1 at a different multiplier)
surfaced two more instances of the same shape in the same view, both
fixed here:

- **Version history** — `for doc in documents: doc.version_history =
  list(doc.versions.all())` was one query per document whenever
  `document_versioning` is enabled, regardless of any select_related on
  it (a per-instance reverse-FK lookup is still a per-instance lookup).
  Replaced with one bulk `DocumentVersion.objects.filter(document_id__in=
  [...]).select_related('uploaded_by')`, grouped by `document_id` in
  Python — the same pattern `linked_minutes_map` a few lines up already
  uses for the identical reason (and the template also prints
  `version.uploaded_by.name` per version, hence the added
  `select_related`).
- **Committee membership/chair checks** — `CommitteeDocument.can_user_view()`
  answered its `committee_only`/`chairs_only`/`custom` branches with
  `user in some_queryset.all()`. `QuerySet` has no `__contains__`, so
  Python's `in` falls back to iterating the whole queryset — fetching
  every column of every committee member — just to answer a yes/no
  question, once per document. Since every document on this page belongs
  to the same committee, `is_committee_member`/`is_committee_chair` are
  now computed once per request in the view and passed into
  `can_user_view(user, is_committee_member=..., is_committee_chair=...)`
  — the same `can_edit_any=` idiom `can_edit_specific_minutes` already
  established for this exact shape of problem (v3.29.35). `custom_viewers`
  was left as a per-document `.filter(pk=user.pk).exists()` rather than
  hoisted — that one is genuinely per-document, not a single
  committee-level fact, and `.filter().exists()` is already the cheap,
  indexed form (a straight improvement over the old `in ... .all()`
  either way).

Net effect on the fixture in the new regression test below: 9 documents
went from N+1-scaling (57 queries, climbing to 99 at 27 documents, before
any of this) to a flat 39 queries regardless of document count.

⚠️ **Not fixed here, noted rather than chased further:** two small
`×2` duplicate-shape queries remain (committee membership, chair status).
This view separately calls `committee.is_vp()`, `committee.is_chair()`,
and `is_committee_member_or_above()` (for the unpublished-minutes section)

queries per fact instead of 1, not one per document — a small, pre-existing
redundancy, not the N+1 this pass was about. Worth a follow-up if this

## 💡 Weak-password checker (set-time validator) + weekly weak-password audit

Requested directly by Mason: *"add a checker to check if a password is
weak, like the password reset checks... `Password123!` or something"* plus
*"a weekly scheduler that checks for that too."* Two separate mechanisms,
because they solve two different problems:

### 1. `src.validators.KnownWeakPasswordValidator` — rejects a weak password at the moment someone tries to set it

Parliament already had three password validators
(`AUTH_PASSWORD_VALIDATORS` in `Parliament/settings.py`): a complexity rule
(`CustomPasswordValidator` — 9+ chars, upper/lower/digit/symbol), Django's
bundled `CommonPasswordValidator` (~20,000 bare common passwords), and
`PwnedPasswordValidator` (checks the live Have I Been Pwned API via
k-anonymity, **fails open** if that API is unreachable — the right call for
an external dependency, since a third-party outage shouldn't block anyone
from setting a password at all).

The gap: something like `Password123!` **passes the complexity rule**
outright (it has all four character classes and is 12 characters long), and
Django's bundled common-password list is bare dictionary words, not
"complexity-rule-passing" variants like this — so the *only* thing standing
between that password and a real account was the HIBP network call. If that
call ever times out, gets rate-limited, or is blocked at the network level,
there was no local fallback at all for this exact shape of password.

Added `KnownWeakPasswordValidator` — a small (~20 entries), hand-curated,
case-insensitive, purely local list (`COMMON_WEAK_PASSWORDS` in
`src/validators.py`) covering exactly this shape: `Password123!`,
`Welcome123!`, `Qwerty123!`, `Changeme123!`, a couple of Beta Theta
Pi/Parliament-specific guesses, etc. Wired into `AUTH_PASSWORD_VALIDATORS`
between `CustomPasswordValidator` and `CommonPasswordValidator`. Deliberately
kept short — every entry is an O(1) set lookup, not a network round trip, so
there's no reason to make it a second copy of Django's own list, and a
short list is also easy to actually read and sanity-check.

Verified this closes every user-chosen password-set path, not just the
validator in isolation: `change_password` (Django's `PasswordChangeForm`),
`forced_password_change` (`ForcedPasswordChangeForm`, which calls
`validate_password` explicitly), and Django's built-in
`password-reset-confirm` flow (`SetPasswordForm`) all now reject
`Password123!` end-to-end. (Two paths intentionally still bypass this by
design and are unaffected: `manage.py reset_all_passwords` /
`reset_user_password` set a system-generated default and immediately force
a change on next login — see below for why that's also not sufficient on
its own.)

### 2. Weekly weak-password audit — checks passwords that are *already* set

The validator above only ever sees a password at the moment someone submits
a form. Two real gaps that leaves open, both worth checking directly rather
than assuming the validator covers them:

- `manage.py reset_all_passwords` / `reset_user_password` set active
  members to a **predictable** `[first_initial][lastname][user_id]`
  password directly via `user.set_password()` (e.g. `mkimball73`) —
  bypassing `validate_password` entirely by design, then relying on
  `force_password_change=True` to prompt a change on next login. If a
  member doesn't log in for a while after a reset, their account sits on a
  guessable password (computable by anyone who knows their name and
  roster ID) for as long as that gap lasts.
- Any account whose password was set before this validator existed is
  grandfathered in — the validator can't retroactively check what's
  already stored, because it's hashed.

Added `src/weak_password_audit.py`
(`audit_active_users_for_weak_passwords()`), a management command
(`manage.py check_weak_passwords`, with `--dry-run`), and a Celery task
(`tasks.check_weak_passwords`) scheduled weekly (Monday 3:35 AM CST, right
after the daily digest's slot — see `setup_celery_schedules.py`). For every
`is_active=True` user, it calls `user.check_password(candidate)` against
the same `COMMON_WEAK_PASSWORDS` list, plus — only for accounts still
flagged `has_default_password=True` — the exact predictable reset-format
guess for that specific user. A match files a `LoginAlert`
(`alert_type='weak_password'`, new choice added this release, severity
`'high'`) visible in the existing admin-v2 Security Alerts dashboard; the
task also emails officers a summary (via the existing
`send_security_alert_task`, `force_send=True` since that helper only
auto-emails on `'critical'`) when anything is found, but only then — an
"all clear" email every single week would just train officers to ignore it,
unlike `send_daily_digest`, which deliberately always sends so its own
absence is the signal.

Deliberately **does not** record which candidate matched, anywhere — the
finding is "this account's current password is known-weak," and nothing
downstream needs the literal guessed string. (Contrast with the existing
admin-initiated force-password-reset flow in `admin_v2.py`, which *does*
store a freshly generated plaintext password in `LoginAlert.resolution_notes`
— a deliberately different case: an officer generates that one specifically
to relay it to the member, once, immediately. Nothing here needs that
treatment.)

Performance is bounded on purpose and worth understanding before widening
the candidate list: `check_password()` runs the real configured password
hasher, which is intentionally slow, so cost is
O(active users × candidates checked). Two things keep it small: the global
list is short (~20 entries, not a breach corpus), and a user with an
**open** `weak_password` alert from a previous run is skipped entirely on
later runs — they drop out of the check pool until an officer resolves the
alert, so steady-state cost shrinks over time instead of re-paying the full
check for every active member every week forever.
