Requested by Mason the same day as v3.28.0's reminder-email feature: give
event-reminder emails the same open/view tracking the announcement email
system already has, so admins can see who has and hasn't viewed a reminder
and send errors show up in the Django logs.

## What was built

**Model:** `EventReminderRecipient.viewed_at` (nullable, same shape as the
announcement system's tracking field).

**Email rewritten as real HTML.** v3.28.0 sent reminder emails as plain
text via `send_mail()`, which can't carry a tracking pixel. The send path
now uses `EmailMultiAlternatives` (HTML alternative + `strip_tags()`
plain-text body), rendering a new `templates/emails/event_reminder.html`
modeled on the existing `announcement_notification.html`. The pixel is a
1×1 `<img>` at `/track/event-reminder/<log_id>/user/<user_id>/`.

`event.description` reaches the HTML template through the `linebreaks`
filter, which escapes the value before inserting `<p>`/`<br>` tags — a
member-authored event description can't inject markup into an email an
officer didn't write.

**New view:** `track_event_reminder_email_view`
(`src/view/officer/manage_events.py`) — no login required, since it's
fetched by the recipient's mail client which has no Parliament session.
Silently no-ops on an unknown `(log_id, user_id)` pair rather than
404ing, matching `manage_announcements.track_email_view`'s reasoning:
distinguishing the failure modes to the client would leak whether a given
pair exists, for no benefit. Keeps the *first* open time if the pixel is
refetched (a mail client re-rendering the message shouldn't reset "when
did they actually open this").

**`send_event_reminder_pushes` restructured, not just extended.** The
`EventReminderLog` row is now created *before* the per-recipient send loop
(was after in v3.28.0) so its id is available to build each recipient's
tracking URL — counts are written once at the end via `save(update_fields
=[...])`, the same "create the log row first so a mid-loop crash still
leaves a record" reasoning `send_announcement_notification` already uses.
A failed send now logs at `ERROR` (was `warning` in v3.28.0) and calls
`_flag_user_email` — the same helper the announcement system uses to flag
a bad address for the member to fix on next login — so a real delivery
problem is both visible in the logs and visible to the affected member,
not silently retried forever.

**Admin-v2 surfacing:** `event_reminder_log_detail` splits dispatched
emails into `emails_viewed`/`emails_not_viewed` querysets, rendered as two
side-by-side lists with names and open timestamps — mirroring the
announcement stats page. The list page annotates each log with a live
`Count` of viewed recipients rather than a stored counter, deliberately:
unlike a dispatch count, "how many have viewed" keeps changing after the
row is created (someone can open the email days later), and a stored
count would go stale the moment it was written.

## Bugs caught while building this, fixed in the same commit

- Two existing tests from v3.28.0's `test_event_email_reminders.py` had
  patched `django.core.mail.send_mail` to inject a send failure — once the
  code called `EmailMultiAlternatives(...).send()` instead, that patch no
  longer intercepted anything (the mock would silently never fire, and the
  "failure" test would have started asserting a real send succeeded).
  Caught by a negative-control run before shipping; fixed by patching
  `EmailMultiAlternatives.send` directly, with a comment explaining why so
  it isn't "fixed" back the wrong way later.
- Two new tests both called a test fixture helper with a blank default
  email, colliding with the DB's `uniq_parliament_user_email_lower`
  constraint (two blank emails aren't distinct under a lowercase-unique
  index) — `IntegrityError` on the second one. Unrelated to the feature;
  fixed by giving the second fixture member a real, unique email.
