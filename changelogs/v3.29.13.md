## The fix — reuse the disposition rule this codebase already has, don't invent a new one

`download_chapter_document` (`src/view/view_document.py`) — the view both
the announcements page's document chip (`templates/announcements.html`)
and the announcement email's document link (added in v3.29.12) point at —
unconditionally returned `FileResponse(..., as_attachment=True)` regardless
of content type, forcing a save dialog for every click, PDF included.

This codebase already decided this exact question once, for `serve_media`
and `serve_private_upload` (`src/utils/content_disposition.py`,
v3.19.7/v3.19.8): `INLINE_SAFE_CONTENT_TYPES` is a narrow allowlist
(`application/pdf` + the raster image types), `should_download()` returns
`True` for anything outside it, and `apply_disposition()` sets both
`Content-Disposition` and `X-Content-Type-Options: nosniff` together so
the two can't drift apart. `committee_documents/` is already in
`PUBLIC_MEDIA_PREFIXES`, so a `CommitteeDocument`'s raw `/media/` URL was
*already* served inline by that rule — `download_chapter_document` was the
one remaining view still hardcoding the old `as_attachment=True` shape
instead of going through it.

`download_chapter_document` now builds its own `Content-Type` the same way
`serve_media` does (`mimetypes.guess_type` on the stored filename) and
calls the shared `apply_disposition()` instead. A PDF or image now opens
in the browser's own viewer — which has its own download control, meeting
Mason's "open it, with the option to download from there" ask directly — a
`.docx`/`.xlsx`/anything else still downloads, because browsers can't
render those regardless of the header. Also added the same
`Cache-Control: private, max-age=3600` `serve_media` sets, since a
visibility-restricted chapter document must never land in a shared/CDN
cache — this view didn't set any `Cache-Control` before.

**Nothing about who may open a document changed.** The lookup
(`published_to_chapter=True`) and the `can_user_view()` check are byte-for-
byte the same as before this change — only what the response tells the
browser to do with the bytes once that check passes.

⚠️ **Scoped narrowly, on purpose.** The other three `download_*` views in
`view_document.py` (`download_legislation_document`,
`download_committee_document`, `download_committee_document_version`) still
hardcode `as_attachment=True` — Mason's ask was specifically about the
announcement-linked document experience, and changing those wasn't asked
for. They're candidates for the same treatment later, but that's a
separate call.

## New tests

`src/tests/documents/test_chapter_document_open_disposition.py` (4 tests):
a PDF gets `Content-Disposition: inline` + `nosniff`; a `.docx` still gets
`attachment`; the response is `Cache-Control: private`; an unpublished
document (`published_to_chapter=False`) is still a 404, unchanged from
before.

(One planned test — a visibility-restricted document returning 403 for an
unauthorized viewer — was dropped after tracing `CommitteeDocument.can_user_view()`:
its very first line is `if self.published_to_chapter: return True`, so for
any document reachable through this view's own queryset filter
(`published_to_chapter=True`), the permission check always passes and the
`visibility` field is not consulted at all. That's pre-existing behavior,
untouched by this change, and reads as intentional — "published to
chapter" reasonably means visible to the whole chapter regardless of a
narrower `visibility` setting meant for pre-publication/committee-scoped
documents. Noting it here rather than silently asserting something untrue,
not raising it as a finding since it's unrelated to what was asked.)
