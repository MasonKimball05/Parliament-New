# v2.14.0 - UserPreferences JSON Consolidation + New User Preferences

**Release Date:** May 11, 2026

**Deployment Status:** Deployed

**Type:** Feature / Code Quality

---

## Overview

The `UserPreferences` model previously stored 20 boolean preferences as individual database columns. Adding any new preference required a schema migration, and the table had 20+ columns for data that was conceptually a single user settings object.

All 20 boolean fields have been consolidated into a single `prefs` JSONField with a nested structure. Adding a new preference now requires only a default value and a UI change — no schema migration.

This release also introduces four new user-configurable preferences that take advantage of this flexibility: home page layout, post-login landing page, and full exposure of all four in-app notification toggles.

---

## What Changed

### `UserPreferences.prefs` JSONField

The new field stores all preferences in one JSON column:

```json
{
  "email": {
    "announcements": true,
    "legislation": true,
    "events": true,
    "committee_updates": true
  },
  "display": {
    "compact_view": false,
    "announcement_popups": true,
    "home_layout": "modern",
    "landing_page": "home"
  },
  "menu": {
    "vote": true,
    "committees": true,
    "chats": false,
    "documents": true,
    "announcements": true,
    "calendar": true,
    "legislation": true,
    "excuses": false,
    "search": true,
    "roberts_rules": false
  },
  "notifications": {
    "announcements": true,
    "legislation": true,
    "events": true,
    "slating": true
  }
}
```

`theme` is kept as its own `CharField` — it has choices, is non-boolean, and is used in the inline `<script>` tag in `base.html` before any request context is available.

### Backward-Compatible Property Layer

18 `@property` definitions on `UserPreferences` expose the individual keys under their original names (`email_announcements`, `show_vote_menu`, `notify_announcements`, etc.). Templates, notification service attribute access, and view code that reads individual prefs don't need to change.

A `_pref(section, key, default)` helper method handles the nested dict access with fallback defaults, so code that reads a pref never has to worry about missing JSON keys.

### New Preferences: Home Layout

Users can now choose between two home page layouts:

- **Modern** (default) — current card-based dashboard (`home_modern.html`)
- **Classic** — the original two-column layout from v2.12.0, recovered and saved as `home_classic.html`

The preference is exposed in the Preferences page under Display Settings. `home.py` reads `user.preferences.home_layout` and renders the appropriate template.

### New Preference: Post-Login Landing Page

Users can choose where they land after signing in:

| Value | Destination |
|---|---|
| `home` (default) | Home dashboard |
| `announcements` | Announcements feed |
| `calendar` | Calendar |
| `vote` | Voting page |

The preference is set in the Preferences page and read in `login_view.py` immediately after a successful authentication.

### In-App Notification Toggles Exposed

All four `notifications` sub-keys are now configurable from the Preferences page:

- **Announcements** — `notify_announcements`
- **Legislation** — `notify_legislation`
- **Events** — `notify_events`
- **Slating** — `notify_slating` *(previously stored in JSON but had no UI)*

The profile page mini-form, which previously controlled only the first three, now also shows `notify_slating` and includes a link to the full Preferences page.

### `UserPreferencesForm` Rewritten

Previously a `ModelForm` over the boolean fields. Now a plain `forms.Form` that:
- Accepts `instance=` kwarg to populate initial values (matching the ModelForm interface `preferences_view.py` expects)
- Exposes the same field names (`email_announcements`, `show_vote_menu`, etc.) so `preferences.html` template doesn't need to change
- Has a `save()` method that writes cleaned data back into `instance.prefs` and calls `instance.save()`
- New fields added: `home_layout` (ChoiceField), `landing_page` (ChoiceField), `notify_announcements`, `notify_legislation`, `notify_events`, `notify_slating` (BooleanFields)

### `profile_view.py` — Notification Pref Write

The profile page manages all four `notify_*` toggles via a small form. Updated to read/write the `prefs['notifications']` sub-dict directly rather than assigning to individual fields.

### ORM Filter Queries Updated

Three places in the codebase filtered users by `preferences__email_announcements=True`. Updated to use the JSON path traversal syntax:

```python
# Before
Q(preferences__email_announcements=True) | Q(preferences__isnull=True)

# After
Q(preferences__prefs__email__announcements=True) | Q(preferences__isnull=True)
```

Files updated: `src/notifications.py`, `src/view/officer/manage_announcements.py` (3 queries), `src/view/admin_v2.py`.

## Migration

Migration `0158` runs in three steps:

1. **AddField** — adds `prefs` column (default `{}`)
2. **RunPython** — reads all 20 boolean fields from each row and writes the nested JSON structure into `prefs`
3. **RemoveField ×20** — drops all 20 boolean columns

The reverse migration restores the boolean columns and reads values back from `prefs`.

---

## Breaking Changes

None externally. The `UserPreferences` model no longer has 20 individual boolean fields as real database columns, but all are accessible via properties with the same names.

Any code that calls `save(update_fields=['notify_announcements', ...])` will fail — those are no longer real fields. The only case of this was `profile_view.py`, which has been updated to `save(update_fields=['prefs'])`.
