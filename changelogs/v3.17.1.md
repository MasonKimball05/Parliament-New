# v3.17.1 — Dev-mode query attribution, and the N+1s it found

**Deployed:** ✅ 07-29-26 — shipped in `619eaae`.
Follow-up to v3.17.0. Dev mode could say *that* a page had an N+1 but not *where
from*, so two duplicate groups could render identically with no way to tell them
apart. Fixing that turned it into a tool that found real problems within minutes
— most of this release is those findings.

Implemented 07-28-26.

---

## 1. Query attribution — the change that made the rest possible

`src/middleware/dev_mode.py`, `src/dev_mode.py`

Capture moved from `connection.queries_log` (needs `force_debug_cursor`, gives
SQL and duration only) to **`connection.execute_wrapper`**, a documented hook
that sees every query regardless of DEBUG and lets us record, per query:

- a **project-filtered stack trace** — Django's own frames stripped, because
  "came from `QuerySet._fetch_all`" is never the answer,
- **parameters**, **rows returned** (`cursor.rowcount`), and **tables touched**.

Duplicate groups now carry the distinct call sites that produced them. That is
what makes two identical-looking N+1 blocks distinguishable, and it is how
every finding below was located.

## 2. New panel tabs

- **Shapes** — unique query shapes with count, total time, tables, rows returned,
  originating call sites, and a verdict derived from the SQL text: *single-row
  lookup by key*, *NO WHERE — full table scan*, *`.get()` — LIMIT 21 is Django
  probing for MultipleObjectsReturned*, *ORDER BY with no LIMIT*, *a write. On a
  GET request this is worth questioning*.

  **No row values, deliberately.** Re-running captured SELECTs to show rows would
  make the developer allowlist a read-anything key to Kai reports, ballots and
  slating notes, bypassing every app-level gate. Row counts, tables and access
  pattern are what you need to optimize; the values are not.

- **Request** — resolved URL name, view, args, status, user, and the timing split
  (total vs SQL vs Python/render), plus every template rendered with its context
  keys. Template capture is a single guarded wrap of the Django template backend
  at import; Django caches compiled templates and offers no per-render signal
  outside the test runner, so this is the accepted approach.

- **Perms** now opens with **this user's standing capabilities** — `is_admin`,
  `is_officer`, `member_type`, `can_view_officer_pages`, `has_cnb_permission`,
  roles, Django `is_staff`/`is_superuser`, admin-v2 allowlist + session, dev-mode
  allowlist. Decorators only record when they fire, and ~31 authorization checks
  in this codebase are inline `if request.user.is_admin` inside a view.
  Instrumenting each would be churn; the capability summary answers for all of
  them at once. The admin-v2 gate is now instrumented too, both halves
  separately, so a redirect tells you *which* half refused.

## 3. 🟠 `passed_legislation` — the N+1 that started this

Reported as "the legislation tracker". The stack pointed at
`passed_legislation.py:259`, the `render()` call — which is what lazy evaluation
during template rendering looks like. Two 6× groups, both `ParliamentUser`:

- **`posted_by`** — `user_id` is ParliamentUser's **primary key**, so every row
  re-fetched the same author by pk. `select_related('posted_by')`.
- **`co_authors`** — iterated per row in the template. `prefetch_related`.

Also fixed on the same page: `_present_members_in_window` ran **one attendance
query per legislation**. Every window is `vote_end − 6h .. vote_end`, so the
union is fetched once and sliced in Python (`_dedupe_latest_per_user`, split out
for the purpose).

## 4. 🟠 `view_legislation_history` — same class, plus a write on GET

Fixed before the report above arrived; a different page with the same shape.
`select_related`/`prefetch_related`, and per-row `yes/no/abstain` counts
collapsed into one aggregate across the page.

**`set_passed()` was writing on every GET.** It did a full-row `self.save()` for
every closed bill, so *viewing* the page rewrote every row. Now it takes an
optional `counts` mapping (issuing **no queries** when the caller already
aggregated them), and saves only when the value actually changed, and only that
column.

## 5. 🟠 ParliamentUser is a wide table — stop reading all of it

The observation that generalises the two above: `ParliamentUser` carries the
whole member profile in one table — a bio, five JSON fields, six social handles,
house, graduation details. ~43 columns. Every `select_related('user')` without a
matching `.only()` drags all of it across, per joined row, on pages that render
a single name.

Two changes, plus a decision recorded:

- **`MEMBER_DISPLAY_FIELDS`** (`src/models/users.py`) — the columns needed to
  show *who someone is*: name, preferred name, member type/status, avatar. Use
  it with `.only()` alongside `select_related`. Applied to the attendance join
  on `passed_legislation`, which previously selected all 43 columns per row to
  print one name.

- **`DeferredProfileModelBackend`** (`src/auth_backends.py`) — the session-user
  load happens on every authenticated request (that is how `request.user`
  exists; it is one indexed pk lookup and cannot be removed) but its *width*
  can. The backend defers the profile-only columns. Pages that genuinely want
  the logged-in user's profile pay one extra query when they touch a deferred
  field — the right place for that cost, and dev mode's object inspector labels
  it *"DEFERRED — reading this fires a query"*.

  Not deferred, on purpose: `onboarding_data` (the onboarding checklist is on
  both home layouts), `profile_picture` (nav avatar), and anything used for
  authorization — deferring an authz field turns every permission check into a
  query and is an excellent way to create a subtle security bug.

- **Splitting the profile into a `MemberProfile` one-to-one** would make this
  structural rather than a convention. It is the right end state and it is
  deliberately **not** in this release: it is a migration touching every profile
  read, and it deserves its own change rather than riding along with a perf pass.

### ⚠️ Deploy note — read this one

Django writes the auth backend's dotted path into the session and logs the user
out on the next request if that path is no longer in `AUTHENTICATION_BACKENDS`.
Five places logged users in with a hardcoded
`'django.contrib.auth.backends.ModelBackend'` — **passkey login, 2FA recovery,
login-as (×2), and the admin user switcher**. Left alone, this change would have
been a production login outage, not merely a test failure. The full suite caught
it.

All five now import `AUTH_BACKEND_PATH` instead of retyping the string, and
**stock `ModelBackend` is deliberately kept listed second**: without it, deploying
signs out every live session at once. It never wins a login. Safe to remove a
release or two from now, once no session predates this.

## 6. 🟡 `FeatureFlag.is_feature_enabled` is now cached

The admin-v2 dashboard asked for `push_notifications_enabled` **five times in one
page load**, five identical uncached `objects.get`s. This closes the standing
"feature-flag caching" item in CLAUDE.md.

Correctness comes from **invalidation, not expiry**: `save()` and `delete()` clear
both the per-flag key and the `context_feature_flags` dict used by templates, so
a toggle in the admin takes effect immediately and Python and templates cannot
disagree about a flag. The TTL is a backstop for writes that bypass the ORM.

Cached lookups are still recorded for the panel (source reads `… (cached)`), so
the count stays visible.

## 7. Fixes to dev mode itself

- **Flag rows are deduped with a count.** A nav template consults the same flag a
  dozen times per render; twelve identical rows tell you nothing.
- **Template-gated flags are recorded.** Covered in v3.17.0's post-release notes;
  restated because it pairs with the caching above.

## Tests — `src/test_dev_mode.py`, 91 tests

New this release: stack capture and project-path filtering, table extraction,
the shape classifier across five verdicts, duplicate groups carrying origins,
the flag cache (repeat lookups, cold lookup, fail-open, invalidation on save and
delete, template-dict busting, still-recorded-when-cached), the capability
summary, the deferred-profile backend (profile columns absent from the session
load, authz columns still present, deferred fields still readable, every deferred
name exists on the model), and **query-budget tests on both legislation pages**.

The budget tests assert *growth*, not a fixed number: doubling the legislation
must add no queries. A fixed budget would only measure how many queries the
middleware and context processors happen to make on a cold request.
