## 🟠 The education dashboard's "Add Meeting" button — and every other chair control on the page — was silently dead in production

Root cause: prod's Content-Security-Policy (`src/middleware/security.py`) is
`script-src 'self' 'nonce-…'` with **no `'unsafe-inline'`**, and has been
since v3.15.9. That blocks every inline event handler *attribute*
(`onclick=`, `onchange=`, `onsubmit=`) outright — a per-request nonce only
ever covers a `<script>` element's own content, never an attribute on some
other tag, even one that calls a function the nonced script defines. Dev
sends no CSP header at all, so this class of bug is invisible until someone
clicks the button in production. `src/tests/guards/test_csp_templates.py`
already existed to catch exactly this shape of bug for `<script>` tags — it
just never checked for inline attributes, only for scripts missing a nonce.

The "Add Meeting" button (`templates/committee/education.html`) was
`<button onclick="document.getElementById('addMeetingModal').classList
.remove('hidden')">` — blocked, so clicking it did precisely nothing, which
is exactly what was reported. Tracing the one button found the same defect
on **every other interactive control on the page**, none of which had been
separately reported yet:

- The "Add Meeting", "Add Task", and both "Restrict a page" modal-open
  buttons (`onclick`).
- Every task-row action a chair has: publish, duplicate, delete, and the
  entire pledge-completion grid (`onclick`, one per cell).
- Both education page-restriction controls: the per-phase checkboxes
  (`onchange`) and the delete-restriction button (`onclick`).
- The three "Activation" radio buttons in the Add Task modal (`onchange`).
- The "Add Task"/"Add Meeting"/"Restrict a Page" **modal shell's own X and
  Cancel buttons** (`components/modal_open.html` / `modal_close.html`,
  shared by all three modals on this page) — so even a modal that somehow
  did open could not be closed except by refreshing.
- The meeting **edit** page's Delete button and its confirm dialog
  (`templates/committee/education_meeting_form.html`).

None of this is new damage — `script-src` has had no `'unsafe-inline'`
since v3.15.9 (07-23-26), and the education dashboard (v3.20.0) and its
modal shell (v3.21.0) were both built after that, using `onclick` the whole
time. It simply never got exercised against the CSP header until now,
because dev never sends one.

### The fix

Two layers, matching how general vs. page-specific each control is:

1. **`templates/base.html`** — one delegated `click` listener, present on
   every page via the layout everyone extends, handling `data-modal-open`
   and `data-modal-close` attributes with a plain `classList` toggle
   (exactly what the `onclick` used to do — no new behavior). This is the
   general fix for the shared modal shell: `components/modal_open.html`'s X
   button and `components/modal_close.html`'s Cancel button now carry
   `data-modal-close="{{ modal_id }}"` instead of `onclick`, so **any**
   current or future page using this component pair is covered, not just
   this one. Deliberately not routed through the existing
   `window.ParliamentModal` module — that requires `.init(modalId, …)` to
   have registered the modal first, or `.open()`/`.close()` silently
   no-op, which is the identical "does nothing" failure mode being removed
   here.
2. **`templates/committee/education.html`** and **`education_meeting_form
   .html`** — page-specific `data-action="…"` attributes (plus whatever
   values each handler needs: `data-task-pk`, `data-pledge-pk`,
   `data-url-name`, etc.) read by delegated `click`/`change`/`submit`
   listeners added to each page's own already-nonced `<script>` block.
   Delegation rather than one `addEventListener` per element because most
   of these actions are followed by a full page reload (see e.g.
   `duplicateTask`, `deleteTask`) — a per-element listener would need
   re-attaching after every one of those; delegation on `document` never
   does.

No function bodies changed (`publishTask`, `toggleCompletion`,
`updateRestriction`, etc. are untouched) — only how they get invoked.

### Regression coverage

- **`src/tests/guards/test_csp_templates.py`** — new
  `NoInlineEventHandlerAttributesTests`, the general, source-scanning guard
  for this bug class going forward (mirrors the existing nonce-check in the
  same file). Scoped as a **ratchet**
  (`KNOWN_INLINE_HANDLER_OFFENDERS`, pinned at 18): fixing all four files
  above was the direct blast radius of the reported bug, but a repo-wide
  sweep found **18 more templates** with the same defect that this release
  does **not** touch — `templates/base.html` itself among them (the
  chat-unread "mark all read" × button, `dismissChatUnread(event)` —
  broken on every page that has unread chats). Full list is in the test
  file. Nothing new may be added to it, and it may only shrink; worth a
  dedicated follow-up sweep if you want it, flagged rather than done here
  to keep this release scoped to what was reported. The detector is
  tag-scoped (`<tag ... onclick=`) specifically so it doesn't flag its own
  explanatory prose or a legitimate `el.onclick = fn` JS-side assignment —
  both tripped a naive substring search while writing this.
- **`src/tests/education/test_education_dashboard_button_wiring.py`**
  (new, 7 tests) — output-level checks in the same spirit as
  `test_modal_component.py`'s `EverySubmitButtonBelongsToAFormTests`
  ("a scanner approximates; a request does not"): renders the real
  dashboard and meeting-edit pages as a chair and asserts no inline
  handler survived, the Add Meeting/Add Task/Restrict-a-page buttons carry
  the right `data-modal-open` value, every modal on the page has a
  `data-modal-close` button, a non-chair still sees none of it, and the
  meeting-edit Delete button/form are wired by id.

All new tests green on sqlite. Re-ran the full `src.tests.education` (194
tests) and `src.tests.guards` (217 tests) suites — both clean, confirming
the rewiring changed nothing about what the page does, only how the click
reaches it. `manage.py check` and `makemigrations --check --dry-run` clean
(no migration, as expected for a template/JS-only change).
