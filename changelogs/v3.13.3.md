# v3.13.3 — Vote confirmation with passkeys + vote-page reliability fixes

**Date:** 07-15-26
**Type:** Feature + bug-fix batch
**Deployed:** 07-15-26 (together with v3.13.0–v3.13.2)

## Feature: confirm votes with a passkey

Members with a registered passkey can now confirm any vote (chapter, committee,
slating slate + individual) with Touch ID / Face ID / hardware key instead of
retyping their password.

**How it works**
- Two new endpoints in `src/view/webauthn.py`:
  `passkey_reauth_begin` / `passkey_reauth_complete`
  (`/accounts/passkeys/reauth/begin|complete/`). Both `login_required`.
  `begin` scopes `allow_credentials` to the current user's keys (same pattern
  as admin-v2's passkey step); `complete` verifies the assertion — the
  credential **must belong to the logged-in user** — and stamps a **one-shot,
  2-minute** grant in the session.
- `check_vote_reauth(request)` is the single identity gate used by all four
  vote views: consumes the passkey grant when `auth_method=passkey`, otherwise
  falls back to `check_password`. One grant = one vote POST (popped on use).
- Failed passkey attempts are rate-limited (5/15 min, same bucket family as the
  v3.13.2 credential re-auth). **Password confirmation on votes is now also
  rate-limited** (10/15 min per user — laxer so meeting-time typos don't lock
  anyone out; previously vote forms allowed unlimited password guessing).
- Frontend: shared include `templates/components/vote_passkey_confirm.html`
  wires every `.js-vote-passkey` button; "Confirm with a passkey instead"
  renders only when the user has passkeys (`has_passkeys` context var).

## Bug fixes (the "vote page barely works" batch)

1. **Votes no longer vanish silently.** A vote POST that failed the `can_vote`
   gate (attendance older than 3 h, stale page, non-voting member type) was
   silently ignored — page re-rendered, no message, no vote. Now returns an
   explicit error telling the member why and what to do (chapter + committee).
2. **No-selection submits now get feedback.** Radios weren't `required` and a
   POST without `vote_choice` didn't even reach the vote handler. Now: radios
   are `required`, the form always sends `action=cast_vote` so the server
   responds with a proper error, and shared JS blocks empty submits client-side.
3. **Double-submit guard.** Chapter/slating forms had no protection against
   double-clicks (no unique constraint on Vote either — multi-select plurality
   rules one out) → duplicate ballots were possible. Shared JS now disables the
   submit button once a valid submit is in flight. Multi-select vote creation
   is also wrapped in `transaction.atomic()` so a mid-loop failure can't record
   a partial ballot.
4. **Committee voting: 'late' members can now vote** (parity with chapter
   voting) — the filter used the legacy `present` boolean, which is False for
   status='late'.
5. **Legacy `Attendance.present` sync fixed.** `Attendance.save()` syncs
   `present` from `status`, but saves with `update_fields` (which
   `update_or_create()` — the quick-attendance panel path — uses since
   Django 4.2) skipped the sync, leaving `present` stale. `save()` now appends
   `present` to `update_fields`. (Heads-up: `passed_legislation.py` still
   filters `present=True` for quorum-style counts — excludes 'late' members;
   left as-is, review if that's not intended.)
6. **Legislation upload no longer fails silently** when a required field is
   missing — explicit error message instead of a quiet page re-render.
7. **Quick-attendance panel actually shows (and saves) what you clicked.**
   Three stacked bugs:
   - *Dark mode:* the JS swapped only light-mode Tailwind classes; the
     template's `dark:bg-gray-700`/`dark:text-gray-400` stayed on the buttons
     and overrode the new state — clicks appeared to do nothing.
   - *Light mode:* the just-clicked button kept its `hover:bg-*-100` classes,
     and since the cursor is still on it, the pale hover tint overrode the
     solid active color — "absent grays out but nothing else happens". The
     class sets now include the dark/hover variants (all already in the
     compiled CSS — no Tailwind rebuild needed).
   - *Saving:* the POST was fire-and-forget, so server errors left the panel
     showing unsaved state until reload. The endpoint now returns JSON, the JS
     checks it and reverts + alerts on failure. Also healed a poison-pill
     race: two rapid clicks could create duplicate Attendance rows (no unique
     constraint), after which `update_or_create` raised MultipleObjectsReturned
     forever and the panel silently stopped saving for that member. Duplicates
     are now detected and collapsed. Bonus: each click no longer renders the
     entire vote page server-side (was a redirect, now lightweight JSON).

## General checkup findings (chapter + committee vote integrations)

**8. The `Legislation.status` field was defined TWICE in the model** — the
second definition (`default='draft'`) silently shadowed the first
(`default='pending'`), so every legislation ever created has status
`'draft'`, which wasn't even in `STATUS_CHOICES`. The vote page only worked
by accident ('draft' isn't in its exclude list). Fixed: duplicate removed,
`'draft'` is now an official choice (the "open" status — matching what
admin-v2 and the committee model already assumed). Migration `0005` is
**state-only** (no database operation). Fallout fixed with it:

- **Home page "pending votes" widget + "active legislation" stat were
  permanently empty** — they filtered `status='active'`, which nothing ever
  sets. Now use the same open-voting semantics as the vote page.
- **`/api/v1/legislation/active` always returned `[]`** — same cause, same fix.
- **Scheduled vote reminders never fired** (`tasks/notifications.py`
  `vote_reminder` filtered `status='active'`). Filter dropped; the
  voting_closed/voting_ends_at bounds do the work.
- **Failed votes vanished from the history page** — `end_vote` marked them
  `'removed'`, which `passed_legislation.py` excludes from *every* tab. Failed
  votes are now marked `'failed'` (and the `passed` bool is set — the old
  `set_passed()` call was commented out); 'removed' is reserved for admin
  removal. ⚠️ Behavior note: failed legislation now *appears* in the history
  Failed tab — confirm that's wanted.
- **Reopening legislation was broken** — it cleared `voting_closed` but left
  status `'passed'`/`'removed'`, which the vote page excludes, so reopened
  votes never reappeared. Reopen now resets status to `'draft'` and clears
  `voting_ended_at`.
- Health-check queries in `tasks/notifications.py` updated to treat
  `'draft'` as an open status.

**Reviewed, no action:** committee end-vote/recalculate (permissions and
tally math correct, consistently uses 'draft'), `delete_chapter_legislation`
(authz correct), `create_runoff` (correct), committee push-to-chapter
(correct), all 7 modified templates parse cleanly.

**Known follow-ups (not changed):**
- `Event.visible_to` is still a Postgres `ArrayField` — the **home page
  cannot render on sqlite dev** (`__contains` lookup). Candidate for the same
  JSONField swap as `plurality_options` (JSONField `__contains` works on
  sqlite); needs its own migration + a sweep of `visible_to` queries.
- `legislation_detail` is viewable by any logged-in member for any
  legislation, including scheduled/not-yet-available items (minor info leak).
- `end_vote` runs one `.count()` per plurality option (twice) — one-time
  action, not worth optimizing now.

## Crossover check: Legislation page + My Work vs vote page

**9. 🔴 `PassedLegislationDetailView` had NO login check** — the function
views in that file use `@login_required`, but the class-based detail view had
no mixin (and there's no global login middleware), so
`/legislation/detail/<pk>/` — vote results, **individual voter names and
choices**, present-members list — was publicly accessible. `LoginRequiredMixin`
added.

**10. Legislation page Active/Pending tabs missed most legislation** — both
tab filters keyed on `voting_starts_at`, but most legislation has it NULL
(the vote-page upload and committee push don't set it; voting then implicitly
starts at `available_at`), and NULL fails both `__gt` and `__lte`. Each
branch now falls back to `available_at`.

**11. Pending tab leaked scheduled legislation** — the vote page promises
scheduled items are "not yet visible to others," but the Legislation page's
Pending tab showed them to every member. Pre-available items are now
author-only there.

**12. Present-members lists** used the legacy `present` bool (missed 'late'
members who legitimately voted) and postgres-only `DISTINCT ON`, which made
the whole Legislation page un-renderable on sqlite dev once any closed vote
had ballots. Replaced with a shared status-based helper + Python dedupe.

My Work (`view_legislation_history`) tab filters verified compatible with
the new status lifecycle (open='draft', failed='failed'); both templates'
status badges fall through to sensible defaults for 'draft'. (Perf note: My
Work still runs 4 count queries per item — small N, left alone.)

## Vote open-timing ("it doesn't open on its own")

**13. The vote page never revealed newly-opened votes.** The 15-second
poller (a) didn't run at all unless the page had author tally widgets — i.e.
never for regular members — and (b) only reacted to votes *closing*. So when
`available_at`/`voting_starts_at` passed while people were on the page,
nothing appeared until a manual refresh — at any offset, which is exactly
"it never opens on time." Fixed: `vote_tally_json` now returns
`votable_ids` (open votes from the current user's perspective), the poller
runs for everyone and reloads when that set changes — unless the user is
mid-ballot, in which case a "Refresh" banner shows instead of yanking the
page.

**14. Appointment votes were stored with UTC-skewed times** —
`upload_legislation.py` never called `make_aware()`, and the DB layer
interprets naive datetimes as UTC, so appointment-vote open times were off
by the UTC offset (5-6 h for America/Chicago). Same fix applied to
`mark_voted_date` in edit_legislation. (The chapter upload path already
converted correctly — verified end-to-end by new tests that POST real
datetime-local strings and assert immediate/scheduled opening.)

⚠️ **Deploy check:** `TIME_ZONE` is env-driven (`settings.py` defaults to
`America/Chicago`). Verify prod's `.env` doesn't override it to UTC — that
would skew every entered time by 5-6 hours and reproduce "opens at the wrong
time" even after these fixes.

## Feature: "Now" buttons for opening legislation

**15.** Two ways to skip the timestamp fiddling:
- **Upload forms:** a "Now" link next to *Available At* and *Voting Starts*
  (chapter form) and *Available At* (appointment form) fills the field with
  the current local time.
- **Legislation cards (author/admin):** *Open Voting Now* appears on any card
  whose voting hasn't started — one click makes it available and starts
  voting immediately. *Show Now* appears on scheduled cards that also have a
  separate scheduled voting start — it reveals the document now but keeps the
  scheduled voting time. Endpoint: `POST /vote/open-now/<id>/` (author or
  admin, refuses closed votes). Everyone else's page picks the change up
  within one poll cycle via the votable_ids reload from fix 13.

**16. Document now optional on the vote-page upload with a detailed
description** (20+ characters — same rule the legislation tracker's add form
already had), with a visible tip on both forms and live `required` toggling
client-side. Plurality votes still never need a document.

**17. Upload confirmation now echoes the parsed schedule** — "Legislation
uploaded — visible now · voting opens Jul 20 at 07:30 PM" — so any
clock/timezone mismatch between what was typed and what the server understood
is visible at submit time instead of surfacing later as "it opened at the
wrong time". (Render-level tests confirm a future available_at with a blank
voting-starts renders as scheduled — banner, no vote form, hidden from
members. Reminder: blank "Voting Starts" means voting opens when the document
becomes available, per the form help text.)

**18. Voting start can now be fully separate from availability.** New toggle
on the upload form — "Open voting as soon as the document is available"
(checked by default = historical behavior). Unchecking it reveals the Voting
Starts field: set a time for a scheduled start, or **leave it blank to open
voting yourself later with "Open Voting Now"** (new `voting_manual_open`
flag, migration `0006`). While waiting, members see the document with a
"Voting hasn't been opened yet" banner; the item counts as *Pending* (not
Active) on the Legislation page, stays out of the home pending-votes widget
and `/api/v1/legislation/active`, and everyone's page auto-reloads when the
author opens it. Forms that don't send the toggle (committee push-to-chapter,
appointment form, older clients) keep unified behavior — the flag defaults
to False.
