Mason: "The docx page handler, on desktop, does not show images from the
document. Can we add that so it will show images instead of just the text
and whatnot?"

## There was never an "images disabled" switch to flip

`convert_docx_to_html()` (`src/view/view_document.py`) calls
`mammoth.convert_to_html()` with no custom `convert_image` argument.
mammoth's own default for that case — `mammoth.images.data_uri` — already
embeds every image straight into the HTML as
`<img src="data:{content_type};base64,{data}">`. Confirmed directly against
mammoth's source (`conversion.py`: `if convert_image is None: convert_image
= images.data_uri`). So mammoth was never the problem, and there was no
missing feature to add on that side.

The image was disappearing one step later. `bleach.clean()`'s default
`protocols` allowlist is `{http, https, mailto}` — `data` isn't in it — and
bleach treats `src` as a URI attribute needing protocol validation
regardless of which tag it's on. Reproduced directly:

```python
>>> bleach.clean('<img src="data:image/png;base64,iVBOR...">', tags=['img'], attributes={'img': ['src']})
'<img>'
```

The `<img>` tag survived sanitization (it's in `_DOCX_ALLOWED_TAGS`, `src`
is in `_DOCX_ALLOWED_ATTRS['img']`) — just with its `src` silently dropped,
leaving nothing to render. That's the actual bug: not a missing feature, a
sanitizer stripping the one attribute that made the feature work.

## Fix

`_DOCX_ALLOWED_PROTOCOLS` (`src/view/view_document.py`) widens bleach's
`protocols` to `{http, https, mailto, data}`, passed into the existing
`bleach.clean()` call.

Widening it isn't free: bleach's protocol allowlist isn't scoped per
tag/attribute, so allowing `data:` for `img[src]` also allows it for
`a[href]` — reproduced directly, a `data:text/html;base64,<script>...`
`href` survives bleach.clean() unchanged once `data` is in the allowlist.
New `_sanitize_docx_html_images()` runs immediately after `bleach.clean()`
and closes that back up:

- any `href="data:...` is stripped outright — a link in a docx has no
  legitimate reason to be a data URI, so this attribute simply never gets
  the widened allowance.
- any `img[src]="data:...` is only kept if it matches
  `data:image/<type>;base64,<data>` exactly. This guards against a docx
  image *part* whose declared content-type has been changed to something
  else (e.g. `text/html`) — the src is dropped and the `alt` text is left
  as a fallback, the same graceful-degradation behavior this file already
  uses elsewhere (unpreviewable DOCX, unreadable text file, etc.).

`import re` and `import bleach` moved to module level (previously imported
inside the function body) since both are now needed at module load time for
the new module-level constants (`_DOCX_ALLOWED_PROTOCOLS`,
`_DOCX_IMAGE_DATA_URI_RE`). Neither is a new dependency — `bleach` is
already pinned in `requirements.txt` and was already imported (locally)
by this exact function; `re` is stdlib.

## New tests

`src/tests/documents/test_docx_image_preview.py` (16 tests):

- `ConvertDocxToHtmlIncludesImagesTests` — builds a real, minimal `.docx`
  (hand-assembled as a zip of OOXML parts, no `python-docx` dependency
  needed at runtime) with one embedded PNG and runs it through the actual
  `convert_docx_to_html()` used in production — not a mocked mammoth or a
  synthetic HTML string. Confirms the image survives with its exact base64
  payload intact and the surrounding paragraph text is untouched.
- **Negative control included in the same test class**: runs the *pre-fix*
  bleach defaults (`protocols` unset) against the identical real fixture
  and asserts the `src` really is stripped — confirms the fixture is
  capable of catching this regression, not just capable of passing.
- `DocxImageProtocolIsScopedToImagesOnlyTests` — the security half: a
  `data:` href is stripped, an ordinary `https://` href is untouched, a
  valid image data URI in `img[src]` is kept byte-for-byte, and an `img[src]`
  relabeled as `data:text/html` is stripped down to just its `alt` text.
  One test exercises the full `bleach.clean()` →
  `_sanitize_docx_html_images()` sequence end-to-end (not just the second
  function in isolation) against a `data:text/html` link and confirms
  neither the `data:` payload nor a `<script` tag survives.
