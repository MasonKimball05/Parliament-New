## 🟠 Two buttons that did nothing: "Approve & excuse" and "Save Attendance"

**Found by:** the 10-04-26 auto-run, following up the open question from the
10-02 session ("check whether the double-submit guard breaks other forms that
depend on a submit button's name").

### Cause
`base.html`'s double-submit guard disabled the form's **first** submit button
inside the `submit` event. The browser builds the POST after that event and
leaves disabled controls out, so when the first button carries `name=` and
`value=`, the server never sees them. This is the same cause as the v3.41.2
resolution Save button (fixed there with a hidden input). The guard dates
from v2.6.0 (02-03-26).

### What it broke
| Page | Button | What happened |
|---|---|---|
| Education dashboard, absence requests | **Approve & excuse** | 400 "Unknown decision". The request stayed pending. "Deny" worked. |
| Service event attendance | **Save Attendance** | Nothing saved, page reloaded with no message. "Finalize & Apply Hours" worked (and saves). |

Three other forms have a named first button but were unaffected, because the
view's default is that button's value: agenda item Save, recruitment RSVP
"Going", slating application "Save draft".

### Fix
- The guard disables the button with `setTimeout(..., 0)`, after the browser
  has collected the form data. A second submit in between is still blocked by
  the guard's `WeakSet`.
- It now acts on the button that was pressed (`e.submitter`), so "Deny" shows
  its own spinner instead of putting one on "Approve". Falls back to the first
  submit button when there is no submitter.

### Verified
- Chromium, with the script lifted from `base.html` and an echo server:
  before, Approve posted `review_note=x`; after, `review_note=x&decision=approved`.
  Deny, Enter-key submit, and four rapid clicks (one POST) also checked.
- Not checked in Safari or Firefox. The HTML spec gives the same behaviour.
- Not driven against the real pages with a signed-in session.
