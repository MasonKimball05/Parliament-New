## Why v3.28.4 didn't fully cover this

v3.28.4's two mechanisms — the silent in-place token refresh on a
bfcache restore with unsaved input, and a submit-time safety net — both
key off exactly one signal: **is the `csrfmiddlewaretoken` field empty
(or missing)**. That was correct for the 09-01 reproduction, whose CSRF
log line recorded `posted_token_present=False` — the field was genuinely
absent from the POST body.

But a field can also be **present with a value that no longer matches**
the `csrftoken` cookie behind it. Django reports that as "CSRF token
incorrect" — a different `reason` string than "missing" — and the safety
net's `if (tokenField && tokenField.value) return;` treats any non-empty
value as "nothing to do," so a stale-but-present token sails straight
through untouched.

`upload_document.html` (and the ~17 other templates with a file input)
is exactly the shape most likely to produce this: choosing a file opens
a native OS picker sheet (Photos, Files, the camera) that can leave the
tab backgrounded for an unpredictable stretch — long enough, on a phone
someone doesn't force-quit, for the session/cookie state behind an
already-rendered page to have moved on without it. Nothing about that
scenario ever clears or removes the hidden field; it just leaves it
holding a value that's gone stale. v3.28.4's checks were never written to
distrust a *present* value at all.

(Confirmed via code inspection that `refreshCsrfToken()` /
`/internal/csrf-token/` (`django.middleware.csrf.get_token`) already
returns a token valid for whatever `csrftoken` cookie is *currently* on
the request — it doesn't matter whether the old value was missing or
merely wrong, a fresh call fixes either. The gap was purely in when the
safety net decided to call it.)

## Fix

One additional condition in the submit-time safety net
(`templates/base.html`): a form with a file input (`input[type="file"]`)
now refreshes the token **unconditionally** before submitting, rather
than only when the field is empty. Every other form on the site keeps
the original, cheaper empty-only check — nothing else here plausibly
backgrounds the tab the way a native file picker does, so there's no
reason to pay an extra round-trip on every ordinary POST.

```js
var hasFileInput = !!form.querySelector('input[type="file"]');
if (!hasFileInput && tokenField && tokenField.value) return;
```

If the refresh itself fails (offline, flaky mobile connection —
`refreshCsrfToken()` already catches and returns `null`), the field is
left exactly as it was and the form submits anyway — no worse than
today's behavior, since this is strictly additive on top of the existing
mechanism.

## New tests

`TheFileInputSafetyNetAlwaysRefreshesTests` in
`src/tests/security/test_bfcache_reload.py` (4 tests, extending the
existing structural-test convention for this file — `base.html` has no
JS test runner in this repo):

- the guard actually detects a file input on the form;
- the empty-only early return is gated on `!hasFileInput` — a file-input
  form cannot take the same shortcut a plain form does;
- `hasFileInput` is computed before the early-return line that reads it;
- a control: a plain form with no file input still takes the early
  return before `preventDefault()` — this is additive, not a blanket
  "always refresh everything" change.

**Negative control, run before trusting the tests**: reverted just
`templates/base.html` to the pre-fix version (`git show HEAD:...`) and
reran the new class — 2 failures + 2 errors (the ordering tests error
outright since the strings they look for don't exist yet), all four for
the documented reason. Restored the fixed version afterward, confirmed

Also updated the pre-existing
`test_a_completely_missing_field_is_created_not_skipped` (in
`TheCsrfSubmitSafetyNetExistsTests`), which pinned the exact old
condition string verbatim — now checks the tail end of the (now
three-part) condition instead, so it still asserts what it always meant
to (present-field-and-value is part of the skip condition) without

## Known, not fixed here

- Still can't confirm from this sandbox whether the live failures are
  literally "CSRF token incorrect" versus some other iOS Safari
  form-state quirk that also leaves a present-but-wrong value — no prod
  log access here. This fix is correct either way: it stops trusting a
  file-input form's token field at all and always asks the server for a
  current one immediately before submit, which closes the gap regardless
  of the exact browser mechanism, same reasoning v3.28.4 used for its own
  submit-time safety net.
- The ~40 templates that bake the CSRF token into a JS constant instead
  of reading it from the meta tag are still outside all of this
  (unchanged from v3.28.4) — the pre-existing, tracked,
  too-large-to-convert-at-once population.
