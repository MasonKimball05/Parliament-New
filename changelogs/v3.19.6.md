## 🔴 1 — `/media/` served eight more upload directories whose promise is narrower than its own

`serve_media`'s entire gate is `@login_required`. It makes exactly one promise —
*any logged-in member may read this* — and until this release eight directories
were stored under a narrower promise and served under that wider one:

| Directory | Model.field | Who the app says may read it |
|---|---|---|
| `kai_reports/` | `KaiReport.attachment` | `KaiMemberPermission` holders, submitter, accused |
| `kai_reports/custom_fields/` | `KaiReportFieldResponse.file_value` | same |
| `slating/gpa_screenshots/` | `SlatingApplication.gpa_screenshot` | slating committee |
| `slating/application_files/` | `SlatingApplicationResponse.file_value` | slating committee (`is_confidential`) |
| `excuse_documents/` | `AttendanceExcuse.supporting_document` | the member, excuse reviewers |
| `service_hours/` | `ServiceHoursSubmission.attachment` | the member, approvers |
| `service_hours/custom_fields/` | `ServiceFieldResponse.file_value` | same |
| `bug_reports/%Y/%m/` | `BugReport.screenshot` | reporter, `bug_admin_required` |

Every one of them was linked from a template as `{{ …field.url }}`, i.e.
`/media/<dir>/<name>`, and the names are `slugify()` of whatever the uploader
called the file — Django's random 7-character suffix only appears on a
*collision*. So the first upload of `IMG_4471.jpeg` was stored, and served, at
`kai_reports/img-4471.jpeg`. `/media/excuse_documents/doctors-note.pdf` is a
guess a curious member makes on the first try.

**Three things make this worse than the draft exposure it rhymes with.**

- **It crosses the standing Kai confidentiality boundary.** CLAUDE.md (07-25-26)
  unregistered all seven Kai models from `/admin/` so a superuser could not route
  around `KaiMemberPermission`, and the same disposition fixed global search
  because *"a permission-less Kai member could full-text search allegation
  bodies."* This was that same bypass one resource over, needing no committee
  membership at all — and reaching **the accused**, who has both the motive and
  the filename.
- **`excuse_documents/` is health information.** The field's own help text says
  "doctor note, etc." It was readable by every member of the chapter.
- **`/media/` is exempt from 2FA enforcement and from emergency lockdown**
  (`two_factor.py:55`, `lockdown.py:26`). Both exemptions are defensible for what
  they were written for — a 2FA-redirected `<img>` is just a broken image — and
  neither is the bug. But a password-only, TOTP-unverified session could fetch
  these, and they stayed readable during a lockdown declared *because* something
  was wrong.

### Why v3.19.5 did not catch it, which is the durable part

v3.19.5 was **right about the property and right about the mechanism**. It wrote
the rule down —

> *A new upload directory inherits `/media/`'s promise by default. If that is the
> wrong promise, it belongs here AND needs its own ownership-aware view.*

— built `PRIVATE_MEDIA_PREFIXES` as a **set** rather than an `if`, checked it on
the resolved path, covered X-Accel mode, chose 404 over 403, and wrote a test
asserting every entry has a replacement route. Then it put **one** entry in it and
called `legislation_drafts/` *"the first such thing in this codebase."*

It was the ninth. Nothing had ever **enumerated the population the set is drawn
from** — a `grep` for `FileField` that takes four minutes.

> **Building the general mechanism is not applying it to the general case. A set
> is only the general form if something enumerates the population; otherwise it is
> an `if` with better manners.**

Note that `test_the_private_set_names_only_directories_that_have_their_own_view`
could not have caught this: it guards entries that are **in** the set and is
structurally blind to a directory that was never added — the same shape, one level
up, as the template `grep` that closed the v3.19.3 finding prematurely.

### The fix, in the order it has to happen

1. **`src/test_media_classification.py` — the enumeration, written first.** Walks
   `apps.get_models()`, takes every `FileField`/`ImageField`'s `upload_to` first
   segment, and requires each to appear in `PUBLIC_MEDIA_PREFIXES` or
   `PRIVATE_MEDIA_PREFIXES`. A new model with an unclassified `upload_to` fails
   the build with a message that states the decision. Also asserts the two sets
   are disjoint, that neither contains a prefix no model writes to any more
   (the `perf_sampled_count` defect class, recorded twice in CLAUDE.md), that the
   hand-maintained callable map has no stale entries, and — the one that matters —
   that `serve_media` **actually refuses** every private prefix at request time,
   with a real file present so a 404 proves the guard fired rather than proving
   the file was missing.
2. **`src/view/serve_private_upload.py` — eight ownership-aware views.** Each
   re-uses the predicate its host page already applies. **The same object, not a
   copy:** `_user_may_read_kai_report` calls `_get_kai_access` narrowed by
   `_case_access` (so recusal applies), the slating views call `_user_can_view`
   and `_period_is_locked`, and `officer_required`/`vpp_required`'s predicates
   were extracted so the file and the page share one rule. All 404 rather than
   403, matching `_get_own_draft`, because whether a record exists is itself
   confidential. `Cache-Control: no-store`.
3. **`PUBLIC_MEDIA_PREFIXES` / `PRIVATE_MEDIA_PREFIXES` populated, 16 template
   links repointed to `{% url %}`.** Adding a prefix before its view exists would
   make the files unreachable by anyone, which looks exactly like the fix working;
   `test_serve_media.py`'s `expected` map is the guard and is updated, not
   loosened.
4. **Migration `0017` — uuid `upload_to` for the four confidential directories.**
   Defence in depth *underneath* the views, explicitly not the access control.
   `AlterField` only: existing files keep their slugified names, so this stops the
   guessable population growing and does not retire it. **`0016` made the same
   call on reasoning that turned out to be false for two days** (its route was
   still open); it is true here because the access controls land in the same
   release. If any of step 2 or 3 is reverted, this migration's premise goes with
   it.

### Three more leak sites the template grep did not reach

The 08-10 report found the templates. Running `grep` over `src/` as well found
four more references that would also have become dead links:

- **`kai_user_dashboard.user_kai_report_attachment` checked access and then gave
  it away.** It scoped the report to `Q(submitted_by=user) | Q(targeted_to=user)`
  — correct, careful — and then `return redirect(report.attachment.url)`, handing
  the browser `/media/kai_reports/<slug>.pdf`. Anyone could request that URL
  directly and never touch the view. Its docstring said *"This ensures users can
  only access their own report attachments."* **A permission check that ends in a
  redirect to an unauthenticated URL is not a permission check; the redirect
  target is the real access control.** It was never routed — `urls.py` imports
  five names from that module and this is not one — so it was a landmine rather
  than a live hole. Kept, delegating to the streaming view, so wiring it up is now
  safe.
- **`officer/event_attendance.py:196`** put `excuse.supporting_document.url` into
  the mark-attendance context. Now `reverse('excuse_document', …)`.
- **`get_display_value()` on all three custom-field models returned `.url`.** The
  only consumer renders it as **text** beside the download link, so the raw
  storage path was being printed to the page. Now the basename — a display value
  is a thing to show a human; the link belongs in an `{% url %}` tag.

## 🟡 2 — the buffer budget was a total that everything around it called per-entry

**Fourth release on this one condition, and the failure changed shape.** The first
three were wrong about the *world* — always true, always true, never true. This one
was wrong about *itself*.

`buffer_is_over_budget` compared `buffer_bytes > MAX_STORED * BYTES_PER_ENTRY_BUDGET`,
a fixed 96,000-byte total, while three places described it as per-entry: the
constant's own comment, the recommendation string (`"N B/entry vs a 192 B budget"`),
and a test docstring. So the answer depended on **occupancy**, not on cost.
Measured 08-10-26, entries of 200-character paths, all at 248 B/entry — 29 % over
the stated budget:

```
500 entries  123,980 B  fires
400 entries   99,180 B  fires
387 entries   95,956 B  SILENT   ← 77 % occupancy
200 entries   49,571 B  SILENT
100 entries   24,771 B  SILENT
```

A partial buffer is not exotic: `CACHE_TTL` is 25 h and sampling is 1-in-20, so
filling 500 slots takes ~10,000 non-slow requests — and `memory_report` is run
*after* someone notices something, often after a restart.

**The test written to prevent exactly this asserted the inverse and passed because
of the bug.** `test_the_budget_is_relative_to_the_bound_it_is_about` fed ten
entries of 2 KB paths (~2,063 B/entry, tenfold over budget) and asserted
`assertFalse(over)` on the reasoning *"ten entries cannot exceed a budget expressed
per entry, whatever they contain."* Against a real per-entry budget, ten entries of
2 KB paths are precisely what does exceed it.

Now genuinely per-entry, with `MIN_ENTRIES_FOR_BUDGET = 50` as an explicit floor
in place of the accidental `MAX_STORED / len(entries)` factor. Three new tests:
a cold process does not trip it, the answer is the same at 50/100/200/387/500 for
the same per-entry cost, and a buffer under budget is never flagged at any size.

> **The rule, and it is the mirror of v3.19.4's rather than the same one:** after
> asking what the world looks like on both sides of a threshold, **check that the
> sentence you print describes the comparison you made.** Three correct
> descriptions of a check that did something else is not a typo — it is what a
> threshold looks like when nobody has run it.

## 🟡 3 — the suppressed `FORGED_CF_HEADER` count still could not survive a burst that ends

v3.19.5 took the 08-09 report's suggested fix verbatim — `FORGED_CF_COUNT_TTL =
FORGED_CF_LOG_WINDOW * 4` — **and the suggestion was the incomplete one.** Trace a
sweep of 10,000 hits between t=0 and t=60, then silence: the first hit logs a line
with no count, hits 2–10,000 build a tally, nothing reads it, and at t≈1262 it
expires. The operator sees one line, no number. A longer TTL widens the window in
which a *rescue hit* can carry the tally; it does not remove the dependence on one
arriving.

`test_the_count_survives_a_burst_that_stops` passes because its last line sends one
more probe. That probe is the rescue hit.

> **A tally flushed only by the next event cannot report the last event.**
> The flush has to be on the write side.

Added `FORGED_CF_COUNT_MILESTONES = {10, 100, 1000, 10000}`: the suppressed count
logs itself when it crosses a power of ten. Self-limiting (≤4 extra lines per peer
per burst), no scheduler, and the volume is visible without waiting. The throttle's
real property — one *throttled* line per peer per window — is unchanged and still
asserted exactly; the tests now split the two kinds of line rather than loosening
`call_count` to "a few".

**One of those is worth calling out as its own finding.**
`test_the_suppression_suffix_does_not_claim_a_window_it_cannot_know` **has never
passed.** `git log -S` puts the assertion and the string it checks in the same
commit, `b7c80be`: v3.19.5 changed the suffix to *"since the last line"* and added
`assertNotIn('last ', suffix)`, which that string contains. Its intent was right —
don't state a duration you cannot vouch for — and "since the last line" names an

duration. **A test committed in the same breath as the code it contradicts is what
seven unrun batches buys you**, and it is the cheapest possible argument for
running them.

addressed here** — they are pre-existing, outside this batch, and belong in their
