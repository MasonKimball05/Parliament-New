## Committee dashboard quick links

New `committee_dashboard_links(user)` in `src/view/home.py`, called from
`home()` and rendered on both home layouts. Shows a link to the Kai,
Service Hours, Recruitment, or Education committee dashboard **only when
the viewer actually has access to that specific dashboard** — a link to
a 403/404 is worse than no link. Slating already had its own equivalent
(`has_slating_access`) and isn't duplicated.

Each link replicates its dashboard's own access predicate exactly,
because the four are gated four different ways:
- **Kai** — `@require_feature_flag('kai_reports')` +
  `_get_kai_access(user, committee)['can_view_report_list']`, same as
  `view_kai_reports` itself.
- **Service Hours** — admin or a member holding the VPP role, same as
  `@vpp_required`. Not committee-based; there's no "service committee"
  model concept.
- **Recruitment** — chair, admin, member, advisor, or holder of the
  committee's linked Role, same as `recruitment_dashboard`'s own
  `_user_access()`.
- **Education** — chair or officer, same as
  `_education_committee_or_404()`.

Recruitment and Education also respect the `committee_home` page toggle
both their own views gate on, checked once rather than per-committee.

⚠️ **Query budget**: this adds 6 flat (non-scaling) queries to the home
page — confirmed via `HomePageQueryBudgetTests`, which still passes its
"does not scale with committee count" check. `BUDGET` in
`test_query_budgets.py` raised 41 → 47 with the reasoning recorded there.

New `src/tests/committees/test_committee_dashboard_links.py` (18 tests):
one class per dashboard, each testing that the link appears for someone
with access and not for someone without — chair, permission-grant
holder, plain member, advisor, role holder, officer, and inactive/
missing committee edge cases.

## Recruitment "Assignments" tab

Requested because the existing "Candidates" tab has an Assigned To
column but answering "how many prospects does each of us have" meant
scrolling and counting by eye. New tab groups candidates by assignee —
one card per committee member with at least one candidate, plus an
"Unassigned" card (sorted last, regardless of size) for anyone with
none.

`_group_candidates_by_assignee()` in `src/view/committee/recruitment.py`
takes the candidates queryset `recruitment_dashboard` already builds
(`select_related('assigned_to')`) and groups it in Python — no second
query. `recruitment_dashboard` now evaluates that queryset once
(`list(candidates)`) before grouping, so the flat "Candidates" tab reads
from the same cached result rather than re-querying.

New `src/tests/committees/test_recruitment_dashboard.py` — unit tests on
the pure grouping function (groups by assignee, unassigned gets its own
group and sorts last even when largest, alphabetical ordering, empty
input) plus tests through the real view (tab renders, context is
grouped correctly, a member without private access gets no grouped
data).

### 🟠 Found along the way: the dashboard 500'd for every non-privileged member with any past event, always

While writing the Assignments tests, a plain committee member loading
the dashboard hit `TypeError: Cannot filter a query once a slice has
been taken`. `past` was built with `[:20]` already applied, and then —
only for non-privileged members — `.filter(visibility='public')` was
called on the now-sliced queryset. Django raises immediately on that,
regardless of whether there was any private past event to actually
filter out. **Every non-privileged member of every recruitment
committee has been getting a 500 on this dashboard whenever a past
event existed**, unrelated to anything in this release — just never
caught because nothing exercised the dashboard as a non-privileged
member with past events until this feature needed that exact fixture.

Fixed by moving the `[:20]` slice to after the visibility filter. New
`NonPrivilegedMemberPastEventsRegressionTests` (in the same test file);
confirmed it fails against the pre-fix code via a scratch-copy negative
control (real repo file untouched throughout).
