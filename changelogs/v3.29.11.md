## 🟠 N+1 on `/officers/excuses/` — 88 queries down to 35 on the measured fixture

`review_excuses` built a fresh `AttendanceExcuse.objects.filter(event=event)`
queryset per event in its loop, then ran `.exists()` plus three
`.filter(status=...).count()` calls plus a `list(...)` on top of that — six
queries per event that has any excuses. Reported live via the dev-mode
query monitor as 33x an identical `SELECT COUNT(*) ... WHERE event_id = %s
AND status = %s` shape, 11x an `.exists()` shape, and 11x the full
excuse SELECT — the chapter's page at the time had 11 events with excuses,
so 11 events × 3 status counts = 33, matching exactly.

Fixed the same way `Event.prime_attendance_stats()` already fixed the
identical class of problem on `/officers/attendance/`: one `Prefetch` pulls
every event's excuses in a single query (`to_attr='prefetched_excuses'`),
and one grouped conditional aggregate
(`.values('event_id').order_by().annotate(pending=Count(..., filter=Q(...)),
...)`) computes the whole page's pending/approved/denied/total breakdown at
once. The status filter that narrows which excuses render under each event
now runs in Python over the already-prefetched list (small per event)
rather than in SQL, while the counts stay the whole-event breakdown
regardless of the active filter — matching what the pre-fix code did,
which is easy to get backwards when moving filtering out of the query.

Measured directly against the reverted view on the same 11-event fixture:
**88 queries pre-fix, 35 post-fix** (`BUDGET = 35` in
`ReviewExcusesQueryBudgetTests`, `src/tests/guards/test_query_budgets.py`).
A second test in the same class (`test_it_does_not_scale_with_the_number_of_
events`) pins the property a single ceiling can't express — adding events
must not add queries. `src/tests/events/test_review_excuses_counts.py`
covers correctness separately: the rewrite doesn't change what an officer
actually sees (per-event counts, the status filter, events with no
matching excuse being hidden).
