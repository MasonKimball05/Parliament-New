Mason: "For some reason on the my work page the bar for passed/failed
isn't working correctly. It shows it was passed at the top, then the bar
shows it failed" — reproduced with "Cover Page and Foreword": top badge
"Passed", vote-result bar directly below it "Failed", for 17 yes (100%),
0 no, 0 abstain against a 51% threshold.

## Root cause — viewing the page was silently corrupting the DB

`view_legislation_history` (the view behind My Work) recomputed
`leg.passed` on every GET via `leg.set_passed(counts=counts)`, where
`counts` is the raw aggregate of real `Vote` rows for that bill —
captured **before** the historical-vote overlay
(`historical_yes_votes`/`historical_no_votes`/`historical_abstain_votes`)
is applied to the `yes`/`no`/`abstain` values used for display a few lines
above it.

For any bill closed through the officer "mark as voted" manual-entry tool
(`edit_legislation.py`) — which sets `status`, `passed`, and the
`historical_*` fields directly and consistently, but creates no real `Vote`
rows at all — `counts` was an empty dict. `Legislation.set_passed()`'s
percentage branch then divides by a `total` of zero and **forces
`passed = False`**, and because the value changed from what was stored, it
**saves that back to the database**:

```python
# src/models/legislation.py, set_passed(), percentage branch
if total > 0:
    yes_pct = (yes / total) * 100
    self.passed = yes_pct >= float(self.required_percentage)
else:
    self.passed = False          # ← forced, then persisted below
...
if commit and self.passed != previous:
    self.save(update_fields=['passed'])
```

The top status badge reads `legislation.status` (untouched — still
`'passed'`); the vote-result bar reads `item.passed` (the value the page's
own render loop just flipped and saved). That's the disagreement: viewing
My Work was quietly re-corrupting `passed` for exactly the bills whose
outcome was recorded historically rather than through a live vote, and it
did so again on every subsequent view.

## Fix

Removed the `set_passed()` call from `view_legislation_history`'s render
loop entirely (`src/view/view_legislation_history.py`). `Legislation.passed`
is already set correctly at every real vote-closing path — the
`auto_close_votes` management command calls `set_passed()` itself the
moment it closes a vote (with the real `counts` it just queried, so no
historical-overlay mismatch there), and `end_vote`'s "End Voting Now"
computes and sets `passed` directly. A render loop on a GET request has no
business recomputing it a third time, from a data source (`counts`) that
doesn't match what's already been resolved for display two lines above it.

This also brings `view_legislation_history` in line with its sibling,
`passed_legislation.py`, which never recomputes `passed` in its render
loop and just trusts the stored value — the pattern this page was the one
outlier from.

Confirmed safe to remove by tracing every call site of `set_passed()`:
only `auto_close_votes.py` (both chapter and committee legislation) calls
it at actual closing time; `end_vote.py` bypasses it and sets `passed`
directly; the only other call site was this page's buggy render loop.
Nothing else in the codebase relies on this view to (re)compute `passed`.
