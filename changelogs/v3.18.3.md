# v3.18.3 — The guards, and what they found

**Date:** 08-02-26
**Type:** Test infrastructure + 🟠 confidentiality fix + N+1 fixes. **No migration.**
**Deployed:** not yet.

A backlog session, not a review batch. Four carried items — a query-budget suite,
a party-safe surface test, the full-suite re-baseline, and file housekeeping —
plus the three bugs those items found within minutes of existing.

**Every fix in this release was found by something written in this release.**
That is the whole argument for the session.

## 1. 🟠 `kai_audit` had the v3.18.1 oracle in it — found by the test written to find it

**`src/kai_audit.py`, `src/test_kai_party_safe_surfaces.py` (new)**

The party-safe surface test is a generalisation: *for a viewer who is a party to
case X, the observable output of a list-shaped surface must be identical whether
or not their search term matches a field of X they may not read.* It runs that
property over a table of surfaces, each with a control proving the surface is not
simply broken.

It failed on its first run, against `src/kai_audit.py` — **written earlier the
same day, to fix the eleventh surface of this exact bug.**

`viewer_kai_identity_flags` reads *committee-level* permissions. For a reviewer
holding both identity grants it returns `(True, True)`, so `redact_kai_logs` and
`audit_search_q` did nothing at all for them — correct for every case **except
the ones they are the accused on**, where `_case_access` withdraws every
permission and the page redacts accordingly. Output redacted, input not. A
fully-permissioned reviewer who was the accused could type their own reporter's
surname into the audit-log search box and watch their own case's rows appear.

Fixed with `viewer_party_case_ids()` — the second axis, the same list
`_kai_search_q` already carries as `redacted_case_ids`. Redaction is now
**per row**, not per viewer.

> **The rule, and this is the third release to restate it: permission is not the
> only thing that redacts.** Any surface gating on committee-level Kai flags must
> also ask whether *this particular row* is one the viewer is a party to.

A subtlety worth recording: the first cut assigned to the outer
`show_submitter` / `show_accused` inside the row loop, which would have leaked
one row's recusal onto every row after it — over-redacting silently, and looking
exactly like the redaction working. Per-row locals, with a comment saying why.

The enumeration test (`test_every_kai_search_surface_is_covered_here`) also
earned its place immediately: it flagged `export_activity_logs` as a routed Kai
search surface with no party-safety coverage. Added as a test row rather than to
the covered set — **there is deliberately no skip list.**

## 2. 🟡 Four N+1s on the calendar — found by the re-baseline

**`src/view/calendar.py`, `templates/calendar.html`**

`test_url_smoke::test_no_page_repeats_a_query_shape` has been **red since
07-30-26** and nobody had run it. The full-suite re-baseline — the first complete
measurement since 07-29 — surfaced it in the first pass.

| Where | Cause |
|---|---|
| `calendar_data_api` | `AttendanceExcuse.objects.filter(event=event, …)` inside the event loop |
| `calendar_data_api` | `event.created_by.get_display_name()` in the per-event dict, never joined |
| `calendar_view` | `{{ event.created_by.get_display_name }}` in the template, never joined |
| `calendar_view` | `event.excuse_requests.all\|filter_by_user:user` in the template |

The last one is worth its own note. **`filter_by_user` is
`queryset.filter(user=user)`, and calling `.filter()` on a prefetched relation
does not read the prefetch cache** — it builds a new queryset and issues a fresh
query, once per event.

That sits directly beside a rule CLAUDE.md already records, and the two behave
oppositely: on a relation that *is* prefetched, `.count()` and `.exists()` **do**
read the cache and cost nothing (measured 07-31-26). `.filter()` does not. Same
shape of call, opposite outcome.

The view now prefetches `excuse_requests` already narrowed to `request.user` via
a filtered `Prefetch`, so the template's `.all` is both correct and free — and it
loads only this member's excuses instead of every member's, which is a small
confidentiality improvement thrown in.

Both event querysets got `created_by` + `member_defer`. The upcoming-events
queryset is the sibling that would have been missed by fixing only the obvious
one.

## 3. 🟠 51 queries on the security-alerts page — found on prod by dev mode

**`src/view/admin_v2.py`**

`security_alerts.html:114` reads `{% if alert.reviewed_by %}` and then its
display name. `manage_security_alerts` joined only `user`, so a page of reviewed
alerts cost one extra `src_parliamentuser` round trip **per alert** — 51 of them,
all 44 columns each, measured live.

What makes this one instructive rather than routine is how it hid: **the
queryset already carried `select_related` and `member_defer`.** It read as
narrowed. A half-narrowed join is indistinguishable from a finished one at a
glance, which is precisely the difference between reading code and measuring it.
Checked the two sibling `LoginAlert` querysets; neither feeds a template that
dereferences `reviewed_by`, so neither needed the same change.

Now permanently budgeted (`SecurityAlertsQueryBudgetTests`), with a scaling test
that is the direct regression test for the incident.

## 4. 🟠 `manage.py check` stayed silent about an unapplied migration

**`src/checks_kai.py`**

v3.18.2 shipped to prod without `migrate` being run. `manage.py check` reported
**no issues**, and the admin dashboard then 500'd with
`relation "src_kaibreakglassgrant" does not exist` — because `_get_kai_access`
consults the break-glass table on every Kai permission resolution, and
`redact_kai_logs` calls it from the dashboard's activity panel.

`src.W001` wrapped its queries in `except Exception: return []`, on the
reasonable grounds that a deploy guard which crashes the deploy it guards is
worse than no guard. The effect was that **the check was silent about a schema
it never queried** — the same failure it exists one level up to prevent.

New `src.W002` reports a missing relation as an out-of-date schema, with the
`migrate` hint and a note that a fresh clone can ignore it. Only genuinely
unexpected `DatabaseError`s stay quiet. Verified in both directions: fires
against an unmigrated database, silent once migrated.

**Two things worth carrying from this.** First: *the blast radius of a Kai
migration is the admin dashboard*, because Kai permission resolution is now on
that page's path — a Kai-specific problem takes out the page you would open to
diagnose it, and that is worth decoupling. Second, and more general: **a guard
that swallows exceptions reports the absence of a signal as the absence of a
problem.** That is the third instance this month, after the red CI gate nobody
read and the sixteen feature flags that gate nothing.

## 5. 🟡 Two stale tests, one of which had been testing the wrong URL for three days

**`src/test_songbook_media.py`**

`test_traversal_is_blocked` and `test_sibling_directory_is_blocked` hardcoded
`/exportable_media/…` with an **underscore**. `50ac888` standardised on hyphens
and v3.17.6 added a legacy `RedirectView`, so both requests started getting a 302
before reaching the traversal guard, and an assertion of `(404, 400)` failed on
the redirect.

**Verified this is a stale test and not a regression:** the canonical hyphen path
404s directly, and following the legacy redirect also ends at 404. Both are now
asserted — a stronger test than the original, covering the guard *and* the
redirect in front of it.

> **A hardcoded path in a test outlives the route it names.** `reverse()` would
> have failed loudly at rename time instead of sitting red in a module nobody ran.

## 6. The query budget suite

**`src/test_query_budgets.py` (new)**

Absolute per-view query ceilings, measured not chosen, for the Kai list, the
activity log and the home page. Carried since 07-29 and justified by 08-02: two
of that day's six findings were perf regressions **introduced by correctness
fixes** — the diff was about confidentiality, the reviewer was thinking about
confidentiality, and the query count was not in the diff at all. A budget puts it
there.

Three details that make it work rather than rot:

* **Cold cache, deliberately.** `cache.clear()` before each measurement.
  Otherwise a page measures ~2 queries cheaper when an earlier test warmed the
  per-user context-processor caches, and **the budget would depend on test
  ordering** — the flake that gets a suite disabled rather than debugged. Every
  number is the pessimistic first-request-after-deploy path, verified identical
  across two full runs.
* **A ratchet in both directions.** Coming in more than `STALENESS_SLACK` under
  budget is also a failure, with the new number in the message. A ceiling nobody
  lowers stops constraining anything, and the slack is where the next regression
  hides.
* **Status-code assertion first.** A 302 or a 500 costs almost no queries and
  would pass any ceiling. A green performance suite measuring redirects is worse
  than no suite.

Also asserts **flatness**: adding rows must not add queries. A fixed ceiling
alone would have absorbed the v3.18.1 activity-panel N+1 at 12 cases and only
failed at 40.

**⚠️ There is a second query-budget class**, `test_query_narrowing.QueryBudgetTests`
(v3.17.3). It is a *scaling* test for the legislation pages with no absolute
ceiling; this module is a *ratchet*. Neither supersedes the other and the
division of labour is written into both docstrings, because two files quietly
claiming the same job is the pattern this codebase keeps paying for.

## 7. The full-suite re-baseline

First complete measurement since 07-29. **50 modules, 778 tests.**

| Result | Count |
|---|---|
| PASS | 43 modules |
| FAIL | 2 modules (`test_url_smoke`, `test_songbook_media` — both fixed above) |
| Sandbox timeout | 5 modules (`test_kai_recusal`, `test_kai_page_health`, `test_pillar1`, `test_pillar3`, `test_query_narrowing`) |

The five timeouts are **sandbox limits, not failures** — each was re-run in class
batches and passed (`test_kai_recusal` 66 green, `test_kai_page_health` 22,
`test_query_narrowing` 22 across its classes). Worth knowing for next time:
`scripts/test_baseline.sh` cannot complete as a background job in the Cowork
sandbox, which reaps long-running processes; it needs driving in resumable
chunks.

## Deploy

Code-only. `git pull` → restart `parliament-gunicorn.service`. No migration, no
dependency change, no static change. **Update `DEPLOYED.md`.**

**Run `manage.py check` after deploying** — `src.W002` now tells you if the
schema is behind the code, which is the failure this release was written after.

**Spot-checks:** load `/admin-v2/security-alerts/` and confirm the "Reviewed by"
line still renders; load `/calendar/` and confirm event cards still show "Posted by
…" and any excuse status — that path changed from a per-event query to a
prefetch, and the template no longer filters.
