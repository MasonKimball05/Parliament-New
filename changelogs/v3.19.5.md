# v3.19.5 — The route the fix left open, and the number nobody re-measured

**Date:** 08-09-26
**Type:** Security + correctness batch. **No migration.**
**Committed & pushed:** 08-09-26 (`b7c80be`, "v3.19.5")
**Deployed:** *not deployed*

The 08-09-26 auto-run fix batch. **The headline finding is not in the code
v3.19.4 added — it is a v3.19.3 fix that two consecutive reports recorded as
closed and which was still open.**

That is the shape of this release: two of the four fixes below are *the second
half of a fix that already shipped*. Worth naming as a category, because it is
the sixth instance of the same thing in this codebase and the first time the
thing left outside the fix was neither a call site nor a branch:

> **A fix that moves callers onto a new path is not finished until the old path
> is closed. Verifying the new callers proves the new path works; it says
> nothing about the old one.**

## 🟠 1. `/media/legislation_drafts/<name>` was still served to any authenticated member

`src/view/serve_media.py` · `src/test_serve_media.py`

**This was reported fixed on 08-07 and again on 08-08. It was not fixed.**

v3.19.3 found that any logged-in member — a pledge included — could fetch any
other member's private legislation draft at `/media/legislation_drafts/<name>`,
because the draft *row* was author-scoped (`_get_own_draft`) and the *file* was
served by `serve_media`, whose entire gate is `@login_required`. It fixed that
correctly, twice over: a new `serve_legislation_draft_document` that goes through
the same helper as the row, and uuid storage names underneath it. Both templates
were repointed. The 08-08 review confirmed by grep that no template still
references `draft.document.url`, and closed the finding.

**Removing the link is not removing the route.** `media/<path:path>` was never
touched. It still resolves anything under `MEDIA_ROOT`, and
`legislation_drafts/` is under `MEDIA_ROOT`. So the only thing standing between
a private draft and any member who could guess a filename was the uuid — the
thing v3.19.3's own changelog calls, at four separate sites, *"defence in depth,
explicitly NOT the access control."* **The defence in depth and the access
control had swapped places, and every document in the tree said otherwise.**

Two populations made it worse than a theoretical inversion:

- **Drafts predating migration `0016`** have no uuid at all. The old `upload_to`
  was the bare string `'legislation_drafts/'`, so the stored name is
  `SanitizedFilenameMixin.get_valid_name()` of the uploaded file — deterministic,
  and usually a slug of the bill's own title.
  `/media/legislation_drafts/dues-restructuring-amendment.pdf` is a guess, not an
  attack. **`0016` deliberately declined to rename these**, on the explicit
  reasoning that "the random name was never what was protecting them" — true only
  once this fix exists, and false for the two days in between.
- **Orphaned files** (finding 2) have no row to be scoped by at all, so they were
  reachable by nothing *but* this route.

### The fix

`PRIVATE_MEDIA_PREFIXES`, a set of first path segments under `MEDIA_ROOT` that
`/media/` refuses. 404, not 403, matching `_get_own_draft` — whether a given
draft exists is itself author-private, and a 403 answers that question.

**It is a set and not an `if`, deliberately.** CLAUDE.md records five releases of
*"a rule stated correctly, a helper written to enforce it, then something left
outside the helper"* — a call site, a branch, a column, a resource, and now a
route. The instance here is one directory; the property is that **`/media/` makes
exactly one promise (*any logged-in member may read this*) and a new upload
directory inherits it by default.** A set makes the next private directory a
one-line decision that shows up in a diff.

Two details that are the difference between a guard and the appearance of one:

- **The check reads the RESOLVED path, not the request.**
  `legislation_docs/../legislation_drafts/x.pdf` has a first segment of
  `legislation_docs` and lands in the private directory. Checking the input
  rather than the value it resolves to is the same *"checked the wrong thing"*
  shape as the finding itself, so the check sits *after* the traversal guard,
  where `os.path.relpath` is guaranteed to yield a segment inside `MEDIA_ROOT`.
  Verified against ten path shapes including percent-encoded separators and the
  near-miss `legislation_drafts_public/`, which must still be served.
- **It runs before the response is built**, so the X-Accel-Redirect path — which
  hands the URI to nginx and never touches the bytes — is covered too. A guard
  placed after the response object would have leaked in accel mode and nowhere
  else, i.e. only in the configuration nobody tests locally.

`PrivateMediaDirectoriesAreNotServedHere` (7 tests) asserts the route, not the
feature: it does not construct a `LegislationDraft` at all, because an orphaned
file has no row. It includes the negative control (`legislation_docs/` still
serves — a guard that refused everything would pass every other assertion) and
**a test that every entry in the set has a named route serving it instead**,
because an entry with no replacement view is not a redaction, it is a silent
feature deletion that looks exactly like the fix working.

## 🟡 2. A draft attachment had "exactly one lifetime" only if you never edited it

`src/forms.py` · `src/test_legislation_drafts.py`

v3.19.4 gave draft attachments a single owner and covered **delete** (a
`post_delete` receiver) and **publish** (unlink the private original once the
copy is durable). Both are correct.

Between them they covered neither thing a member actually does. **Replacing** an
attachment writes a fresh uuid and overwrites the field; **clearing** it empties
the field. In both cases the previous file stays on disk with nothing in the
database naming it, ever again — the exact orphan class the release existed to
abolish, reached through the edit button instead of the delete button. The test
class asserting the property was called
`ADraftAttachmentHasExactlyOneLifetime`, and the property did not hold.

> **Enumerate the ways a reference can END, not the ways you have already written
> code for.** Delete is the one that looks like cleanup, so it is the one that
> gets cleanup written for it. Replace and clear are *edits*, and an edit does
> not look like a deletion until you ask what happened to the bytes.

### The fix

`LegislationDraftForm` captures the stored name in `__init__` and unlinks the
replaced file on commit, through the same guarded
`delete_draft_document_file` the receiver uses.

- **Captured in `__init__`, not in `save()`** — the FileField descriptor replaces
  `instance.document` in place during cleaning, so by `save()` the old name is
  gone with no record of it. This is the second instance of that ordering
  constraint in one feature (`publish_legislation_draft` reads
  `private_original` above its `atomic()` block for the same reason), so it is
  spelled out at both sites.
- **Compares stored NAMES, not `changed_data` alone.** "Changed" and "points
  somewhere else" are different questions, and only the second licenses an
  unlink. `test_editing_without_touching_the_attachment_keeps_the_file` is the
  control: every other test here passes against an implementation that unlinks on
  every save, and that one does not.
- **Only on `commit=True`.** `commit=False` is the create path, where there is no
  previous file by definition — and unlinking before the row is written would
  destroy a file the unsaved row still points at if the save then failed.
- **The form advances its own record after unlinking**, so saving the same bound
  form twice cannot schedule an unlink of the file the row now points at. There
  is a test for exactly that, because it is the way this fix would become a data
  loss bug.

Four new tests, plus the control.

## 🟡 3. The buffer threshold could not fire — and the measurement it came from was 2x too small

`src/middleware/performance.py` · `src/management/commands/memory_report.py` ·
`src/test_middleware_hot_path.py`

`memory_report`'s "the performance buffer is costing too much memory"
recommendation has now been wrong three releases running, in both directions:

| Release | Condition | Problem |
|---|---|---|
| ≤ v3.18.7 | `total_requests > MAX_STORED * 0.8` | Always true once the counter went unbounded |
| v3.19.3 | `stored_samples > MAX_STORED * 0.8` | Always true — a full ring buffer is the steady state of a ring buffer |
| v3.19.4 | `buffer_bytes > 512 * 1024` | **Never** true — ~38x a completely full buffer |

v3.19.4 diagnosed the second one correctly and wrote down the right rule:
*before writing a threshold, ask what the world looks like when it is NOT
crossed.* It then violated the rule's missing half in the same commit. **A
threshold needs both answers. A check that cannot fire is worse than no check,
because it reads as coverage.**

### ⚠️ And the number all three were reasoned from is itself wrong — `pickle` memoises

`_append_metric`'s docstring records *"500 entries of the real tuple shape →
13,693 bytes"* (~27 B/entry), and that figure has been quoted as the size of this
buffer ever since. Re-measured 08-09-26 on the same tuple shape:

```
500 entries, one shared timestamp + one shared path       13,577 B     27 B/entry
500 entries, realistic mix of ~10 app routes              22,201 B     44 B/entry
500 entries, every path distinct (/legislation/<id>/)     33,428 B     67 B/entry
500 entries, every path distinct, 200 chars              125,937 B    252 B/entry
500 entries, every path distinct, 2 KB (scanner sweep)  1,029,673 B  2,059 B/entry
```

The first line reproduces 13,693 to within 116 bytes. That is what it was: a
synthetic buffer whose entries were all *the same objects*, so `pickle` wrote the
timestamp and the path once and back-referenced them 499 times. A real buffer
holds 500 different requests. **The true steady-state cost is 22–33 KB, not
13.7 KB** — a 1.6–2.5x understatement that has been load-bearing for three
releases of threshold arithmetic.

> **A fixture whose rows are identical does not measure serialisation, because
> every serialiser worth using deduplicates.**

This does not weaken the case for sampling; it strengthens it, because every
per-request cost in that docstring was measured on the same too-small object.

### The fix

`BYTES_PER_ENTRY_BUDGET = 192`, and `buffer_size_bytes()` /
`buffer_is_over_budget()` living in `performance.py` **next to the measurement
they are judged against**. Splitting a threshold from its evidence is how 512 KB
came to be written thirty-eight times too large in a file that imports from the
one recording the real size.

192 B/entry sits ~3–4x above realistic traffic (44–67 B) and below a buffer of
200-character paths (252 B): false in the steady state, true when paths grow
enough to matter. **Expressed per entry, so it keeps meaning the same thing after
someone tunes `MAX_STORED`** — which is the bound the recommendation is really
about, and which a fixed total silently decouples from.

`EveryThresholdHasBothAnswers` (7 tests) builds the world where it should fire
and the world where it should not, and requires the answers to differ. Every
fixture uses **distinct paths and distinct timestamps**, and one test asserts the
memoisation trap directly so nobody re-derives a threshold from an identical-row
fixture again.

Also folded in: `memory_report` was reading the buffer four times and pickling it
twice per run, and printing a size measured by one `pickle.dumps` while warning
about a size measured by another — two chances to disagree, in the same output.
Both halves now go through `buffer_size_bytes`, and the printed line gains a
B/entry figure, which is the number that actually moves.

## 🟡 4. The suppressed `FORGED_CF_HEADER` count expired unread

`src/utils/security_utils.py` · `src/test_forged_cf_throttle.py`

v3.19.4's throttle promises, in its docstring: *"Suppressed hits are counted, and
the count rides on the next line that gets through, so the volume is still
visible."* It gave both cache keys the same TTL, and they are written at
different moments — the gate by the **first** hit, the counter by the **second**.
So the counter expired a moment *after* the gate and was only ever read by a hit
arriving inside that sliver.

A **burst that stops** — a scanner sweep, a one-off probe run, which is exactly
the shape this alarm exists to characterise — had its whole tally expire unread.
The operator got one line with no number and no way to tell one probe from ten
thousand. That distinction is the alarm's entire value: one forged header is a
curiosity, sustained forgery is a decision to make about the firewall.

> **Two cache keys that must be read together cannot be given the same TTL if
> they are written at different moments.** "The same duration" reads like "the
> same lifetime" until you ask when each clock starts.

### The fix

`FORGED_CF_COUNT_TTL = FORGED_CF_LOG_WINDOW * 4`. `cache.incr` does not extend an
existing TTL, so the single `set` on the first suppression fixes the lifetime of
the whole tally and has to be the generous value.

The log suffix also stopped claiming a window it can no longer vouch for — it
read *"in the last 300s"* and a tally may now span several windows. That is the
sixth false statement-in-a-comment this codebase has deleted in three weeks, and
the first one caught in the release that introduced it.

Two new tests, including one asserting the suffix does **not** name a duration.

## ⚠️ Verification — what was and was not checked

**No Django test run.** The sandbox has no working Django (the repo `.venv` is a
macOS interpreter). **This is the seventh consecutive batch shipping with unrun
tests**, and the backlog is now eight modules deep. Run before deploying:

```
manage.py test src.test_serve_media src.test_legislation_drafts \
               src.test_middleware_hot_path src.test_forged_cf_throttle
```

`src.test_serve_media` and `src.test_legislation_drafts` are the two that matter
— one covers an authz boundary that has now moved three times in four days, the
other covers a code path that **deletes files**.

**What WAS verified mechanically, and it is more than usual:**

- `py_compile` clean on all 9 changed files; `pyflakes` clean on all 9 (the only
  findings are four pre-existing ones this release did not touch).
- **The `/media/` guard simulated against ten path shapes** outside Django, using
  the identical `realpath`/`relpath` logic: bare private path, nested private
  path, three traversal spellings into the private directory, the bare directory
  name, the near-miss `legislation_drafts_public/` (must serve), two public
  directories (must serve), and `../etc/passwd`. All ten correct.
- **Every threshold assertion re-run against the real algorithm** —
  `pickle.dumps(..., HIGHEST_PROTOCOL)` over the exact fixtures the tests build,
  with the real `MAX_STORED` and the chosen budget. Ordinary traffic 52 B/entry
  (under), 2 KB paths 2,062 B/entry (over), ten long entries (under), empty
  `(False, 0)`, headroom 52 < 96, memoisation ratio 25,921 vs 20,366. Six for
  six. **This is what caught the first draft of the fix**, which used a uniform
  path in its fixture and would have shipped a test asserting a full buffer of
  2 KB paths is over budget — it was 15,570 bytes, and the assertion would have
  failed for a reason that had nothing to do with the code.
- The five-line measurement table above, produced fresh rather than quoted.

**What was NOT verified:** anything requiring a database or a request cycle. In
particular the `ClearableFileInput` clear semantics in
`test_clearing_an_attachment_removes_the_file` are reasoned from Django's source,
not observed, and the `on_commit` capture in the new form tests has never been
executed.
