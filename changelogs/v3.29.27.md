v3.29.26's server-side logging on `csrf_token_refresh` answered its own
question and opened a new one. Mason's latest live retest produced this
three-line sequence in `logs/django_actions.log`:

```
13:41:54,110  CSRF token refresh called | ... | returned_a_token=True | ...
13:41:54,275  CSRF failure | reason=CSRF token missing. | ... | posted_token_present=False | ...
13:41:54,288  CSRF failure | ... (duplicate/retry of the same request)
```

The refresh ran, and succeeded, 165ms before the failure. That rules out
"the safety net never ran" (v3.29.26's other branch) but opens a harder
question: did the JS's own resubmit — using the token it had just
received — reach the server without the token, or did an entirely
separate, uncontrolled submission fail around the same moment by
coincidence? Both are consistent with the log as it stands; nothing in
it says which POST produced that failure line.

## The fix

A hidden marker field, `csrf_diag_resubmit`, is now stamped onto the
form with value `'1'` immediately before `base.html`'s submit-safety-net
calls `form.submit()` on its own resubmit attempt (after a token
refresh) — see the code comment marked `v3.29.27` in the submit
listener. It's set after both the success (`if (token)`) and
fallback-to-existing-value (`else if`) branches converge, so a resubmit
that goes out via either path is marked; only the `P.toast(...)`
bail-out (no usable token at all, which returns before reaching
`form.submit()`) is correctly left unmarked.

`csrf_failure.py` now reads `request.POST.get('csrf_diag_resubmit')`
(same "presence-parsing is safe here" reasoning as the existing
`posted_token_present` read — `CsrfViewMiddleware` has already parsed
the body) and logs it as `is_js_resubmit=True/False` on the existing
`CSRF failure | ...` line.

- `is_js_resubmit=True` on a failing line → confirmed, this was the
  safety net's own resubmit, and it still failed to deliver the token
  it had just set. Points at something wrong with `form.submit()`
  itself not transmitting a field value set moments earlier — a
  genuinely surprising DOM behavior if true, worth testing directly.
- `is_js_resubmit=False` → this POST was never touched by the safety
  net at all. Some other, uncontrolled submission (a double-tap on
  mobile, or a native submit racing ahead of `preventDefault()`) is
  what actually failed, and the "successful refresh 165ms earlier" log
  line is coincidental timing, not cause-and-effect.

## New tests

`TheResubmitMarkerTests` (4 tests) in `test_bfcache_reload.py` —
structural, same convention as the rest of that file (parses the raw
template text, strips Django comments, asserts substring
presence/ordering):
- the marker field name and `input[name="csrf_diag_resubmit"]` selector
  both appear;
- the marker is stamped before the actual `form.submit()` call;
- **the point of the fix** — the marker line sits after the closing
  brace of the `if (token) {...} else if (...) {...}` block, not inside
  either branch, so both the success and fallback-to-existing-value
  paths are covered;
- control — the `P.toast(...)` bail-out `return`s before reaching the
  marker line.

`CsrfFailureResubmitMarkerTests` (2 tests) in
`test_csrf_failure_diagnostics.py`, using the real `enforce_csrf_checks`
test client:
- posting with `csrf_diag_resubmit=1` logs `is_js_resubmit=True`;
- posting without it (every pre-existing test in the file) logs
  `is_js_resubmit=False` — not `None`, not blank.
