## Why v3.26.5 didn't cover this

v3.26.5 reloads a bfcache-restored page (`pageshow`, `event.persisted`) to
refresh a token that may have gone stale — *unless* a text field, textarea,
or contenteditable element holds unsaved content, in which case it skips
the reload entirely rather than risk discarding a half-written draft. That
guard was written with chat replies and Kai report drafts in mind, and the
v3.26.5 changelog explicitly accepted the skip as a rare residual risk.

`upload_document.html` (and every page shaped like it) breaks that
assumption: it's a plain `<form>` with a **required** title text input
ahead of the file picker. Typing the title is normal use of the form —
not an abandoned draft — so the guard fires on essentially every real
submission. On mobile specifically, picking a file opens a native
picker sheet that can suspend/restore the tab, which is exactly the
`pageshow persisted` scenario the guard was written for. "Rare" wasn't
rare here. At least 17 templates in this codebase have a file input;
this page isn't the only one shaped this way, though it's the only one
confirmed live so far.

(Whether the underlying cause is a genuinely stale-but-present token, or
some other iOS Safari form-restoration quirk that drops the hidden field
entirely — the CSRF log recorded the token as **absent**, not merely
wrong, which fits either — doesn't change the fix below; it's correct
either way.)

## Fix: refresh the token in place instead of doing nothing

Two changes, both in the same `pageshow`/CSRF machinery in `base.html`:

1. **On a bfcache restore with unsaved input** (the branch that used to be
   a bare `return`): call a new `refreshCsrfToken()` instead. It fetches a
   fresh token from `GET /internal/csrf-token/`
   (`src/view/csrf_token.py`, `django.middleware.csrf.get_token`) and
   patches it into every `csrfmiddlewaretoken` hidden field **and** the
   `<meta name="csrf-token">` tag on the current DOM — no navigation, so
   nothing typed or selected is touched. Strictly better than the reload
   it replaces for plain `<form>` pages. Does **not** reach the ~40
   templates that bake the token into a JS constant at render time rather
   than reading the meta tag — those still only get refreshed via the
   reload path (no unsaved input). That population is the same one
   `test_fetch_error_visibility.py`'s ratchet already tracks as
   too-large-to-convert-at-once; this doesn't grow or shrink it.

2. **A submit-time safety net**, independent of the `pageshow` signal: a
   `document`-level `submit` listener that checks, right before any plain
   `<form>` actually goes out, whether its `csrfmiddlewaretoken` field is
   empty. If so, it prevents the submit, refreshes the token, and
   resubmits (`form.submit()`, which per spec does not re-fire the
   `submit` event — no loop risk). This is the guard that's correct
   regardless of the exact browser mechanism that leaves the field empty,
   since it checks the actual value at the actual moment of risk rather
   than inferring "this might be a restore."

`GET /internal/csrf-token/` (new, `csrf_token_refresh`): no
`@login_required` (CSRF applies to anonymous sessions too — a public
contact form, for instance — and this discloses nothing a normal page
render doesn't already put in `{% csrf_token %}`), `Cache-Control:
no-store`.

## Amendment, same day: the safety net had the same bug it was fixing

Deployed, and the restart confirmed finished — and jbush hit the identical
failure again minutes later. Traced it: the submit-time safety net read
`if (!tokenField || tokenField.value) return;` — so a **completely
missing** `csrfmiddlewaretoken` element took the exact same early-return
as a **present-and-filled** one. `posted_token_present=False` in the
security log records the key as absent from the POST body, which a
browser can produce either by clearing the hidden input's value or by
dropping the node entirely — nothing in the DOM lets you tell those apart,
and the guard only handled the first case. In precisely the situation the
whole feature exists for, it did nothing.

**Fixed:** the early-return now requires a present field AND a value
(`if (tokenField && tokenField.value) return;`); when the field is
missing, one is created (`document.createElement('input')`, `type =
'hidden'`, `name = 'csrfmiddlewaretoken'`, appended to the form) and given
the refreshed token directly, since `refreshCsrfToken()`'s own DOM patch
only touches fields that already exist.

New `test_a_completely_missing_field_is_created_not_skipped`. **Verified
it fails against the pre-amendment code** (reverted just the condition
back to `!tokenField || tokenField.value`, reran — 1 of 7 in that test
class failed, for the documented reason). Full `src.tests.security` (428)
+ `src.tests.guards` (208) — 0 failures. bandit, `makemigrations --check`
— clean.

**Still can't confirm from here** whether a genuinely missing DOM node is
what actually happened on either of the two live failures, versus this
being a second instance of the "same tab, stale JS from before either
deploy" possibility raised earlier — both would produce an identical log
line. This closes the gap either way, so it doesn't block on knowing
which.

## Known, not fixed here

- The ~40 templates that embed the CSRF token as a JS constant instead of
  reading it from the meta tag still don't get a silent refresh in the
  guarded case — they fall back to today's behavior (reload-or-nothing).
  Converting them is the pre-existing tracked population, not new scope
  for this fix.
- Haven't audited which of the other 16 templates with a file input share
  `upload_document.html`'s exact shape (a required text field ahead of the
  picker). This fix is general — it doesn't matter which pages have the
  shape, since the safety net triggers on the actual empty-token condition
  — but it might be worth a pass to see how many members this was
  plausibly affecting before today.
