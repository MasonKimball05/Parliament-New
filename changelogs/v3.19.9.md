## 🟠 1 — four ordinary malformed Office files were HTTP 500, not "rejected"

v3.19.8 replaced libmagic sniffing for the six zip-backed document formats with
a structural check — open the archive, read what the file declares about itself
— which is the right design and is not in question here. Its error handling is.

`_validate_zip_container`'s docstring made the argument explicitly:

> ⚠️ THIS RAISES ITS OWN VERDICT AND CATCHES NOTHING BROAD, deliberately. … the
> detection cannot fail in a way that should be tolerated

and then wrapped `(zipfile.BadZipFile, OSError, EOFError)` around the
`zipfile.ZipFile()` **constructor only**, leaving `archive.open(...)` and
`fh.read(...)` — four lines below, in the same operation — outside it.

Measured 08-15-26 against the real `validate_uploaded_file` (Python 3.10,
Django 5.2.16), building each malformation from the standard library:

```
good .docx                -> ACCEPTED
unsupported compression   -> *** UNCAUGHT NotImplementedError            -> 500
encrypted zip entry       -> *** UNCAUGHT RuntimeError                   -> 500
corrupt member (bad CRC)  -> *** UNCAUGHT zipfile.BadZipFile             -> 500
encrypted ODF `mimetype`  -> *** UNCAUGHT RuntimeError                   -> 500
```

`validate_uploaded_file` is called from **17 upload sites** and every one of
them catches `ValidationError` and nothing else — excuse documents (doctors'
notes), legislation, committee and chapter documents, Kai attachments, slating
files, service-hours evidence. So each row above is an unhandled 500 any
authenticated member can produce by uploading a file, with an error-log entry
and no message telling them what was wrong.

None of these is exotic. Deflate64 comes out of several Windows archivers;
password-protected zips are a thing people make on purpose; a corrupt member is
what a file recovered off a failing disk looks like.

⚠️ **Look at the third row.** `BadZipFile` is *named in the handler* — and
raised, unhandled, four lines later by the second half of the same operation.
Enumerating exception types got the type right and the **place** wrong. This is
the eighth instance of CLAUDE.md's *"a rule stated correctly, a helper written
to enforce it, then something left outside the helper"*, and the first where the
thing left outside was the rest of the same call.

### The fix, and why it is a second function rather than a longer tuple

Detection now lives in `_read_container_declaration`, which contains **no
`raise ValidationError` anywhere**; every verdict lives in
`_validate_zip_container`, which calls it.

That separation is what makes the catch safe to widen to `Exception`.

> **THE RULE: a `try` narrowed to what is allowed to fail has to be narrowed
> around the WHOLE of what is allowed to fail.** v3.19.7's finding was that
> `validate_mime_type`'s `try` contained both the detection and the verdict, so
> failing open on a missing libmagic also failed open on a real mismatch. The
> remedy is to separate them — v3.19.8 read it as *"make the `try` small"* and
> made it smaller than the detection. Once the verdict is in a different
> function there is nothing in scope for a broad catch to swallow, and broad is
> the only honest width: the alternative is a blocklist of a stdlib parser's
> failure modes, which is what just failed.

The catch logs the exception type before converting it, so that a systematic
misdiagnosis — a Python upgrade changing what `zipfile` raises, a bug in the
four lines below — appears as a run of rejections in the log rather than as a
run of malicious uploads.

New `src/test_upload_container_errors.py` (10 tests). **Negative control run:
6 of the 10 error against `HEAD`'s `file_validation.py` and pass here**; the
other 4 are the controls (a well-formed `.docx` is still accepted, a non-zip is
still rejected, a `.docx` carrying a spreadsheet manifest is still rejected, the
pointer is still rewound on success) and pass in both trees, which is what a
control is for.

Two of the ten are worth calling out:

- `test_the_control_a_well_formed_docx_is_still_accepted` is written **first**
  in the class, because a validator that rejected everything would pass every
  other test here — and that is precisely the regression v3.19.8 existed to fix.
- `test_the_pointer_is_rewound_after_a_rejection`. v3.19.8 established that a
  validator which consumes the stream stores a truncated document, and covered
  the success path. The **rejection** path needs the same guarantee for a
  different reason: several call sites catch the `ValidationError`, drop the
  file and keep the record. A validator that leaves the pointer mid-file on the
  way out is a data-loss bug on the error path — the path nobody exercises.

## 🟠 2 — `tblib` was missing, so the parallel suite could not report any failure

**This closes v3.19.8 §5**, recorded there as *"a failure reported as a pickling
error, and I could not reproduce it"*.

Django's parallel runner moves results between processes by pickling them. A
failure's `sys.exc_info()` contains a traceback object, which is not picklable,
so `django/test/runner.py` calls `tblib.pickling_support.install()` — guarded by
`if tblib is not None`. `tblib` was not in `requirements.txt`, so that guard was
`None` and the branch never ran.

The consequence is worse than a missing traceback. `RemoteTestResult.addFailure`
calls `check_picklable`, which re-raises, which kills the pool worker, which
raises in the parent as `TypeError: cannot pickle 'traceback' object` **and
aborts the run** — so the other 1,336 results are never reported either. Django
does print a block naming the test, but the child prints it *after* the parent
has already raised; across eight workers, at the end of a hundred seconds of
output, it is easy to lose entirely. That is why the symptom looked like "no
test name".

Reproduced in a two-module scratch project on 08-15-26:

```
without tblib, --parallel=2  ->  TypeError: cannot pickle 'traceback' object
                                 (no results, run aborted)
with    tblib, --parallel=2  ->  FAILED (failures=1) + full traceback
```

**And then demonstrated on the real suite by accident, which is the better
evidence.** The first full run of this batch failed — `test_hardcoded_urls`
flagged `/word/document.xml`, an OOXML part name in this release's own new
fixture, correctly. It reported as a clean `FAIL:` line with a complete
traceback under `--parallel=4`. That is the identical guard, failing for the
identical reason, on the identical command that produced an unreadable
`TypeError` on 08-13.

⚠️ **CORRECTION TO THE 08-13 REPORT.** It concluded *"CI runs in parallel, which
means there is a class of failure the suite currently cannot report."*
`.github/workflows/ci.yml` runs `python manage.py test --verbosity=2` with **no
`--parallel`** — CI is serial and was never affected. This was a developer and
auto-run problem. The claim was inherited rather than checked, which is the
eight-report deploy-backlog error in one line; it is corrected here rather than
quietly dropped.

`tblib==3.2.2` added to `requirements.txt`, with the reasoning beside the pin.
`src/test_parallel_reporting.py` asserts `django.test.runner.tblib is not None`,
that it is pinned, and that a traceback actually round-trips through `pickle`
after `RemoteTestResult()` has installed the support — the import being
importable is necessary and is not the mechanism.

## 🟡 3 — the cache isolation did not exist in spawned workers, i.e. on macOS

v3.19.7 patches `SimpleTestCase.run` from
`CacheIsolatedTestRunner.setup_test_environment`, which runs in the process that
invoked `manage.py test`. Whether a worker gets it depends entirely on the
multiprocessing start method:

| start method | worker is | patch present |
|---|---|---|
| **fork** (Linux default) | a memory copy of the parent | **yes** |
| **spawn** (macOS since 3.8, Windows) | a fresh interpreter | **no** |

Under spawn, Django's `_init_worker` re-bootstraps with `django.setup()` and the
**module-level** `django.test.utils.setup_test_environment()` — not the runner's
override, which it holds no reference to.

Measured 08-15-26: `_parliament_cache_isolation_installed` is `True` in a forked
child and **absent** in a spawned one.

**Parliament is developed on macOS.** So `manage.py test --parallel` there ran
with no cache isolation at all — the exact partitioning-dependent failure count
v3.19.7 exists to abolish, on the one machine where the suite is run
interactively — while the file explaining the fix sat in the repo looking
applied. The evidence *for* the fix ("two partitionings agree", 08-13) was
gathered in a Linux sandbox, where it genuinely works.

> **A harness verified in the launching process is not verified.** The same
> sentence as v3.19.8's *"test isolation that reaches outside the test process
> is not isolation"*, pointed the other way: that one was about the cache
> reaching too far, this is about the fix not reaching far enough.

Fixed by `CacheIsolatedParallelSuite`, whose `run_subsuite` installs the patch
in whatever process is about to run the tests. `run_subsuite` is one of the two
seams Django documents for this (*"In case someone wants to modify these in a
subclass"*) and is the right one: `process_setup` fires **before**
`django.setup()` in the worker, where importing test machinery is not safe.
Idempotent, so it is a no-op under fork.

⚠️ **THE TESTS USE `subprocess`, NOT `multiprocessing`, AND THAT IS NOT A STYLE
CHOICE.** The direct reproduction — `get_context('spawn').Process(...)` — cannot
work here: `multiprocessing.Pool` workers are daemonic and daemonic processes
may not have children, so such a test passes serially and **errors under
`--parallel`**, i.e. fails in exactly the mode it was written to protect. A bare
interpreter gives the same thing a spawned worker gets.

The negative control is the finding itself:
`test_the_runner_hook_alone_does_not_reach_a_fresh_interpreter` runs precisely
what `_init_worker` runs and asserts the patch is `ABSENT`.

## 🟡 4 — the pre-push hook has never been installed

`scripts/pre-push.sh` was written 07-18-26 (v3.14.1) on entirely correct
reasoning — *prod deploys are `git pull` of main, so an untested push is one
`git pull` away from prod* — and `make hooks` installs it.

`.git/hooks/` contains nothing but Git's own `.sample` files and
`core.hooksPath` is unset. **It has never been installed.** The cost is legible
in this repo's own history:

- `test_url_smoke` was red from 07-30 to 08-02 across several pushes, and was
  found by a nightly review;
- v3.19.6 ran the full suite for the first time in eight batches and found 12
  pre-existing failures, all reproducible on the already-pushed commit;
- seven consecutive releases were pushed with a stale ledger line.

Every one of those is a thing this hook refuses to push.

> **A guard needs a trigger it does not have to be remembered — and so does the
> trigger.** v3.19.8 stated the first half and applied it to `src.W003` by
> moving it into `preflight`. This is the same sentence one level up: the hook
> is the trigger, `make hooks` is the trigger for the trigger, and nothing ever
> checked it. **A one-time manual setup step is indistinguishable, six months
> later, from a setup step that was done.**

Three things in this release:

1. **The hook now also gates on the release-integrity system checks.** `src.W003`
   fires on a line that can only ever be written stale; `preflight` catches it
   at deploy time, by which point it is already in history and needs a follow-up
   commit. **At push time it is still a `git commit --amend`.** The gating set
   moved to `preflight.RELEASE_GATING_CHECK_IDS` and the hook imports it — one
   definition, two triggers at opposite ends of the release. Verified by
   negative control: with the v3.19.8 line reverted to *not yet*, the gate exits
   1 and names `src.W003`; restored, it exits 0.
2. **`src/test_repo_hooks.py` (6 tests)** fails the suite when the hook is
   missing, out of date with `scripts/pre-push.sh`, or not executable (git
   ignores a non-executable hook *silently* — the same failure one permission
   bit down). Skipped under `CI` and outside a git working tree, and
   deliberately **not** skipped when the hook is absent: skipping when the thing
   you are asserting is missing is how a guard becomes decorative.
3. **The hook was installed in this working tree** (`make hooks`), because
   leaving the suite red on a configuration fact would have reproduced this
   codebase's most-recorded failure — a red suite nobody notices. ⚠️ **This
   changes what `git push` does on the machine**: it now runs the sqlite suite
   (~100 s) and the ledger check first. `git push --no-verify` bypasses a single
   push and `rm .git/hooks/pre-push` undoes it entirely.

⚠️ **This is the weaker half of a fix and says so.** A git hook is local
configuration living in `.git/`, which is untracked — **no commit can deliver
it.** What the test can do is make the absence visible from inside the thing the
hook guards, so it is reported by every suite run rather than by a review three
days later.

## Housekeeping — two carried items, closed in the same release

Both were listed as open in the 08-15 report and both are small. They are here
rather than deferred because neither needed anything the batch did not already
have open.

### `test_hardcoded_urls` — a rule instead of a third literal

v3.19.8 exempted `/main.xml` and this release added `/word/document.xml`. Both
are OOXML **part names** in synthesised document fixtures, and a part name is a
rooted path *by specification*, so the list was going to grow one entry per
fixture forever. Replaced with `_is_ooxml_part_name`: a path introduced by
`PartName=` is a package part, not a URL. Both literals removed — leaving them
would have meant two mechanisms where the literal masks the rule, so a broken
rule would go unnoticed.

Three tests back it, and the shape of them is the point:

- the **control** — the identical string *without* the introducer is still
  scanned, so the rule exempts by mechanism rather than by shape;
- the **boundary** — every path the rule exempts must sit on a line naming an
  OOXML namespace, which is a claim about this tree rather than about the
  format and is therefore asserted;
- the **negative control**, run: with `_is_ooxml_part_name` disabled the scan
  reports both fixtures again.

⚠️ **TWO DRAFTS OF THE BOUNDARY TEST FLAGGED THIS MODULE'S OWN PROSE**, and the
fixture in the control test flagged itself. A scanner run over the tree
containing the file that documents it will always find the documentation first:
the first draft grepped for `PartName` and hit ten lines of comment; the second
narrowed to exempted paths and still hit the worked example above the regex; the
control's `path = '/word/document.xml'` was a real unresolvable literal in a
scanned file. Fixed by skipping comment lines exactly as `_scan` does, and by
assembling the fixture path as `'/' + 'word/document.xml'`. **The module already
knew this** — `_strip_comments` exists because the first run of the whole test
flagged the `{% comment %}` blocks written to explain the links it was fixing.
The lesson had to be re-learned one level up.

### `preflight.check_system_checks` — one partition, stated once

`advisory = [m for m in messages if m not in blocking]` replaced with a single
pass.

⚠️ **AND THE REASON GIVEN FOR FLAGGING IT WAS WRONG, WHICH IS RECORDED RATHER
THAN QUIETLY DROPPED.** The 08-15 report suspected that `CheckMessage.__eq__`
comparing every attribute would let a non-gating message be swallowed by an
equal gating one. Building the reproduction showed it cannot: `__eq__` includes
`id` and `level`, so two messages that compare equal are gating or advisory
*together*. Verified 08-15-26.

What remains is real and smaller: the classification was stated twice, once as a
predicate and once as its complement over a list, and the second statement's
correctness depended on an equality method this project does not own. One pass
states it once. **A "this is O(n²) and fragile" finding that arrives with a
mechanism attached should have the mechanism checked before the fix is written**
— it took four minutes and it changed what the comment says.

## Addendum, 08-15-26 — the hook blocked the first push it ever saw

Recorded rather than quietly patched, because the failure is the same defect
class the hook exists to catch.

`git push` of `ee295da` aborted with:

```
ImportError: Couldn't import Django. Are you sure it's installed …?
[pre-push] ✗ tests failed — push aborted.
```

**A git hook runs in a non-interactive, non-login shell with no virtualenv
activated**, so bare `python3` is the system interpreter — on macOS, one with no
Django in it. Parliament's dependencies live in `.venv` (Python 3.14). Nothing
was wrong with the tree.

Two things were wrong with the hook, and the second is the one worth keeping.

1. **It assumed an activated environment.** Now it resolves an interpreter
   deliberately — `$PARLIAMENT_PYTHON`, `$VIRTUAL_ENV/bin/python`,
   `.venv/bin/python`, `venv/`, `env/`, then `python3` — and takes the first
   that can actually `import django`, rather than the first that exists. It
   prints which one it chose.
2. ⚠️ **It reported "tests failed" for a check that never ran.** That is the
   thing this codebase keeps recording under other names — *a guard that
   swallows exceptions reports the absence of a signal as the absence of a
   problem* — arriving from the opposite side: **a check that cannot run must
   not report like a check that failed.** A guard whose broken-environment mode
   is indistinguishable from a broken tree is a guard people delete, which is
   precisely how this repo went a month with the hook uninstalled.

   So "no usable interpreter" is now a **loud skip that allows the push**, with
   a block explaining what was looked at, that nothing was checked, and how to
   fix it. Verified: with every candidate unavailable the hook prints the
   warning and exits 0; with one available it names it and proceeds.

`test_it_does_not_invoke_manage_py_with_a_bare_interpreter` pins the regression.

**And the ledger gate then did its job, on schedule.** With the interpreter
fixed, the second half of the hook stopped the same push and reported `src.W003`
against `ee295da` — v3.19.9's own two ledger lines, still reading *not yet* and
*not committed* inside the commit that made them false. **That is the eighth
consecutive release with a stale ledger line and the first one caught before the
push rather than days after.** Both lines now carry `ee295da`.

⚠️ **The hook's own hint text was wrong about how to fix it, and is corrected.**
It said `git commit --amend`. Amending rewrites the commit, which changes the
sha just written down — and `src.W003` checks that a recorded sha **matches**
the commit git says added the file (`checks_ledger.py`, third failure mode). An
amend trades one red check for another. The remedy is a follow-up commit, which
is what every previous corrected row in `DEPLOYED.md` actually was.

**Follow-up commit:** `713d27c` — `scripts/pre-push.sh`,
`src/test_repo_hooks.py` (+1 test), `changelogs/v3.19.9.md`,
`changelogs/DEPLOYED.md`. ✅ **1,340 tests, 0 failures.**

### And then it blocked a second push, correctly

The next `git push` failed with the suite red on Mason's machine and green
everywhere else. The cause: **`tblib` is new in this release and had not been
`pip install`ed yet.** `test_django_can_pickle_tracebacks` is a dependency
assertion, so it fails until the dependency exists — which is the test doing its
job, and is also the first thing anyone will hit after pulling v3.19.9.

Two changes, both about the *message* rather than the check:

- **The failing assertion now names the command.** `Run: pip install -r
  requirements.txt`, plus the fact that it is expected on the first run after
  pulling this release. The old text said the package was "pinned in
  requirements.txt", which describes the state of the repo and not the action.
- **`test_a_traceback_actually_round_trips` now SKIPS when tblib is absent**
  instead of failing alongside it. **One cause should produce one failure.** Two
  tests failing for the same missing package gives a reader two problems, and in
  a push gate that is the difference between a message someone acts on and a
  message someone bypasses.

⚠️ **And the hook was hiding which test failed.** Several tests in this suite
print progress to stdout, so a `FAIL:` line lands hundreds of lines above the
hook's own message and the last thing on screen is an unrelated test's debug
output — the failure above was first read as "the vote-summary test broke". The
hook now tees the run and, on failure, replays just the `FAIL:`/`ERROR:`/`Ran`/
`FAILED` lines, names the full log, and prints both the re-run and the bypass
command. **A gate that says "something failed" without saying what gets bypassed
rather than acted on**, and a bypassed gate is the state this hook was written
to leave behind.

(`set -o pipefail` is already at the top of the script, so teeing does not
swallow the test runner's exit status — verified rather than assumed, because a
`cmd | tee` that always reports success would have turned this gate into
decoration.)
