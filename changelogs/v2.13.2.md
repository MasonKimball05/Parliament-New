# v2.13.2 - Magic Strings, Wildcard Imports & Committee Flag Consistency

**Release Date:** May 10, 2026

**Deployment Status:** Deployed

**Type:** Code Quality / Maintainability

---

## Overview

Three related problems were addressed in this version: **magic strings**, **wildcard imports**, and **inconsistent committee permission patterns**. None of these change how Parliament behaves — every string value, every queryset, and every URL route is identical to before. The improvement is entirely in how the code reads and how maintainable it is for whoever comes next.

---

## Problem 1 — Magic Strings

### What the problem was

Throughout models, views, and decorators, member type and status comparisons were written as raw string literals scattered across at least 6 files:

```python
# In models.py
def is_officer(self):
    return self.member_type == 'Officer'

# In attendance.py
users = ParliamentUser.objects.filter(member_type__in=['Member', 'Chair', 'Officer'])

# In decorators.py
if not (request.user.is_officer or request.user.member_type == 'Chair'):
```

These are independent string literals that happen to match each other and match what's stored in the database. The risks:

- **Typos are silent failures.** `'officer'` instead of `'Officer'` gives an empty queryset, no error.
- **Refactoring is dangerous.** Renaming a member type means grepping the whole codebase and hoping nothing is missed. Miss one and access control breaks.
- **No single source of truth.** `MEMBER_TYPES` already existed on `ParliamentUser` for Django's `choices=` — but none of the comparison logic used it.

### What was done

`src/constants.py` was created with two classes as the single source of truth:

```python
class MemberType:
    MEMBER  = 'Member'
    CHAIR   = 'Chair'
    OFFICER = 'Officer'
    ADVISOR = 'Advisor'
    PLEDGE  = 'Pledge'

    CAN_VOTE               = (MEMBER, CHAIR, OFFICER)
    CAN_VIEW_OFFICER_PAGES = (OFFICER, CHAIR, ADVISOR)
    CAN_MANAGE_EVENTS      = (OFFICER, CHAIR)

class MemberStatus:
    ACTIVE   = 'Active'
    INACTIVE = 'Inactive'
    ALUMNI   = 'Alumni'
    REMOVED  = 'Removed'
```

Now the same comparisons read like this:

```python
def is_officer(self):
    return self.member_type == MemberType.OFFICER

users = ParliamentUser.objects.filter(member_type__in=MemberType.CAN_VOTE)
```

Misspelling `MemberType.OFICER` raises a `NameError` immediately at import time, not silently at runtime.

**Files updated:** `src/models.py`, `src/decorators.py`, `src/view/officer/attendance.py`, `src/view/officer/user_list.py`, `src/view/committee/committee_index.py`, `src/view/committee/committee_detail.py`

## Problem 2 — Wildcard Imports

### What the problem was

Several files used `from X import *` — importing everything from a module without naming what was needed:

```python
# In src/urls.py
from src.view.officer import *
from src.view.committee import *
from src.view.chat import *

# In src/decorators.py
from src.models import *   # dumps all 50+ models into this file's namespace
```

This matters because:

- **You can't tell what a file depends on.** Opening `attendance.py` and seeing `from src.models import *` gives no information about whether it uses 1 model or 20. You have to already know the whole codebase.
- **IDEs can't help.** Autocomplete, "Go to definition", and "Find all references" all break when names arrive via wildcard. A new maintainer is essentially coding blind.
- **Name collisions are invisible.** `urls.py` did `from src.view.officer import *` and then re-imported from specific submodules below it. The order mattered, but nothing in the code made that obvious.

### What was done

Every wildcard was replaced with an explicit list of the names that file actually uses:

```python
# src/urls.py — after
from src.view.officer.officer_home import officer_home
from src.view.officer.attendance import attendance
from src.view.officer.user_list import user_list, export_user_list
from src.view.officer.archive_event import archive_event, unarchive_event
# ... and so on

# src/decorators.py — after
from src.models import Committee   # that's the only one it actually uses
```

A future maintainer opening any file can now see its exact dependencies at the top. IDE tooling works. If a function is renamed, the error appears on the import line.

**Files updated:** `src/urls.py` (3 wildcards removed), `src/decorators.py`, `src/view/officer/attendance.py`, `src/view/officer/user_list.py`, `src/view/committee/committee_index.py`, `src/view/committee/committee_detail.py`, `src/view/committee/manage_members.py`

## Problem 3 — Inconsistent Committee Permission Patterns

### What the problem was

Parliament has several committees that carry special behavior beyond normal committee logic. EXEC and SLATING had already been converted to use boolean flags on the Committee model (`is_exec_board`, `is_slating_committee`), which is the right approach — the flag makes the behavior database-driven, so a future chapter can reassign which committee plays each role without touching code.

But KAI and CHAPTER hadn't been converted, and even EXEC had one remaining code comparison that was missed:

```python
# In models.py — EXEC's is_chair() method still used the string even though is_exec_board existed
def is_chair(self, user):
    if self.code == 'EXEC' and self.members.filter(pk=user.pk).exists():
        return True

# In kai_form_builder.py, kai_reports.py, kai_user_dashboard.py, etc. — 15+ places
kai_committee = Committee.objects.get(code='KAI')

# In global_search.py
if request.user.committees.filter(code='KAI').exists():

# In committee_detail.py
if committee.code == 'KAI' and (is_chair or user.is_admin):

# In manage_chapter_documents.py
chapter_committee = Committee.objects.get(code='CHAPTER')
```

The problem with code-based lookups is that they bind the behavior to the string in the database. If a chapter wants to rename the Kai Committee, or delegate conduct reporting to a different committee, or reassign chapter document management, they'd have to find and change every reference in the Python source — which they're unlikely to be able to do without Mason's help.

### What was done

Two new flags were added to the `Committee` model, following the same pattern as `is_exec_board` and `is_slating_committee`:

```python
is_kai_committee = models.BooleanField(
    default=False,
    help_text='If True, this is the conduct committee — enables Kai report management, form builder, and chair notifications'
)
is_chapter_committee = models.BooleanField(
    default=False,
    help_text='If True, this committee owns chapter-level documents (the chapter documents page)'
)
```

Migration `0155` adds both fields and sets `is_kai_committee=True` on the KAI committee and `is_chapter_committee=True` on the CHAPTER committee.

All 15+ KAI code comparisons were updated:

```python
# Before
kai_committee = Committee.objects.get(code='KAI')
if request.user.committees.filter(code='KAI').exists():
if committee.code == 'KAI' and (is_chair or user.is_admin):

# After
kai_committee = Committee.objects.get(is_kai_committee=True)
if request.user.committees.filter(is_kai_committee=True).exists():
if committee.is_kai_committee and (is_chair or user.is_admin):
```

EXEC's leftover code comparison in `is_chair()` was also fixed:

```python
# Before
if self.code == 'EXEC' and self.members.filter(pk=user.pk).exists():

# After
if self.is_exec_board and self.members.filter(pk=user.pk).exists():
```

A `CommitteeCode` class was also added to `src/constants.py` to document the canonical code strings, with a note that the boolean flags should be preferred for logic:

```python
class CommitteeCode:
    """
    Prefer the boolean flags (is_kai_committee, is_exec_board, etc.)
    for permission logic. These constants exist for the rare cases where
    a code comparison is unavoidable and as a reference for what codes exist.
    """
    KAI     = 'KAI'
    EXEC    = 'EXEC'
    SLATING = 'SLATING'
    CHAPTER = 'CHAPTER'
```

### The net effect

Every special committee's behavior is now governed by a database flag, not a hardcoded string. The full picture:

| Committee | Flag | Behavior it enables |
|---|---|---|
| EXEC | `is_exec_board` | All members carry chair-level permissions; membership auto-syncs with exec role holders |
| SLATING | `is_slating_committee` | Special visibility rules; President auto-assigned as admin |
| KAI | `is_kai_committee` | Kai report management, form builder, chair notifications, global search visibility |
| CHAPTER | `is_chapter_committee` | Chapter documents page document source |

A future chapter admin can now reassign any of these roles through the admin panel without touching a single line of Python.
