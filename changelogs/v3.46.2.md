## 🟢 `/csp-report/` stops storing reports past a cap

### Before
`/csp-report/` is public and CSRF-exempt by design (browsers post to it with no
session). Every POST with a report-shaped JSON body wrote one `CSPViolation`
row and one WARNING line on the `security` logger. Nothing deletes
`CSPViolation` rows, and the `security` logger shares one 10 MB x 3 rotating
file with `django` and `src` (see v3.19.4). The only ceiling was nginx's
`general_zone`: 10 r/s per IP, about 864,000 rows and log lines a day from a
single client.

### After
- Per ten-minute window: at most **60 stored reports per client IP** and
  **1,000 site-wide**. Counters live in the cache (Redis in prod).
- Over either cap the browser still gets **204**. Browsers never retry a
  report, so nothing changes for them; the report is just neither stored
  nor logged.
- Crossing a cap is logged **once** (WARNING, `security`), not once per
  dropped report.
- The cap check runs before the per-report log line, so a flood can't push
  real entries out of the shared log file.
- If the cache is unreachable, the report is stored as before (fails open).

### Why these numbers
A real browser on a page with a CSP problem sends a handful of reports per
page view, and the admin CSP view groups reports by (directive, blocked URI),
so the 61st copy of the same violation adds nothing. The site-wide cap is
there because the per-IP one can be stepped around by a client that can vary
its address. **Trade-off:** after a deploy that breaks CSP on every page, a
busy ten minutes could hit 1,000 and drop the rest of that window. By then
there are 1,000 rows showing the problem.

### Checked, no change
- **"May be dropping reports in the newer list format"** (raised 10-09): no.
  The CSP header only sets `report-uri`, not `report-to`, so browsers send
  the classic `application/csp-report` body (`{"csp-report": {...}}`), which
  this view handles. The list format (`application/reports+json`) is only
  sent to a `report-to` / `Reporting-Endpoints` group, which this site does
  not declare. If one is ever added, this view will need to accept a list.
