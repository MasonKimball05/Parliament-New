**Migration:** `0029_kai_accommodations` — adds `form_type` to
`KaiFormField` (backfilled `'discipline'` on every existing row, so no
existing custom field silently disappears from the report form) and
creates three new tables: `KaiAccommodationRequest`,
`KaiAccommodationFieldResponse`, `KaiAccommodationRequestActivity`. No
data migration beyond the `form_type` default; safe on a live DB
(additive + one column with a default).

Requested by Mason: a way to submit something to the Kai Committee that
is **not** a disciplinary report — a request for accommodation (medical,
religious, scheduling, or otherwise) — with a toggle between the two
forms on the submission page, and a way for the Kai committee admin to
edit the accommodation form's fields the same way the discipline
report's fields are already editable.

## What it does

**A separate model, not a flag on `KaiReport`.** `KaiAccommodationRequest`
has no accused, no case number semantics beyond its own `ACC-YYYY-NNN`
counter, no recusal, no appeals, no deliberation outcome — none of
`KaiReport`'s machinery exists for it because that machinery exists
*because there's an adversarial pair of parties*, and an accommodation
request has none. Full reasoning is in
`src/models/kai_accommodations.py`'s module docstring.

**What IS reused, deliberately:**
- The `KaiFormField` dynamic-custom-field system, now discriminated by a
  new `form_type` field (`'discipline'` / `'accommodation'`,
  `db_index=True`, defaults to `'discipline'` so nothing about the
  existing report form changes silently). Both `kai_reports.py`'s
  save-path and GET-path custom-field queries are now scoped
  `form_type='discipline'`, so an accommodation-only field can't leak
  onto the report form or get processed as if it belonged to a report
  someone is submitting.
- The Kai committee's `KaiMemberPermission` grants
  (`can_view_report_list`/`can_view_report_details`/`can_edit_open_cases`/
  `can_add_activity`) — whoever a chair has already given committee
  access to sees accommodation requests too, with the same granularity.
  Mason's call: accommodation requests are sensitive (often
  medical/disability/religious) and the Kai committee is already the
  body this chapter trusts with sensitive personal information under a
  permission system built for exactly that, rather than a second access
  surface to keep in sync with the first.

**Member-facing:**
- `submit_kai_accommodation_request` / `templates/kai/submit_accommodation_request.html`
  — same shape as `submit_kai_report`: attachment validated through
  `validate_uploaded_file` before anything is saved, custom fields
  handled identically, chair(s) notified by email. `submit_report.html`
  and this template each render a two-tab toggle linking to the other.
- The requester's identity is **not** withheld from a permitted
  reviewer — there's no accused to withhold it from — so unlike
  `KaiReport`'s activity feed, `KaiAccommodationRequestActivity` carries
  no redaction machinery. `src/tests/kai/test_kai_redaction_surfaces.py`
  (a directory-wide guard over every `templates/kai/*.html`) needed a
  narrow, named, documented exemption for this reason — see that file's
  `_NOT_A_KAI_REPORT_ACTIVITY_FEED` and its own negative-control test.

**Committee-facing:**
- `manage_kai_accommodation_requests` (list, status filter) and
  `manage_kai_accommodation_request_detail` (status/assignment/committee-notes,
  each writing an activity row) — gated by `_get_kai_access`, imported
  from `kai_reports.py` rather than reimplemented so the two forms'
  access control can never drift apart. Linked from the Kai dashboard
  header ("Accommodation Requests" button, next to Form Builder).
- `kai_form_builder` now takes a `form_type` kwarg from the URL
  (`kai_form_builder` defaults `'discipline'`,
  `kai_accommodation_form_builder` passes `'accommodation'`) rather than
  duplicating the whole builder view — every query and redirect inside
  it is now scoped to one form. Field-name uniqueness stays a **global**
  check across both forms (the field lives on one shared model), by
  design.

**Private file serving.** Attachment + custom-field file responses on
accommodation requests are confidential the same way Kai report
attachments are (often medical/disability/religious). `kai_accommodations/`
was added to `PRIVATE_MEDIA_PREFIXES` (refused by `/media/`, which is
only `@login_required`) and two new ownership-aware views —
`serve_kai_accommodation_attachment` / `serve_kai_accommodation_response_file`
— serve them instead, gated by a new `_user_may_read_kai_accommodation`
predicate (requester, or a committee member with
`can_view_report_details`) that mirrors `_user_may_read_kai_report`
one level simpler (no `_case_access`/recusal narrowing, because there's
no second party). `src/tests/guards/test_media_classification.py` and
`src/tests/documents/test_serve_media.py` both enumerate every
`PRIVATE_MEDIA_PREFIXES` entry against a replacement route — both were
updated (there are two copies of this enumeration in the tree; missing
the second one is exactly the "left outside the helper" shape CLAUDE.md
already tracks, and the full-suite run below is what caught it).

**Admin.** `KaiAccommodationRequest`, `KaiAccommodationRequestActivity`
and `KaiAccommodationFieldResponse` are deliberately **not** registered
in `/admin/` — same reasoning as the seven existing unregistered Kai
models (v3.16.2's standing confidentiality boundary): visibility here is
decided by `KaiMemberPermission`, not by Django's own perms, so
registering them would let any Django admin read accommodation requests
regardless of whether a Kai chair actually granted that access.
