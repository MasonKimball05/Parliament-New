# v3.5.0 — Security Hardening & API Cleanup

**Release Date:** June 12, 2026

**Deployment Status:** 🔲 Not Deployed

**Type:** Security / Bug Fix / Cleanup

---

## Overview

Five security and correctness issues identified in the 06-12 automated report. All are now resolved. No new features — pure hardening and cleanup.

---

## What Changed

### 1. Email Normalization + Case-Insensitive Uniqueness

Email addresses are now normalized to lowercase before being saved anywhere in the system. This closes a silent correctness gap: `ParliamentUser.email` was `unique=True` but Postgres's uniqueness index is case-sensitive, meaning `Mason@x.com` and `mason@x.com` could coexist. Once a case-variant pair existed, `email__iexact` lookups would raise `MultipleObjectsReturned`, causing email login to silently fail for both accounts with no error message.

**Changes:**
- `src/models/users.py` — Added `save()` override that normalizes `self.email` to `self.email.strip().lower()` before calling `super().save()`. Added `UniqueConstraint(Lower('email'), name='uniq_parliament_user_email_lower')` to `Meta.constraints`. Added `from django.db.models.functions import Lower` import.
- `src/view/profile_view.py` — Changed email uniqueness check from `filter(email=new_email)` to `filter(email__iexact=new_email)`.
- `src/view/admin_v2.py` — Same fix for the admin user-edit email uniqueness check.
- `src/view/officer/manage_members.py` — Same fix for the officer member-edit email uniqueness check.
- `src/migrations/0206_email_lower_unique_constraint.py` — Migration adding the functional unique index.

> **Deploy note:** Run `python manage.py migrate`. If any existing users have case-variant email duplicates, the migration will fail — run `SELECT LOWER(email), COUNT(*) FROM src_parliamentuser GROUP BY 1 HAVING COUNT(*) > 1` first to check. In practice this is unlikely given the system was always single-entry.

### 2. Passkey Login Now Runs the Full Post-Auth Security Pipeline

Passkey authentication bypassed the post-auth pipeline that the password login path runs: IPBlacklist check, foreign-IP detection, LoginHistory creation, LoginAlert creation, and watch-flag alerts. A blacklisted IP could log in via passkey, and a watched or geo-anomalous account produced no alert.

The shared logic was extracted into `run_post_auth_pipeline()` in `src/utils/security_utils.py`. Both the password and passkey login paths now call this helper.

**`run_post_auth_pipeline(request, user, ip_address, user_agent, method='password')`:**
- Checks the IP against `IPBlacklist`. If actively blacklisted, returns a `JsonResponse(403)` error and the view must deny the login immediately.
- Runs `is_foreign_ip()`, sets `login_geo*` session variables, creates `LoginHistory` and `LoginAlert` (for non-US IPs), fires `send_watch_flag_alert()` if the user has an active watch flag.
- Returns `(None, {'is_foreign': bool, 'login_record': obj})` on success.

**Changes:**
- `src/utils/security_utils.py` — Added `run_post_auth_pipeline()` function. Added `from django.http import JsonResponse` import.
- `src/view/webauthn.py` — Added `from src.utils.security_utils import get_client_ip, run_post_auth_pipeline`. In `passkey_authenticate_complete`, call `run_post_auth_pipeline()` after credential verification and before `login()`. Removed the now-redundant standalone `security_logger.info` login line (the pipeline logs it).

> **Note:** `login_view.py` still runs an equivalent inline copy of the same logic. Both paths are correct and equivalent today. Refactoring `login_view` to call the shared helper is tracked as a future cleanup (the helper's `JsonResponse` return type requires a small adaptation for the redirect-based form flow).

### 3. Email Change Now Requires Ownership Verification

Email addresses are now used as login identifiers (added in v3.3.0) and as the password-reset channel. However, a logged-in session could change the account's email instantly with no confirmation, meaning a hijacked session (e.g., shared computer) could permanently lock out the real user via a password reset to the attacker's address.

**Fix:** Changing an existing email now sends a confirmation link to the new address. The change is not applied until the link is clicked.

- **First-time email set** (when `user.email` is currently null/empty) continues to save immediately — no verification needed for the initial setup.
- **Clearing an email** (setting it to blank) also saves immediately.
- **Changing from one address to another** triggers the token flow.

The confirmation token, email sending, and click-to-confirm view already existed in `src/view/set_email.py` (from prior work). The core send logic was extracted into a `_send_email_confirmation(request, user, new_email)` helper so it is shared between the `set_email` view and `profile_view`.

For AJAX submissions, the profile view returns `{'success': True, 'email_pending': True, 'email_pending_address': '...'}` when a confirmation email was sent instead of an immediate save.

**Changes:**
- `src/view/set_email.py` — Extracted `_send_email_confirmation(request, user, new_email)` from the `set_email` view body. The `set_email` view now calls this helper. `_send_email_confirmation` handles rate limiting, token creation, and email sending.
- `src/view/profile_view.py` — Email block now branches on whether `user.email` is already set. If it is, calls `_send_email_confirmation` and returns early (does not save the new address). First-time set and clearing continue to save immediately. AJAX responses include `email_pending` and `email_pending_address` fields when a confirmation is in flight.

### 4. Removed DRF `TokenAuthentication` and `authtoken` App

`rest_framework.authtoken` was still in `INSTALLED_APPS` and `TokenAuthentication` was still in `DEFAULT_AUTHENTICATION_CLASSES`. No URL for `obtain_auth_token` was registered, and no production code imports `rest_framework.authtoken.models.Token` except a now-deleted Celery pruning task. Previously minted DRF tokens could authenticate any DRF view that didn't override `authentication_classes`.

**Changes:**
- `Parliament/settings_postgres.py` — Removed `rest_framework.authtoken` from `INSTALLED_APPS`. Removed `rest_framework.authentication.TokenAuthentication` from `REST_FRAMEWORK['DEFAULT_AUTHENTICATION_CLASSES']`.
- `src/tasks.py` — Removed `prune_old_auth_tokens` Celery task (it existed solely to clean up the DRF token table).

> **Deploy note:** After deploying, confirm no Celery beat schedule exists for `tasks.prune_old_auth_tokens`. If the schedule was created by `setup_celery_schedules`, it can be deleted from the Django admin under Periodic Tasks.

---

### 5. EventViewSet and AttendanceViewSet Now Paginated

Both viewsets had `pagination_class = None` and implemented their own caps: `EventViewSet` returned all results from a Python list comprehension, `AttendanceViewSet` sliced to `[:100]`. Both now use `ParliamentAPIPagination` (the same paginator used by Legislation and Committee viewsets).

`EventViewSet.list` and `EventViewSet.upcoming` were updated to call `paginate_queryset()` / `get_paginated_response()` since they iterate a Python list rather than a queryset. `AttendanceViewSet` had a custom `list` override with the manual `[:100]` slice — that override was removed, letting the default DRF list action + `ParliamentAPIPagination` handle it.

**Changes:**
- `src/api/views.py` — `EventViewSet`: changed `pagination_class = None` to `ParliamentAPIPagination`; updated `list` and `upcoming` to use `paginate_queryset`/`get_paginated_response`. `AttendanceViewSet`: changed `pagination_class = None` to `ParliamentAPIPagination`; removed the custom `list` override.
