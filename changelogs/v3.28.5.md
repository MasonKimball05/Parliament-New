## The safety net leaked live CSRF tokens into GET request URLs

v3.28.4 added a `document`-level `submit` listener: if a plain `<form>` is
about to submit with an empty (or, after the same-day amendment, missing)
`csrfmiddlewaretoken` field, refresh the token and resubmit rather than
letting the request 403. The listener had no method check, so it treated
every `<form>` on the site the same way — including `method="get"` forms,
which never render `{% csrf_token %}` at all, because Django only checks
CSRF on state-changing methods. On one of those, `tokenField` reads `null`
for a reason that has nothing to do with what the guard exists to catch,
and the existing code still ran the fix: `preventDefault()` the real
submission, await an async token refresh, create a new hidden
`csrfmiddlewaretoken` field, and call `form.submit()`.

On a GET form, `form.submit()` serializes every field — including the one
just created — into the query string. That means a live, valid CSRF token
would have been appended to the URL of **every ordinary site search**
(global search, reachable from the navbar on every page) plus every other
GET filter/search form with a real submit button: `songbook.html`,
`announcements.html`, `kai/view_reports.html`, and `directory.html`'s CSV
export form. A token in a URL ends up in browser history, in
nginx/Cloudflare access logs, and in the `Referer` header sent to any
third-party resource the results page loads — the standard reasons secrets
don't belong in query strings. It also added a needless async round-trip
before every one of those pages loaded, since the listener always
`preventDefault()`s before checking whether there was ever anything to
fix.

(The many `onchange="this.form.submit()"` filter dropdowns — status
filters, assignment filters, etc., mostly in admin-v2 — turned out **not**
to be affected: `HTMLFormElement.submit()` called directly from JS does not
fire a `submit` event per spec, so those never reached this listener in
the first place. The forms that were affected are the ones submitted via
a real `<button type="submit">` or the Enter key, which do dispatch a
genuine, cancelable `submit` event.)

**Not a regression in the amendment** (`91b3eb0`, same day) — the original
`34952f0` version had the identical gap; the amendment only changed how a
present-vs-missing token field is told apart, not which forms the listener
acts on.

## Fix

One line, at the top of the listener, right after the existing
`instanceof HTMLFormElement` check: `if (form.method.toLowerCase() !==
'post') return;`. `form.method` is the IDL attribute, not the raw content
attribute — the browser always normalizes it to `'get'` or `'post'`
(lowercase), including when the `method` attribute is absent (defaults to
GET) or holds something invalid, so no extra fallback is needed.

New `test_it_ignores_get_forms` in `TheCsrfSubmitSafetyNetExistsTests`
(structural, same reasoning as every other test in that class — `base.html`
has no JS test runner in this repo). Asserts the method check runs after
confirming it's a real `HTMLFormElement` (so `form.method` can't throw) and
before the code ever touches `tokenField`. **Verified it fails against the
pre-fix code**: reverted just the new `if` line and reran — `ValueError:
substring not found` (the guard line the test looks for doesn't exist),
confirming the test would have caught this before it shipped.
