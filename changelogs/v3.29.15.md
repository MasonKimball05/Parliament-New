Mason: "The site is not well optimized for iPad. The drop down menu bar
for tabs does not open and the document UI is really bad."

Both turned out to be the same category of bug: a breakpoint or
device-detection check that a mouse-and-keyboard desktop, or a small
phone, would never land in the gap of — but a mid-size touch tablet does.

## Bug 1 — the mobile nav menu could never open from 1024px–1279px wide

`#mobile-menu-button` (`templates/base.html`, the hamburger icon) is
`xl:hidden` — visible on any viewport below 1280px. The panel it toggles,
`#mobile-menu`, was `hidden lg:hidden` — Tailwind's `lg:hidden` forces
`display:none` on it from 1024px up, in a plain CSS media query, with no
regard for the JS `hidden` class the toggle button's click handler
actually flips. So on any viewport from 1024px to 1279px, the hamburger
button rendered and was clickable, but the menu it opens could never
appear — the media query was overriding the JS every time.

Most iPads in landscape orientation fall exactly in that gap: a regular
iPad is 1024px wide landscape, an iPad Air 11" is ~1180px, both squarely
inside the 1024–1279px dead zone. (iPad Pro 12.9" landscape, at 1366px,
clears the gap entirely into the desktop nav instead — and any iPad in
*portrait*, at 768–834px, was never affected either, since that's well
below the 1024px `lg` breakpoint.) That's the "drop down menu bar for
tabs does not open" report.

**Fix:** change the panel's breakpoint to match its own button's —
`hidden xl:hidden` instead of `hidden lg:hidden`. Both now agree on 1280px
as the cutoff, so there's no viewport where the button shows without the
menu being able to.

## Bug 2 — iPads were getting the one PDF viewer WebKit can't scroll

`templates/view_document.html` (the shared document-viewer page behind
every "View" link on Chapter Documents, Committee Documents, and Passed
Legislation) renders PDFs two different ways: an `<iframe>` for "desktop"
(`hidden md:block` — shown from 768px up) or pre-rendered page images for
"mobile" (`md:hidden` — shown below 768px). The comment above the iframe
already explains why: it's there "for better scrolling" on a real desktop
browser, and the image-rendered path exists specifically because WebKit
has never reliably supported scrolling a PDF embedded inside an
`<iframe>` — tapping and dragging inside the frame does little to
nothing, or scrolls only a tiny inner viewport.

The `md` (768px) viewport check was meant to route touch devices away
from the iframe and onto the image-rendered path. It doesn't, for two
compounding reasons: (1) iPadOS 13+ requests desktop sites by default, so
Safari's own user-agent string on a modern iPad reports as a plain
"Macintosh" with no "iPad" token in it at all — there was never a UA
check here to begin with, but even a naive one would miss this; and (2)
every iPad, in portrait or landscape, is comfortably ≥768px wide. Combined,
every iPad landed in the iframe branch — the one branch this file's own
comment says WebKit can't scroll. That's the "document UI is really bad"
report: tap-and-drag inside the embedded PDF barely responds, or scrolls
a tiny inner region instead of the page.

**Fix:** a small inline script (nonce'd, matching this file's existing
iOS-PWA-detection script's convention) that detects Apple touch devices
directly rather than trusting viewport width, and overrides the CSS
choice when it finds one:

```js
var isAppleTouch = /iPad|iPhone|iPod/.test(navigator.userAgent) ||
    (navigator.platform === 'MacIntel' && navigator.maxTouchPoints > 1);
```

The first half is the classic (now largely dead-letter) UA check, kept
for any device that still reports it. The second half is what actually
matters for a real iPad today: a genuine Mac reports
`navigator.maxTouchPoints === 0`, so `platform === 'MacIntel' &&
maxTouchPoints > 1` is the standard way to unmask an iPad that's
disguising itself as a Mac. When either half matches, the script removes
the `<iframe>` outright and strips `md:hidden` off the pre-rendered image
view so it displays regardless of viewport width.

No new server-side work: `pdf_images` (the page-image data the mobile
view renders) is already computed unconditionally for every PDF request
in `_build_document_context()` (`src/view/view_document.py`), not gated
on viewport — so the data this script reveals is already sitting in the
page's DOM, and this is purely a display-toggle fix.
