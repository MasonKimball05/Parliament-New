## 🟡 Double-escaped `alt` text in unsupported-image notices

`src/view/view_document.py::_replace_unsupported_image` called Django's
`escape()` on an `alt` attribute value that was pulled straight off HTML
`_sanitize_docx_html_images` receives *already* `bleach.clean()`-serialized
— meaning already HTML-entity-escaped. Escaping it a second time turned
`&amp;` into `&amp;amp;` and similarly mangled any `<`/`>`/`"` in a docx
image's alt text. Fixed by not re-escaping; the value is already safe for
the HTML context it's inserted into. Removed the now-unused `escape` import.

## 🟡 N+1 in the committee documents page's unpublished-minutes loop

`src/view/committee/documents.py::committee_documents` called
`can_edit_specific_minutes(user, committee, m)` once per unpublished
minutes record, and that function re-ran `can_edit_committee_minutes(user,
committee)` — a `CommitteePermissions.objects.filter(...).exists()` plus a
chair check — every time, even though `user` and `committee` never change
across the loop and the view had *already* computed that exact value one
line above (`can_edit_minutes`) for an unrelated purpose. Added an optional
`can_edit_any` parameter to `can_edit_specific_minutes` (defaults to `None`,
preserving the other three call sites in `committee_minutes_editor.py`
unchanged) and passed the precomputed value through from the loop. Zero
extra queries in the loop now, regardless of how many unpublished minutes
a committee has.

## 🟡 `view_service_submissions` — unbounded, now paginated

The VPP-facing service-hours submissions list had no `Paginator` — every
submission ever made rendered in one response. Paginated the filtered
queryset (`Paginator(submissions, 50)`) *before* the v3.29.23 batch-count
materialization, so that logic now only ever works over one page's worth
of rows. `page_obj` added to the template with the same pagination-nav
markup `activity_logs.html` already uses. Known, accepted limitation:
the "select all N" button for a multi-date batch submission only checks
checkboxes present in the current page's DOM, so a batch of more than 50
dates submitted at once could straddle a page boundary — rows are ordered
by `-submitted_at` and a batch's rows share near-identical timestamps, so
in practice this doesn't happen; documented in a code comment rather than
solved with cross-page AJAX for a case this unlikely.

## 🟠 The 6 dead feature flags — resolved (Mason: wire them up)

Investigating each of the six (`activity_logs`, `calendar`,
`chapter_documents`, `chat_channels`, `committee_documents`,
`login_as_user`) before touching anything found the backlog's framing was
half right: only two were genuinely unwired.

**Four were already covered by a different, real mechanism under a
different name** — wiring the `FeatureFlag` with the same name as the page
would have created a second, do-nothing switch rather than fixing
anything:
- `calendar` / `chapter_documents` / `committee_documents` — each page is
  (and always was) gated by `@require_page_enabled(...)`, which reads
  `PageToggle`, a completely different model these `FeatureFlag` rows never
  touched.
- `chat_channels` — the real chat system (`src/view/chat/`,
  `src/view/committee/chat.py`) is gated by `@require_feature_flag('chats')`
  throughout — a different, already-wired `FeatureFlag`.

Removed these four from `seed_admin_v2.py`'s list (so a fresh install
stops creating the dead rows) and added new
`manage.py prune_dead_feature_flags` (dry-run by default, `--apply` to
delete) to remove them from a database that already ran the old seeder.
The command re-derives "is this name actually read anywhere" at runtime
before deleting each one, rather than trusting its own reasoning to still
be true by the time it runs.

**Two were genuinely unwired, and one of those was a real, live gap:**
- `activity_logs` — now gates `activity_logs_view` and
  `export_activity_logs` (`@require_feature_flag('activity_logs')`) plus
  the nav link in `admin_base.html`. Moved from `seed_admin_v2.py` to the
  canonical `seed_feature_flags.py`, `is_enabled=True` (same default it
  always had).
- 🟠 `login_as_user` — **this one was a genuine, live security gap.**
  `login_as_view.login_as_view` (`/staff/login-as/<id>/`) and a *second,
  independent* implementation in `ParliamentUserAdmin.login_as_user`
  (admin action, `admin.py`) were both reachable by any `is_staff` user —
  which on this model is just `is_admin` — with **no app-level way to turn
  impersonation off short of a code change.** Impersonating a user bypasses
  every permission check the app makes for the rest of that session,
  including the Kai/Slating confidentiality boundaries documented
  extensively elsewhere, since those checks ask "who is the current user,"
  not "is this session an impersonation." Both entry points now check
  `login_as_user`, which is new to `FeatureFlag.DISABLED_BY_DEFAULT`
  (joining `maintenance_mode`, `cnb_foreword`, `qr_attendance_checkin`) and
  seeded `is_enabled=False` — an admin now has to deliberately turn
  impersonation on, then back off, rather than it always being live.
  Deliberately gated only the *start* of impersonation, not
  `return_to_original_user` — turning the flag off mid-impersonation must
  not trap someone in the account they were impersonating. The admin
  action needed an **inline check, not a stacked decorator** —
  `@require_feature_flag`'s wrapper expects `request` first, and a bound
  ModelAdmin method's first argument is `self`, the exact "decorator
  written for views, applied to something else" shape `changelogs/v3.16.2.md`
  (`_get_kai_access`) and `changelogs/v3.24.0.md`
  (`ParliamentUserAdmin`/`@log_function_call`) both already document. Also
  hid the "Login As User" button in the admin list when the flag is off,
  rather than leaving a live-looking link to a 403.

  New `src/tests/security/test_login_as.py::LoginAsUserFeatureFlagTests`
  (8 tests): no-row-fails-closed, explicitly-off, explicitly-on (control),
  both entry points independently, the mid-impersonation-return property,
  and the button visibility. Fixed two pre-existing tests that assumed
  impersonation was always live (`LoginAsViewTest.setUp` now seeds the flag
  on; `test_the_actions_column_still_offers_login_as` in
  `test_user_id_is_permanent.py` does the same, with a note pointing at the
  new class for the flag's own behavior).

## 🟠 `manage_db` — raw stdout dump printed Kai/Slating content and stored secrets

Raised directly by Mason mid-session. `manage.py dump_db` walked
`apps.get_models()` and printed every field of every row to stdout with no
filtering at all — Kai case content, Slating interview notes, API tokens,
WebAuthn credentials, password hashes, everything. None of the app's
existing redaction layers (`kai_audit.py`, the admin's `exclude`-respecting
`export_as_csv`) run anywhere near this code path, since it reads straight
off the ORM outside the admin/API/CSV/search surfaces that boundary was
built at.

New `src/dump_redaction.py`, applied by `dump_db.py` per field instead of
printing the raw value:
1. **Whole-model** — every field (except `id`/timestamps) on any model
   defined in `models.kai`, `models.kai_commendations`, or `models.slating`
   is redacted. Derived from the module, same technique as
   `_model_is_confidential` in `src/models/activity.py` (v3.25.2) — not
   reused directly, since this needs a wider module set and a wider field
   set than that activity-log-specific helper, and coupling a dump tool to
   an unrelated helper is how a fix breaks quietly later.
2. **Named fields** — `APIToken.key`, `EmailVerificationToken.token`,
   `PushSubscription.p256dh`/`.auth`, `WebAuthnCredential.credential_id`/
   `.public_key` (the same list `export_as_csv`'s `exclude` fix closed for
   CSV exports, v3.16.2), `password` on any model, and any field using
   `EncryptedFieldMixin` (currently only IP-address fields — but that
   mixin's `from_db_value` decrypts transparently on every Python-level
   read, so `dump_db` was printing the plaintext straight through the
   encryption and defeating it entirely).

Redacted as `[REDACTED sha256:<16 hex chars>]` — a keyless digest, not a
secret-resistant hash, whose only job is letting two dumps be diffed for
"did this change" without the plaintext ever reaching stdout. Matches
Mason's own phrasing ("encrypted/hashed at the minimum") more literally
than dropping the field would. `None`/blank values pass through unredacted
— "was this ever filled in" is a structural fact a redacted dump should
still answer.

⚠️ **Not covered, flagged rather than guessed at:** per-row anonymous
vote/poll redaction (`Vote`/`CommitteeVote` where
`legislation.anonymous_vote`, `AnnouncementPollAnswer` where
`response.poll.is_anonymous`) needs a relation traversal per row that this
dump tool's flat per-field loop isn't structured for. Also out of scope on
purpose: `backup_db.py` (real `pg_dump -Fc` backups) — that's a
restore-capable disaster-recovery mechanism that has to contain real data
to be useful, stored access-controlled server-side, a genuinely different
job from `dump_db`'s human-readable stdout export.

New `src/tests/security/test_dump_redaction.py` (19 tests): module
detection, Kai/Slating field redaction, the safe-field allowlist
(id/timestamps pass through), blank values pass through, digest stability
(same value → same digest, changed value → different digest), all four
named-secret-field pairs, `password`, a non-confidential-model control, and
one end-to-end test that runs the real `dump_db` command against a Kai
report with unique marker strings and asserts neither marker appears in
the output.
