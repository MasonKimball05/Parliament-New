## Bug Fixes

### Timezone Display — Global Fix (CST/CDT)

**Problem:** Timestamps across the site (emails, logs, admin panel, security reports) were displaying in UTC (e.g., "2:00 AM") instead of the local Central time (e.g., "8:00 PM").

**Root Cause:** `TIME_ZONE` in `base_settings.py` was set to `'UTC'`. Django's template `|date` filters respect this setting automatically, but Python `strftime()` calls in views bypassed it entirely.

**Solution:**
1. Changed `TIME_ZONE` default to `'America/Chicago'` — this alone fixes all template `|date` filters site-wide.
2. Wrapped all `timezone.now().strftime()` and datetime `.strftime()` calls in views/models with `localtime()` to convert to the configured timezone before formatting.
3. Added `%Z` to all timestamp format strings so emails and logs show the timezone abbreviation (e.g., "CST" or "CDT").

**Files Changed:**
- `Parliament/base_settings.py` — `TIME_ZONE = os.getenv('TIME_ZONE', 'America/Chicago')`
- `src/notifications.py` — console log timestamps
- `src/security_notifications.py` — all 4 timestamp calls
- `src/context_processors.py` — server time display
- `src/view/kai_reports.py` — all email body timestamps + CSV exports
- `src/view/officer/manage_members.py` — last login display
- `src/view/officer/user_list.py` — last login display + export
- `src/view/service_hours.py` — submitted/reviewed timestamps in emails
- `src/view/activity_logs.py` — log timestamp display
- `src/view/slating/transition.py` — transition completion messages
- `src/view/slating/results.py` — results email timestamps
- `src/utils/security_utils.py` — unusual login time detection (critical: was checking UTC hour)
- `src/admin.py` — last login, login history, maintenance, activity log inline
- `src/models_feature_flags.py` — scheduled maintenance `__str__` and notification email
- `templates/emails/announcement_notification.html` — added `T` format token to `|date` filters

**Notable security fix:** The "unusual login time" detection in `security_utils.py` was checking whether it was 2–6 AM in UTC. A login at 8 PM CST is 2 AM UTC, causing normal evening logins to be flagged as suspicious. Now correctly checks local time.

**Solution:** After regenerating the PDF in `save_committee_minutes_data`, the linked `CommitteeDocument` record's `title` and `description` fields are now synced to match the updated minutes.

**Files Changed:**

**Problem:** There was no way to navigate from the committee documents page back to the minutes editor for an existing published document.

**Solution:** The committee documents view now reverse-queries `ChapterMinutes` to find which minutes are linked to each document. An "Edit Minutes" link is shown on documents that have linked minutes, gated by the `can_edit_committee_minutes` permission.

**Files Changed:**
- `src/view/committee/documents.py` — added `ChapterMinutes` reverse lookup, `linked_minutes_map`, `can_edit_minutes` context
- `templates/committee/documents.html` — added "✏️ Edit Minutes" link

### Admin-v2 — Performance Metrics (Multi-Worker Cache)

**Problem:** Performance metrics on the admin-v2 dashboard showed 0 or inconsistent data in production because the cache was stored in a process-local Python dict. With multiple Gunicorn workers, each worker had its own separate dict and could not see metrics recorded by other workers.

**Solution:** Replaced the in-process dict cache with Django's shared cache backend (Redis in production), so all workers read from the same store.

**Files Changed:**
- `src/view/admin_v2.py` — performance metrics now use `cache.get`/`cache.set` instead of a module-level dict

---

### Admin-v2 — Activity Logs Blank Page

**Problem:** The activity logs page in admin-v2 rendered blank — no content was visible.

**Root Cause:** The template extended `base.html` and used `{% block admin_content %}`, but the base template expected `{% block content %}`.

**Solution:** Renamed the block to `content` to match the base template.

**Files Changed:**
- `templates/admin_v2/activity_logs.html` — `{% block admin_content %}` → `{% block content %}`

### Manage Roles — "Grant Admin" Hidden from Non-Admins

**Problem:** The "Grant Admin Access" option in the manage roles page was visible to non-admin officers, allowing them to escalate privileges.

**Solution:** The option is now hidden in the template and the server-side view validates that the requesting user is an admin before applying the grant.

**Files Changed:**
- `src/view/officer/manage_roles.py` — server-side admin check before granting admin access
- `templates/officer/manage_roles.html` — "Grant Admin" option gated by `{% if user.is_admin %}`

### IP Blocking — Blacklist Enforcement in Security Middleware

**Problem:** IPs added to `IPBlacklist` were logged but not actually blocked — the security middleware checked the blacklist incorrectly and always allowed requests through.

**Solution:** Fixed the blacklist query in security middleware to correctly match the request IP against active blacklist entries and return a 403 response.

**Files Changed:**
- `src/middleware/security.py` — fixed `IPBlacklist` lookup and enforcement

---

### Honeypot — Cache Fix

**Problem:** The honeypot view was calling `cache.set` with positional arguments in the wrong order, causing geo cache lookups to always miss.

**Solution:** Corrected the argument order to `cache.set(key, value, timeout)`.

**Files Changed:**
- `src/view/honeypot.py` — fixed `cache.set` argument order

## Enhancements

### Announcement Emails — Inactive Member Management

**Problem:** There was no way to include inactive or alumni members in announcement email sends.

**Solution:** Added a collapsible "Include Inactive Members" accordion section to the announcement email confirmation page. Each inactive member has an individual Add/Remove button with a confirmation dialog. Added members are tracked via an `extra_user_ids` URL parameter, so the warmup system generates previews for the exact set of recipients before sending.

**UX details:**
- Accordion is closed by default; auto-opens if any members have been added
- Each Add/Remove triggers a `confirm()` dialog, then cancels the current warmup and navigates to the updated URL
- The "Manually Added Inactive" members are shown as a separate subsection in the recipients preview
- Cancel/skip warmup now queries the DB for active warmup logs instead of using hardcoded cache keys (supports the dynamic cache key scheme)

**Files Changed:**
- `src/view/officer/manage_announcements.py` — `confirm_announcement_email`, `warmup_announcement_email`, `send_announcement_emails`, `cancel_warmup_announcement_email`, `skip_announcement_email`
- `templates/officer/confirm_announcement_email.html` — collapsible accordion, per-member Add/Remove, recipients subsection

### Service Hours — VPP Email Notification on Submission

**Problem:** The VPP had no way to know when a member submitted service hours without manually checking the dashboard.

**Solution:** When a member submits service hours (for a period that requires approval), an email is automatically sent to all users holding the VPP role. If no VPP is assigned, the email falls back to admin users. Resubmissions after a rejection also trigger the notification.

The email includes the member's name, hours, organization, description, period, and a link to the VPP dashboard.

**Files Changed:**
- `src/view/service_user_dashboard.py` — added `_notify_vpp_new_submission()` helper; called after new submissions and after rejection resubmits

## Legislation Bug Fixes & Improvements

### Pending Legislation Hidden from Voting Page (Bug Fix)

**Problem:** Legislation with `pending` status was appearing on the `/vote/` page even though voting had not started.

**Fix:** Added `'pending'` to the excluded statuses in the vote page queryset. Only `active` legislation now appears on the voting page.

**Files Changed:**
- `src/view/vote_view.py` — added `'pending'` to exclude list

---

### Tabled → Pending No Longer Shows as "All Closed" (Bug Fix)

**Problem:** When transitioning legislation from `tabled` back to `pending`, it still appeared under the "All" (closed) tab in the legislation list because `voting_closed` was not being reset.

**Fix:** The `pending` status transition in the edit view now explicitly sets `voting_closed = False` and clears `voting_ended_at`, matching the expected lifecycle of pending legislation.

**Files Changed:**
- `src/view/edit_legislation.py` — reset `voting_closed` and `voting_ended_at` on transition to `pending`

---

### Co-Authors for Legislation (Feature)

Authors can now add co-authors to a piece of legislation. Co-authors receive the same edit permissions as the primary author.

**How it works:**
- A searchable checkbox list of active/inactive members appears in the legislation edit form
- Any checked member becomes a co-author and can edit the legislation
- Co-authors are managed per-save (checking/unchecking updates the list)

**Files Changed:**
- `src/models.py` — added `co_authors` ManyToManyField to `Legislation`
- `src/view/edit_legislation.py` — `is_author` check now includes co-authors; co_authors saved on form submit
- `templates/edit_legislation.html` — co-author searchable checkbox list
- `src/migrations/0140_add_legislation_co_authors.py` — new migration

---

### Transfer Primary Authorship (Feature)

Officers, admins, and the primary author can now transfer ownership of a piece of legislation to another member.

**How it works:**
- A "Transfer Primary Authorship" section appears at the bottom of the edit form
- Selecting a member and confirming transfers `posted_by` to that member
- The previous primary author is automatically added as a co-author so they retain edit access
- If the new author was already a co-author, they are removed from the co-authors list to avoid duplication

**Files Changed:**
- `src/view/edit_legislation.py` — handles `action_type=transfer_authorship` POST action
- `templates/edit_legislation.html` — transfer authorship form section

## Deployment Notes

1. **Migration required** — run `python manage.py migrate` to apply `0140_add_legislation_co_authors` (adds the `co_authors` M2M table to `Legislation`).

2. **`TIME_ZONE` environment variable** — if `TIME_ZONE` is explicitly set in your environment or `settings_postgres.py`, it will override the new default. Remove or update it to `America/Chicago` if needed.

3. **Verify timezone display** — after deploying, check a few timestamps in the admin panel and in sent emails to confirm CST/CDT is shown instead of UTC.
