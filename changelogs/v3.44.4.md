## 🔴 One scanned PDF took the site down (PDF preview memory)

**What happened (10-04-26, evening):** the site stopped answering, and came
back only briefly after each restart. systemd showed the process had not
crashed: it was running, at a 571.8 MB memory peak with 377 MB in swap, and
Daphne was logging `/chapter-documents/view/74/ ... took too long to shut down
and was killed`. Document 74 is a 5-page, 4.3 MB scanned PDF.

### Cause
`convert_pdf_to_images` (`src/view/view_document.py`) renders a PDF's pages
into the viewer page for phones and iPads. It rendered each page at 150 dpi
of the size the PDF declares. A scan often declares its page in
pixels-as-points (for example 2550 x 3300 pt), which makes one page a
5,300 x 6,900 pixel bitmap: over 100 MB raw, plus PNG and base64 copies.

Two things turned that into an outage:
- Daphne runs every ordinary view on one shared thread, so nothing else is
  served while one conversion runs.
- The work is done for every viewer, desktop included, and again on every
  load. Anyone opening the document restarted the stall.

This code is from September and was not changed by v3.44.1–v3.44.3.

### Fix
- Each page is rendered to at most 1400 x 2000 px
  (`PDF_PREVIEW_MAX_WIDTH_PX`, `PDF_PREVIEW_MAX_HEIGHT_PX`). An ordinary
  letter page is under that and renders exactly as before (1275 x 1650).
- Pages are JPEG (quality 80) instead of PNG, and MuPDF's image cache is
  released after each page.
- The template takes the image type from the data (`page.mime`).

### Also fixed: the preview threw its work away
The function read `len(doc)` after `doc.close()`. Current PyMuPDF raises on
that, the `except` caught it, and the function returned `None` after doing
all the rendering. With PyMuPDF 1.27.2.3 (the pinned version) every PDF
therefore showed the "Open the PDF in your device's viewer" fallback on
phones. The page count is now read while the document is open. I did not
check which PyMuPDF version prod has.

### Measured (synthetic 5-page scan, 2550 x 3300 pt pages, cloud machine)
| | Time | Peak memory | Result |
|---|---|---|---|
| Before | 24 s | 669 MB | `None` |
| After | 2.7 s | 232 MB | 5 pages, 2.4 MB |

About 165 MB of both peaks is the Django process itself. A 60-page text PDF
(50 rendered): 3.6 s, 167 MB peak.

### Not done
- The conversion still runs inside the request, for every viewer. Rendering
  pages on demand (one request per page) would remove the remaining few
  seconds from the shared thread. Not built.
- The real document 74 was not available to test with; the synthetic scan is
  larger than it.
- The live systemd unit has no memory limit and runs as `User=root`; the
  unit file in the repo has `MemoryLimit=256M` and `User=parliament`.
