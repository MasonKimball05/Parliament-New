## 🟠 1. `EmergencyLockdownMiddleware` read the `SystemLockdown` singleton on every request

`src/middleware/lockdown.py:36` → `src/models/security.py`, `get_instance()`.

```python
instance, _ = cls.objects.get_or_create(pk=1)   # one SELECT, no cache
```

Exempting only `/static/`, `/media/`, `/health/` and `/favicon.ico`, so
**everything else paid it** — the landing page, the login page, every 404,
every scanner probe, every anonymous hit on a public route.

**This was wider than the 08-05 finding it sits beside.** `Enforce2FAMiddleware`
costs more queries but only for *authenticated* requests to non-exempt paths;
this had in effect no exemption at all, which made it the widest per-request DB
read in the application. Anonymous traffic on a public-facing site is not a
rounding error, and unauthenticated requests are the ones you most want to be
cheap when someone is hammering you.

The value is the best cache candidate in the codebase: a singleton row whose
`is_active` is `False` essentially permanently.

**Fix.** `get_instance()` caches, with a `post_save`/`post_delete` receiver at
the bottom of `models/security.py`.

⚠️ **This caches a SECURITY CONTROL, and the invalidation is the load-bearing
half.** A stale `is_active=False` means an activated lockdown does not take
effect — failing open — and a five-minute TTL delay defeats the word
*emergency*. Two decisions follow from that:

* **A signal, not a `cache.delete` in `activate()`/`deactivate()`.** Those two
  methods are not the only writers: `SystemLockdownAdmin` (`admin.py:2130`)
  lets an admin edit `is_active`, `whitelisted_ips` and `message` directly on
  the changeform, and that path calls `save()` without going near `activate()`.
  A delete inside the two methods would have covered one path and *looked*
  complete — the exact shape of the five-release pattern in `CLAUDE.md`.
  `SystemLockdownCacheTests.test_a_plain_save_also_invalidates` fails against
  that weaker implementation and passes against this one.
* **The TTL is a backstop, not the mechanism.** Same reasoning already written
  down for `FeatureFlag` in v3.17.3.

Caching also removes a quieter problem: `get_or_create` in a request path means
that if the row is ever missing, every concurrent request races to create it.

## 🟠 2. The `IPBlacklist` gate skipped `/admin/` and the public contact form

`src/middleware/security.py`, `InputSanitizationMiddleware`.

`__init__` defined `skip_paths` with a correct and explicit rationale — these
are paths whose *content* trips the SQLi/XSS regexes (a rich-HTML editor, a
free-text contact form, officer legislation notes). `__call__` returned early
for any of them. The `IPBlacklist` enforcement sat **below that early return**,
under this comment:

```python
# Enforce IPBlacklist for all requests (…)
```

It was not all requests. It was all requests except eight, two of which matter:

* **`/admin/`** — the Django admin in its entirety, the single most-probed path
  on any Django deployment;
* **`/contact/submit/`** — public, unauthenticated, `csrf_exempt` by design.

**What makes this concrete rather than theoretical is the honeypot.**
`view/honeypot.py:120` auto-inserts a tripping IP into `IPBlacklist` with the
comment *"so InputSanitizationMiddleware blocks this IP"*. The designed flow is
scanner trips honeypot → gets blacklisted → middleware blocks it. A scanner
that trips the honeypot and then walks to `/admin/` — which is what scanners do,
in that order — was not blocked. The mechanism is aimed squarely at automated
probing and had a hole at the probe target.

**Why 🟠 and not 🔴.** Blacklisting is defence-in-depth, not the access control.
Both login paths check `IPBlacklist` themselves before `authenticate()`
(`login_view.py:207`, and `security_utils.py:347` on the passkey path), and
Django admin's login redirects to `login_view` via `LOGIN_URL` — so a
blacklisted IP still could not log in. What it gained was *reach*: enumeration
and probing of the admin surface, and posting to the public contact form.

**Fix.** The gate moved above the early return, with its own short exemption
list (`/static/`, `/media/` — nginx serves both in production, so the exemption
is a dev-time cost saving and nothing more). `skip_paths` renamed
`skip_scan_paths` so the name says which control it governs, with a ⚠️ block
above it explaining why the two lists must not be merged back together. No
alias kept: verified no other reader in the tree, and a compatibility shim
nobody needs is one more thing to believe.

**This is the codebase's recurring shape with the polarity flipped.** `CLAUDE.md`
records five releases of *"a rule stated correctly, a helper written to enforce
it, then something left outside the helper."* Here the rule was stated in a
comment that was simply false, and the thing left outside was a set of paths.
The skip list was correct for the job it was written for; it was inherited by a
second, unrelated job four months later and never re-derived for it.

## 🟠 3. Session-hijack detection was blind for half of every cycle

`src/middleware/session_tracking.py`.

Two throttles with different intervals:

```python
self.update_interval_seconds    = 300   # how often the record is REWRITTEN
self.fingerprint_check_interval = 600   # how often it is COMPARED
```

`_check_fingerprint` compared the stored `UserSession`'s browser/OS against the
current request. `create_or_update_session` **overwrites those same two fields**
from whatever User-Agent is on the current request. Both keys are set together
at login, so they stayed in phase:

| t | fp key | update key | What happened |
|---|---|---|---|
| 0 | set (exp 600) | set (exp 300) | Legit UA compared, then stored. |
| ~300 | **alive** | expired | Record **rewritten with no comparison**. A hijacker's UA lands in the baseline silently. |
| ~600 | expired | expired | Compare runs — against the record written at t≈300. Attacker vs attacker. Clean. |

**Any hijack whose first request arrived in the back half of a cycle was never
detected — not late, at all.** The ordering *within* a request was correct
(check first, then update); the bug was entirely in the two interval constants
being different numbers, one of which was smaller.

**Why it survived.** The two throttles read as unrelated tuning knobs — one
described as reducing DB load, the other as avoiding log spam — and both
comments were locally true. Nothing said the values were coupled, and they sat
in different methods twelve lines apart. There was also no negative signal to
notice: **the failure mode of a detector is silence, which is indistinguishable
from safety.**

**Fix, and the shape of it matters.** Not "set 600 to 300" — equal intervals
still race the moment either is touched, and the next person to tune one has no
way to know it is load-bearing. Collapsed to **one throttle key and one ordered
block**: read → compare → write. `_check_fingerprint` now takes the
already-fetched row rather than re-querying by session key, which is what makes
it *impossible* to call it against a baseline the caller has already
overwritten. The invariant is stated at the call site:

> the stored fingerprint is never rewritten without first being compared
> against the request doing the rewriting.

It is also **cheaper**: one `SELECT` plus one `update_or_create` on the
throttled path where the two paths previously issued their own `SELECT`s, and
one `cache.get` per authenticated request instead of two.

**Behaviour deliberately unchanged:** detection still logs and lets the session
continue. Confirmed as the intended choice 08-06-26 — a genuine browser upgrade
changes the User-Agent, and logging a member out for updating Chrome is worse
than the thing being detected. Recorded in the docstring as a decision rather
than a default, with the notification path named as the softer option if it is
ever revisited.

## 🟠 4. Performance monitoring reported zeros — three causes, one root

`performance.py` was rewritten from a process-local dict to the shared cache.
Its three readers were not updated. Each failed differently, and none loudly.

**(a) `/api/debug/performance/` read a cache key nothing writes.**
`debug_panel.py:426` read `perf_metrics_recent`; the middleware writes
`perf_requests`. `git log -S` dates the read to `dfa42a9` (2026-02-08) and the
key was **never written by anything, at any point** — so this endpoint returned
zeros on every call it has ever served, for six months. The shapes did not match
either: it did `m.get('response_time')` on each entry and the middleware stores
plain *tuples*, so even with the key corrected it would have raised
`AttributeError`. Two independent breaks stacked, the outer masking the inner.

**(b) `db_query_count` was structurally zero in production.**
`len(connection.queries)` is populated only when `connection.queries_logged` is
true, and that is `force_debug_cursor or settings.DEBUG`
(`django/db/backends/base/base.py:170`). Production runs `DEBUG=False`, so the
delta was always 0. Consequences:

* `avg_db_queries` / `avg_db_time_ms` permanently 0 (mitigated: the dashboard
  template renders only `slow_requests`, so no tile showed a wrong number);
* **the slow-request alarm always blamed something other than the database** —
  `Slow request: … (0 queries, 0ms DB time)`, on every slow page, forever. In a
  codebase whose last six weeks are almost entirely N+1 hunts, an alert that
  fires on a slow page and reports no database work points the investigator away
  from the answer roughly every time.

The tell that this was an oversight and not a decision: `db_time_ms` was already
wrapped in `if settings.DEBUG`, one statement *below* the unguarded count. The
author knew DEBUG gates the query log, guarded the timing line, and missed the
counting line directly above it.

**(c) `memory_report` imported a name deleted in April.**
`from src.middleware.performance import get_performance_summary, _performance_metrics`
— `_performance_metrics` was removed in `f341820` (2026-04-08). The import sat
inside `except Exception as e`, so section 6 printed
`Error: cannot import name '_performance_metrics'` where the stats should be,
and took `get_performance_summary` — in the same statement, working fine — down
with it. Four months. The second use sat under a bare `except Exception: pass`,
so its recommendation could never fire and said nothing about why.

**Why the whole cluster went unnoticed: there is a *working* performance tool.**
`DevModeMiddleware` uses `connection.execute_wrapper`, which is independent of
`DEBUG` — that is why prod dev mode could find the N+1s in v3.18.3 and v3.18.6
that this middleware could not. A broken tool sitting beside a working one gets
no traffic and therefore reports no errors.

**Fixes.**

1. New `_QueryCounter` wired through `connection.execute_wrapper` — the same
   mechanism `dev_mode.py:78` already uses, so there is a working local model.
   Counts and times in a `finally` so a *failing* query is still counted, which
   is exactly when the number matters. Single-database only; if that ever
   changes it counts a subset rather than reporting zero, which is the better
   failure. The now-unused `settings` import is gone.
2. `debug_performance_metrics` rewritten to delegate to
   `get_performance_summary()` / `get_slow_requests()`, with the tuple entries
   serialised field by field (a datetime is not JSON).
   **⚠️ Deviation from the review, recorded deliberately:** the 08-06 report
   suggested *deleting* this endpoint on the grounds the dashboard covers it.
   Kept and rewritten instead — it is one of six sibling `/api/debug/*`
   endpoints, deleting one member of that family leaves a hole for the next
   person to wonder about, and the rewrite was ten lines against a data source
   that already existed. The report's underlying concern (two readers of one
   metric drifting apart) is answered by delegating rather than re-aggregating.
3. `memory_report` reads `get_performance_summary()` and `MAX_STORED`, now also
   prints avg queries/request, and its bare `except Exception: pass` is narrowed
   to `(KeyError, TypeError, ValueError)` — an `ImportError` there should be a
   traceback, not a silently absent recommendation. Third instance this month of
   `CLAUDE.md`'s rule that a guard swallowing exceptions reports the absence of
   a signal as the absence of a problem.

## 🟡 5. `src/middleware/__init__.py` exported four of ten middlewares

It re-exported four classes plus four performance helpers, via an `__all__` that
read as authoritative and was missing more than half the chain — including every
security middleware (`security.py` alone holds six). **Nothing in the tree
imported any of it:** `settings.MIDDLEWARE` names every middleware by full
dotted path, and the two real consumers of the performance helpers import from
`src.middleware.performance` directly.

So the list served no importer and misinformed every reader. Rather than grow it
to ten and take on keeping it in step with `settings.py`, it is **gone**:
`settings.MIDDLEWARE` is the single register of what runs, and module paths are
how you import. One place to look, and it is true by construction because Django
reads it.

## 🟡 7. `SiteSetting.get_setting` was the uncached sibling of a cached helper

Carried from the 08-05 review. `src/models_feature_flags.py`: two classes in one
module answering the same shape of question — *look up a row by key, return its
value* — and one had a cache, a documented TTL rationale and `post_save`/
`post_delete` invalidation while the other had none. Nothing about `SiteSetting`
made it a worse candidate; it simply was not the one that hurt in v3.17.1. One
of its seven call sites is `Enforce2FAMiddleware`, on every authenticated
request.

**Fix.** Cached, mirroring `FeatureFlag` exactly, plus a `post_save`/
`post_delete` receiver.

⚠️ **The cache stores whether the ROW EXISTED, not the default.** Callers pass
different defaults for the same key (`get_setting('x', 'none')` vs
`get_setting('x', True)`), so caching a miss as its default would hand the first
caller's fallback to the second. A `found` flag is what keeps a stored `None`
distinguishable from a missing row.
`test_a_cached_miss_does_not_leak_one_callers_default_to_another` is the guard;
it is the subtlety most likely to be lost in a future refactor.

Also fixed: `_seed_site_settings` (`admin_v2.py`) calls `invalidate_cache()`
after its `bulk_create`, because **`bulk_create` sends no `post_save`** — a key
seeded there may well have been asked for and missed already, leaving it cached
absent for the TTL after the row exists. Same bulk-path gap v3.17.3 closed for
flags.

No `_drop_context_dict()` for settings: they are not part of the `feature_flags`
context dict, so there is nothing template-side to keep in step.

## Tests

**New module: `src/test_middleware_hot_path.py`.** Six classes. The assertions
are deliberately about **observable behaviour** rather than implementation — "a
blacklisted IP gets a 403 on `/admin/`", not "the gate is above the early
return", because the second phrasing passes for the wrong reason as soon as
someone rearranges the file.

| Class | What it pins |
|---|---|
| `SystemLockdownCacheTests` | Warm reads cost no queries; activate/deactivate/plain-`save()`/whitelist edits all take effect on the **next** read. The plain-`save()` case is the one that fails against a `cache.delete`-in-`activate()` implementation. |
| `IPBlacklistPathCoverageTests` | 403 on `/admin/` and `/contact/submit/`; a clean IP is **not** blocked (negative control); `/static/` stays exempt; an inactive row does not block; pattern scanning is still skipped where it was; the two path lists are not the same object. |
| `SessionFingerprintOrderingTests` | A changed UA is detected after the throttle expires **and after several cycles** (that second one is the actual regression test); an unchanged UA is not flagged; the write still happens after the compare; the throttle still throttles. |
| `PerformanceQueryCountingTests` | The counter counts with `DEBUG=False` — plus a test asserting `len(connection.queries)` **would** have reported zero, so the first test cannot pass vacuously. |
| `SiteSettingCacheTests` | Warm reads free; misses cached; **a cached miss does not leak one caller's default to another**; `set_setting` and queryset `.delete()` both invalidate; typed values survive the cache. |
| `MonitoringReaderLivenessTests` | The debug endpoint returns non-zero numbers; `memory_report` runs without an import error; no file in `src/` reads `perf_metrics_recent`. |

**New: `MiddlewareChainQueryBudgetTests` in `test_query_budgets.py`** (08-06 idea
11). Measures the chain as its own number instead of as a share of everyone
else's — the blind spot that hid *two* separate findings, since middleware cost
is a constant added to every per-view ceiling and reads as the floor.

⚠️ **It ships WITHOUT a `BUDGET` constant, deliberately — same rule as v3.18.6.**
That module's standard is that a ceiling is a *measured* number, and there is no
working Django here to measure with; an invented ceiling reads exactly like a
measured one. It asserts constant-free properties instead, each of which fails
against the pre-v3.18.7 tree:

* `SystemLockdown` is not queried on a warm anonymous request;
* `SiteSetting` is not queried on a warm authenticated request;
* **an anonymous request is strictly cheaper than an authenticated one** — an
  ordering that was *false* before this release, and the assertion most likely
  to catch the next one of these, because it needs no advance knowledge of which
  middleware or which table;
* the chain reaches a steady state (request N and N+1 cost the same);
* `test_the_chain_reports_its_own_cost` prints cold and warm counts — this is
  the measurement instrument to read the future `BUDGET` off.

## ✅ Test run — 08-06-26

**49 tests, 48 green on the first run.** The single failure was **a defect in a
new test, not in the code**, and it is worth recording because it is this
codebase's own rule catching its author:

`test_no_view_reads_the_dead_perf_cache_key` grepped every file in `src/` for
the literal string `perf_metrics_recent` and failed on `view/debug_panel.py` —
whose **docstring names the key while explaining the bug**. The code no longer
reads it; the prose mentions it. A substring search cannot tell those apart, so
the test failed on documentation and would equally have passed on a read
spelled any other way. v3.18.4: *an assertion that cannot distinguish the bug
from the fixture is not an assertion.*

Rewritten to parse rather than grep: walk the AST and collect string literals in
the **first-argument position of a `cache.get`/`cache.set`/`get_or_set`/`delete`
call**. Comments and docstrings are invisible to that by construction, which is
exactly the distinction that was missing. Verified: the AST check returns `[]`
while the old grep returned `['view/debug_panel.py']`.

**Also fixed:** `test_the_chain_reports_its_own_cost` printed the label
`authenticated GET /` while measuring `reverse('home')` (`/home/`) — a stale
label of precisely the kind §8 of this release exists to correct. It now prints
the URL it measured.

**First measurement of the middleware chain** (authenticated GET `/home/`,
sqlite):

```
cold: 42 queries    warm: 20 queries
```

The 22-query gap is the size of the caching layer across a whole request. See
item 2 below before pinning either number.
