## 🟢 Mobile Phase 3 (part 2): Calendar endpoints

Under `/api/mobile/v1/`, for the app's Calendar tab:

- **`GET events/?from=YYYY-MM-DD&to=YYYY-MM-DD`**: visible events in a date
  range, in the chapter's time zone with `to` inclusive. Defaults to today
  plus 31 days. At most 93 days per request, within a year either side of
  today (the web calendar's window).
- **`GET events/<id>/`**: one event. Hidden, inactive or archived is a 404.
- **`POST` / `DELETE events/<id>/signup/`**: sign up (or join the waitlist)
  and cancel. Refusals are `{"error": "signup_refused", "detail": <the web
  page's message>}`.
- **`GET calendar/subscription/`**: the member's `webcal://` feed URL, for
  "Subscribe". Behind the `calendar_subscriptions` flag, like the web.

Each event has its sign-up state (counts, full, waitlist, the member's own
status), excuse state (`Event.can_submit_excuse`, any excuse's status), add-to-
calendar links and `updated_at`, so the app can refresh a cached event.

**Same rules as the website.** The audience rule is `visible_to_q`, the SQL
twin of `Event.is_visible_to_user`. The `calendar` page toggle and pledge
restriction apply through `web_page`. Sign-up also honours restrictions on the
web buttons' own names (`event_signup`, `event_cancel_signup`), because on the
web those are separate restrictable routes.

**Sign-ups are one implementation.** The join/cancel logic (row lock,
waitlist, promotion on cancel, 404 for an event you can't see) moved out of
the two web views into `src/event_signups.py`. The website's buttons and the
app both call it. Unlike `/api/calendar-data/`, the app's list fetches
sign-up counts and the member's own sign-ups and excuses once per page, not
per event (the query count is the same for 3 events and 13).

## 🟠 Fixed: the last sign-up slot could never be taken

`event_signup` saved the member's new sign-up as confirmed (`get_or_create`)
and only then counted confirmed sign-ups to see if a slot was free, so it
counted the member themself. On an event with N slots the Nth person was put
on the waitlist, or refused with "This event is full" if there was no
waitlist. A 1-slot event waitlisted its first sign-up. Their own row is now
left out of the count. Regression tests go through both the web button and
the app, and both fail with the old count.

## 🟢 Subscribed calendars now see edits (`Event.updated_at`)

The feed sent every event with `LAST-MODIFIED` = creation time and
`SEQUENCE:0`, so calendar apps kept the first copy they saw: a moved or
renamed event stayed wrong on members' phones. Events now have `updated_at`
(`auto_now`). The feed sends it as `LAST-MODIFIED`, and `SEQUENCE` is
`Event.ical_sequence` (seconds from creation to the last edit: 0 until edited,
higher after each one, no counter to maintain).

- Bookkeeping saves with `update_fields` (reminders, RSVP emails) don't count
  as edits.
- "This and following" / "all" series edits use `bulk_update`, which skips
  `auto_now`, so `apply_series_edit` stamps the moved occurrences itself.
- The migration backfills existing events to `created_at`, so nothing looks
  edited and subscribed calendars don't all refresh at once.

This was the plan's Phase 0 item "bump `sequence` on edits".
