## Overview

This security-focused release adds multiple layers of protection against common web attacks, implements session management for users to monitor and control their active logins, and adds rate limiting to prevent brute force attacks on the login system.

---

## Security Features

### Login Rate Limiting

Implements cache-based rate limiting to prevent brute force attacks on the login page.

**Configuration:**
- **Maximum Attempts:** 5 failed login attempts
- **Lockout Duration:** 15 minutes
- **Attempt Window:** 15 minutes (attempts reset after this period)

**How It Works:**

1. Each failed login attempt increments a counter stored in Django's cache
2. After 5 failed attempts, the IP address is locked out for 15 minutes
3. Successful login clears all attempt counters
4. Lockout applies to both invalid credentials and disabled accounts

**User Feedback:**
- Warning shown when only 2 attempts remain
- Clear message shows remaining lockout time
- All rate limiting events are logged to security logs

**Files Changed:**
- `src/view/login_view.py` - Added rate limiting functions and integration

### SQL Injection & XSS Protection

Added `InputSanitizationMiddleware` that detects and blocks common attack patterns in all incoming requests.

**Attack Patterns Detected:**
- SQL injection (UNION, SELECT, DROP, etc.)
- Cross-site scripting (XSS) attempts
- Path traversal attacks (../, etc.)
- Command injection attempts

**Blocking Behavior:**
- First 10 attacks: Logged with warning
- After 10 attacks in 1 hour: IP automatically blocked for 1 hour

**Security Headers Added:**
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: SAMEORIGIN`
- `X-XSS-Protection: 1; mode=block`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: geolocation=(), microphone=(), camera=()`

**Files Changed:**
- `src/middleware/security.py` - Added `InputSanitizationMiddleware`
- `Parliament/settings_postgres.py` - Registered middleware

### Session Viewer

Users can now view and manage all their active login sessions, with the ability to remotely log out of any session.

**Features:**
- View all active sessions with device type, browser, OS, and IP address
- See when each session was created and last active
- Identify current session vs. other sessions
- Log out individual sessions remotely
- Bulk "Log Out All Other Sessions" action

**Session Tracking:**
- Device type detection (mobile, tablet, desktop)
- Browser detection (Chrome, Firefox, Safari, Edge, etc.)
- Operating system detection (Windows, macOS, iOS, Android, Linux)
- IP address logging
- Last activity timestamp

**Security Logging:**
- Session revocation events logged to security logs
- Bulk logout events logged with count

**New Files Created:**
- `src/view/session_viewer.py` - Session management views
- `templates/account/sessions.html` - Session list UI

**Files Changed:**
- `src/models.py` - Added `UserSession` model
- `src/urls.py` - Added session management URL routes
- `src/view/login_view.py` - Create session record on login
- `templates/preferences.html` - Added Security & Privacy section with links

## New Models

### UserSession

Tracks active user sessions for security monitoring.

| Field | Type | Description |
|-------|------|-------------|
| `user` | ForeignKey | The user who owns this session |
| `session_key` | CharField | Django session key |
| `ip_address` | GenericIPAddressField | Client IP address |
| `user_agent` | TextField | Raw user agent string |
| `device_type` | CharField | mobile, tablet, or desktop |
| `browser` | CharField | Detected browser name |
| `operating_system` | CharField | Detected OS |
| `location` | CharField | Reserved for future geo-IP |
| `created_at` | DateTimeField | Session creation time |
| `last_activity` | DateTimeField | Last request time |

**Methods:**
- `parse_user_agent()` - Extracts device, browser, and OS from user agent string
- `create_or_update_session()` - Creates or updates session record for a user
- `cleanup_expired_sessions()` - Removes records for expired Django sessions

## New Features

### Legislation Tracker Enhancements

The legislation page has been renamed to "Legislation Tracker" and significantly enhanced with new filtering and management capabilities.

**Status Filtering:**
- Added tabbed navigation to filter legislation by status
- Status tabs: All Closed, Pending, Active, Passed, Failed, Tabled
- Each tab shows count of items in that status
- Filter preserves across pagination

**Add Legislation (Officers/Admins):**
- New "Add Legislation" button in header
- Modal form to add legislation with:
  - Title (required)
  - Status selection (Pending, Active, Passed, Failed, Tabled)
  - Description (required - minimum 20 chars if no document)
  - Document upload (optional PDF/DOC/DOCX)
  - Historical vote counts (optional - Yes/No/Abstain)
  - Required percentage setting

**Historical Vote Tracking:**
- New model fields to store manual vote counts
- `historical_yes_votes`, `historical_no_votes`, `historical_abstain_votes`
- Allows recording votes for legislation entered after the fact

**Files Changed:**
- `src/models.py` - Added historical vote fields to Legislation model
- `src/view/passed_legislation.py` - Added filtering, add_legislation view
- `src/urls.py` - Added add_legislation route

### Edit Tabled/Pending Legislation

Added the ability to edit and reintroduce tabled or pending legislation back to voting.

- Authors, officers, and admins can edit tabled or pending legislation
- Status dropdown allows changing between Pending, Active, and Tabled
- Changing to "Active" reopens voting and reintroduces the legislation to the vote page
- Edit buttons appear on legislation cards in the Legislation Tracker for editable items
- Passed and failed legislation cannot be edited (must submit new version)

**Permissions:**
- Authors can edit their own pending/tabled legislation
- Officers and admins can edit any pending/tabled legislation
- Legislation with active voting cannot be edited (except by admins)

**Files Changed:**

## Security Recommendations

After deploying this update:

1. **Monitor Logs:** Review security logs for attack attempts
2. **Configure Redis:** Rate limiting works best with Redis cache (shared across workers)
3. **Review Sessions:** Encourage users to check their active sessions
4. **Enable 2FA:** Combine with 2FA for maximum security
