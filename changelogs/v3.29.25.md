v3.28.4's original "empty field" safety net itself, which had already
shipped, been unit-tested, and was believed sound.

## Root cause: a failed refresh was silently treated as a submit-anyway

`refreshCsrfToken()`'s `fetch()` call can itself fail — not because the
token or cookie are wrong, but because the network genuinely isn't ready
yet. The exact scenario this bug lives in (a native file-picker sheet
backgrounding a mobile tab, then the member returning to it) is also
exactly the scenario where the OS may still be re-establishing the
network connection in the first moment the tab resumes. A `fetch()`
issued right then can fail outright.

Before this fix, that failure was swallowed
(`.catch(function() { return null; })`) and the submit-time safety net's
`.then(function(token) { ... form.submit(); })` ran `form.submit()`
**unconditionally** at the end regardless of whether `token` came back
null. If the field had never had a usable value (the missing-field case
this whole mechanism exists for), it still didn't after the failed
refresh — so the resubmission went out with the same empty field,
reproducing the exact original 403, immediately, with no retry and no
feedback to the member.

This is a gap in the mechanism itself, not in which forms trigger it —
v3.29.24's file-input change is unrelated to this failure and stays
in place as a correct fix for the different (present-but-stale) case it
targets.

## Fix

Two changes, both in `templates/base.html`:

1. **`refreshCsrfToken()` retries once** on failure, after a 400ms pause,
   before giving up and resolving to `null`. Gated on a new `attempt`
   parameter so it terminates — one retry only, never open-ended. The
   pause is long enough to matter for "the network just isn't back up
   yet" without meaningfully slowing down what was already the failing
   path.

2. **The submit-time safety net no longer submits into a guaranteed
   failure.** After the (possibly-retried) refresh resolves: if a fresh
   token came back, use it (unchanged). If it didn't, and the field is
   STILL empty, stop — don't call `form.submit()` — and show a toast
   (`Parliament.toast`, the same mechanism `P.post` already uses for
   failed requests) telling the member to try again. Nothing typed or
   picked is lost; they just get told to retry instead of silently
   hitting the exact bug they were supposed to be protected from.

```js
if (token) {
    tokenField.value = token;
} else if (!tokenField.value) {
    P.toast('Could not verify your session before submitting — please try again.', 'error');
    return;
}
form.submit();
```

## New tests

`TheCsrfRefreshRetriesOnFailureTests` in
`src/tests/security/test_bfcache_reload.py` (7 tests, same structural
convention as the rest of this file — `base.html` has no JS test runner
in this repo):

- the helper takes an `attempt` parameter;
- it retries exactly once on failure (`if (!attempt)` gating a single
  `refreshCsrfToken(1)` call — not an open-ended retry loop);
- the second-failure path still resolves to `null` rather than hanging or
  rejecting;
- a still-empty field after the refresh attempt is not submitted;
- that bail-out branch actually `return`s before `form.submit()` (not
  dead code);
- it tells the member via `P.toast(...)`;
- **control**: a successful refresh still reaches `form.submit()` —
  this is additive, not a new way to block working submissions.

## Known, not fixed here

- Still can't confirm from this sandbox whether the underlying browser
  behavior is "fetch genuinely fails" versus something else that also
  leaves the field empty and happens to be timing-sensitive in the same
  way — no prod log access here, and there's no client-side signal that
  distinguishes "the fetch threw" from other failure shapes inside
  `.catch()`. The retry is a reasonable, low-cost hedge against the
  network-timing explanation either way; if the failure recurs a THIRD
  time with a fresh log line, that log line (particularly whether
  `posted_token_present` is `False` again or something new) is the next
  thing to look at before writing more client-side retries — at some
  point the fix belongs server-side (e.g. a grace-period token) rather
  than in an increasingly elaborate client-side dance.
- The toast message is generic ("please try again") rather than naming
  the mechanism — deliberate, matching `P.post`'s existing 403 message
  style; a member doesn't need to know what a CSRF token is, only that
  retrying is the right next step.
