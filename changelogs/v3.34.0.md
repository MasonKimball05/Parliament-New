## 💡 Manual point adjustments on the education dashboard

Requested by Mason: "can we adjust the amount of points a person has
manually? Add, remove, or otherwise adjust... whether it be current or
maximum." Everything the Pledge Progress card shows (added 09-22-26, see
`v3.33.0`'s sibling work and `src/tests/education/test_education_dashboard_
points.py`) was derived — task points plus meeting attendance points, computed
fresh on every request — with nothing a chair could directly edit for a
one-off bonus, a correction, or a deduction.

- **New `PledgePointAdjustment` model** (`src/models/education.py`) — an
  append-only log, not an editable running total on the pledge or a mutable
  field anywhere. Each row carries `current_delta` and `max_delta`
  (independent signed integers — a chair can adjust either, both, or
  reject an all-zero no-op), an optional `reason`, `created_by`, and
  `created_at`. Undoing an adjustment deletes the row; nothing here is ever
  edited in place. Scoped to a specific education `committee`, matching how
  `education_home` already treats points as committee-scoped.
- **`education_home`** sums every pledge's adjustments (one query, grouped
  in Python — no per-pledge query) into the exact same `ps['points']`/
  `ps['max_points']` the dashboard already renders, so a manual adjustment
  reads identically to an earned point everywhere on the page. A
  `ps['has_adjustments']` flag drives a small dotted-underline + tooltip on
  the points badge so a chair scanning the list can tell at a glance which
  numbers include a manual correction.
- **Two new endpoints**, both gated on `can_manage_tasks` (the same
  permission that already covers editing a task's own point value):
  `education_adjust_points` (create a row; rejects an all-zero submission
  with a 400) and `education_delete_point_adjustment` (remove one row;
  looked up scoped to `committee=committee`, not bare `pk=`, so a chair of a
  *different* education committee cannot delete this one's row by guessing
  or incrementing an id).
- **UI:** one shared "Adjust Points" modal (not one per pledge row) opened
  via the same `data-action` + delegated-listener pattern every other
  control on this page already uses — **not** an inline `onclick=`/
  `onsubmit=`, which prod's CSP (`script-src 'self' 'nonce-…'`, no
  `unsafe-inline`) blocks silently. This page has been bitten by exactly
  that bug before (v3.31.1); the new button and form go through the
  existing delegated `click`/`submit` listeners instead of adding a fresh
  inline attribute. The modal shows a per-pledge adjustment history (add/
  remove/reason/who/when) built server-side into one small JSON payload
  (`_script_safe_json`, same `<` → `<` escaping as `quote_book.py`'s
  copy, needed for the same reason: `reason` is free-text chair input
  rendered into a `<script>` block).
- **Admin:** registered read-only (`has_add_permission`/
  `has_change_permission` both `False`) under the existing "Pledge
  Education" section — the dashboard's own delete action is the correct way
  to undo a mistake; an editable admin row would defeat the append-only
  design the model exists to guarantee.
- **Known gap, not built:** the pledge's own My Tasks page (`total_points` in
  `src/view/pledge_tasks.py::build_pledge_tasks_context`) does **not** read
  these adjustments — a pledge with a manual bonus or correction will see a
  different total on their own page than a chair sees on the dashboard.
  `build_pledge_tasks_context` isn't committee-scoped today (it assumes one
  education committee per pledge), so folding this in cleanly needs that
  question answered first. Flagged in code comments; not fixed in this pass.
