## 1 — 🔴 The Django CI workflow has never passed. Not once, in 400 runs.

GitHub retains 400 runs of `Django CI/CD`. Filtering them:

| filter | result |
|---|---|
| `is:success` | **0 workflow run results** |
| `is:failure` | **400 workflow run results** |

The most recent, `#400` on `f241f45`, reports **Status Failure**, with the
`Run Tests` job exiting 1.

Eight consecutive release notes in this directory open with a green tick and a
test count. Every one of them is honest. **The suite was green on one laptop.**

### Why, exactly — reproduced, not inferred

The suite was run twice on `f241f45`: once with Mason's environment and once
with CI's. Mason's: **1,528 tests, 0 failures.** CI's: **18 failures.**

**15 of them** are `test_two_factor.TwoFactorAdminDashboardTestCase` (13) and
`test_pillar1.AdminV2DashboardContextTests` (2). Both reach an `@require_admin_v2_auth`
view, whose first gate is

```python
on_allowlist = request.user.user_id in ALLOWED_USER_IDS
```

and since v3.17.0 (`619eaae`, 07-29-26) `ALLOWED_USER_IDS` is parsed from the
`ADMIN_V2_USER_IDS` **environment variable** at import. `.env` is gitignored.
Mason's lists `73`; the fixtures use `73`; CI sets nothing, so the allowlist is
empty and every one of those tests is redirected to `/home/`.

Both classes carried a comment explaining the id:

> `# Create admin user - must use user_id='73' for admin_v2 access`
> `# user_id must match ALLOWED_USER_ID ('73') in admin_v2.py`

True when written. **Eight other modules patch the allowlist**; these two
inherited it. This is the fifth entry in the category CLAUDE.md already tracks —
*a comment that was true of a simpler version and was never revisited* — and the
first where the stale comment kept a whole CI pipeline red.

**The other 3** are `test_digest_watchdog`. It does
`@override_settings(BASE_DIR=<tmpdir>)` and the command builds its path as
`os.path.join(settings.BASE_DIR, os.getenv('LOG_DIR', 'logs'))`. `os.path.join`
discards everything left of an absolute component, and CI sets `LOG_DIR: /tmp`.
The override was silently thrown away.

> **A test that overrides a setting has not pinned the value if the code also
> reads the environment.**

### And the alarm was broken too, in the same folder

`.github/workflows/slack.yml` exists to shout when CI fails. Since `dfa42a9`
(02-08-26) it has contained five lines:

```yaml
- name: Slack notification on failure
  if: failure()
  uses: rtCamp/action-slack-notify@v2
  with:
    slack_webhook_url: ${{ secrets.SLACK_WEBHOOK_URL }}
    status: failure
```

That is a job **step**, pasted at the top level of a workflow file. No `on:`, no
`jobs:` — GitHub cannot parse it, so every push produces an instant red run.
**312 runs, 312 failures, zero notifications sent.** Two further errors in those
five lines: the action reads the webhook from the `SLACK_WEBHOOK` *environment*
variable, not a `slack_webhook_url` input, and `failure()` refers to the current
workflow, so even inside a valid one it could only ever have described itself.

> **A notifier that has never fired and a notifier with nothing to report look
> identical from the outside.**

And a permanently-red workflow beside `Django CI/CD` in the same list is part of
why a red run there stopped meaning anything.

### The fix, and why it is in the runner

`src/cache_isolated_runner.py` already exists because *the cache leaked between
tests*. This is the same defect one layer out: **configuration leaking in from
the host.** Both make the verdict a property of how you ran it.

* `_ENV_DERIVED_TEST_DEFAULTS` neutralises the three module-level env-derived
  constants in `src/` — both halves of the admin-v2 allowlist and
  `MEDIA_ACCEL_PREFIX` — from the one call site the parent process and every
  spawned worker already reach.
* The two classes now patch the allowlist like everybody else.
* `test_digest_watchdog` pins `LOG_DIR` as well as `BASE_DIR`.
* New `src/digest_heartbeat.py`: the heartbeat path was written out twice, in
  the writer and in the watchdog that reads it. They did not disagree; this is
  so they cannot start to. A watchdog whose reader and writer compute a path
  independently can be permanently wrong in the quietest way available, and its
  alert would send you to look at Celery.
* `slack.yml` rewritten as a valid `workflow_run` workflow, with the missing
  secret handled as a **skip rather than a failure** — this repo has just spent
  three weeks learning what a permanently-red workflow does to red workflows.

**Emptying the allowlist does not make those tests pass. It makes them fail
everywhere, deterministically** — which is what forces them to say what they
need.

`src/test_environment_independence.py` is the enumeration: it AST-walks `src/`
for module-level `os.environ.get` / `os.getenv` assignments and fails the build
on one nobody has classified. CLAUDE.md records twice (v3.19.6, v3.19.11) that
*a set is only the general form if something enumerates the population it is
drawn from*, and twice the missing enumeration was a four-minute grep never run.
This one is `os.environ.get` at module scope, and there are exactly three.

⚠️ **Module level, deliberately.** A read inside a function happens at call time
and a test can patch `os.environ` around it — which is what the watchdog tests
now do. A read at import time is baked into the process before any test runs,
and patching the variable afterwards changes nothing. That is what made the
admin-v2 one survive three weeks.

⚠️ **The keys are what the scanner sees, not what the code uses.** Both
allowlists are built in two steps, and only the first mentions the environment,
so the constant that actually gates the request is invisible to an `os.environ`
scan. The neutralisation therefore names the *derived* constants: the scanner
finds the doorway, the fix has to reach the room. The first draft listed the
derived names in both places and the stale-entry test caught it.

## 2 — 🟠 "Class totals" were one pledge's result, under a sentence promising otherwise

v3.21.0's pledge-facing quiz breakdown is gated on the chair ticking
`show_analysis_to_pledges`. That gate decides *whether* the class may see class
totals. It does not ask whether what is on the page **is** a class total.

Reproduced against `f241f45`: one pledge submits a scored quiz; a second pledge,
who has submitted nothing, opens the page and reads

```
Submissions 1 · Average 4 · Lowest 4 · Highest 4
"Who founded Beta?"   1 answer · 0 right · 1 wrong
```

directly beneath the header *"These are class totals. Nobody's individual
answers are shown here."* That is the first submitter's exact score and his exact
right/wrong pattern. **Being first is not an edge case** — it is a state every
quiz passes through, and in a pledge class everyone knows who else is in it.

Fixed with `PLEDGE_ANALYSIS_MIN_SUBMISSIONS = 3`, matching
`announcement_polls`' `respondent_count > 2`, which this codebase added for the
identical reason and wrote down as *"prevents identifying early respondents by
elimination"*.

⚠️ **The suppression is in the context builder, not the template.** A template
`{% if %}` protects the page it is written on; the values have to be absent from
the context so a second template — or a future JSON endpoint — cannot render
what this one hides. Same correction CLAUDE.md records under the admin
confidentiality boundary: redact in the queryset, not only in the view.

⚠️ **Educators are unaffected**, deliberately. They are entitled to individual
results and reach them from the grading page anyway, so withholding the summary
from them would remove information and protect nobody.

⚠️ **Residual, named:** the gate counts *submissions*, not answers per question,
so a question only one of three submitters answered still renders "1 answer".
That narrows the field to one of three rather than naming anyone — the ordinary
weakness of a small-N aggregate, not the defect being fixed, which was a page
presenting one person's complete result as "the class". Per-question suppression
would blank most of the page. If revisited, revisit it as a decision about what
a class total means.

**6 of the 7 new tests fail against `f241f45`.** The seventh is a control for
behaviour that did not change.

## 3 — 🟡 A parallel run can fail and report no test at all

v3.21.4 turned on `--parallel` in the push gate, on the reasoning that `tblib`
has been a dependency since v3.19.9 *"precisely so that a parallel failure still
reports which test failed"*. That is true and it is not sufficient.

Reproduced deterministically on 08-20-26: on a badly-red tree the run dies with

```
multiprocessing.pool.MaybeEncodingError: Error sending result: ...
Reason: AttributeError("Can't pickle local object
        'convert_exception_to_response.<locals>.inner'")
```

having reported **zero results** — no `FAIL:` line, no count, no summary. Django's
own `check_subtest_picklable` passes and the pool then fails on the same payload.
It did not reproduce with the same failing class run alone, so it depends on what
else the worker has accumulated; the mechanism is not fully pinned and the
behaviour is.

The hook now notices — the absence of a `Ran N tests` line is itself the signal —
and **re-runs the suite serially to go and get the answer**, rather than printing
an empty "What failed:" list under a `multiprocessing` stack trace.

> **A gate that cannot say what failed is, at that moment, a gate that did not
> run.** Same rule as the missing-interpreter branch above it, which v3.19.9
> added for the same reason.

⚠️ **`scripts/pre-push.sh` changed — run `make hooks`.** `src/test_repo_hooks.py`
will fail until you do; that is the guard working.

## 4 — 🟠 The pledge analysis view asked the sharing flag and not the entitlement

`pledge_take_quiz` has always applied two predicates before rendering: the task
must be **live**, and if it carries an explicit `assigned_to` list this pledge
must be on it. `pledge_quiz_analysis`, added four months later against the same
model, applied **neither** — it checked `show_analysis_to_pledges` and stopped.

Reachable as a result: the breakdown for a quiz assigned to one specific pledge,
by any other pledge; and the breakdown for an **unpublished draft**, which
matters because `education_duplicate_task` copies `show_analysis_to_pledges` onto
a clone whose entire purpose is to be invisible until the chair publishes it —
and the analysis page renders every question's text.

⚠️ **My first draft of this section said nothing was actually disclosed**, on the
reasoning that a fresh clone has no submissions so §2's threshold would empty the
rows. Then I ran the new tests against `f241f45` and
`test_the_question_text_does_not_reach_the_page` **failed** — because that tree
has no threshold either. I had reasoned about shipped code using a protection
introduced in the same release I was writing.

> **A protection you added yourself five minutes ago is not evidence about the
> code you are reviewing.** Run the control; do not derive it.

Fixed with `pledge_may_see_task(user, task)`, called by both views, plus a
structural test that fails the build if either stops calling it. Tenth instance
of the shape CLAUDE.md tracks — *a rule stated correctly in one place and left
out of a second place added later* — so the response is a function rather than a
second copy of the check.

**8 of the 12 new tests fail against `f241f45`.** The four that pass are the
controls: a live unassigned quiz is still readable, a quiz assigned to *this*
pledge is still readable, an educator still sees his own draft, and
`pledge_take_quiz` behaves exactly as before the refactor.

Also on that view: `pledge_request_absence` gained `@require_POST` (it read only
POST and answered a GET with a misleading validation error), and the fact that it
deliberately accepts **any** future meeting is now written down — `my_pledge_tasks`
lists every future meeting regardless of committee, so narrowing one without the
other would only make the two disagree.

## 5 — 🟡 A meeting is two rows and was not written atomically

`EducationMeeting.event` is a `OneToOneField`, so `education_add_meeting` must
save the `Event` first. Without a transaction, a failure on the second save left
the Event behind as **a pledge-education entry on the chapter calendar with
nothing behind it** — no attendance page, no row on the education dashboard, and
`education_delete_meeting` deletes *through* the meeting, so nothing in the
interface could remove it. An orphan that has to be deleted from a database
shell is precisely the kind of thing this app is being hardened to avoid handing
to the next chapter.

Both the create and the edit path are now `transaction.atomic`, the same
reasoning v3.19.3 used for `publish_legislation_draft`. The test simulates the
failure rather than waiting for it, and ships with a control, because a view
that wrote nothing at all would pass the orphan assertion trivially.

## 6 — 🟡 Query budgets for the education pages

This module's honest limitation has always been its coverage: v3.18.6 found two
N+1 dashboards in **production dev mode**, not here, and recorded that it
constrains only the pages somebody remembered to add. The 08-20 review measured
three of the new education pages by hand and found them flat — **and a
measurement in a report is not a ratchet.**

`education_home` (**37**) and `education_pledge_detail` (**34**) now have
measured ceilings and, more importantly, the property tests: doubling the pledge
roster must not add a query to the dashboard, and tripling one pledge's
attendance history must not add one to his detail page. Those two loops are over
the populations that grow every autumn.

⚠️ Neither number is small, and neither is the grid: the only repeated shapes are
the two django-otp device lookups every authenticated page in this suite pays on
a cold cache (`home` is 41, `activity_logs` 38). Flatness is the claim, and it is
the one the property tests pin.

## 7 — 🟡 A rule replaces two literals in the URL scanner

`test_hardcoded_urls` kept `/var/backups/parliament/` in `_NOT_SITE_PATHS` under
a comment reading "Filesystem paths, not URLs" — a correct classification made
one path at a time. `_is_filesystem_path` replaces it, and **the literal is
deleted rather than kept alongside**: an entry that also matches the rule makes
the rule untestable, since it would keep passing if the rule were wrong.

⚠️ **My first draft of the rule was `('/tmp', '/var/')`, and `startswith('/tmp')`
also matches `/tmpl/`.** The control caught it on the first run. That is the
failure mode an exemption-by-rule has and an exemption-by-literal does not: it
can silently grow.

## What this release did to itself, which is most of the value

Four separate guards in this repo caught this batch while it was being written:

1. `test_hardcoded_urls` flagged **its own new docstring** for naming the two
   filesystem roots in prose — a Python docstring is not a comment line, so the
   module scans itself. **Fourth time this module has done that**, after the
   `{% comment %}` blocks, the worked example above the regex, and a control
   fixture.
2. `bandit` returned **5 new MEDIUM findings**, all B108, all mine, all from
   writing `/tmp` in a test that opens no file. Zero before, zero after — but
   the pre-push hook and CI's security job would both have refused the push.
3. The new control for `_is_filesystem_path` caught the over-broad prefix.
4. `test_both_audiences_are_given_the_same_numbers` failed with an `IndexError`
   on the threshold change — and reading it revealed its fixture created **quiz
   answers and no completion rows at all**, so `submissions` was 0. Worth
   knowing: a quiz can have answers on record and report nothing taken.

None of that was reasoning. All four came from running the gates, which is the
same lesson as the one at the top of this file.

## What was checked and found sound

Recorded so it is not re-audited. The notification dropdown in `base.html` was
suspected of two things and is clean on both: `getCookie('csrftoken')` **prefers
the meta tag** (so it is not the dead httpOnly-cookie read v3.20.0 removed
elsewhere), and the unescaped `data-link="${n.link}"` is safe because every
`Notification.link` in the codebase is either a literal or an f-string over an
integer pk, with the one non-obvious case (`channel_chat`) built by `reverse()`.
Titles and messages are already `escapeHtml`-ed. No `csrf_exempt`, no raw SQL and
no new `mark_safe` anywhere in the v3.20–v3.21 diff.

Also sound: authorisation on all eleven new education routes
(`_education_committee_or_404`, delete chair-only, attendance POST accepts only
roster pks); `education_mark_answer` and `education_review_absence` are both
scoped to the committee in the lookup; `quiz_analysis_context` renders no
per-pledge identity for either audience; `unique_together` and indexes present on
all three new education models.

⚠️ Run on Linux/sqlite in the review sandbox. **CI is Postgres**, and the point
of this release is that an environment difference decides the answer — so the
claim to check is the CI run on the push, not this table.
