## 🟠 1 — every private upload was rendered inline, and four upload paths validated nothing

`_stream_private_file` sent all eight of v3.19.6's new views with
`as_attachment=False` and a content type from `mimetypes.guess_type`, i.e. from
the stored **filename**. Measured on Django 5.2.16:

```
x.html  →  text/html        inline; filename="x.html"
x.svg   →  image/svg+xml    inline; filename="x.svg"
x.js    →  text/javascript  inline; filename="x.js"
```

**A file rendered inline is a page on this origin** — at am-parliament.org, in
the session of whoever opened it, which for these eight views is by construction
a Kai reviewer, a slating committee member, an officer or the VPP.

Whether that mattered depended on what could reach those directories, and four
of the eight writers validated nothing:

| Path | Before |
|---|---|
| `SlatingApplication.gpa_screenshot` | `if hasattr(f, 'content_type') and f.content_type not in [...]` |
| `KaiReportFieldResponse.file_value` | nothing |
| `SlatingApplicationResponse.file_value` | nothing |
| `ServiceFieldResponse.file_value` | nothing |

`UploadedFile.content_type` is the multipart part header — **sent by the
uploader, never measured.** A file named `transcript.html` declaring `image/png`
passed, was stored as `slating/gpa_screenshots/<uuid>.html` (the uuid path keeps
the extension), and came back as `text/html`. The `hasattr` guard made it weaker
still: a part with no declared type skipped the check entirely.

CSP (`script-src 'self' 'nonce-…'`) blocks an inline `<script>`, but `'self'`
permits `<script src="/slating/applications/responses/<id>/file/">` — and the
same unvalidated field accepts a `.js`. With no script at all, a login form
rendered at the real domain is a better phishing page than one hosted anywhere
else, and `form-action 'self'` does not help when the form is already on
`'self'`.

**Not a regression.** `serve_media` has served `as_attachment=False` since
v3.14.1. It is fixed now because v3.19.6 is the release that took ownership of
serving these files, and it reasoned explicitly about `Cache-Control` three
lines below without reasoning about `Content-Disposition`.

### The fix is three independent layers

1. **Serving — `INLINE_SAFE_CONTENT_TYPES`** (`serve_private_upload.py`). PDFs
   and raster images render; everything else, including
   `application/octet-stream`, downloads. Plus an explicit
   `X-Content-Type-Options: nosniff` on the response rather than only the global
   setting. ⚠️ **`image/svg+xml` is deliberately NOT in the set** — an SVG is an
   XML document that may contain `<script>`, and that is exactly why this is an
   enumerated allowlist and not `startswith('image/')`.
2. **Storage — `_reject_browser_executable`** (`storage.py`). Every upload in
   the application funnels through `Storage.get_valid_name`, so the smallest
   guarantee that no writer can forget lives there. Deliberately a blocklist,
   not the allowlist: songbook `.mp3` is a real feature and is not in
   `ALLOWED_FILE_TYPES`. It runs on the **cleaned** name, after slugification,
   so `report .HTML` is caught.
3. **Validation — the four writers** now call `validate_uploaded_file`
   (allowlist + size + `magic` MIME agreement). The service-hours pair share one
   `_validated_upload` helper because the create path and the edit path were the
   same eight lines twice, which is how one of them came to be missed.

Rejections **drop the file and tell the member** rather than failing the POST:
by the time these run the parent record is saved, and refusing an attachment
must not discard the allegation text or the hours it belongs to.

### Two things found while fixing it

⚠️ **`validate_mime_type` had never rejected anything.** Its
`raise ValidationError` sat *inside* a `try` whose `except Exception` caught it
and downgraded it to `logger.warning`. Every caller — including the excuse
documents and the Kai attachment, the two paths that were doing it "properly" —
believed it was getting a content check and was getting a log line. The broad
catch is still right for what it was written for (python-magic needs libmagic,
and a missing system library must not take out every upload form), so the `try`
now covers only the detection call.

> **A `try` that contains both the detection and the verdict cannot fail open on
> one without failing open on the other.**

⚠️ **`BLOCKED_EXTENSIONS` named what runs on a SERVER and nothing that runs in a
BROWSER.** `.php`, `.jsp`, `.exe` — for a Python application that has never
executed an upload in its life. `.html` and `.svg` were absent. Added, with the
rule: *an upload blocklist should name what is dangerous where the file ends up.*

### New tests — `src/test_private_upload_rendering.py` (17)

Grouped by layer, deliberately: a single end-to-end "a member cannot upload
HTML" test would pass with any one of the three layers working and would go
quiet the moment someone removed the other two, reporting green while defence in
depth silently became defence in one.

⚠️ **The AST guard's first draft found three of the four writers.** It asserted
that a function which writes an upload field *mentions* the validator —
and `submit_kai_report` mentions it, on `request.FILES['supporting_document']`,
a field name the Kai form does not have, left from an earlier version. Dead code
made the function look validated. The shipped version matches the **value**
assigned into the field against the values that function validated. Run against
pristine `aef4f73` it reports **5 write sites** (4 findings; slating has two);
against this tree, none.

> **A test that greps for the presence of the right call cannot tell the right
> call from a call on the wrong object. Match the value, not the vocabulary.**

## 🟡 2 — the two monitoring-liveness tests could not pass

`MonitoringReaderLivenessTests.test_the_debug_endpoint_returns_real_numbers` and
`PerformanceQueryCountingTests.test_the_middleware_records_a_nonzero_count_for_a_real_request`
each make **one** request and assert a stored metric exists for it. Since
v3.19.3, `_append_metric` opens with `if random.randrange(SAMPLE_ONE_IN): return`
— `SAMPLE_ONE_IN` is 20, so one request is stored 5 % of the time and both tests
failed ~95 % of runs.

The v3.19.6 batch ran them, saw them red, and recorded the cause as
*"cache-throttle timing; may be LocMem-vs-Redis"*. It was neither. **The tests
were written in v3.18.7 against a middleware that stored every request, and the
release that made storage probabilistic did not revisit the two tests whose
subject is whether storage happens.** These are the guards against the
monitoring silently reporting zeros — the docstring says *"both dead readers
failed silently for months"* — so the guard against that recurring was itself
failing silently.

Both now pin `SAMPLE_ONE_IN` to 1 around the request, and a third test
(`test_the_exact_request_counter_is_not_affected_by_sampling`) asserts
`total_requests`, which sampling cannot touch — that is the liveness check to
reach for first, because it needs no control over the sample rate at all.

> **When you make an operation probabilistic, every test asserting that the
> operation happened becomes a coin flip — and a coin flip that usually loses is
> indistinguishable from a broken feature.**

## 🟡 3 — the lockout-release negative control was unpassable by construction

`test_a_non_admin_cannot_release_a_lockout` asserted
`assertNotEqual(status, 302)` and then, three lines later,
`assertIn(status, (302, 403, 404))`. 302 forbidden and permitted by the same
test. It could only pass if the denial returned 403 or 404, and
`require_admin_v2_auth` answers a non-allowlisted user with `redirect('home')`.

**The endpoint is not vulnerable** — verified by reading the decorator, and now
by an assertion that can actually fail: seed the lockout, POST as an outsider,
assert `is_account_locked()` is still true. A denial that redirects and a
success that redirects are the same integer, so the status code could never
answer the question. A companion test records the denial's shape explicitly, so
the next person to write a negative control here does not rediscover this.

The cost of the defect was that the only guard on an **account-unlock** endpoint
sat red in the suite being read as "pre-existing".

## 🟡 4 — the suite's failure count depended on how it was partitioned

Two careful runs of `aef4f73` disagreed: **12 failures** in four batches,
**8** in three batches with `--parallel=4`. Both were honest reports of what the
runner said; neither was a property of the code.

`src.test_login_as` passes alone. `test_two_factor.test_update_policy_invalid`
passes alone and fails when its own class runs (`302 != 400`). Two of the four
`test_middleware_hot_path` failures behaved the same way.

**Django rolls back the database between tests and does not touch the cache.**
`LocMemCache` is per-process, so a value written by one test is visible to every
later test in the same process — and since v3.18.7 that includes the three
things middleware reads on every authenticated request: `SiteSetting.get_setting`
(the 2FA policy), `FeatureFlag.is_feature_enabled`, and
`SystemLockdown.get_instance`. Each is cached against a row the next test's
rollback has already deleted.

`src/cache_isolated_runner.py` + `TEST_RUNNER` clears every cache alias before
every test. Several modules already did this in `setUp` — the same fix,
discovered one module at a time by whoever was bitten.

⚠️ **Two mistakes worth keeping.** The hook was first written on
`SimpleTestCase._pre_setup`, which is a **`classmethod`** in Django 5.2 and runs
once per test *class* — wrong signature, and even fixed it would have left every
test after the first in a class sharing state with its siblings, which is the
exact failure being fixed. It is on `run()` now. And the file was first called
`src/test_runner.py`, which matches Django's `test*.py` discovery pattern, so the
runner listed itself among the test modules and made the first partition
comparison come out 24 tests short. **A file that changes how tests are found
must not look like a test.**

## 🟡 5 — the four `5x src_featureflag` N+1s, and the exemption that outlived its reason

`GoverningDocument.enabled_doc_types()` asked `is_feature_enabled` for four
flags in a loop, so `/constitution-bylaws/` and `/cnb/resolutions/new/` did four
identical-shaped queries on a cold cache. Red in `test_url_smoke` and
`test_detail_route_smoke` since v3.19.1 and carried through five reports.

New `FeatureFlag.resolve_many(names)` resolves N flags in one query. ⚠️ **It is
not a second cache** — it writes the identical `_cache_key(name)` entries in the
identical shape, so it warms `is_feature_enabled` and is covered by the existing
v3.17.3 invalidation without that signal knowing it exists. `is_feature_enabled`
now delegates to it, so the fail-open / `DISABLED_BY_DEFAULT` rules have exactly
one home; `cnb_foreword` still fails closed and `test_cnb_foreword` still says so.

⚠️ **The first draft had `.only('name', 'is_enabled')` and it silenced a
detector.** Narrowing the column list split this query's SQL text away from every
other read of the table, so `admin_api_tokens` went from `3x src_featureflag` to
two shapes at 2x and 1x, dropped under `REPEAT_THRESHOLD`, and
`test_accepted_repeats_are_still_repeating` failed on an entry whose N+1 was
entirely intact. Removed.

> **A detector that groups by query shape can be silenced by changing the shape,
> and the result looks exactly like having fixed something.**

Chasing that failure honestly found the real one: the `ACCEPTED_REPEATS` entry
for `admin_api_tokens` said the page *"reads three different flags through the
cached `is_feature_enabled`; the repeats are cache misses on a cold cache"* —
harmless, in other words. Two of the three were raw
`FeatureFlag.objects.get(name=…)` calls in `src/view/api.py` that never touched
the cache and repeated on a **warm** cache, on every request. Now one query; the
exemption is deleted, which is what that guard exists to force.

> **An exemption is a claim about a mechanism, not about a number. Write the
> mechanism down and check it, or it becomes permanent by sounding reasonable.**

## 💡 7 — `src.W003`, the ledger check, built after five instances

Two lines in every changelog record facts that **do not exist while the
changelog is being written**:

```
**Committed & pushed:** *not yet*
**Deployed:** *not deployed*
```

Every other line is finished when the author saves it. These two become wrong a
few minutes later, in the very commit that makes them wrong, by which point the
author is in `git commit` and not in the editor. v3.18.8, v3.19.2, v3.19.4,
v3.19.5, v3.19.6. The fifth is the clearest: `v3.19.6.md` went into `aef4f73`
still reading *"not yet"* — inside the commit.

**No amount of care at authoring time can fix a line whose value does not exist
until after the writing is over.** That is the whole argument, and it is why the
response has to be a check that runs *after* the commit. `manage.py check`
already gates the deploy, so it runs on the machine that just pulled it.

Deferred four times on v3.18.4's principle that the response to a pattern should
not ride along with an instance of it. That principle has now been honoured
three times over.

### What it will not do

⚠️ **It never infers whether a release was deployed.** CLAUDE.md's 08-02-26
amendment records the trap exactly: `--diff-filter=A` can only tell you when a
changelog FILE was committed, never whether the release SHIPPED. A run used it,
got a date, and concluded v3.18.1 was live while `DEPLOYED.md` said *not
deployed* in as many words.

> Use `--diff-filter=A` to **date** a commit. Use `DEPLOYED.md` to answer **"is
> it live"**.

Only a human knows the second. The check validates the committed half and is
silent about the deployed half — a guard that guesses at what it cannot observe
is worse than none, because its silence then means nothing. It is a `Warning`
and every failure path returns `[]`: no `.git`, no `git` binary, a shallow
clone, a rewritten history all produce nothing rather than blocking a deploy.

### Both of its first two runs found bugs in itself

⚠️ **Run 1 reported 68 historical releases as missing from `DEPLOYED.md`.** They
are missing because the ledger was reconstructed on 07-31-26 and starts at
v3.13.0. Three real findings were buried in the middle of the list. Scope now
derives from the ledger's own oldest row — so backfilling an old row widens the
check automatically, and nobody maintains a constant.

⚠️ **Run 2 reported v3.18.8 and v3.19.2**, whose lines were corrected on
08-07-26 and now read *"Corrected 08-07-26 — this line read "not yet" while the
release was already on origin/main."* The phrase is present **because the line
documents having been stale.** A substring search cannot tell a claim from prose
about the claim — the same shape as
`test_no_view_reads_the_dead_perf_cache_key`'s first draft, which failed on a
docstring that named the dead cache key while explaining the bug. The check now
asks the positive question first: *does this line name a commit?* A line naming
a real sha is a finished claim whatever else it says about its own history.

> **Both are one failure in two costumes: a guard that reports things that are
> fine is a guard nobody reads.** That is the red-CI-gate lesson (08-02-26)
> arriving from the opposite direction, and it is why the tests below are mostly
> negative controls.

### Run 3 found the thing it was built for

```
?: (src.W003) The release ledger disagrees with git. Changelogs that still say
   "not yet" under **Committed & pushed** although git has them:
   v3.19.6 (committed in aef4f73).
```

`v3.19.6.md` line 5 is corrected, with a note recording that the check found it
on its first clean run. `manage.py check` is now silent — and correctly silent
about `v3.19.7.md`, which says *not yet* and is not yet committed.

`src/test_ledger_check.py` — 11 tests, each building a real throwaway git
repository with real commits rather than mocking `git log`. ⚠️ **They do not read
this repo's own `changelogs/`**: that would make them a test of today's ledger,
red whenever a release is half-recorded, which is a normal transient state the
check exists to *report*. A suite that fails on the condition its own check
announces trains everyone to ignore both.
