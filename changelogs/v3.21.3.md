# v3.21.3 — "log in as" now clears the forced password change too

**Date:** 08-19-26
**Type:** Bug fix + a policy written down. **No migration.**
**Committed & pushed:** 08-19-26, `d2d871e`
**Deployed:** *not deployed*

Reported by Mason: logging in as a user from `/admin/` bypasses 2FA but not the
forced password change.

✅ **1,525 tests, 0 failures, 3 skipped**, two partitionings. `manage.py check`
silent, `makemigrations --check` clean, bandit exit 0. Negative control verified.

---

## The bug

`Enforce2FAMiddleware` exempted impersonation sessions.
`ForcePasswordChangeMiddleware` did not.

So **Log in as** a user with `force_password_change` set dropped the admin on a
change-password screen for an account whose password he does not know. He could
not proceed, and could not do the thing the feature exists for.

⚠️ **And "just set one" is worse than the screen.** It locks the user out of his
own account and hands the admin a working credential for it. The right answer is
to walk past the requirement without touching it — which is what this does. The
user's flag is untouched, so he is still asked the next time *he* logs in. A
test asserts that specifically, because a bypass that quietly resolved the
requirement would look identical from the admin's side.

---

## Two decisions about one flag, in two files, and only one written down

The impersonation session key was read by name in three places — the 2FA
middleware, a context processor, and the view that sets it. **Every raw read is
an independent decision about what impersonation bypasses**, and two of them
disagreed without either file mentioning the other.

That is the ninth instance of the shape CLAUDE.md tracks: *a rule stated
correctly, a helper written to enforce it, then one call site left outside it.*

So the response is not "add the missing check":

- **`src/impersonation.py`** — one `is_impersonating(request)`, and the policy
  written next to it: what is bypassed, what is not, and why for each.
- **`test_no_module_reads_the_session_key_directly`** — a fourth independent
  decision now fails the build.

---

## ⚠️ What impersonation deliberately does NOT bypass

Worth your eye, because I stopped short of the obvious generalisation.

**Bypassed — account-setup interstitials.** These make a *user* finish setting up
his own account, and an impersonating admin can neither complete them honestly
nor get past them: **2FA** (no authenticator) and **forced password change** (no
password).

Onboarding is not on the list because it is only forced at login, and
impersonation calls `login()` directly rather than going through `login_view` —
so it never blocks an impersonated session. Checked rather than assumed.

**Not bypassed — restrictions:**

- **quarantine** (`QuarantineEnforcementMiddleware`)
- **emergency lockdown** (`EmergencyLockdownMiddleware`)
- **maintenance mode** (`MaintenanceModeMiddleware`)

Those are not setup steps somebody failed to finish. They are decisions someone
made *about* an account or the whole site, usually in response to a problem.
"I am an admin" is not a reason to walk through a quarantine — if you want to
use a quarantined account, lift the quarantine, which is deliberate and logged.

> **A bypass that also disables the controls you reach for in an incident is a
> bypass that works against you exactly when it matters.**

`RestrictionsAreNotBypassedTests` asserts none of those three consults the
helper — not because the trade could never be worth making, but so that making
it is a deliberate act with the argument in front of you rather than a
consistency tidy-up. **Say the word if you want any of the three, and I will
change the policy in the docstring as well as the code.**

## Verification

```
manage.py test --parallel=4      → 1,525 tests, 0 failures, 3 skipped (138.6s)
manage.py test --parallel=8      → 1,525 tests, 0 failures, 3 skipped (128.2s)
manage.py check                  → no issues
manage.py makemigrations --check → No changes detected
bandit -r src/ -ll               → exit 0
```

**9 new tests.** The order matters: the **first** asserts a real user is *still*
forced to change his password, because every other assertion in that class would
pass against a bypass that had accidentally switched the requirement off for
everyone.

**Negative control:** removing the four-line exemption fails exactly one test —
`test_an_impersonating_admin_is_not_forced_to_change_it` — so the suite is
pinned to this defect and not to the middleware in general.
