## 🟠 Education committee member permissions (Kai-style)

Mason: *"Can we also add the an education permissions dashboard so the
admin of the committee can set what permissions the members have whether
it's none, some permissions; view and grade tasks (2 separate perms), or
all permissions where they can make tasks and whatnot. Kai has a version
of this already."*

### What changed

Before this release, the education dashboard had no per-member permission
system at all: any chapter officer (`request.user.is_officer`) had full
access to virtually everything — viewing pledge progress, grading quizzes,
creating/editing/deleting tasks — regardless of whether they were actually
on the education committee. Only two actions (publishing a manual task,
deleting a meeting) were chair-gated as one-off exceptions.

This release replaces that with a granular, opt-in model mirroring Kai's
`KaiMemberPermission` almost exactly, at Mason's explicit direction:

- **New `EducationMemberPermission` model** (`committee`, `user`, three
  independent booleans, `granted_by`/`granted_at`/`updated_at`,
  `unique_together` on `(committee, user)`).
- **Three permission tiers**, confirmed with Mason before building:
  - `can_view_submissions` — view the dashboard, pledge progress, and quiz
    answers/submissions. Read-only.
  - `can_grade_submissions` — mark quiz answers right/wrong, enter scores,
    and set a completion's status (pass/incomplete). Deliberately scoped to
    quiz grading only, per Mason's confirmation — it does **not** cover
    attendance marking or absence-request review.
  - `can_manage_tasks` — everything else: create/edit/duplicate/delete
    tasks, publish/unpublish, manage quiz questions, manage meetings
    (add/edit/delete), mark attendance, review absence requests, and edit
    pledge page restrictions.
- **A real committee chair, or a site admin, gets automatic full access**
  to all three tiers with no permission row needed — same as Kai. Unlike
  Kai, there is no separate break-glass grant mechanism for admins, since
  education data carries no confidentiality boundary (this is the same
  admin bypass `education_toggle_task_published` already had before this
  release).
- **Everyone else now gets NOTHING by default.** This is the behavior
  change Mason confirmed before building it (he chose the full Kai-style
  lockdown over an additive-only option that would have preserved existing
  officers' blanket access): a chapter officer with no explicit grant can
  no longer open the education dashboard at all.

### New page: Education Member Permissions

`manage_education_permissions` (linked from Committee Home next to the
Education Dashboard button, chair/admin-visible only) — a table of every
committee member (chairs + members + voting members) with three checkboxes
each, saving automatically on click via AJAX. Chair rows render
all-checked-and-disabled, since chairs don't need an explicit row. A
"Reset All to No Access" button wipes every grant for the committee.
Mirrors `manage_kai_permissions.html` almost line for line.

### Permissions auto-reset on role change

`EducationMemberPermission` rows for a committee are wiped automatically
when the exec role tied to that committee (`committee.role`) changes
holders — mirroring the existing Kai behavior, via a new
`reset_education_permissions_on_role_change` hooked into the same
`sync_exec_committee_on_role_change` signal. A new chair starts with a
clean slate rather than inheriting the outgoing chair's grants.

### Two previously chair-only actions folded into `can_manage_tasks`

`education_toggle_task_published` and `education_delete_meeting` were
chair-only (with an admin bypass on the first) before this release. The
3-tier model has no room for a separate "chair only" sub-tier, so both are
now gated on `can_manage_tasks` like every other management action —
someone granted task-management permission can now also publish tasks and
delete meetings, which they could not before if they weren't the chair.

### Every education view re-gated

`_education_committee_or_404` now returns an `access` dict (from new
`_get_education_access`, mirroring `_get_kai_access`) instead of a plain
`is_chair` boolean. Every view in `src/view/committee/education.py` was
re-audited and gated on the specific permission its action needs:

| Tier | Views |
|---|---|
| View (base gate — any of the three) | `education_home`, `education_pledge_detail`, `education_quiz_analysis`, `education_quiz_submissions` (page itself) |
| Grade | `education_toggle_completion`, `education_mark_answer` |
| Manage | `education_add_task`, `education_edit_task`, `education_delete_task`, `education_duplicate_task`, `education_toggle_task_published`, `education_add_quiz_question`, `education_edit_quiz_question`, `education_delete_quiz_question`, `education_manage_quiz_questions`, `education_add_meeting`, `education_edit_meeting`, `education_delete_meeting`, `education_meeting_attendance`, `education_review_absence`, `education_update_page_restriction`, `education_delete_page_restriction` |

GET-rendered pages that need more than the base "any access" gate raise
`Http404` on a missing permission (via new `_require_education_permission_or_404`),
matching `_education_committee_or_404`'s own choice — a view-only member
should not be able to tell from the response that an edit page exists.
AJAX/form POST actions return a 403 JSON error instead (via new
`_require_education_permission`), since those already have a UI context to
show the error in.

### Deliberately NOT registered in Django admin

`EducationMemberPermission` stays out of `/admin/`, alongside Kai's models
— not for Kai's confidentiality reason (education has none), but because
editing a row through the admin would bypass `granted_by`/`granted_at` and
the auto-reset-on-role-change signal, giving a chair two different places
to manage the same grants that could silently disagree.

### Tests

`src/tests/education/test_quiz_grading_visibility.py` (v3.31.7) had one
test rewritten: `test_the_link_is_visible_to_a_non_chair_officer_too`
assumed the old "any officer has access" rule and needed an explicit grant
added to keep passing; a new companion test confirms an ungranted officer
is now denied.

New `src/tests/education/test_education_permissions.py` (39 tests):
`_get_education_access` branch coverage (chair, admin, explicit grant, no
grant); model defaults and uniqueness; the base view-tier gate; every
manage-tier and grade-tier action tested both allowed (with the right
grant) and denied (without it, or with only an unrelated grant — confirming
the three permissions are independent, not implied by one another);
attendance/absence-review confirmed as manage-tier, not grade-tier; the
full `manage_education_permissions` page (chair access, non-chair redirect,
admin access, granting, rejecting a redundant chair grant, reset, no inline
event handlers); and the role-change auto-reset signal.
