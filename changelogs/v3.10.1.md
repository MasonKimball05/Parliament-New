# v3.10.1 — Chapter Stats, Bug Fixes & Performance

**Release Date:** June 22, 2026
**Deployment Status:** ✅ Deployed — June 22, 2026
**Type:** Feature / Bug Fix / Performance

---

## Overview

New chapter statistics dashboard for officers, a batch of bug fixes across the recruitment and chapter-stats views (including two silent crashes that caused data to always show as empty/zero), and a performance pass over the education and profile-card views. All changes are WIP on top of v3.10.0 and deploy together with it.

---

## What Changed

### 1. Chapter Statistics Dashboard — New View

New officer-facing read-only page at `/officers/chapter-stats/` (linked from the Quick Links panel on the officer home). Aggregates across existing models — no new DB structures required.

**Sections:**
- **Attendance** — overall rate across chapter meetings in the last 90 days; per-meeting breakdown (last 10); at-risk member list (below 75% over ≥3 meetings). All backed by a single annotated query each; no loops.
- **Voting** — overall participation rate; per-legislation breakdown (last 10 closed votes). Single annotated query.
- **Service hours** — active period summary (N/M members met their requirement); per-member breakdown sorted by hours logged. Respects per-member overrides from `ServicePeriodMemberOverride` — fetched in one query upfront.
- **Recruitment** — event count and unique RSVPs in the last year; active pledge count. Wrapped in `try/except` so the view still works on instances without the recruitment module.

Recruitment events (linked via `RecruitmentEvent.event` OneToOneField) are excluded from chapter meeting attendance stats — they should not pollute finalized attendance records.

**Files:** `src/view/officer/chapter_stats.py` *(new)*, `templates/officer/chapter_stats.html` *(new)*, `src/urls.py`, `templates/officer_home.html`

### 2. Chapter Stats — Service Hours Respect Per-Member Overrides

**Bug:** The view used `active_period.default_hours_required` for every member, ignoring any `ServicePeriodMemberOverride` records set by the VPP.

**Fix:** All overrides for the active period are fetched in a single query upfront (`active_period.member_expectations.all()`). Each member's individual requirement is used for both the "members met" counter and the per-row `met` flag.

The breakdown table now shows a "Required" column per member. Members with a custom override show a blue `*` with a tooltip ("Custom requirement set by VPP"). The subtitle line reads "Default requirement: Xh · N/M members met their requirement." A footnote explains the asterisk.

**Files:** `src/view/officer/chapter_stats.py`, `templates/officer/chapter_stats.html`

---

### 3. Chapter Stats — Recruitment Events Excluded from Attendance

**Bug:** `Event` rows linked to a `RecruitmentEvent` (sign-up/RSVP events) were included in the `chapter_meetings` queryset. Users who RSVPed to a recruitment event appeared as "present" in the chapter attendance section.

**Fix:** Added `.exclude(recruitment_event__isnull=False)` to the `chapter_meetings` queryset. Events with a linked `RecruitmentEvent` reverse relation are now excluded.

**Files:** `src/view/officer/chapter_stats.py`

### 4. Chapter Stats — `required_hours` AttributeError (Silent Crash)

**Bug:** `active_period.required_hours` raised `AttributeError` — the field is `default_hours_required`. The exception propagated up, crashing the service hours section.

**Fix:** `float(active_period.default_hours_required or 0)`.

**Files:** `src/view/officer/chapter_stats.py`

---

### 5. Chapter Stats — Recruitment Stats Always `None` (Silent FieldError)

**Bug:** `RecruitmentEventRSVP.objects.values('member')` raised `FieldError` — the field is `user`, not `member`. The `except Exception: pass` block silently swallowed it, leaving `recruitment_stats` as `None` on every page load.

**Fix:** `.values('user')`.

**Files:** `src/view/officer/chapter_stats.py`

---

### 6. `committee_home.py` — Filter-After-Slice AssertionError

**Bug:** `_upcoming_qs[:5].filter(visibility='public')` raised Django's `AssertionError: Cannot filter a query once a slice has been taken`. Silently swallowed by an outer `except Exception: pass`, so non-privileged recruitment committee members always saw 0 upcoming events.

**Fix:** Moved `[:5]` after the visibility filter.

**Files:** `src/view/committee/committee_home.py`

---

### 7. `recruitment.py` — Double DB Lookup in `update_recruitment_permission`

**Bug:** The view called `.get()` to fetch the `RecruitmentMemberPermission` object, then immediately called `get_or_create()` on the same row — two DB round-trips, and the first `.get()` had no `DoesNotExist` handler.

**Fix:** Removed the redundant `.get()`. The `get_or_create()` call alone is sufficient.

**Files:** `src/view/committee/recruitment.py`

---

### 8. `recruitment.py` — Double-Eval on Signups/RSVPs in Event Detail

**Bug:** `signup_count = signups.count()` fired a second DB query on a queryset that was already evaluated (or would be) by the template. Same issue with the RSVP queryset: `.exists()` then `.filter()` then iteration fired separate DB hits.

**Fix:** Evaluated signups and RSVPs to `list()` upfront; used `len()` and `sum()` over the lists.

**Files:** `src/view/committee/recruitment.py`

---

### 9. `recruitment.py` — Unguarded `int()` on `rsvp_reminder_hours_before`

**Bug:** `int(request.POST.get('rsvp_reminder_hours_before', 24))` raised `ValueError` on empty string or non-numeric input, crashing both the create and edit recruitment-event views.

**Fix:** Wrapped in `try/except (ValueError, TypeError)` with fallback to `24`.

**Files:** `src/view/committee/recruitment.py`

---

### 10. `notifications.py` — Double-Eval in `send_recruitment_rsvp_reminders`

**Bug:** `going_rsvps.exists()` evaluated the queryset once; `for rsvp in going_rsvps` evaluated it again — two DB queries for the same data.

**Fix:** Forced `list()` upfront; `if not going_rsvps` checks the list.

**Files:** `src/tasks/notifications.py`

---

### 11. `profile_card.py` — Prefetch Cache Bypass

**Bug:** `member.chair_roles.filter(is_active=True, is_archived=False)` and `member.committees.filter(is_active=True, is_archived=False)` bypassed Django's prefetch cache, firing per-card DB queries.

**Fix:** Switched to `.all()` + Python filtering. Removed the dead `chaired` variable (it was assigned but never read).

**Files:** `src/view/profile_card.py`

---

### 12. `PledgePageRestriction.is_allowed()` — Per-Request DB Query → Cached (5 min)

**Bug:** Every pledge page load called `PledgePageRestriction.is_allowed()`, which issued an uncached `objects.get()`. On pages loaded frequently during a pledge phase this fired on every request.

**Fix:** Result cached at `pledge_restriction_{url_name}` for 5 minutes. Uses `'__open__'` sentinel for the `DoesNotExist` case (unrestricted pages). Added `invalidate_cache(url_name)` classmethod; wired into the update and delete restriction views in `education.py`.

**Files:** `src/models/education.py`, `src/view/committee/education.py`

---

### 13. `education.py` — Chair-Only Gate on `toggle_task_published`

**Bug:** Any education committee member (not just chairs) could publish or unpublish tasks via `education_toggle_task_published`.

**Fix:** Added explicit check — `committee.chairs.filter(pk=request.user.pk).exists() or request.user.is_admin` — returning 403 otherwise.

**Files:** `src/view/committee/education.py`

---

### 14. `education.py` — Deduplicated `assigned_to.all()` in Pledge Summaries

**Bug:** `pledge_summaries` loop called `t.assigned_to.all()` per task per pledge, even though `task_rows` had already resolved `assigned_pks` for every task.

**Fix:** Extracted `task_assigned_pks = {row['task'].pk: row['assigned_pks'] for row in task_rows}` and reused it in the summaries loop — no extra queries.

**Files:** `src/view/committee/education.py`

### 15. `education.py` — `_parse_non_negative_int()` Helper

Replaced ad-hoc inline `int()` guards on `points` and `display_order` with a shared `_parse_non_negative_int(value, default=0)` helper. Cleaner and consistent.

**Files:** `src/view/committee/education.py`

### 17. `education.py` — `task_type` and `phase` Validated Before Save

**Bug:** `education_add_task` saved `task_type` and `phase` directly from POST without validating against the model's `TASK_TYPES` / `PHASE_CHOICES` sets. A malformed value would save silently and could break template rendering or filtering later.

**Fix:** Both fields are now checked against their respective choice sets; invalid values fall back to `'task'` and `'all'` respectively.

**Files:** `src/view/committee/education.py`

---

### 18. `education.py` — `phases` JSONField Validated Before Save

**Bug:** `education_update_page_restriction` wrote the raw `phases` list from POST to the `PledgePageRestriction.allowed_phases` JSONField without checking values. A typo or malformed POST would silently save garbage, causing `is_allowed()` to never match and locking all pledges out of the page with no visible error.

**Fix:** `phases` is filtered to only the valid values `{'all', '1', '2', '3'}` before saving.

**Files:** `src/view/committee/education.py`

---

### 19. `education.py` — Eliminated Redundant `is_chair` DB Query

**Bug:** `_education_committee_or_404` called `committee.chairs.filter(pk=user.pk).exists()` to gate access, then `education_home` called the same query a second time to set `is_chair` in context. `education_toggle_task_published` also duplicated the check inline.

**Fix:** `_education_committee_or_404` now returns `(committee, is_chair)`. All callers unpack the tuple; `education_home` and `education_toggle_task_published` reuse the value directly — no second query.

**Files:** `src/view/committee/education.py`

---

### 20. `chapter_stats.py` — `active_members` Queryset Evaluated Only Once

**Bug:** `active_members` (a lazy queryset) was iterated at line 184 (at-risk section), caching the result internally. Then `.order_by('name')` was chained to produce the service-hours breakdown loop — this creates a new queryset object, bypassing the cache and issuing a second `SELECT`.

**Fix:** Evaluated to `list(... .order_by('name'))` upfront; `active_count` uses `len()`. Both loops share the already-fetched list.

**Files:** `src/view/officer/chapter_stats.py`

---

### 21. `education.py` — `activation_mode` Validated Before Save

**Bug:** `education_add_task` read `activation_mode` from POST and passed it directly to `PledgeTask.objects.create()` without checking against `ACTIVATION_MODES`. An invalid value would save silently, `is_published` would incorrectly default to `False` (since `activation_mode != 'immediate'`), and the `timed` datetime branch would be skipped.

**Fix:** `activation_mode` is now validated against `{c[0] for c in PledgeTask.ACTIVATION_MODES}` before use; invalid values fall back to `'immediate'`. Consistent with the same pattern applied to `task_type` and `phase` in item 17.

**Files:** `src/view/committee/education.py`

---

### 22. `education_home` — Dead `pledge_pks` Variable Removed

**Bug:** `pledge_pks = {p.pk for p in pledges}` was computed on every request but never read anywhere in the view — the pledge summary and task-row loops both work directly off the `pledges` queryset. The comprehension was also an unnecessary second iteration over the pledges queryset.

**Fix:** Line removed.

**Files:** `src/view/committee/education.py`

---

### 23. `notifications.py` — Health Check `exists()` + `count()` Double-Evals

**Bug:** Two blocks in the daily health check task called `.exists()` on a queryset and then, if truthy, called `.count()` on the same queryset — two DB hits when one is sufficient. Both the `stale_watch` (UserWatchFlag) and `old_whitelist` (IPWhitelist) checks had this pattern.

**Fix:** Fetch the preview rows in one query (e.g. `.values_list(...)[:5]`); check `if list:` to gate the block; run a single `.count()` only inside the block to get the real total. Net change: 3 queries → 2 per block.

**Files:** `src/tasks/notifications.py`

---

### 25. `@pledge_page_allowed` Wired to Slating & Documents Views

**Previously:** `slating/results.py`, `slating/apply.py`, and `chapter_documents.py` used `@exclude_pledges`, which blocks all pledges unconditionally regardless of any `PledgePageRestriction` records set by the VPE.

**Change:** All three views now use `@pledge_page_allowed(url_name)` instead. The VPE can open any of these pages to pledges via the Education dashboard's Page Access panel — no code deploy needed.

URL names mapped: `slating_results`, `slating_apply`, `chapter_documents`.

**Note:** Phase-specific restrictions are not used (no `pledge_phase` field on users). The restriction is binary: a page is either open to all pledges or closed to all pledges.

**Files:** `src/view/slating/results.py`, `src/view/slating/apply.py`, `src/view/chapter_documents.py`

### 26. Chapter Stats — Date-Range Picker

Officers can now filter the chapter stats dashboard by selecting a time window: 30, 90, 180, or 365 days. The selection is passed as `?days=N` and affects the attendance, voting, and recruitment sections. Service hours are always scoped to the current active period (period-based, not date-based).

A pill button group appears in the header; the active selection is highlighted. Default remains 90 days.

**Files:** `src/view/officer/chapter_stats.py`, `templates/officer/chapter_stats.html`

### 27. Weekly Chapter Digest Email

New Celery task `send_weekly_chapter_digest` sends a personalised digest to every active non-pledge member every Sunday at 8:00 AM CST.

**Sections (each omitted when empty):**
- **Upcoming events** — next 7 days, filtered to events visible to that member's type. Sign-up link included for events with `requires_signup=True`.
- **Open votes** — chapter legislation currently accepting votes with a direct link.
- **Service hours** — hours logged vs. individual requirement in the current active period (respects per-member overrides).

All DB work is batched upfront (one query per section); the loop over recipients only builds and sends email — no per-member DB hits.

Registered in `setup_celery_schedules.py` as a Sunday crontab (`hour=14, minute=0, day_of_week=0` → 8:00 AM CST). Run `python manage.py setup_celery_schedules` on prod to register it.

**Files:** `src/tasks/notifications.py`, `src/management/commands/setup_celery_schedules.py`

### 24. `chapter_stats.py` — `active_members.filter()` AttributeError After List Conversion

**Bug:** Item 20 converted `active_members` from a lazy queryset to a `list`. The at-risk attendance section still called `active_members.filter(pk__in=at_risk_pks)` to build a lookup dict — a `list` has no `.filter()`, so this would raise `AttributeError` at runtime.

**Fix:** Replaced with a Python set lookup: `at_risk_set = set(at_risk_pks)` then `{m.pk: m for m in active_members if m.pk in at_risk_set}`. This is actually faster than the original DB query it replaced.

**Files:** `src/view/officer/chapter_stats.py`

## Performance Summary

| Location | Before | After |
|---|---|---|
| `chapter_stats` — attendance section | 3 separate counts + 10×4 per-meeting counts | 2 annotated queries |
| `chapter_stats` — at-risk list | 1 query per member (N×2) | 1 aggregated query |
| `chapter_stats` — vote breakdown | 1 count per legislation (10×) | 1 annotated query |
| `chapter_stats` — service hours | default req for all; no override fetch | 1 override query; per-member req used |
| `profile_card` — committees | `.filter()` bypassing prefetch × per-card | `.all()` + Python filter |
| `PledgePageRestriction.is_allowed()` | 1 DB query per pledge page load | Cached 5 min per URL |
| `education_home` pledge summaries | `assigned_to.all()` × tasks × pledges | Dict lookup from already-resolved sets |
| `education_home` is_chair check | 2 queries (helper + view) | 1 query — helper returns tuple |
| `chapter_stats` active members | 2 SELECT (queryset + re-sorted) | 1 SELECT — list evaluated once |
| `chapter_stats` at-risk lookup | DB `.filter(pk__in=...)` | Python set lookup (no DB hit) |
| Health check `stale_watch` | `exists()` + `values_list()` + `count()` = 3 queries | `values_list()[:5]` + `count()` = 2 queries |
| Health check `old_whitelist` | `exists()` + `values()` + `count()` = 3 queries | `values()[:5]` + `count()` = 2 queries |
