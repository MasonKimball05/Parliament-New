## 🟢 Slating: import applications from another form

**Asked (Mason, 10-26-26):** the President collected officer applications in
his own Google Form before he knew Parliament had slating. Members who already
filled that out shouldn't have to apply again. Show a confirmation of who gets
an application and what goes in it, and make sure nothing is missing from
questions the Parliament form asks but the Google form didn't. Also let
managers fill fields in by hand.

**Import Applications** (Applications → *Import from another form*, or the
period's quick links). For the period's managers only (slating manager,
committee admin or chairs; site admins only while the period isn't locked).
1. **Upload** the CSV (Google Forms → Responses → Download responses, or
   Sheets/Excel → CSV).
2. **Match the columns.** Each column is the applicant (email, username or
   name), the timestamp, GPA, first/second/third-choice or "do not want"
   positions, one of the period's form questions, or ignored. Guesses come
   from the headers. Position text matches titles or codes, so "Vice
   President, President" finds both.
3. **Confirm.** For each applicant, everything their application will
   contain: positions, GPA, every Parliament question with the imported
   answer (or "Not asked on the outside form" / "No answer"), and answers
   kept in notes. It lists which Parliament questions the outside form never
   asked, and every skipped row with its reason. Import stays disabled until
   the manager ticks "I've checked who is getting an application and what's
   in it".
4. **Import.** Re-plans from the CSV (the preview is never trusted) and writes
   in one transaction.

**Rules.**
- Nobody's own Parliament application is changed: a member who already has
  one, drafts included, is skipped.
- One application per member: their latest response wins.
- Imported applications are Submitted, dated by the form's timestamp, GPA
  unverified.
- Answers to unmapped questions go into the review notes, so nothing is lost.

**Marked as imported.** Applications get `imported_at` and the list of
questions the outside form didn't ask (`import_not_asked`). The list and
detail pages show an *Imported* badge, and the detail page lists the "Not
asked on the outside form" questions, so reviewers don't read them as skipped.

**Fill in answers.** On an imported application, managers can type in
answers collected another way, or correct an imported one. Answered questions
leave the "not asked" list. Each save is logged in the slating activity and
the review notes. A member's own application can't be edited this way (404).

## 🟢 Default slate positions

"+ Default Positions" no longer adds Vice President of Administration, Vice
President of Risk Management or the Constitution & Bylaws Chair. They're still
roles (`Role.DEFAULT_ROLES` also rebuilds the chapter's roles); they're just
not slated (`SLATE_EXCLUDED_ROLE_CODES`). The confirmation modal now lists
exactly what the button adds. It was a hardcoded list that had already drifted
(it never showed the C&B Chair the button added).

## 🟠 Fixes from a review of the slating code

- **Locked periods leaked to site admins.** The confidentiality model says
  that once a slating manager or committee admin is set, site-admin status
  alone grants nothing. Three views checked a bare `is_admin` instead:
  - `complete_interview`, whose GET returns the confidential interview
    notes, so any site admin could read them;
  - `schedule_interview`, which also left out the slating manager;
  - `api/slating/period/<id>/status/`, which gave any site admin
    application stats and the LIVE approve/reject/abstain tallies while
    voting was open.

  All three now use the module's lock-aware helpers. Removing the fix makes
  the notes test fail.
- **A slate ballot could be recorded twice.** The "already voted" check ran
  unlocked, and the ballots' unique constraint can't catch a slate ballot
  (its `position` is NULL; Postgres treats NULLs as distinct). The ballot and
  vote are now one atomic write under the period's row lock, with the check
  inside. Individual-position votes too: a double submit was a 500, and a
  failure partway through left some positions recorded and others not.
- **`rejected_positions`** was `int()` on whatever was posted (junk was a
  500) and stored any position id. Now only this slate's positions.
- **Apply:** posted position ids got the same treatment (500 on junk, other
  periods' ids stored). Now only the period's active positions, each in its
  first tier only.

## 🟡 Performance

- Individual-position tallies were three COUNTs per candidate in three places
  (setup page, results, closing the vote): 21 queries for 7 positions. Now
  one grouped query (`src/view/slating/tallies.py`).
- The results page's objections table ran a query per position; the slate
  status API ran four COUNTs on applications where one aggregate does.
- Removed two dead duplicate views (`form_builder.reorder_fields`,
  `position_manager.reorder_positions`): the routes use `api.py`'s, and the
  dead form-builder one had the weaker `is_admin` check.

### Not changed — for Mason to decide
- **Slating activity IPs.** Slating's activity log still records
  `REMOTE_ADDR` (the nginx socket, so effectively nothing). Switching to the
  real client IP is a pending anonymity decision
  (`test_client_ip_single_source.PENDING_DECISION`), not a sweep item. An
  edit in this release was reverted for that reason.
- **Who may apply.** `check_eligibility` says pledges and non-Active members
  can't apply, but `apply_view` only checks the pledge page restriction (it's
  `pledge_page_allowed`, so pledge applications look deliberate). Inactive
  members and alumni can apply.
- **Destroying interview notes has no button.** `slating_destroy_notes`
  exists but no page links to it.
- **Live tally after voting.** A member who has voted sees the running tally
  while others are still voting.
- **Re-votes delete history.** Re-opening individual voting deletes the
  failed positions' votes, so that round's breakdown is gone from the summary.
- **Known residual (not new):** sequential ids on ballots and votes still
  allow coarse ordering at the database level (v3.16.2's note).
- `make check-css` fails on `add` and `index`. Those come from an arbitrary
  Tailwind class Tailwind reads out of `double-submit.js` and its test (since
  v3.46.x), not from this release.
