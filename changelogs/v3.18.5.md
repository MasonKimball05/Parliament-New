## 🔴 `redact_kai_logs` redacted three fields and the page rendered four

`src/kai_audit.py`, `templates/activity_logs.html`, `src/view/activity_logs.py`.

`ActivityLog.ip_address` is a plain `GenericIPAddressField` filled from
`request.META` on every write, and every Kai writer passes `request=request`.
So a Kai submission row carries **the reporter's IP address** — and the page
printed it, in its own column, immediately beside `display_actor` reading
*Anonymous*. The CSV export wrote it too. `audit_search_q` left
`ip_address__icontains` in `open_columns`, deliberately, and the search box
placeholder advertises the fact: *"Search description, IP..."*.

**Why an IP counts.** The old docstring's justification was
*"neither carries a name"* — and that is the wrong test. v3.16.2 settled this
already, in the general form: *when redacting, ask what the redacted view can
be joined against — a timestamp, a sequence, or an ordering is a join key.* An
IP is a considerably better join key than any of those. It does not have to
identify anyone by itself; it only has to be matchable against something that
does.

**And the other half of the join is on the same page.** Two requests, by any
officer or chair, no special access:

```
1.  /activity-logs/?user=<member>&date_range=all
    → their NON-Kai rows, each rendering their IP.        (IP → member)

2.  /activity-logs/?category=kai&date_range=all
    → Kai rows: actor "Anonymous", description scrubbed,
      IP column intact.                                   (Kai row → IP)
```

Or collapse it into one: `/activity-logs/?q=<ip>&category=kai`. That is the
`?user=` dropdown oracle v3.18.4 closed, reached through the search box.

There is a small irony worth recording: **v3.18.4 made step 1 cleaner.** Before
it, `?user=<member>` returned that member's Kai rows too; now it returns only
their non-Kai rows, which is a tidier lookup table.

**Blast radius:** `officer_required` — every officer and chair, consulting no
`KaiMemberPermission`. Same population as the 08-02 and 08-03 🔴s.

**Scope, checked rather than assumed:** `/activity-logs/` page and CSV only.
`admin_v2.py:1789/:1813` and `admin.py:1136` use `exclude_kai_logs`, so no Kai
row reaches them; `templates/admin_v2/dashboard.html`'s activity panel renders
`display_actor` and has no IP column at all.

**Honest caveat.** A chapter house or campus network NATs many members behind
one address, which makes the match ambiguous for on-campus activity. It is not
ambiguous for a case filed from a phone on cellular or from home broadband, and
a reporter filing a Kai case is unlikely to have done it from the common room.
NAT is noise, not a control.

### The fix

`display_ip`, the fourth member of the set, attached by `redact_kai_logs`
alongside `display_actor` / `display_actor_id` / `display_description`. The
template and the CSV read it; `test_no_template_renders_raw_audit_fields` now
watches `log.ip_address` as well.

The invariant is deliberately narrower than "blank every Kai row":

```
display_ip is blank  ⟺  display_actor was replaced
```

which is why the three blanking sites are exactly the three places
`display_actor` is assigned a constant, including the `entry is None`
fail-closed branch. A Kai row authored by a chair who is neither party keeps
its IP — nothing about that row is redacted, and over-redacting the audit log
costs real fidelity for no confidentiality gain.

And the input half, because output-without-input is the oracle this module has
now closed four times: `ip_address__icontains` moves from `open_columns` into
`identity_columns`. Non-Kai rows are unaffected — an IP search still matches
every one of them, and a fully permissioned reviewer still reaches Kai rows.
`object_repr` stays open: a case number identifies a case, not a person, and
the confidentiality matrix already accepts it at officer level.

### Why neither guard caught it

Both enumeration guards are syntactic. `TheEnumerationIsMaintainedTests` greps
for search terms; `TheAuthorFilterEnumerationIsMaintainedTests` greps for
author-valued filters. An unredacted **rendered column** is neither.

So the new `TheRedactionCoversEveryRenderedColumnTests` asserts on *output*
instead: render the page as an unpermissioned officer and ask whether anything
identifying the reporter survives anywhere in the body. That is weaker as an
enumeration and stronger as a guarantee — it needs no advance knowledge of
which columns exist, so the next column added to this template is covered on
the day it is added, by nobody remembering anything.

## 🟠 A negated JSON key transform silently dropped unrelated rows

`src/kai_audit.py`, `audit_search_q`'s final line.

`~rows_for_cases_q(...)` was applied directly. One of that helper's two terms
is a JSON key transform, and `metadata -> 'report_id'` is SQL `NULL` on a row
that has no such key:

```
NULL IN (…)      → NULL
FALSE OR NULL    → NULL
NOT NULL         → NULL   →  row fails the WHERE clause and vanishes
```

Django rescues half of it. `sql/query.py`'s `build_filter` adds an
`IS NOT NULL` term inside a negated clause when the target field is nullable,
which covers rows where `metadata` itself is NULL. It does **not** cover
`metadata = {"record_count": 42}` — non-null, key absent, transform still NULL.
`KeyTransformIn` (Django 5.2, `db/models/fields/json.py`) is a plain
`lookups.In` subclass that only massages the parameter; there is no
key-presence guard anywhere in it.

**Effect:** for a viewer holding both Kai identity flags who is a party to at
least one case — i.e. the Kai chairs and reviewers, on the audit log — a search
silently lost every matching row whose metadata was a non-null dict without
`report_id`. Those are common; the CSV export writes one about itself on every
run. It **fails closed**, so it was never a disclosure, but a search box that
returns a fraction of its matches with no signal is a bad failure mode.

**Fix:** negate a pk set. A pk is never NULL, so there is no three-valued logic
left to get wrong:

```python
party_rows = Q(pk__in=ActivityLog.objects.filter(rows_for_cases_q(party_cases)).values('pk'))
```

`Q(metadata__has_key='report_id') & …` would also work, because `HasKey`
returns a real boolean and `FALSE AND NULL` is `FALSE` — but it asks the next
reader to re-derive a subtlety, and the subquery does not. `rows_for_cases_q`
stays the single resolution rule, which is what v3.18.4 added it for.

**The general lesson, and it has nothing to do with Kai: a JSON key lookup is
not safe to negate.** The section-10 tests added in v3.18.4 could not see this
because they only ever use the helper positively.

## 🟡 The export's truncation banner was counted as a record, and sat first

`src/view/activity_logs.py`.

- `len(rows)` included the banner, so `description` and `metadata.record_count`
  were **off by one** on exactly the exports worth auditing. Now counted before
  the banner is appended, with `total_matched` and `truncated` recorded
  alongside — the number an auditor wants is "how much existed", not just "how
  much left".
- The banner was row 1, directly under the header, with prose in the
  `Timestamp` column. Anything reading the file as data (`pandas.read_csv`, a
  spreadsheet sort, a script) took it as a record with an unparseable
  timestamp. It goes last now, where it degrades gracefully: a reader who stops
  early loses the warning, not the parse.

## Tests

**14 new tests**, all of which fail against the v3.18.4 tree.

`src/test_kai_audit_log.py`

- `TheIpAddressIsPartOfTheIdentityTests` (8) — the helper-level invariant:
  redacted row blanks the IP; non-Kai row keeps it; full reviewer keeps it; a
  Kai row by a non-party keeps it; the `entry is None` branch fails closed on
  the IP too; and the three search-side cases (an officer's IP search does not
  reach Kai rows, still reaches non-Kai rows, and a full reviewer still can).
- `TheNegatedPartyPredicateDoesNotDropUnrelatedRowsTests` (4) — a row with
  `metadata` lacking `report_id` survives the negation; a NULL-metadata row
  does too (pinning the half Django already handles, so a refactor cannot lose
  it); plus two controls proving the narrowing still works — the viewer's own
  case is still excluded from identity columns, including the metadata-only
  appeal row, which is what would break if someone "fixed" the NULL problem by
  dropping the metadata term.
- `test_no_template_renders_raw_audit_fields` extended to watch
  `log.ip_address`.

`src/test_kai_party_safe_surfaces.py`

- `TheRedactionCoversEveryRenderedColumnTests` (7) — end-to-end through the
  Django test client: the Kai row does not render the reporter's IP, the
  control row still does, a non-party's Kai row keeps its IP, the CSV export
  does not carry it, searching the IP does not return the Kai row, searching it
  still finds non-Kai rows, and a full reviewer can still search by IP.

Every assertion has a control, per this module's standing discipline: a surface
that is simply broken — returning nothing to anybody — must not pass.

✅ **Executed 08-04-26 by Mason, on sqlite dev settings: 47 + 25 = 72 tests, all
green.** This is the first time either module has been run, so it also clears
v3.18.4's 15 — the "never executed" warning carried since 08-03 is closed.

⚠️ **But green on the first run is not evidence the tests catch the bugs.** The
claim "every test here fails against the v3.18.4 tree" is written in three
docstrings and has not been checked. This module's own standing lesson applies:
*an assertion that cannot distinguish the bug from the fixture is not an
assertion.* The negative control:

```
git stash push src/kai_audit.py src/view/activity_logs.py templates/activity_logs.html
.venv/bin/python manage.py test src.test_kai_audit_log src.test_kai_party_safe_surfaces
git stash pop
```

**Revert the template too, not just the helper** — and that subtlety is worth
keeping. Reverting `kai_audit.py` alone leaves `display_ip` unset while the
template still asks for it, and Django resolves a missing attribute to `''`, so
the IP renders nowhere and `test_the_kai_row_does_not_render_the_reporters_ip`
**passes for the wrong reason**. Only `test_the_control_row_still_renders_its_ip`
would fail. A partial revert produces a false clean bill of health here, which
is exactly the shape of thing this suite exists to catch.

⚠️ **The 🟠 was verified on sqlite, and the argument was made about jsonb.**
`TheNegatedPartyPredicateDoesNotDropUnrelatedRowsTests` passes on sqlite, whose
`JSON_EXTRACT` returns NULL for an absent key the same way Postgres's `->`
does, so the semantics should be identical — but prod and CI are Postgres and
that is where the finding was reasoned about. Worth one run against Postgres
(`DB_BACKEND=postgres`) before relying on it.
