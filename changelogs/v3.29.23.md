## Part 1 — per-date hours

v3.29.22 gave every extra date the primary submission's own `hours`
value, on the assumption that "same service, several days" meant the
same number of hours each day. It doesn't — a member might do 2 hours
one day and 4 the next for the same organization.

**Template** (`submit_hours.html`): each "+ Add another date" row now
adds a *paired* `<input type="number" name="extra_hours">` next to the
date input, added and removed together so the two lists
(`extra_dates`/`extra_hours`) stay index-aligned — no hidden field or
JSON needed, since `request.POST.getlist()` already collects each by
name. Same bounds as the primary Hours field (`step=0.25`,
`min=0.25`, `max=24`).

**View** (`src/view/service_user_dashboard.py`): `_extra_service_dates_from_post`
is now `_extra_service_entries_from_post`, returning `(date, hours)`
pairs instead of bare dates. Hours validation mirrors
`ServiceHoursSubmissionForm.clean_hours` (`0 < hours <= 24`). A row with
a bad date is still dropped silently (unchanged from v3.29.22 — no
different than the lack of a bounds check on the primary date field);
a row with a bad **hours** value is dropped with a `messages.warning`
naming the date, since unlike a blank date, a typed hours value is
something the member will expect to see reflected — silently discarding
it would look like data loss. One bad row doesn't block the rest of the
submission.

The activity-log line for each row already read `target.hours` (not the
primary submission's hours), so per-row logging needed no change. The
success message and the VPP notification email *did* assume uniform
hours ("X hours for each of N dates" / "N dates, X hrs each") — both
rewritten to report the combined total without claiming a uniform
per-date number, and the notification body now lists each date next to
its own hours.

## Part 2 — approve a batch together

**Design.** Every row created from one multi-date POST now gets a
shared `batch_id` (`uuid.uuid4()`, generated once and copied onto every
clone; stays `NULL` for an ordinary single-date submission).
Deliberately **not** used by approval, editing, or the CSV export — those
stay exactly the per-row model v3.29.22 already built. It exists purely
so the officer review page can identify which rows came from the same
submit action, without guessing from matching hours/organization/
timestamp (which could coincide by chance; a UUID assigned once can't).

**Reuse, not a new endpoint.** `bulk_actions_service`
(`src/view/service_hours.py`) already accepted an arbitrary list of
`submission_ids` and bulk-approved/rejected whichever of them were still
`pending` — built for the existing "select rows, choose an action, Apply"
UI on `/service-hours/submissions/`. Approving "all the ones submitted
together" doesn't need a new view; it needs an easy way to *select* a
batch's rows, then the existing Apply button does the rest. No new
route, no new template.

**`view_service_submissions`** now computes, in two grouped queries (not
one query per batch on the page — the page was never paginated, so a
busy period could have many batches), `batch_pending_count` (siblings
still awaiting review — what the "select together" control acts on) and
`batch_total_count` (all siblings regardless of status — purely
informational) for every row, attached as plain attributes on each
already-materialized `ServiceHoursSubmission` instance.

**`view_submissions.html`**: a row whose batch has more than one
still-pending sibling gets a small "select all N" button under its
checkbox (`data-batch-id`-keyed), which checks every pending checkbox
sharing that batch id — reusing the page's existing select/Apply flow
rather than adding a second form. A row that's part of any multi-date
submission (any status) also gets a small "multi-date (N)" badge next to
its date, so an officer reviewing one date can tell there were others
even after some have already been approved/rejected individually.

## New tests

- `src/tests/legislation/test_service_hours_multi_date.py` — rewritten
  for the new `extra_dates`/`extra_hours` pairing (22 tests): distinct
  hours per date, `batch_id` shared across a multi-date submission and
  null for a single-date one, two separate submissions getting two
  different batch ids, and the new hours-hygiene cases (blank/
  non-numeric/zero-or-negative/over-24 hours drop just that date; one bad
  row doesn't block the others) — plus every v3.29.22 case updated to
  post the paired field.
- `src/tests/legislation/test_service_hours_batch_approval.py` (NEW, 8
  tests) — the officer side: `batch_pending_count`/`batch_total_count`
  computed correctly (including as siblings get reviewed individually),
  the template actually renders the `select-batch-btn`/`data-batch-id`
  markup for a real batch and not for a single date, and — the actual
  promise — posting a whole batch's ids to the real, pre-existing
  `bulk_actions_service` endpoint approves/rejects every row together in
  one request (and, separately, that approving only some of a batch
  leaves the rest pending — the control isn't a constraint).
