Reported by Xander Guill (#72) and Nate Creutzinger (#71), who noticed the
CSRF 403s reported 08-25-26 (`v3.26.2.md`/`v3.26.3.md`) were landing almost
entirely on mobile, and flagged the pattern to Mason. That observation is
what pointed at the actual mechanism.

## Why mobile specifically

`Cache-Control: no-store` (v3.26.2) doesn't reliably stop this. Checked
current browser behavior rather than assuming: Safari has bfcached
`Cache-Control: no-store` pages on both desktop and mobile all along, and
Chrome finished rolling out the same change in March 2025, evicting a
bfcached entry only on things like a cookie change — which isn't guaranteed
to fire on a server-side session/CSRF rotation. So a page can be restored
from a swipe-back or an app-switch-and-return holding a CSRF token that was
baked in when the page was frozen, no longer matching a since-rotated
cookie (login rotates it). This is disproportionately mobile because
swipe-back / backgrounding-and-returning is the ordinary way a phone gets
used, not an edge case — desktop users rarely trigger the same page-freeze
sequence.

## Fix

`pageshow`'s `persisted` flag is `true` exactly when the browser restored a
frozen page instead of loading fresh. `base.html` now reloads on that
signal, inside the same `Parliament` IIFE that already owns CSRF handling
(`Parliament.post`). A reload re-renders the whole page from the server,
which is the only fix that reaches every place this codebase embeds a
token — the `<meta name="csrf-token">` tag, every `{% csrf_token %}` hidden
field, **and the ~40 templates** (chat, Kai, slating, admin-v2, profile,
calendar, and more) that bake the token into a JS constant at render time
and don't read the meta tag at all — without touching each one
individually. Those ~40 are the same population `test_fetch_error_visibility
.py`'s ratchet already tracks as a known, too-large-to-convert-at-once set;
this fix reaches all of them anyway because a reload re-executes every
script fresh, regardless of how each one reads its token.

### Guarded against wiping unsaved typing

bfcache's other job is preserving exactly that — a half-written chat message
or Kai report draft — across a back-navigation. Silently discarding a draft
to fix a *different* page's staleness would be a worse bug than the one
being fixed, and it's a real scenario on mobile specifically: get
interrupted mid-draft, come back later, see the draft restored — that's
bfcache working as intended. So before reloading, the code checks whether
any text input, textarea, or `contenteditable` element holds content that
differs from what the server rendered (`.value !== .defaultValue`, or
non-empty text for `contenteditable`). If so, the reload is skipped and the
page behaves exactly as it did before this change — no regression;
submitting could still 403 in the rare case the token actually rotated,
same as today.

## Verification

New `src/tests/security/test_bfcache_reload.py` (8 tests) — structural
assertions that the listener exists, checks `persisted` first, and that the
unsaved-content guard is defined and evaluated *before* `location.reload()`
is ever reached (order matters: a version that reloaded first and checked
second would already have discarded what it exists to protect).

The guard's actual truth table has no Python side to assert on, so it was
exercised directly with a small Node harness during review: a clean page
(no field changed from its rendered default) → reload fires; a dirty
`<textarea>` (the chat compose box shape, `#message-input` in
`chat/channel.html`) → reload skipped; a search box pre-filled from a query
param and left untouched → reload fires (value equals its rendered default,
correctly not flagged as "unsaved"); a dirty `contenteditable` → reload
skipped; an empty/whitespace-only `contenteditable` → reload fires.

`node --check` on the extracted script — syntax clean. `manage.py check` —
clean (unrelated pre-existing sandbox-only Kai-schema warning). Full
targeted run — `test_fetch_error_visibility` (confirms this doesn't disturb
`Parliament.post`'s ordering or content, which that suite pins byte-for-byte
in places), `test_csrf_token_source`, `test_csrf_failure_diagnostics`,
`test_changelog_cache`, `test_middleware_hot_path`, `test_bfcache_reload` —
**109 tests, 0 failures**. Bandit — 0 MEDIUM+, no new findings. Confirmed no
pre-existing `pageshow` listener anywhere else in the repo to conflict with,
