# v3.9.1 — Performance: Context Processor Caching & Query Reduction

**Release Date:** June 18, 2026
**Deployment Status:** 🔲 Not Deployed
**Type:** Performance

---

## Overview

Targeted query reduction across the most trafficked code paths. Every authenticated page load was firing 3–5 unnecessary uncached DB queries via context processors. The home view had several N+1 patterns. Two composite indexes added for the most common queryset filters.

---

## What Changed

### 1. `two_factor_status` Context Processor — Cached (5 min)

Previously fired 2 uncached DB queries on every single page load for every authenticated user (`StaticDevice.filter().first()` + `token_set.count()`). Now cached per-user at `2fa_status_{pk}` for 5 minutes. Cache is invalidated immediately when backup codes are regenerated (`_generate_backup_codes`) or acknowledged (view-backup-codes page).

**Files:** `src/context_processors.py`, `src/view/two_factor.py`

---

### 2. `user_preferences` Context Processor — Cached (5 min)

Previously called `UserPreferences.objects.get_or_create(user=request.user)` on every request with no caching. Now cached per-user at `user_prefs_{pk}` for 5 minutes. Cache is invalidated immediately on form save in the preferences view.

**Files:** `src/context_processors.py`, `src/view/preferences.py`

---

### 3. Chat Unread Count — N+1 → Single Annotated Query

On cache miss the chat unread badge was fetching all `ChatReadReceipt` rows for the user and calling `get_unread_count()` in a Python loop — one COUNT query per channel. Replaced with a single annotated queryset using `Subquery` + `Coalesce`: newer-than-last-read messages are counted in the DB, with a fallback to all-messages for receipts with no `last_read_message`. A user in 10 channels went from 11 queries to 1.

**Files:** `src/context_processors.py`

---

### 4. `home.py` — Four Query Fixes

**`new_announcements_week` / `new_events_week`**
Was loading all recent announcements/events into Python then calling `is_visible_to_user()` in a loop. Replaced with ORM COUNT queries using the `_vis_q` visibility filter already built on the same page. 2 full-table fetches → 2 indexed COUNT queries.

**`user_committees` double query**
`user_committees.count()` in the context dict was firing a second DB round-trip after the queryset was already being evaluated in the template. Queryset is now forced to a `list()` and `len()` used for the count.

**Legislation preview loop — plurality N+1**
Plurality mode was calling `votes.filter(vote_choice=opt).count()` in a Python loop per option per legislation item. Now a single `values('legislation_id', 'vote_choice').annotate(n=Count('id'))` prefetch covers all items; the loop reads from the in-memory dict.

**Legislation preview loop — percentage extra query**
Percentage mode called `Vote.objects.filter(legislation=leg, vote_choice='no').count()` per item when `historical_no_votes` was None. Eliminated by the same prefetch above.

**Files:** `src/view/home.py`

---

### 5. Composite Indexes — Announcement & Event

Added indexes on the two most-queried filter patterns that had no composite coverage:

- `Announcement(is_active, -posted_at)` — covers `filter(is_active=True).order_by('-posted_at')`
- `Event(is_active, archived, date_time)` — covers `filter(is_active=True, archived=False).order_by('date_time')`

**Files:** `src/models/announcements.py`, `src/models/events.py`

---

### 6. `active_quarantines` ORM — Excludes Expired Records

Three `filter(released_at__isnull=True)` queries in `admin_v2.py` (dashboard count, security view, quarantine management page) were not excluding records where `expires_at` had passed but the nightly Celery task hadn't run yet. Added `Q(expires_at__isnull=True) | Q(expires_at__gt=now)` to all three so the UI stays consistent with the `is_active` property.

**Files:** `src/view/admin_v2.py`
