## 1. Error pages left a database connection open (the one on prod)

Under ASGI, Django renders the page for an exception that reaches its
outermost async layer with `sync_to_async(response_for_exception,
thread_sensitive=False)` (`django/core/handlers/exception.py`). That runs the
404/403/400/500 handler on asgiref's shared thread pool, not on the request's
own thread, so the end-of-request `close_old_connections` never sees the
connection it opened. Every unmatched URL takes this path (`Resolver404`), and
so does an `Http404` / `PermissionDenied` raised by a view.

The pages read the database: the `feature_flags` context processor re-reads
`src_featureflag` and `src_pagetoggle` whenever its 60-second cache has
expired, and `request.user` loads the session. So a bot 404 in a quiet minute
left one idle PostgreSQL backend in Daphne until the next restart. A thread
that already had one reused it on the next cold 404, which is why prod's
connections were hours old and still being used.

- `src/view/error_handlers.py`: `_closes_db_connections` wraps all four
  handlers. After the response is built it calls `close_old_connections()`,
  unless a transaction is open (then the normal end-of-request close handles
  it).
- `src/urls.py`: `handler400` and `handler403` are now set (to Django's default
  pages, wrapped). Before only 404 and 500 were custom.
- **Reproduced end to end** on a cloud copy (Daphne + PostgreSQL 16, Python
  3.12.3 like prod, `DEBUG=False`): a 404 after the flag cache expired left one
  idle backend whose last query was the `src_pagetoggle` SELECT, the same as
  prod. With the fix: none, after cold and warm 404s, signed-in 404s, normal
  pages and a honeypot hit.

## 2. The honeypot's geolocation thread left a connection open

`honeypot()` starts a plain `threading.Thread` for `lookup_geo`, which reads and
saves the `HoneypotAccess` row. That thread isn't a request, so its connection
was never closed: one idle backend per honeypot hit (reproduced; last query
`UPDATE "src_honeypotaccess" …`). Not what was on prod on 10-21, but the same
kind of leak.

- New `_lookup_geo_in_thread()`: runs `lookup_geo`, logs any error, and always
  calls `connections.close_all()`. `honeypot()` starts that instead.
