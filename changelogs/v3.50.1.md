## 🔴 Any chair could make himself an admin

`officer_required` lets in officers **and chairs**. `transfer_role` sets
`is_admin = True` on the incoming holder of a role with `grants_admin`. So a
chair could POST `{"incoming_user_id": "<himself>"}` to
`/officers/transitions/<President role id>/transfer/` and be an admin, and the
same request took the role away from the real President (one-per-chapter roles
clear the old holder). Checked with a test on `b6e9fec`: 200, `is_admin` True.

The same gap, one step slower, in `edit_member` (a chair could put the
President role on his own account), `assign_role_member`, `add_member` (an
account whose temp password he's shown) and `assign_appointment`: none of
these sets `is_admin` itself, but "Sync officer admins" makes every holder of a
`grants_admin` role an admin, so the next admin to press it would promote him.

Who may *set* `Role.grants_admin` was already admin-only (`role_detail`,
`add_role`). Now who may *hold* such a role is too:

- New `src.permissions.role_change_error(actor, role, member=None)`: a non-admin
  may not give or take a `grants_admin` role, and may not change the roles on
  an admin's account (v3.50.0's rule for `edit_member`, applied to roles).
- Checked in `transfer_role` (incoming holder, outgoing holder, and everyone a
  one-per-chapter transfer clears), `assign_role_member`,
  `unassign_role_member`, `edit_member` (only the roles actually added or
  removed), `add_member` and `assign_appointment`. Nothing is saved on refusal
  (403).
- `edit_member` also refuses a `roles` value that isn't a list of ids (it was a
  500).

Not changed (#needs-review): a chair can still give himself or anyone any
*other* role, and change his own `member_type` to Officer on `edit_member`.

## 🔴 GroupMe never posted anything on PostgreSQL

`deliver()` did `select_for_update().select_related('channel')`. `channel` is a
nullable FK, so Django uses a LEFT OUTER JOIN, and PostgreSQL refuses:
`FOR UPDATE cannot be applied to the nullable side of an outer join`. Every
announcement echo and event reminder raised `NotSupportedError`, which is not a
`GroupMeError`, so the task didn't retry and `queue_send` logged it as "broker
down". The message stayed `queued` with 0 attempts and the 5-minute sweep
re-queued it forever. The dashboard's **Send test** posts directly, so it
worked and made the channel look fine.

SQLite ignores `FOR UPDATE`, which is why the v3.49.0/v3.50.0 checks passed. CI
runs PostgreSQL: 7 of the 37 GroupMe tests fail there on `b6e9fec`.

Fix: drop the `select_related` (one extra query; only the message row is
locked). New test checks the query has no outer join, on any backend.

## 🟡 A GroupMe retry didn't re-check anything

A message can wait minutes (retries at 1, 2, 4 min; the sweep; the dashboard's
Retry). `deliver()` now re-checks, right before posting: the channel is still
on; the announcement still exists, is published, and its "Visible to" still
allows that group; the event still exists, isn't hidden, hasn't started, and
still allows that group. Otherwise the message is marked **skipped** with the
reason. This is the rule Mason set on 10-17 ("a GroupMe only receives what
everyone in it can see on Parliament").

## 🟢 Moving an event didn't re-send its reminders

The officer event editor never cleared `reminder_1_sent_at` /
`reminder_2_sent_at` (push) or `groupme_reminded_at` when the time changed, so
an event moved after its reminder went out got no reminder for the new time
(the GroupMe one had already named the old time). The Service Hours editor has
always cleared the push marks for this reason. Now, when the time changes, the
marks are cleared on the edited event(s) that are still in the future. An event
whose GroupMe reminder had gone out keeps its groups and lead time (the form
doesn't show the boxes for it).

Also: the set of events a series edit covers is now worked out before the other
occurrences move. After moving more than one occurrence earlier, the GroupMe
boxes skipped the next occurrence.
