# v3.18.8 — Every audit trail was recording Cloudflare, not the visitor

**Date:** 08-06-26
**Type:** Security / forensics fix. **No migration.**
**Committed & pushed:** 08-06-26 (`f260539`). *Corrected 08-07-26 — this line read "not yet" while the release was already on origin/main, and `DEPLOYED.md` had no row for it at all. Verified with `git log --diff-filter=A -- changelogs/v3.18.8.md`.*
**Deployed:** *not deployed*

Found from a **production activity-log export**, not from a code review — Mason
exported `/activity-logs/` after noticing a run of `admin`/`root`/`django`
failed logins and asked whether the attacker knew the stack.

They didn't (see below). The export answered a different and worse question.

---

## What the log showed

**All 22 distinct IP addresses in the export were Cloudflare edge addresses.
Not one was a visitor.**

A 47-attempt credential-stuffing burst at 01:46–01:50 and six members' logins
over the preceding week were recorded from the **same address pool**, with four
addresses appearing in both. The audit log could not distinguish an attacker
from a brother.

## Why — and it is not the setting

`.env` has `BEHIND_CLOUDFLARE=True`, and it has been working the whole time,
everywhere it is consulted. `src/utils/security_utils.get_client_ip` knows two
things nothing else does:

* `BEHIND_CLOUDFLARE` means the visitor is in `CF-Connecting-IP`;
* the **rightmost** X-Forwarded-For entry is the safe one *only* when nginx is
  the sole proxy — nginx appends the socket peer via
  `$proxy_add_x_forwarded_for`, so leading entries are forgeable and the last is
  not.

**That second fact inverts behind Cloudflare.** nginx's socket peer is then the
Cloudflare edge, so rightmost returns Cloudflare and the visitor — which
Cloudflare puts *earlier* in XFF, and also in `CF-Connecting-IP` — is thrown
away.

Five places reimplemented those four lines without the reasoning, and none of
them called the helper:

| Site | Consequence |
|---|---|
| `models/activity.py:203` | **Every `ActivityLog` row** — the export above |
| `models/users.py:886` | **Every `UserSession`** — Active Sessions panel, and the "Stored IP / Current IP" pair in the session-hijack warning |
| `view/admin_v2.py:3024` | **The lockdown whitelist suggestion** — see below |
| `context_processors.py:424` | Per-request, every page |
| `middleware/maintenance.py:71` | Maintenance-mode block logging |

Fifteen other modules import the helper correctly.

⚠️ **The `admin_v2` one had teeth.** That value is offered to an admin as *"the
IP to whitelist"* while activating **emergency lockdown**. Whitelisting a
Cloudflare edge does not whitelist you — it whitelists every visitor Cloudflare
routes through that edge, plausibly including whoever the lockdown was for. A
whitelist that admits the attacker is worse than no lockdown.

## The pattern, sixth release running

v3.16.3, v3.18.1, v3.18.3, v3.18.4, v3.18.5 and now this: *a rule stated
correctly, a helper written to enforce it, and call sites left outside the
helper.*

What makes this instance the clearest argument yet for structural enforcement:
**the copies look right.** They are the same four lines the helper contains, and
the thing that makes them wrong lives in the *docstring of the function they
did not call*. There is nothing in the diff of a copy to review. Review cannot
see an absent call.

So the fix is not only the five edits. It is
**`src/test_client_ip_single_source.py`**: an AST walk that fails on any read of
`HTTP_X_FORWARDED_FOR`, `HTTP_CF_CONNECTING_IP` or `REMOTE_ADDR` off `request.META`
anywhere in `src/` except the helper itself.

It parses rather than greps, deliberately — this file and the helper both
*discuss* `X-Forwarded-For` in prose, and a guard that cannot tell a mention
from a read gets silenced rather than obeyed. It carries negative controls for
the same reason `test_template_comments.py` does: a test that passes by finding
nothing is indistinguishable from a detector that can't find anything, and the
reason five copies survived is that nothing was looking.

**The guard immediately found 32 more that the original grep missed** — reads of
`REMOTE_ADDR` rather than XFF, which behind nginx's unix socket is the socket
peer. Two were unambiguous and are fixed here:

* `view/webauthn.py:257` — a security-log line for an unknown passkey
  credential; `get_client_ip` was already imported at the top of that module and
  used elsewhere in it. This one line missed.
* `view/home.py:43` — the per-request home-page log line.

## ⚠️ 26 slating call sites are NOT fixed — deliberately, awaiting Mason

The other 30 are in `src/view/slating/`, feeding `SlatingActivity.ip_address` on
vote-cast, application, slate-build and interview rows. They are wrong the same
way, and they are listed in `PENDING_DECISION` in the new test rather than
changed.

**Because fixing them adds data that is not currently recorded**, to the one
module whose anonymity rules are the most carefully dispositioned thing in
CLAUDE.md. `SlatingVote.voted_at` is excluded from the admin *specifically*
because a timestamp is a join key, and v3.18.5's rule is that **an IP does not
have to name anyone, it only has to be a join key.** Populating real IPs into
slating audit rows is a change in kind, not a bug fix — it should be made on
purpose, not by a sweep labelled "fix the Cloudflare thing".

*Current reading, for whenever that decision happens:* `SlatingActivity` already
records `user` and is visible by design (participation is not secret; the
**ballot** is), and `SlatingVote` stores no IP — so a real IP there adds no new
join against the ballot table. That argues it is safe. It is still a decision.

`test_the_pending_list_has_no_dead_entries` keeps the exemption honest in both
directions: every listed file must still contain a raw read, so fixing one
forces deleting its entry in the same commit. An exemption list that outlives
what it exempts is how a temporary allowance becomes permanent silently — the
same failure as the deploy claim that cost eight reports.

## On the attack itself — no, they didn't know it was Django

Username order was `admin` ×25 → `root` ×5 → `administrator` ×5 → `test` ×4 →
`dev` ×4 → `django` ×4, at machine-regular 3–5 second intervals over 3.5
minutes. A static wordlist worked top-down with the count decaying: spray the
likely one, then walk the list. `django` is in every off-the-shelf username
list, and the site self-identifies anyway — the `csrftoken` and `sessionid`
cookie names and the `/admin/` login page fingerprint Django in one request.
Commodity bot.

**One thing from that burst is still open and is NOT explained by any of the
above:** `admin` was attempted **25 times against a 5-per-username limit** that
blocks *before* `authenticate()` — so those 25 should never have been logged.
Username bucketing does not involve IP, so the Cloudflare bug does not account
for it. Worth checking whether Redis is actually up on prod: `settings.py`
documents a LocMemCache fallback, and a per-process cache would make every rate
limit per-worker.

## Also: every logout was writing two ActivityLog rows

Spotted in the post-deploy verification export, three rows deep — the same
logout appearing twice, one second apart, as *"Authentication / User Logout"*
and *"Other / Other Action"*, distinguishable only by a trailing full stop.

`view/logout_view.py` wrote a row manually with `action_type='other'` and then
called `logout()`, which fires Django's `user_logged_out` signal, which
`middleware/activity_logging.py:37` already logs. Two writers, one event, since
whenever the signal receiver was added.

The manual one is removed. The signal is the right survivor on both counts:

* **It categorises correctly.** `action_type='other'` put half of every logout
  under "Other" rather than "Authentication", so a category filter on the
  activity log has been showing an incomplete picture of both.
* **It covers every path.** This view is one way out; forced logouts from the
  session viewer and `QuarantineEnforcementMiddleware` call `logout()` without
  passing through it, and the signal catches those too. A per-view writer only
  ever logs the exits someone remembered to instrument — which is the same shape
  as the finding above, one layer up.

Historical rows are left alone; deduplicating them would be a data migration
over an audit table, which is not worth it for a cosmetic duplicate.

## Deploy

**Code-only, no migration.** `git pull`, restart `parliament-gunicorn.service`.
No static assets → no `collectstatic`, no Cloudflare purge.

✅ **Verify immediately after deploying:** log in, then open `/activity-logs/`
and confirm your own row shows a residential/campus IP rather than a
`104.x` / `162.158.x` / `172.7x.x` address. That check takes ten seconds and is
the only thing that proves the fix landed — the failure mode here is silent by
construction.

⚠️ **Do not blacklist any IP from the 08-06 burst.** They are Cloudflare edges;
four were also used by real members. `IPBlacklist` entries added on that
evidence should be reviewed and removed — and note v3.18.7, pushed and pending
deploy, *widens* `IPBlacklist` to cover `/admin/`.
