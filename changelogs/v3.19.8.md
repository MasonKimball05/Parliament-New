## 🔴 1 — `validate_mime_type` began rejecting every Word and Excel document in the chapter

v3.19.7 found that this function's `raise ValidationError` sat inside a `try`
whose `except Exception` caught it and downgraded it to a log line, so it had
**never rejected anything** since the day it was written. That finding was right
and the fix was right.

What the fix did not come with is any check of **what the function starts
rejecting once it works** — and `ALLOWED_FILE_TYPES`, the map from extension to
the MIME types libmagic is expected to report, was written under conditions where
being wrong had no consequence and had been dead code ever since.

Measured against the real `validate_uploaded_file`, on real files (Django
5.2.16, libmagic 5.41, files built by `python-docx` and `openpyxl`):

```
note.pdf       ACCEPTED
shot.png       ACCEPTED
shot.jpg       ACCEPTED
notes.txt      ACCEPTED
data.csv       ACCEPTED
doc.docx       REJECTED — appears to be "application/octet-stream", extension ".docx"
sheet.xlsx     REJECTED — appears to be "application/zip", extension ".xlsx"
```

**Two different causes, and only one of them is fixable by widening a buffer.**

```
xlsx  window=  2048 -> application/zip              ← the window the code used
xlsx  window=  8192 -> …spreadsheetml.sheet         ← the truth
docx  window=  2048 -> application/octet-stream
docx  window=262144 -> application/octet-stream
docx  from_file      -> application/octet-stream    ← never identifies it at all
```

- **`.xlsx` and `.pptx` failed on the read size.** `validate_mime_type` did
  `uploaded_file.read(2048)`. An OOXML file is a zip and libmagic cannot tell
  *which* OOXML it is until it has seen entries that sit past the first 2 KB of
  any real document. Deterministic — every real spreadsheet, every time.
- **`.docx` failed for a second reason that widening does not fix.** libmagic's
  OOXML rules fall back to `application/octet-stream` when they recognise the
  container but not the subtype.

**Blast radius was the whole upload surface — 17 call sites — and the ones that
hurt are the ones that were already doing it properly:** `submit_excuse.py:103`
(a doctor's note saved as `.docx`, the most likely form of the most sensitive
attachment in the app), `upload_legislation.py`, `edit_legislation.py`,
`manage_resolutions.py` (legislation is drafted in Word), the committee and
chapter document uploads, `kai_reports.py`, and the four writers v3.19.7 had just
added. On those four a rejection **drops the file and keeps the record**, so a
member submitting service hours with an `.xlsx` log gets a message and the hours
are saved without the evidence — right for a malicious upload, wrong for a
spreadsheet.

### The fix, in the order it had to happen

1. **The enumeration first — `src/test_upload_type_fixtures.py` (12 tests).**
   `test_every_allowed_extension_has_a_fixture_or_a_stated_reason` walks
   `ALLOWED_FILE_TYPES` itself and fails the build when someone adds an
   extension without adding a real sample file for it. Written first, it fails
   against the v3.19.7 tree and names exactly which entries are wrong. The
   fixtures are built in-process from the **standard library only** — no
   `python-docx`, no `Pillow`, no committed binaries.
2. **`SNIFF_BYTES` 2048 → 65536**, with the measurement recorded next to the
   constant rather than in a changelog nobody re-reads.
3. **Zip-backed formats are validated structurally instead of sniffed.** New
   `_validate_zip_container` opens the archive and reads what the file declares
   about itself: `[Content_Types].xml` for OOXML, the `mimetype` entry for ODF.
   ⚠️ **The tempting fix was to add `application/zip` and
   `application/octet-stream` to the `.docx` row.** That makes the check pass and
   makes it meaningless — `octet-stream` is what libmagic says about anything it
   cannot identify, so admitting it admits everything. Reading the container is
   the question the MIME map was always pretending to answer, and unlike
   libmagic's heuristics it does not depend on which version of a system library
   the server happens to have.
4. **`seek(0)` moved into a `finally`** on the magic path, which a raising
   `read()` used to skip.

### Three things found while fixing it

⚠️ **THE NEW TEST CAUGHT A BUG IN THE FIX, ON ITS FIRST RUN.** The first draft of
`_validate_zip_container` put `finally: seek(0)` on the `try` around
`ZipFile()` — correct for the pointer as of that line, and wrong by the time the
function returned, because `archive.open(...)` reads the manifest and moves it
again. `.docx` came back at offset 413 and `.odt` at 77, so the caller's `save()`
would have stored a truncated document. The rewind now wraps the whole function.

> **A validator that consumes the stream is a data-loss bug wearing a security
> fix's clothes, and it is invisible to every test that only asks whether
> validation passed.** `test_validation_leaves_the_file_pointer_at_the_start` is
> the one that asks the other question.

⚠️ **`raise ... from None` IS LOAD-BEARING HERE, NOT COSMETIC.** Django's parallel
test runner moves failures between processes by pickling them, and a chained
exception drags a traceback object along, which cannot be pickled. See §5.

⚠️ **THE THREE LEGACY OLE2 EXTENSIONS ARE THE ONE PLACE IN THE MAP NOT BACKED BY
A FIXTURE, AND THEY SAY SO.** `.doc`/`.xls`/`.ppt` cannot be constructed without
a builder library this project does not have. They are in a `NO_FIXTURE` dict
whose values are **reasons stating the mechanism**, not bare exemptions —
CLAUDE.md records that *an exemption is a claim about a mechanism, not about a
number*, and there is a test asserting the reasons are long enough to be
checkable. They are covered one step weaker by
`test_legacy_office_extensions_accept_the_generic_ole_types`, which pins the
mapping (the generic `x-ole-storage` / `vnd.ms-office` / `CDFV2` types are now
listed alongside the specific one) because it cannot pin a file against it.
**Pinning a mapping is not as good as pinning a file, and saying so is the
point.**

> **THE RULE: an allowlist that has never rejected anything has also never been
> tested. Turning on a dead check is a behaviour change on every path that
> called it — and the paths that called it "properly" for years change most.**
> This is the exact inverse of v3.19.6's lesson. There, a general mechanism was
> never pointed at the general population. Here, a specific mapping was never
> measured against the world it claims to describe.

## 🟠 2 — the test-isolation fix reached outside the test process

v3.19.7's `TEST_RUNNER` clears every cache alias before every test, which is the
right fix for the partitioning problem and is argued well. What it does not
constrain is **which** cache. `settings.py` picks the backend from the
environment, not from whether a test is running:

```python
if REDIS_URL and not DEBUG:
    CACHES = {'default': {'BACKEND': 'django_redis.cache.RedisCache', …}}
    SESSION_ENGINE = 'django.contrib.sessions.backends.cache'
    SESSION_CACHE_ALIAS = 'default'
```

**That alias is the session store.** The `if 'test' in sys.argv` block two hundred
lines below sets Celery to eager and says nothing about `CACHES`. So
`manage.py test` on the production host — with the production `.env` loaded,
which is the normal way anyone would run it there — clears live Redis 1,277 times
and signs out every logged-in member of the chapter.

The hazard predates v3.19.7: several modules call `cache.clear()` in `setUp`. But
it was bounded to those modules and visible in them. **Making it universal made
it silent, and inherited by every test written from now on.**

Fixed in two halves that check each other:

1. **`settings.py` forces LocMem + DB sessions** under `manage.py test`. The
   stronger half — it also stops a test run *reading* production cache state,
   which is a correctness problem before it is a safety one.
2. **`_assert_caches_are_disposable()` refuses to start** against any backend
   that is not LocMem or Dummy, with a message naming the alias and saying what
   to do instead.

(2) is not redundant: the settings' test probe is
`'test' in sys.argv or os.getenv('PYTEST_CURRENT_TEST')`, and
`PYTEST_CURRENT_TEST` is set during test *execution*, after settings import — so
under pytest the forcing never fires and only the runner's check stands between
the suite and Redis.

⚠️ **The check is a separate early assertion and deliberately NOT raised from
inside `_clear_all_caches`**, whose `except Exception: pass` exists for good
reasons and would swallow it. *A guard that swallows exceptions reports the
absence of a signal as the absence of a problem* — CLAUDE.md records that failure
three times in one month — **so the thing that must not be swallowed cannot live
inside the thing that swallows.** It also fires once per run, not once per test:
a guard that fires 1,313 times is a guard someone silences.

New `src/test_cache_isolation_guard.py` (6 tests), including the control that
LocMem is accepted, that a **non-default** alias is refused too (`_clear_all_caches`
iterates every alias, and the alias most likely to be added later is the one
named for sessions), and an assertion that the running suite is itself on a
disposable cache.

> **Test isolation that reaches outside the test process is not isolation.** The
> runner was right that the cache is shared state; the same sentence is true of
> the cache one environment over.

## 🟡 3 — the inline allowlist protected the smaller surface

v3.19.7 decided what an uploaded file is allowed to become when a member opens
it, built `INLINE_SAFE_CONTENT_TYPES`, argued the `image/svg+xml` exclusion
correctly — and applied it to `serve_private_upload` only. `serve_media` kept
`as_attachment=False` for every content type, as it had since v3.14.1.

**`serve_media` is the larger surface by every measure that matters:** ten public
prefixes (`legislation_docs`, `committee_minutes`, `committee_documents`,
`committee_legislation`, `document_versions`, `profile_pictures`, `songbook`,
`landing_photos`, `passed_resolutions`, `og_images`), audience **every logged-in
member in the chapter**, where the private views answer a committee of four.

CLAUDE.md's *"a rule stated correctly, a helper written to enforce it, then
something left outside the helper"* is now **seven releases deep**, and this is
the first time the thing left outside was the **bigger half**. The fix went where
the attention was rather than where the surface was.

⚠️ **IT WAS NEVER EXPLOITABLE, AND THAT IS THE INTERESTING PART.**
`_reject_browser_executable` refuses to store a `.html`/`.svg`/`.js` from any
writer including the public prefixes, and a `find` over `media/` and
`exportable_media/` returns **zero** such files. So the protection was real and
**incidental** — supplied by a blocklist of extensions somebody thought of, one
layer down, rather than by a decision about what this response renders.

> **A blocklist protects you from the files you named. An allowlist protects the
> response.** Both layers stay.

New `src/utils/content_disposition.py` holds the set, `should_download()` and
`apply_disposition()`; both views import it. New
`src/test_upload_serving_disposition.py` (13 tests) asserts mostly the
**property** — `test_the_two_upload_views_share_one_rule` fails if either module
re-declares the set locally, which is exactly how this happened — plus the
behaviour at the route, with a control that a PDF still renders inline (a guard
that attached everything would pass every other assertion and break every
document preview in the application).

Two details worth keeping:

- **The `.html` and `.svg` fixtures are written straight to disk, bypassing
  storage, on purpose.** `_reject_browser_executable` would refuse them through
  the normal write path, and the question is what happens to a file that is
  nonetheless present — a pre-v3.19.7 upload, a restored backup, a file placed by
  hand. Testing only what the blocklist lets through would test the blocklist.
- **`apply_disposition` is called in BOTH branches of `serve_media`.** Under
  X-Accel nginx streams the body and Django supplies only headers, so that branch
  is the only place the disposition can be set at all — and it is the branch
  developers never run locally, i.e. the one that would have looked correct
  forever under the `else`.

**Audio is deliberately not in the set and the songbook still works.** `<audio>`
and `<img>` load sources as *subresources*, and `Content-Disposition` is ignored
for subresource loads; `serve_song_audio` is a separate view with its own route
and `songbook_detail.html` points at `{% url 'song_audio' %}`, not at
`/media/songbook/`.

## 🟡 4 — `src.W003` works, and nothing ran it

`v3.19.7.md` went into `de0aeea` still reading `**Committed & pushed:** *not
yet*`, and its `DEPLOYED.md` row still said *not committed*. **Sixth release
running**, and the first one the check caught *after the fact* — it reported both
halves correctly on the 08-13 auto-run's `manage.py check`, two days after the
commit, to nobody.

Both lines are corrected. But the correction is the small half.

v3.19.7 built the check on exactly the right argument — *no amount of care at
authoring time can fix a line whose value does not exist until after the writing
is over*, so the response has to run **after** the commit — and then left the
running to `manage.py check`, which prints warnings and exits 0.

**`manage.py preflight` already gates deploys and cron** (v3.15.8, exits 1,
`--strict`, `--email-on-fail`). So the fix is not a new gate; it is one more
check inside the one that exists. New `check_system_checks()` runs Django's
system checks and promotes `src.W002` (Kai schema looks unmigrated) and
`src.W003` to **errors**, because both are release-integrity facts rather than
style advice. Every other warning stays a warning — promoting all of them would
make preflight noisy, and a preflight nobody reads is the failure mode it was
built to avoid.

Verified by negative control rather than asserted: with the ledger line
reverted, `preflight` goes from `39 passed / 4 failed` to `38 passed / 5 failed`
with `✗ System check src.W003`; restored, it returns to `✓ System checks`.
5 new tests in `src/test_ledger_check.py` pin the promotion, including the
control that an ordinary warning stays a warning.

> **A guard needs a trigger it does not have to be remembered.**

## 🟡 5 — a failure in `test_hardcoded_urls` was reported as a pickling error, and I could not reproduce it

Recorded because it is unresolved, not because it is fixed.

While verifying this batch, the full suite under `--parallel` died with

```
TypeError: cannot pickle 'traceback' object
```

**and no `FAIL:` line, no module name, no test name.** Running the same tree with
`--parallel=1` showed the real result immediately: one failure in
`test_hardcoded_urls.test_every_hardcoded_path_resolves` — this release's own new
tests, correctly caught (see below). The failure is now fixed and both
partitionings are green.

⚠️ **A minimal reproduction did not reproduce it.** A scratch test failing on
`assertEqual(['a'], [])` pickles fine under `--parallel=4`, and so does the
`test_hardcoded_urls` failure when that module is run **on its own**. So the
mechanism is something about the full-suite parallel run and I have not
established what. Adding `raise ... from None` in `_validate_zip_container`
(§1) removes one real way to produce an unpicklable failure and did **not** by
itself clear this one.

**The practical rule until someone does establish it: `TypeError: cannot pickle
'traceback' object` is not a result. Re-run with `--parallel=1` before concluding
anything.** CI runs in parallel, which means there is a class of failure the
suite currently cannot report — and given this codebase's history with guards
that appear to run and do not, that is worth a proper look rather than the
guess I would otherwise be writing here.

### The failure it was hiding, which the guard was right about

`test_hardcoded_urls` flagged three strings in this release's new tests:
`/protected-media`, `/protected-media/legislation_docs/notice.html` and
`/main.xml`. All three are genuinely **not site paths** — the first two are the
nginx *internal* location (`MEDIA_ACCEL_PREFIX`), which by definition Django
cannot resolve, and the third is a zip entry name inside a synthesised OOXML
package. Added to `_NOT_SITE_PATHS` with reasons, under the module's own standing
caveat: **the exemption list is for strings that are not site paths, not for site
paths that are wrong.**
