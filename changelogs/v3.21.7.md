## 1 — 🟠 `get_client_ip` returned attacker-chosen strings, and nine of ten writers were never enumerated

### What v3.21.6 got right

`ActivityLog.log_activity` was writing the `'unknown'` sentinel into an `inet`
column. v3.21.6 fixed it **at the point of storage**, explicitly rejecting the
one-call-site fix, with this reasoning in the code:

> *It is fixed here rather than at the one call site that hit it, because this is
> the only method that writes this column and a call site is exactly what gets
> left out.*

That is right, and the release also built the reusable helper — `ip_or_none`,
which validates through `django.core.validators.validate_ipv46_address` so it
cannot drift from what the column accepts. Good tool, correct instinct.

### What was left outside it

**There are ten `GenericIPAddressField` columns and v3.21.6 normalised the
writer of one.** `HoneypotAccess`, `LoginLockout`, `QuarantinedAccount`,
`CSPViolation`, `SecurityNotificationLog`, `APIAccessLog`, `AdminActionLog`,
`SlatingActivity` and `UserSession` were untouched.

And the release's own enumeration test could not see that, because it enumerates
the wrong set. `TheSentinelIsInvalidForEveryInetColumnTests` walks
`apps.get_models()` — which looks exactly like the enumeration CLAUDE.md demands,
and its docstring cites that rule by name — and then asserts:

```python
field.clean(MISSING_IP_SENTINEL, model())   # must raise ValidationError
```

That is a property of `django.db.models.GenericIPAddressField`. It is true in
every Django project ever written. It was true before v3.21.6, it is true now,
and it will still be true after any future regression in this code.

> ⚠️ **A WALK THAT CANNOT FAIL IS NOT AN ENUMERATION.** Before trusting one, ask
> what would have to be true for it to go red. If the answer is *"Django would
> have to change"*, it is measuring the framework, not the codebase.
>
> The population that mattered was never the **columns**. It was the **writers**.

### The measured part

`get_client_ip` returned whatever arrived in the header, verbatim. Under
`BEHIND_CLOUDFLARE=True` with `CLOUDFLARE_VERIFY_ORIGIN=False` — **the shipped
default**, and v3.19.3 introduced that setting precisely because the origin *is*
directly reachable — a request carrying

```
CF-Connecting-IP: '; DROP--
```

made `get_client_ip` return `"'; DROP--"`. Measured, not reasoned about. That
string was then written into `HoneypotAccess.ip_address` (`inet`, **NOT NULL**)
and `IPBlacklist.ip_address`, and used to build four cache keys.

`HoneypotAccess.ip_address` accepting a non-address is the v3.21.6 bug exactly,
in the next model over, on a path unauthenticated scanners reach **by design**.

### The fix

`get_client_ip` now returns **an address or `None`, and nothing else** — one
gate, at the single source v3.18.8 consolidated every consumer onto and that
`test_client_ip_single_source.py` already fences. That covers all ten columns,
the four cache keys, and writers nobody has written yet, which is the difference
between fixing a population and fixing a list.

A junk `CF-Connecting-IP` now **falls through to the socket peer** rather than
beating it. Note the `if`→`elif` on the forged-header branch below it: while the
first branch always returned, the two were equivalent; now that it can fall
through, a *trusted-but-unparseable* header must not be reported as a *forged*
one.

⚠️ **No new log line, on purpose.** This condition is attacker-triggerable at
zero cost, and v3.19.4 already had to retrofit a per-peer throttle onto
`_log_forged_cf_header` because an unthrottled one could roll a file shared with
every other security event. Where verification is ON, the existing branch
already reports the thing that matters (the origin being directly reachable);
where it is OFF, the deployment has declared it trusts this header and the
documented remedy is a firewall rule. A second attacker-triggerable log line is
the larger of the two blind spots.

⚠️ **NAMED RESIDUAL — narrowing a hole is not closing it.** A forged header that
*is* a well-formed address still wins, and still lets a direct-to-origin client
choose its own login rate-limit bucket. That is the firewall problem v3.19.3
documented and dispositioned; nothing here changes it, and the new module's
docstring says so rather than letting a later reader infer otherwise.

### Second layer — the honeypot must not be able to 500

`HoneypotAccess.objects.create()` was **the only unwrapped database call** in a
function scanners are meant to reach. Every other DB access there is already
wrapped — the blacklist check above it, the `IPBlacklist` write below it, the geo
save in `lookup_geo` — and this one sat **above the three lines that perform the
ban**.

That is the wrong way round twice over. A honeypot that raises returns a 500
where it promised a plausible fake, which is a **distinguishing** response: it
tells the scanner the path is real. And it does so while skipping the ban.

> **Recording the hit is the optional half. Banning is the point.**

Now wrapped and logged, with the geo thread guarded on the row existing. This is
the layer that does not depend on having enumerated the callers correctly — which,
on the evidence of the last two days, is the layer worth having.

**Files:** `src/utils/security_utils.py`, `src/view/honeypot.py`.
**New:** `src/test_client_ip_is_always_an_address.py` (11 tests; 6 of 11 methods
fail against `d7f925f`, 28 subtest failures + 1 error, the other 5 are controls
that must pass on both trees).

## 2 — 🟠 The quiz anonymity threshold counted a population the page does not show

### What v3.21.5 got right

Yesterday's run found that the pledge-facing quiz breakdown with a single
submission was that pledge's exact score and right/wrong pattern, printed under
a header reading *"These are class totals. Nobody's individual answers are shown
here."* It added a minimum of 3, in the **context builder rather than the
template**, on the explicit reasoning that a template `{% if %}` protects only
the page it is written on. All correct.

### What it counted

```python
submissions = completions.count()      # PledgeTaskCompletion
```

**A completion is not a submission.** `education_toggle_completion` calls
`get_or_create`, so a chair marking somebody `waived` or `incomplete` on the grid
mints a row with no answers behind it.

Reproduced on `d7f925f` — one pledge sits a quiz, the chair marks two others:

```
submissions = 3 | withheld = False
   Q1  answered=1  correct=1  wrong=0  pct=100
   Q2  answered=1  correct=0  wrong=1  pct=0
score_count = 1   low/high/avg = 4 4 4.0
```

That is the disclosure the threshold exists to prevent, one day after it
shipped, reached by an **ordinary chair action** rather than by an attack.

> ⚠️ **A THRESHOLD PROTECTS THE POPULATION IT COUNTS.** The number gating the
> page came from `PledgeTaskCompletion`. Every number *on* the page is drawn
> from `PledgeQuizAnswer` (per question) or from `PledgeTaskCompletion.score`
> (the score band). Three populations, and the gate was on the one that is
> easiest to inflate and hardest to look at.
>
> Before trusting a minimum: ask what it counts, ask what the page prints, and
> check they are the same set.

This is a near relative of two shapes already recorded — v3.20.0's *"N pledges
marked" counted rows rather than marks*, and v3.16.2's *ask what the redacted
view can be joined against* — and is neither. Nothing is joined here and nothing
is miscounted for display. The protection was simply attached to a different set
from the one it protects.

### The fix

Each statistic is gated by **its own** population:

* `submissions` now counts distinct pledges with an answer to this task.
* Each row is suppressed when **that question's** answer count is under the
  minimum. Questions are not answered equally often — v3.20.0 records that a
  chair may add a question to a quiz people have already sat, and it then
  carries only the answers given since. A page-level count of 12 says nothing
  about the question three people have seen.
* The score band is withheld when fewer than the minimum are scored.
  `score_low`/`score_high` over one scored completion are one pledge's mark
  printed under two labels, with `score_average` as a third.

`suppressed` is defaulted to `False` **in the row builder**, not only where it is
set — a template resolving a missing key to `''` is how the v3.16.2-era feature
flags failed closed and invisibly, and that is a mistake worth not repeating in
a smaller place.

⚠️ **Educators are unaffected, deliberately.** All three gates sit inside
`elif viewer_is_pledge`. A chair grading the quiz is entitled to every number,
including one submission's, and the new controls pin that: a suppression that
quietly spread into the grading workflow would be a regression wearing a fix's
clothes.

**Files:** `src/view/committee/education.py`,
`templates/committee/_quiz_analysis_body.html`.
**New:** `src/test_quiz_analysis_populations.py` (5 tests; 3 fail on `d7f925f`,
2 more error there only because they assert the new `suppressed` key).

## 3 — 🟠 The schema could not say "no address", so every writer invented one

*Second pass. This is the item the first pass deliberately left for Mason; he
asked for it fixed.*

Finding 1 stopped `get_client_ip` returning a non-address. It could not finish
the job, because three of the ten columns were `NOT NULL`:

```
HoneypotAccess.ip_address        inet NOT NULL
LoginLockout.ip_address          inet NOT NULL
QuarantinedAccount.ip_address    inet NOT NULL
```

`None` into a `NOT NULL` column is an `IntegrityError`. That is the same failure
with a different exception class, and **moving a failure is not fixing it.**

> **A column that stores a client's address must be able to say it does not have
> one.** A schema that cannot express "unknown" forces every writer to invent a
> value, and an invented value in a typed column is wrong data. That is the
> whole causal chain here, from v3.21.6's 50 CI errors down to this release.

**Migration `0020` makes all three nullable.** Chosen over the alternative — a
second reserved sentinel such as RFC 5737 `192.0.2.0`, which is valid `inet` and
never routable — because these three tables are read *during incidents*, by
people who will not have read the comment explaining the convention, and a
sentinel that looks like an address gets read as one. `NULL` is the one value
every reader already has to think about.

⚠️ **`0020` is safe on a live database, and "AlterField" alone is not a reason
to believe that.** The three inet changes are `NOT NULL → NULL`, which is a
widening: no existing row can violate it, nothing is rewritten, no backfill.
The `IPBlacklist` change is metadata only. Verified forward → `migrate src 0019`
→ forward.

⚠️ **The rows are worth writing without an address.** A lockout with none is a
*username* lockout (`source='middleware_user'`), where the address was always
incidental — and before this change every writer wrapped the insert in
`except Exception: pass`, so the row was silently dropped and the admin console
showed nothing at all. **A row with a NULL address is strictly more than no
row.**

`QuarantinedAccount.quarantine_user` normalises its argument, because it is the
model's single entry point and both callers hand it
`get_client_ip(...) or 'unknown'`. The three `LoginLockout` writers normalise at
the write, there being no such entry point to put it behind.

**New:** `src/test_null_ip_columns.py` — and note what its enumeration asserts.
v3.21.6's walk asserts a `GenericIPAddressField` rejects `'unknown'`, which is
Django. `test_every_inet_column_can_store_no_address` walks the same models and
asserts `field.null`, which is **this schema** — it goes red the day someone adds
a `NOT NULL` inet column, i.e. at the structural precondition for the next
instance of this bug. That is what the difference looks like in practice.

## 4 — 🟡 Widening a column is one line; the readers pay for it

Three readers took the value straight into another `NOT NULL` column and would
have raised on the first NULL row:

* **Bulk-blacklist every honeypot IP** — `values_list('ip_address')` now yields
  `None`, and the loop writes each into `IPBlacklist` (still `NOT NULL`). It
  would have raised **partway through**, after creating some entries.
* **Lockout → blacklist** and **lockout → whitelist**. The second is the worse
  one: it is what an admin clicks when a member is locked out and needs to get
  back in, and the `IntegrityError` would have fired *before*
  `clear_lockouts_for` ran — so the member stays locked out and the admin gets a
  500 while trying to help him.

All three now say so plainly instead. There is genuinely nothing to add: both
lists match by exact equality on an address we do not have.

Also 🟡 **the blacklist gate in `InputSanitizationMiddleware` skips the query
when there is no address.** It was querying for the sentinel on the hot path of
every such request — harmless against a `CharField`, and the single thing
standing between this codebase and converting that column to `inet`, because the
same query against `inet` raises rather than returning empty. **A read is as
much a party to the type contract as a write is.**

## 5 — 🟡 `IPBlacklist` promised CIDR support that has never existed

`help_text` read *"IP address or **CIDR range** to block"*. Every consumer
matches with `filter(ip_address=<the client's address>)` — exact string
equality — so `10.0.0.0/8` is an entry that can never equal any client address.

**An admin who entered a range got a ban that silently protected nobody**, and
the list then reads as coverage. Fifth instance of the false-comment category
CLAUDE.md tracks, and the first where the false statement was in a `help_text`
a human reads *while typing into the field it describes*.

Corrected, plus `validators=[validate_ipv46_address]` so the admin form rejects
both ranges and junk. ⚠️ Validators do **not** run on `objects.create()` — this
is a guard on the human path; the code path is covered by finding 1.

⚠️ **The column is deliberately NOT converted to `GenericIPAddressField`, and
that is a decision.** The conversion is
`ALTER COLUMN ... TYPE inet USING ip_address::inet`, which **hard-fails
mid-deploy** on any row PostgreSQL cannot cast — and the entire point of finding
1 is that we know such rows could have been written. Nobody knows what
production holds. `manage.py preflight` now counts them and says which of the
two things to do; convert once it reports zero.

## What the review did NOT change, and why

* **The forged-header hole is narrowed, not closed.** A `CF-Connecting-IP` that
  *is* a well-formed address still wins, and still lets a direct-to-origin
  client pick its own login rate-limit bucket. The fix is a firewall rule;
  v3.19.3 documented it and dispositioned it, and nothing here changes that.
* **`IPBlacklist.ip_address` stays a `CharField` this release** — see §5. It is
  a one-line migration the day `preflight` reports zero non-address rows.
* 🟡 **`is_ip_honeypot_banned()` in `src/view/honeypot.py` has no callers.** Not
  touched: deleting it is a judgement about whether it is a landmine or a
  utility somebody meant to wire up, and it is the sort of thing that should be
  a deliberate line in a diff rather than a drive-by.
* `pledge_may_see_task`, `pledge_request_absence`'s deliberately un-narrowed
  lookup, the shallow-clone guard in `checks_ledger.py`, and `ip_or_none`
  itself were all read closely and are sound. The quiz threshold's placement in
  the context builder is right; only the number it read was wrong.

  `test_hardcoded_urls` failed the build on `'/a/'` and `'/b/'` — fixture values
