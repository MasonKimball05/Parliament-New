# v3.12.0 — Scheduled Notification Execution, Email Retry Dedup & Admin Polish

**Type:** Feature / Bug Fix / Performance
**Status:** WIP — not yet committed or deployed

---

## Overview

Completes the `NotificationSchedule` feature introduced in v3.11.x. The model and full officer CRUD UI (create, edit, toggle, delete, log viewer) were already shipped; this release adds the missing execution layer — a Celery task that reads active schedules every 15 minutes and fires email and/or in-app notifications when events fall into the send window.

Also includes a retry-deduplication guard for `send_event_signup_announcements`, an mtime-keyed cache key for the URL explorer, and polish on the notification admin UI.

---

## New Features

### 1. `fire_scheduled_notifications` — Scheduled Notification Execution Task

New Celery task registered every 15 minutes (`setup_celery_schedules.py`). Implements the full execution loop for active `NotificationSchedule` records.

**Trigger types supported:**
- `event_reminder` — fires for any upcoming event once `now >= event.date_time - hours_before`
- `attendance_reminder` — same, restricted to events with `requires_attendance=True`
- `vote_reminder` — fires for active legislation with `voting_ends_at` set once `now >= voting_ends_at - hours_before`; automatically filtered to members who haven't voted yet (no reminder sent if all eligible recipients have already voted)
- `dues_reminder` / `custom` — logged and skipped; no data model yet

**`send_at_time` gate:** If `NotificationSchedule.send_at_time` is set, the schedule is only fired within an ±8-minute window of that local time of day. Midnight-crossing handled via modular minute-of-day arithmetic. Ensures officers who configure a specific send time (e.g. 8:00 AM) don't see emails arrive at 2:30 AM on a background tick.

**Recipient resolution** by `target_audience`: `all_active`, `all_members`, `officers`, `pledges`, `committee` (respects `target_committee` FK). Unknown audiences log a warning and skip.

**Template rendering:** `message_template` and `email_subject_template` support placeholders rendered per object type. Malformed or unknown placeholders fall back to the raw string (no crash).
- Event/attendance reminders: `{event_name}`, `{event_date}`, `{event_time}`, `{event_location}`
- Vote reminders: `{legislation_title}`, `{vote_deadline}`, `{vote_deadline_date}`, `{vote_deadline_time}`

**Deduplication:** DB-backed — `NotificationLog.filter(schedule, related_object_type='event', related_object_id, status='sent')`. All sent `(schedule_id, event_pk)` pairs are pre-fetched in a single query before the loop (not per-event EXISTS queries) and checked via in-memory set lookup.

**Delivery:**
- `send_email=True` → `send_mass_mail()` over `DEFAULT_FROM_EMAIL`
- `send_in_app=True` → `Notification.objects.bulk_create()` + `cache.delete_many()` to invalidate notification bell counts

**Lifecycle logging:** A `NotificationLog(status='pending')` entry is created before delivery. On completion it is updated to `'sent'` (with `sent_at`) or `'failed'` (with `error_message[:500]`).

**Files:** `src/tasks/notifications.py`, `src/management/commands/setup_celery_schedules.py`

## Bug Fixes & Hardening

### 2. `send_event_signup_announcements` — Retry Deduplication

`send_mass_mail` sends all recipients over a single SMTP connection — if the connection drops mid-batch, Django's SMTP backend has already delivered some messages but has no way to report which ones. Without dedup, the next Celery tick would re-send to the entire recipient list, including those who already received the announcement.

A cache key `signup_ann_sent_{event.pk}` (TTL: 24h) now tracks the set of addresses attempted in any partial run. On retry, those addresses are excluded before building the datatuple. If all recipients are already covered, the event is marked done and the key deleted.

**Cache-down behaviour:** if Redis is unavailable, `cache.get` returns `None` → dedup is skipped → a retry re-sends. Acceptable — can't guarantee dedup without storage. The conservative choice (all *attempted* addresses treated as sent, not just confirmed) prevents the more common duplicate scenario.

**Files:** `src/tasks/notifications.py`

### 2a. Settings Hardening — `base_settings.py` (07-05-26)

Removed the literal `'fallback-secret'` SECRET_KEY default and `ALLOWED_HOSTS = ['*']`. Now mirrors the `settings_postgres.py` pattern: `SECRET_KEY` from env (`DJANGO_SECRET_KEY`, falling back to legacy `DJANGO_SECRET_KEY_GENERAL`) with a DEBUG-only dev fallback and a hard `ValueError` in production; `ALLOWED_HOSTS` env-driven with `localhost,127.0.0.1` default. Not exploitable as deployed (prod uses `settings_postgres`), but removes the one-wrong-`DJANGO_SETTINGS_MODULE` foot-gun. The unused `SECRET_KEY_GENERAL` name is gone — nothing referenced it.

**Files:** `Parliament/base_settings.py` *(submodule — won't ride along with an outer-repo push)*

### 2b. Dead `SECURE_BROWSER_XSS_FILTER` Removed (07-05-26)

`SECURE_BROWSER_XSS_FILTER` was removed from Django in 3.0; on Django 5.1 the line in `settings_postgres.py` was inert config. Deleted, with an explanatory comment left in place. `FIXES_APPLIED.md` §1.4 corrected to match (the middleware's `X-XSS-Protection: 0` header is the complete fix).

**Files:** `Parliament/settings_postgres.py` *(submodule)*, `FIXES_APPLIED.md`

### 2c. DOCX Preview — `target` Attribute Dropped from Link Allowlist (07-05-26)

`_DOCX_ALLOWED_ATTRS` permitted `<a target>` without forcing `rel="noopener"`, enabling reverse tabnabbing from a malicious .docx (`target=_blank` page gets a `window.opener` handle). `target` removed from the allowlist — bleach now strips it and links open in the same tab.

**Files:** `src/view/view_document.py`

## Performance

### 3. URL Explorer — mtime-Keyed Cache Key

Cache key changed from the static `admin_v2_url_explorer_data` to `admin_v2_url_explorer_data_{mtime}` where `mtime = int(os.path.getmtime('src/urls.py'))`. On deploy, `git pull` updates `urls.py`'s mtime; the old cache key is never looked up and the new key is populated on first hit. TTL extended from 1h to 24h — mtime rotation handles freshness so a long TTL is safe.

A single `os.stat` syscall per request (negligible for a rarely-accessed admin tool). Old keys expire naturally within 24h of a deploy.

**Files:** `src/view/admin_v2.py`

### 4. `notification_dashboard` — 4 COUNT Queries → 2 `aggregate()` Calls

`notification_dashboard` was firing 4 separate `COUNT(*)` queries (2 for schedule totals, 2 for today's log totals). Replaced with 2 `aggregate()` calls using `Count` + `Q` filter expressions. Net: 2 DB round-trips instead of 4 on every dashboard load.

**Files:** `src/view/notification_admin.py`

### 4a. Login Path — Reuse Cached Geo Lookup (07-05-26)

`log_successful_login` (signals.py) made a fresh, uncached HTTP call to ip-api.com on every login even though `run_post_auth_pipeline()` had just done a 24h-cached lookup and stashed it on `request._login_pipeline`. The handler now reuses the stashed geo (mapping geo_utils' `lat`/`lon` keys onto the `latitude`/`longitude` shape it expects) and only falls back to a direct lookup for impersonation logins, private IPs, or failed pipeline lookups. Saves one external HTTP round-trip per password/passkey login and halves pressure on ip-api.com's 45 req/min free-tier limit. Failed-login handler unchanged (never has pipeline context).

**Files:** `src/signals.py`

### 4b. `role_transitions` — N+1 Holder Queries → 1 (07-05-26)

The view ran one `ParliamentUser` query per role (~1+N for N roles). Replaced with a single M2M-join query (`filter(roles__in=roles).values(..., 'roles')`) grouped by role id in Python. Behavior identical: same holder dict shape, name-sorted per role. Officer-only page, bounded N — minor, but free while in the file.

**Files:** `src/view/officer/transitions.py`
