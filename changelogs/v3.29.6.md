## C&B resolution builder: collaborator permissions can now be edited in place

Previously the only way to change a collaborator's role (viewer ↔ editor) on
`resolution_detail.html` was to remove them and re-add them with the new
role — losing no data, but clumsy, and easy to fumble on a resolution with
several collaborators. The backend already supported this: `add_collaborator`
has always done a `get_or_create` and updated the role on an existing row
rather than erroring on a duplicate. So this is template-only — each
collaborator row now has an inline role `<select>` (pre-selected to their
current role) plus a Save button, posting to the same
`cnb_add_collaborator` endpoint, alongside the existing Remove form. Gated
behind the same `is_cnb` check that already gates the Remove form; a
non-CNB viewer still sees the role as plain text.

## Profile: role history entries can now be edited, not just deleted and re-added

`RoleHistory` entries (role name, start/end semester) previously supported
add and delete only — fixing a typo meant deleting the entry and losing its
position in the list to re-add it at the bottom. Added a `role_history_edit`
POST branch to `profile_view.py`, scoped to `RoleHistory.objects.filter(id=rh_id,
user=user)` (the same ownership scoping the existing delete branch uses,
so a member can only ever edit their own entries) and an inline edit form on
`profile.html` — clicking the new pencil icon swaps the display row for
three inputs (role name, start semester, end semester) and a Save/Cancel
pair, submitted via the existing `postAjax` helper the rest of the profile
page's inline editors already use.

## Pledges no longer show a false "initiated at" badge

Mason: "make sure that pledges do not get the initiated at badge
automatically. That gets added to them once their member type changes from
pledge to member/officer/chair."

`initiation_chapters` is a self-reported `JSONField` with no server-side
default anywhere (confirmed via the shared `profile_card_json` API, which
every consumer below fetches from — it returns the raw list, empty or not,
never injecting a default itself). The bug was entirely client-side: the
"Initiated at" popup row on `directory.html`, `house_map.html`, and
`chat/channel.html`, plus the equivalent note on `profile.html`'s own
Initiation Chapters section, all defaulted an *empty* list to
`Alpha Mu — Samford University` unconditionally. Correct for the overwhelming
majority of members (who really are Alpha Mu by definition, so requiring
them to type it in would be pure friction) — wrong for a pledge, who by
definition hasn't been initiated into anything yet and has nothing to
report, but got "Initiated at: Alpha Mu (ΑΜ) — Samford University" displayed
as though it were already true.

Fixed by branching the default on member type rather than removing it:
`d.member_type === 'Pledge'` client-side in all three popup templates
(empty array instead of the Alpha Mu fallback when true), and
`user.is_pledge` server-side in `profile.html` (a pledge sees "You haven't
been initiated yet, so this section defaults to empty..." instead of the
"Defaults to Alpha Mu..." text, and the "Defaulting to Alpha Mu — Samford
University." filler line under the empty-list fallback is likewise gated to
non-pledges only). The badge still appears the moment a pledge is initiated
and their `member_type` changes — nothing about the initiation flow itself
needed to change, only the display default for members who haven't reached
it yet.
