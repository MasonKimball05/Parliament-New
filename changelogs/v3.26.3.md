add more logging to be able to try and tell what the issue is coming from
other than this general csrf issue on this page?"* Fair complaint — the only

bare reason string ("CSRF token missing."), which is what every line in the

had to be guessed at.

## What changed

`CSRF_FAILURE_VIEW` now points at `src.view.csrf_failure.csrf_failure`
instead of Django's default. It logs one structured line to the `security`
logger (matching this codebase's existing style — `csp_report.py`'s
`"CSP violation | IP=%s | ..."`) and then renders this app's own styled 403
page via the existing `_render_403` helper, rather than Django's generic
default template.

Logged, per failure: Django's own `reason` string; `path`/`method`; whether
the `csrftoken` cookie was present at all (`has_csrf_cookie`) and whether
`sessionid` was (`has_session_cookie`) — both `False` points at cookies
being dropped/blocked wholesale, a different and more general problem than a
CSRF-specific one; whether a token was actually submitted
(`posted_token_present`) — this being `True` on a "token missing" failure
would itself be a contradiction worth flagging; `Referer` and `Origin`;
`CF-Ray` (Cloudflare stamps every request it proxies with this — its
absence on a request that should have come through Cloudflare is the same
class of signal as the `144.126.251.9` direct-origin noise from the same log
dump, now checkable per-failure instead of only by IP-pattern-matching);
`Sec-Fetch-Site`; a truncated `User-Agent` (mobile Safari's bfcache being the
documented repeat offender — see `_render_403`'s existing comment); the
client IP via the same `get_client_ip` this app uses everywhere else; and,
if somehow authenticated, which member.

**⚠️ Deliberately never logged: the actual CSRF token or cookie value**, from
either the request or the session — only presence/absence and metadata. A
diagnostic log is itself an asset; logging the secret it exists to protect
would defeat the point.

## Verification

11 new tests (`src/tests/security/test_csrf_failure_diagnostics.py`), using
`Client(enforce_csrf_checks=True)` — the test Client bypasses CSRF entirely
by default, which would have made every test here a false pass. Covers: the
exact reason string differs by scenario and each is captured correctly (no
cookie at all → "CSRF cookie not set.", cookie present but no token
submitted → the literal "CSRF token missing." Mason's log showed, cookie
present with a wrong-value token → "CSRF token from POST incorrect."); the
app's own 403 page renders, not Django's; the response is still `no-store`;
missing headers log as a literal `-`, not a blank; an authenticated user is
identified; and — the test that matters most given what this view is for —
a real CSRF cookie value and a deliberately suspicious token string are both
confirmed **absent** from the log line. `manage.py check` clean. Targeted
run alongside the modules touched in v3.26.2 — 206 tests, 0 failures.
Bandit — 0 MEDIUM+. Full suite not run against this specific commit due to
sandbox contention this session (same caveat as v3.26.2 — **run it before
deploying**).

## What this does and doesn't tell you

This makes the NEXT occurrence diagnosable — it doesn't retroactively
explain the ones already in Mason's pasted log, which predate this view.
Once this is deployed and it happens again, the `security` logger will have
exactly the fields needed to tell "stale bfcache" from "Cloudflare cache
poisoning" from "cookies blocked" from "direct-origin bypass" apart, instead
of one sentence that's consistent with all four.
