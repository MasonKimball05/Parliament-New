# v2.15.0 - User Watch Flag

**Release Date:** May 23, 2026

**Deployment Status:** Deployed — May 23, 2026

**Type:** Feature / Security

---

## Overview

Admins can now place a hidden watch flag on any user from the Admin-v2 Login Security page. When active, any successful login or repeated failed login attempts for that user immediately trigger an alert email to the site administrator and create a `LoginAlert` record for audit purposes.

The flagged user sees nothing — the flag is invisible to them.

---

## What Changed

### `UserWatchFlag` Model

New model in `src/models.py`:

| Field | Type | Notes |
|---|---|---|
| `user` | OneToOneField → ParliamentUser | The user being watched |
| `reason` | TextField | Required — why the flag was placed |
| `notes` | TextField (blank) | Optional admin notes |
| `is_active` | BooleanField | Can pause alerts without removing the flag |
| `created_by` | FK → ParliamentUser | Admin who placed it |
| `created_at` / `updated_at` | DateTimeField | Auto-managed |

### Alert Triggers (`src/view/login_view.py`)

**Successful login** — if the user has an active watch flag, fires immediately after the geo check and `LoginHistory` record are created, so the alert has full context (location, risk level, etc.).

**Repeated failed logins** — triggers when ≥2 failed attempts in the current rate-limit window match a watched user's username. Performs a geo lookup at trigger time since no geo data is available on failed attempts.

Both paths are wrapped in `try/except` — a notification failure never interrupts the login flow.

### `send_watch_flag_alert` (`src/security_notifications.py`)

New function that:
- Creates a `LoginAlert` record (type `other`, severity based on event — `high` for failed, risk-level-based for success)
- Sends an HTML email to `SECURITY_ALERT_EMAIL` using `EmailMultiAlternatives`
- Uses `UserSession.parse_user_agent()` to extract browser, OS, and device type from the raw user agent string

### Email Template (`templates/emails/watch_flag_alert.html`)

Rich HTML email containing:
- Trigger label and timestamp
- Watch reason callout
- User info (name, username, ID, type, status)
- Location & IP (city/region/country, ISP, coordinates, whitelist/blacklist/rate-limit status)
- Device & browser (user agent, parsed browser, OS, device type)
- Risk assessment (level, non-US flag, risk factors)
- Direct link to the user's Login Security page in admin-v2

### Admin-v2 UI (`templates/admin_v2/user_login_security.html`)

New **Watch Flag** panel on the Login Security page, between the User Information card and the Statistics dashboard:

- **Not set**: Shows a "+ Watch User" button that expands an inline form (reason + notes)
- **Active**: Shows reason, notes, set-by, set-on; buttons to Pause, Edit, or Remove
- **Paused**: Same as active but with a "Resume Alerts" button instead of Pause

The panel border color changes with state: red (active), yellow (paused), gray (not set).

All button interactions use `addEventListener` in a nonce'd `<script>` block — no inline `onclick` handlers.

### URL

```
POST /admin-v2/users/<user_id>/watch-flag/   name='admin_v2_toggle_watch_flag'
```

Actions: `add`, `remove`, `activate`, `deactivate`. All require Admin-v2 auth and log to `ActivityLog` and `admin_actions` logger.

### `has_default_password` Field (Performance Fix)

The "Manage User" popup in the officer user list was slow because clicking it triggered up to 4 bcrypt password checks synchronously to determine if the user still had their default password.

**Fix**: Added `has_default_password = BooleanField(default=False)` to `ParliamentUser`. The field is:
- Set to `True` when a user is created or their password is reset to a default-pattern value (user creation, `reset_user_password` command, `reset_all_passwords` command)
- Set to `False` when a user changes their own password via `PasswordChangeForm`, or when an admin issues a random-password force reset via admin-v2

The bcrypt method `has_default_password()` has been renamed to `check_is_default_password()` to avoid shadowing the field — it should only be called from the one-time backfill migration.

**Migration `0160`** runs the bcrypt check once for all existing users to backfill the field. This migration will be slow on large user tables, but only runs once.

### Django Admin (`src/admin.py`)

The Django admin was significantly out of date — models added over the past several versions had no admin registration, and `ParliamentUser` was missing recently-added fields.

**New admin classes registered:**

| Model | Key features |
|---|---|
| `UserWatchFlag` | Active/paused badge, reason preview, set-by/created-at |
| `LoginLockout` | Source badge (IP vs middleware), active/expired/cleared state, read-only |
| `KaiReport` | Category, status, and deliberation color badges; all review and accused-notification fields |
| `KaiReportTemplate` | Template content fieldsets, active badge |
| `PassedResolution` | Border color, display order, visible/hidden badge |
| `ChapterMinutes` | Draft/finalized/published status badge, edit-after-publish tracking |
| `SlatingPeriod` | Full schedule date fields, voting config, GPA thresholds, status badge |
| `SlatingApplication` | GPA fields, position preferences, reviewer notes |
| `AnnouncementEmailLog` | All count fields readonly, debug console log collapsed, no manual add |
| `UserSession` | Device/browser/network fieldsets, no manual add |

**Updates to existing classes:**

- `ParliamentUser` — added `anonymous_vote`, `allow_abstain` to Member Information fieldset; added `has_default_password`, `email_flagged`, `is_quarantined` to `list_filter`
- `Announcement` — added `visible_to` and `publish_at` (new Visibility & Scheduling section); added `send_email_on_publish` and `email_sent_at` (Email Notifications section, collapsed); updated `list_display` and `list_filter`
