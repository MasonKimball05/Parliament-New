# v2.15.1 - Bug Fixes & Server Performance

**Release Date:** May 24, 2026

**Deployment Status:** Deployed — May 24, 2026

**Type:** Bug Fix / Performance

---

## Overview

Post-deployment fixes for v2.15.0, covering a CSP regression that broke interactive UI elements site-wide, a server misconfiguration causing high memory usage, and several smaller issues introduced alongside the watch flag feature.

---

## What Changed

### CSP Overhaul (`src/middleware/security.py`)

The previous nonce-based Content Security Policy (`script-src 'self' 'nonce-xxx'`) was silently breaking `onclick=`, `onchange=`, and other inline event handlers across every page on the site. Per the CSP spec, nonces only apply to `<script>` blocks — they never cover inline event handlers regardless of configuration. This caused dropdowns, modals, confirm dialogs, and action buttons to stop working in production (where CSP is enforced) while appearing fine in local development (where it is not).

**Fix:** Replaced the nonce-based approach with `'unsafe-inline'` site-wide for `script-src`. The nonce added no meaningful protection in practice since all `<script>` blocks are developer-authored. The real XSS protections remain: Django's template auto-escaping, `InputSanitizationMiddleware` attack detection, `form-action 'self'`, and `frame-ancestors 'self'`.

The `request.csp_nonce` attribute is still generated per-request (used by `admin/base_site.html`) and templates still emit `nonce="{{ request.csp_nonce }}"` on `<script>` tags — this is harmless and requires no template changes.

Affected areas included but were not limited to: the admin-v2 dashboard, security alerts, two-factor management, officer user list, edit landing page, member list, committee pages, slating, kai reports, and the base navigation template.

### Watch Flag Redirect Bug (`src/view/admin_v2.py`)

`toggle_watch_flag` was redirecting to `'user_login_security'` after every action (add, remove, activate, deactivate). This URL name does not exist — the correct name is `'admin_v2_user_login_security'`. All three redirect call sites fixed.

### Django Admin Dark Mode (`templates/admin/base_site.html`)

Django's `theme.js` was overriding the custom dark background by reading the system/browser light mode preference and setting CSS variables to light values. Fixed by forcing `document.documentElement.dataset.theme = 'dark'` in a `<script>` block in `base_site.html` after `{{ block.super }}`, which runs after `theme.js` and overrides it.

### Gunicorn `child_exit` Cache Clear Removed (`gunicorn_config.py`)

`child_exit` was calling `cache.clear()` on every worker recycle (every 500 requests). Since production uses the Redis cache session backend (`SESSION_ENGINE = django.contrib.sessions.backends.cache`), this was clearing all active sessions and logging every user out approximately every 500 requests. The `cache.clear()` call has been removed. Database connections are still closed properly on exit.

### Orphaned `parliament.service` Removed (Server)

A second systemd service (`parliament.service`) was running alongside the correct `parliament-gunicorn.service`. The old service used a hardcoded `--workers 3` command with no config file and a typo in the `Environment=` directive, meaning `DJANGO_SETTINGS_MODULE` was never set. Both services were binding to the same Unix socket, with the old service winning the race and serving all production traffic while consuming ~250MB with three unoptimized workers. The old service has been disabled and stopped — only `parliament-gunicorn.service` now runs.

### Gunicorn Configuration Tuned (`gunicorn_config.py`, `parliament-gunicorn.service`)

- Workers reduced from 2 → 1 with `threads = 2` enabled. One worker with two threads handles the same concurrency as two workers at roughly half the memory footprint — appropriate for low-concurrent-user traffic.
- `MemoryLimit` in the service file updated from 512M → 256M to reflect the new single-worker configuration.

### `UserSession` Cleanup (`src/management/commands/cleanup_sessions.py`)

`UserSession` records were never pruned, accumulating indefinitely. Two cleanup strategies added to the existing `cleanup_sessions` management command:

1. Delete records with `last_activity` older than `SESSION_COOKIE_AGE` (30 days) — if the cookie is expired, the session is gone.
2. Per-user cap of 10 most recent sessions — prevents accumulation even within the active window.

The `cache.clear()` call that previously existed in this command was also removed (same issue as the gunicorn hook — would log all users out).

A weekly cron job (Sundays at 3am) has been set up on the production server to run this command automatically.
