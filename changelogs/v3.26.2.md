**Committed & pushed:** *not yet*
**Deployed:** *not deployed*

Reported live by Mason: members getting CSRF 403s ("CSRF token missing.")
on `/login/` and on other actions (e.g. `/chapter-documents/upload/`),
seemingly at random, for multiple different people the same day. Prod logs
also showed continuous `django.security.DisallowedHost` tracebacks for Host
header `144.126.251.9` (the origin's own IP) over the same window.

## 🟠 No dynamic response carried `Cache-Control`, and this codebase has hit that exact gap twice before

Every page in this app renders `{% csrf_token %}` (it's in the shared layout
nearly everything extends), so the body of almost every response is specific
to whoever asked for it — and nothing told a browser or an intermediary not
to keep a copy around. Before this release, `add_security_headers()` in
`InputSanitizationMiddleware` only set `Cache-Control: no-store` on **403**
responses (`_render_403`, with a comment already noting *"the #1 cause of
users seeing stale 403s after successful login" is mobile bfcache*); ordinary
200s — including `/login/`'s own GET, which embeds the CSRF token every
subsequent POST is checked against — carried no cache directive at all.

This is the same failure class `test_changelog_cache.py` was written for in
v3.17.4: `@cache_page` on `changelog`/`roadmap` let one visitor's cached
response (session, name, theme) leak to another via Cloudflare, because
`Vary: Cookie` gets added too late in the response cycle to affect the cache
key. That incident's own docstring states the rule generally: **"never cache
a response whose body depends on who asked for it."** Nothing in this
release used `@cache_page` (the `test_no_view_uses_cache_page` guard is still
clean), but a login page can go stale two other ways that guard can't see:
a browser serving it back out of **bfcache** after Back/forward navigation
(the token in that cached HTML no longer matches a cookie that may have
rotated since — e.g. on a successful login in between), or an intermediary
(Cloudflare, if any Cache Rule / Page Rule matches the URL) caching the
response and handing one visitor's embedded token to another.

### Fix

`add_security_headers()` now sets `Cache-Control: no-store, no-cache,
must-revalidate, private` (plus `Pragma: no-cache`) on every response that
doesn't already set its own `Cache-Control`, with `/static/` and `/media/`
excluded (genuinely cacheable — `/media/` is access-gated by
`serve_media`'s own `@login_required`, not by this header, and in production
`/static/` is served by nginx directly and never reaches this middleware).
`no-store` is the one directive unambiguous to both audiences: it is
explicitly excluded from bfcache eligibility per the spec, and no HTTP cache
is permitted to store a `no-store` response regardless of any cache
configuration pointed at the URL.

### ⚠️ This is a defensive fix, not a confirmed root cause

I could not reproduce the CSRF failures directly (no access to the live
server, Cloudflare dashboard, or an affected member's browser) — this closes
the most likely mechanism given this codebase's own history with the exact
symptom shape, but it has not been confirmed as *the* cause. **Worth
checking to confirm, when you have a minute:**
- `curl -I https://am-parliament.org/login/` — look for `CF-Cache-Status:
  HIT`. If present, Cloudflare is caching a page it should never cache, and
  something (a Cache Rule / Page Rule / APO setting) needs to exclude it
  regardless of this fix.
- Cloudflare dashboard → Caching → Configuration / Page Rules, for anything
  matching `/login/` or applying broadly (`Cache Everything`, wildcard rules).

### On the `144.126.251.9` DisallowedHost noise

Reproduced as continuous, unrelated to the CSRF reports as far as I can tell
— a bare IP in the Host header with no session, no login, nothing but the
traceback. This matches CLAUDE.md's already-documented, already-accepted
residual gap from v3.19.3 (*"a forged header that is a well-formed address
still wins and still lets a direct-to-origin client pick its own rate-limit
bucket — the firewall problem v3.19.3 documented. Narrowing a hole is not
closing it."*) — most likely routine bot/scanner traffic hitting the origin
IP directly, bypassing Cloudflare, which Django correctly rejects via
`ALLOWED_HOSTS`. Not treated as connected to the CSRF issue without evidence
they are; flagging separately rather than folding one into the other. The
actual fix for this class of noise is a firewall rule restricting the origin
to Cloudflare's IP ranges — infrastructure, not a code change, and already
on record as open.
