## Resolution title and type are checked before saving

`create_resolution` and `edit_resolution` wrote `title` and `resolution_type`
from the POST with no check. `title` is `CharField(max_length=300)` and the
input had no `maxlength`; `resolution_type` is `CharField(max_length=20)` with
three choices. On PostgreSQL a 301-character title, or a type longer than 20,
raised `DataError` — a 500. A short unknown type (`bogus`) was saved as-is.
SQLite doesn't enforce CharField lengths, so the suite never saw it.

This was already true for the C&B Chair. v3.51.0 opens resolutions to every
brother, so it is now reachable by any member.

- New `cnb._resolution_field_error(field, value)`: title at most 300 characters,
  type one of `Resolution.TYPE_CHOICES`.
- Create: refused with a message, nothing saved.
- Edit (field-level save): the bad field is skipped with a message, the other
  changed fields still save — the same way a blank title already worked.
- `resolution_form.html`: `maxlength="300"` on the title input.

## `make stamp-ledger` refuses the multi-chapter checkout

On 10-19-26 the v3.50.2 stamp (`0e05afe`) was made in
`~/Documents/GitHub/Parliament` (on `multi-chapter`) and pushed there. `main`'s
`DEPLOYED.md` never got the v3.50.2 row, and the two branches then edited the
same lines differently — a conflict at the next main → multi-chapter merge.

`scripts/stamp_ledger.py` now stops, changes nothing and says to run it in the
main worktree when the `.multi-chapter` marker is present.
`STAMP_ON_MULTI_CHAPTER=1` overrides it for the day that branch ships.
