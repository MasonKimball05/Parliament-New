## 🟢 Live editing on the resolution edit page

**Asked (Mason, 10-02-26, during a bylaws committee meeting):** "the edit
resolution page should have a websocket so work isn't written and overwritten
by multiple people working on it at the same time."

**The problem.** Every save wrote all nine fields from whatever the browser
was holding. With two people on the page, the second save put back the first
person's *stale* copy of every field they had not touched.

**What it does now.** Three layers; each works without the one above it
(`src/cnb_live.py` has the design):

1. **A save writes only the fields you changed, and never over someone else's
   change.** The page tells the server which fields you edited and what each
   held when you loaded it. If someone else changed one of those meanwhile,
   it is not written: you get the page back with your text still in the box
   and their saved version shown above the form. Saving again replaces theirs.
   This needs no websocket.
2. **Field locks.** Click into a field and it is yours; everyone else sees it
   read-only, outlined, with "NAME is editing this". An untouched field
   unlocks when you click away; an edited one stays yours until you save.
   A lock that stops being refreshed (closed laptop, lost connection) expires
   after 75 seconds.
3. **Presence and live updates.** A bar shows who else is on the page. When
   someone saves, their changes appear in everyone else's untouched fields.
   When someone adds or removes an amendment, the others get a "save my edits
   and reload" bar.

If the socket drops, the page says so and keeps reconnecting; layer 1 still
protects every save.

**Who can connect.** `/ws/cnb/resolutions/<id>/` accepts only people who may
edit that resolution (C&B permission or an Editor collaborator), and only
while it is draft or pending — the same rule as the edit page. No text goes
client→server over the socket; saving is still a normal POST.

### Also fixed: the Save button left the page (v3.41.2)

The Save button was meant to save and stay on the edit page. In a real
browser it went to the resolution page: base.html's double-submit guard
disables the first submit button during the submit event, and a disabled
button's `name` is left out of the POST, so the server never saw `save_stay`.
The v3.41.2 tests posted the field directly and could not see this. It is now
a hidden input. Found by driving two browsers against a running server.

### Tests
- `src/tests/legislation/test_cnb_live_editing.py` (15): only changed fields
  are written; a field changed by someone else is not overwritten (409, both
  versions on the page); re-save replaces; line endings alone are not a
  change; the socket admits only editors of an open resolution; one lock
  holder per field; disconnect releases locks; a save is broadcast.
- Two real browsers against a running server (Chromium, two accounts):
  presence both ways, lock on focus, lock kept while edited, live update on
  save, field-level save, conflict page, re-save.

### Known limits
- Someone who edits a field and then leaves the page open keeps that field
  locked until they save or close the tab. There is no "take over" button.
- Locks are per browser tab, so the same person in two tabs can lock
  themselves out of a field.
- The amendment editor is not locked. Two people editing the *same section's*
  amendment at once still overwrite each other (last save wins).
