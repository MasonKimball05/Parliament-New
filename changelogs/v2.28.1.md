# v2.28.1 — Login 403 Bug Fix, Middleware Reorder & CSP Fix

**Release Date:** 2026-06-01
**Deployment Status:** Pending
**Type:** Bug Fix

---

## Overview

Fixes a bug where users (especially on mobile) would receive a 403 page after a successful login, and addresses a CSP violation on the profile page caused by an external CDN script load.

---

## Bug Fixes

### Login 403 on First Successful Attempt

`LoginRateLimitMiddleware` was returning a raw `403.html` render when an IP or username lockout was active. This caused two separate problems:

1. **Self-clearing lockout:** The after-response hook detected the middleware's own 403 as a successful login (anything that wasn't a 200 form re-render was assumed to be a success), so it deleted the lockout cache keys on every blocked request — meaning the lockout was immediately undone and the next request went through.

2. **Mystery 403 page:** Legitimate users on shared mobile carrier IPs could hit a lockout set by another device on the same NAT IP, and receive a blank 403 page with no explanation or path to recovery.

**Fix:**
- Lockout responses now redirect to `/login/?rl=30` instead of rendering `403.html` directly
- `login_view` reads the `?rl=` query param and shows a clear "Too many failed login attempts. Please try again in 30 minutes." message
- After-response hook now only clears counters on a real login success (302 redirect without `rl=` param), only increments on a failed form render (200), and ignores all other status codes (including its own lockout redirects)

**Files changed:**
- `src/middleware/security.py` — redirect instead of render for lockouts, fixed after-response hook logic
- `src/view/login_view.py` — handle `?rl=` query param and show rate limit message

### InputSanitizationMiddleware auth bypass never worked

`InputSanitizationMiddleware` was positioned before `AuthenticationMiddleware` in the middleware stack. `request.user` is not set until `AuthenticationMiddleware` runs, so the `if request.user.is_authenticated` guard that skips attack scanning for logged-in members always evaluated to `False`. All authenticated requests were being scanned unnecessarily, adding latency and false-positive risk.

**Fix:** Moved `InputSanitizationMiddleware` to after `AuthenticationMiddleware` in `settings_postgres.py`.

**Files changed:**
- `Parliament/settings_postgres.py` — middleware reorder

### Slow login on mobile

The `is_foreign_ip()` geo lookup uses a blocking HTTP call to ip-api.com. With a 4-second timeout, a slow or cold response added up to 4 seconds of latency to every login — most noticeable on mobile where IPs rotate between cell towers and cache misses are more frequent.

**Fix:** Default timeout reduced from 4 seconds to 2 seconds. A failed geo lookup returns `(False, {})` and the login proceeds normally, so this has no functional side effect.

**Files changed:**
- `src/geo_utils.py` — timeout reduced to 2s in `get_ip_geo()` and `is_foreign_ip()`

## CSP Fix — cropperjs Moved to Local Vendor

The profile page was loading cropperjs from `cdnjs.cloudflare.com`, which is not in Parliament's `script-src` allowlist. This caused a CSP violation logged to the security notification panel and blocked the profile picture cropper in strict browser environments.

**Fix:** Both `cropper.min.js` and `cropper.min.css` downloaded and saved to `static/vendor/`. Profile template updated to use `{% static %}` references.

**Files changed:**
- `static/vendor/cropper.min.js` — new file (vendored from cdnjs, v1.6.1)
- `static/vendor/cropper.min.css` — new file (vendored from cdnjs, v1.6.1)
- `templates/profile.html` — CDN references replaced with `{% static 'vendor/cropper.min.*' %}`

## Deployment Notes

Run `collectstatic` and purge Cloudflare cache — new static vendor files need to be served.

```bash
python manage.py collectstatic --noinput
```

Then purge cache in Cloudflare dashboard → Caching → Purge Cache.
