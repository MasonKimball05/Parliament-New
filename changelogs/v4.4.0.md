## Songbook: what "Play all" needs

The app's songbook can now keep a song playing after you leave its page, play
every recording one after another ("Play all"), and play in the background and
from the lock screen (parliament-mobile; it needs a new app build, since
background audio is a native setting). To queue the recordings from the list,
the list API (`GET songbook/`) now gives each song its `audio_ext` and
`updated_at`, as the song's own endpoint already did. Older app builds ignore
them; the new app falls back to `.mp3` without them.

**Test:** `test_songbook_quotes.test_list_detail_and_audio` checks both fields.

## Quick Links on the app's Home

Feedback from the chapter: the website Home's Quick Links are well liked. The
app's Home now has them too, as a wrapping row of buttons at the bottom of
Home, after the announcements (parliament-mobile).

`GET home/` gains `quick_links`: the website's links in its order, each with
`key`, `label`, site `path`, an `icon` (SF Symbol and Material names), a
`tone` (Vote is highlighted, Report a bug and Feedback amber, Slating purple)
and a `badge` (Vote's count of ballots waiting). The list is
`views_home.QUICK_LINKS`, so a link added there reaches the app without an app
update. The website's rules apply: a page the member couldn't open (its page
toggle off, or no access) is left out; GroupMe is for officers and chairs;
Slating shows while a period is active, to everyone but pledges (cached for a
minute so Home's query count stays flat). Directory and Documents are left out
(they're the app Home's big shortcuts), and so is the admin site. Songbook is
added. The app opens each natively where it has the page, else in the web view.

**Tests:** `QuickLinksTests` (3) in `test_home_and_notifications.py`.

every push since at least 10-23-26, with two findings in code that hadn't
changed (CI installs the latest bandit, which is stricter):

## Every Quick Link opens a native screen

The seven Quick Links that still opened the website in the app's web view now
have native screens (parliament-mobile), each on a new API that calls the
same code as the website page. Where a view did everything inline, its logic
moved into helpers the web view and the API both call, so the two can't
drift; the web pages behave as before.

| Page | API (`/api/mobile/v1/`) | Web view now built from |
|---|---|---|
| Preferences | `preferences/` (GET, PATCH) | `view/preferences.py` helpers |
| My work (legislation history) | `legislation/history/`, `…/polls/`, `…/drafts/` | `view_legislation_history.py` helpers |
| Robert's Rules | `roberts-rules/` | unchanged; see below |
| Profile | `profile/` and its photo, role history, socials, chapters, academics | `profile_view.py` helpers |
| Report a bug | `support/bug-report/` (JSON or multipart) | `bug_report.create_bug_report` |
| Feedback | `support/feedback/` | `feedback.create_feedback` |
| GroupMe (officers and chairs) | `officer/groupme/…` (8 routes) | `officer/groupme.py` action functions |

- **Robert's Rules** is data now (`src/roberts_rules_content.py`): 21
  motions and the guide's 21 sections. The web template stays hand-written, so
  `TemplateInSyncTests` reads it and fails on any heading, line, motion card
  or quick-reference cell the data doesn't match (858 lines checked). The app
  keeps it offline, for meetings.
- **My work** gains a title search (`q`), app-only; the web page has none.
- **Profile**: password, 2FA, passkeys and browser sessions stay on the
  website (they need the browser); the app shows their status.
- **GroupMe**: the access token is never returned and bot ids show only their
  last four characters.

### Photo upload in the app

`POST profile/photo/` (multipart `photo`) sets the profile picture; bug
reports already took a multipart `screenshot`. The app picks from the photo
library (expo-image-picker, a native module, so build 13 or later); on an
older build the rows still open the website.

### Fixed on the website along the way

- **Preferences wouldn't save while dark mode is off chapter-wide.** `theme`
  is a required field and the form only rendered it with dark mode on, so
  every save failed. The form now posts `theme=light` then.
- **A taken username was a 500** on the Profile page (an IntegrityError at
  save). `save_account_fields` refuses it: "That username is taken."
- **Profile picture checks never ran.** `validate_profile_picture` (JPEG,
  PNG or WebP, at most 5 MB) is a model field validator, and `save()` doesn't
  run those, so the page stored any file. `save_profile_picture` now runs it;
  the page already showed its message.
- **Feedback** now checks page, priority and request type against their
  choices and trims fields to their column lengths, as bug reports have since
  v3.51.6 (a too-long value was a 500 on PostgreSQL).
